# Open Knowledge Format (OKF) — Google's open format for agent knowledge

> Covers **Open Knowledge Format (OKF) v0.1** (Google Cloud, announced **2026-06-12**): an open, vendor-neutral format/contract for representing organizational knowledge as a **directory of markdown files with YAML frontmatter**, consumable by agents and humans. Feeds the boundaries of dimensions **11** (data/domain catalog — the strongest contact point), **2** (current architecture / docs frontmatter), **10** (memory — `log.md` convention), **12** (boundary doctrine — "the format is the contract"; knowledge × behavior layer) and the candidate **AGENTS.md / cross-tool interoperability** (OKF extends interop from *behavior* to *world-state*). Snapshot from **2026-06-29** — OKF is ~2 weeks old; treat fields and rules as moving v0.1.

## Summary

OKF formalizes the "LLM-wiki standard" into a **portable format**: a *bundle* is a hierarchical directory of `.md` files (the unit of distribution), a *concept* is exactly **one** markdown file, and the **concept's identity is the file path minus `.md`** (`tables/users.md` → `tables/users`). The YAML frontmatter reserves six fields — **only `type` is required** (a free string chosen by the producer, for routing/filtering/presentation, **with no central registry**); `title`, `description`, `resource` (URI of the underlying asset), `tags`, `timestamp` (ISO-8601) are recommended in priority order. **Producers MAY add arbitrary keys; consumers MUST preserve unknown fields.** Links between concepts are plain markdown (absolute `/tables/customers.md` or relative `./other.md`); the **relationship type is given by the surrounding prose, not by the link**. The body has no required sections, but there are conventional headings (`# Schema`, `# Examples`, `# Citations`) and two reserved files: `index.md` (directory listing) and `log.md` (chronological history).

The central design move is **"the format is the contract; the tool at each end is independently swappable"**: no schema registry, no central authority, no mandatory SDK ("if you can `cat` a file, you read OKF; if you can `git clone` a repo, you distribute OKF"). Hence the **decoupled producer/consumer model**: humans, agents from any framework (ADK/LangChain/custom) and catalog export pipelines (Dataplex, Unity Catalog, Collibra) **produce**; static servers, KM UIs (Obsidian/Notion/MkDocs), LLMs loading files into context, search indexes, and graph viewers **consume**. **Conformance is minimal and bundle-side** (parseable frontmatter + non-empty `type` on every non-reserved `.md`) and **consumption is deliberately permissive**: consumers **MUST NOT reject** a bundle for a missing optional field, unknown `type`, extra key, broken link, or missing `index.md` — everything beyond the two hard rules is "soft guidance", so the bundle remains useful "as it grows, is refactored, and is partially generated by agents".

Positioning among adjacent standards (the most relevant axis for the skill): OKF **stacks**, it does not compete. It differs from **AGENTS.md by SCOPE** — *AGENTS.md says how the agent behaves (one repo); OKF says what exists in the world (all org knowledge)*; the AGENTS.md itself may point "see the OKF bundle at /knowledge". Composes with **llms.txt** (signpost) and **schema.org** ("layers of the same cake"). Against **RAG**: instead of re-deriving knowledge from raw chunks at query time, OKF stores **curated, versioned, cross-linked** concepts that the agent reads and updates directly — "lives in version control alongside the code it describes". The reference CLI **`kcmd` is already an MCP server** (pull/push/list/lookup/modify) — meaning OKF (format/world-state) and MCP (transport) are distinct and composable layers. The `quenching-management` skill is, structurally, a close neighbor: it already uses markdown-directory-with-frontmatter, concept-per-file, and identity-by-path (especially in `docs/catalog/`), with the difference that it is a **prescriptive method** (canonical taxonomy + trust frontmatter) where OKF is a **permissive format** (one field).

The sharpest critique (Marc Bara, "A Standard, or Just a Folder?") **does not contradict any fact**: it concedes the format is open and neutral, but argues that OKF **standardizes the container/structure, not the semantics/vocabulary** — since `type` is not registered, interoperability "consumed without translation" is real only at the **structural layer** and remains open at the **semantic layer** in v0.1. Two additional frictions are noted: (1) a possible parser-vs-spec gap (the reference parser reportedly required ~4 fields while the spec requires only `type`); (2) "ecosystem gravity" — examples pull toward BigQuery/Dataplex despite formal neutrality.

## Sources

### **[How the Open Knowledge Format can improve data sharing — Google Cloud Blog](https://cloud.google.com/blog/products/data-analytics/how-the-open-knowledge-format-can-improve-data-sharing)** — _official Google Cloud · 2026-06-12_

Canonical announcement (authors Sam McVeety and Amir Hormati). Defines the three principles: **minimally opinionated** ("OKF requires exactly one thing from each concept: a `type` field… the spec defines the interoperability surface, not the content model"), **producer/consumer independence** ("the format is the contract; the tool at each end is independently swappable") and **format, not platform** ("will never require a proprietary account or SDK to read, write, or serve"; "no new runtime, no mandatory SDK").

**Key facts:**
- Problem: the knowledge that models use lives fragmented across catalogs with proprietary APIs, wikis, drives, code comments, and "in the heads of a few senior engineers"; "every agent builder solves the same context-assembly problem from scratch".
- Use cases: tables/datasets, metrics ("weekly active users"), playbooks/runbooks, APIs and deprecation notices, join paths.
- "Lives in version control alongside the code it describes"; the team curates the content "and manages it like code" (cites Karpathy: LLMs don't get bored with wiki bookkeeping).
- Reference implementations (PoC, not mandatory): **enrichment agent** (scans BigQuery dataset → writes one concept per table → 2nd LLM pass crawls docs and adds schemas/joins/citations) and **static HTML viewer** (graph view in a single file). Sample bundles: GA4, Stack Overflow, Bitcoin.

### **[knowledge-catalog/okf/SPEC.md — GoogleCloudPlatform (authoritative spec)](https://github.com/GoogleCloudPlatform/knowledge-catalog/blob/main/okf/SPEC.md)** — _official / open spec · v0.1 · accessed 2026-06-29_

The source of truth. Defines Bundle ("self-contained hierarchical collection of knowledge documents; the unit of distribution"), Concept ("a unit of knowledge; a markdown document") and Concept ID ("the file path within the bundle, without the `.md` suffix").

**Key facts:**
- Frontmatter: `type` **REQUIRED**; `title`/`description`/`resource`/`tags`/`timestamp` recommended in priority order. "Type values are not centrally registered… consumers MUST tolerate unknown types." Producers may add keys; consumers must not reject them.
- Linking: absolute (`/`) or relative; "a link from A to B asserts a **relationship**; the type of the relationship (parent/child, references, joins-with, depends-on) is given by the surrounding prose, not by the link".
- Body: no required sections; "prefer structural markdown — headings, lists, tables, code blocks — over free prose"; conventional headings `# Schema`, `# Examples`, `# Citations`.
- Reserved: `index.md` (§6, directory listing), `log.md` (§7, chronological history).
- Conformance (§9): (1) every non-reserved `.md` has parseable YAML frontmatter; (2) every frontmatter has a non-empty `type`; (3) reserved files follow their structure when present. "Consumers MUST tolerate broken links… MUST NOT reject for a missing optional field, unknown `type`, extra key, broken link, or missing `index.md`… remaining constraints are soft guidance. This permissive model is intentional."
- "No schema registry, central authority, or mandatory tooling"; "diffable in version control". Versioning `<major>.<minor>`.

## How this feeds the method's evolution

OKF is simultaneously a **validation** of choices the skill has already made and a **new adoption frontier**. Mapping by dimension:

- **Dim 11 (catalog) — strongest contact point and greatest leverage.** `docs/catalog/<system>/<catalog>/<schema>/<table>.md` **is already** a de facto OKF bundle: concept-per-file, identity-by-path, half-generated / half-curated (= OKF's "export pipeline-generated bundle"), `# Schema` = the column table from the `_table.md` template. **Candidate evolution (additive, low risk):** make the `_table.md`/`_schema.md`/`_system.md` templates **OKF-conformant** — `type` (e.g., `Table`/`Schema`/`System`), `resource` (the table's FQN/URI in Unity Catalog), `timestamp`; OKF's consolidated `index.md` maps to the `schema.md` (1-line-per-table index); the reserved `log.md` provides a home for the catalog's **change history**. Gain: the curated catalog becomes consumable by ANY OKF consumer (Obsidian, the static viewer, `kcmd`/MCP, an agent from another org) **for free**, without the method giving up its curation.
- **Dim 2 / frontmatter — REQUIRED×RECOMMENDED discipline + preserve unknown keys.** The skill's `docs-front` is **more** prescriptive than OKF (it requires `audience`+`authority`, which OKF doesn't have — and that is the right choice: it makes trust verifiable). The transferable lesson is **not** "go minimal"; it is (a) explicitly classifying each frontmatter field as **required × recommended** (in priority order, as OKF does) to combat bloat, and (b) adopting the rule **"preserve / do not reject unknown keys"**, so that installed frontmatter **coexists** with pre-existing frontmatter in the target (interop with AGENTS.md/OKF ecosystems) rather than conflicting with it.
- **Dim 12 (boundaries) — "the format is the contract" and the knowledge × behavior layer.** OKF gives a clean framing of the boundary doctrine: **AGENTS.md = behavior, OKF = world-state**. This mirrors exactly the skill's internal boundary: CLAUDE.md/skills (behavior) × `docs/`+`docs/catalog/` (world-state). Hence the sharp rule: **be prescriptive about the INTEROP SURFACE (the contract/frontmatter), permissive about the rest** (tolerate partial/agent-generated content; no hard-fail). This **tempers** the prescriptive reading without weakening it — and the method already does "proposes, never renames without OK", which OKF validates.
- **Dim 10 (memory) and Dim 5 (ADR) — `log.md` convention.** The reserved `log.md` (append-only chronological history per bundle) generalizes what the `audit-config-change.py` hook already does (append-only audit trail) to the knowledge base; it is a concrete home for agent-maintained memory/decision history.
- **Candidate "AGENTS.md / interop" — extending from behavior to knowledge, via a `quenching-to-okf` export.** The skill already carries `claude-to-agents` (CLAUDE.md→AGENTS.md, **behavior** interop). The exact analog is an **export step/payload** that serializes `docs/`+`docs/catalog/` as an **OKF bundle** (**knowledge** interop), making the repo's knowledge consumable by non-Claude agents and the OKF ecosystem (viewer, `kcmd`/MCP). Field mapping: `authority:current` → an OKF `type`; `audience`/`source`/`maintainer`/`updated` travel as **extra keys** (OKF preserves them). This candidate **expands** the AGENTS.md boundary already in the backlog.

**What NOT to adopt (boundary — consistent with the method's rejection discipline):** (1) do **not** dilute the prescriptive canonical taxonomy to chase OKF's minimalism — the "standardizes container, not semantics" critique shows that OKF **leaves open** precisely the semantic interop that the skill's prescription resolves; (2) do **not** create a dependency on Google tooling — adopt **principles + optional export**, never an SDK/runtime; (3) treat OKF as a **moving target** (v0.1, ~2 weeks old, with a reported parser-vs-spec gap) — cite as a snapshot, revalidate before any round that materializes it.
