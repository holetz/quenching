# Claude Code Hooks — deterministic lifecycle automation

> Covers the programmatic lifecycle control mechanisms of Claude Code (PreToolUse, PostToolUse, UserPromptSubmit, Stop, SessionStart, SubagentStop, Notification, PreCompact and 20+ other events); directly feeds **Dimension 8 (hooks)** and informs boundaries **12 (each piece of information with one canonical home)**, **13 (house conventions)** and **14 (behavioral guardrails)**.

## Synthesis

Hooks are shell commands (or HTTP calls, LLM prompts, or sub-agents) configured in Claude Code's `settings.json` that trigger automatically at fixed points in the lifecycle — before a tool runs (`PreToolUse`), after it finishes (`PostToolUse`), when the user submits a prompt (`UserPromptSubmit`), at the end of each turn (`Stop`), when starting or resuming a session (`SessionStart`), before context compaction (`PreCompact`), when a sub-agent terminates (`SubagentStop`), among many others. The fundamental difference from instructions in CLAUDE.md or skills is the deterministic guarantee: the harness executes the hook logic regardless of whether the model chooses to follow it. This transforms hooks into the most reliable policy enforcement layer of the system, while CLAUDE.md provides probabilistic guidance and permissions configure static limits.

Communication between hook and harness occurs via three channels: stdin receives the event JSON (with fields like `tool_name`, `tool_input`, `session_id`, `cwd`); stdout returns structured JSON with decisions (`permissionDecision`, `updatedInput`, `additionalContext`); and the exit code carries control semantics — 0 indicates no objection (normal flow continues), 2 blocks the action and sends stderr as feedback to the model, any other code does not block but logs the error in the debug log. A critical detail: exit 2 and JSON do not combine — the harness ignores stdout JSON when the exit code is 2; use exit 0 with JSON for rich decisions. For `PreToolUse`, the `permissionDecision` values are `allow`, `deny`, `ask`, and `defer`; the `deny` from any hook wins over the others in parallel resolution (most restrictive rule). PreToolUse hooks block even in `bypassPermissions` mode, making them the only mechanism that cannot be bypassed by the user.

Matchers filter which calls trigger each hook. Simple strings or alternatives with `|` do exact matching on the tool name; any other sequence is treated as a JavaScript regex. The `if` field (requires v2.1.85+) adds filtering by arguments via permission rule syntax (e.g., `Bash(git *)`), avoiding unnecessary process spawning. MCP tools use the `mcp__<server>__<tool>` pattern, requiring regex like `mcp__memory__.*` to cover all tools from a server. Hooks configured in `.claude/settings.json` are shared by the repository; `~/.claude/settings.json` applies to all user projects; `settings.local.json` is gitignored; and managed settings (organization) have maximum priority and can activate `allowManagedHooksOnly` to restrict hooks to only admin-approved ones.

From a security perspective, two risks deserve special attention. First, the hook executes with the user's full shell privileges — configuring hooks in repositories is treated as executable code, not inert configuration. Until 2025-2026, a real vulnerability allowed `.claude/settings.json` from a cloned repository to trigger hooks before the trust prompt was shown to the user; the fix was to defer reading and executing project configuration until after trust acceptance. Second, HTTP hooks exposed credential exfiltration risks; the `allowedEnvVars` field in the hook definition and `httpHookAllowedEnvVars` in managed settings limit which environment variables can be interpolated in headers. Audit logs generated by hooks may contain secrets, requiring deliberate retention and access policies.

For a skill that AUDITS the knowledge surface of a repository (dimension 8 — hooks), hooks offer three direct capabilities. The `InstructionsLoaded` event (fires when CLAUDE.md or `.claude/rules/*.md` is loaded) can capture which instruction file was read and at what time, producing a log that evidences whether the knowledge surface is being correctly consumed. The `SessionStart` event with matcher `compact` re-injects critical context after compaction — an essential mechanism to ensure that house conventions, FQNs, and behavioral guardrails are not lost when context is compressed. The `ConfigChange` event monitors changes to configuration files during the session, allowing an audit trail of unauthorized changes to the knowledge surface itself. Combined, these three hooks create a continuous audit cycle: what was loaded, what survived compaction, and what was modified.

## How it feeds the method evolution

- **Dimension 8 (hooks) — absence smell:** the audit skill should verify whether `.claude/settings.json` defines at least (a) an `InstructionsLoaded` hook to log which CLAUDE.md was loaded, (b) a `SessionStart` hook with matcher `compact` to re-inject critical context after compaction, and (c) a `ConfigChange` hook for configuration change audit trail. Absence of any one is a concrete smell.

- **Dimension 8 (hooks) — sharper «good» criterion:** a hook is well-configured when: (1) uses `if` field to filter by arguments instead of leaving the logic in the script, (2) uses exit 0 with structured JSON for rich decisions and exit 2 only for simple blocks with message in stderr, (3) operates under 500ms on the critical path (uses `async: true` for logging), and (4) includes `stop_hook_active` check in Stop hooks to avoid loops.

- **Dimension 12 (boundary doctrine) — single canonical home for policy enforcement:** the boundary is clear — CLAUDE.md is the home for guidance/culture (probabilistic); permissions.allow/deny is the home for static rules; hooks are the home for dynamic and deterministic enforcement. Moving from CLAUDE.md to a hook is the correct action when the rule MUST be guaranteed (e.g., do not edit generated files, do not expose secrets). The skill should detect rules in CLAUDE.md that should be hooks.

- **Dimension 14 (behavioral guardrails) — detection command:** `grep -r "Never\|NEVER\|never edit\|don't commit\|don't expose" .claude/CLAUDE.md` and equivalents — any imperative instruction that should be deterministically enforced is a candidate for migration to a PreToolUse or PostToolUse hook.

- **Dimension 8 (hooks) — security workflow step:** when auditing a repository that will be cloned by others, verify that hooks in `.claude/settings.json` do not execute sensitive logic at startup before the trust prompt has been accepted — the pre-trust vulnerability was fixed in the harness, but the defense-in-depth pattern requires that SessionStart hooks be idempotent and non-destructive.

- **Dimension 7 (sub-agents) — new dimension to consider:** `SubagentStart` and `SubagentStop` hooks (with matcher by agent type) allow the knowledge management skill to audit the sub-agent lifecycle — injecting context at start (`SubagentStart` → additionalContext) and validating results at termination (`SubagentStop` → block decision if validation fails). This is a boundary not covered by the current 14 dimensions that deserves elevation.
