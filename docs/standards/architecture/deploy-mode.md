# Deploy mode — install the surface in a target repository

<!-- rules -->

## Two modes, one source

Deploy is the only mode: since [ADR 0017](../../decisions/0017-install-only-by-deploy.md) no
plugin carries the command surface, and `cq deploy` materializes the selected surface from
`quenching` in a target repository. It never edits a target's knowledge or code by itself.

`cq deploy` is a **top-level command**, not a front. `delivery` and `ops` keep their own meaning
for deployment; this verb installs the tool surface. It never invokes a model, never aligns
`/docs/`, never chooses a provider and never runs a target pipeline.

## The target layout

| Path | Kind | Owner |
| --- | --- | --- |
| `AGENTS.md` | instructions | target; seeded only when absent |
| `.agents/quenching.json` | configuration | target; seeded only when absent |
| `.vscode/settings.json` | VS Code workspace settings: the generated trees out of search and the semantic index, and room for long agent runs | target; seeded only when absent and `shared.workspace.vscode` is true |
| `.agents/skills/quenching-<command>/SKILL.md` | one-segment skills | generated |
| `.agents/quenching/` | vendored payload: runtime, references, templates, commands, agent protocols | generated, read-only |
| `.agents/.quenching-deploy.json` | manifest: version, modules, profiles, hashes, skills | generated; one blank line separates each entry of `files` |
| `.claude/skills/<name>/` | Claude bridge, byte copy of every skill | generated |
| `.agents/rules/<name>.md` | path-scoped rule source: `paths:` globs and a markdown body | target; the deploy projects it, never owns it |
| `.claude/rules/<name>.md` | Claude rules, the source's `paths:` frontmatter | generated when the `claude` harness is selected |
| `.github/instructions/<name>.instructions.md` | Copilot path-scoped instructions, the same globs as one quoted `applyTo:` | generated when the repository declares `shared.projections: ["github"]` |
| `.claude/agents/quenching-<name>.md` | Claude subagents | generated when the `claude` harness is selected |
| `.opencode/agents/quenching-<name>.md` | OpenCode subagents, `mode: subagent` | generated when the `opencode` harness is selected |
| `.github/agents/quenching-<name>.agent.md` | Copilot subagents, the native custom-agent format | generated when the repository declares `shared.projections: ["github"]` |
| `.mcp.json` | Claude Code project MCP registration | target; the `quenching` entry merged when the `claude` harness is selected |
| `opencode.json` | OpenCode MCP registration, subagent depth and sibling directories | target; the `quenching` entry, `experimental.subagent_depth` and the `external_directory` allows merged when the `opencode` harness is selected |
| `CLAUDE.md` | legacy pointer to `AGENTS.md` | never created; removed only by `--prune-legacy` |
| `.claude/commands/`, `.claude/references/` | legacy layout | refused; run `cq components migrate` first |

`AGENTS.md` is read natively by Claude Code 2.1.277+ when no `CLAUDE.md`/`CLAUDE.local.md` exists
in the working directory or above it (§Surface translation below). Claude
does **not** read `.agents/skills/`; the generated `.claude/skills/` bridge is the only reason it
is present. A repository therefore never authors `.claude` for quenching.

**The hash manifests merge textually.** `.agents/.quenching-deploy.json` and `.claude/skills/.generated-files.json`
are tracked and regenerated by every change to the source, so two parallel branches rewrite them
together. Both are written by `dumps_hash_manifest`, which puts one blank line between the entries
of `files`: git treats changes in neighbouring lines as a conflict and changes with an untouched
line between them as a clean merge, so only two branches that change the same file's hash still
conflict (and its deployed copy conflicts with it). JSON admits the blank lines, so every reader
parses the file unchanged.

## Selection and the manifest

`--modules` selects principal modules, not fronts. `core` means `specs,git,knowledge,components`
(the modules `quenching-specs`, `quenching-git`, `quenching-knowledge` and `quenching-components`; the
alias `align` is `knowledge,components`); `specs` is always included because it
owns the one `cq`. `--profiles` overrides the `shared.profiles.installed` seed; otherwise the
fronts of the selected modules are derived. `specs` is kept in that list as the provider axis.

A target that already carries a manifest reuses its recorded `modules`, `harnesses`, `runtime` and
`profiles` for every flag the caller omits, so `cq deploy --write` upgrades what is installed
instead of reinstall `core`. An explicit flag always wins; the manifest is a default, not an
authority over the plan.

The manifest is the authority for what deploy owns. A generated file must be listed before it may
be overwritten; a file at a generated path that the manifest does not own is a conflict
(`ct-deploy-unowned`, exit 2) and nothing is written. Drift is content and the executable bit —
the only part of the mode git carries — so a checkout that creates files group-writable
(`umask 0002`) is clean. A target's own skills, references, `AGENTS.md` and configuration are never
in the manifest's write set.

The plan is **three-way**: the bytes on disk, the sha256 the manifest recorded, the new bytes. An
owned file that still holds its recorded bytes and differs from the new ones is an `update` (the
source moved on); one whose bytes no longer match the record is `edited` (someone changed it in the
target). `--check` reports both (exit 1). `--write` applies updates but refuses an `edited` file
(`ct-deploy-edited`, exit 2) and writes nothing, because regenerating it would discard work; the
edit belongs in a target-owned skill or in the quenching source, and `--force` discards it on
purpose. A manifest entry without a hash cannot tell the two apart and is read as `update`.

A generated path is written only when it **resolves inside the target**: a symlinked directory that
carries it elsewhere is a conflict in the plan, never a write through the link.

The manifest records the `version` that wrote it. When it differs from the source's, the plan
carries `installedVersion` and a warning naming both, so release lag reads apart from content drift.

## Remove

`cq deploy --target <repo> --remove` plans removing the whole surface (exit 1 while there is
something to remove); `--remove --write` does it. Each owned file that still holds its recorded
bytes is deleted, and directories it leaves empty go with it; an `edited` file is **kept** and
reported, becoming the target's own file, unless `--force`. Only the hooks and keys a past deploy
merged leave `.claude/settings.json`, which is deleted only when that leaves it empty. The manifest
goes last. Seeds — `AGENTS.md`, `.agents/quenching.json` — the target's own skills and `/docs/`
are never owned, so never removed. A target without a manifest refuses (`ct-deploy-remove`, exit 2):
nothing is owned there.

## Runtime

`--runtime vendor` copies the selected Python packages and the entry point into
`.agents/quenching/assets/bin/` and **generates** the launcher `.agents/quenching/bin/cq` (with its
`bin/cq.cmd` for Windows), a shim that re-executes `../assets/bin/cq`; it is offline and
self-contained. The source ships no `bin/` of its own. `--runtime uvx` omits the
packages and writes `.agents/quenching/bin/cq` as a shim pinned to the release tag, so the target
needs network and `uvx` at call time.

Every deployed command body uses the target-local path `.agents/quenching/bin/cq`; the generated
grant is `Bash(.agents/quenching/bin/cq:*)`.

## MCP registration

Deploy always registers the whole quenching MCP server, with no declaration. It writes the
`quenching` entry into one file per selected harness — `.mcp.json` for `claude` (which the GitHub
Copilot harness reads too), `opencode.json` for `opencode` — with
the same argv: `<command...> .agents/quenching/assets/bin/cq mcp`, every catalogued tool of the
pillars present. `shared.mcp` (`{mount: "all"|"specs"|"core"|<pillars>, command: [...]}`, see
[plugin-configuration.md](../workflows/plugin-configuration.md#the-sharedmcp-block)) only overrides
the mount and the Python prefix: `mount: "specs"` registers the specs-only
`<command...> .agents/quenching/assets/bin/cq specs mcp` instead, `mount: "core"` registers
`<command...> .agents/quenching/assets/bin/cq mcp --only specs,git,components` (the pillars a spec
cycle reaches through MCP, the `MOUNTS` table in `mcp/catalog.py`), and a comma list of pillars
registers exactly those. The name is expanded in the argv, so the registered file says which pillars
it publishes, and `cq mcp --only` refuses a pillar the router does not have (`ct-mcp-only`). The
mount comes from the declaration alone, never from the manifest, so a target deployed under the old
`specs` default moves to the whole server on its next `--write`.

**The prefix is a direct interpreter, found without pinning a version.** Declared
`shared.mcp.command`, else the `mcp.command` the last deploy recorded in the manifest (so two
machines never flap), else the first of `python3`, `python` and `py -3` that runs a Python 3.11 or
later here, else `python3`. A prefix through `uv` or `uvx` never reaches the server: `uv run`
resolves the project before the server answers, which is what timed a harness out at 30 s. The MCP
server and the Claude Code hooks run one and the same direct prefix
([hooks.md](../automation/hooks.md)), recorded as `mcp.command` and `claudeSettings.command`, and
the deploy warns when it replaced a `uv` one. `initialize` plus `tools/list` of the whole server
answer within one second (`quenching/tests/test_quenching_mcp_startup.py`).

**The registered server closes the CLI door it replaces.** With the whole server (`all`) registered
and `shared.mcp.cliFallback` absent or `false`, the grants a harness reads — a skill's
`allowed-tools`, a Claude Code agent's `tools:`, an OpenCode agent's `permission.bash` — carry the
MCP tools a `Bash(cq <prefix>:*)` covers *instead of* that grant: only the verb paths under the
prefix with no tool survive as shell grants, on both launchers, collapsed to the shortest path with
nothing covered below (`coverage.cli_residue`). The `coverage.EXCEPTIONS` verbs (`deploy`,
`specs serve`, …) stay shell; `specs claim take` is reached by no grant, tool or shell. A prefix
that names no verb is kept whole, so the narrowing never widens and never guesses. The payload's
`.agents/quenching/agents/` copy keeps the source grants, because a target-local deploy re-reads
it; `cliFallback: true`, a narrower mount (`specs`, `core`, a list) and a runtime that registers no
server keep both doors. A narrower mount narrows no door but does filter the names: the MCP tools a
grant enumerates are only the ones the mount publishes (`mcp_tools(names, mount)`), so a skill's
`allowed-tools` and an agent's `tools:` never name a tool the server does not serve. The narrowed
residue is computed against the mount too (`coverage.cli_residue(prefix, mount)`): a verb whose MCP
tool the mount hides keeps its shell grant, so a pillar outside the mount never loses both doors.

**The files stay the user's: merged, never owned.** Like `.claude/settings.json`, they are not in the
manifest's `files`; the manifest records `mcp` and `mcpFiles`, and only the `quenching` entry is the
deploy's. JSON keeps every other key and entry (`$schema` is added to `opencode.json` only when
absent); TOML swaps only the `[mcp_servers.quenching]` table. A file that is not a JSON object (a
JSONC `opencode.json`, say) is left untouched and reported as a warning. `--check` reports a merge
that would change a file as `mcp` drift; selecting fewer harnesses, or `--remove`, takes the entry
out of the files it left and deletes a file only when nothing else remains in it.

**The runtime.** The command points at the vendored entry point, which a `uvx` runtime omits: with
a declared `shared.mcp` that runtime refuses (`ct-deploy-mcp`); without one it registers nothing
and warns.

**The registered server is approved, so it starts without a prompt.** With `claude` among the
harnesses and the server registered, deploy adds `quenching` to `enabledMcpjsonServers` in
`.claude/settings.json`, keeping every other name. Claude Code honours that project approval only
in a trusted folder (code.claude.com/docs/en/mcp, "Project server approvals and workspace trust").
A `disabledMcpjsonServers` that names `quenching` stays as the user wrote it and becomes a warning.
The manifest records `claudeSettings.mcpjson` only when deploy added the name, and removal takes
out only that name.

**OpenCode gets the depth and the sibling directories.** With `opencode`, the `opencode.json`
merge also writes:

- `experimental.subagent_depth: 4`, the conductor → orchestrator → runner → child chain (OpenCode
  defaults to 1). A higher project value stays.
- `permission.external_directory` set to `allow` for exactly two patterns: the slots
  (`<parent>/<repo>-slot-*`) and the sibling store (`<primary>.*`). Both come from the git common
  directory, so a deploy run inside a slot writes the same patterns. They are written with `~/`
  when under the home directory. A target outside git gets neither.

`--check` reuses the depth and the patterns the manifest records (`opencodeConfig`) instead of
deriving them again: both name the deploying machine's global config and checkout, so a committed
`opencode.json` read on another machine is not drift. `--write` derives them for the machine it
runs on.

Nothing else is granted. The permission uses the V1 object form, which OpenCode still reads and
which the generated agents use.

A project `experimental` block replaces the user's global one instead of merging with it
(anomalyco/opencode#60410). So when the global config (`$OPENCODE_CONFIG`, then
`$XDG_CONFIG_HOME/opencode/`, read as JSONC) sets an `experimental` key that the project lacks,
deploy writes no depth and warns with the keys and the line to add by hand. A project block that
already exists hides nothing new, so the depth goes into it.

The manifest records what was written as `opencodeConfig`. A later run takes that out first. A
value still equal to the recorded one leaves when the harness is dropped or on `--remove`.

## The `.claude/settings.json` merge

With `claude` among the harnesses, deploy installs the hooks of the selected modules into the
target's `.claude/settings.json`, which stays the user's file, as the MCP harness files do: it is
merged, never owned, so it is not in the manifest's `files`.

- **Own entries only.** An entry is quenching's when its `command` points under
  `.agents/quenching/assets/hooks/`; that path is the marker, valid even without a manifest.
  Everything else in the file (keys, groups, hooks, order) is left as written. A wanted entry that
  already exists is updated in place; a missing one is appended in a new `{matcher, hooks}` group.
- **`attribution`.** Deploy writes `commit: ""` and `pr: ""` only for keys that are absent. A value
  the user set stays and becomes a warning, not drift. Removal deletes only the keys that are still
  `""` and that the manifest records (`claudeSettings.attribution`) as written by deploy.
- **`--check`.** The merge result differing from the file is `settings` drift (exit 1).
- **Removal.** Selecting fewer modules drops the hooks of the module that left; a harness list
  without `claude` (`opencode`, `none`) wants nothing, so only deploy's own entries leave.
  A file reduced to `{}` by that removal is deleted.
- **Refusal.** Invalid JSON, a root that is not an object, or `hooks` / `hooks.<event>` of the
  wrong type is `ct-deploy-settings` (exit 2) and nothing is written. A successful merge rewrites
  the file once with two-space indentation; later runs are idempotent.

## The `.vscode/settings.json` seed

The VS Code workspace settings that keep the flow quiet are a **seed**, opted in by the
repository's own `shared.workspace.vscode` (`true`/`false`, scope `project`, read from the
repository document and never from the merged envelope, so the file does not vary by machine). The
key is off by default: a target that does not use VS Code never receives the file.

- **The block.** `files.exclude` for `.agents/quenching`, `.claude/skills`, `site` and
  `site-source`, all root-relative, plus `chat.agent.maxRequests: 100`. `files.exclude` is the
  setting that excludes from the Explorer, from text search and from the semantic index; the
  client's `search.exclude` would only narrow text search and grep. The default ceiling is 25 and
  the long flows (`execute`, `orchestrate`, `autopilot`) need more. `common/workspace.py` is the one
  source of the block, the snippet and the per-key report.
- **Created only when absent.** The file is a seed like `AGENTS.md`: it is written only when the
  target does not carry one, it is not listed in the manifest's `files`, `--check` does not compare
  its contents, and `--remove` never deletes it. An edit made in the target survives every later
  deploy.
- **`--check`.** A declared key with no file is a `seed` change (exit 1) until the first write; a
  file that exists is never drift, whatever it carries.
- **Suggestions, never a rewrite.** `cq deploy` reports three cases as `suggestions`, which are
  advice and never a drift finding: a `.vscode/` workspace that does not declare the key, a declared
  seed whose file lacks a recommended key or carries a lower ceiling, and a file that cannot be read
  as JSONC. The deploy never edits an existing `.vscode/settings.json`; rewriting it would discard
  the JSONC comments and formatting that belong to the user.
- **Reporting.** `cq doctor` prints one `workspace:` line when the file exists, when the key is
  declared or when the target carries a `.vscode/` directory, and `cq doctor --workspace` prints the
  per-key state and the block. Both only report: neither writes, and a missing key is information,
  never a failed prerequisite.

## What deploy does not do

- It does not install `/docs/` or call an align; the target runs its own
  `quenching-knowledge` skill (flow `align`) after the surface exists. `AGENTS.md` names that next step when the bundle is absent.
- It does not touch `.claude/settings.local.json` or the user's `~/.claude`, and edits
  `.claude/settings.json` only through the merge above.
- It does not choose the specs backend, license, release provider or any product policy.
- It does not merge a content-bearing `CLAUDE.md`; the target's
  `quenching-components` skill (flow `harness-align`) owns that, and a pointer-only file is removed only on
  `--prune-legacy`.

## Surface translation

The source, `quenching/`, is written in the target dialect: `/quenching-<vertical> <flow>` ids and
`.agents/quenching` citations, with no `${CLAUDE_PLUGIN_ROOT}` and no `:` in an id
([source-layout.md](source-layout.md)). **`cq deploy`** rewrites only the frontmatter, the generated
header, the grants (and the OpenCode permissions) and the `cq.cmd` launcher; a source that still
carries a plugin-root marker or a plugin-surface id is refused. It writes a target repository's
generic layer — `.agents/skills/` (read by OpenCode), the payload under
`.agents/quenching/`, the Claude bridge under `.claude/skills/`, the rules under `.claude/rules/`,
the subagents under `.claude/agents/` and `.opencode/agents/`, and — when the repository declares
`shared.projections: ["github"]` — the Copilot projections under `.github/agents/` and
`.github/instructions/`, all from the same generic sources (§The target layout above). No Codex package, no `codex` harness ([ADR 0020](../../decisions/0020-remove-the-codex-executor-and-harness.md)) and no
user-level OpenCode distribution exist since [ADR 0017](../../decisions/0017-install-only-by-deploy.md).
A target's `.claude/commands/` is the legacy layout, which `cq components migrate` converts; the
`cq components translate` that once copied it into `.agents/` is retired, and a copy it wrote beside
its `.claude/` source is, to `migrate`, a second editable copy and a conflict for the human to settle.

`integrations/opencode-vitrine/` is outside every translation: a hand-written OpenCode Desktop GUI
plugin that carries no skill body and no generated byte ([source-layout.md](source-layout.md)).

This section retired with surface-translation.md (spec 2174, 2026-11-03): the standard that held the
translation is gone because the deploy does the translating, so the rules live beside it.

### Target repositories and the generic layer

A target repository's single editable source is the generic layer. Each artifact has one home:

| Artifact | Home | Why there |
| --- | --- | --- |
| skill | `.agents/skills/<name>/SKILL.md`, sibling files in the same folder | read by OpenCode; the name is one segment ([command-surface.md](../naming/command-surface.md)) |
| reference | `.agents/references/**` | cited by the skills beside them |
| eval | `.agents/evals/<name>/` | beside the skill it scores |
| instructions | `AGENTS.md` at the root; subfolder `AGENTS.md` loads with that folder | read natively by Claude Code 2.1.277+ and OpenCode |
| rule | `.agents/rules/<name>.md`, one flat file per rule | projected to the directories the clients read; no client reads `.agents/` itself (§Path-scoped rules) |
| configuration | `.agents/quenching.json`, `.claude/quenching.json` read as legacy ([plugin-configuration.md](../workflows/plugin-configuration.md)) | one editable file |

There is no root `CLAUDE.md` in a conformant target: Claude Code reads `AGENTS.md` itself when
no `CLAUDE.md`/`CLAUDE.local.md` exists in the working directory or above it. The Claude interface
carries only what the facts below require: `.claude/skills/<name>/` as a **generated copy** of
`.agents/skills/<name>/`; and `.claude/agents/`, `.claude/hooks/`, `.claude/settings*.json`, which
have no generic home Claude Code reads. `.claude/commands/`, `.claude/references/` and
`.claude/CLAUDE.md` do not exist in a conformant target. A pointer-only `CLAUDE.md` (`@AGENTS.md`)
is legacy, kept only for hosts before Claude Code 2.1.277, and `cq components migrate` removes it.

#### Verified facts

Probed on Claude Code 2.1.312 and OpenCode 1.18.35 (2026-10-28), with real `claude -p` sessions in
throwaway repositories against a positive control, and by reading the installed binaries:

| Question | Answer |
| --- | --- |
| Does Claude Code discover a skill only under `.agents/skills/<n>/SKILL.md`? | **No.** `.agents/skills` appears only in its Cursor importer, which copies into `.claude/skills/` |
| Does it discover a nested `.claude/skills/<a>/<b>/SKILL.md`? | **No**; only the flat sibling skill is listed |
| Does it load `AGENTS.md` alone as project instructions? | **Yes**, by default since 2.1.277 (`claude-md-or-agents-md`): with no `CLAUDE.md`/`CLAUDE.local.md` in the working directory or above it, every `AGENTS.md` and `.claude/AGENTS.md` in that path loads. With both files, only `CLAUDE.md` loads unless the setting is `claude-md-and-agents-md`. Nothing under `.agents/` is read as instructions. |
| Does it read a subagent under `.agents/agents/`? | **No** |
| Does OpenCode read `.claude/skills` and `.agents/skills`? | **Yes, both**, in that order; a repeated name logs `duplicate skill name` and the `.agents` copy wins, so the listing does not duplicate |

A newer host version may change any row; the bridge manifest records the version it was verified
against (`verifiedClaudeCode`), and a row is re-probed before the layout is relaxed.

#### The bridge

`cq components bridge --target <repo> [--write|--check] --json` copies every `.agents/skills/<name>/`
folder to `.claude/skills/<name>/` byte for byte, inserting one marker line right after the
`SKILL.md` frontmatter — `<!-- generated from .agents/skills/<name>/SKILL.md by cq components bridge;
edit the source -->`. The manifest `.claude/skills/.generated-files.json` records one sha256 per
generated file and `verifiedClaudeCode`; freshness is a byte comparison, with no aggregate digest.
`--check` exits 1 on drift (an edited copy, a new source, an orphan). A `.claude/skills/<name>/` the
manifest does not list is the human's: the bridge refuses (exit 2, `ct-bridge-unowned`) rather than
overwrite it. No symbolic link is used ([windows-support.md](../platform/windows-support.md)).

#### Migration and conformance

`cq components migrate --target <repo> [--write] --json` plans the move from the legacy layout and
applies it with `git mv`/`git rm`, preserving history: `.claude/commands/<a>/<b>.md` becomes
`.agents/skills/<a>-<b>/SKILL.md` (replacing a generated translation of the same command),
`.claude/references/**` becomes `.agents/references/**`, a hand-written `.claude/skills/<n>/` moves
to `.agents/skills/<n>/`, the old translation manifests are removed, `.claude/quenching.json` moves to
`.agents/quenching.json`, and `CLAUDE.md` content moves to `AGENTS.md`. A pointer-only `CLAUDE.md`
(`@AGENTS.md`) is removed, never recreated: Claude Code 2.1.277+ reads `AGENTS.md` directly. Moved bodies have `/a:b`
invocations rewritten to `/a-b` and `.claude/references/` citations to `.agents/references/`. A
conflict (two divergent configurations, two harness files with their own content) is reported in
the plan (exit 1), and `--write` refuses it (exit 2, `ct-migrate-conflict`) and writes nothing. A target is **conformant** when `migrate` reports an empty plan
(`conformant: true`) and `bridge --check` exits 0.

### Model pins

Deployed skills carry no model pin: `cq deploy` drops `model` and `effort` from their
frontmatter. Source Claude model pins remain intact. The shared configuration file
(`.agents/quenching.json`, or the legacy `.claude/quenching.json`) remains the configuration home.
The Codex executor and its quota guard were removed ([ADR 0020](../../decisions/0020-remove-the-codex-executor-and-harness.md)).

Import-memory may read existing Claude-format memory files as data, with the original source path
explicit.

### OpenCode agents

With the `opencode` harness selected, `cq deploy` writes each source agent to
`.opencode/agents/quenching-<agent>.md` as `mode: subagent`. No model is pinned: the source tier
and effort survive as prose. Permissions are mapped deny-only from the source `tools:` — no edit
tool → `edit: deny`, no `WebFetch` → `webfetch: deny`, no `Agent`/`Task` → the task tool off,
unrestricted `Bash` → `bash: allow`, no `Bash` → `bash: deny` — with one decided exception: scoped
`Bash(cq <verbs>:*)` grants give a `bash` map that opens with `"*": ask`, then one
`"cq <verbs> *": allow` pattern per grant, in source order, followed by one `"<command> *": allow`
pattern per scoped non-cq `Bash(<command>:*)` grant (`git worktree list`, `gh pr view`). OpenCode
applies the last rule that matches, so a catch-all written last would override every allow: the
order is the policy, and a `Bash` grant with no scope form → `bash: ask`. Only the commands the source grants are allowed, so a
read-only agent never runs `cq git push` or `cq specs record` unasked. Per-agent permission sets
beyond this mapping and hooks are not generated; they widen or reshape grants and stay a human
decision.

### Copilot agents

With `github` in `shared.projections`, `cq deploy` writes each source agent to
`.github/agents/quenching-<agent>.agent.md`: `name`, `description`, `tools`, `model`,
`reasoning-effort`, `include-custom-instructions: true` and `target: github-copilot`. The tool list
is the Claude grant re-spelled in the client's aliases — `read`, `search`, `edit`, `web`, `todo`,
`agent`, `execute`, and `quenching/<tool>` (or `quenching/*` for a bare `Bash`) — so it is never
wider than the grant the Claude projection carries; `Skill` has no alias and is dropped, and an
unmapped head refuses the deploy (`ct-deploy-source`). `model` is an ordered band of the client's
model ids derived from the source's `model`, with `effort` as `reasoning-effort`; the small tier is
refused. `include-custom-instructions` carries the repository's `AGENTS.md` into the subagent, and
`target: github-copilot` pins the schema. The key is read from the repository document only; an
unknown value refuses with `ct-deploy-projection` before anything is written. The same `github`
projection also writes `.github/instructions/` from the target's `.agents/rules/` (§Path-scoped
rules).

### Path-scoped rules

A path-scoped rule is authored once, in the target's generic layer: `.agents/rules/<name>.md`, a
flat file whose frontmatter carries `paths:` — a non-empty block list of globs — and an optional
`description`, with a markdown body. No client reads `.agents/rules/` itself; the deploy writes one
generated copy per client directory a declared client reads:

| Client | Generated copy | Gate |
| --- | --- | --- |
| Claude Code | `.claude/rules/<name>.md`, the same `paths:` list | the `claude` harness is selected |
| VS Code + GitHub Copilot | `.github/instructions/<name>.instructions.md`, the same globs in one quoted `applyTo:` | the repository declares `shared.projections: ["github"]` |

The projection translates the frontmatter and nothing else: `paths:` stays a list in the Claude
copy, and the Copilot copy joins the same globs with commas into the client's quoted scalar form.
`description` crosses both. A source with no frontmatter, no `paths:`, an inline `paths:`, an empty
or non-list item, an unknown key, or a file name that is not a flat slug refuses the deploy
(`ct-deploy-source`) before anything is written: an always-on instruction belongs in `AGENTS.md`,
which every client reads.

The copies are generated with the deploy header and their hashes are in the manifest; the source
never is. `--check` reports an edited copy as drift, `--write` refuses it (`ct-deploy-edited`), and
removing a source — or the `github` projection — deletes the copy on the next `--write`. A copy the
manifest does not own is `ct-deploy-unowned`, never overwritten; `cq components migrate` moves a
target's tracked `.claude/rules/**` to `.agents/rules/**` first, skipping the copies the deploy
already owns, and reports two editable copies as the usual conflict.

## Verify

```bash
cq deploy --target . --modules core --check --json   # 0 clean, 1 drift, 2 refusal
cq deploy --target . --remove --json                 # the removal plan; --write applies it
python3 .agents/quenching/bin/cq --version
python3 .agents/quenching/bin/cq components status --json
python3 .agents/quenching/bin/cq components bridge --target . --check --json
```

The target's `components` surface excludes the skills listed in the deploy manifest and reports
them as `generated`; only the target's own skills are audited.
