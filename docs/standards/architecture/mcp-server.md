# The quenching MCP server

<!-- rules -->

## One protocol, two mounts

`cq mcp` serves the available pillars and plugin references over stdio as `quenching`.
`cq specs mcp` remains the specs-only mount. Both use `quenching/mcp/server.py` for JSON-RPC,
size guards, elicitation and in-process dispatch; the specs tool names and schemas stay compatible.
The Claude plugin registers `quenching` from its own `.mcp.json`
(`.agents/quenching/assets/bin/cq mcp`); a deployed target instead gets the file generated by
`cq deploy`, which registers the whole server (`cq mcp`) by default and merges it into the target's
own file (`shared.mcp` only overrides the mount — `specs` for the specs-only one — and the Python
prefix;
[deploy-mode.md](deploy-mode.md#mcp-registration)). A harness that reads neither manifest launches
`cq mcp` itself.
The `mcp` package belongs to `quenching-specs`, under [source-layout.md](source-layout.md).

The workspace is the launch cwd or launch-time `--root`. One call may name another tree with
`root`, which every tool takes: the CLI's `--root`, an existing directory, relative to the
workspace; the call runs with it as the verb's `--root` and as its cwd, and anything else is a
`mcp-bad-arguments` refusal.
Each call isolates stdin and captures stdout/stderr, restores cwd and stdin in `finally`, and turns
`SystemExit` into an exit code. A verb without JSON output returns `{ok, exit, text}`.

## Closed catalog, parser-derived arguments

`quenching/mcp/catalog.py` owns the explicit `CATALOG`: each row names a pillar, fixed verb path
and class. Its keys are logical names `<pillar>_<verb>[_<subverb>]`, replacing hyphens with
underscores: `components_read`, `knowledge_site_source`, `git_pr_create`,
`components_session_context`. Specs keep their logical names, including `specs_section_write` and
`specs_record`.

**One published tool per pillar and class.** The server does not publish the logical names:
`quenching/mcp/grouped.py` wraps the surface and publishes one tool per `(pillar, class)` pair —
`git_read`, `git_write`, `git_external`, `specs_read`, … — with a required `verb` argument, the
logical name minus its pillar (`git_pr_create` is `git_external(verb="pr_create")`). A client that
cannot list a hundred tools (Copilot) lists two dozen: measured on 2026-11-26, the whole server went
from 115 tools and 74,986 bytes of `tools/list` to 23 tools and 23,120 bytes, and the `core` mount
to 8 tools and 11,276 bytes. The published schema carries `verb` (an enum of the group's verbs plus
`help`), `of` and `root`, and admits the verb's own arguments flat beside `verb`; each verb keeps
its own `inputSchema` and validation in the inner tables. `verb="help"` answers the group's verbs
and their schemas (`of=<verb>` narrows it to one), a bad argument is refused with that verb's
`inputSchema`, and an unknown verb with `mcp-unknown-verb` and the group's verbs. The description
names every verb with its summary cut to 60 characters (`SUMMARY_CHARS`). A group's annotations
aggregate its verbs: `readOnlyHint` and `idempotentHint` only when every verb has them,
`destructiveHint` and `openWorldHint` when any verb has them. `catalog.tool_names(prefix)` answers
the published names a `cq <prefix…>` grant reaches, `catalog.verb_names(prefix)` the logical ones.
`tools/list` is the authoritative available inventory; an absent pillar contributes no tools.

The schema comes from each pillar's `build_parser()`: flags become booleans, choices become enums,
repeated values become arrays, and positional arguments become properties. Required arguments stay
required. Every schema rejects additional properties. The server owns `--json` and turns `root`
into `--root`; there is no generic argv passthrough. `components` never receives the workspace as `--root`,
because its `--root` names the surface root holding `commands/`; it runs with the workspace as cwd
and finds the nearest `.claude/` from there. A new parser option on a catalogued verb is exposed without
editing the catalog; a new verb requires a new row. Interactive or long-running entry points,
including `specs serve`, `specs mcp` and `portal serve`, are not catalogued.

**Catalog coverage.** Every `cq <pillar> <verb>` that a body under `quenching/skills/**` or
`quenching/agents/**` cites has a tool: a catalog row, a hand-written specs tool (whose verb path
`specs/mcp.py`'s `COVERS` names), or an entry of `quenching/mcp/coverage.py`'s `EXCEPTIONS`, which
carries its reason (`deploy`, `modules`, `mcp`, `specs mcp`, `specs serve`, `portal serve`).
The verb path is what the pillar's parser consumes, so a citation that ends on a
group names no verb and is prose. The gate's `MCP catalog coverage` check fails on any other
citation. A parameter that would move a row out of its class is hidden from the tool rather than
reclassifying it: `specs_artifact_read` takes no `out`, and `specs_handoff_write` takes no `push`,
which stays with `specs_push` — an `external` verb, published under `specs_external`.

**Citation form.** A body cites a covered verb as the call it makes: the unprefixed published tool,
`verb` first, then the verb's `inputSchema` argument names — `specs_read(verb="status", spec=<id>)`
— never as `cq <pillar> <verb>` nor by the logical name alone
([tool-resolution.md](/quenching/references/align/tool-resolution.md) §Citing a verb in a body). The
CLI stays where no tool covers the verb and on a line marked `cli: <reason>`, from a closed set:
`flag` (a flag the tool does not publish) and `fallback` (a CLI synopsis beside its tool). A call
on another tree passes `root`, a multi-section write passes `sections` to
`specs_write(verb="section_write")` or `specs_write(verb="create")` (one atomic write, refused whole like the CLI's stream), and an `approved` stamp
other than `by=human` passes `by`. `cq components lint` holds the form with `sk-cq-cli-citation` and `sk-mcp-unknown-tool` over
the bodies `components/mcp_citations.py`'s `ENFORCED` names: every `quenching-*` skill and every
shared reference, and the flow agents under `quenching/agents/`; an agent's `tools:` grants no raw `git`
or `gh` for a verb a tool covers.

| Class | Meaning | MCP annotation |
| --- | --- | --- |
| `read` | Reads the workspace | `readOnlyHint: true`; a row whose verb reads the remote (`specs_claim_list`) also sets `openWorldHint: true` |
| `write` | Can change the workspace or specs store | `readOnlyHint: false`; worktree retire, worktree release and artifact rm also set `destructiveHint: true` |
| `external` | Can act outside the machine | `openWorldHint: true`; destructive merge/prune also set `destructiveHint: true` |

Annotations describe capabilities; they grant no permission. The specs surface asks the human once:
`approved` is the only gated record, and only a client acceptance writes it as `by=human`, and only
on a spec that met the ready gate; missing capability, decline or cancel refuses without a write.
`by` `session` or `orchestrator-forced` claims no human, so it writes without asking, still only on
a ready spec — the values the CLI writes for the simple track and declared autonomy. What
the flow concludes after that approval is not a second decision — the `reviewed`, `merge` and
`outcome` records and `specs_write(verb="promote")` run without asking, exactly as their CLI verbs
do, so an autonomous run archives a spec without stopping to ask again.
`git_external(verb="pr_merge", spec=<id>)` stamps the
`merge` record once the PR merged, as the CLI's `--spec` does.

`specs_external(verb="push")` is the one spec-store write with no confirmation gate: it publishes every pending local write
of the clone with one push of the store branch, exactly like `cq specs push`, and calling the tool is
the publish. It takes no arguments and a repository without a git store gets a `sp-push-no-store`
tool error. `cq mcp` and `cq specs serve` start with `GIT_TERMINAL_PROMPT=0` so git can never block
the stdio loop on a credential prompt.

## Bounded resources

`quenching://references` indexes the shipped references. A resource
`quenching://references/<path>.md` resolves only inside `references/`, including after
symlink resolution. Documents at or below `DOC_WHOLE` (24,000 characters) can be returned whole;
larger documents return an outline. Repeated `?section=<heading>` parameters select sections
using the same section reader as `components read`. A served reference rewrites its
`.agents/quenching/references/` links to `quenching://references/`, so its sibling
citations resolve inside the MCP surface rather than to a checkout path. The shared
60,000-character response guard marks oversized replies as truncated and supplies a narrower-read
hint.

The specs resources remain available when the specs pillar is present: `quenching://config`,
`quenching://standards`, individual standards and `quenching://glossary`. Tool lists, spec listings
and document reads retain the existing specs size and pagination rules.

## Distribution and proof

`quenching/pyproject.toml` uses hatchling and reads the package version from the plugin's
`VERSION`. The wheel keeps the plugin tree under `quenching_plugin/`, so asset lookups using
`parents[N]` keep their meaning. Its `launch` module adds `assets/bin` to the import path and
exposes `quenching-mcp` and `cq`. Runtime dependencies are the Python standard library only;
Python 3.11 is the floor.

```bash
uvx --from "git+https://github.com/holetz/quenching@<tag>#subdirectory=quenching" quenching-mcp
```

Consumers pin a published tag; publishing that tag is a separate release decision. The local
packaging smoke is `bash quenching/assets/checks/functional-checks.sh --mcp-smoke`:
it builds the current committed HEAD through `git+file`, initializes the server and compares
its tool count with the in-process catalog. Missing uvx or unavailable network is inconclusive
(exit 2), never a pass. The MCP test families and repository gate prove the source and mirrors;
the target-host smoke after release remains a deployment check.
