# Source layout — what lives under `quenching/` and `integrations/`

<!-- rules -->

## One source and two satellites

The source is `quenching/`; the trees that install into no repository sit under `integrations/`,
one folder per harness satellite. The skill surface reaches a repository only through `cq deploy`
([ADR 0017](../../decisions/0017-install-only-by-deploy.md)); the shape of the source is
[ADR 0019](../../decisions/0019-router-skills-and-target-dialect-source.md).

| Path | What it is | Owner |
|---|---|---|
| `quenching/` | the source, the only editable tree of the skill surface, never published; `cq deploy` installs it into a target ([deploy-mode.md](deploy-mode.md)) | — |
| `integrations/claude-hud/` | the band above the Claude Code prompt, the only entry of `.claude-plugin/marketplace.json` | hand-written; the gate runs `claude plugin validate` |
| `integrations/opencode-vitrine/` | the OpenCode Desktop GUI plugin (TypeScript + Solid); `npm run build` writes the committed `dist/gui-experimental.cjs`, `node_modules/` is ignored, and OpenCode installs it from the `plugins` array of its configuration | hand-written |

Inside `quenching/` each folder has one job:

| Folder | Holds |
|---|---|
| `skills/<name>/` | one skill: `SKILL.md` and the `references/` only that skill cites |
| `references/<name>/` | the references two or more skills cite |
| `agents/` | the subagent protocols, one `.md` per agent |
| `assets/` | everything that is not an entry point or a reference: the `cq` tool, molds, hooks, checks, evals |
| `tests/` | the suite, importing from `assets/bin` |

`assets/modules.json` declares the HUD under `plugins`, which is what keeps it in the marketplace
and the release lockstep ([versioning-release.md](../ci-cd/versioning-release.md)). The vitrine
carries no skill prose and no generated byte: edit its `src/` and rebuild `dist/`.

A new harness gets a new first-level directory under `integrations/`, never a `quenching-<harness>/`
sibling of the source. A move between these paths is a `git mv` followed by the path changes in the
generators and manifests, so the history follows the files. How the deploy translates the source
for each harness is [deploy-mode.md](deploy-mode.md) §Surface translation.

## One editable source, installed by deploy

`quenching/` is the **only** tree anyone edits for the skill surface, and it is **not published**
as a plugin. `assets/modules.json` (schema 3) is the deploy manifest: each module record names its
`owned` skills, agents and Python packages and the `generatedSupport` closure they need, and
`cq deploy --modules core|all|<list>` selects which records a target receives
([install-profiles.md](install-profiles.md)).

- **The source is written in the target dialect.** A skill is `/quenching-<vertical> <flow>`, a
  citation is `.agents/quenching/…`, and the source carries no plugin-root marker; `cq deploy`
  rewrites only the frontmatter, the generated header and the grants
  ([command-surface.md](../naming/command-surface.md), [deploy-mode.md](deploy-mode.md)).
- **The source cannot be loaded as proof.** Surface-load checks
  (`assets/checks/functional-checks.sh`) deploy this checkout into throwaway targets and grade the
  deployed copy; they never load the source tree directly
  ([surface-verification.md](../quality/surface-verification.md)).
- **An absent module is a refusal, never a traceback.** A subcommand whose package the target did
  not receive exits 2 naming the module and `cq deploy --modules`, and the help lists only the
  fronts present. `cq modules --json` lists each module with its pillars, whether it is enabled,
  and its root.
- **Resources stay inside the payload.** A body cites `.agents/quenching/…`; routing to another
  module's skill is a Skill call, offered only when that module is deployed.

<!-- rationale -->

Splitting the source into one authored directory per module was rejected (spec 1635 §Design): the
suite imports from `quenching/assets/bin`, and one source per module would need one edit
per module per change. Spec 2160 kept the single source and retired only the published copies —
the module plugins, the specs reader, the Codex plugin and the OpenCode distribution — because a
deployed target already received everything they carried. The read-only reader standard,
specs-reader-plugin.md, retired with it (spec 2160, 2026-11-03): a deployed target carries the read
verbs, so no separate read-only plugin is left to govern.

## `skills/<name>/SKILL.md` is the only entry point

An entry point is a folder `quenching/skills/<name>/` holding a `SKILL.md`. **The skill name is the
folder name**: the `name:` the deploy writes comes from the folder, so the name is one segment with
the `quenching-` prefix of its vertical or front ([command-surface.md](../naming/command-surface.md)),
and a name written inside the file that disagrees with the folder is not a second name.

A skill is a **router** when it carries a table of flows: its body picks one flow and reads that
flow's reference, and it grants the union of its flows' `allowed-tools`
([skills.md](../automation/skills.md)). A flow is a file under `skills/<name>/references/`, never
a skill of its own.

Where a reference goes is decided by who cites it:

- **Inside the skill** (`skills/<name>/references/<file>.md`) when every citing file belongs to
  that skill — the flow files of a router and the material only they read.
- **In the common `quenching/references/<name>/`** when two or more skills cite it. The folder is
  named for the owner that would have to *change* the procedure, flattened (`/` → `-`), not for
  every reader: `references/align/` is cited by every front's align, and
  `references/components-command-new/` by several skills.

Anything that is neither an entry point nor a reference lives under `assets/`. A stray `.md` under
`skills/<name>/` outside `SKILL.md` and `references/` is not a skill and registers as nothing; the
deploy lists it as an unowned file, and `cq components doctor` reports a skill folder without a
`description` as **`sk-no-description`**, so the layout needs no check of its own.

<!-- rationale -->

The previous layout made every `.md` under `commands/` a command, because the path was the identity,
and so forced every non-entry file out of the tree. With one folder per skill the adjacency of a
`references/` folder to its `SKILL.md` is legal again and is how a router carries its flows, so
the exile of references to a distant folder ended for the files only one skill reads.

### The source has no `bin/`

The source is not an installed plugin, so it ships no `bin/`: the entry point is `assets/bin/cq`,
cited by absolute path from the skill surface and the golden fixtures, and `cq deploy`
**generates** the target's `.agents/quenching/bin/cq` and `bin/cq.cmd` (or a `uvx` shim there with
`--runtime uvx`). Two properties of the generated launcher are load-bearing:

- **the execute bit.** A `100644` mode is not a cosmetic slip — it is the whole feature missing;
  `cq deploy --check` reports a non-executable `bin/cq` as drift.
- **self-location from `__file__`.** Never from `.agents/quenching`, which is a path in a skill
  body's *text* and is **empty in a shell**. This binds anything executable the surface ever ships.

The order between the launcher and the entry point is
`quenching/references/align/tool-resolution.md` §Resolving the tool.

## Code `cq` runs ships under `assets/`

The deploy translation (`assets/bin/quenching/deploy/`) lives under `assets/`. A target receives
the payload under `.agents/quenching/`, never this repository's root `scripts/`; placing it in
`scripts/` would make it a checkout-only accident.

## Where it goes instead: `assets/`

`assets/` is deliberately wide:

> **`assets/` is everything that is not an entry point and not a reference.**

The installable payload is a subset of that, not the whole of it. The split `assets/payload/` +
`assets/internal/` was weighed and rejected: both halves share the single property that defines the
folder, and the split would buy a second directory level and a second citation prefix to distinguish
two things no reader confuses. A folder whose membership rule is a **list** means nothing; this
one's rule stays one sentence, and the rows below are consequences a reader can derive. Revisit when
a subtree stops being derivable from the sentence, not when the table gains a row.

The rule that decides where an executable sits is **by how it is invoked, not by whether it
ships.** `hooks/` holds a handler dedicated to one hook event; an entry that serves both a skill
body and a hook lives in `bin/`. The only hooks are those declared in `assets/modules.json` and
installed by `cq deploy` (`deny-claude-coauthor` and `warn-git-add-all`, in `assets/hooks/`).

Current subtrees, by the reason each is here:

| Reason | Subtrees |
| --- | --- |
| payload copied whole by an align | `knowledge/` `specs/` `claude/` `zensical/` `design/` |
| payload applied per insert (molds) | `templates/` |
| tool the surface executes | `bin/cq` |
| artifact of developing this repository | `evals/` `checks/` |

### A contract a skill reads at runtime is a reference, not a standard

The split between a bundle standard and a reference is **by kind, not by size**. A standard states
what this repo holds itself to — a rule its own work is graded against. A reference carries what a
skill reads *while running inside a target*: procedure, not a fact about anyone's repo.

Two standards already sit on that line and delegate across it. [skills.md](../automation/skills.md)
states the skill taxonomy rule and leaves the writing doctrine to
`references/components-command-new/`; [plan-artifacts.md](../workflows/plan-artifacts.md)
states what a spec must contain and leaves the per-section authoring to `specs-develop/`. Both keep
a standard because both **have** a rule this repo is graded against, separable from the procedure.

**Where a contract is entirely runtime procedure, there is no standard left to shrink** — it moves
whole into a reference and the standard is **retired**, under
[retiring-a-standard.md](../workflows/retiring-a-standard.md), never kept as a stub. A stub that
restates the reference is the second copy the delegation existed to prevent, now with the two
halves graded by different validators.

**A spec that declares both artifacts must say which half each carries, or both get written whole.**
`cq knowledge validate` grades the standard, `cq components lint` grades the reference, and neither
sees the other. Declare the split in `## Impact` — the rule this repo is graded against on one side,
the runtime procedure on the other — and the branch review stops being the only net. A standard
that restates [align-surface.md](align-surface.md) in the reference is the same defect.

## References are cited by absolute path, never relatively

Every citation of a bundled reference is the target-dialect path:

```
.agents/quenching/references/<name>/<file>.md
.agents/skills/<skill>/references/<file>.md
```

A relative path encodes the depth of the *citing* file, so two files at different depths would need
different strings for the same target. The absolute form is one string everywhere, which is what
makes the citation set mechanically rewritable and mechanically checkable. Because the source is
written in the target dialect, the string a source file cites is the string the target file cites
([deploy-mode.md](deploy-mode.md) §Surface translation).

### `<name>` is the owning skill's path, flattened

A common reference folder is named for the flow or skill that owns it, with `/` → `-`:
`references/knowledge-add/` for the `add` flow of `quenching-knowledge`, `references/align/` for
the root align. A directory name that lies is forbidden by
[../naming/command-surface.md](../naming/command-surface.md). **Owning is not exclusive**: the folder
is named for the owner that would have to *change* the procedure, not for every reader.

**`evals/` encodes the same source differently, and the difference is deliberate.** An eval tree
keeps the slashes because it mirrors exactly one flow 1:1 and is renamed in the same mechanical step
as that flow (`quenching/skills/quenching-components/references/components-command-eval/evaluation.md`
§Where the artifacts live). A reference folder is shared, has no 1:1 to preserve, and gains a flat
listing from being flattened. Same input, two encodings, two jobs — do not reconcile them.

### A mold cites nothing it does not also install

The rule above governs citation **inside** the payload, where `.agents/quenching` resolves. A mold
becomes target content when copied: a `bash` block pasted by a human into a raw terminal, or the
copy a target's own `/docs/` makes governing, dangles an `.agents/quenching/references/` citation
the moment it is read outside the payload. Three trees answer this test today —
`assets/templates/**` (the harness and front-matter molds), `assets/knowledge/**` (the OKF
skeleton, copied by `/quenching-knowledge align`) and `assets/specs/templates/**`; a fourth surface
added later inherits the rule without amending this list.

So **a template states its caveat self-contained**, citing only what the same align installs
alongside it. This is why a mold and the repository's own copy of the same standard legitimately
differ in wording; that difference is the rule being obeyed, not drift.

**What may diverge is the form, never the rule.** A change to what a rule *says* lands in the mold
in the same commit as the standard: the pair is one rule kept in two places. Whoever edits a
standard the payload also ships as a mold owns both halves; `grep -rl` the rule's own words across
`assets/templates/**` before declaring the change complete. **No validator catches this** — a path
that fails to resolve reads as ordinary prose.

<!-- rationale -->

The alocar-comandos-skills-por-categoria spec (2026-08-15) rewrote the skill classification axis
across `automation/skills.md` and both consuming bodies, and left
`assets/templates/automation/skills-standard.md` declaring the axis the change had just replaced.
Its `## Impact` had enumerated the consumers and the mold was not among them, and only the branch
review caught it.

### A skill body cites the target's bundle only where the align installs it

The opposite direction — a skill or a reference, which stays in the payload forever, citing a path
in the target's own bundle — has its own rule. `/docs/standards/<subject>/<file>.md` is a **fixed
string** ([bundle-root.md](bundle-root.md)), so it reads as a well-formed link in every repo whether
or not the named file exists there. A target only carries that file if `/quenching-knowledge align`
installs it — that is, only if it exists under `quenching/assets/knowledge/**`.

**A skill body or a reference under `skills/**` or `references/**` links a `/docs/` path only when
that path exists under `quenching/assets/knowledge/**`.** Where it does not, the body names the
target in backticks, without a markdown link, and states the rule the citation would have carried
directly in its own prose — the citation was never load-bearing there, only provenance.

**The citation's form is not part of the rule.** An absolute `](/docs/standards/…)` and a relative
climb are the same citation of the same target file, and both dangle identically where the align
installs nothing. Derive the class from the target file, never from the link's spelling. Same
warning: **no validator catches this**.

### A boundary reminder is not a restatement

The neighbouring question — *is this text a restatement at all?* — decides whether a collapse sweep
may fold it. A boundary reminder states the edge of a rule the citing place **already owns**, seen
from the other side: `/quenching-knowledge add` owns where a doc goes and what its slug looks like,
so "the slug is canonical English, the body may follow the repo's language" is that flow's own rule
at its border. A restatement states a fact the citing place neither owns nor can change. The
canonical-structure boundary itself is
[../naming/command-surface.md](../naming/command-surface.md): the slug stays English, the prose
around it follows the tag.

**The verifiable guardrail** — three properties, each checked against the owning doc:

1. **One clause.** A reminder names the border and stops. A paragraph is a copy.
2. **No fact the owner states.** The owner's scope, its exclusions and its declaration form belong
   to the owner.
3. **Never a narrowing.** A reminder may not scope the rule smaller than the owner scopes it
   ([../agents/communication.md](../agents/communication.md) governs all prose the agent authors).

**Apply the guardrail, not the sentence.** "A boundary reminder is not a restatement", read loosely,
absolves every copy there is.
