## Problem

Num repositório sem `.claude/quenching.json` e com remote no GitHub, o store efetivo é o backend `github`, que o README dá como deprecated. Mesmo assim, `cq specs doctor` devolve `findings: []` e `backend: null`, então o aviso `sp-backend-deprecated` nunca aparece no caso em que um projeto novo cai no modo errado.

Reprodução (quenching 6.4.0, `holetz/my-career` em 2026-10-17, antes de declarar a config):

- `cq specs config --json` → `"backend": "github"`, `"present": false`
- `cq specs list --lean --json` → `"backend": "github"`
- `cq specs doctor --json` → `{"ok": true, "backend": null, "findings": []}`

Causa: `plugins/quenching/assets/bin/quenching/specs/commands/doctor.py:92` testa `cfg["backend"] in ("github", "azure-boards")` sobre o backend **declarado**. Sem arquivo, esse valor é `None`. Já `list` e `config` usam o backend **efetivo**, inferido do remote em `specs/config.py:164-173` (`detect_provider`). O doctor e o resto do CLI discordam sobre qual é o store.

Consequência: o autopilot e o `/quenching:specs:create` gravam specs completas em issues sem nenhum sinal, e o único comando que existe para perguntar "o que está errado no workspace" diz que está tudo certo. O problema só apareceu porque o humano esperava a branch `quenching`.

Relação: a #1654 trata a causa (tornar a branch obrigatória e nunca inferir um tracker). Esta spec é o conserto estreito e imediato: enquanto existir inferência, o doctor precisa acusar o backend efetivo deprecated, e dizer que ele foi inferido, sem config declarada. Quando a #1654 fechar, este finding vira o guarda contra regressão.
