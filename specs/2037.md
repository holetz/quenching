## Problem

Only `components:hook:new` and `components:agent:new` carry evals today, in the Claude plugin-eval format, so there is no way to measure whether a cheaper model or another harness runs the specs, git and knowledge commands well. Add eval suites for those commands and a runner that executes the same cases against any harness and model and reports a comparable approval rate; it is the instrument of the H1 spike.

Member S2 of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent).

## Proposal

Ship the instrument the H1 spike (holetz/forge#2) runs, and nothing beyond it:

- **`scripts/run_evals.py`**, a stdlib-only runner that executes the committed `evals.json` case sets against any harness and model, through harness profiles in **`scripts/eval_harnesses.json`** (`claude`, `codex`, `opencode`, each an argv template with `{prompt}`, `{model}`, `{workdir}` and `{max_turns}` placeholders, plus the per-arm extras: the `with` arm loads the quenching modules, the `without` arm loads nothing). A custom profile file can be passed with `--harnesses`.
- Every case runs in a **disposable fixture**: the suite's `fixture/` tree is copied into a temporary directory, initialised as a git repository with an initial commit, then the suite's optional `setup.sh` runs there (with `CQ`, `EVAL_CASE` and `EVAL_WORKSPACE` exported). After the arm, the runner takes a **snapshot** of what is observable: `git status --porcelain`, every ref's recent log with file stats, the working-tree diff, and the output of the suite's optional `inspect.sh`.
- **Grading is harness-agnostic too**: a grader profile and model (`--grader-harness`, `--grader-model`), the same for every arm and every model compared, receives the assertions, the arm's output and the snapshot, and returns `pass` / `fail` / `unknown` with a quoted excerpt. The runner **downgrades to `unknown` any grade whose evidence is not a verbatim substring** of the arm's output or snapshot, so an unquoted pass never counts.
- Output under `.quenching/evals/<run-id>/` (the run id is passed in, never read from the clock): one `grading.json` and one `benchmark.json` per suite in the shapes `components-command-eval/evaluation.md` owns, extended with `harness`, `model`, `grader` and `caseApprovalRate` (cases with every assertion passing), and one `summary.json` across suites that is the comparable approval rate H1 tables per harness and model.
- `--check` validates the suites without running anything (every field present, unique case ids, at least one declining case, fixture and scripts resolvable); `--dry-run` prints the argv each arm would run.
- **Three suites, one command per front**, mirrored under `plugins/quenching/assets/evals/<path>/`: `specs/create` (`/quenching-specs:specs:create`), `git/commit` (`/quenching-specs:git:commit`) and `knowledge/define` (`/quenching-align:knowledge:define`), each with a happy path, a conditional branch and a declining `Not for:` case, natural-language prompts so routing is measured on every harness.

## Out of Scope

- **Running H1 itself**, fixing its quality threshold or choosing the light-tier model: that is holetz/forge#2, which consumes this runner.
- **The OpenCode port of the command surface** (holetz/quenching#2038). The `opencode` profile only shapes the invocation; whether the commands load there is 2038's.
- **Suites for every specs, git and knowledge command.** One command per front is the first cut H1 needs; more suites are follow-ups.
- **Choosing the tool permissions an arm runs with.** The shipped profiles widen no permission; the operator passes them with `--extra-arg` (see `## Open Decisions`).
- **Wiring the runner into `scripts/verify_repo.sh` or CI.** A live run needs a harness and costs tokens; the gate only runs the runner's unit tests, which also validate every committed suite.
- **Changing `/quenching-align:components:command:eval`** or the `evals.json` format: suites keep the existing shape, and the fixture lives beside it by convention (`fixture/`, `setup.sh`, `inspect.sh`).

## Design

### Run flow

```
evals.json + fixture/ + setup.sh + inspect.sh   (one suite)
        │ per case × arm
        ▼
tmp workspace ← copy fixture/ → git init + commit → setup.sh "$case"
        │
        ▼
harness profile argv (claude | codex | opencode | custom), cwd = workspace, timeout
        │ stdout/stderr, exit, duration, tokens when the profile can parse them
        ▼
snapshot: git status, refs + log --stat, diff, inspect.sh
        │
        ▼
grader profile (fixed for the whole comparison) → JSON grades
        │ evidence not a verbatim substring → unknown
        ▼
.quenching/evals/<run-id>/<suite>/grading.json, benchmark.json; summary.json
```

### Decisions taken from evidence

- **Runner under `scripts/`, not a new `cq` verb.** The epic allows new scripts under the repo pattern; a script needs no router, module manifest or mirror change, and H1 runs it from a checkout of this repository. Promoting it to `cq` is a later decision once a target repo needs it.
- **Fixture by convention beside `evals.json`.** `evaluation.md` adopts skill-creator's format verbatim and says every field is required; adding a field would diverge, while a sibling `fixture/` keeps both readers working.
- **The spec store in the specs fixture is the git backend with a local bare `origin`.** Probed on 2026-10-24: with no `.claude/quenching.json` the backend is unconfigured, `backend: files` is refused (`sp-backend-removed`), and `backend: git` without an `origin` refuses with `sp-git-no-remote`; with a bare repository as `origin`, `cq specs new` writes `specs/1.md` on the `quenching` branch. So `setup.sh` creates the bare origin next to the workspace and `inspect.sh` prints `cq specs list --json`.
- **`cq` on `PATH` for the `with` arm only.** The runner prepends `plugins/quenching/bin` for the `with` arm, so a harness without plugin loading still reaches the tool the commands call; the `without` arm gets no path to it.
- **The grader never sees the skill.** It runs in an empty temporary directory with the grader profile's `without` extras.

## Open Decisions

- **Default tool permissions for an arm.** Commands call `cq` and `git` through Bash, which a non-interactive harness denies unless permitted. The shipped profiles widen nothing; whether a profile should carry a permission mode (`--permission-mode`, `--dangerously-bypass-approvals-and-sandbox` or similar) inside the disposable fixture is the human's, decided before H1's first live run. Until then the operator passes it with `--extra-arg`.
- **What would make this not worth doing** is not stated in `## Problem`: decided by H1's owner if the first live run shows the grader's variance swamps the difference between models.
- **The `opencode` profile's flags** are taken from OpenCode's documented `opencode run`; they are confirmed or corrected by 2038 or by H1's first run.

## Risks

- **Grader variance.** An LLM grader can flip a grade between runs; the substring check removes unquoted passes but not judgement noise. Mitigation: the grader is fixed per comparison and recorded in every artifact, and `unknown` counts are reported.
- **Harness CLI drift.** Flags for `claude -p`, `codex exec` and `opencode run` change between versions; profiles are data, so a fix is a JSON edit, and `--dry-run` shows the argv before any spend.
- **Fixture realism.** A fixture too thin makes the arm explore instead of act (the skill-evaluation standard's fixture rule); each suite seeds the smallest repository its prompts can be answered in.
- **Cost.** A live run spends tokens per case × arm plus grading; nothing in the gate runs it.

## Handoff

- H1 (holetz/forge#2) runs, from a checkout of this repository: `python3 scripts/run_evals.py --harness opencode --model <flash> --grader-harness claude --grader-model <fixed> --run-id <ts> --extra-arg ...`, then the same with the baseline, and tables `summary.json` from both runs.
- The first live run settles the permission and OpenCode-flag decisions in `## Open Decisions`.
