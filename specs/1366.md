## Problem

Estreitamento. A 1339 pôs `Bash(az repos pr:*)` fixo no `tools:` do steward, e o matcher admite `az repos pr update --id 7 --status completed --bypass-policy true` e `create --auto-complete --bypass-policy true` (`/tmp/claude-1000/-home-unicred-Projetos-claude-quenching/a284eb01-1fc3-4a7f-ae95-abf7651b3d1b/scratchpad/review11/`); no GitHub o merge só passa por `cq git pr merge` com checks verdes, no Azure não.

Origem: item T2 da fila da rodada 3 do autopilot de 2026-10-08 (`.quenching/autopilot/2026-10-08/round3-queue.md`), da revisão de correção opus da rodada 2 (épico 1337).

## Proposal

Direção: tirar o grant; a rota Azure por verbo `cq` de argv fixo, sem `--bypass-policy` nem `--auto-complete`. Depois do T1.

## Out of Scope

- Um `cq git pr merge` para Azure: o passo `merge` do steward continua só GitHub (`gh`); num repositório Azure ele segue `STATE: blocked`, como hoje sem o grant.
- Os `az repos pr show|list` e `az devops invoke` de `/quenching:git:pr:status` e `/quenching:git:pr:review`: são comandos do humano, fora do `tools:` do steward.
- Retirar o verbo `cq git pr record`: continua valendo para um PR aberto fora do verbo (ver `## Open Decisions`).
- A rota GitHub de `cq git pr create`: o argv fica igual.

## Design

Hoje (pós-1339/1365) o `/quenching:git:pr:create` no Azure roda `az repos pr list` (sondagem) e `az repos pr create` crus, e o steward herda `Bash(az repos pr:*)` para segui-lo. O matcher é por prefixo, então o mesmo grant admite `az repos pr update --status completed --bypass-policy true`: um merge sem política nem checks verdes, enquanto no GitHub o único merge é `cq git pr merge`.

Proposta, igual ao padrão que já fechou `gh pr create`:

```
antes:  steward --Bash(az repos pr:*)--> az repos pr create|update|... (qualquer flag)
depois: steward --Bash(cq git:*)--> cq git pr probe   --> az repos pr list --status all --top 1 --detect true --output json
                                    cq git pr create  --> az repos pr create --detect true --source-branch B --target-branch T
                                                          --title X --description Y [--work-items N]
                                                          [--transition-work-items true] [--delete-source-branch true] --output json
```

- O provedor sai da config (`load_config(root)["provider"]`, o mesmo `provider` que `cq specs config --json` imprime). Premissa: é a mesma fonte que o corpo do comando já usa para escolher a rota, então verbo e corpo não divergem. `github` mantém o argv de hoje.
- No Azure o verbo valida `--base`/`--head` como o caminho GitHub, monta o argv numa lista (sem shell), normaliza a resposta com `normalize_azure_pull_request` (`webUrl`, nunca `/_apis/`) e, com `--spec`, carimba pelo mesmo `_stamp`. Flags só-Azure: `--work-item N`, `--transition-work-items`, `--delete-source-branch`. As duas últimas são booleanas, e o corpo só as passa com o consentimento que já pede.
- `cq git pr probe --json`: leitura apenas. Roda a sondagem do provedor (`gh repo view --json nameWithOwner` / `az repos pr list ...`). Sai 0 com rota e 1 com `reason` (`no-route`, `unauthenticated`).
- O `/quenching:git:pr:create` passa a chamar `cq git pr probe` e `cq git pr create` nas duas rotas. O passo 5 Azure (`cq git pr record`) some do corpo porque `--spec` já carimba.
- `git-steward.md` e `pr/create.md` perdem `Bash(az repos pr:*)`. Os dois só estreitam, e `StewardSkillSubset` continua exigindo `allowed-tools` ⊆ `tools:`.

## Open Decisions

- Aposentar `cq git pr record` depois que `cq git pr create --spec` carimbar também no Azure. Decide-se no conclude com `grep -rn "pr record" plugins/quenching/commands plugins/quenching/agents`: sem chamador → vira linha de `## Discoveries` para uma spec de remoção; com chamador → fica.

## Risks

- **A rota Azure não tem prova viva aqui**: o repositório é GitHub e os testes usam um `az` falso no PATH. Mitigação: o teste fixa o argv exato e o normalizador já testado. A validação de campo vai para `## Handoff`.
- **O provedor lido da config diverge do remoto**: o probe confere antes do create, e o corpo continua mandando parar quando a sondagem falha.
- **O espelho Codex ou o README defasam**: a tarefa 3.1 regenera, e o gate roda `translate --check`.

## Handoff

- Validação de campo depois do merge: num repositório `azure-boards`, rodar `/quenching:git:pr:create <id>` pelo steward com `autonomous` e conferir que o PR abre sem `autoCompleteSetBy` e que o `pr` da spec traz o `webUrl` `.../pullrequest/<id>`.
