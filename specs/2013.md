## Problem

O mapa da rodada 10 do autopilot (2026-10-22, main 58437f3a1) achou isto, e o condutor releu o código.

Evidência, em `plugins/quenching/assets/bin/quenching/git/`:

- `pull.py:147` consulta `_is_merged` uma única vez, antes do loop de checks.
- `pull.py:170-174`: se o PR já foi mergeado durante a espera, `_view` não devolve um estado mergeável e o verbo sai `ok: false` com `reason: merge-state`.
- `pull.py:177-181`: qualquer saída não zero de `gh pr merge` vira `reason: merge-refused`, sem reler o estado do PR.
- `azure_pull.py:154` e `:167` fazem o mesmo `merge-refused` no caminho Azure.

Consequência: uma segunda chamada de merge, concorrente ou repetida, sobre um PR que a primeira já mergeou relata `blocked`. Na rodada 8 o steward fez duas chamadas concorrentes. A que perde a corrida faz o steward pular o retire do worktree e da branch, e o orquestrador lê como não terminada uma spec que está no main.

Validação esperada: um teste em `plugins/quenching/tests/` com `gh` simulado. Nele o PR passa a MERGED entre a primeira leitura e o `gh pr merge`, e o merge falha. O verbo deve sair `ok: true` com `alreadyMerged: true`, nos caminhos `merge-refused` e `merge-state`. Um PR que não foi mergeado continua recusado. O caminho Azure recebe o mesmo tratamento. Todo arquivo de saída dos geradores (espelhos e `.generated-files.json`) fica declarado no `files:` da tarefa que os regenera.

## Proposal

- `cq git pr merge` sobre um PR GitHub que outra chamada mergeou durante a espera sai `ok: true` com `alreadyMerged: true`, tanto quando a releitura pré-merge não devolve estado mergeável (`merge-state`) quanto quando `gh pr merge` falha (`merge-refused`).
- O mesmo vale no caminho Azure quando o PATCH de conclusão falha e uma releitura mostra o PR `completed`.
- Um PR que não está mergeado continua recusado com o mesmo `reason`, `message` e exit 1 de hoje.
- Um teste com `gh` e `az` simulados prova as duas faces: o PR vira MERGED entre a primeira leitura e o merge (relatado como já mergeado) e o PR não mergeado (continua recusado).

## Out of Scope

- Serializar ou travar chamadas concorrentes de merge: a corrida é legítima e o relato é que estava errado.
- Mudar a decisão do steward sobre retire de worktree e branch: ele passa a ler `alreadyMerged` como já lê hoje.
- Reler o estado no caminho `checks != green`: ali o PR não foi mergeado pela própria chamada e o motivo dos checks continua verdadeiro.

## Design

- Decisão: reler o estado só no desvio de falha, não antes do `gh pr merge`. Uma releitura prévia não elimina a janela; a releitura após a falha elimina o falso relato e custa uma chamada só no caminho de erro.
- Regra durável: quando um verbo de merge falha, ele confirma o estado do PR antes de relatar recusa; PR já mergeado é sucesso idempotente (`alreadyMerged: true`), nunca `blocked`.
- GitHub: em `_merge`, nos dois blocos que hoje emitem `merge-state` e `merge-refused`, chamar `_is_merged(args.url)` antes de emitir; verdadeiro emite o mesmo payload do ramo inicial (`ok`, `url`, `number`, `alreadyMerged`) e retorna OK.
- Azure: no ramo `code != 0` do PATCH, reler a rota GET; `status == "completed"` e `pullRequestId == number` termina com `finish(alreadyMerged=True)`; leitura ilegível ou outro estado mantém `merge-refused`. O caminho `merge-state` do Azure já trata `completed` na releitura pré-merge.
- Assunção: `gh pr view --json state` devolve `MERGED` assim que o merge concorrente termina; o teste simula isso.

## Alternatives Considered

- Lock/serialização entre chamadas de merge: rejeitado, exige estado compartilhado entre processos e não cobre o merge feito pela interface web.
- Ajustar o steward para reler o PR após `blocked`: rejeitado, deixa o verbo mentindo para todo outro chamador.

## Open Decisions

- none — a única incerteza (momento em que `state` vira MERGED) é coberta pela assunção do Design e pelo teste simulado.

## Risks

- Uma releitura que falha (rede) não encobre um merge: cai no relato de recusa original, o mesmo de hoje. Mitigado por testar o ramo de leitura ilegível.
- Mascarar uma recusa real como sucesso: só ocorre se o PR estiver de fato MERGED, e então o sucesso é verdadeiro.
