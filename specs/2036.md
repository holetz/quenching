## Problem

An epic only resolves members from its own store (`parse/epics.py` reports an item whose `spec:` is not in the store), so a portfolio epic cannot track work that is built in other repositories, and a spec can only be executed in the repository that holds it. Teach epics a cross-repository member reference (`spec: <owner>/<repo>#<id>`) that `status --epic`, `next`, `validate` and the portal derive from the member's own store, with `after:` edges across repositories.

Member S1 of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent).

## Proposal

- An epic item may name a member in another repository's spec store: `- [ ] S1 Title — spec: holetz/quenching#2036 — after: S2`. The bare `#<id>` form keeps its meaning (this store), and a reference naming this repository's own `<owner>/<repo>` is the same member as the bare id.
- `cq specs status --epic`, `cq specs next --epic` and the epic's archive gate derive a cross-repository item's state from the member document in its own store, read read-only, with `after:` edges between local and cross-repository items working exactly as today.
- `cq specs validate` accepts a cross-repository member that exists in its store, flags one that is absent (`sp-epic-missing-member`), and warns — never errors — when the member's store cannot be read (`sp-epic-member-unreadable`); the back-reference (`epic:` on the member) is not required across repositories.
- `cq specs epic add <epic> <owner>/<repo>#<id>` lists a cross-repository member with its title read from its store, and writes nothing into that store.
- The portal's epic view resolves cross-repository members the same way, so holetz/forge epic 1 can carry every `## Design` §Roadmap waves row in `## Tasks` with its real `after:` edges.

## Out of Scope

- Writing into another repository's store (`epic:` back-reference, card links): the reader is read-only by construction, and a foreign write would need that repository's own permissions and gate.
- Stores whose origin does not have the `<host>/<owner>/<repo>` path shape (Azure DevOps `/_git/` URLs, the tracker backends): the GitHub-shaped git store is what the forge#1 consumer uses; other shapes report the member as unreadable.
- Dependencies between specs that are not epic items, and a derived schedule — that is 2039 (S4 of epic 2042), which waits for this spec.
- An MCP or remote API over the stores — tempering#1 wraps `cq`, so it inherits this through the CLI.
- A configuration map from `<owner>/<repo>` to an arbitrary URL or local path: the sibling URL derived from `origin` covers the consumer; a map waits for a store it does not cover.

## Design

**Reference grammar.** `spec: <owner>/<repo>#<id>` beside `spec: #<id>`. The item's `spec` field carries the normalized key: a bare id string for this store, `owner/repo#id` (owner and repo lower-cased) for another. A reference whose `<owner>/<repo>` equals this repository's origin collapses to the bare id, so the same member is never listed twice under two spellings.

**Resolution is derived from `origin`, never configured.** The member's store URL is this repository's `origin` URL with its trailing `<owner>/<repo>[.git]` replaced — `https://github.com/holetz/forge.git` → `https://github.com/holetz/quenching.git`, `git@github.com:holetz/forge.git` → `git@github.com:holetz/quenching.git`, and a local path the same way (which is what lets the tests use two bare stores side by side). The store is read with the existing read-only `GitBackend(mirror_dir=…, remote_url=…)` mode, the mirror living under `$XDG_CACHE_HOME/quenching/mirrors/`, so nothing is ever written into either repository's `.git`, and the fetch TTL and `QUENCHING_SPECS_NO_FETCH` apply unchanged. One `read_specs` call per foreign repository.

**Unreadable is a state, not an absence.** A store that cannot be fetched yields item status `unreadable`: it never satisfies an `after:`, it keeps the epic from archiving as done, and `validate` reports it as a warning, because a network failure is not a defect of the epic. A store that was read and lacks the id is `missing`, an error, as today.

**No back-reference across repositories.** The member's `epic:` key names an epic in its own store; a member may therefore also belong to a local epic (2036 belongs to 2042 and to forge#1). `sp-epic-divergent` is checked only for same-store members; `sp-epic-nested` still applies to a cross-repository member. A member whose own `epic:` uses the reference form is accepted unverified by `claim_findings`.

**PR state.** A cross-repository member's PR is read with `gh pr view <n> --repo <owner>/<repo>` (or its recorded URL), never against this repository.

Binding contracts: `docs/standards/workflows/epics.md` (state derived, never ticked; one level only), the git store's read-only mirror mode in `backends/git.py`, and the derivation staying pure in `parse/epics.py` (the I/O lives in `members.py` and the commands).

## Alternatives Considered

- **A configured map `<owner>/<repo>` → URL or local path in `.claude/quenching.json`.** Lost: it adds a config key every adopter must keep in sync, while the sibling-of-origin rule already resolves every repository of the forge#1 consumer; kept as the extension point named in `## Out of Scope`.
- **Reading a local sibling checkout (`../<repo>`).** Lost: it depends on the reader's directory layout and on that checkout's fetch state, and it would read the clone's `.git`; the mirror reads the remote store itself.
- **Mirroring foreign members as local tracking specs** (forge#1's fallback). Lost: two copies of one fact, the thing the derived-state rule forbids.
- **GitHub API reads of the `quenching` branch.** Lost: ties the store to one host and to `gh` auth, where git transport already works for every git host the store supports.

## Open Decisions

- none — the gear answered every item from the code and the consumer's `## Design`; the scope limits are recorded in `## Out of Scope`.

## Risks

- **Network on every epic read.** Mitigation: the existing 30 s fetch TTL and cache file, `QUENCHING_SPECS_NO_FETCH` reading the mirror as it stands, and `unreadable` instead of a refusal when the fetch fails.
- **Credentials for a private foreign repository.** The fetch uses the same git credentials as `origin`; a repository the user cannot read becomes `unreadable`. ACCEPTED — the forge#1 repositories share one owner.
- **A member renamed or moved between repositories** reads `missing`. ACCEPTED — the epic is edited by hand, the same as a local id change.
- **Mirror directory growth** under the cache: one bare repository per foreign store, fetching only the `quenching` branch. ACCEPTED.
