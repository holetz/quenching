## Problem

Na rota Azure, um branch que começa com `@` vira leitura de arquivo: `cq git pr create --base main --head '@notes.txt' --title t --body b` passa `--source-branch=@notes.txt`, que o `_expand_file_prefixed_files` real do az troca pelo conteúdo do arquivo; `git check-ref-format --branch '@notes.txt'` aceita o nome. Onde: `plugins/quenching/assets/bin/quenching/git/pull.py:269-270`; a trava da 1388 (`:313`) só olha título e corpo. Direção: recusar `@` no início de todo valor repassado ao `az`.

Origem: fila da rodada 5 do autopilot de 2026-10-08 (`.quenching/autopilot/2026-10-08/round5-queue.md`), item X2 (baixa), da revisão de correção opus da rodada 4 (épico 1394).

## Proposal

- `cq git pr create` on the Azure route refuses, with the existing `git-pr-azure-at-prefix` code and exit 2, a `--head` or `--base` that begins with `@`, before `az` is invoked.
- The refusal message names which flag (`--head`, `--base`, `--title` or `--body`) carried the `@`.
- Title and body keep being refused as today; a GitHub-route `--head`/`--base` starting with `@` is unchanged.

## Out of Scope

- The GitHub route: `gh` receives `--head=<value>` and has no `@file` expansion, so nothing is refused there.
- Other `az` values (`--work-items`, which is an integer) and `pull.py` callers other than `_create`: not reachable with a leading `@`.
- Rewriting or escaping the value for `az`: the direction is refusing, as for title and body in 1388.

- `bash scripts/verify_repo.sh` exits 0.

## Design

- Rule: on the Azure route, every free-text or ref value forwarded to `az` as `--flag=<value>` is refused when it starts with `@`, because `az` expands `@path` into the file's contents. The guard is the one tuple check already in `_create`, widened to `(title, body, head, base)`; one code, `git-pr-azure-at-prefix`.
- `git check-ref-format --branch` accepts `@notes.txt`, so `_branch_ok` cannot be the place; the guard stays beside the 1388 one so a single list names every forwarded value.
- The message names the offending flag so the caller knows which value to rewrite.

## Alternatives Considered

- Refusing `@` inside `_branch_ok`: rejected, it would also refuse `@`-prefixed heads on GitHub, where they are harmless.
- Passing the value after `--` or quoting it: rejected, `az` expands `@` regardless of how the argument is delivered.

## Open Decisions

- none — the code, the flags covered and the message are settled by the 1388 precedent.

## Risks

- A legitimate branch beginning with `@` on Azure is now refused. ACCEPTED — such a branch cannot be published through `az` without the file substitution, so refusing is the only safe behaviour.
