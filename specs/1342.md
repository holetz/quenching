## Problem

O registro `pr` do `pr create` (1321): no Azure nada grava mais o `pr` num run orquestrado (`plugins/quenching/agents/orchestrator.md:56`, `git-steward.md:37`, passo 5 Azure de `plugins/quenching/commands/git/pr/create.md:121-126` pede `cq specs record` que ninguém concede; a rota `stamp-pr` saiu); e o verbo valida `--spec` só depois de criar a PR (`plugins/quenching/assets/bin/quenching/git/pull.py:172-189`: `--spec 999` → `stamp-failed` com a PR aberta) e não confere `--spec` contra `--head` (`--spec 2` gravou a PR de outro branch).

Origem: item R6 da fila da rodada 2 do autopilot de 2026-10-08 (`.quenching/autopilot/2026-10-08/round2-queue.md`), da revisão de correção opus do épico 1306.

## Proposal

Validar antes de criar, conferir spec × branch, e o Azure gravar pelo mesmo caminho.

## Out of Scope

- Merging or changing the `merge:` record route — only the `pr` record and the `--spec` check move.
- Making `cq git pr create` open Azure PRs: Azure keeps `az repos pr create`; only its stamp gets a verb.
- Validating `--spec` against anything but existence and ownership of `--head` (no check of the spec's stage).

## Impact

- `bash scripts/verify_repo.sh` exits 0.

## Design

- Rule: `--spec` is validated before any PR exists. The spec must resolve, and own `--head`: its `branch.work` record equals `--head`, or, before that record exists, the head carries `<id>-` (`plan/<id>-<slug>`). A refusal is exit 2 (`git-pr-spec-unknown`, `git-pr-spec-head-mismatch`) with no `gh` call.
- Rule: the Azure stamp is the verb `cq git pr record`, running the same check and the same `cmd_record` function as the GitHub path. The steward holds `Bash(cq git:*)`, so no new grant and no `cq specs record` grant is needed.
- Rule: `pr record` refuses `/_apis/` urls and non-positive numbers (exit 2, `git-pr-record-invalid`).
- Assumption: the head-carries-id fallback matches the repo's `plan/<id>-<slug>` branch convention.

## Alternatives Considered

- Granting `cq specs record` to the steward: rejected, it widens the spec-write grant the steward deliberately lacks.
- Restoring a `stamp-pr` route in the orchestrator: rejected, it was removed on purpose by 1321 and spawns a worker for a one-line write.

## Open Decisions

- none — the design settled every choice above.

## Risks

- A branch not named `plan/<id>-…` with no `branch` record is refused on create. Mitigation: the `branch` record is stamped at execute start, so orchestrated runs always have it; ACCEPTED for hand-made branches, whose operator can stamp it first.
- `pr record` trusts the caller's number and url. ACCEPTED — the same trust the old `cq specs record` step had, now with the spec/head check added.
