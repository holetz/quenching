## Problem

The 6.11.0 deploy spent most of its wall time waiting for the repository gate. The session log at
`.quenching/deploy-session/` records `bash scripts/verify_repo.sh` six times (259–273 s each) plus
five extra full-suite runs (120–232 s each): roughly 40 of its 142 minutes were the same 2,400 tests
executed again. Measured on 2026-10-29, one local gate takes ~200 s idle and ~282 s under load, and
the unit suite alone accounts for ~150–235 s of it; every other check together fits in ~50 s.

CI pays the suite twice in the same job: `verify_repo.sh` runs `coverage run -m unittest` and the
`gate` job then runs `uv run pytest ... -p randomly` over the identical tests (2 m 41 s in run
40816767803). The 3.11/3.13 matrix repeats the whole gate in both cells, so the run's wall time is
the slowest full gate (6 m 49 s) for a check whose file-level assertions do not depend on the
interpreter.

## Proposal

Make the suite run **once per gate**, with the ordering evidence the proof front already requires:

- `scripts/verify_repo.sh` runs `pytest -p randomly -n auto` through `pytest-cov`, writing the same
  `coverage.json` artifact `cq proof ratchet --check` reads. Random order and parallel workers replace
  the serial `unittest` pass; the floor, doctors and builds stay untouched.
- Without the dev group the gate keeps today's stdlib fallback (`unittest`, serial, coverage when
  available) and states the skip loudly, so a bare checkout still verifies.
- `.github/workflows/ci.yml` drops the duplicate randomized step (the gate now carries it) and keeps
  the matrix: Python 3.11 runs the full gate, Python 3.13 runs the suite as a compatibility check.

Expected result: the local gate drops from ~200 s to ~100 s (suite ~60 s), CI's critical path from
6 m 49 s to roughly 2 min, and the deploy loop stops paying for the same test twice.

## Out of Scope

- Deleting or skipping existing tests, and changing what the gate verifies beyond how the suite runs.
- Changed-files test selection for the gate: at ~60 s the full suite is cheap enough that a
  selection heuristic would buy little and risk false negatives.
- The opt-in `QUENCHING_FUNCTIONAL` and `QUENCHING_DISTRIBUTION` checks, and `cq deploy` itself.
- Branch-protection or required-check renames.

## Impact

- `scripts/verify_repo.sh`: the measured test block selects pytest (randomized, parallel, coverage)
  first and falls back to the current serial paths.
- `.github/workflows/ci.yml`: one gate step per cell, no second suite run, full gate only on 3.11.
- `pyproject.toml` + `uv.lock`: `pytest-xdist` and `pytest-cov` join the `dev` group.
- `docs/standards/ci-cd/index.md`: the pipeline description and the gate contract text.
- No change to the plugin payload: the shipped package stays stdlib-only, and the dev group remains
  the only place these tools live.

## Validation

- `bash scripts/verify_repo.sh` exits 0 with the pytest path, in ~100 s, coverage floor green.
- The same suite passes serially (fallback) and under `-n auto` with the same counts
  (2,414 passed, 7 skipped) and a coverage artifact above the 76.5 floor.
- `cq proof doctor` stays green: CI still declares randomized order.
- A CI run on the pull request is green and its wall time is recorded against the 6 m 49 s baseline.
- With the dev group hidden, the gate reaches the stated serial fallback instead of failing.

## Design

The measured test block in `scripts/verify_repo.sh` becomes a three-way selection, tried in order:

1. **pytest path (default when the dev group is installed).**
   `uv run python -m pytest plugins/quenching/tests -q -p randomly -n auto --cov=plugins/quenching/assets/bin/quenching --cov-report=json:"$COVERAGE_JSON"`.
   `pytest-randomly` supplies the ordering evidence the proof gate expects; `pytest-xdist` runs one
   worker per core; `pytest-cov` combines worker data, because `coverage run -m pytest` would measure
   only the controller process once tests move to workers. The JSON artifact is the same
   coverage.py schema, so `cq proof ratchet --check --artifact` and `.coverage-floor.json` are
   unchanged.
2. **Serial measured fallback** when pytest's plugins are missing but `coverage` is importable:
   today's `coverage run -m unittest discover` + `coverage json`, with the skip stated.
3. **Bare fallback** with neither: `python3 -m unittest discover`, unmeasured, stated loudly.

`PYTEST_RANDOMLY_SEED` is honored when set, so CI can pin the ordering to `github.run_id` and a
failure is reproducible without making local runs depend on a stored seed. Worker count stays
`auto`: 12 workers measured 56 s against 62 s for `-n 4`, and CI's 2–4 cores get exactly the
workers they can use.

In `.github/workflows/ci.yml` the `gate` job keeps the `3.11`/`3.13` matrix and its check names.
Python 3.11 runs `uv run bash scripts/verify_repo.sh` with the seed in the environment; Python 3.13
runs the suite alone (`uv run python -m pytest plugins/quenching/tests -q -p randomly -n auto`), the
compatibility claim the second cell actually adds. The step name carries `pytest-randomly` so
`cq proof doctor` keeps seeing randomized order declared in CI without a second execution.

## Alternatives Considered

- **Stdlib sharding** (`unittest` per shard + `coverage --parallel-mode` + `combine`): no new
  dependency, but it reimplements coverage combination inside the gate and leaves ordering
  unproven, so the second run would return.
- **Remove only the CI duplicate**: saves 2 m 41 s per job but leaves the deploy loop, which is what
  actually cost 40 minutes, unchanged.
- **Delete "redundant" tests**: no test is proved redundant; the 4 s worst case is a process-kill
  assertion, not a slow fixture. Deleting coverage to buy seconds trades assurance for time.
- **Changed-files selection in the gate**: a false negative here is a red main; at ~60 s for the
  whole suite the heuristic is not worth that risk. It stays a possible local-only helper, not part
  of this change.
- **Fixed `-n 4`**: measured 62 s against 56 s for `auto`; pinning a number would waste cores on the
  development machine and oversubscribe a two-core runner only if set too high.

## Open Decisions

- none — worker count (`auto`), seed policy (honor `PYTEST_RANDOMLY_SEED`) and the 3.13 scope are
  decided here on measurement.

## Risks

- **Latent order or parallel dependence becomes a red gate.** That is the evidence the randomized
  pass exists to produce; the fix is the test, never serializing the gate. The CI seed makes the
  failure reproducible.
- **Timeout-sensitive tests under load.** `test_run_evals` kills processes on a 4 s budget; a
  saturated 12-worker run could flake. If the first CI runs show it, cap workers at 4 rather than
  dropping parallelism.
- **Coverage drift under xdist.** Measured artifact 83.66% against a 76.5 floor; the ratchet guards
  the trend, and a missing artifact fails the floor loudly rather than passing empty.
- **A contributor without the dev group** gets the serial fallback and a stated skip, exactly as
  today; the release command runs under `uv run`, so it exercises the pytest path.
