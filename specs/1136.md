## Problem

O `cq knowledge validate` emite `generated-listing-drift`/`generated-listing-missing` com o remédio "(regenerate the zone)", mas nenhum subcomando (`validate`, `doctor`, `status`, `project`, `nav`, `site-source`) regenera a zona GENERATED de um `index.md`; `project --write` só cuida do glossário. Observado em holetz/eclume#57 (2026-09-28): a linha do `standards/index.md` foi reescrita à mão para casar com a `description` nova, o que é exatamente o trabalho mecânico que o achado sugere existir.

## Proposal

- `cq knowledge listing --write` rewrites the rows inside the `<!-- BEGIN GENERATED -->` zone of `standards/index.md` from the docs on disk: a stale description is replaced by the doc's own frontmatter `description`, an unlisted `standards/**` doc gets a row, a row whose doc is gone is dropped.
- `cq knowledge listing` (and `--check`) is read-only, prints the same two findings `validate` emits and exits 1 while the zone is stale.
- Running `listing --write` twice is a no-op the second time, and prose outside the zone is byte-identical afterwards.
- The `generated-listing-missing` and `generated-listing-drift` remedies name the verb instead of the bare "(regenerate the zone)".

## Out of Scope

- A second GENERATED zone, or a generic zone engine — `structure.py` pins one zone on purpose (population of one).
- The `index.md` of every other home — `index-orphan` keeps its own remedy; this spec owns the standards listing only.
- Hooking the verb into `quenching:knowledge:add`/`align` bodies — a follow-up once the verb exists.

- `bash scripts/verify_repo.sh` exits 0.

## Design

- **Rule: the verb preserves what it can.** Existing rows keep their order and subfolder headings; only the description cell is rewritten, so a diff shows exactly the drift. Missing docs are appended to their `### <subfolder>/` table, and a new subfolder section is added when none exists. The existing zone is not sorted: the on-disk zone is not alphabetical and a re-sort would bury the real change.
- **Rule: a separate verb, not `project --write`.** `project` is the glossary projection and its payload and message are about that; overloading it would make `project --check` change meaning. `listing` follows the `--write`/`--check`/`--json` shape of `project`, `nav` and `site-source`.
- **Rule: the zone regex is reused.** `GENERATED_ZONE_RE`, `GENERATED_ROW_RE` and the corpus reading stay in `structure.py`; the regenerator is a function there so detection and repair cannot disagree about what a row is.
- **Rule: no zone, no write.** A bundle whose `standards/index.md` lacks the markers is refused (exit 2) rather than having a zone invented.
- Frontmatter descriptions are written whitespace-squashed, matching the comparison the checker already uses.

## Alternatives Considered

- Extend `project --write` — rejected: changes the meaning of the glossary verb.
- Re-sort and rebuild the whole zone from scratch — rejected: noisy diffs against a zone that is not alphabetical today.
- Only improve the remedy message — rejected: the finding promised a mechanical step that still would not exist.

## Open Decisions

- Whether `quenching:knowledge:add`/`align` bodies should call the verb — decided in a follow-up spec once the verb has shipped (parked in Discoveries).

## Risks

- Rewriting a hand-authored row loses prose — mitigated: the zone is marked "DO NOT edit by hand" and the verb only rewrites cells that differ from the description.
- Codex mirror drift — mitigated by the translate task and the repository gate's `translate --check`.
- ACCEPTED — dropping rows for deleted docs removes `index-broken-link` evidence; the zone is rebuilt from disk by contract.
