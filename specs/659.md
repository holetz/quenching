## Problem

Na limpeza de 2026-11-27, depois do release 7.19.0, `cq git stale --full` listou `~/Projetos/quenching-slot-7` como worktree `candidate` (`merged-clean`, `slot-above-floor`). `cq git prune --worktree <path> --expect-tip … --id … --confirm-inactive` saiu com 2 `git-prune-unlock-failed` ("could not be unlocked for removal; nothing was removed") duas vezes, com o relatório renovado entre uma e outra. O slot estava livre mas **sem lock**: `git worktree list --porcelain` não mostrava `locked`, e `git worktree unlock` responde `fatal: '…/quenching-slot-7' is not locked` (exit 128). `slots.unlock_free` trata essa recusa como falha, então um slot livre já destravado nunca é removido pelo verbo. A remoção só saiu com a ação `git worktree remove` crua, sem `--force`.

A correção precisa garantir que um slot livre sem lock seja removido pelo `prune`, sem tentar destravar o que já está destravado.

Minimal fix proposed: em `unlock_free`, considerar sucesso quando o worktree já não tem lock (ler o `locked` do porcelain antes, ou aceitar o "is not locked"), e não religar um lock que não existia quando a remoção falhar.

**Insumos**

- quenching/assets/bin/quenching/git/slots.py:235-237 (`unlock_free` → `_unlock`)
- quenching/assets/bin/quenching/git/prune.py:125-131 (recusa `git-prune-unlock-failed`)
- `git worktree unlock ~/Projetos/quenching-slot-7` → `fatal: … is not locked`, exit 128
- limpeza pós-release 7.19.0, 2026-11-27
