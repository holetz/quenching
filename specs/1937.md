## Problem

Achado reproduzido pelo reviewer `opus` na revisão de correção do épico 1928 (rodada 1 do autopilot de 2026-10-17), sobre o merge `5392dc95` (#1932, spec 1849).

Em `plugins/quenching/assets/bin/quenching/specs/commands/doctor.py:92-94`, o aviso de backend inferido só aparece quando falta o arquivo de config: `inferred = not cfg.get("present", True)`. A inferência não depende de o arquivo existir:
- `common/config.py:168-174` sempre define `provider` a partir do remote.
- `specs/config.py:379` copia esse valor para `"backend": provider`.
- `_read_backend` (`specs/config.py:181-186`) só sobrescreve quando o arquivo declara `"git"`.

Com isso, um `.claude/quenching.json` sem a chave `backend` (só `{"specs": {...}}`) num remote GitHub chega com `backend: github` inferido e `present: true`. O `sp-backend-deprecated` sai sem "inferred" e sem o pedido de declarar `backend: git`, e esse é o caso do título da 1849. O teste `plugins/quenching/tests/test_specs_doctor.py:64-82` faz mock de `load_config` e só exercita `present=False/True` com o backend já resolvido.

**Reprodução:**
- `cq git history show 6e977e0f --path plugins/quenching/assets/bin/quenching/specs/commands/doctor.py`
- `grep -n 'def _read_backend' -A30 plugins/quenching/assets/bin/quenching/specs/config.py`
- `sed -n 360,400p plugins/quenching/assets/bin/quenching/specs/config.py`
- `sed -n 164,175p plugins/quenching/assets/bin/quenching/common/config.py`

**Consequência.** Um projeto que tem config mas nunca escolheu o backend cai no store deprecado sem receber o aviso que a 1849 prometia.

## Proposal

- `load_config` de `specs/config.py` passa a expor `backendDeclared`: verdadeiro só quando o arquivo de config traz a chave `backend` como string não vazia.
- `sp-backend-deprecated` em `doctor.py` marca "inferred" (texto e remédio de declarar `backend: git`) sempre que `backendDeclared` for falso, com ou sem arquivo de config.
- Um teste exercita o caminho real, sem mock de `load_config`: `.claude/quenching.json` só com `{"specs": {...}}` num remote GitHub produz o aviso com "inferred".
- Os espelhos gerados ficam regenerados.

## Out of Scope

- Mudar como o backend é resolvido (`provider` continua inferido do remote): só o aviso muda.
- Deixar de aceitar `backend: github` declarado: continua deprecado, sem "inferred".
- Qualquer outro finding do doctor.

## Design

- Decisão: o fato "o arquivo declara o backend" é lido onde o arquivo é lido (`_read_backend`), não deduzido em `doctor.py` a partir de `present`. Regra durável: o que foi inferido e o que foi declarado são campos distintos do config, e quem avisa lê o campo.
- `out["backendDeclared"]` nasce `False` no dicionário base e vira `True` em `_read_backend` quando `obj.get("backend")` é string não vazia, qualquer que seja o valor.
- Em `doctor.py`, `inferred = not cfg.get("backendDeclared", False)`.

### Mapa de dependências (2026-10-17)

- `specs/config.py` é consumido por `doctor.py` e pelos demais comandos de specs; a chave nova é aditiva, nenhum consumidor existente a lê.
- Os espelhos de `specs/config.py` e `specs/commands/doctor.py` em `quenching-specs`, `quenching-specs-reader` e `quenching-codex` são derivados e se regeneram pelos geradores do repositório.

## Alternatives Considered

- Manter `present` e acrescentar a checagem do arquivo em `doctor.py`: rejeitada, duplicaria em `doctor.py` a leitura do arquivo que `_read_backend` já faz.

## Open Decisions

- none — o comportamento para `backend` declarado como `github`/`azure-boards` é "declarado, sem inferred", coerente com a mensagem atual; assumido por evidência do código.

## Risks

- Um consumidor externo do dicionário de `load_config` que compare chaves exatas: mitigado por a chave ser só aditiva.
- Os testes existentes mockam `load_config` sem `backendDeclared`: o `cfg.get(..., False)` os faria passar a "inferred"; os asserts desses testes são revisados na tarefa 1.1.
