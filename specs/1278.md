## Problem

A 1265 (#1273) deu ao verifier, que é só leitura, grants com curinga no meio: `Bash(git -C * status:*)`, `Bash(git -C * stash list:*)` (e os mesmos para `reflog show` e `merge-base`) e `Bash(bash */scripts/verify_repo.sh:*)` (`plugins/quenching/agents/verifier.md:4`). Pela documentação de permissões do Claude Code, `*` casa qualquer texto, inclusive espaços. A re-revisão de 2026-10-08 reproduziu, num repositório descartável, o que o git executa para comandos que casam esses padrões: `git -C repo branch -D victim1 status` apagou a branch; `git -C repo -c core.fsmonitor="touch …" status` executou o comando; `git -C repo diff --output=<arquivo fora> -- status` zerou o arquivo; `git -C repo clean -fdx -- . status` removeu os não rastreados; e `bash -c "touch …" x/scripts/verify_repo.sh` executou código. Os grants antigos `git log:*` e `git diff:*` também admitem `--output=<arquivo>`. E `verifier.md:23-24` ainda manda rodar `bash scripts/verify_repo.sh` sem caminho, contradizendo `:14-18`.

Consequência: o agente de aceite, documentado como só leitura, pode apagar branches e trabalho, truncar arquivos e rodar código — e fica exposto a prompt injection vinda do diff que audita. É uma regressão de segurança introduzida pela própria noite.

## Proposal

Tirar do `verifier` todo grant `Bash(git …)` e `Bash(bash …)` e dar a ele um único verbo `cq` estreito, `cq git audit`, que executa por conta própria — com argv fixo, nunca montado a partir do texto do agente — as leituras que as checagens 2, 3, 4, 5 e 7 precisam dentro do worktree da spec. O grant passa a ser `Bash(cq git audit:*)`: um prefixo sem `*` no meio, cujas opções o argparse do próprio verbo recusa quando não as conhece. O frontmatter final do agente fica `Read, Grep, Glob, Bash(cq specs status:*), Bash(cq specs show:*), Bash(cq git audit:*), Bash(gh pr view:*)`.

```
hoje:  verifier --(git -C * status:*)--> git <qualquer argv> ... status     (apaga, trunca, executa)
depois: verifier --(cq git audit:*)--> argparse --> git argv fixo, cwd = worktree registrado
```

O verbo recebe `--worktree <path> --base <ref> --branch <ref> [--sha <sha>]… [--gate] [--json]`, recusa (exit 2) um worktree que `git worktree list --porcelain` não registra e qualquer ref que comece com `-` ou não resolva para commit, e devolve um payload com `status`, `stash`, `commits`, `changed`, `ancestry`, `reflog.branch`, `reflog.head` e, com `--gate`, o exit code de `bash scripts/verify_repo.sh` rodado com cwd no worktree.

## Out of Scope

- Os grants do `orchestrator` (`Bash(git log:*)`, `Bash(git status:*)` …): têm o mesmo vetor `--output=` em `git log`, mas são outro agente e outra revisão; ficam como uma linha em `## Discoveries`.
- Mudar o que o `verifier` checa ou o seu formato de retorno: só muda o meio pelo qual ele mede.
- Corrigir a cópia instalada 6.4.0 em `~/.claude/plugins/cache/…`: ela só muda por release, que é do `/release`.
- Endurecer o próprio `scripts/verify_repo.sh` contra um diff malicioso: rodar o gate é executar o código da branch por definição (ver `## Risks`).

## Design

O verbo segue o molde de `git/stale.py`: um módulo, um `cmd_audit(args)`, `emit` para as duas renderizações, `refuse` para exit 2. Cada chamada git usa `_git_run` com cwd no worktree e prefixo fixo `git --no-optional-locks -c core.fsmonitor=false -c core.hooksPath=/dev/null`, para que nem a configuração do repositório auditado execute algo durante a leitura. Refs passam por `git rev-parse --verify --quiet --end-of-options <ref>^{commit}` antes de qualquer uso, e só o sha resolvido entra nas chamadas seguintes (`log --oneline <base>..<branch>`, `diff --name-only <base>...<branch>`, `merge-base --is-ancestor <sha> <branch>`). O reflog lê `reflog show --format=%gs refs/heads/<branch>` (nome validado por `check-ref-format --branch`) e `reflog show --format=%gs HEAD` no worktree. O gate roda `bash scripts/verify_repo.sh` via `subprocess.run` com argv fixo, cwd no worktree e timeout de 1800 s; ausente o script, `gate` vem `{"exit": null, "reason": "absent"}`.

O verbo reporta fatos e sai 0; julgamento é do `verifier`. Recusa (2) só para entrada inválida.

## Open Decisions

- Se o gate deve ficar dentro do verbo (`--gate`) ou sair para `cq proof`: decidido aqui por `--gate` no próprio audit para manter um único grant; revisitado na revisão de segurança do `/quenching:specs:conclude` se ela apontar que um verbo de leitura não deveria executar o gate.

## Risks

- `--gate` executa `scripts/verify_repo.sh` da branch auditada, que o worker pode ter alterado: é a mesma execução que a checagem 3 já fazia, agora sem argv livre. Aceito; o grant deixa de admitir qualquer comando além desse script.
- O agente instalado (6.4.0) não roda a correção: o `cq` no PATH dele não tem `audit`, e o `verifier.md` instalado segue com `Bash(git branch:*)`. A correção só vale após o próximo release; até lá as execuções usam a cópia antiga.
- O emulador `match.py` aproxima o casamento do Claude Code pela documentação; um casamento real mais permissivo que o documentado não seria visto por ele. Os testes guardam a forma dos grants, não o motor.
