## Problem

A 1204 (#1226) deixou aberta, em Open Decisions, se push e PR devem sair do spec-runner para o git-steward no fluxo orquestrado; o Outcome dela ainda diz que depende da 1185, que entrou em `main` (#1206). A medida que motivou a pergunta: nos logs de sessão de 2026-09-24 a 2026-10-07, a criação de PR dentro do runner custou em média 372K tokens por run (14 runs), contra 61K e 93K quando o git-steward a fez (2 runs); o spec-runner responde por 83% dos tokens orquestrados.

Consequência: cada spec orquestrada paga ~280K tokens a mais num passo mecânico, e o comportamento do pouso segue dividido entre dois agentes.

## Proposal

- In an orchestrated run (input carries `autonomous`), `/quenching:specs:conclude` stops after the green gate and names the PR handoff instead of invoking `/quenching:git:pr:create`; the `spec-runner` returns `STATE: done` with `PR: -`.
- The `orchestrator` hands the `pr` step (push and PR) to the `git-steward`, with `autonomous`, only after the verifier returns PASS for the spec.
- The standalone `low` gear (no `autonomous`) keeps chaining `pr:create`.

## Out of Scope

- The merge step stays out: neither agent merges. The report mold and any other autonomous behaviour stay as the 1204 left them.
- Measuring the token saving in a new run: deferred, it needs real orchestrated runs.

## Validation

- `bash scripts/verify_repo.sh` exits 0.
- `python3 -m unittest discover -s plugins/quenching/tests -p 'test_specs_execute.py'` passes, asserting that conclude does not chain `pr:create` under `autonomous`.

## Design

Decision: move push and PR to the git-steward. Evidence: the 14 runner PR creations cost 372K tokens on average against 61K and 93K for the steward (2 runs); the steward already exists, already forwards `autonomous` to `pr:create`, and the orchestrator already routes mechanical steps to it. Assumption: the gap is dominated by the runner's accumulated context, so a fresh steward context stays cheap.

Durable rule: the worker that built the spec never publishes it in an orchestrated run; the publish is a separate step after independent acceptance. This also fits the orchestrator rule that a PR is handed over only for a spec the verifier accepted. `conclude` already archives before the handoff, so check 8 holds without a PR.

Binding contract: `git-steward` pushes only when its prompt names the step and target, so the orchestrator prompt names push and the PR against the base.

## Alternatives Considered

- Keep the runner publishing and trim its context: rejected, the cost is the runner's accumulated context, which cannot be trimmed at the last step.
- A new `no-pr` word for conclude: rejected, `autonomous` is only ever passed by the spec-runner, so a second word is surface with no caller.

## Open Decisions

- none — the 1204 question is decided here; token savings are measured by the next orchestrated runs.

## Risks

- A PR is never opened if the orchestrator skips the step: mitigated by the orchestrator protocol naming it as part of acceptance, and a spec without a PR is reported as `PR: -`.
- A spec archived with no PR on its branch: ACCEPTED — the branch stays pushable by the steward or the human.
