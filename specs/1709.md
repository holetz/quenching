## Problem

Correctness review of PR #1708 (range cdf32779..e7bc280f) reproduced a RED cleanup failure in targets using checkout conversions. plugins/quenching/agents/spec-runner.md:50 and plugins/quenching/assets/references/specs-execute/execution.md:146 restore tracked test files with `git -C .quenching/red show HEAD:<file> > .quenching/red/<file>`. This emits repository bytes instead of checkout bytes.

Reproduction in an isolated fixture with a committed tests/test_x.py and `.gitattributes` containing `*.py text eol=crlf`:

```bash
git worktree add -q --detach .quenching/red "$BASE"
cp tests/test_x.py .quenching/red/tests/test_x.py
git -C .quenching/red show HEAD:tests/test_x.py > .quenching/red/tests/test_x.py
git -C .quenching/red status --short
git worktree remove .quenching/red
```

Actual output: ` M tests/test_x.py`, then `fatal: ... contains modified or untracked files, use --force to delete it`, exit 128. The reviewer independently reproduced the same failure with core.autocrlf=true. Plain LF targets clean up successfully. Git 2.43.0 on Linux. No LFS reproduction was performed.

Consequence: the documented restoration leaves the RED worktree dirty, so its safe removal is refused, the runner blocks, and the nested RED worktree prevents retiring the spec worktree. Fix the restoration contract and protect this case with a meaningful regression check. Preserve unrelated files and existing prohibitions on force removal; do not widen grants, hooks, scripts, CI, or agent tools. Any solution requiring such widening must be deferred to the human epic. The reviewer verified that cat-file --filters restores the expected bytes, but solution selection must also account for existing tool grants and filter execution boundaries.

## Proposal

Trocar, nos dois portadores do contrato (`plugins/quenching/agents/spec-runner.md:50` e `plugins/quenching/assets/references/specs-execute/execution.md:146`), a restauração `git -C .quenching/red show HEAD:<file> > .quenching/red/<file>` por `git -C .quenching/red cat-file --filters HEAD:<file> > .quenching/red/<file>`. O `--filters` aplica ao blob as mesmas conversões de checkout (`eol`, `autocrlf`, `filter.*.smudge`) que o `git worktree add` aplicou, então a árvore volta a bater com o índice e o remove sem `--force` passa. Também ganha um teste de comportamento que executa o comando documentado numa fixture git com conversão de fim de linha.

## Out of Scope

- Grants, `tools:` do `spec-runner`, `allowed-tools`, hooks, `scripts/`, CI e `.claude/settings.json`: nada muda.
- As proibições existentes continuam: sem `checkout`, `restore`, `stash`, `git apply -R`, `worktree remove --force` e sem outro caminho além de `.quenching/red`.
- Reproduzir LFS, que não foi reproduzido. A correção o cobre pelo mesmo mecanismo, mas não entra no teste.
- O caso em que o teste copiado sobrescreve o próprio `.gitattributes`.
- Mudar o desenho do fluxo de RED (onde a worktree mora, quem a remove) ou o protocolo autônomo.

## Impact

O `spec-runner` e quem segue `/quenching:specs:execute` em repositórios consumidores com `eol=crlf`, `core.autocrlf=true` ou filtros de checkout. Hoje esses alvos bloqueiam (`STATE: blocked`) e prendem o `retire` da worktree da spec. Em alvos LF sem filtros, o comportamento não muda, porque `cat-file --filters` devolve os mesmos bytes que `show`. São três arquivos: duas prosas executáveis e um teste.

## Validation

- **Aceite A1:** em uma fixture git com `.gitattributes` `*.py text eol=crlf`, sobrescrever `tests/test_x.py` na worktree `.quenching/red` e restaurá-lo com o comando extraído literalmente de cada portador deixa `git -C .quenching/red status --short` vazio, e `git worktree remove .quenching/red` sai com 0 sem `--force`.
- **Aceite A2:** o mesmo vale com `core.autocrlf=true` e sem `.gitattributes`.
- **Aceite A3:** em um alvo LF sem atributos, o mesmo fluxo continua limpo (sem regressão).
- **Aceite A4:** os testes de prosa exigem `git -C .quenching/red cat-file --filters HEAD:<file>` nos dois portadores e recusam `show HEAD:<file>`, `checkout`, `restore` e `worktree remove --force`.
- **RED:** o teste novo, copiado para uma worktree da base e7bc280f, falha ali porque a prosa da base ainda usa `show`. Isso é registrado como `RED: <test> fails without <fix> (copied test, base worktree)`.
- **Evidência prévia:** a fixture do revisor (`../resume-review.json`) e uma reprodução independente em git 2.43.0 confirmaram que `show` deixa ` M` com remove recusado (exit 128) e que `cat-file --filters` deixa o remove limpo nos modos `attr` e `autocrlf`.
- `python3 -m unittest plugins/quenching/tests/test_specs_execute.py` sai com 0, e `bash scripts/verify_repo.sh` sai com 0.

## Design

Os dois portadores mudam só no verbo de restauração. O resto da frase fica como está: apagar o teste copiado se ele é novo, `worktree remove` sem `--force`, `rmdir .quenching` e `STATE: blocked` se o remove recusar. Uma meia frase explica por que é `--filters`: devolve os bytes do checkout, não os do repositório.

Em `test_specs_execute.py`, `test_red_cleanup_restores_tracked_file_from_base` passa a exigir `cat-file --filters HEAD:<file>` e a proibir `show HEAD:<file>`. Um teste novo de comportamento, dentro de `tempfile.TemporaryDirectory()` e com o helper `git()` que já existe, monta três casos (`eol=crlf`, `autocrlf`, LF puro). O comando sai da prosa de cada portador, com `<file>` substituído, e roda por `subprocess` sem `shell=True`: redireciona o stdout do `git cat-file` para o arquivo. O teste confirma o status vazio e o remove com 0. Como o comando vem da prosa, uma regressão textual para `show` derruba o teste.

**Consistência de permissões:** o `spec-runner` já tem `Bash`, e `git cat-file` é leitura. Os filtros que `--filters` executa são os mesmos que o `git worktree add --detach .quenching/red <base>` já executou no checkout dessa base. Então não há grant nem fronteira de execução novos.

## Alternatives Considered

- **`git -C .quenching/red checkout -- <file>` ou `restore`:** recusado, porque o contrato proíbe esses comandos na RED (risco de apagar trabalho na checkout compartilhada) e o teste existente os recusa.
- **`git worktree remove --force`:** recusado, porque a proibição é explícita e mascararia sujeira real.
- **Backup do arquivo original antes de sobrescrever e cópia de volta depois:** funciona sem filtros, mas acrescenta estado e passos ao runner. O `cat-file --filters` resolve num comando, a partir da base.
- **`git show` seguido de normalização manual de EOL:** não cobre filtros nem `autocrlf` de forma geral, e é frágil.
- **Alterar hooks, scripts ou grants para limpar a RED automaticamente:** fora da política do épico 1710, iria para needs-human. Não é necessário.

## Open Decisions

- none — a correção cabe nas permissões existentes e não pede decisão de protocolo autônomo. Se o build descobrir que precisa alargar algo, para e vira needs-human no épico 1690.

## Risks

- **Filtros de smudge com rede (LFS):** o `--filters` pode acessar a rede. O `worktree add` da mesma base já fez isso, então não há exposição nova. Não está coberto por teste.
- **Teste de fixture dependente de git:** a CI precisa de git ≥ 2.11 (`--filters`). O repositório já usa fixtures git em `test_specs_execute.py`.
- **Avisos `LF will be replaced by CRLF` no stderr da fixture:** são inofensivos, e o teste não deve fazer assert sobre o stderr.
