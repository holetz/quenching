## Problem

Achado reproduzido pelo reviewer (opus) do épico 1978, 2026-10-22, sobre o merge da 1976 (#1981, 9198f22df).

`plugins/quenching/README.md:325-327` diz que "Any change, a git command of the guard that fails, or any file-system error while taking the snapshot, before or after, is exit `2` `codex-git-guard` with no fallback". Em `plugins/quenching/assets/bin/quenching/codex/review.py:173` o payload base é montado como `out = {"ok": False, "fallback": True, …}`. A recusa por mudança (ref movido ou path alterado) volta em `review.py:186` como `return {**out, "code": "codex-git-guard", …}` e não sobrescreve `fallback`, então carrega `"fallback": True`. Só as recusas por falha de git e por erro de sistema de arquivos passam por `guard_refusal`, que não tem a chave `fallback`. `codex-pillar.md:100` limita o "no fallback" a esses dois casos e bate com o código; o README não.

Reprodução: `cq git history show 9198f22df --path plugins/quenching/README.md` e `grep -n '"fallback": True\|return {\*\*out, "code"' plugins/quenching/assets/bin/quenching/codex/review.py` → `173: out = {"ok": False, "fallback": True, …` e `186: return {**out, "code": "codex-git-guard",`.

Consequência: o contrato documentado e o JSON divergem. Um consumidor que leia `fallback` de um payload da guarda vê `true` numa recusa que, pelo README e pelo autopilot (exit 2 `codex-git-guard` → parar e entregar ao humano), nunca tem fallback. Hoje nada lê essa chave (o reviewer procurou), então o risco é um consumidor futuro tratar a recusa como fallback e seguir em frente.

Correção esperada: decidir qual dos dois está errado. Recomendação do condutor: o payload da recusa por mudança passa a `"fallback": False`, alinhado ao `codex-pillar.md` e ao README, com um teste que confere a chave em cada um dos três caminhos de exit 2.

## Proposal

- O payload da recusa `codex-git-guard` por mudança no tree (ref movido ou path alterado) de `cq codex review` carrega `"fallback": false`.
- Os payloads das recusas `codex-git-guard` por falha de git e por erro de sistema de arquivos carregam `"fallback": false` explícito, de modo que os três caminhos de exit 2 da guarda exponham a mesma chave com o mesmo valor.
- Um teste confere `fallback` falso nos três caminhos de exit 2.
- O README, `codex-pillar.md` e o código passam a dizer a mesma coisa; nenhuma prosa muda.

## Out of Scope

- Alterar o README ou `codex-pillar.md`: os dois já descrevem o contrato correto (exit 2 não tem fallback); o código é que diverge.
- A recusa por mudança de `cq codex implement` (`implement.py`), que também herda `"fallback": True` do payload base: o README só afirma "no fallback" para a guarda do review; fica como achado em `## Discoveries`.
- Qualquer consumidor novo da chave `fallback`: hoje nenhum a lê.

## Design

- Decisão: o código se alinha à documentação, não o contrário. Recusa de guarda é uma parada para o humano (README, autopilot, `codex-pillar.md:100`); `fallback: true` seria o sinal oposto. Alternativa pesada: reescrever README e pillar para dizer que o payload carrega `fallback: true`, rejeitada por tornar a recusa legível como "seguir adiante".
- Regra durável: toda recusa `codex-git-guard` do review expõe `"fallback": false`; a chave nunca está ausente nem verdadeira num exit 2.
- A recusa por mudança troca o valor com `{**out, "fallback": False, "code": ...}`; `guard_refusal` ganha `"fallback": False` para os três caminhos terem o mesmo formato.
- Gerados: `plugins/quenching-specs/**`, `plugins/quenching-codex/**` e `.generated-files.json` saem dos geradores, nunca à mão.
