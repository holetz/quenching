## Problem

Na orquestração do épico 1197 (2026-10-08), `/quenching:git:pr:create` publicou os PRs #1224 e #1225 sem `Closes #<n>`, e o orquestrador corrigiu os corpos à mão. O corpo (`plugins/quenching/commands/git/pr/create.md:62-63`) tira o número da issue do `path` do status ("its trailing number is an issue `<n>`") e não tem fallback para o id da spec, que no backend GitHub é o próprio número da issue [causa exata a confirmar].

Consequência: a issue da spec não fecha com o merge e o vínculo PR↔spec some do provider; num run autônomo ninguém percebe.

## Proposal

- On `github`, `/quenching:git:pr:create` takes `<n>` from the status `id` (the spec id, which is the issue number), so the body always ends with `Closes #<n>` even when `path` is a file locator such as `quenching:specs/1238.md`.
- The `azure-boards` branch keeps reading the work item from the provider locator, unchanged.
- The command test pins the new github rule.

## Out of Scope

- Changing the azure-boards link rule: it is not reported broken.
- Verifying the issue state after merge: that belongs to `/quenching:specs:conclude`.

## Impact

### Product code this spec expects to touch

- `plugins/quenching/commands/git/pr/create.md` — step 2 provider-link paragraph
- `plugins/quenching/tests/test_git.py` — provider-locator fixture test
- `plugins/quenching/assets/codex/` — regenerated translation, if present

## Validation

- `python -m unittest discover -s plugins/quenching/tests -p 'test_git.py'` exits 0 and the pinned github rule is asserted.
- `bash scripts/verify_repo.sh` exits 0.
- Measured on main: `cq specs status --spec 1238 --json` gives `path` `quenching:specs/1238.md`, which has no trailing issue number, while `id` is 1238.

## Design

- Durable rule: on `github` the spec id is the issue number, so `Closes #<n>` takes `<n>` from the status `id`; `path` is a locator and is never parsed for the number.
- Alternative weighed: parse the number out of `path` with a regex. Rejected: the locator shape differs per backend and the id is already a field.

## Alternatives Considered

- Regex over `path`: rejected, see Design.
- Fixing the orchestrator to patch bodies by hand: rejected, it hides the defect.

## Open Decisions

- none — the cause is confirmed by measurement: `path` carries no issue number and the body has no fallback.

## Risks

- A non-GitHub backend whose id is not an issue number: mitigated by scoping the rule to `github`; azure-boards keeps its own rule.
