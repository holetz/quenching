## Problem

Com o `## Problem` no stdin, `cq specs new` imprime "next: write ## Problem, then continue with the provider-native spec ID" — instrução falsa — e a saída humana não carrega o id nativo nem o locator, de modo que o `&& cq specs validate --spec <id>` que o corpo de /quenching:specs:create manda encadear no mesmo bloco não tem de onde tirar o id. Observado em holetz/eclume#57 (2026-09-28): o id foi adivinhado por `gh issue list` e o primeiro `validate` saiu com `no spec with id '57'` antes de o issue ser indexado.

## Proposal

- A `cq specs new` whose stdin already carried a filled `## Problem` no longer prints "next: write ## Problem"; its human output points at the next real step.
- A bare capture (no `## Problem` from stdin) keeps telling the caller to write the Problem.
- The three copies of `create.py` stay byte-identical, and a regression test pins both outputs.

## Out of Scope

- The id missing from the human output: already fixed on main (`id: N` is printed, with a test), so it is not rebuilt.
- The `gh issue list` indexing lag that made the first `validate` fail with `no spec with id '57'`: a backend timing matter, deferred.
