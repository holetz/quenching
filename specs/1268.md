## Problem

O orquestrador de `main` diz que nenhum worker começa antes de a dependência ser mergeada (`plugins/quenching/agents/orchestrator.md:21-22`), manda o merge para o steward (`:36`) e cita um "merge step" (`:44-45`), mas o passo 4 só define o `pr` (`:45-48`); o `git-steward.md:18-20` só repassa `autonomous` ao `pr:create`; `commands/git/merge.md:38` pergunta a estratégia via AskUserQuestion sem token; e `commands/git/pr/create.md:15` diz que o pr:create "stops there". Achado da revisão de coerência de 2026-10-08; nas orquestrações da noite o merge (`gh pr merge --merge --delete-branch`) só aconteceu porque o prompt da sessão condutora o mandou.

Consequência: num épico com dependências, a onda 2 nunca fica pronta com os agentes de `main` — o orquestrador para ou o steward volta `blocked`; rodar `git:merge` local com o PR aberto contornaria o PR.

## Proposal

Dar dono ao merge que as ondas exigem: o `orchestrator` passa a definir um passo `merge` de PR, entregue ao `git-steward`, e o `git-steward` ganha a regra estreita que o executa. O merge roda no próprio PR (`gh pr merge <url> --merge`, sem `--delete-branch`, `--admin`, `--auto`, `--squash` ou `--rebase`), só para um spec já aceito pelo `verifier` (PASS, check 8 incluído) e com PR publicado, só quando um spec ainda pendente no DAG depende dele, e só quando o run carrega `autonomous`. Sem `autonomous`, os dependentes saem do DAG com `STATE: blocked` e `NOTE: needs-merge: <id> <PR url>`, espelhando o `needs-approval`. O `pr:create` deixa de afirmar que só o `/quenching:git:merge` faz merge.

## Out of Scope

- `/quenching:git:merge` (`commands/git/merge.md`) — continua sendo o merge local com a estratégia escolhida pelo humano; usá-lo com o PR aberto contornaria o PR, por isso o passo novo não passa por ele.
- Escolher estratégia no lugar do humano fora de um run `autonomous`: sem a palavra, nada é mergeado.
- Merge de specs folha (de que nenhum spec pendente depende): o PR fica aberto para o humano.
- Apagar a branch remota ou local após o merge — fica para `/quenching:git:cleanup`.
- Carimbar o record `merge` do spec no caminho de PR — vira linha de `## Discoveries`.
- Alterar os `tools:` dos agentes: `Bash(gh:*)` do `git-steward` já cobre `gh pr merge`; nenhuma concessão de ferramenta nova.

## Design

Contradição em `main` (origin/main 0f63e06b, depois do #1271): `orchestrator.md:21-22` exige dependência mergeada antes de qualquer worker; `:36` manda "merge" ao `git-steward`; `:44-45` cita "the merge step", mas o passo 4 (`:45-48`) só define o `pr`. `git-steward.md:18-20` só cobre o `pr`, e `:24` proíbe merge que o prompt não nomeie. `commands/git/merge.md:38` pergunta a estratégia por AskUserQuestion, sem token, e é local. `commands/git/pr/create.md:15` diz que o `pr:create` "stops there".

Fluxo proposto, por spec com dependentes pendentes:

```
worker → conclude (archive) → verifier PASS → git-steward pr (autonomous) → PR url
   └─ algum spec pendente depende dele?
        não → PR fica aberto (humano)
        sim, run autonomous → git-steward merge: gh pr merge <url> --merge → onda seguinte
        sim, sem autonomous → dependentes: blocked, needs-merge: <id> <url>
```

Concessão mais estreita: autorização em prosa, não ferramenta nova. O `git-steward` só roda o merge quando o prompt nomeia o passo `merge`, a URL do PR e carrega `autonomous`; estratégia fixa `--merge` (o padrão de `merge.md`, preserva os commits por tarefa); sem flags que apagam branch ou contornam proteção. `--delete-branch` fica fora também porque, numa worktree na branch do PR, o `gh` tentaria trocar de branch.

## Alternatives Considered

| Abordagem | Custo | Ganho | Fecha |
| --- | --- | --- | --- |
| `git-steward` roda `gh pr merge --merge` no passo `merge`, só com `autonomous` (escolhida) | 3 arquivos de prosa | ondas andam sem o prompt do condutor; PR preservado | nada |
| `git-steward` chama `/quenching:git:merge` | nenhum arquivo novo | reaproveita o comando | contorna o PR (merge local) e para no AskUserQuestion sem token |
| Dar o merge ao próprio `orchestrator` | grant `Bash(gh pr merge:*)` no orquestrador | um salto a menos | quebra "you never merge" e o papel de condutor |
| Relaxar a regra de onda (não exigir merge) | 1 linha | nada para mergear | workers da onda 2 constroem sobre base sem a dependência |

## Open Decisions

- Merge de specs folha num run `autonomous` — fica fora; decide-se numa spec própria se o humano pedir, pelo uso real das orquestrações.

## Risks

- Um merge automático entra em `main` sem revisão humana do PR — mitigado: só com `autonomous` (pré-resposta humana), só após `verifier` PASS e só para dependências que a onda seguinte exige.
- O PR pode não estar mergeável (checks vermelhos, conflito) — o `git-steward` devolve `STATE: blocked` com a saída do `gh`, nunca `--admin`.
- Os agentes instalados (6.4.0) não refletem a mudança até o próximo release — a prova fica textual.
