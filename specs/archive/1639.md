## Problem

Publishing a repository that began private can expose secrets removed from the current tree but retained in history, internal hosts and URLs, corporate addresses and machine paths in tracked files and commit metadata. Dependency licenses, missing third-party attribution, large committed binaries and generated artifacts, and historical authors whose licensing consent is unproven add separate publication risks. Baseline controls assume an already public project and do not establish pre-publication readiness. The existing security probe checks ignore coverage rather than historical secret contents.

Publication makes the history available to others and cannot be reliably undone once cloned. The owner needs a read-only assessment before align or publication, with safe locations and commit IDs, explicit blocking findings and warnings, and honest unmeasured coverage when an existing scanner or sufficient evidence is unavailable. Rewriting history remains the target owner's responsibility.

## Proposal

- Provide a distinct pre-publication readiness operation in the new front selected by spec 1637, separate from align and baseline conformity.
- Assess the working tree, reachable history and commit metadata through read-only local inspection and supported existing tools, including gitleaks, trufflehog and reuse lint where available.
- Return sanitized findings with class, location, commit where applicable, severity, coverage and a human-owned remediation route; never emit secret values or raw scanner output.
- Show publication blockers, warnings and unmeasured categories separately. A missing scanner, incomplete history or absent consent/license evidence cannot establish readiness.

## Out of Scope

- Repository visibility changes, publication, history rewriting, author identity rewriting, secret rotation, installing scanners or network verification of detected credentials.
- Automatic licensing choices, legal compatibility conclusions without evidence, inferring consent from commit authorship or DCO alone, and writing missing attribution.
- Extending frozen security, delivery, toolchain or proof probes; duplicating catalog controls owned by those fronts; spec 1638 owns any freeze exception.
- Implementing the new front's align/status and module packaging, which spec 1637 owns. Readiness has an additional publication-risk result rather than replacing baseline status.

### Operation and scope

The neutral internal engine is `quenching.opensource.readiness`. Its public flow is the `cq opensource readiness` verb and the read-only `/quenching-opensource:opensource:readiness` command on the `opensource` front the owner selected in spec 1637 (2026-10-17, D4 A). It runs before align when the user requests opening a private repository. It reports, and never invokes publishing, align writes or history repair. Standalone engine delivery alone is insufficient acceptance for this spec.

Inventory includes current tracked content and reachable commit history over local branches/tags. Declare the exact refs and history completeness; shallow or missing objects yield unmeasured historical coverage. Untracked/ignored files are neither silently scanned nor silently represented as committed history; report this boundary. Do not fetch, change refs, populate target caches or execute target repository scripts. Any temporary scanner report belongs outside the target in a disposable process-owned directory and is never retained raw.

### Coverage and evidence

Use existing supported gitleaks or trufflehog for secret content/history, with explicit versions, bounded execution and offline/no-verification options. Do not install or fall back to an unvalidated regular-expression secret detector as equivalent coverage. If neither is usable, secret assessment is not-measured. Adapt reuse lint as attribution/license-file evidence; it does not establish dependency license compatibility or author consent. These require structured target evidence and named human review; unavailable or ambiguous evidence stays not-measured. Review heuristic internal identifiers and large/generated artifacts as warnings unless an explicit policy elevates them; a secret finding blocks publication. Missing established attribution or confirmed incompatible license evidence blocks publication; unknown legal facts remain coverage gaps rather than invented failures.

Define stable finding classes and coverage rows for secrets, internal identifiers, dependency-license compatibility, attribution, large/generated artifacts and historical consent. Each finding includes a sanitized relative location (or opaque location identifier), a validated commit hash when historical, severity, disposition and owner remediation. Never include snippets, credentials, entropy matches, scanner messages, personal addresses or absolute machine paths. Treat scanner JSON fields, filenames and commit metadata as untrusted sensitive input; use allowlisted fields and fixed diagnostic codes. Unknown schema, unsupported safe flags or parser failure cannot produce a clean result.

### Result contract

The summary has separate blockers, warnings and unmeasured/refused coverage plus history scope and scanner versions. Typed exit 0 means a complete measured assessment with no findings; exit 1 means measured findings; exit 2 means assessment unavailable/refused/incomplete, with any already measured findings preserved; usage uses the shared CLI convention. A clean result describes the assessed scope and never grants visibility-change approval. Catalog maturity and baseline compliance are separate, with no readiness-to-OSPS score conversion.

## Open Decisions

- Resolved 2026-10-17 by the owner (D4 A): the front is `opensource`; readiness lives inside it on the single `cq opensource` entry point. Paths are bound in `## Impact` and `## Tasks`.
- Target-dependent licensing policy and historical author consent are decided by the target owner with explicit evidence during assessment; unknown decisions remain not-measured and do not prevent implementing the honest read-only result.
- Supported scanner versions, safe offline flags and bounded execution defaults must be established from the actual installed supported interfaces during task 1.1; inability to establish a safe adapter is reported refused/unmeasured, never a reason to run unsafe defaults. On the build host none of gitleaks, trufflehog or reuse is installed (2026-10-17), so adapters are proved against fixture scanners and real coverage reports not-measured there.
## Risks

- Scanner stdout/stderr, malformed payloads, filenames and commit metadata can leak sensitive values. Allowlist output fields, sanitize locations, suppress raw errors, and test sentinel absence across every output channel.
- Incomplete history or unavailable scanners can be misread as readiness. Carry per-category coverage and scope, exit inconclusive, and never equate no findings with approval.
- Scanner invocation may verify secrets remotely or write target state. Permit only supported offline read-only invocations, isolate temporary reports and refuse unknown safe capabilities.
- License and consent heuristics can create false legal assurances. Require explicit evidence and owner judgment; reuse/DCO/author lists alone cannot close these categories.
- Concurrent edits to cq and the new front could overwrite ownership. Resolve namespace and integration ownership before approval/execution; keep frozen probes unchanged.
