## Problem

The plugin converges four surfaces of a target repository — its knowledge, its plans, its design
source and its `.claude/` automation — and none of them reaches the layer the repository is
actually *operated* through: its executable entry points.

Measured on `databricks-risco-gold` on 2026-08-30, a target that has already adopted the OKF
bundle and the `.claude/` surface:

- `scripts/` holds **61 tracked Python modules, 12,653 lines, 13 packages**. Its own `README.md`
  — which the folder's `CLAUDE.md` names as "o mapa completo" — documents **8** of them.
  `bootstrap/`, `fork/` (1,700+ lines with a `cli.py` of its own), `migration/`, `naming/` and
  `revalidacao_gold/` appear nowhere in it.
- **28 modules carry `if __name__ == "__main__"`; the project declares zero `[project.scripts]`.**
  The only way to discover an entry point is to read a document that is already wrong.
- **13 modules resolve the repository root by hand** with `Path(__file__).resolve().parents[N]`,
  while one shared `achar_raiz()` exists and exactly two modules call it.
- **23 modules print; one logs. 19 exit through an untyped `SystemExit`.**
- **`clone_to_dev.py` and `clone_to_coop_0051.py` deep-clone production schemas into a sandbox,
  take no arguments at all, and are armed by editing booleans at the top of `main()`.** Twelve
  modules offer `--dry-run`; the other sixteen do not, and the destructive ones are in that
  second group.
- In `ci/deploy.py`, the build entry point itself, **six verification calls are disabled by
  comment** — `ci_check_external_fqn_catalogued`, `ci_check_fqn_without_task`,
  `ci_check_tasks_fqn_exists`, `ci_check_tasks_schemas`, `ci_check_columns_registry` and
  `run_ci_ruff`.

None of this is visible to any check this plugin ships, because the plugin has no notion of an
operations surface. The defect classes are general, not local to one repository: an entry point no
document names, a registry that drifts because a human maintains it, a destructive path armed by
editing source rather than by passing a flag, a gate switched off by a `#`. What is missing first
is the **contract** — what a conformant operations surface *is*. Without it a verifier has nothing
to verify against and an align has nothing to converge toward.
## Proposal

Declare `ops` as the plugin's sixth pillar and its fifth **front**: the target repository's
operations surface.

This spec writes the **contract alone** — the standard, the reference target structure, the
entry-point contract, the lifecycle rule and the vocabulary. It ships no code and no command body.
The verifier (`cq ops doctor`), the align and the minting command are three separate specs that
build against what this one declares, exactly as the design front's standard preceded its tooling.

The contract has four parts:

**1. The canonical tree.** One declared operations root (default `scripts/`), packages grouped by
domain and never by lifecycle, a generated registry document, and an `_archive/` for entry points
that have run their course.

**2. The normalized outer interface.** A fixed set of names every adopting repository answers to —
`bootstrap`, `setup`, `update`, `check`, `test`, `deploy` — after GitHub's *Scripts to Rule Them
All* pattern, implemented as a **router** over the domain packages and never as a second copy of
the logic. A repo declares **exactly one router as canonical**: a `[project.scripts]` console
script, a `justfile`, or a `Taskfile.yml`. Further wrappers are legal and common — a `justfile`
whose recipes call the console script is one router with a convenience skin, not two — and the
contract binds the declaration, not the file count.

**3. The entry-point contract**, seven rules. Each answers a measured defect class, and each is
either **checked** by the verifier or **prose** the align reports on but cannot decide:

| # | Rule | The defect it closes | Kind |
| --- | --- | --- | --- |
| 1 | Every entry point is reachable from the router and named by the generated registry | 5 undocumented packages | checked |
| 2 | Root resolution, `sys.path` and shared flags come from ONE bootstrap module | 13 hand-rolled `parents[N]` | checked |
| 3 | Exit codes are typed — `0` success, `1` findings, `2` misuse | 19 untyped `SystemExit` | checked |
| 4 | Data on stdout, diagnostics on stderr; `--json` puts nothing but data on stdout | 23 print / 1 log | checked |
| 5 | An entry point that writes outside the repo is preview-first, armed by flag and never by source edit | 2 unarmed deep-clones | checked |
| 6 | `--help` carries a usage example | discovery by stale prose | **prose**, with a static proxy |
| 7 | Every entry point declares a lifecycle — `active` or `archived` | one-shot code beside daily tooling | checked |

Rule 6 is prose because proving it means **running** the entry point to read its `--help`, and a
verifier that executes arbitrary target code to grade it is a worse defect than the one it grades.
Its checked proxy is static and honest about being a proxy: the parser carries a non-empty
`description` or `epilog`. The align reports the proxy and names the rule; it never claims the rule
itself was proven.

**4. The disabled-gate rule.** A verification call commented out inside an entry point is a
**finding, not a configuration**. A gate switched off by a `#` is invisible to every other check,
carries no record of who switched it off or when, and reads as present to anyone skimming the file.
A repo that wants a check off declares it off; it does not comment it out.

The standard also names the eight finding codes the next spec implements — `op-undocumented`,
`op-registry-stale`, `op-adhoc-root`, `op-untyped-exit`, `op-unarmed-write`, `op-disabled-check`,
`op-orphan`, `op-no-router` — so the verifier is written against a published contract rather than
inventing its own vocabulary.
## Out of Scope

- **Any code.** No `assets/bin/quenching/ops/` module, no `cq ops` route in `assets/bin/cq`.
  Spec `ops-inventory-and-doctor` owns all of it.
- **Any command body.** No `commands/ops/**`. Two later specs own the align, the status and the
  minting command.
- **Wiring the front into `/quenching:align`, the README surface table, or the Codex projection.**
  The integration spec owns them, after both fronts exist.
- **Changing `databricks-risco-gold`.** That repository is the *measured target* this contract is
  written against, not a deliverable here. Converging it is what running the finished front does.
- **Prescribing a task runner.** The contract requires exactly one router and names the three
  acceptable mechanisms; which one a repo picks is that repo's declaration.
- **Linting the entry points' internals.** The front converges the *surface* — discovery,
  contract, lifecycle. Code quality inside a module remains the target repo's own linter's job.

## Design

**Why a front and not a pillar.** `align-surface.md` draws the line: a **front** is a tree this
plugin converges toward a canonical shape and can prove with a verifier; a **pillar** like `git`
answers live questions about a target and converges nothing. `scripts/` is a tree, its conformant
shape is decidable from the tree plus the declared configuration, and a program can answer "is
there work?" with an exit code. So `ops` earns an `align`, a `status` and a row in the
aligned-front column.

**Why the name is `ops` and not `scripts`.** `command-surface.md` records why `skill` was retired
as a front name: it was simultaneously the front's name and the name of an artifact inside it.
`scripts` has exactly that defect — the artifacts inside are scripts. `ops` names the surface;
nothing inside it is called "an op".

**Why the contract ships before any code.** The design front's standard preceded its tooling, and
the ordering is not stylistic: a verifier written before its contract invents a private vocabulary,
and the standard that arrives later is then a transcription of whatever the code happened to do.
Publishing the eight finding codes here means spec 2 implements a contract it can be held to.

**Why the router is required but not chosen.** The normalized script pattern earns its place
because it makes the *outer* interface identical across repositories — a contributor who knows the
pattern needs no knowledge of the application. Which mechanism implements it is a real local
decision (a Python-only repo reasonably uses `[project.scripts]`; a polyglot one reasonably uses
`just`). Requiring one *declared* router is what the contract needs; requiring a particular one, or
forbidding a wrapper over it, would make the front un-adoptable in repos that already chose.

**Why the disabled-gate rule is a finding and not a warning.** The measured case is decisive: six
checks are commented out in the one entry point every deploy runs, and nothing in the repository —
not the linter, not the tests, not the README — reports it. A commented call is the only kind of
disabled gate that leaves no trace anywhere else. A declared-off check is greppable, dated, and
attributable; a `#` is none of those.

**How `op-disabled-check` is detected, and why the standard has to say so.** A comment is not in
the AST, so the code cannot be found the way the other seven are. The mechanism the standard
declares is `tokenize` over the entry point's source: a `COMMENT` token whose text, stripped of its
`#`, parses as a Python **call expression**, and whose indentation places it inside a function the
AST already identified as part of the entry point's own control flow. The standard names the
mechanism because a heuristic whose shape is not published is a heuristic nobody can argue with —
and because the measured target already pairs AST with `tokenize` in its own `task_lint.py`, so
this is a proven technique in the exact ecosystem the front is written for, not a hope.

**Why the registry is generated.** A hand-maintained map drifts the moment somebody adds a package
in a hurry, which is what the measured 8-of-13 is. Generation makes the drift impossible rather
than merely detectable, and makes `op-registry-stale` a one-command fix rather than an editing
chore.

**Why the pattern doc is a concept and not an external tool fact.** `external/` holds *what we
consume* — the measured behaviour of tools this plugin drives, like the `gh` CLI. The normalized
script pattern and the `clig.dev` conventions are neither: nothing here drives them, and they are
generic knowledge that would be true in a repo that never installed this plugin. `type-follows-home.md`
makes the home the signature of the type, so the doc goes to `concepts/automation/` and is stamped
`type: concept`.
## Alternatives Considered

- **Fold this into the `components` front.** Rejected: `components` converges `.claude/` — commands,
  agents, hooks, the harness files. An operations surface is the repo's own executable code, with a
  different canonical shape, a different verifier and a different audience (CI and operators, not
  agents). Sharing a namespace would force one `align` to carry two unrelated trees.
- **Ship the verifier first and let the standard follow.** Rejected for the reason under §Design:
  it inverts the dependency and produces a standard that documents an implementation.
- **Mandate one router mechanism (a `justfile`).** Rejected: it would refuse every repo that
  already ships `[project.scripts]`, including the measured target's own ecosystem, for a
  uniformity the *names* already provide.
- **Name the front `tooling`.** Rejected as less precise: `tooling` covers linters, formatters and
  editor configuration, none of which this front converges. `ops` names what the surface is for.
- **Make the registry hand-written but checked.** Rejected: a check that reports drift on a
  document a human must then edit is the same chore with an extra step. The measured target already
  has the check-free version of this and it drifted by five packages.

## Open Decisions

- **Where the front's configuration is declared.** `.claude/quenching.json` already carries
  `backend`, `specsBranch`, `worktreeSetup` and `profiles`; `opsRoot` and `router` fit there. The
  alternative is a front-local `ops.json`. Resolved at spec 2, task 1, against whichever the
  `config` loader can read without a second parser — the contract only requires that the two
  values are declared somewhere a verifier reads.
- **Whether `_archive/` is a directory or a frontmatter-style marker.** A directory is greppable
  and moves the code out of the way; a marker keeps import paths stable for anything still
  importing an archived module. Resolved in `lifecycle.md` at task 3.3, after the target's own
  one-shot packages are checked for inbound imports.
- **Whether the contract requires the router to be executable without the project installed.**
  `[project.scripts]` needs an install; `just` and `Taskfile` do not. Deferred to spec 2's doctor,
  which can report the difference rather than the standard forbidding a mechanism.
- **Whether `op-disabled-check`'s tokenize heuristic ships as an error or a warning on its first
  release.** The mechanism is declared here; its severity is spec 2's call, made against the false-positive
  rate measured on the target's 61 modules. The standard states both severities are legal and that
  the code may not change meaning when the severity does.
## Risks

- **A contract with no implementation ages badly.** If specs 2–4 stall, this spec leaves a standard
  describing a front that does not exist, which is exactly the `authority: current` drift
  `command-surface.md` warns about. *Mitigation:* the README row says **declared**, and the
  standard's own `authority` is set to reflect a contract awaiting its tooling rather than a shipped
  capability.
- **The seven rules are derived from one measured repository.** A contract generalized from a single
  target can encode that target's accidents. *Mitigation:* every rule is stated against a defect
  class and cites the external source that independently motivates it (`clig.dev` for streams and
  exit codes, the normalized script pattern for the outer names); the rule survives only if both
  the measurement and the external source support it.
- **`op-disabled-check` is a heuristic and will produce false positives.** A commented call inside a
  docstring example, a template, or a deliberately parked experiment is not a disabled gate.
  *Mitigation:* the mechanism is published (§How `op-disabled-check` is detected), the finding
  carries the line so a human dismisses it in one look, and its severity is left to spec 2 to set
  against a measured false-positive rate rather than fixed here by assertion.
- **Rule 6 can be mistaken for a proven check.** A reader who sees seven rules in one table may
  assume all seven are verified. *Mitigation:* the table carries a `Kind` column, and the align's
  report is required to name the proxy rather than the rule when only the proxy was checked —
  the same restraint `unproven-capability-warning.md` already binds elsewhere.
- **Adding a sixth pillar widens the surface every align-surface claim quantifies over.** Several
  standards say "the three local aligned fronts" and "five pillars". *Mitigation:* the Impact names
  `align-surface.md` and `command-surface.md` explicitly, and `citation-check.sh` is in the
  validation set precisely to catch the count claims this spec invalidates.
