## Problem

Achado reproduzido pela revisão de correção do épico 2247 (rodada 6 do autopilot 2026-11-21), em origin/main c23fda1a1.

Repro em repositório descartável: `git init -b main; git commit --allow-empty -m a; git branch ff; git commit --allow-empty -m b; git checkout ff; git merge --ff-only main; git checkout main`. Depois `cq git stale` → `stale branches: ff (merged)`; `slots.has_own_work(R,'ff')` → `False`; `cq git prune --branch ff` → `pruned branch ff`.

Onde: `quenching/assets/bin/quenching/git/stale.py:53` — `_has_own_commits` aceita a branch quando `created and created != [tip]`; um fast-forward tira o reflog do commit de criação, então uma branch sem commits próprios passa. É o critério antigo (2235) que 2241 trocou, no mesmo épico, por `slots.has_own_work` (`git/slots.py:211`, só entradas commit/cherry-pick/revert). A docstring em `stale.py:44` e o Design de 2242 afirmam paridade com `merge_evidence`/`_merged_holder`, e ela não existe. Por `chain` (`stale.py:93`), `remoteBranches` segue o mesmo caminho para uma branch local homônima só avançada.

Consequência: uma branch de spec cortada e apenas sincronizada com a base por fast-forward, ainda sem commits próprios, é listada como mesclada e apagada pelo prune — o caso que 2242 pretendia fechar. Não é regressão (antes do épico todo ancestral era apagado), é uma lacuna deixada pela correção.

## Proposal

`stale._has_own_commits` (`quenching/assets/bin/quenching/git/stale.py:43`) passa a decidir pela mesma regra de `slots.has_own_work` (`git/slots.py:205`): uma branch local tem trabalho próprio só quando o reflog de `refs/heads/<branch>` traz uma entrada `commit`, `cherry-pick` ou `revert`. O fallback pela first-parent chain (`tip not in chain`) fica restrito ao reflog vazio ou expirado, quando não há histórico para ler. Com isso, uma branch cortada e só avançada por fast-forward fica em `keptBranches` com `no-own-commits`, e `cq git prune --branch` a recusa. Por `chain`, o mesmo vale para `remoteBranches` de uma branch local homônima só avançada. A docstring e o standard `docs/standards/workflows/plan-git-record.md` passam a descrever a regra real.

## Out of Scope

- `slots.has_own_work`, `_merged_holder` e `promote.merge_evidence` — já usam a regra; não mudam.
- O critério de `remoteBranches` para tips fora da first-parent chain — continua listando por ancestralidade com merge commit.
- `cq git cleanup` e `prune` além do que herdam do relatório de `stale` — nenhum código próprio muda.
- O Design de 2242 (spec concluída) — não é reescrito.

## Design

- 2026-11-21 — Decisão do épico 2252: `_has_own_commits` lê os movimentos do reflog (`audit._reflog`); com reflog não vazio responde `slots.has_own_work(cwd, branch)`; vazio, mantém `tip not in chain`. Uma regra só para slot reclaim, `promote` e `stale`. `stale` importa de `quenching.git.slots` (que não importa `stale`: sem ciclo).
- Efeito: apaga menos branches. Uma branch criada já num tip fora da chain e nunca comitada (ex.: `git branch copia feature` depois do merge) passa a ficar `no-own-commits` — aceitável, o prune é conservador por desenho.

### Assumptions

- `has_own_work` lê o reflog local; em clones onde o reflog está desligado (`core.logAllRefUpdates=false`) o reflog é vazio e o fallback decide, como hoje — base do Design.

## Alternatives Considered

- Manter a regra "reflog moveu do commit de criação" e excluir entradas `merge`/fast-forward — reimplementaria `has_own_work` com outra lista; descartada por duplicar a regra que 2241 centralizou.
- Remover o fallback por chain — uma branch merged sem reflog deixaria de ser candidata; o épico decidiu mantê-lo para o reflog vazio.

## Open Decisions

- none — o épico 2252 (## Design, 2026-11-21) fixou a regra e o fallback.

## Risks

- Uma branch merged cujo reflog só tem entradas não-`commit` (ex.: criada por `reset`/`update-ref` sobre trabalho de outra) deixa de ser candidata — falso negativo seguro: fica em `keptBranches`, nada é apagado.

## Outcome

**O que entrou**

- `_has_own_commits` (`quenching/assets/bin/quenching/git/stale.py`) passa a delegar a `slots.has_own_work`, a mesma regra que o reclaim de slots e a evidência de merge do `cq specs promote` aplicam desde 2241: só um `commit`, `cherry-pick` ou `revert` no reflog conta como trabalho próprio. Uma branch apenas avançada por fast-forward até a base fica em `keptBranches` com `no-own-commits`, e `cq git prune --branch` a recusa (`git-prune-not-reported`). Com reflog vazio ou expirado, a cadeia first-parent da base continua decidindo.
- O mesmo vale para a candidatura de uma branch remota cuja homônima local só avançou por fast-forward.
- Dois testes de regressão em `quenching/tests/test_git.py` (classe `Stale`), e `docs/standards/workflows/plan-git-record.md` com a regra atualizada (fonte `spec 2250`).

**O que ficou de fora**

- Nenhuma mudança em `merge_evidence` nem em `has_own_work`; a regra continua única e mora em `slots`.

**Para o próximo leitor**

- Branch "mesclada" no relatório de `cq git stale` agora significa a mesma coisa nos três consumidores (stale/prune, reclaim de slot, promote). Um reflog expirado cai na first-parent chain, que não distingue uma branch cortada de uma mesclada por fast-forward sobre a base.
