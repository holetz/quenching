## Problem

The Azure Boards backend takes its organization and project from `az devops configure --list` (`specs/backends/azure.py:292`), a default that belongs to the machine, not to the repository: a person who works for two organizations must isolate `az` with `AZURE_CONFIG_DIR` per project to keep them apart (done by hand for quenching on 2026-10-24). Declare a store's organization and project (or GitHub owner and repository) in the repository's `specs` namespace, versioned beside `backend`, and resolve the credential outside the repository: the user layer (`~/.config/quenching/config.json`) names where it comes from — the OS keyring, `az`/`gh` logins, or an environment variable — and a secret is never written into the repository or a worktree. On forge's HTTP deployment the specs service holds one central credential as the single writer, and clients never see it.

Member S32 of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent).

## Proposal

- A repository declares where its spec store lives in the `specs` namespace of `.claude/quenching.json`: `specs.store.azure.{organization, project}` and `specs.store.github.repository`. A declared store is the answer; the machine's `az devops configure` defaults and `gh repo view` are no longer consulted for it.
- The credential is resolved outside the repository. The user layer (`~/.config/quenching/config.json`, `specs.credential.<azure|github>`) names where it comes from: the CLI's own login (optionally with a private config directory, which replaces the hand-set `AZURE_CONFIG_DIR`) or an environment variable that holds the token. The token is read at call time and handed to the one subprocess that needs it, never printed, cached or written.
- A secret can not reach the repository or a worktree through this path: a repository-layer `specs.credential`, or a `specs.store` key that names a secret, is refused with `sp-store-secret` (exit 2) before any spec is read or written.
- A `keyring` source, or any unknown source, is refused with a message that points at the `az`/`gh` login (which already uses the OS keyring), so no silent fallback to another credential happens.
- `cq specs config --json` shows the declared `store`, so the answer to "which board does this repository write to" is one read.
- `docs/standards/workflows/plugin-configuration.md` carries the contract.

## Out of Scope

- Writing to a real Azure DevOps organisation or GitHub repository: every test runs against doubles of `az` and `gh`.
- The OS keyring as a first-class source (a new dependency, or a per-OS shell-out). It stays an Open Decision.
- The credential held by the specs service on forge's HTTP deployment as the single writer. That belongs to the service members (2085, 2086); this spec only states in the standard that behind the service the client never resolves a credential. Nothing here implements the service side.
- Any change to grants, `allowed-tools`, hooks, CI or scripts (epic 2045), and any change to how the backend itself is selected (`backend` and the provider derived from `origin` are untouched).
- Moving the existing `azurePlacement` keys: they stay where they are; the store only adds the location of the store.

## Design

**Rule 1 — location is data of the repository, credential is data of the person.** The repository layer may say *which* organisation, project or repository; it may never carry anything that authenticates. The user layer may say *where the credential comes from*; it never says which store. Reason: the first is shared by every clone and reviewed in a PR, the second differs per person and must never be committed.

**Shape.**

```json
// .claude/quenching.json
{"specs": {"store": {"azure": {"organization": "https://dev.azure.com/<org>", "project": "<project>"},
                     "github": {"repository": "<owner>/<name>"}}}}

// ~/.config/quenching/config.json
{"specs": {"credential": {"azure":  {"source": "login", "configDir": "~/.config/azure-<name>"},
                          "github": {"source": "env",   "env": "<VARIABLE_NAME>"}}}}
```

**Rule 2 — declared wins, nothing declared is today's behaviour.** `resolve_azure_project` returns the declared organisation and project without `az devops configure --list` and without the project-name round trip (a declared project is a name, not a default that may be a GUID); `resolve_github_repo` returns the declared `owner/name` without `gh repo view` (no open-issue count, which the caller already treats as unknown). A bare organisation name is normalised to `https://dev.azure.com/<name>`. With no `specs.store`, the existing resolution runs untouched.

**Rule 3 — the secret travels only in the subprocess environment.** `store.subprocess_env(cwd, tool)` returns `None` (inherit, today's behaviour) or a copy of `os.environ` with the credential variables set: `source: login` sets `AZURE_CONFIG_DIR` / `GH_CONFIG_DIR` from `configDir` when given (expanded, a path not a secret); `source: env` reads the named variable at call time and sets `AZURE_DEVOPS_EXT_PAT` / `GH_TOKEN`. `_az_run` and `_gh_run` pass it as `env=`. The value is never put in argv, a refusal, the cache files or the config view. An unset variable refuses with `sp-credential-env-missing` naming the variable only; an unknown source (`keyring` included) refuses with `sp-credential-source`.

**Rule 4 — the repository layer is read raw.** The merged envelope hides which file a key came from, so `store.py` reads `.claude/quenching.json` itself (as `config/effective.py` does) to refuse `specs.credential` and secret-named store keys (`token`, `pat`, `password`, `secret`, `key`, case-insensitive, any depth) there. Any other unknown store key is refused as `sp-store-unknown-key`, so a typo does not silently fall back to the machine default.

**Binding contracts.** `docs/standards/workflows/plugin-configuration.md` (one configuration home, the user layer merges key by key and the repository wins, no flat fallback); `docs/standards/architecture/spec-backend.md` (one refusal boundary: every refusal is an exit-2 `BackendRefusal` with nothing read or written); the leak gate in `common/leak.py` stays in force on every write.

## Alternatives Considered

Reference projects read from epic holetz/forge#1 §Reference projects (2026-10-24):

- **microsoft/azure-devops-mcp (MIT, to confirm): adapts, in part.** It puts the organisation in the endpoint (`mcp.dev.azure.com/{org}`), not in a per-machine default, and authenticates with Entra ID outside the server's own configuration. Reused: the same split, location named explicitly and authentication resolved separately. Rejected: the remote endpoint and Entra ID flow itself, because this adapter drives the `az` CLI and its login; a remote MCP endpoint is the specs service's concern (2085).
- **MrLesk/Backlog.md (MIT): adapts, in part.** It versions the store's configuration beside the store in the repository. Reused: committing the location. Rejected: it has no external tracker and so no credential model to compare; nothing to reuse for the user layer.
- **Keep reading `az devops configure` / `gh repo view` and document `AZURE_CONFIG_DIR`.** Rejected: it is the machine default the Problem names, and a wrong default writes to someone else's board without failing.
- **One file that carries location and credential reference, committed.** Rejected: a reference to a credential source differs per person and would be reviewed and merged as if it were shared.
- **A first-class OS keyring source now.** Deferred (Open Decisions): the `az` and `gh` logins already store the token in the OS keyring, and a direct source adds a dependency or a per-OS shell-out for no new capability.

## Open Decisions

- Whether a `keyring` source is worth adding. Decided by a measured need: a person who cannot use the `az`/`gh` login or an environment variable. Until then it is refused with a pointer to the login, and the refusal names this spec's follow-up path (`cq specs discover`).
- Whether a declared `specs.store` should also be cross-checked against the `origin` provider and warn on a mismatch (a GitHub store declared in a repository whose remote is Azure DevOps). Decided at the first report of such a repository; today the declaration is authoritative, as the Problem asks.

## Risks

- A declared store pointing at the wrong board writes to it. Mitigation: the declaration is versioned and reviewed in a PR, is shown by `cq specs config --json`, and is validated for shape before any call.
- A refusal text or a log could echo a token. Mitigation: the value is never placed in argv, cache or a message; the tests assert the token string is absent from every refusal and from argv.
- The credential refusal escaping from `_az_run` into `git/base.py`, which has no handler. Mitigation: that caller catches `BackendRefusal` and reads it as "unknown", and a test covers it.
- A user-layer `specs.store` would merge into the namespace and look like a repository declaration. Mitigation: only the repository file is read for `store`; ACCEPTED — a user-layer `store` is ignored and the effective view still lists it for the person to see.
