## Problem

Na spec 314 (épico 306, 2026-11-24), a tarefa 2.4 redeployou este repositório e o diff passou a carregar `opencode.json`. Com `QUENCHING_TEST_SCOPE=affected bash scripts/verify_repo.sh`, o seletor abriu para a suíte inteira (3394 testes, ~47 s) em vez dos ~15 s de `test_deploy*.py`: `scripts/toolchain/affected.py:381` devolve `fail-open: no rule covers opencode.json`. O mesmo acontece com `.mcp.json`; já `.claude/settings.json` cai em `IRRELEVANT` (`.claude/`, `affected.py:50-59`) e é tratado como "change outside the tested surfaces" — assimetria entre arquivos que o mesmo `cq deploy` escreve.

Reprodução (no conclude da 314):

```
python3 - <<'PY'
import pathlib,sys; sys.path.insert(0,'.')
from scripts.toolchain import affected as a
for f in ['opencode.json','.claude/settings.json','.mcp.json']:
    print(f, a.select(pathlib.Path('.'), files=[f]).reasons)
PY
opencode.json ('fail-open: no rule covers opencode.json',)
.claude/settings.json ('change outside the tested surfaces',)
.mcp.json ('fail-open: no rule covers .mcp.json',)
```

O que a melhoria tem de tornar impossível: uma spec cujo diff só acrescenta os arquivos de configuração de harness que o deploy gera pagar a suíte inteira no escopo `affected`, e esses arquivos receberem tratamentos diferentes entre si.

Minimal fix proposed: uma `Rule` em `RULES` de `scripts/toolchain/affected.py` mapeando `opencode.json`, `.mcp.json` (e, coerente, `.claude/settings.json`/`.codex/config.toml` se forem escritos pelo deploy) para `test_deploy*`, com teste em `quenching/tests/` do seletor.

**Insumos**

- `scripts/toolchain/affected.py:37-59` (GLOBAL, IRRELEVANT), `:72` (RULES), `:377-381` (fail-open)
- spec 314, `## Discoveries` (linha `measurement:` com 3394 testes/47 s e a linha sobre o escopo affected)
- conserto vive neste repositório (`scripts/toolchain/`), não no payload deployado

## Proposal

- `opencode.json`, `.mcp.json`, `.codex/config.toml` and `.claude/settings.json` — the four harness files `cq deploy` writes at the root — resolve to one `Rule` in `scripts/toolchain/affected.py` that selects `test_deploy*`.
- A diff that only adds or changes those files selects the deploy tests and is `complete=False` under `QUENCHING_TEST_SCOPE=affected`, instead of failing open to the whole suite.
- The four files are treated alike: none of them is `fail-open` and none is silently `IRRELEVANT`.
- A test in `quenching/tests/test_toolchain_affected.py` pins that treatment.

## Out of Scope

- Any change to `.agents/`, `.opencode/` or the other `IRRELEVANT` prefixes: they are generated mirrors the deployed-surface lockstep check already guards.
- Any change to the fail-open line for unknown paths: a path no rule covers still opens to the whole suite.
- Changing what `diffUnreadable` does (spec 362, merged).

## Impact

### Product code this spec expects to touch

- `scripts/toolchain/affected.py` — one `Rule` entry in `RULES`
- `quenching/tests/test_toolchain_affected.py` — the selection test

## Validation

- `python3 - <<'PY'` selecting `['opencode.json']`, `['.mcp.json']`, `['.codex/config.toml']`, `['.claude/settings.json']` each returns `complete=False` and tests including `quenching/tests/test_deploy.py`.
- `python3 -m unittest quenching.tests.test_toolchain_affected` is green.
- `python3 -m scripts.toolchain.test --affected` on the branch diff stays green.

## Design

### Decisions

- **One `Rule`, `test_deploy*`, prefixes the four exact paths.** `_covers` matches a path equal to the prefix, so a root file needs no new matching code. The deploy writes these files (`deploy/mcpfiles.py` `FILES`, `.claude/settings.json` through the settings merge), and `test_deploy.py`, `test_deploy_opencode_config.py` and `test_deploy_settings.py` are the tests that read them.
- **`.claude/settings.json` moves from irrelevant to covered.** Rules are consulted before `IRRELEVANT`, so the rule overrides the `.claude/` prefix for this one file only; the rest of `.claude/` stays generated mirror. This is a strengthening: a settings diff now runs the settings tests it used to skip.
- **No removed or weakened line in `affected.py`.** The change adds an entry; the fail-open and `diffUnreadable` lines are untouched.

### Assumptions

- The `.codex/config.toml` path is written by the deploy (mcpfiles `CODEX`), so it belongs with the others — supports the Rule.

### Mapa de dependências

- `scripts/toolchain/affected.py` `RULES` ← `quenching/tests/test_toolchain_affected.py` (`test_every_rule_names_a_test_that_exists` resolves every stem).
- `scripts/` is covered by a Rule, and `scripts/toolchain/` is GLOBAL: this edit itself runs the whole suite at the gate; that is expected.

## Alternatives Considered

- Add the four paths to `IRRELEVANT`: rejected, a bad `opencode.json` merge would then go unproven by `test_deploy_opencode_config.py`.
- A separate Rule per file: rejected, they share one test set and one owner.

## Open Decisions

- none — every decision above is settled by the deploy code and the existing rule shape.

## Risks

- A new test stem that matches nothing makes the selector fail open: mitigated by `test_every_rule_names_a_test_that_exists`.
- ACCEPTED — the extra `test_deploy*` run (~15 s) on a `.claude/settings.json`-only diff; safer than skipping it.
