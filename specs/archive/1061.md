## Problem

The plugin's meta-work axis set is open-ended and does not distinguish a converging front from an answering pillar, allowing product-code and domain-specific surfaces to be proposed as fronts. The security subject is therefore at risk of being rejected for the wrong reason or minted with the wrong shape.

This contract is needed before the umbrella's new-axis work proceeds: umbrella spec 1057 makes the A1 declaration a prerequisite for the future toolchain, delivery, and security work. Without it, later proposals can treat failure of the front test as rejection, or can name an unbuilt namespace as if it already existed.
## Proposal

- Publish a closed admissibility contract in `docs/standards/architecture/align-surface.md` for the plugin's meta-work axes.
- Define a **front** as an axis that converges a local tree toward a canonical shape, has a probe that can find drift, and has a static verifier that can decide conformance.
- Define a **pillar** as an axis that answers live questions about the target repository without owning a tree that this plugin converges; a pillar therefore does not earn an align, doctor, bands contract, or conductor row merely by being named.
- Exclude product code and domain-specific trees from the meta-work front set. An axis that fails the front test is evaluated as a possible pillar rather than rejected automatically.
- Record the `security` subject as pillar-shaped on the measured evidence in umbrella 1057: its candidate observations are borrowed workflow, advisory, ignore, and hygiene concerns rather than one local tree with an independent static verifier. This records a classification, not a `security` route or namespace.
- State explicitly that an admitted or classified axis name is not evidence that its front, pillar, command, route, or namespace has been built; only the corresponding implementation spec can make that claim.
## Out of Scope

- Building or minting the future toolchain and delivery fronts, or the security pillar, including their routes, command bodies, profiles, bands, and translations. Those are separate umbrella work items.
- Deciding the exact arbiter table for workflow-directory keys, the security pillar's concrete verbs, or the delivery tree boundary. Those decisions belong to the corresponding sibling work and require their own implementation evidence.
- Repairing the existing front-count, anchor, configuration, conductor-order, README, or front-mold drift identified by umbrella 1057. This spec establishes the admission rule; it does not repair its consumers.
- Converging product code or a target repository's domain-specific tree as a plugin meta-work front. Such work remains with the product or domain owner.
- Updating `docs/glossary.md` or adding a new glossary term. The existing glossary definition of `pillar` is sufficient for this contract.

## Design

### Contract shape

`docs/standards/architecture/align-surface.md` is the governing home because its existing contract already defines one align per local front, probe-before-inventory, and the structural reason the `git` pillar has no align. The new `## The axis contract` section will state the reusable distinction before the aligned-front inventory, so readers can apply the rule before interpreting the current rows.

The front test has three conjunctive parts: a local tree exists, a probe can find that tree drifted, and a static verifier can decide conformance. A front must converge and repair that tree. A pillar has no converging tree and instead exposes answers about live target state; its lack of an align is a consequence of ownership shape, not a rejection. Product code and domain-specific trees fail the meta-work boundary before either shape is proposed.

The contract closes open-ended invention by requiring every future axis proposal to state its question, its owned tree or lack of one, its drift signal, and its verifier or live-answer evidence. It does not enumerate future commands or imply that a classified name is installed.

### Security classification evidence

| Observed candidate | Evidence from umbrella 1057 | Contract consequence |
| --- | --- | --- |
| Workflow `permissions:` blocks | A workflow permissions block is a key inside the future delivery tree, not a security-owned tree. | The security subject reads the permission answer as a pillar concern and owns no workflow tree. |
| Dependency advisory configuration such as `dependabot.yml` or `renovate.json` | Advisory configuration is a statement about the lock and belongs with the future toolchain tree. | It does not create an independent security front. |
| Secret and ignore patterns | The repository's ignore rules cover local settings files in one file; this is not a probeable security tree. | The contract does not mint a front for the pattern. |
| “Never ingest a secret” hygiene | Existing hygiene rules already state this obligation in the knowledge-import and harness-routing surfaces. | Repeating the rule as a new front would duplicate an owned contract. |

The conclusion is deliberately narrower than an implementation promise: `security` is recorded as a pillar-shaped subject because its evidence consists of live answers distributed across other owners, while the future pillar's verbs and payload remain outside A1.

### Binding invariants

- The front-versus-pillar classification is about ownership shape, not implementation status.
- A pillar reads or reports live state and does not acquire a tree merely because another front reads the same file.
- Product code and domain-specific trees are not admitted as plugin meta-work fronts.
- A failed front test routes the question to pillar evaluation; it is not, by itself, a rejection.
- A name is not a namespace claim until a separate implementation spec builds and verifies it.
## Alternatives Considered

- **Treat every axis as a front.** Rejected because the security evidence is distributed across other owners and has no independent local tree plus static verifier; this would reproduce the unowned-surface failure that umbrella 1057 is repairing.
- **Reject every axis that fails the front test.** Rejected because the existing `git` pillar proves that an axis can be valid when it answers live repository questions without converging a tree.
- **Keep an open-ended list of candidate axes.** Rejected because it permits product-code and domain-specific surfaces to enter the plugin's meta-work contract and encourages readers to treat planned names as installed namespaces.
- **Make security only a cross-cutting property with no pillar shape.** Rejected because it would provide no direct live-state question surface and would confuse “not a front” with “not an axis”; the shipped `git` pillar is the counterexample.
## Open Decisions

- **Whether publishing this contract now is worth its maintenance cost.** Decide at human review before execution by checking that the rule removes the specific A1 ambiguity (front rejection versus pillar admission), records the measured security classification, and does not introduce a second owner for an existing contract. If that evidence is not persuasive, stop this spec rather than widening it.
- **Whether a future `data` candidate ever earns an axis.** Decide only when a target repository supplies evidence of a repository-level question, an owned local tree or a justified live-answer shape, and a probe/verifier or equivalent read contract; until then the candidate remains outside the admitted set and no namespace is named as built.
## Risks

- **The front test is too narrow and hides a genuinely useful axis.** Mitigation: failure routes to pillar evaluation rather than rejection, and future proposals must show the live question they answer.
- **The front test is too broad and admits a domain-specific tree.** Mitigation: the product/domain boundary is explicit and the proposal must name an ownership source, drift signal, and static verifier.
- **The security measurement is mistaken for a security implementation.** Mitigation: the standard records only a pillar-shaped classification and explicitly forbids inferring a route, command, or namespace from the name.
- **The new section creates stale citations or changes the meaning of the aligned-front column.** Mitigation: preserve existing headings and rows, validate the docs bundle, and leave consumer repairs to their owning specs.
- **Future readers duplicate an existing hygiene rule as a new axis.** Mitigation: require the dependency/ownership check and cite existing contracts before classifying a candidate.
- **The standard's English artifact wording is revised into a conversation-language variant.** Mitigation: keep the durable spec and standard text in canonical English under the repository communication contract; translate only interactive reports.
