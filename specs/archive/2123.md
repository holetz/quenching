## Problem

Every write to the git spec store builds one commit and pushes it at once (`GitBackend._store_once`),
and every `cq specs record/section/task/discover/promote` is its own process, so a spec's lifecycle
becomes a stream of pushes. A downstream repository measured a median of 19 store pushes per spec
(p90 49, max 163), bursts of five pushes in six seconds during a conclude, and 3,295 commits on its
store branch; this repository's own store holds 8,253.

Nothing shipped reads that history: no `git log`, `blame` or `rev-list` runs on the store branch, a
spec's date comes from its frontmatter and a card links to the branch tip. The commits are noise on
the remote, in its push feed and in every fetch; only the tests pin commit counts and subjects.

## Proposal

Store writes accumulate in ONE local pending commit and reach the remote only at sync points:
`create`, `archive`/`restore`, `import`, `configure`, the code-side `cq git push`, `cq git pr create`
and `cq git pr merge`, and a new explicit `cq specs push`. Every sync replaces the store branch with
one parentless commit through `--force-with-lease`, so the branch always holds a single commit and
the lease stays the compare-and-swap. A remote that refuses the rewrite receives the same tree as a
fast-forward child, and the next writer allowed to rewrite collapses it again. Card transitions move
to the sync, one request per spec whose lifecycle facts changed. A lifecycle drops from about 19
pushes to about 4 (create, PR, archive, merge).

## Out of Scope

- Rolling the release into a downstream repository (`cq deploy --write` there): it follows the
  release, outside this spec.
- The deprecated tracker backends (`github` and `azure-boards` as spec stores): unchanged.
- The read-only mirror mode used for cross-repository epic members, beyond ignoring the pending ref.
- Any history or audit trail of store changes: deliberately dropped.
- Syncing at the end of every agent turn (a Stop hook): weighed and not chosen.

## Design

1. **The pending ref.** `refs/quenching/pending/<branch>` lives in the common `.git`, so every
   worktree of a clone shares it, and it is never pushed. It points at ONE commit: its parent is the
   remote tip it is based on, its tree is the store with the local writes, and its message
   accumulates the operations (`write 12 13; archive 12`). Each local write replaces that commit, like
   an amend, so the local ref never accumulates history either. Since `create`, `move`, `import` and
   `configure` always sync, a pending commit only ever modifies existing documents.
2. **Deferred write.** `write_specs` writes locally, with no network. The compare-and-swap moves from
   the push to `git update-ref <ref> <new> <old>`; the re-apply loop and the `sp-git-stale-write`
   refusal stay as they are. The leak guard and `_guard_identity` still run before the commit, and
   `_store` remains the one funnel for every mutation of the pending ref, so the specs-reader keeps
   blocking it by name.
3. **Reads see their own writes.** In normal mode a read sees the pending view, under
   `QUENCHING_SPECS_NO_FETCH` too (the HUD reads that way). Mirror mode ignores the pending ref.
4. **Replay onto the remote — computed by reads, persisted only by writes.** When a fetch brings a
   new tip, a read builds its snapshot in memory as the new tip's listing with the pending paths
   (parent → pending) substituted, and **never moves the pending ref**: reads never write, which is
   what keeps the specs-reader and the functional-check probes honest. A write inside `_store`
   persists the same replay. A conflict is judged per spec ID (`specs/<id>.md` and
   `specs/archive/<id>.md` are the same spec), and `specs/.next-id` takes the larger value. On a
   conflict the read keeps the local document for that spec, and the sync refuses.
5. **The sync.** Each attempt re-reads the pending ref, fetches the remote tip T, replays the pending
   commit onto T, runs the sync operation if any (create, move, import, configure) on that snapshot,
   builds one parentless commit with the final tree and the accumulated message, and pushes it with
   `--force-with-lease=refs/heads/quenching:<T>` (an empty lease when the branch does not exist
   yet). `[rejected] (stale info)` retries up to `MAX_ATTEMPTS`. A sync carries every pending change
   of the clone, not only the spec that triggered it.
6. **Permission fallback.** When the remote refuses the rewrite (`[remote rejected]`: no force-push
   right, or a protected branch), the same tree is pushed as a child of T, a fast-forward, and the
   result carries `history: appended`. The next sync by a writer allowed to rewrite collapses the
   branch again.
7. **Closing.** The tracking ref moves to the pushed commit by CAS against the tip the sync
   observed, and the pending ref is deleted by CAS against the pending commit the sync sent. If a
   concurrent write replaced it meanwhile, only that write's own intent (the specs where the current
   pending differs both from its own parent and from what was sent) is replayed onto the pushed
   commit, never the remote drift between two bases, so that write survives without reverting
   anyone. When the pushed commit also changed a spec under that late write, the new pending
   commit's parent keeps the document the write read (a local-only commit, not a remote tip), so the
   next sync refuses it as a conflict instead of overwriting the remote. Only a sync deletes the
   pending ref: a local write whose changes all went back to their base text keeps an empty pending
   commit, which `status` and the sync treat as nothing to send, so a close can tell a write retracted
   during its sync from a pending already retired by another sync.
8. **Cards at sync.** Card transitions leave the per-write path: for each spec in the T → pushed diff,
   `lifecycle_key` before and after is compared, one request per spec that changed. A creation still
   creates its card first.
9. **Sync points in code.** `create_spec`, `move_spec`, `import_specs`, `write_config`, the new
   `cq specs push [--drop <id>...] [--json]`, and the end of `cq git push`, `cq git pr create` and
   `cq git pr merge` on GitHub and Azure.
10. **Visibility.** `cq specs status` reports how many specs hold unsent local writes, and since when.
    A conflict refusal (`sp-git-stale-write`) names each spec with its local and remote blob, so the
    local text is recoverable with `git cat-file` before `--drop <id>` discards it. `store_tips` in
    the functional checks includes the pending ref, or a probe that wrote would escape the proof.

## Alternatives Considered

- One squashed commit per sync on top of the existing history, plus an on-demand `cq specs compact`:
  every sync stays a plain fast-forward, but the branch keeps growing. Not chosen; the branch must
  always hold one commit.
- Sync points plus a Stop hook at the end of every agent turn: the remote never lags more than a
  turn, at about 5–8 pushes per spec. Not chosen.
- Only an explicit `cq specs push`: the fewest pushes, but the remote and the board lag until someone
  remembers. Not chosen.
- A lock file serialising local writes: simpler to reason about, but it needs a per-platform lock and
  breaks with the CAS design; `update-ref <new> <old>` keeps the existing retry loop.

## Risks

- **Lag.** Other clones and the board see a spec's new state only at the next sync point; develop and
  triage stay local until the first code push, `cq specs push` or the next create. The `status` line
  makes the pending specs visible.
- **Loss.** A clone deleted with pending writes loses them; the archive and merge sync points make a
  leftover rare.
- **Late conflict.** Two clones editing the same spec now collide at the sync, not at the write. The
  refusal names the specs and both blobs and keeps the pending ref; `--drop <id>` discards the local
  side once its text is recovered.
- **Mixed runtimes during a rollout.** Worktrees on branches older than the upgrade run the 6.11
  `cq`: they read only the remote, so they miss pending writes made elsewhere in the clone, and they
  push directly. Detected, not prevented: a spec changed on both sides refuses at the next sync with
  both blobs. Mitigation: sync before rolling out, and merge the base into in-flight worktrees.
- **Downgrade strands pending writes.** An older `cq` ignores the pending ref. Mitigation: the ADR
  says to run `cq specs push` before a downgrade.
- **The close races a concurrent write.** Deleting the pending ref unconditionally would drop a write
  that landed during the sync; the CAS close with replay prevents it, and a test proves it.
- **Rewrite permission.** A writer without force-push rights appends instead of collapsing, and the
  result says so.
- **The first collapse drops the existing remote history** (8,253 commits here). A local backup ref
  is kept before it.
- **Tests pin commit counts and subjects.** They are rewritten to the new contract, never deleted.
## Handoff

- The store backend now keeps writes in refs/quenching/pending/quenching (common .git) and syncs one parentless commit with --force-with-lease; this worktree's deployed cq already runs it.
- Backup refs in the shared .git: refs/quenching/backup/2026-10-29 (8,259 commits) and refs/quenching/backup/2026-10-29-pre-2123 (ca09651, 8,269 commits, the tip before the first collapse). Never move or delete them.
- Older runtimes (the main checkout on 6.11) ignore the pending ref and push directly; the next sync from this runtime collapses their fast-forwards.

## Outcome

The functional check `store_tips` now compares heads, remote tracking and pending refs, one `rev-parse` per ref (the old form always compared two empty strings). Commands, docs, ADR 0016 and the distributions were updated. Two independent review rounds fixed findings on the sync close, card failures and local writes. Left out: the release (version bump and CHANGELOG) is cut separately; the specs-reader bare-mirror doc mismatch and the triage batch doc mismatch stay as discoveries. Known limit documented: a three-process race can lose a late write back to base text.
