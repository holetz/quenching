## Problem

The Specs panel's **Dependências** tab answers one question: which specs this one waits for and which
wait for it, read from the `dependsOn` edges. An epic answers a different one, and the tab is silent.

In the SAFRA store, epic `1025689` composes eight specs — `1025690`, `1025691`, `1025692`,
`1025693`, `1025697`, `1025698`, `1025699`, `1020947` — and every one of them carries
`dependsOn: []`. That is the whole store's shape: 454 specs and 21 declared edges. A reader who opens
the epic gets no tab at all, because `hasDeps` is false; the composition only appears as inert text
in the `Tasks` tab (`— spec: #1025690`), which clicks nowhere.

The data is not missing. `cq specs status --spec <id>` already returns, for an epic, `level: epic` and
`composition: {progress, groups, items}` — `items` carrying `label`, `spec`, `title`, `status`,
`stage`, `after` and `waitingOn` — and the panel reads exactly that payload in `readDetail` and drops
both keys on the floor. The board is blind in the same way: `cq specs list --lean` reports
`workItemType: "epic"`, and the `Row` schema does not carry it, so an epic is drawn as a spec with a
0/0 task count.

Composition is not a dependency, and this spec does not pretend it is: `dependsOn` is an execution
edge that `validate` and `schedule` reason about, while a member of an epic is a unit of the same
delivery. Mixing them into `up`/`down` would make the panel assert an edge the store's own checks do
not recognise.

## Proposal

Three pieces, none of them an extra `cq` read:

1. **The composition rides the payload that is already read.** `readDetail` passes
   `status.composition` into the `Detail` and takes the epic's `workItemType` from the document's own
   frontmatter; nothing new is spawned. A spec that is
   not an epic carries no `composition` key, exactly as the store reports it.
2. **A member block inside the Dependências tab**, above the two existing lists: the epic's members
   in their declared order, each row showing the label, the spec id, the title, the member's own
   status and stage, and the members it waits for (`espera S1, S2`). Every row opens that spec. The
   header carries the epic's progress — `1/8 concluídas · 1 bloqueada` — and the tab now renders when
   there is an edge, a cycle **or** a composition.
3. **The board marks an epic.** `workItemType` joins the `Row`, and a list row whose type is `epic`
   carries a small `épico` badge, so a reader can find the composition before opening it.

The wording is the contract: the block says *specs deste épico*, never *abaixo*, because a member is
not a dependent. A `cq` too old to report `composition` yields no block — the view degrades, it does
not fail — and an epic whose tasks are plain checkboxes has no composition and is untouched.
## Out of Scope

- Turning composition into `dependsOn`. The store's edges stay the only input to `up`/`down`, to
  `validate` and to `schedule`.
- Writing membership from the panel. `cq specs epic add` / `cq specs link add` stay the only writers.
- The Azure Boards child links. The plugin never talks to the tracker; the document is the source of
  truth for this view.
- Reordering members, or editing `after` from the panel.
- Any change to the epic document's format, to `cq specs status --epic`, or to the portal.

`integrations/opencode-vitrine/src/specs.ts` carries `level` and `composition` into the detail and
`workItemType` into the row; `src/rpc.ts` states both in the contract and in the types; `src/gui.tsx`

## Design

- **The shape.** `composition?: {progress: {done, total, blocked, ready}, groups: [{group, title,
  done, blocked, total}], items: [{label, title, spec, status, stage, after, waitingOn, group}]}`,
  copied from `status` without reinterpretation; `additionalProperties: false` at every level, so a
  field the CLI starts emitting fails loudly instead of being dropped in silence.
- **Optional, not required.** `deps` is required on every detail because every spec has an answer;
  `composition` is absent for the 446 specs that are not epics, and requiring it would make the
  contract lie. The key is omitted rather than null, the same way the store omits it.
- **The gate.** `hasDeps(spec)` becomes `hasView(spec)`: edges, cycle, or composition. The tab keeps
  its id and its position past the document's sections, so a spec with edges reads as it does today.
- **The rows.** The member's `status` (`done`, `dropped`, `in-progress`, `waiting`) is the primary
  mark, `stage` the secondary; the `after` labels name what it waits for inside the epic, and
  `waitingOn` is the subset actually unmet. `dropped` is rendered, not hidden — an abandoned member
  is part of what the epic's progress means.
- **The badge.** `workItemType` is the store's own word; the badge only prints it when it is `epic`,
  so a `melhoria` row looks exactly as it does today.

## Alternatives Considered

- **Deriving membership from the epic's `Tasks` markdown in the GUI.** It would re-parse `— spec:
  #1025690 — after: S1` that the CLI already parsed into `composition`, and would drift from the
  epic commands the moment either side changed.
- **A second `cq specs status --epic <id>` call.** The same payload as `status --spec`, spawned once
  more per epic opened; the panel's whole read budget is built on not doing that.
- **Merging members into `deps.down`.** One list, no new UI, and a lie: `schedule` does not treat a
  member as a dependent, so the panel would show a wait that blocks nothing.
- **A separate `Épico` tab.** Cleaner separation, but it costs a second tab for a fact that lives in
  the same question — what this spec is part of and what it needs.
- **Reading `epic` from the lean list to invert membership.** The lean row reports `epic: null` even
  on a member (verified on `1025690`), so the inversion has no input; only the epic document knows.

## Open Decisions

- none — the block lives in the Dependências tab, the data comes from the read already made, and the
  wording keeps composition out of the dependency vocabulary. All three follow from the constraints
  above.

## Risks

- **One more concept in one tab.** A reader may take "specs deste épico" for "abaixo". Mitigation:
  the two existing lists keep their own headings and the member block leads with the epic's progress,
  which reads as composition, not as waiting.
- **A composition that grows.** A 30-member epic makes a long block inside a tab; the bench's 8 rows
  do not press it. Mitigation: the block is a scrolling list like the task list, and the groups are
  already in the `Tasks` tab for the long form.
- **A member that no longer exists.** `items` comes from the epic document, which may name a spec the
  store dropped. The panel renders the id it was given and the click opens a spec that may error;
  the `cq` side already reports the broken reference (the epic's `ready` findings).
- **The badge on a stale `cq`.** A `cq` that omits `workItemType` from the lean list yields an empty
  row type and no badge — today's behaviour, not a regression.

## Handoff

- **Built:** the two tasks below, in order; the second rebuilds `dist/` and proves the bench.
- **Decisions taken at build:** composition carried from `status` rather than a second call; the
  block inside the Dependências tab rather than a new tab; `workItemType` on the row for the badge.
- **Not done here:** any write path, the Azure child links, and any change to how the store computes
  composition.
