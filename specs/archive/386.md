## Problem

Medido em 2026-11-24 por um scout do autopilot (strace num clone; Linux como proxy de Windows com antivírus de varredura em tempo real), a pedido do humano: "Um custo relevante que vem consumindo muita CPU é a carga do antivírus sobre as operações de arquivos e execução de scripts". Os `.pyc` do payload são gravados sob demanda na primeira chamada de cada deploy e de cada slot novo: 4 no `cq specs status`, 4 no primeiro `tools/call` do MCP, 5 no primeiro dispatch de hook (`.agents/quenching/assets/hooks/__pycache__`); `cq deploy --write` não roda `compileall`. `PYTHONDONTWRITEBYTECODE` não ajuda (troca escrita por recompilação a cada chamada). O `cq git worktree release` abre 1.692 arquivos por causa do `git status` do slot; no Git for Windows, `core.fscache` já vem ligado, mas `core.untrackedCache` não.

**Consequência:** cada slot e cada processo novo no Windows grava e faz o antivírus varrer bytecode que poderia existir desde o deploy, e cada `git status` de slot varre o checkout inteiro.

Proposta: `cq deploy --write` roda `compileall` (quiet, no mesmo interpretador do MCP e dos hooks) sobre `.agents/quenching/assets/` e os `__pycache__` ficam fora do manifesto e do `--check`; `cq doctor` no Windows avisa quando `core.untrackedCache` não está ligado no repositório e imprime o `git config` a rodar (sem aplicar). Medir os `.pyc` gravados na primeira chamada antes e depois.

## Proposal

1. `cq deploy --write` pré-compila o bytecode do payload: depois de gravar a árvore, roda `<prefixo dos hooks/MCP> -m compileall -q` sobre `.agents/quenching/assets/`, no mesmo interpretador que o deploy grava para os hooks e o servidor MCP (o tag `cpython-3XY` do `.pyc` é do interpretador que vai carregá-lo). Falha ou ausência do interpretador vira um aviso no relatório, nunca uma recusa: o deploy já gravou e o bytecode é só cache.
2. Os `__pycache__` continuam fora do manifesto e do `--check` (a árvore construída já os ignora; o plano só percorre a árvore). Quando o deploy apaga um `.py` que era seu, apaga junto o `.pyc` irmão em `__pycache__/` e o diretório que ficar vazio, para que módulo removido não deixe bytecode órfão nem diretório preso.
3. `cq doctor` no Windows lê `core.untrackedCache` do repositório (`git config --get`, considerando também `feature.manyFiles=true`, que o liga implicitamente) e, quando não está ligado, imprime uma linha com o comando `git config core.untrackedCache true` a rodar — sem aplicar, sem mudar o exit code. Fora do Windows ou fora de um repositório git, nada é impresso.

## Out of Scope

- Configurar o git do usuário ou o antivírus automaticamente — decisão de 384 ## Design (2026-11-24): o doctor só informa.
- A lista de exclusões de antivírus e a raiz única de caches — spec #385.
- Fixtures de git da suíte (spawns do gate) — fora por 384 ## Design; segue na #339.
- `core.fscache` — já vem ligado no Git for Windows (medição do scout).
- Documentação de produto (README): a #385 edita a mesma área do doctor; o CHANGELOG do conclude carrega a mudança.

- `--check` logo após um `--write` sai 0 com os `__pycache__` presentes.

## Design

- 2026-11-24 — o interpretador da compilação é `hooks_python` (o prefixo direto que o deploy já resolve para hooks e MCP, nunca `uv`); sob `--runtime uvx` o payload não carrega `assets/bin`, mas os hooks sim, então a compilação roda igual sobre o que existir.
- 2026-11-24 — a compilação é subprocesso com timeout (120 s), `capture_output`, e roda só quando `written`; o `--check` nunca compila (não grava nada).
- 2026-11-24 — o aviso do doctor vive em `common/gitcache.py` com `platform` injetável para teste; `doctor.py` ganha só a chamada, o campo `gitCache` no JSON e uma linha humana — mudança mínima porque a #385 mexe no mesmo arquivo.
- 2026-11-24 — medição de base (scout local, Linux, Python 3.14): deploy recém-gravado tem 0 `.pyc`; a primeira `cq specs status` grava 44; `compileall -q` do payload leva ~0,25 s e grava 170.

### Assumptions

- O custo de ~0,3 s por `--write` é aceitável no alvo; nos testes de deploy (≈80 writes) a compilação é substituída por um dublê, exceto no teste que a prova (## Tasks 1.1).

## Alternatives Considered

- `PYTHONDONTWRITEBYTECODE` — descartada pelo scout: troca a escrita por recompilação a cada chamada.
- Commitar/empacotar `.pyc` no payload — descartada: o tag do `.pyc` depende do interpretador do alvo e o manifesto compara bytes.
- Compilar em processo com `compileall.compile_dir` — descartada: o interpretador do deploy pode não ser o dos hooks, e o `.pyc` gravado seria de outra versão.
- Aplicar `git config core.untrackedCache true` — descartada por 384 ## Design (nada configura o git do usuário).

## Risks

- Conflito com a #385 em `common/doctor.py` — mitigado: o código novo fica em módulo próprio e o diff em `doctor.py` é de poucas linhas.
