## Overview

A cada turno, o Claude recebe uma base fixa antes de executar qualquer tarefa. Nesta árvore, o arquivo que controlamos nessa base é o `CLAUDE.md`: ele tem 8.548 bytes e 126 linhas, embora parte dele apenas repita contratos que já vivem em `/.knowledge/` ou a documentação do plugin. A medição histórica também contou o system prompt e o registro de descriptions, mas esses componentes pertencem ao runtime e não podem ser reduzidos por um commit desta árvore.

Depois da mudança, o `CLAUDE.md` continuará declarando o idioma, a identidade do repositório, os poucos checks necessários para operar o plugin e os caminhos de navegação. As explicações duráveis e o manual ficarão em seus homes já existentes, consultados sob demanda. O resultado será uma base fixa local menor, com o proxy medido separadamente do custo externo que esta spec não controla.
## Problem

A base fixa relida a cada turno de uma sessão de comando é dominada pelo **system prompt e pelo
`CLAUDE.md`**, não pelo corpo do comando. Medido na sessão
`c56cff41-e5b1-43f0-85dc-eca1b17e03d0` (duas passagens de `/quenching:specs:develop` sobre uma
spec): 9,73M de contexto lido em 100 turnos, dos quais **4,44M são 100 releituras de uma base de
44,4k** — ~46% da sessão. O corpo do comando é ~7k dessa base, então emagrecê-lo compra ~7% da
sessão; o resto da base é a alavanca que ninguém tomou.

A spec `revisar-fluxo-do-develop-custo-e-gates` atacou o outro fator do integral — a contagem de
turnos — e registrou esta linha como discovery justamente por ela ser **alavanca de repositório
inteiro**, e não de um comando: qualquer corte aqui vale para toda sessão do repo, e nenhuma spec
até hoje mediu de que exatamente esses 44,4k são feitos nem quanto deles é remível.

O primeiro entregável é a decomposição medida da base — quanto é system prompt (fixo, fora do nosso
alcance), quanto é `CLAUDE.md`, quanto é o registro de descriptions dos 26 comandos, quanto é o
corpo do comando em execução — porque sem ela qualquer proposta de corte é palpite sobre o termo
errado.

## Proposal

- `CLAUDE.md` será um harness de entrada curto, com apenas o contexto mínimo que precisa estar disponível em todo turno e ponteiros para a fonte detalhada.
- As regras que já têm dono em `/.knowledge/` e no README deixarão de ser copiadas no harness; nenhum novo home será criado apenas para satisfazer a meta de tamanho.
- Permanecerão no harness a declaração de idioma, a identidade/natureza do repositório, os checks mínimos de operação e os alertas de segurança que não podem depender de uma leitura posterior.
- O system prompt, as descriptions dos comandos e os corpos carregados somente quando um comando é invocado permanecerão explicitamente classificados como fora do alcance desta spec.
- A mudança terá uma medição reprodutível de bytes, linhas e categorias do harness, com uma regressão que recuse o retorno de conteúdo operacional duplicado.
- A validação demonstrará que os ponteiros e os checks mantidos no harness continuam resolvendo no checkout e que o corte não altera a superfície de comandos.
## Out of Scope

- **System prompt do Claude:** é fornecido pelo produto/runtime, não está no repositório e não pode ser reduzido por um commit desta árvore.
- **Descriptions registradas dos comandos:** pertencem à superfície `.claude/` e ao seu próprio trabalho de roteamento/custo; esta spec não reescreve as entries do plugin nem presume que o número histórico de 26 ainda seja o número atual.
- **Corpos de comandos, skills e references:** são contexto sob demanda e têm donos próprios; não serão reescritos apenas para melhorar a medição desta base.
- **`AGENTS.md` e `.agents/AGENTS.md`:** são o harness Codex e sua saída gerada, com loader e ciclo de tradução próprios; não são tratados como equivalentes ao `CLAUDE.md` sem evidência de que o mesmo carregador os releia neste fluxo.
- **README do produto:** continuará sendo a documentação ampla; a spec só poderá corrigir um ponteiro quebrado necessário para o novo harness, não reorganizar o manual.
- **Criação de uma nova taxonomia de conhecimento:** a implementação deve reutilizar homes existentes. Se uma regra não tiver dono, ela fica fora do corte e é registrada como bloqueio/follow-up, não é empurrada para um arquivo conveniente.
- **Otimização do prompt cache ou do custo do modelo:** cache e system prompt são propriedades externas. A meta aqui é retirar bytes duplicados do arquivo que controlamos e provar o limite alcançado.
## Impact

### Standards this spec will write into knowledge/standards/

- none — esta spec não declara a adoção de um standard novo; ela apenas reaponta regras já cobertas e adiciona uma guarda local para o harness.

### Product code this spec expects to touch

- `CLAUDE.md` — o harness Claude raiz que será reduzido e manterá os invariantes mínimos.
- `scripts/check_claude_harness.py` — novo relatório/guard de bytes, categorias e ponteiros do harness.

## Validation

- `python3 scripts/check_claude_harness.py --report --json` deve sair com código 0 e imprimir JSON contendo bytes/linhas do `CLAUDE.md`, a contagem e o tamanho das descriptions na fonte dos comandos, e os componentes externos como `unavailable` em vez de inventar seus bytes.
- `python3 scripts/check_claude_harness.py --check --json` deve sair com código 0, confirmar `CLAUDE.md` com no máximo 4.274 bytes, a declaração `Language: pt-BR`, os ponteiros locais e os checks mínimos, e recusar os blocos operacionais duplicados removidos.
- `python3 plugins/quenching/assets/bin/cq --root . components doctor --json` deve sair com código 0 e nenhum finding para a superfície `.claude/`; o número observado de entries é informativo, não critério de corte.
- `python3 plugins/quenching/assets/bin/cq knowledge validate .knowledge` deve ser lido como zero errors; avisos advisory preexistentes devem ser reportados separadamente.
- `python3 -m unittest discover -s plugins/quenching/tests` deve concluir sem falhas atribuíveis a esta mudança; se o checkout não suportar essa suíte por uma condição preexistente, o resultado será registrado como inconclusivo, nunca como verde.
- `git diff --check` deve sair com código 0.

## Design

A decisão central é manter um único `CLAUDE.md` raiz como ponteiro mínimo, em vez de tentar eliminar o arquivo ou despejar seu conteúdo inteiro em outro arquivo que também seria sempre carregado. A linha `Language: pt-BR — the contract is /.knowledge/standards/agents/communication.md` é uma declaração de runtime que precisa permanecer no harness; os índices de `/.knowledge/`, o README do plugin e os checks de operação podem ser apontados por links curtos.

O detalhamento que sair do harness será roteado por propriedade e somente para homes já existentes: contratos sobre como o repositório trabalha vão para os standards atuais, o manual do produto fica no README e fatos externos continuam fora do harness. O executor não poderá apagar uma regra sem apontar o destino que já a cobre ou declarar, com evidência, que ela era duplicação.

### Mapa de dependências

Medido em 2026-08-19 neste checkout, antes da implementação:

| Fonte | Evidência observável | Dependência da mudança | Decisão |
| --- | --- | --- | --- |
| `CLAUDE.md` | 8.548 bytes, 126 linhas; contém operação, regras de refatoração, mapa de conhecimento e manual do plugin | É o artefato diretamente relido em todo turno Claude e o único alvo controlável desta spec | reduzir e manter como ponteiro |
| `/.knowledge/standards/**` | já contém contratos de comunicação, superfície e verificação | é a fonte durável que o harness deve citar, não copiar | reutilizar; não criar um home novo |
| `plugins/quenching/README.md` | já é o manual longo do produto | recebe o leitor que precisa de catálogo, política e instalação | apontar, não duplicar |
| `plugins/quenching/commands/**` e `assets/references/**` | corpos e referências são lidos por comandos específicos | podem ser quebrados por links errados, mas não são parte do corte | validar citações existentes, não reescrever |
| system prompt/registro de descriptions | aparecem na medição da sessão, mas são produzidos pelo Claude/runtime | não há arquivo ou contrato local para editar neste trabalho | medir como limite externo e deixar intacto |
| `AGENTS.md`/`.agents/AGENTS.md` | superfície Codex separada, com tradução gerada e loader próprio | uma edição aqui teria outro contrato e outro risco de drift | fora do escopo |

O corte será aceito somente se a soma de bytes do `CLAUDE.md` ficar no máximo em 50% do baseline medido (4.274 bytes), sem perder a declaração de idioma, os ponteiros de navegação ou os checks que o arquivo promete. Esse limite é uma meta de tamanho do artefato e um proxy local; a validação não poderá apresentá-lo como redução dos 44,4k externos da sessão histórica.
## Alternatives Considered

- **Apagar o `CLAUDE.md`:** rejeitado porque remove a declaração de idioma e o primeiro caminho de operação justamente do arquivo que o loader consulta.
- **Mover tudo para um README:** rejeitado porque README não é o harness e a regra deixaria de estar disponível sem uma busca adicional.
- **Enxugar somente descriptions:** rejeitado porque descriptions pertencem ao registro da superfície e não explicam os 8.548 bytes medidos no `CLAUDE.md`; seria outra spec e não resolveria o alvo local.
- **Confiar apenas no prompt cache:** rejeitado porque cache não remove conteúdo da entrada nem fornece um contrato reprodutível de tamanho do harness.
- **Copiar o conteúdo para outro harness sempre carregado:** rejeitado porque troca o nome do custo e cria duas fontes de verdade; a forma escolhida deixa o detalhe sob demanda em um único home.

## Open Decisions

- none — o alvo é o `CLAUDE.md` raiz, o limite é 50% do baseline local medido, os componentes externos permanecem fora do alcance e o trabalho não cria um novo home de conhecimento.

## Risks

- **Perda de uma regra operacional essencial — probabilidade média, impacto alto.** Um corte que atinja as regras de operação pode deixar o próximo agente sem o check correto. Mitigação: declarar uma lista de invariantes que devem sobreviver, testar os links/commands do harness e revisar o diff inteiro antes do gate; detecção por `git diff`, `components doctor` e os checks executáveis.
- **Ponteiro quebrado ou destino errado — probabilidade média, impacto alto.** A prosa pode parecer menor enquanto a instrução fica impossível de seguir. Mitigação: validar cada caminho citado a partir do root e rodar a checagem de citações apropriada; detecção pelo comando de validação e por uma busca de arquivos-alvo.
- **Proxy local confundido com ganho no runtime — probabilidade alta, impacto médio.** O limite de 4.274 bytes pode ser reportado como se provasse o corte do system prompt/44,4k. Mitigação: separar no relatório bytes/linhas do arquivo, componentes externos e qualquer medição histórica; detecção por uma asserção de validação que não use os números externos como resultado do check.
- **Meta alcançada por apagar contexto necessário — probabilidade média, impacto alto.** O arquivo pode ficar curto, mas perder idioma, navegação, checks ou alertas de segurança. Mitigação: checklist de preservação e teste de presença dos invariantes antes de aceitar o limite; detecção automática e revisão do diff.
- **Drift entre o número histórico e a superfície atual — probabilidade média, impacto baixo.** A descrição do problema fala em 26 descriptions, enquanto o checkout declara uma superfície diferente. Mitigação: não usar o número como critério de aceitação; registrar a contagem observada pelo doctor apenas como inventário e deixar a redução das descriptions para outra spec.
- **Regra sem home adequado — probabilidade baixa, impacto médio.** Remover uma passagem única sem destino torna a operação dependente de memória. Mitigação: não criar home durante esta spec nem apagar a passagem; registrar o caso como bloqueio explícito para uma spec de conhecimento/harness.
