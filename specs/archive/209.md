## Problem

Dois defeitos no mesmo corpo, `quenching/agents/spec-orchestrator.md` (autopilot round 11, scout c, rechecados duas vezes):

1. `:91` (Hard prohibitions) diz "you never merge or close a spec yourself", mas `:53` manda o orquestrador rodar `cq git pr merge --url <url> --spec <id> --wait 90 --json` e, depois, `cq specs reconcile --write --json`, que arquiva a spec; `orchestrate.md:19` e `autopilot.md:178` confirmam que o merge é dele. `git blame -L 89,92` → `ba829e843e` (2026-10-07), anterior ao passo de merge. Um orquestrador que obedece `:91` publica e não mergeia: dependentes ficam `blocked`/`needs-merge` e o épico para.
2. `cq git pr merge --spec` pode sair `ok:false, reason:"stamp-failed"` (exit 1) depois de um `gh pr merge` bem-sucedido (`quenching/assets/bin/quenching/git/pull.py:168-177`), e `checks-unreadable` (`pull.py:215-216`) também existe; `:53` só enumera `pending`, `alreadyMerged`, `failed`, `skipped-required`, `merge-state`, `merge-refused` (`grep -rn 'stamp-failed\|checks-unreadable' quenching/agents` vazio). Um PR já mergeado é tratado como não mergeado: o reconcile não roda e os dependentes saem bloqueados.

Correção só no corpo: `:91` vira "nenhum `git merge` cru; merge e arquivamento só pelos verbos do passo 4"; `stamp-failed` no merge = mergeado (NOTE com a falha, segue para o reconcile); `checks-unreadable` = `blocked`. Não toca `pull.py` (branch do humano plan/1037500-merge-sem-checks).

## Proposal

- `## Hard prohibitions` de `quenching/agents/spec-orchestrator.md` deixa de proibir o merge e o fechamento de spec: proíbe `git merge` cru e qualquer merge ou arquivamento por outra via que não os verbos do passo 4 (`cq git pr merge`, `cq specs reconcile --write`).
- O passo 4 mapeia `reason: stamp-failed` do `cq git pr merge` como merge que aconteceu: o NOTE carrega a falha do carimbo `merge` e o orquestrador segue para o `cq specs reconcile --write --json`.
- O passo 4 mapeia `reason: checks-unreadable` como `STATE: blocked` com a mensagem do verbo, ao lado de `failed`, `skipped-required`, `merge-state` e `merge-refused`.
- Um teste de contrato em prosa trava as três frases, e a superfície implantada (`.agents/`, `.claude/`, `.opencode/`) é regenerada.

## Out of Scope

- `quenching/assets/bin/quenching/git/pull.py` — decisão do dono no épico 212 (`## Design`, bullet 209): o arquivo está na branch do humano (plan/1037500-merge-sem-checks); o verbo já emite os dois `reason`, só o corpo não os trata.
- `orchestrate.md` e `autopilot.md` — já atribuem o merge ao orquestrador (`orchestrate.md:19`, `autopilot.md:178`); não contradizem o passo 4.
- `no-checks` / `--allow-no-checks` — o passo 4 já trata "nenhum CI" como `needs-human`; a semântica nova do merge sem checks é da branch do humano.

## Design

- O merge e o arquivamento são do orquestrador, e só pelos verbos do passo 4: a proibição vale para `git merge` cru e para qualquer fechamento fora de `cq git pr merge` + `cq specs reconcile --write` — evidência `orchestrate.md:19`, `autopilot.md:178` e o próprio passo 4 (`:53`).
- `stamp-failed` descreve um merge que aconteceu (`pull.py` `_merged`: o `gh pr merge` já rodou, só o carimbo `merge` falhou): tratá-lo como não mergeado bloqueia dependentes de um PR já na base. O reconcile roda mesmo assim; a falha do carimbo vai ao NOTE para o humano.
- `checks-unreadable` é o fallback do mapa de estados dos checks: sem leitura não há certificação de CI, e o passo 4 só mergeia com checks verdes, então é `blocked`.
- Decisão do dono delegado registrada no épico 212 (`## Design`, 2026-11-21, bullet 209).

### Assumptions

- O `reconcile` arquiva pelo estado do PR no provedor, não pelo record `merge`, então um `stamp-failed` ainda arquiva a spec — sustenta o bullet de `stamp-failed` em `## Proposal`; o NOTE avisa se o reconcile devolver `needs-human`.

## Alternatives Considered

- Tratar `stamp-failed` como `blocked` (conservador) — rejeitado: o PR já está na base; bloquear para os dependentes é exatamente o defeito descrito em `## Problem`.
- Corrigir no `pull.py` (sair `ok:true` com aviso) — rejeitado pela decisão do dono: arquivo da branch do humano.
