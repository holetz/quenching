## Problem

O execute da spec 460 adicionou a prova `quenching/tests/test_git_worktree_workspace.py` e o gate afetado parou em `proof doctor` com `pf-readme-stale`: `quenching/README.md` conta os módulos de teste e ficou desatualizado, e a correção só virou a task 5.2 no fim do build. Qualquer task que crie, mova ou renomeie uma prova deixa o README gerado stale, e o fluxo não antecipa a regeneração.

Minimal fix proposed: a task que cria ou move uma prova roda `cq proof readme --write` e declara `quenching/README.md` em `files:`, ou o gate afetado regenera o README antes de checar.

**Insumos**

- `quenching/README.md` — a zona `quenching-proof-readme-start`/`end`, escrita por `cq proof readme --write`.
- `python3 quenching/assets/bin/cq proof doctor` → `[error] quenching/README.md — generated proof README is absent or stale (pf-readme-stale)`, no gate afetado da spec 460; corrigido pela task 5.2.
- `scripts/verify_repo.sh` — o passo `proof doctor` que reprovou o gate.
- Spec 460, execute/close, 2026-11-25.

## Proposal

Antecipar a regeneração do README de prova na definição e no build, não no gate: a doutrina de `artifacts.md` passa a declarar `quenching/README.md` em `files:` de toda task que cria, move, renomeia ou apaga um módulo `quenching/tests/test_*.py`, com `cq proof readme --write` no corpo da task; e o loop de validação de `execution.md` passa a rodar `cq proof readme --check` antes do commit de uma task cujo diff muda o conjunto de provas, regenerando no mesmo commit da task.

## Out of Scope

- Regenerar o README dentro do gate (`verify_repo.sh`) ou do `proof doctor`: o gate segue só verificando, e escrever no passo de verificação esconderia a deriva.
- Novo hook, passo de CI, grant ou `allowed-tools` (épico 559 §Design).
- Mudar o gerador `cq proof readme` ou o código do `proof doctor`.

## Impact

### Process surface this spec expects to touch

- `quenching/references/specs-develop/artifacts.md` — o parágrafo "Two triggers bring derived files" ganha o gatilho do README de prova
- `quenching/references/specs-execute/execution.md` — o loop de validação ganha o passo de checar e regenerar o README antes do commit da task

## Validation

- `grep -c "proof readme" quenching/references/specs-develop/artifacts.md quenching/references/specs-execute/execution.md` imprime `1` ou mais em cada arquivo depois das tasks e `0` antes.
- `python3 quenching/assets/bin/cq proof doctor` segue sem `pf-readme-stale`.
- `python3 quenching/assets/bin/cq deploy --target . --write` seguido de `QUENCHING_TEST_SCOPE=affected bash scripts/verify_repo.sh` fecha sem drift do deployed surface lockstep.

## Design

- Duas pontas da mesma regra: quem define a task declara o README em `files:` (develop), quem constrói confere antes do commit (execute). A segunda cobre o que a primeira não previu.
- A regra cita `cq proof readme --check`/`--write`, verbo existente: nenhuma ferramenta MCP nova.
- decision: doutrina em vez de regeneração no gate — o título da spec exclui o gate e o padrão de listagens geradas (generated-listings.md) quer o dono escrevendo e o checador só lendo.

### Assumptions

- O README de prova é o único arquivo derivado que uma prova nova invalida (evidência: specs 460 e 488). Depende: Proposal.

## Alternatives Considered

- Regenerar no gate afetado antes de checar: rejeitada, o gate passaria a escrever na árvore e a mascarar a omissão do `files:`.
- Hook de commit que roda `proof readme --write`: rejeitada, hook novo é vedado pelo épico 559.

## Open Decisions

- none — a escolha entre doutrina e regeneração no gate está fechada em Out of Scope.

## Risks

- A regra pode ser ignorada por um autor que não leia o parágrafo: o passo de execute pega o resíduo antes do commit, então reduz e não elimina.
- ACCEPTED — o resíduo ainda vira um README no commit da task fora do `files:` declarado se o autor omitiu; o `--check` torna isso visível e não silencioso.
