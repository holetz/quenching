## Problem

Achado da revisão de correção do épico 306 (2026-11-24, PR #352, spec 314), lido no código: `quenching/assets/bin/quenching/deploy/mcpfiles.py:107` só escreve a profundidade quando o valor do usuário falta ou é menor, mas `cli.py:173` devolve `{"subagentDepth": depth, "externalDirectory": patterns}`, que o deploy grava no manifesto como `opencodeConfig`, tenha escrito ou não. Na remoção (harness OpenCode ou MCP retirado), `mcpfiles.py:138` apaga `experimental.subagent_depth` quando vale exatamente o valor registrado, e `mcpfiles.py:145` apaga todo allow de `external_directory` igual a um padrão registrado — contra a docstring "Take out what the deploy wrote".

**Consequência:** um usuário que já tinha `"subagent_depth": 4` ou o mesmo allow perde a própria configuração quando o deploy sai; sem a profundidade, o fluxo orquestrado volta a falhar no OpenCode.

Proposta: o manifesto registra só o que o deploy de fato escreveu (chave ausente → escrita; já presente → não registrada); a remoção apaga só o registrado; teste com valor do usuário igual e maior.

## Proposal

- O manifesto (`opencodeConfig`) registra só o que o deploy de fato escreveu em `opencode.json`: profundidade ausente ou menor → registrada; igual ou maior do usuário → não registrada; allow de `external_directory` já `allow` → não registrado.
- A remoção (harness retirado ou MCP retirado) apaga só o registrado; a profundidade e os allows que o usuário já tinha sobrevivem.
- Teste com valor do usuário igual e maior cobre a regressão.

## Out of Scope

- Spec 370, que segue em `deploy/mcpfiles.py`: não é absorvida aqui.
- Restaurar o valor anterior do usuário quando o deploy o sobe (profundidade menor) ou o troca (allow `deny`): o deploy precisa do seu valor, e a remoção apaga a chave gravada.

## Design

- Decisão: uma função pura `written_extras(base, extras)` calcula, sobre o arquivo já sem o registro anterior, o que a mescla altera. O cli grava esse resultado no manifesto. Alternativa rejeitada: fazer `_opencode_extras` devolver o escrito, o que muda a assinatura de `merged` usada por 370.
- Regra durável: o manifesto nunca registra o que o usuário já tinha; a remoção só apaga o registrado.
- Uma profundidade menor que o usuário tinha é subida e registrada (o deploy precisa dela); um allow com outro valor é trocado e registrado.
- Se nada foi escrito, `opencodeConfig` não entra no manifesto.

### Assumptions

- A profundidade menor do usuário e o allow trocado são perdidos na remoção — depende de Out of Scope.

## Alternatives Considered

- Restaurar o valor anterior do usuário na remoção: exige guardar o valor antigo no manifesto, ampliando o formato; rejeitado por ora.
