## Problem

`cq knowledge --help` sai com exit 2 e escreve em stderr (`knowledge/cli.py:264-280` roteia por token, sem argparse); é o único pilar sem `--root`. `cq specs --version` imprime `specs 6.3.0`, `cq components --version` imprime `skills 6.3.0`, os outros `cq <pilar> 6.3.0`. O exit 2 sai por duas portas: `common/output.py:refuse()` em stderr (10 módulos) e `emit_err()` em stdout (os 16 módulos de `specs/commands/`). Um erro de sintaxe do argparse e uma recusa deliberada compartilham exit 2. Há 14 prefixos de código de finding (`sp` 90, `design` 22, `pf` 12, `se` 7, `site`, `delivery`, `git`, `op`, `sk`, `nav`, `glossary`, `ct`, `tc`, `security`). `common/io.write_text` diz ser "the atomic replace every writer goes through" e só `specs/release.py` a usa; 14 outros writers escrevem direto. Cinco valores de timeout em três fontes. `azure.py:690,1204` grava corpos de work item em `tempfile.mkstemp` sem `dir=`, no temp do sistema. `git/base.py:34-55` colapsa "gh ausente", "não autenticado" e "não é o default" em `isDefault: false`, contra a própria docstring; `:43` chama `az repos show` fora de `_az_run`. `cq design genre` e `cq components session` não têm `--json`. O piso de Python não está declarado em nenhum lugar do plugin.

## Proposal

- Pilar knowledge sobre argparse, com `--root`, help em stdout e exit 0.
- Uma gramática de `--version` e uma porta de exit 2 (stderr para o humano, `--json` para a máquina), com código distinto para erro de uso.
- Convenção documentada de prefixo de finding, um por pilar, e migração dos códigos existentes.
- `write_text` atômico em todo writer; uma constante de timeout; `tempfile` com `dir=`; `isDefault: null` para desconhecido; `az repos show` via `_az_run`; `--json` nos dois pais; piso de Python declarado em `assets/bin/cq` com mensagem nomeada.

## Out of Scope

- Não alterar o contrato de provider ou a semântica dos fronts além do que é necessário para o CLI uniforme.
- Não trocar o piso de Python por runtime externo nem adicionar dependências que o plugin não publica.
- Não converter mensagens humanas em JSON arbitrário: o payload continuará sendo a fonte para automação.

## Impact

- plugins/quenching/assets/bin/quenching/git/base.py e specs/backends/azure.py

### Standards this spec will write into docs/standards/

- none — a mudança implementa o contrato já descrito pelo plugin; alterações normativas de documentação ficam em specs próprias.
## Validation

- Cada pillar responde help com 0 em stdout e version com cq <pillar> X.Y.Z; recusa deliberada mantém código 2 e JSON estruturado quando solicitado.
- Os writers não abrem arquivos diretamente para sobrescrita fora de common/io.py, e os testes confirmam que nenhuma substituição parcial ocorre.
- git base retorna isDefault null somente quando não há evidência; a chamada Azure passa pelo runner.
- Um runtime abaixo do piso termina com mensagem nomeada antes do traceback de imports.
## Design

assets/bin/cq será o único ponto de entrada e exibirá ajuda e versão no formato cq <pillar>. A raiz usará argparse para separar erro de uso (código próprio e mensagem de uso) de recusa deliberada (código 2, stderr ou payload JSON). Cada pillar receberá --root onde a operação aceita raiz; os dois comandos pais também aceitarão --json.

common/output.py concentrará a emissão e recusa; common/io.py concentrará escrita atômica via arquivo temporário no mesmo diretório e replace. Os writers restantes passarão por esse helper. A constante de timeout ficará em common ou no adapter de transporte compartilhado. Os arquivos temporários do Azure usarão dir do checkout quando o contrato exigir uma escrita local.

git base distinguirá default conhecido, não-default e desconhecido usando null no último caso, e todas as chamadas az passarão pelo runner que normaliza autenticação/erro. O piso de Python será verificado antes dos imports que exigem tomllib.

### Mapa de dependências

Atualizado em 2026-09-02. assets/bin/cq roteia todos os pillars e importa common/version; output e io são usados por todos os writers. Os CLIs e seus testes golden dependem dos códigos, stdout/stderr e payloads. git/base.py é consumido por branch, pr e merge. azure.py usa os caminhos temporários e timeouts. A documentação de resolução, o README e os manifestos registram a versão e o piso.

## Alternatives Considered

| Forma | Custo | Benefício | O que fecha | Decisão |
| --- | --- | --- | --- | --- |
| Corrigir cada CLI separadamente | menor diff inicial | risco localizado | mantém versões e portas divergentes | rejeitada |
| Manter traceback/argparse misturados | nenhuma migração | implementação simples | consumidores não distinguem uso de recusa | rejeitada |
| Contrato comum em entrypoint e helpers, com adapters específicos | refatoração moderada | comportamento determinístico e teste único | exige atualizar fixtures e mensagens | escolhida |

## Open Decisions

- A faixa numérica dos códigos de uso será a primeira livre na tabela do output; o teste de contrato a fixa sem reutilizar código de finding.
- O timeout final será o maior valor já exigido por uma operação legítima, medido pelos testes de provider; não será reduzido para ganhar latência.

## Risks

- Normalizar stderr/stdout pode quebrar scripts que dependem da forma antiga; mitigação: fixtures de payload e migração documentada.
- A escrita atômica no mesmo diretório pode falhar em filesystem sem permissão; mitigação: recusar com caminho e não substituir parcialmente.
- Checar Python antes dos imports pode divergir entre versões; mitigação: mensagem estável e teste em subprocesso quando o runtime existir.
- Alterar isDefault para null pode exigir consumidores tri-state; mitigação: testes de git e relatório explícito de desconhecido.

## Handoff

Executar após manter a árvore limpa e capturar os goldens atuais. Alterações de output exigem rodar a suíte completa; não usar --no-verify nem ajustar testes para aceitar a forma antiga.

## Outcome

Concluída. O contrato do cq foi unificado: knowledge agora usa argparse com --root, a gramática de versão é `cq <pillar> 6.3.0`, recusas deliberadas usam exit 2, erros de uso usam exit 3, códigos de finding seguem prefixos estáveis, e design genre/components session aceitam --json.

A escrita de specs e cache é atômica, os temporários Azure ficam no checkout, o timeout é único em 60 s, git base distingue true/false/null, e o entrypoint declara e verifica Python 3.11+ antes dos imports do pacote. A suíte passou com 570 testes; validação do bundle, doctor de components e tradução Codex passaram.
