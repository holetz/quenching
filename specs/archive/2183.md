## Problem

The proof front teaches a target to declare what a run costs: `proof.cost` in `.agents/quenching.json`, with a temp root, a worker budget and three scopes. Spec 2182 shipped it, and the standard at `docs/standards/ci-cd/test-cost.md` names the tiers — a task runs "the diff's tests", a close runs "the same selection inside the whole gate", CI and the release run everything.

The middle tier is where the contract leaks. A target's every spec task declares the repository gate as its `verify:` — in SAFRA, `uv run test --afetados`, which is the close's selection, not a task's proof. Five tasks pay five selective runs, and `cq proof doctor` reports nothing: `scopes.task` is optional, so a declaration may omit it, and nothing ever compares it with `scopes.close`. The behaviour the standard recommends — a cheap proof per task, the repository gate at the close — has no code behind it and no finding when it is absent.

Two consequences follow. A target that never declares `task` is indistinguishable from one that does the right thing, and its generated README prints "Task scope: not declared" without a code explaining why. And the `specs execute` flow carries no sentence saying which command belongs to a task; its only cost guidance is about billed agent sessions, a different cost.

## Proposal

Five pieces, none of them a runner:

1. **`scopes.task` becomes required.** `COST_REQUIRED` gains `scopes.task`, and `pf-cost-undeclared` names it in the order the contract reads: `tempRoot`, `workers`, `scopes.task`, `scopes.close`, `scopes.ci`. A target that declares layers and never decided what a task pays is told exactly that.
2. **A fourth judgement code, `pf-task-wide`.** It fires when `scopes.task` and `scopes.close` are both declared and identical: every task pays the close's selection. Silent when either is absent — the absence is `pf-cost-undeclared`'s fact, not this code's. Same shape as `pf-scope-wide`: read the declaration, one error at `config_path`, registered in `CHECK_REGISTRY`.
3. **The standard states the tiers as three different proofs**, in both copies: a task's proof is *targeted* — the file or directory the task touched; the close's proof is the diff's selection inside the whole gate; CI and the release run everything. A task's `verify:` is not the repository gate, and the cadence of the gate is the spec's `verification` policy (`per-task`, `per-section`, `end-of-plan`), declared once per spec, never encoded in a task's command.
4. **`gate-contract.md`, `bands.md` and `align.md`** gain the code with its closing command — "declare a narrower `scopes.task`" — beside the three that already exist.
5. **Tests**: one fixture per code, the minimal correction that retires each (`pf-task-wide` retires when the task scope narrows), the required-key case whose message names `scopes.task`, and a README case proving the digest changes when only the task scope changes.

`proof/readme.py` needs no rendering change: it already prints the three scopes and their "not declared" state, and the digest already folds `scopes`.

## Out of Scope

- Changing any target's runner or its specs: the front grades a declaration and never edits a command. SAFRA's own tiers move in SAFRA's spec.
- Making `verification: end-of-plan` the default: it is a per-spec decision, and the flow already exposes it.
- Shipping the selector or a temp-root helper: unchanged — the plugin never installs a runner.
- Bumping the plugin version: a release is cut by `/release`, never at a spec's close.

## Design

The check is a pure read of `inventory.cost`, in the same shape as `check_scope_wide`:

- `cost is None` → nothing (the absence belongs to `pf-cost-undeclared`).
- either `scopes.task` or `scopes.close` absent → nothing, same reason.
- equal strings → one `pf-task-wide` error at `config_path`.

Requiring the key is a one-line change in `_cost_missing`, and its order in the message follows
`COST_REQUIRED`, which is also the order the README prints. Nothing else moves: the loader already
accepts `task` (`COST_SCOPES`), the model already carries it, and the digest already folds it.

## Alternatives Considered

- **Keep `task` optional and only fire when declared.** A target dodges by omitting the key, and the generated README keeps printing "Task scope: not declared" with no code behind it — the surface would describe a tier that the contract never asked for.
- **Infer the tiers from the command text** (e.g. flag a task command containing the close's selector). Fragile: the commands are prose, and a target may wrap the selector in a script. Equality of the two declared strings is the only fact the front can know.
- **A separate `pf-task-absent` code.** Two codes for one fact; `pf-cost-undeclared` already exists to name missing keys, and adding the key to its list keeps one message per missing decision.

## Open Decisions

- none — the shape follows `pf-scope-wide`, and the required-key change has one obvious order.

## Risks

- **A declaration tightening is visible in every target.** A target that declares `proof.cost` without `scopes.task` starts reporting `pf-cost-undeclared`. Mitigation: the message names the key, the standard carries the adoption note, and the release note repeats it; the finding is advisory, never a refusal.
- **The declaration is a claim the front cannot verify.** A target may name a task command its specs do not run. Mitigation: the standard says so explicitly, and the close's gate stays the proof of the branch; `pf-task-wide` only removes the case where the claim is contradicted by the target's own words.
- **The doctor's signal moves for a target that was already right.** A target whose task scope is narrower keeps reporting zero cost codes; only the undeclared case changes, and that is the case the spec exists to surface.
