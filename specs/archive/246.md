## Problem

Seguimento da 231 (que cortou imports do pilar specs e deixou o backend git fora do escopo). Medido em 2026-11-22 neste repositório (Windows, Python 3.14, main 35698fa04, release 7.12.0), com um audit hook em `subprocess.Popen` em volta de `.agents/quenching/assets/bin/cq`:

| chamada (só leitura) | processos git |
|---|---|
| `cq specs status 245` | 15 |
| `cq specs show 224` | 9 |
| `cq specs next --epic 245` | 10 |
| `cq specs section 224 Problem` | 9 |

Cada leitura abre um Python e mais 9 a 15 `git.exe`, e o Defender verifica cada um. Boa parte é repetição dentro da mesma chamada: `rev-parse --verify --quiet <sha>^1` 2 a 4 vezes, `rev-parse quenching^{commit}` 2 a 3 vezes, `remote get-url origin` 2 vezes (uma com `-C` da store), `ls-tree -r -z --full-tree` de dois commits e `cat-file --batch` aberto mais de uma vez. Além disso, os agentes chamam o cq pela shell, um Python novo por pergunta, embora o servidor MCP `quenching` exista e o `cq deploy` o registre sempre desde a 235.

Decisão do humano (2026-11-22): prioridade máxima, à frente da fila do épico 245, com novo release ao concluir. Escopo:
1. **Cortar os spawns git repetidos de cada chamada** por memoização dentro do processo (ref resolvido, URL do remote, árvore da store por sha, um `cat-file --batch` reutilizado). Alvo a medir: cerca de 3 processos git por leitura, sem mudar nenhuma saída (os goldens decidem).
2. **Agentes no MCP.** Com o processo vivo do MCP, a árvore da store pode ficar em cache por ref, e os corpos de comando e agentes passam a preferir as tools `quenching.*` quando presentes, com a shell como fallback. Só entra com medição: processos Python e git abertos num ciclo típico (por exemplo, um runner de uma task) antes e depois, e o custo em tokens dos schemas das tools MCP contra o das chamadas pela shell. A cautela do humano vale: nada de camada que custe tokens sem retorno medido.
3. **(opcional) Roteador `cq` como módulo com `.pyc` (P3 da 231)**, só se a medição mostrar ganho além do ruído.

Fora, por decisão do humano: mover os diretórios temporários dos testes para `.quenching/` e migrar os testes para rodarem em processo. Continuam valendo as decisões da 231: piso Python 3.11+ e nada de daemon novo, porque o MCP já existe.

**Insumos**
- `quenching/assets/bin/quenching/specs/backends/git.py` e o leitor da store (`ls-tree`, `cat-file --batch`, `rev-parse`)
- `quenching/assets/bin/quenching/mcp/server.py`
- o audit hook de medição: `sys.addaudithook` contando `subprocess.Popen` em volta de `runpy.run_path(".agents/quenching/assets/bin/cq")` com `.agents/quenching/assets/bin` no `sys.path`
- spec 231 (Outcome com a medição de imports) e spec 235 (MCP sempre registrado)

## Proposal

- Uma leitura do cq no backend git (`specs status`, `show`, `next`, `section`) abre no máximo 5 a 9 processos git em vez de 9 a 15, sem mudar nenhuma saída: os goldens e as suítes existentes ficam intactos.
- O tip remoto, o commit pendente e o pai do pendente saem de UM `git for-each-ref`, e o pai de um commit é memoizado por sha (commits são imutáveis).
- A URL do `origin` é lida uma vez por processo: `detect_provider` semeia uma memória em `quenching/common/git.py` que `open_git_backend` e `members.origin_url` reutilizam.
- Um teste de regressão conta os processos git de uma leitura com um audit hook em `subprocess.Popen` e falha se a contagem voltar a subir.
- A medição antes e depois (processos git e Python por leitura e num ciclo típico pela shell e pelo MCP, e o custo em tokens dos schemas MCP) fica registrada na spec, e a preferência pelas tools `quenching.*` só entra se a medição mostrar ganho.

## Out of Scope

- Mover os diretórios temporários dos testes para `.quenching/` e migrar os testes para rodarem em processo — fora por decisão do humano (2026-11-22).
- Um processo `git cat-file --batch` persistente por backend — no Windows, um filho vivo com cwd no repositório temporário impede a limpeza dos testes e exige ciclo de vida explícito; o ganho é de 1 processo em `status` e `next`. Fica como achado, não como entrega.
- Pré-carregar todos os textos da store na primeira leitura — medido: 1021 blobs, 14,4 MB, 1,4 s contra 45 ms de um spawn; troca processo por bytes e perde.
- Roteador `cq` como módulo com `.pyc` (item 3, P3 da 231) — só com ganho além do ruído; esta spec mede e registra, e um ganho vira spec própria.
- Daemon novo ou cache em disco novo — vale a decisão da 231: o MCP já é o processo vivo.
- Mudar o fetch de `status` ou a janela `FETCH_TTL_S` — são semântica de frescor, não repetição.

## Design

### Decisões

- **Tip, pendente e pai num único spawn.** `git for-each-ref --format=%(objectname) %(objecttype) %(parent) %(refname)` sobre o ref de rastreio e o ref pendente devolve os dois tips e o pai do pendente; ref ausente simplesmente não aparece, o que reproduz o `rev-parse --verify --quiet` que devolvia None. O modo espelho (só leitura) continua sem ref pendente. Os métodos `_local_tip`, `_pending` e `_parent` continuam existindo (testes e escritas os chamam).
- **Memoizar só o imutável ou o que a própria chamada controla.** O pai de um commit nunca muda, então `_parent` guarda por sha sem invalidação. O tip continua sob `TIP_MEMO_S` e é limpo a cada escrita, como hoje, para o portal e o MCP verem um commit externo.
- **URL do remote por processo.** `_STORES` já congela a URL por repositório e processo; a memória nova só evita a segunda leitura. `detect_provider` continua chamando o `_git` injetável (os testes o substituem) e semeia a memória; os leitores consultam a memória antes de abrir `git remote get-url`.
- **Prova por contagem, não por tempo.** O teste conta `subprocess.Popen` de git com `sys.addaudithook` filtrado por uma flag de ativação (o hook não pode ser removido), numa store de fixture com ref pendente.

### Contratos que não podem ser contrariados

- Saída byte a byte igual: goldens e suítes `test_specs_*`.
- Piso Python 3.11+ e nada de daemon (231).
- `docs/standards/workflows/task-execution.md` §Pre-existing errors para os vermelhos de plataforma.

### Assumptions

- O pai do pendente é lido via `%(parent)` do `for-each-ref`, que existe desde git 2.x antigo — depende disso: `## Design` §Decisões.
- O custo em tokens das tools MCP é medido pelo tamanho do `tools/list` do servidor local — depende disso: task 2.2.

## Alternatives Considered

- **`cat-file --batch` persistente servindo refs, árvores e blobs num só processo** — chegaria perto de 2 processos por leitura, mas exige um filho vivo com ciclo de vida explícito; no Windows ele prende o diretório temporário dos testes e no MCP vive indefinidamente. Rejeitado pela cautela de correções mínimas.
- **`diff-tree` no lugar do segundo `ls-tree`** — mesmo número de processos; não paga a mudança.
- **Aumentar `TIP_MEMO_S`** — esconderia a repetição do ref pendente, mas muda a janela que o portal usa para ver commits externos e quebra o teste da janela.

## Risks

- O `for-each-ref` devolver o tip de um ref que não é commit (peel) — mitigação: filtrar `%(objecttype)` igual a `commit`, como fazia o `^{commit}`.
- Memória da URL ficar velha num processo longo (MCP) após `git remote set-url` — ACCEPTED — `_STORES` já congela a URL por processo hoje.
- O audit hook do teste vazar para outros testes — mitigação: o hook só conta enquanto uma flag de módulo está ligada.
- Gate local vermelho por plataforma mascarar falha nova — mitigação: comparar com a linha de base e esperar o CI.

## Outcome
