## Problem

Sub-spec da 262 (gate local verde no Windows): os testes que dirigem uma ferramenta falsa ou um processo filho. Depende da sub-spec de fundação (helpers `quenching/tests/_tools.py`: ferramenta falsa, ferramenta real no PATH sem symlink, Git Bash). Medido em 2026-11-23 no slot 3 (main `efd26cfe2`, Windows 11, Python 3.12, `pytest -n auto`); cada sintoma se reproduz com `python -m pytest quenching/tests/<módulo>`.

**Módulos e sintomas:**
- `test_codex_implement` (19): `os.symlink(shutil.which("git"), bin/git)` → `[WinError 1314]` no `setUp`; a falsa `codex` é um script com shebang sem extensão.
- `test_codex_probe` (18): `codex is not on PATH` — `shutil.which("codex", path=…)` não acha a falsa sem extensão no Windows.
- `test_specs_chat` (8) e `test_portal_serve` (2): a falsa `claude` não é achada e o `which` devolve o `claude.EXE` real do usuário (`'Job' object has no attribute 'thread'`, `log.json` ausente); `TypeError: Object of type MagicMock is not JSON serializable`.
- `test_public_readiness` (11+): symlink do `git` no PATH isolado; scanners falsos.
- `test_git_preflight` (3): `gh` falso não achado (`ci: unknown`).
- `test_verify_repo_functional` (8), `test_functional_checks_isolation` (2), `test_study_material`, `test_align_contract` (4), `test_deploy_settings`: `bash` resolve o lançador do WSL (`execvpe(/bin/bash) failed`) ou é ligado por symlink.
- `test_run_evals` (16): `bash` do WSL, `os.getuid` inexistente no Windows, `a_timeout_kills_the_grandchildren_too` (`exit 1` em vez de `timeout`).
- `test_design` (2): `typst` falso → `[WinError 193]`.
- `TargetLauncher` (`test_git_ignored` e afins, 5): o teste executa o lançador `cq` (script Python com shebang) direto → `[WinError 193]`.
- `test_toolchain_test`, `test_toolchain_layers`: a execução real de pytest dentro do teste falha no Windows.

**A pergunta de produto em cada caso:** quando o código de produção resolve o binário com `shutil.which` (codex, claude, gh, typst), um `codex.cmd`/`claude.cmd` instalado pelo npm funciona no Windows? Onde não funciona é bug de produto e se corrige no código, com teste. Onde o comportamento testado não existe no Windows (sinal POSIX, `getuid`), `skipIf(os.name == "nt")` com o motivo escrito.

**Pronto quando** `python -m pytest` desses módulos passa no Windows sem PYTHONUTF8 e continua verde no Linux (CI). Regra do humano: corrigir teste e código, nunca esconder falha.

## Proposal

Fazer os testes que dirigem uma ferramenta falsa ou um processo filho passarem no Windows, sem PYTHONUTF8 e sem perder o verde no Linux, corrigindo o produto onde o Windows revela um bug e o teste onde ele supõe POSIX.

- **Ferramentas falsas** (`codex`, `claude`, `gh`, `typst`, scanners de `/quenching-opensource readiness`): os testes passam a escrevê-las com `_tools.fake_tool`, e o `git` real entra no PATH isolado com `_tools.link_tool`, sem symlink.
- **Produto que detecta com `shutil.which` e executa pelo nome puro** (o readiness acha `gitleaks.cmd` e depois chama `gitleaks`, que o Windows não acha): passa a executar o caminho que resolveu. O `cq git preflight` resolve o `gh` pelo mesmo `which` antes de chamar.
- **`bash`**: os testes que rodam scripts POSIX usam `_tools.bash()` (Git Bash) em vez do nome `bash`, que no Windows cai no lançador do WSL.
- **`git/ignored.py`**: as regras de ignorados do git sempre usam `/`; o código passa a comparar com `posixpath`, não com `os.sep`.
- **`scripts/run_evals.py`**: `os.getuid` e `killpg` só existem no POSIX; o runner ganha o caminho Windows onde o comportamento existe (matar a árvore de processos com `taskkill /T`) e o teste do contêiner com `--user uid:gid` fica `skipIf(os.name == "nt")` com o motivo escrito.

## Design

- As ferramentas falsas usam `_tools.fake_tool(bin_dir, name, source)`: no Windows um `.cmd` que chama `sys.executable` com o corpo Python; no POSIX o script com shebang de sempre. O `git` real entra com `_tools.link_tool`.
- Onde o produto já resolve com `shutil.which(name, path=env["PATH"])` (codex, claude, typst), um `.cmd` funciona sem mudança de produto: o `Popen([caminho.cmd, ...])` passa pelo `cmd.exe`. Onde ele detecta com `which` e executa o nome puro (readiness), o Windows só acha `.exe`, e a correção é executar o caminho resolvido.
- Um `.cmd` interposto não morre junto quando o produto mata o processo no timeout: o `cmd.exe` morre e o `python` filho fica. O `codex/probe.py` já usa `taskkill /T`; onde outro caminho de timeout mata só o pai, o produto passa a matar a árvore.
- `skipIf(os.name == "nt")` só para o que não existe no Windows (o `--user uid:gid` do contêiner do `run_evals`), com o motivo escrito no decorador.

## Alternatives Considered

- **Generalizar `common/tools.spawn_argv` para resolver qualquer ferramenta com `which`.** Rejeitada: `test_windows_tools` registra a decisão de não pôr o `cmd.exe` no meio de outra ferramenta além do `az`, por causa de `&`, `%` e aspas em argumentos livres.
- **Compilar um `.exe` falso (csc) para ser achado pelo nome puro.** Rejeitada: dependência de compilador e um binário por teste; o produto resolver com `which` é o comportamento correto e já é o dos outros comandos.
- **`skipIf` nos módulos inteiros no Windows.** Rejeitada pela regra do humano: o comportamento existe no Windows.

## Outcome

**O que entrou.** Os testes que dirigem ferramentas falsas e processos filhos passaram a correr no Windows. As ferramentas falsas (`codex`, `claude`, `gh`, `typst`, os scanners do readiness, o `git` dos testes) são escritas com `_tools.fake_tool` e ligadas com `_tools.link_tool`. Os scripts POSIX dos testes e do `run_evals` rodam pelo Git Bash, não pelo lançador do WSL (`System32\bash.exe`). No produto, cinco mudanças:
- `opensource/readiness._run` e `git/preflight._gh` executam o caminho que o `which` resolveu. No Windows, um nome puro só alcança `.exe`.
- O timeout de `specs/chat.py` e de `scripts/run_evals.py` mata a árvore com `taskkill /F /T`.
- O `run_evals` não chama `os.getuid` fora do POSIX.
