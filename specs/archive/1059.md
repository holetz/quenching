## Problem

`/quenching:git:branch` leads its isolation offer with Worktree **unconditionally** and states the
cost in the same block as the ask — a fresh checkout carries only what git tracks, so no installed
dependencies, no `.env`, no venv, no build output. `assets/references/git/isolation.md` §The
worktree is the preferred form calls that statement of cost the deliberate alternative to sniffing
the target for `package.json` or `.venv/`.

Stating the cost is honest. Offering no remedy is the gap: the only relief a target has is
`worktreeSetup`, a shell command it must author alone (`plugins/quenching/assets/bin/quenching/specs/config.py:69`,
run at `commands/git/branch.md:73-74`). Every adopting repository therefore rewrites the same
script — resolve a path beside the repo, create a link, be idempotent, refuse to clobber — and
most simply do not, because the plugin never suggests that anything *could* survive.

The class of file this costs most is the one that cannot be made again: a dated extract, the
notebook behind a number, a dump too large or too sensitive to track. Git treats "reproducible in
two minutes" and "irreproducible" as one ignored category; so does every worktree teardown. The
sibling spec declares the contract that names the difference — this one is the mechanism that makes
the declared area actually survive, without which that contract is advice.

Measured evidence that the loss is real and not hypothetical is in
`~/.claude/plans/estamos-com-um-problema-warm-floyd.md`: a live repository with an orphaned
worktree directory holding **4.2 GB** of `notebooks/` that no command of that repo can see, and
563 MB of ignored analysis data existing in the primary checkout only.

## Proposal

One optional key, one deterministic subcommand, one step in the isolation flow.

**The key.** `.claude/quenching.json` gains `sharedPaths` beside `worktreeSetup` — a list of
repo-relative paths that resolve to one store shared by every checkout of the repository:

```json
{"sharedPaths": ["trabalho"]}
```

Absent, empty or unparseable-in-the-usual-way behaves exactly as `worktreeSetup` does today:
no key means no behaviour, and declaring nothing costs nothing.

**The store is a sibling of the repository, owned by no checkout.** Derived from any checkout —
**and `--path-format=absolute` is not optional**:

```bash
STORE="$(dirname "$(git rev-parse --path-format=absolute --git-common-dir)").<name>"
```

Measured on git 2.43.0: without the flag, `--git-common-dir` returns the **relative** `.git` in the
primary checkout, so `dirname` yields `.` and the store is created as `..<name>` under the current
directory — a different store per invocation path, each checkout silently seeing its own. The
worktree case returns an absolute path and would appear to work, which is what makes the bug
survive a casual test. The identity assertion in §Validation is the test that catches it.

The consequence that decides the design: `git clean -fdx` in any checkout — primary included —
removes only the link, never the content.

**The subcommand.** `cq git worktree link` resolves the store, normalises each declared path in the
current checkout, and reports what it did as `--json`. Its four states are the whole contract:

| State of `<path>` in the checkout | Action |
| --- | --- |
| a symlink already resolving to the store | nothing — idempotent, and the common case |
| a symlink resolving elsewhere | re-point it at the store |
| a real directory with **any** entry, dotfiles included | **refuse (exit 2)**, naming the path and the merge the human must do |
| absent | create the link |

The refusal is the guardrail against the very loss this spec exists to prevent: the tool never
deletes content to make room for a link. "Any entry" is literal — a directory holding only
`.env` or `.cache` is not empty, and treating it as empty is how the guardrail is defeated by a
listing that skipped dotfiles.

**The step.** `commands/git/branch.md` step 4 runs `cq git worktree link` immediately after
`git worktree add` and **before** `worktreeSetup` — the setup script may legitimately want to write
into the shared area. Its consent is the isolation offer itself, exactly as `worktreeSetup`'s is:
the declared paths are displayed verbatim in the offer block, and choosing Worktree is the OK. A
failing link is reported and never undoes the worktree, on `worktreeSetup`'s own precedent.
## Out of Scope

- **What goes in the shared area, and the rule that sorts a write between destinations.** That is
  the sibling contract spec. This one materialises whatever the target declared.
- **Local history, snapshots, backup and retention for the store.** The original plan proposed
  `git init` in the store with no remote plus a `SessionEnd` snapshot hook. It stays with the
  target: a second unbacked repository holding possibly sensitive data is a policy decision a
  plugin does not make for a corporation. A target wanting it declares it in `worktreeSetup`.
- **Moving any existing data.** The tool creates and re-points links. It never `mv`s a directory,
  never merges two trees, and refuses rather than guessing — a migration of an existing ignored
  tree into a store is a one-time human act, per repository.
- **Hardlinking individual ignored files inside a versioned tree.** The plan's Phase 4 needed this
  because a versioned directory cannot become a symlink. It is a genuinely different mechanism with
  its own failure modes (same-filesystem requirement, silent divergence on mutation) and it is not
  admitted here on one repository's evidence.
- **Windows-first support.** See §Risks: the fallback is named, not engineered, in this spec.

```bash
echo ping > <worktree>/<path>/ping && cat <primary>/<path>/ping

# idempotence: a second run changes nothing and exits 0
cq git worktree link --json    # twice

# the guardrail: a real directory with content REFUSES and preserves it
mkdir <path> && touch <path>/keep && cq git worktree link ; echo "exit=$?"  # exit 2, keep intact

# git ignores the link on both sides
git status --porcelain | grep -c <path>   # 0
```

## Design

### Why a declared list and not a convention

A fixed conventional path would be greppable across repositories, which is the bundle's usual
argument and the right one for `/docs/`. It loses here on two counts: the path must appear in the
target's own `.gitignore`, which the plugin does not write; and the name carries meaning the target
owns. A list also lets a repository share more than one area without the plugin inventing a
hierarchy for them.

### Why the store is a sibling and no checkout owns it

If the store lived inside the primary checkout, every worktree would depend on the primary
existing, `git clean -fdx` in the primary would destroy shared content, and the primary's own
`git status` would carry it. As a sibling, all checkouts are symmetric, and the destructive
command reaches only links.

### Why refuse instead of merge

A real directory with content at the link path means two histories exist. Merging them is a
judgement about which copy is newer or truer, and a tool that guesses wrong here destroys exactly
the irreproducible files this whole line of work is about. Refusing costs the human one manual
merge, once.

### Why the link runs before `worktreeSetup`

The setup script is the target's own code and may write into the shared area — a venv cache, a
downloaded fixture. Ordering it second makes the shared area available to it; ordering it first
would make the two steps' dependency direction a coin flip.

## Alternatives Considered

- **Extend `worktreeSetup` and ship nothing else.** The target already can do all of this in its
  own script. Rejected because the cost is paid per repository, forever, for a mechanism that is
  identical everywhere; and because a plugin that recommends worktrees unconditionally owes a
  remedy for the cost it names.
- **A `sharedDirectories`-style key that copies rather than links.** Copying is portable (no
  symlink, no Windows problem) and wrong: two divergent copies of an irreproducible file is a worse
  failure than one missing copy, because nothing tells you which is which.
- **Make the store a git repository the plugin manages.** The plan's Phase 6. Rejected as target
  policy, not plugin behaviour — see §Out of Scope.

## Open Decisions

- **Settled key name.** Use `sharedPaths`: it reads plainly and matches the config's existing camelCase. `sharedDirectories` is the plan's Orca precedent, and `worktreeShared` would group it visually with `worktreeSetup`, but neither is needed.
- **Settled store naming.** Use `<repo>.<name>` (`acme.trabalho`), one sibling per declared path; it is simpler to derive and clean up than `<repo>.shared/<name>`, which would keep the parent directory tidy when several paths are declared.
- **Whether `cq git worktree link` runs in the primary checkout too.** It must, or the primary is the one checkout holding a real directory while every worktree holds a link — the asymmetry the design explicitly rejects. What remains undecided is *when*: on demand only, or also from some other command the human already runs.
## Risks

- **The derivation is silently wrong without `--path-format=absolute`, and the wrong result looks
  like success.** Measured on git 2.43.0 (§Proposal). Each checkout gets its own store, every write
  appears to work, and the loss is only discovered when someone looks for a file in the other
  checkout. Mitigation: the identity assertion in §Validation compares `readlink -f` from both
  sides, and it is a required test rather than a manual check.
- **A directory holding only dotfiles reads as empty and the guardrail is defeated.** The refusal
  state is the one thing standing between this tool and the data loss it exists to prevent, and the
  natural implementation (`os.listdir` truthiness) is correct here only if nothing filters hidden
  entries. Mitigation: a fixture whose only content is `.env`.
- **A target declares `sharedPaths` and forgets its `.gitignore`.** Every checkout then shows the
  link as untracked, and someone eventually commits a machine-specific absolute symlink into the
  repository. This was an Open Decision; it is a risk with a named mitigation instead — the offer
  block displays the declared paths verbatim, and the link step reports a declared path that
  `git check-ignore` does not cover, as a warning beside the link it just made.
- **The target's own `worktreeSetup` may already create the same link**, and the re-point state then
  has two authors alternating. Mitigation is ordering plus documentation: the link runs first, and
  §A target may declare a setup command states that a setup script must not re-create a declared
  shared path.
- **Windows.** `mklink /D` needs Developer Mode or elevation; the junction fallback (`mklink /J`)
  does not, but a junction is traversable by `git clean -fdx`, which reintroduces the one path to
  destroying the store. For a plugin that must be portable this is a permanent support cost, not a
  one-repository annoyance. Minimum bar for this spec: never leave a *wrong* link — degrade to no
  link, reported.
- **A shared area partially defeats the isolation a worktree exists to give.** Under fan-out, two
  executors write to one store concurrently. Mitigation is contractual and belongs in spec 1058's
  standard: the shared area is **stamped append** (`<date>/`, `<slug>/`, `<session>/`), never a
  mutable shared workspace. Ship the two specs with that sentence in both, or trade data loss for
  data corruption.
- **`config.py` is contended.** Spec 1057 Phase A moves key validation out of the specs loader.
  Whichever lands second rebases onto a moved home. Read 1057 before touching `CONFIG_KEYS`.
- **Accepted:** running the subcommand in a repository that declares `sharedPaths` but has no
  worktrees creates a sibling store nobody else will ever open. It costs an empty directory, it is
  removed by deleting it, and guarding it would mean refusing the primary checkout — which the
  design requires to be symmetric with every other.
