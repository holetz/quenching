## Problem

Achado estacionado na conclusão da spec 2265 (2026-11-21), fora do escopo dela. Em `_commits_to_push` (`quenching/assets/bin/quenching/common/leak.py:258-275`), usado por `cq leak --pre-push` e `cq identity --pre-push`:

1. `local_sha`, lido do stdin do hook de pre-push, chega ao `git rev-list` sem validação: um campo não-hex (por exemplo `--all`) seria lido pelo rev-list como opção, alterando o conjunto varrido. A 2265 só passou a validar `remote_sha` (regex `_SHA` de 40/64 hex + `git cat-file -e <sha>^{commit}`).
2. `ZERO_SHA = "0" * 40` (`leak.py:33`): num repositório com object format sha256 o git envia 64 zeros para um delete (local) ou para uma ref nova (remote). O `local_sha == ZERO_SHA` não reconhece o delete, e o `remote_sha != ZERO_SHA` só cai no recorte de ref nova porque o `_known_commit` da 2265 recusa o sha inexistente — por acidente, não por regra.

O que a correção tem de tornar impossível: um campo do stdin do pre-push ser interpretado como opção do rev-list, e um delete/ref nova sha256 ser tratado diferente do equivalente sha1.

**Insumos**

- `quenching/assets/bin/quenching/common/leak.py:33` (`ZERO_SHA`), `:34` (`_SHA`), `:250-256` (`_known_commit`), `:258-275` (`_commits_to_push`)
- testes vizinhos: `quenching/tests/test_leak_scan.py::test_an_old_tip_this_clone_lacks_is_judged_as_a_new_ref`, `quenching/tests/test_identity_cli.py`

## Proposal

- `_commits_to_push` (`quenching/assets/bin/quenching/common/leak.py`) recusa um `local_sha` do stdin do pre-push que não seja nome completo de objeto (regra `_SHA`, 40 ou 64 hex): nenhum campo do stdin chega ao `git rev-list` como opção (`--all`) ou expressão de revisão (`HEAD~1`). A recusa sai como exit 2 pelos caminhos já existentes (`leak-git-failed` em `cq leak --pre-push`, `identity-git-failed` em `cq git identity --pre-push`): o push é bloqueado, nunca varrido com conjunto alterado.
- O zero de qualquer largura (40 zeros sha1, 64 zeros sha256) é reconhecido por regra: delete local (`local_sha` zero) devolve nenhum commit, e ref nova (`remote_sha` zero) cai no recorte de ref nova sem depender do `_known_commit` recusar o sha inexistente.
- Testes de regressão nos dois verbos provam as duas propriedades.

## Out of Scope

- Validar `local_ref`/`remote_ref` do stdin — não chegam ao `git rev-list`; só os shas chegam.
- Usar `--end-of-options` no `rev-list` — o épico 183 diz "pode usar"; aqui não serve, porque tudo depois dele (`--not`, `--remotes=<r>`) viraria revisão. A validação `_SHA` já fecha a injeção.
- Um código de recusa próprio (`leak-push-input-invalid`) — exigiria tocar `security/__init__.py` e `git/identity.py`; os códigos `*-git-failed` existentes já bloqueiam com exit 2.
- Repositórios sha256 de ponta a ponta (fixture `git init --object-format=sha256`) — o recorte se prova pelos shas do stdin; o object format do clone não muda a regra.

## Design

- **Regra:** um sha do stdin do pre-push só chega ao `git` depois de casar `_SHA` inteiro; o zero é `_SHA` com todos os dígitos `0`, de qualquer largura que `_SHA` admite. Um `_is_zero(sha)` único decide delete e ref nova, e `ZERO_SHA` (40) fica como constante que os testes já usam.
- **Ordem em `_commits_to_push`:** `local_sha` zero → `[]` (delete); `local_sha` fora de `_SHA` → recusa; `remote_sha` zero → recorte de ref nova; `remote_sha` conhecido → `local --not remote [--remotes=<r>]`; desconhecido → recorte de ref nova (comportamento da 2265, inalterado).
- **Recusa fail-closed sem tocar os chamadores:** `PushInputInvalid` é subclasse de `subprocess.CalledProcessError` com a mensagem em `stderr`, então os `except CalledProcessError` de `security/__init__.py::_leak` e `git/identity.py::cmd_identity` já a convertem em exit 2. Pular a linha seria fail-open; o git nunca envia um sha não-hex, então a recusa só dispara sobre stdin forjado.
- Contratos que não podem ser contrariados: o comportamento da 2265 para `remote_sha` desconhecido (judged as a new ref) e os testes vizinhos (`test_an_old_tip_this_clone_lacks_is_judged_as_a_new_ref`, `test_pre_push_over_an_old_tip_this_clone_lacks_judges_instead_of_refusing`).

### Assumptions

- O git envia shas em hex minúsculo (40 ou 64) no stdin do pre-push — sustenta a recusa de qualquer outra forma (`## Design`).

## Alternatives Considered

- **Pular a linha com `local_sha` inválido** — perdeu: fail-open, um stdin forjado passaria sem varredura.
- **`--end-of-options` antes dos argumentos do rev-list** — perdeu: transforma `--not`/`--remotes=` em revisões; exigiria reordenar o comando sem ganho sobre a validação.
- **Código de recusa novo nos dois verbos** — perdeu: mais superfície (dois CLIs) pelo mesmo exit 2.

## Open Decisions

## Risks

- Um sha em hex maiúsculo vindo de uma ferramenta que não é o git seria recusado — ACCEPTED: o git sempre envia minúsculo; recusar é fail-closed.
- A mensagem de recusa sai sob `*-git-failed` ("git failed while ...") embora o git não tenha rodado — ACCEPTED: o texto do `stderr` nomeia o campo inválido; o código só decide o exit.
