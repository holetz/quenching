## Problem

O passo 2c de `/quenching-specs execute` só re-verifica numa retomada; na primeira execução "Nothing checked yet → run nothing" (`quenching/skills/quenching-specs/references/execute.md:142`). Um vermelho pré-existente só aparece depois de o agente já ter escrito código, e classificá-lo exige montar o worktree `.quenching/red` com o contexto já contaminado pelo diff — o oposto do que o artigo "Effective harnesses for long-running agents" recomenda (um smoke antes de qualquer feature).

## Proposal

- Na primeira execução, logo após o `worktreeSetup`, rodar uma vez o `verify:` da primeira task (ou o comando mais estreito de `## Validation`), antes de qualquer código.
- Vermelho nesse ponto é da base por construção (o worktree está limpo): rota 5i direto, sem worktree RED.
- Respeitar a regra de `execution.md` §The verification policy: comando que gasta sessões faturadas não roda nesse baseline, e o relatório diz isso.

## Out of Scope

- Mudar a re-verificação de retomada já existente no 2c.

## Impact

### Standards this spec will write into docs/standards/

- none — a regra vive numa frase do passo 2c do `execute.md`; nenhum padrão novo.

### Product code this spec expects to touch

- `quenching/tests/test_specs_execute.py` — o teste que fixa a frase "Nothing checked yet → run nothing"

### Process surface this spec expects to touch

- `quenching/skills/quenching-specs/references/execute.md` — passo 2c: a primeira execução roda o baseline
- `.agents/skills/quenching-specs/references/execute.md`, `.claude/skills/quenching-specs/references/execute.md` e `.agents/.quenching-deploy.json` — espelhos gerados pelo deploy

## Validation

- `python -m unittest discover -s quenching/tests -p test_specs_execute.py` passa, com o teste atualizado para a frase nova.
- O teste atualizado falha contra a main (a frase antiga não traz o baseline).
- `python3 quenching/assets/bin/cq deploy --target . --write` deixa os espelhos em lockstep.
- `bash scripts/verify_repo.sh` não aumenta a linha de base de falhas.

## Design

- **Decisão: muda-se a frase final do 2c, sem passo novo.** "Nothing checked yet → run nothing" vira: rodar uma vez o `verify:` da primeira task (o comando mais estreito de `## Validation` quando não houver), antes de qualquer código. A cautela do humano pede nenhum passo novo em corpo de comando.
- **Decisão: vermelho no baseline é da base por construção** (árvore limpa, `worktreeSetup` já rodou): segue direto à rota 5i, sem worktree `.quenching/red`.
- **Decisão: comando que gasta sessões faturadas não roda no baseline** (`execution.md` §The verification policy); o relatório diz que foi pulado.
- **Decisão: o vermelho que é só o RED da própria task** (o `verify:` exercita código que a task ainda vai criar) não é da base e não aciona a 5i.
- **Decisão: a re-verificação de retomada do 2c fica intacta** (Out of Scope).

### Assumptions

- O `verify:` da primeira task roda na árvore limpa; o caso de teste novo que a task cria é o RED dela — `## Risks` depende disso.

## Alternatives Considered

- **Rodar o gate inteiro do repositório no baseline.** Descartado: caro e já coberto pelo conclude; a spec pede o comando mais estreito.
- **Novo passo 2d dedicado.** Descartado: acrescenta passo ao corpo sem retorno medido; uma frase no 2c basta.

## Open Decisions

- none — o fix cabe numa frase de um passo existente.

## Risks

- **Falso vermelho** quando o `verify:` da primeira task exercita código que a própria task cria: MITIGATED — o texto exclui esse RED da rota 5i.

## Handoff

Uma frase no 2c de execute.md (+ teste e espelhos do deploy); nada além do escopo da 2256.

## Outcome

Entregue: o passo 2c de `execute.md` deixou de dizer "Nothing checked yet → run nothing" e passou a rodar o baseline uma vez antes de qualquer código: o `verify:` da primeira task (o comando mais estreito de `## Validation` quando ela não tem), pulando comando que gasta sessões cobradas e dizendo isso no relatório. Um vermelho ali é da base por construção: rota **5i** direta, sem o worktree `.quenching/red`, salvo se o comando só nomeia código que a própria task vai criar (o RED da task). O teste `test_specs_execute.py` e os espelhos do deploy (`.agents`, `.claude`, manifestos) foram atualizados; `cq deploy --check` sai 0. Revisado, destilado (nada a cruzar para /docs/) e sem obrigação de release.

Custo do passo (registrado pela cautela do humano): no primeiro run o passo roda 1 comando extra — o `verify:` da primeira task, uma vez; resumes não o rodam (já re-rodam o último `verify:` marcado). O texto acrescentado ao corpo carregado de `execute.md` é de +402 chars (436 da frase nova menos 34 da antiga), ≈100 tokens por chars/4.

Fora: nenhum comando novo, nenhuma camada nova. Nota: o subject truncado do commit 63e339f (1.1) fica, sem reescrita de sha já reportado (ver decision em Discoveries). Base e verificação: o CI prova o gate; na plataforma Windows há ~280 falhas pré-existentes na main.
