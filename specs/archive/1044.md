## Problem

`ops-front-contract` declares what a conformant operations surface is and publishes eight finding
codes, but nothing can answer the one question the align surface is built on: **is there work?**

`align-surface.md` §Probe before the inventory makes that answer load-bearing. Every front opens by
running its own verifier and branching on the exit code, and the rule is not an optimization — an
align that pays a full read-only inventory on a clean repo is an align nobody runs once the repo
grows, which is exactly when drift accumulates. `knowledge` has `cq knowledge validate`, `design`
has `cq design doctor`, `components` has `cq components doctor`/`lint`. `ops` has nothing, so it
cannot have an align at all.

The surface it must read is not trivial. On the measured target there are 61 tracked modules across
13 packages, 28 of which carry a `__main__` block, and the six things worth reporting about them —
who the entry points are, which router reaches them, where the root is resolved, how each exits,
what each writes, and whether any gate is commented out — are all recoverable from the source
without executing a line of it. Nothing today recovers any of them.

## Proposal

Add `ops` as the sixth route in `assets/bin/cq` and build the pillar behind it: a reader that
inventories the operations surface, and a verifier that grades it against the published contract.

**`cq ops inventory [--json]`** — walks the declared operations root and emits, per entry point:
its path, its importable module, its canonical invocation, its one-line purpose (the first docstring
line), its declared flags, whether it writes outside the repository, and its lifecycle. This is the
front's read model, and everything else consumes it.

**`cq ops doctor [--json]`** — runs the eight checks over that inventory and exits `0` when clean,
`1` when it has findings, `2` on refusal, the contract every `cq` pillar is already frozen to.

**`cq ops status [--json]`** — the human-facing read: counts by package, router health, lifecycle
split, and the finding tally by code, without the per-finding detail `doctor` carries.

The checks read **source, never behaviour**. Seven are AST-based; `op-disabled-check` is the
`tokenize` heuristic the standard published. Nothing imports a target module, and nothing executes
an entry point — a verifier that runs arbitrary target code to grade it is a worse defect than any
it could find.

Configuration is two values, `opsRoot` and `router`, read through the loader that already serves
`backend` and `specsBranch`. A repository that declares neither gets a refusal that names the two
keys, not a guess.

## Out of Scope

- **Any command body.** `commands/ops/**` belongs to `ops-align-and-status` and
  `ops-entrypoint-new`. This spec ships the programs those bodies will run.
- **Writing anything into a target.** `doctor` and `inventory` are read-only. The registry
  *generator* (`cq ops registry --write`) is `ops-entrypoint-new`'s.
- **Auto-fixing findings.** No `--fix`. Convergence is the align's, on a human's OK.
- **Executing target code.** No import of a target module, no subprocess of an entry point, in any
  check.
- **Non-Python entry points.** Shell and `.cmd` entry points are inventoried by path and lifecycle
  only; the seven AST checks do not apply and the payload says so per entry point rather than
  scoring them silently.
- **Wiring `ops` into `/quenching:align` or the README surface table.** The integration spec owns
  both.

## Design

**Inventory first, checks second, and the checks never re-walk.** The eight codes all need the same
facts, and eight independent tree walks would be eight chances to disagree about what an entry point
is. `inventory.py` produces one read model; `checks.py` is eight pure functions over it. That is
also what makes `status` cheap — it is a fold over the same model, not a second traversal.

**Every path in every payload is relative to the declared operations root.** An absolute path is
machine-dependent, and the plugin freezes these payloads in `tests/fixtures/golden/`, where a
machine-dependent field makes the fixture unfreezable and the check untestable on a second
developer's checkout. The root itself is the one absolute value, and it is reported once at the top
of the envelope rather than repeated into every row.

**How each code is decided, from source alone:**

| Code | Decided by |
| --- | --- |
| `op-no-router` | the declared router is absent from configuration, or its file does not exist |
| `op-undocumented` | an entry point in the inventory that the registry document does not name |
| `op-registry-stale` | a registry row naming no file, or a generated block whose hash does not match the inventory |
| `op-adhoc-root` | AST: a module-level binding to a root derivation outside the declared bootstrap module |
| `op-untyped-exit` | AST: a `__main__` block that discards `main`'s return value, or exits on a value that is neither a call to `main` nor an integer literal |
| `op-unarmed-write` | AST: a module that both reaches a session/client import and calls a write verb, while its parser declares no arming flag — or declares no parser at all |
| `op-disabled-check` | `tokenize`: a `COMMENT` whose stripped text parses as a call expression, indented inside a function the AST placed in the entry point's own control flow |
| `op-orphan` | an entry point with no declared lifecycle, or one declared `archived` outside `_archive/` |

**Why `op-untyped-exit` keys on the shape and not on an annotation.** The first draft of this check
required `main()` to be annotated `-> int`, which is true of the measured target because its Ruff
configuration selects `ALL`. In a repository that does not enforce annotations the same check fires
on every entry point at once, which is not a finding — it is a configuration mismatch wearing a
finding's code. What is decidable everywhere is whether the `__main__` block *carries the exit
status out*: a block that calls `main()` and throws the result away cannot have a typed exit code,
whatever the annotations say. An annotation, when present, is read as corroboration and never as the
trigger.

**Why `op-unarmed-write` keys on the parser and not on a name list.** A denylist of dangerous verbs
is unbounded and wrong on the first repo that names its own. What is decidable is the *shape*: the
module can reach a live session and can issue a write, and offers the operator no way to see the
plan first. The measured target's two deep-clone modules are exactly that shape — no parser at all —
and the check finds them without knowing what a deep clone is.

**Why `op-registry-stale` is inert when there is no registry.** The generator that writes the
registry document ships in the *next* spec, so on every real target this check would otherwise fire
on its first run against a document that no command has ever been able to produce — a finding whose
remedy does not exist yet. Absence of the registry is already fully described by `op-undocumented`
firing on every entry point, which is the honest report: nothing is documented. `op-registry-stale`
answers a narrower question — the registry exists and disagrees with the tree — and stays silent
until it can.

**Why severity is measured before it is set.** `op-disabled-check` is the one heuristic in the set.
Shipping it as an error before knowing its false-positive rate would make the front's first
impression on a real repository a wall of noise, and a check people learn to ignore never comes
back. Task 4 measures it on 61 real modules and writes the number into the standard alongside the
chosen severity.

**Why the no-execution property is asserted by a test and not by a review.** "We do not import
target code" is the kind of invariant that survives review and dies to a convenience call three
commits later. Patching `import_module` and `subprocess.run` to raise, then running the full doctor,
turns it into something the suite refuses to lose.
## Alternatives Considered

- **Run the entry points with `--help` and parse the output.** Rejected: it executes arbitrary target
  code, it needs the target's environment installed, and it makes the verifier's cost proportional to
  the slowest import in the repository. It is also what makes rule 6 prose in the contract.
- **Import each module and introspect its parser object.** Rejected for the same reason with a
  sharper edge: an import runs module-level code, and the measured target has modules whose import
  opens a Spark session.
- **One check function that walks the tree and yields every code.** Rejected: it makes the eight
  codes untestable in isolation and guarantees they drift apart in what they consider an entry point.
- **Ship `inventory` alone and let the align interpret it.** Rejected: it moves the contract into a
  command body, where it cannot be tested, and violates the probe rule — an align that must read and
  judge an inventory to learn there is no work is the expensive no-op the rule exists to prevent.
- **Reuse `components lint`'s finding machinery.** Rejected as coupling for its own sake: that
  machinery is shaped around command-body sections. The shared contract that actually matters — the
  `--json` envelope and the three exit codes — is honoured without sharing an implementation.

## Open Decisions

- **Whether `status` earns its own subcommand or is `doctor --summary`.** Both are one fold over the
  inventory. Resolved at task 3 against the other pillars' shape: `design` ships a separate `status`,
  `components` does not, and the tiebreaker is whether the align's status body needs a payload the
  doctor's would not carry.
- **Whether non-Python entry points get their own finding code.** Inventorying them by path is
  settled; whether a shell entry point outside the router is `op-undocumented` or a fourth
  lifecycle state is resolved at task 2, once the target's `bootstrap/` and `worktree/` trees are
  inventoried and counted.
- **The registry document's format.** The generator is the next spec's, but `op-registry-stale`
  needs to know what it compares against. Resolved at task 2 by declaring the generated block's
  delimiters and hash form here, so the generator implements a contract rather than inventing one.

## Risks

- **The AST checks encode one repository's idioms.** `parents[N]` is the measured target's way of
  finding a root; another repo uses an environment variable or `importlib.resources`.
  *Mitigation:* `op-adhoc-root` fires on *any* module-level root derivation outside the declared
  bootstrap, keyed on the binding's role rather than on one expression shape, and the fixture set
  includes two derivations the measured target does not use.
- **A check can fire universally because the target's conventions differ, not because it is
  broken.** That is how `op-untyped-exit` nearly shipped — see §Why `op-untyped-exit` keys on the
  shape. *Mitigation:* task 4.4 runs the whole doctor against a real repository before any severity
  is fixed, and a code that fires on more than half the inventory is treated as a contract defect to
  re-derive, not as 30 findings to report.
- **`op-unarmed-write` can miss a write that goes through an indirection.** A module that calls a
  helper which writes will not show a write verb of its own. *Mitigation:* the check is documented as
  a floor, not a proof; the front reports what it found, and
  `/docs/standards/quality/unproven-capability-warning.md` binds the report not to claim more.
- **Eight codes is a vocabulary the next three specs depend on.** Renaming one after the align cites
  it is a cross-spec break. *Mitigation:* the codes are already published by
  `ops-front-contract`; this spec implements them and may only *resolve severity*, never rename.
- **Golden fixtures make every payload change a two-file edit.** *Mitigation:* that is the plugin's
  existing contract for every pillar, and `capture_golden.py` already exists to re-freeze them.
