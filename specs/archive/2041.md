## Problem

The commands are executable prose written for Claude Code; on the platform they must run as Omnigent agents under any harness and model, with evals telling which model each command is safe on. Package the commands as Omnigent agent definitions, wire the S2 runner per model, and publish a per-command model compatibility table. Depends on the H1 spike result and the forge local profile (forge epic S6, S13).

Member S12 of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent).

## Proposal

- `plugins/quenching-omnigent/` exists, generated by `python3 scripts/sync_omnigent_plugin.py --write` from `plugins/quenching/`: one Omnigent agent bundle (`agents/<id>/config.yaml` plus `instructions.md`) per source command and per source agent, the cited payload under `quenching/`, and a README with the install path. Nothing in it is edited by hand.
- Every bundle loads with the Omnigent `v0.19.1` spec loader and carries a deny-only permission policy derived from the source `allowed-tools:` (commands) or `tools:` (agents): what the source does not grant is denied, and a scoped `Bash(cq <verbs>:*)` allows only those verbs. A grant Omnigent cannot express is denied and listed in the generated `PERMISSIONS.md`.
- The repository gate fails on drift of that tree (`sync_omnigent_plugin.py --check`), and `docs/standards/architecture/surface-translation.md` states the Omnigent rules, including how Omnigent orders permission rules.
- `scripts/run_evals.py` runs a suite under an Omnigent-hosted harness per model through a new `omnigent` profile in `scripts/eval_harnesses.json`; `--dry-run` prints each arm's argv and a test drives the plumbing against a stub, with no model call.
- A per-command model compatibility table is generated into `plugins/quenching-omnigent/MODEL-COMPAT.md` from `plugins/quenching/assets/translation/omnigent-model-compat.json`: only cells measured in spike H1 are filled, every other cell reads `unmeasured`, and the human step to fill the rest is recorded with its cost.

## Out of Scope

- Running any eval, any Databricks call or any paid model call: this spec proves the wiring with the dry run and a stub only. The Omnigent-hosted measurement is the human step recorded in `MODEL-COMPAT.md`.
- Editing a source command or agent: no `tools:` or `allowed-tools:` line changes, so the verifier's grants check (9) has nothing to report. A grant beyond the source stops the work as `needs-human`.
- Widening any permission beyond the source (non-`cq` scoped `Bash` grants such as `python3` are denied in v1, see `## Open Decisions`).
- Server-side Omnigent policies, the policy pack and the egress proxy: those are forge specs (S16, S14). Packaging the bundles into the forge image or compose is forge's (S13); this spec ships the tree and the install path.
- Mapping Claude `hooks:` frontmatter, `model:` pins and `Agent(...)` sub-agent allowlists: they are recorded as not generated, never approximated.
- Re-grading, the grader choice and any change to H1 data (forge specs 2, 14, 16).

### Layout and prose

The tree is `plugins/quenching-omnigent/` with `agents/<id>/{config.yaml,instructions.md}` (ids `quenching-<front>-<verb>` for commands and `quenching-<agent>` for agents, the OpenCode names), `quenching/` (the payload, same members as the OpenCode payload including the bundled `cq`), `PERMISSIONS.md`, `MODEL-COMPAT.md`, `README.md`, `.generated-from.json` and `.generated-files.json` (sha256 per file, the OpenCode manifest form). Rule: the generator reuses the OpenCode translation and re-roots it (`~/.config/opencode/quenching` to `~/.omnigent/quenching`, `QUENCHING_OPENCODE_ROOT` to `QUENCHING_OMNIGENT_ROOT`, the word OpenCode to Omnigent, the runtime preamble replaced by an Omnigent one), so one prose pass exists and a second harness vocabulary is not forked. The preamble names no model and no vendor CLI: the bundle runs on whatever `--harness`/`--model` the caller passes, and the source tier and effort are reported as preferences, as on OpenCode.

### config.yaml shape

`spec_version: 1`, `name`, `description`, `instructions: instructions.md`, `executor: {type: omnigent, config: {harness: opencode}}` (the loader requires a harness; `omnigent run --harness X --model Y` overrides both and no model is pinned), `os_env: {type: caller_process, cwd: .}` only when the source grants Read, Write, Edit or Bash, `spawn: true` only when the source grants a bare `Agent`/`Task`, and `guardrails.policies.source_tools` — the one deny policy below. The pin is the constant `OMNIGENT_VERSION = "0.19.1"` (server image `omnigent-server:v0.19.1`, forge S13), written into the README and checked by the test against the tag the forge compose pins.

### Rule ordering in Omnigent (recorded, v0.19.1)

Omnigent has no positional allow/deny list. Policies are evaluated in declaration order within a level, levels run session, then agent spec, then server, and a DENY from any policy short-circuits; DENY outranks ASK outranks ALLOW (`docs/POLICIES.md` and `PolicyResult` in `omnigent/policies/types.py`, tag v0.19.1). OpenCode is the opposite (last matching rule wins), so the OpenCode "catch-all first" ordering does not carry over. Durable rule: an Omnigent bundle states only denials; an ALLOW can never reopen a DENY, so the order of two denials is irrelevant to the outcome and the allowed `cq` verbs are expressed as the exception inside the one denial, not as a rule of their own.

### Permission mapping (deny-only)

One CEL policy (`omnigent.policies.builtins.cel.cel_policy`) per bundle, returning DENY on a `tool_call` whose `event.data.name` is in the denied set, else ALLOW. Tool names are Omnigent's `sys_os_*` plus the native names the harnesses expose (`omnigent/policies/builtins/safety.py`, `orchestration.py`).

| Source head | Absent or not granted: denied names |
| --- | --- |
| `Write` / `Edit` / `NotebookEdit` | `sys_os_write`,`Write`,`write` / `sys_os_edit`,`Edit`,`MultiEdit`,`edit` / `NotebookEdit`; each head independently, so `Edit` alone never grants `Write` |
| `Read` / `Grep` / `Glob` | `sys_os_read`,`Read`,`read` / `Grep`,`grep` / `Glob`,`glob` |
| `WebFetch` | `WebFetch`,`webfetch`,`WebSearch`,`websearch` (a granted `WebFetch` has no Omnigent tool to express it and is listed in PERMISSIONS.md) |
| `Agent` / `Task` bare | `sys_session_create`,`Task`,`Agent`,`task` when neither is bare; a scoped `Agent(names)` is not expressible and stays denied, listed |
| `Skill` | `Skill` when absent |
| `Bash` | absent: `sys_os_shell`,`Bash`,`Shell`,`bash`; bare `Bash`: none; scoped only: the shell rule below |

Shell rule when the source grants scoped `Bash(cq …:*)` and no bare `Bash`: DENY a shell call unless its `command` argument matches, in full, one or more allowed segments joined by `&&`, `||` or `;`, each segment being `cq <verbs>` (the source's verbs, in source order, bare `Bash(cq:*)` meaning `cq`) followed by arguments free of `; & | < > $` backtick, backslash and newline. A missing `command` is denied. Consequences, recorded: a heredoc, a redirect, a pipe or a command substitution is denied (Omnigent has no parser a CEL expression can call; the conservative regex denies what it cannot split), and a non-`cq` scoped grant (`python3`, `py`, `rm`, `mkdir`, `git ls-files`, …) is denied and listed per bundle in `PERMISSIONS.md` as "not expressed", never widened.

`allowed-tools:` on a command is a pre-approval in Claude Code (the human is prompted for the rest) and `tools:` on an agent a restriction. The mapping reads both as the grant set, which makes command bundles stricter than the Claude command, never wider (recorded in `## Open Decisions`). `hooks:` and `model:` frontmatter are dropped and listed.

### Model compatibility table

`omnigent-model-compat.json` holds, per measured command and model, the approved cases, the assertion pass rate and the agent cost from forge `spikes/h1/` (`REPORT.md`, forge specs 2, 14, 16): git commit, knowledge define and specs create on `opus-5-5`, `sonnet-5-5`, `haiku-5-5` and `deepseek-v4-1-flash-1017`, three cases each. The generator renders one row per generated command id and one column per model, `unmeasured` unless the JSON holds the cell; the header states that H1 ran OpenCode 1.19.4 with the quenching-opencode port, not an Omnigent-hosted run, so the cells are evidence about the model on that harness and not about Omnigent. The fill-in cost is recorded as a human step: agent cost per case is the H1 total over 9 cases (Flash US$ 0.1856, Opus US$ 1.1727, Sonnet US$ 0.7816, Haiku US$ 0.0359), the five committed suites hold 3 cases each, so re-measuring one suite on one model costs about 3 cases at that rate, and the ceiling left is about US$ 3.65 (grader cost not included; the grader is the Flash 1017 default of `run_evals.py`). The generator computes and prints these figures from the JSON so they cannot drift from it.

### Eval wiring

The `omnigent` profile: `argv` = `omnigent run {arm} --harness {agent_harness} --model {model} --no-session {extra} -p {prompt}`, arms `with: ["{agent}"]` (the generated bundle for the suite's `skill`) and `without: []` (the bare harness), `output: text`, and a `container` block with the same argv and no permission token. `run_evals.py` gains `--agent-harness` (default `opencode`) and one `arm_values` helper used by both the dry run and `run_arm`, adding `agent` (absolute bundle path from the suite's `skill`, refused when the bundle is missing) and `agent_harness`. Other profiles are unchanged.

### Binding contracts

`docs/standards/architecture/surface-translation.md` (OpenCode distribution section is the model), `docs/standards/agents/ephemeral-writes.md` (nothing outside `.quenching/`), the generated tree is never hand-edited and nothing flows back.

## Alternatives Considered

- **Only the 7 agents, not the commands.** Rejected: the problem is that commands must run on the platform; agents alone leave the 61 commands unreachable.
- **Hand-written bundles.** Rejected: 68 bundles drift from the source on every edit; the Codex and OpenCode ports already chose generation with a byte-compare gate.
- **Server-wide Omnigent policy instead of per-bundle policy.** Rejected for this spec: it belongs to forge's policy pack (S16) and cannot know a command's source grants; a per-bundle policy travels with the bundle wherever it is hosted.
- **A Python policy function with a real shell parser (`omnigent.policies.builtins._shell`).** Rejected: an uploaded bundle cannot ship server-side Python, and `_shell` is private API of an alpha; revisit with S16.
- **Forking the payload by pointing at the OpenCode tree.** Rejected: it ties the Omnigent install to another harness's directory; a 5 MB generated copy is the price of an independent tree, as for Codex.
- **Pinning a model per bundle from the source tier.** Rejected: H1 shows tier does not predict quality (Flash passes where Sonnet fails), and the table, not the bundle, is where model choice is evidenced.

## Open Decisions

- **Non-`cq` scoped Bash grants** (`python3`, `py`, `rm`, `mkdir`, `find`, `git ls-files`, `gh pr view`, …) are denied in v1. The human decides, per command and from the PERMISSIONS.md list plus the Omnigent-hosted eval results, whether to express them as allowed prefixes; each is a source grant, so allowing it exceeds nothing, but the human's 2026-10-25 instruction named only `cq` verbs.
- **Command `allowed-tools` read as a restriction** (stricter than Claude Code's prompt). Decided by the first Omnigent-hosted eval: a command that cannot finish because of a denial is the evidence to move it to ASK in forge's policy, not here.
- **Heredocs and redirects under scoped `cq`** are denied; whether Omnigent gains a parser the policy can call (S16) or the commands change their idiom is decided after the eval shows how many commands hit it.
- **Payload root `~/.omnigent/quenching`** is a default; forge S13 decides the path inside the image and the README names `QUENCHING_OMNIGENT_ROOT` for it.
- **Omnigent-hosted compatibility cells.** Human step, not executed here: run `python3 scripts/run_evals.py --harness omnigent --agent-harness opencode --model <m> --image <img> --run-id <id> --suite <suite>` per suite and model, judged by the fixed Flash grader, at the per-case cost recorded in `MODEL-COMPAT.md`, within the ~US$ 3.65 ceiling; update `omnigent-model-compat.json` and regenerate.

## Risks

- The permission regex lets through something a shell parses differently (quoting, `cq` aliasing via `PATH`). Mitigation: the allowed argument class excludes every metacharacter, the whole command must match, and the test evaluates the real policy with `celpy` on adversarial commands (`cq x; rm -rf /`, `cq x $(y)`, newline, backtick, `cq xx`). ACCEPTED — residual: the harness's own sandbox (`os_env.sandbox`, deployer's) is the boundary, not the policy.
- Native tool names change in Omnigent after `v0.19.1` and a denial silently stops matching. Mitigation: the pin is a constant checked against the forge tag, the policy lists both `sys_os_*` and native names, and the dry-run/eval step is what reveals a new name; a version bump regenerates and re-reviews the table.
- Commands become unusable under Omnigent because of the stricter reading. Mitigation: `PERMISSIONS.md` lists every denial per bundle; the cost is a failed eval, not a silent widening. ACCEPTED — safer failure.
- H1 cells read as evidence about Omnigent. Mitigation: the table header and the standard say the cells were measured on OpenCode directly.
- The 5 MB duplicated payload bloats review. Mitigation: it is generated and excluded from lint and citation checks; the drift check keeps it exact.
