## Overview

`cq specs task --check` grava por padrão um `subject:` pensado para ancorar o commit que implementa
a task (ver `## Proposal`). Quando a task declara `files:` vazio — um trabalho manual ou apenas de
verificação, sem diff esperado — nenhum commit chega a ser tentado, e o `subject:` gravado nunca
resolve via `git log --grep`. Este spec ensina o procedimento de execução (`execution.md` /
`execute.md` — não a ferramenta `cq`) a reconhecer esse caso e pular a tentativa de `--subject`/commit
inteira para ele, generalizando a regra que já existe hoje para repositórios sem git (`## Design`). O
que fica de fora — reescrever o registro já arquivado da spec #902, ou construir um checker de
validação simétrico a `sp-bad-merge` — está detalhado em `## Out of Scope`. Os três arquivos tocados
(`execution.md`, `execute.md` e o standard correspondente) e o check que prova a consistência entre
eles estão em `## Impact`/`## Tasks`/`## Validation`.
## Problem

`cq specs task --check` sempre grava `subject:` no formato `plan/<slug>: <task-id> <task title>` mesmo
quando a task não tem `files:` (ex.: `files: []`, `verify:` manual — só roda um script e confirma o
resultado, sem produzir diff nenhum para commitar). Não há commit correspondente para esse subject
resolver, e re-rodar `--check` sem `--subject` não limpa o valor já gravado.

Achado durante `/quenching:specs:conclude` da spec `revisar-politica-de-assets-checks` (issue #902),
task 5.1 ("Rodar citation-check.sh uma vez, à mão, da raiz do repo") — `files: []`, `verify: bash
plugins/quenching/assets/checks/citation-check.sh`. A tarefa foi ticada corretamente e a verificação
em si é genuína (o script rodou limpo, confirmado duas vezes), mas o `subject:` gravado nunca resolve
via `git log --grep`, o que `plan-git-record.md`/`cq specs validate` poderiam achar suspeito no futuro
(`sp-bad-merge`-like, embora hoje não haja checker específico para o caso task-level).

## Proposal

- Uma task sem `files:` declarado (linha ausente ou `files: []`) nunca mais recebe um `subject:`
  gravado por `cq specs task --check` durante a execução — a task ainda é ticada normalmente
  (`cq specs task --check <id> --spec "<slug>"`, sem `--subject`), mas a cadeia de `git add`/`git
  commit` e a decisão de `--subject` deixam de ser tentadas para ela.
- `execution.md` §The commit passa a descrever esse caso lado a lado com o caso já existente "sem
  git no repo" — as duas frases compartilham a mesma regra: nenhum commit existe → nenhum
  `subject:` é inventado.
- A cadeia literal de exemplo em `execute.md` step 5e (5d–5e) reflete a mesma condição, de forma
  que as duas cópias do procedimento concordem.
- O `subject:` já gravado na spec arquivada `revisar-politica-de-assets-checks` (issue #902, task
  5.1) permanece como está — nada é reescrito retroativamente.

## Out of Scope

- **Corrigir/limpar o `subject:` já gravado na spec arquivada #902** (task 5.1), ou em qualquer
  outra spec já arquivada. Specs arquivadas nunca são reescritas — precedente já estabelecido para
  o mesmo par `subject:`/`commit:` em `plan-git-record.md`/`git.md` §The subject is the anchor:
  "Neither form is backfilled... rewriting an archived spec to 'modernise' it would falsify when
  the record was made."
- **Qualquer mudança na CLI `cq specs task --check`** — um novo flag, uma recusa, uma limpeza
  automática. A correção fica inteiramente na decisão do procedimento chamador sobre QUANDO passar
  `--subject`; a ferramenta continua gravando o que recebe e nunca inventando ou resolvendo nada
  por conta própria — o mesmo contrato que `task.py` já documenta para `--commit`/`--subject`.
- **Um checker de validação no nível de task, simétrico a `sp-bad-merge`** (ex.:
  `sp-task-bad-subject`, checando se o `subject:` gravado resolve via `git log --grep`). É um
  follow-up real — o próprio `## Problem` já nomeia esse risco futuro — mas é uma superfície de
  validação nova, com perguntas de design próprias (se `cmd_validate` hoje tem acesso a git, o que
  isso significa para um backend cujo checkout local pode não ter o histórico que um subject
  ancora). Registrado em `## Discoveries`, não construído aqui.
- **Qualquer distinção por backend** (`files` vs. `github`/`azure`). A correção proposta é
  backend-agnóstica: olha somente se a task declara `files:`, nunca qual backend está configurado
  — ver `## Design`.

## Design

**Decisão: pular a cadeia de subject/commit quando a task declara `files:` vazio, reaproveitando o
sinal de intenção que a task já declara — sem inventar um sinal novo.**

- **Gatilho.** `t["files"]` vazio — linha `files:` ausente ou escrita como `files: []`. As duas
  formas já são indistinguíveis no parser hoje (`quenching/specs/parse/tasks.py`: `files` nasce
  `[]` e só é preenchida quando uma linha `files:` casa), então nenhuma mudança de gramática e
  nenhuma mudança de CLI são necessárias para detectar o caso.
- **Por que esse sinal é confiável.** `files:` já é documentado como uma declaração deliberada, não
  uma conveniência opcional — `specs-develop/artifacts.md` §Execution metadata: "`files:` is the
  exception to 'where it earns its place.' It is not a convenience... Decide that deliberately or
  declare the paths." Quem escreveu a task com `files:` vazio já declarou, na gramática existente,
  "esta task não produz um diff delegável".
- **O que muda na cadeia** (`specs-execute/execution.md` §The commit, espelhado em
  `specs-execute/execute.md` step 5e): quando `files:` da task está vazio, rodar apenas `<o
  verify: da task> && cq specs task --check <id> --spec "<slug>"` — sem `--subject`, sem `git add`,
  sem `git commit`. É a mesma forma que o procedimento já usa para "sem git no repo": "tick the box
  without `--subject` and say so once in the report, rather than inventing a placeholder." Esta
  correção generaliza o princípio desse ramo já existente (nenhum commit existe → nenhum subject é
  inventado) para um segundo caso onde a mesma coisa é verdade — o mesmo padrão que
  `plan-git-record.md` já usa no nível de merge, com a **Anchorless strategy** (`fast-forward`,
  `rebase`): nenhum commit de merge existe, então `subject:` grava um none explícito em vez de um
  ponteiro fabricado. Esta task é o análogo no nível de task.
- **Por que não condicionar (também) por backend.** Sob o backend `files`, ticar uma task sempre
  toca o arquivo local da spec, então mesmo uma task `files: []` ainda tem algo para staged e seu
  commit (e subject) resolveria normalmente — o defeito relatado só é visível sob um backend
  externo (`github`, o backend deste próprio repositório), onde o tick é só-API e uma task `files:
  []` realmente não produz diff local nenhum. Mas condicionar por backend adiciona um segundo eixo
  de raciocínio a um conserto de complexidade `low`, e a regra baseada só em `files:` é segura nos
  dois casos: sob `files` ela só adia o commit só-do-checkbox (uma latência benigna — o tick pega
  carona no commit da próxima task ou no squash da seção), e sob um backend externo ela remove o
  subject pendurado por completo. Uma regra só, mesmo formato de resultado, sem o procedimento
  precisar saber qual backend está configurado.
- **Por que não fazer a CLI recusar em vez disso.** Ver `## Alternatives Considered`.

## Alternatives Considered

- **Checker de validação no nível de task** (ex.: `sp-task-bad-subject`), flagando um `subject:`
  gravado cujo substring nunca resolve via `git log --grep`. Rejeitado para este spec: trata o
  sintoma (um campo obsoleto, descoberto depois do fato) em vez da causa (o campo nunca deveria ter
  sido gravado), exige que `validate` ganhe acesso a git que talvez não tenha hoje, e é uma
  superfície grande o bastante para ter spec própria — pertence a quem quiser detecção de deriva no
  nível de task, não a um conserto de escrita de complexidade `low`. Registrado como descoberta em
  vez de promovido aqui.
- **Dar a `cq specs task --check` um modo de recusa/`--no-subject`** condicionado ao `files:` da
  própria task (fazendo a CLI impor a regra em vez de confiar no chamador). Rejeitado: duplica uma
  decisão que o procedimento chamador já precisa tomar (ele já lê os metadados da task para montar
  a cadeia), e vai contra a filosofia que a própria ferramenta já declara — gravar o que recebe,
  nunca inventar ou resolver por conta própria.
- **Fazer o backfill do `subject:` já pendurado** na spec arquivada #902 (task 5.1) como parte deste
  conserto. Rejeitado: o precedente do próprio par `subject:`/`commit:` em specs arquivadas é
  explícito que um registro arquivado nunca é reescrito para "modernizá-lo" — fazer isso
  representaria erradamente quando o registro foi de fato feito.

## Risks

- **`files:` vazio nem sempre significa "sem diff" em specs já escritas.** Se alguma task existente
  declarou `files: []` por descuido em vez de intenção, ela deixa de ganhar `subject:`/commit
  automático depois deste conserto. ACCEPTED — `files:` já é documentado como uma declaração
  deliberada (`specs-develop/artifacts.md` §Execution metadata: "Decide that deliberately or
  declare the paths; do not leave it to whether the line felt worth typing"), então este conserto
  só acrescenta mais uma consequência a um sinal que já bloqueia delegação e `[P]` hoje — não é um
  risco novo introduzido por este spec.
- **As duas cópias do procedimento (`execution.md` e `execute.md`) driftarem** — uma editada, a
  outra não, ou com redação diferente. Mitigado pelo gate da seção (`verification: per-section`):
  a verify da task 1.3 casa a mesma frase-âncora nos três arquivos.
- **Os anchors `file:line`/`source:` de `/.knowledge/standards/workflows/task-execution.md`
  ficarem desatualizados** se a edição de `execution.md` mudar as linhas que o standard cita.
  Mitigado por 1.3 exigir a atualização do próprio standard no mesmo commit; o gate de citação já
  existente no repositório fica fora deste `## Validation`/`verify:` por instrução do CLAUDE.md
  deste repositório.
- **Instâncias já gravadas (ex.: issue #902, task 5.1) continuam com `subject:` pendurado.**
  ACCEPTED e documentado em `## Out of Scope` — nenhuma spec arquivada é reescrita.

## Handoff

Construída em 2026-08-17 no branch `holetz/batch-execute` (base `develop`), 5ª de uma fila de 9
specs conduzida por `/quenching:specs:execute-queue` — o branch é compartilhado com as outras specs
da fila e **não** foi mergeado. 3/3 tasks, seção 1 fechada e squashada.

O que um executor novo não deriva do `git log`:

- **A correção é inteiramente prosa.** Nenhum Python de `plugins/quenching/assets/bin/quenching/**`
  mudou, e a CLI `cq specs task --check` continua gravando o que recebe — como o `## Out of Scope`
  exige.
- **As linhas `verify:` das três tasks não rodam como escritas.** Elas põem o literal com crases
  dentro de aspas duplas, e o bash faz substituição de comando ali: o padrão vira "no  declared" e
  a linha é um vermelho impossível de fechar, qualquer que seja o estado da árvore. O gate foi
  rodado com o mesmo padrão em **aspas simples**, que é a mesma asserção, e fechou verde nos três
  arquivos. Registrado em `## Discoveries`.
- **Há um commit extra na seção 1**, `1 corrige o source: de task-execution.md truncado pelo # do
  YAML`: o `source:` acrescentado pela task 1.3 citava a issue com `#`, e um `#` num escalar YAML

- **O `subject:` órfão da spec arquivada `revisar-politica-de-assets-checks` (issue 902, task 5.1)
  segue intocado**, como o `## Out of Scope` manda. O checker `sp-task-bad-subject` que o pegaria

## Discoveries

- Follow-up fora de escopo: um checker de validate (ex.: sp-task-bad-subject) simétrico a sp-bad-merge, que flagasse um subject: de task cujo substring nunca resolve via git log --grep — trataria a deriva já existente em vez de só impedir novas; exige investigar se cmd_validate hoje tem acesso a git.
- As verify: das tasks 1.1/1.2/1.3 escrevem o literal com crases dentro de aspas duplas ("no `files:` declared") — bash faz substituicao de comando, o padrao vira "no  declared" e a linha e um vermelho impossivel de fechar; um grep de prosa cujo padrao contem crases precisa de aspas simples no momento da autoria
- O texto de task ecoado por cq specs task --check e por status.promote.openTasks e truncado na primeira linha fisica quando a task quebra em varias linhas — o id resolve certo, mas o titulo exibido fica cortado no meio da frase
- Um '#' dentro de um escalar YAML nao-aspado do frontmatter (ex.: 'issue #902' no source:) inicia um comentario e trunca silenciosamente o resto da linha — cq knowledge validate pega como okf-frontmatter-unparsed, mas so depois do commit; citar numero de issue no frontmatter sem o '#'

## Outcome

Entregue. O procedimento de execução passou a reconhecer a task sem `files:`, nos três lugares que o
declaram — a reference, o corpo do comando e o standard — de modo que `cq specs task --check` não
grave mais um `subject:` que aponta para um commit que ninguém fez.

O `verify:` da seção era um vermelho impossível como escrito: o literal com crases dentro de aspas
duplas faz o bash substituir comando e o padrão degrada. Rodado com aspas simples, mesma asserção com
o quoting correto, exit 0. Reportado, nunca substituído em silêncio — e é uma das três instâncias que
o standard `unanswerable-verify-lines.md` desta mesma fila registra.

Revisada, destilada, pronta para merge.
