## Problem

After the delivery contract exists, the plugin still lacks a `cq delivery` route, command bodies, Codex translation and goldens for converging a target pipeline. The implementation must use the shared mold and preserve the explicit boundaries with toolchain declarations, proof's CI gate evidence, ops deployment entries and the security pillar's read-only audit.

## Proposal

- Add the `cq delivery` route with probe, inventory, bands and structured reporting for a target pipeline.
- Add align and status command bodies that separate not-applicable, conformant, mechanical, structural and judgement results.
- Add tests and goldens for workflow triggers, job reachability, setup provenance, runtime agreement and release reachability.
- Translate the route into the Codex mirror and prove it against a target shape beyond the plugin's own workflow.

## Out of Scope

- Changing the delivery architecture contract or finding vocabulary belongs to C3.
- Selecting a CI provider, environment or promotion policy is a judgement result and is never auto-repaired.
- Reporting test outcomes or becoming the proof gate belongs to `proof`; delivery reports the pipeline that makes those outcomes reachable.
- Managing operational deploy commands or the plugin's own release path belongs to `ops` and the existing release surface.

## Design

The route probes the provider-equivalent workflow tree before inventory. It inventories triggers, jobs, stage dependencies, checkout/setup provenance, runtime declarations and release reachability, then classifies each finding through the C3 bands. It returns JSON as the stable interface; align and status render the same result without inventing another source.

Delivery is read-mostly. A structural finding can identify a missing or unreachable artifact, but changing a workflow or release path remains an execution decision because provider syntax and deployment intent are not universally inferable.

## Alternatives Considered

- **Use one generic `cq pipeline` command.** Rejected because the declared axis name and front contract are `delivery`, and generic pipeline wording obscures release reachability.
- **Run delivery only as a shell lint.** Rejected because the front needs structured applicability, inventory and cross-front boundaries.
- **Repair workflows automatically.** Rejected because provider syntax and promotion intent can make a seemingly mechanical change unsafe.
- **Ship without a second-target probe.** Rejected because one GitHub repository cannot prove the front's provider-equivalent boundary.

## Open Decisions

- Whether provider adapters are needed in the first implementation is decided by the second target's workflow shape; unsupported syntax must report not measurable rather than green.
- Whether `status` and `doctor` share an inventory call is decided by the front-mold route contract, while their outputs remain semantically distinct.

## Risks

- **The route duplicates proof's CI findings.** Mitigation: delivery owns reachability and pipeline shape; proof owns evidence produced by running it.
- **An unsupported provider is mistaken for no pipeline.** Mitigation: return an explicit not-measured result and preserve the target's judgement path.
- **A workflow edit leaks into security or ops scope.** Mitigation: keep C3 boundaries in the implementation and test the arbiter/read-only rules.

## Handoff

Execution builds the delivery route after C3 and B1+B2 are available, then proves the route on a non-identical target. It must return an honest not-measured result for unsupported provider shapes and must not auto-edit a workflow.
