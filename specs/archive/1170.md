## Problem

A memória do projeto registra o incidente: com vários `cq specs` em paralelo contra o GitHub, a
leitura devolve **front vazio com `ok: true`, `count: 0`, exit 0**. A guarda que existe hoje é parcial:

- GitHub: `empty_listing_refusal` só recusa quando `open_issues > 0`
  (`specs/backends/github.py:287-290`); a contagem vem de `issues.totalCount`, só das abertas, com
  cache de 300 s (`GH_CACHE_TTL_S`, 40; leitura 417-437). Com `rows == 0` e paginação não vazia, ou
  na listagem lean, só sai um aviso em stderr (626-627, 691-694). A guarda passa com `any(page)`, então
  não pega truncamento parcial.
- Azure: nenhuma guarda. `found = self._az(... expect="array") or []` e depois `_show_many` sem
  comparar ids pedidos com itens devolvidos (`specs/backends/azure.py:738-746`, 802; `_guard_wiql`,
  718-731, só cobre o teto). [unverified: não reproduzido contra um Azure real]

Consequência: `status`, `next` e `parallel` concluem "nada a fazer" sobre um front que existe. Uma
escrita que resolve o slug recusa com `sp-unknown-slug`, acusando a spec e não o backend.

## Proposal

- A full GitHub listing whose open, non-PR issues number fewer than the repository's open-issue count refuses with `sp-gh-short-listing` (exit 2), instead of returning a partial front as `ok: true`; the refusal drops the cached count so the next run re-reads it.
- An Azure listing whose batch read returns fewer work items than the WIQL query named refuses with `sp-az-batch-short` (exit 2), naming the missing ids.
- Both refusals carry a remedy line and are covered by tests that fail before the change.

## Out of Scope

- The GitHub lean listing (`_lean_rows`): it searches spec issues only, so no independent count exists to compare; it keeps its current guard. Ruled out: inventing a second count would be a guess.
- Retry of the failed read (spec 1166 owns HTTP 500 retry).
- Reproducing the Azure fault against a real organisation: the guard is a pure id comparison, proved by a stubbed batch.

## Design

- Decision: compare against the count of ALL open issues (`issues.totalCount`, PRs excluded), not specs. The REST listing returns every issue, so open non-PR issues seen must be at least that count; a lower number proves truncation, where "zero specs" never could. Rejected: refusing on zero specs (a repository adopting the backend legitimately has none).
- Decision: the count is cached up to 300 s, so a concurrent close can make the listing legitimately shorter. The refusal therefore deletes the cache entry (via an overwrite with the unknown count) and says to re-run; at most one false refusal per window, never a silent wrong front. Assumption: stale-high is rarer than a silent empty front, which is the incident.
- Decision: Azure compares requested ids with the returned `id`s; a short batch refuses. Assumption (unverified): items deleted between the query and the batch are rare enough to accept a refusal.
- Rule: a listing guard refuses on proof of truncation, and warns on mere suspicion.

## Alternatives Considered

- Retrying the read inside the backend until counts agree: hides the fault and belongs to the transport (1166).
- Failing on every empty front: breaks repositories with no specs yet.

## Open Decisions

- Why now / what makes this not worth doing: not answered by `## Problem`; decided by the human at review — default is to build, as the incident is recorded in the project memory.

## Risks

- A stale cached count yields one false refusal. ACCEPTED — the remedy is a re-run and the cache entry is cleared.
- Existing tests that feed a short listing against a positive count may fail; they are updated to a consistent fixture.
