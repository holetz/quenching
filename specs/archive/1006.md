## Problem

O plugin estampa um site layer Zensical sobre `/.knowledge/documentation/` de qualquer repositório-alvo, mas este repositório não instala o seu: não há `zensical.toml` na raiz e ninguém constrói o próprio home. O custo de não dogfoodar é que toda regressão do layer só aparece num consumidor — a spec 1003 descobriu que o payload estampado falhava em `--strict` por seis links absolutos, e descobriu porque construiu à mão, não porque algum gate deste repo reclamou.

## Proposal

- Reconciliar a premissa obsoleta da captura: o repositório já possui zensical.toml, pyproject.toml, uv.lock e a home documentation.
- Adotar dogfooding como build local reproduzível mais gate de CI em pull requests e na branch principal, sem publicar em GitHub Pages.
- Decompor a execução em specs filhas para: tornar o build observável, completar a cobertura dos verificadores, restaurar a paridade do payload Codex e instalar o gate CI.
- Usar o site gerado como evidência de produto, não apenas a validação estática das fontes.

## Out of Scope

- Publicação em GitHub Pages, Azure ou outro destino remoto; não há destino aprovado nem necessidade demonstrada.
- Corrigir o runtime upstream do Zensical.
- Reescrever a arquitetura do bundle OKF ou migrar o backend de specs.

## Impact

### Product code this spec expects to touch

- zensical.toml, pyproject.toml e uv.lock — configuração e resolução já existentes que o dogfooding consumirá.
- README.md — contrato de desenvolvimento local.
- .github/workflows/docs.yml — gate raiz a ser criado.
- plugins/quenching/assets/zensical/ — payload que deve permanecer distribuível.
- plugins/quenching-codex/ — tradução gerada que deve resolver os caminhos documentados.
- plugins/quenching/assets/checks/ — verificadores e fixtures exercidos pelo gate.

- O build dogfooded gera HTML real, sitemap parseável e passa os checkers de estrutura, glossário, capabilities e catálogo.

## Design

A decisão é deliberadamente local + CI. A configuração raiz representa este repositório; o payload em plugins/quenching/assets/zensical continua sendo o contrato para consumidores. O gate usa um runner único para evitar que README, CI e subagentes exerçam comandos diferentes.

O mapa de dependências é:

- 1006 decisão de dogfooding
  - 1021 build observável e bloqueante
    - 1024 workflow raiz consome o runner e os gates
  - 1022 checker, fixtures e cobertura de glossário/capability
    - 1024 workflow executa os self-tests
  - 1023 paridade do payload e tradução Codex
    - 1024 workflow exige sync verde
  - 1025 verificadores de catálogo e capability
    - 1024 workflow executa os self-tests

As specs filhas são independentes quanto aos arquivos principais; o workflow depende dos runners e verificadores, portanto deve ser concluído depois deles. A construção do site segue a mitigação local documentada para o watcher do Zensical: polling explícito e guarda contra falso sucesso.

## Alternatives Considered

- Não dogfoodar e confiar apenas em consumidores — rejeitado porque a regressão de links absolutos só foi descoberta em um consumidor.
- Publicar imediatamente o site — rejeitado por falta de destino aprovado e porque publicação não é necessária para testar o layer.
- Fazer uma única spec monolítica — rejeitado porque mistura runtime externo, checkers, geração Codex e CI com ciclos de verificação diferentes.

## Open Decisions

- none — esta decomposição fixa o dogfooding local + CI; publicação remota fica para uma futura decisão independente.

## Risks

- A versão atual do Zensical pode falhar por corrida de watcher — mitigado na spec 1021 com polling e guarda de saída.
- O espelho Codex pode ocultar payload ausente — mitigado pela spec 1023 e pelo gate de sync.
- O gate pode ficar mais caro — aceito porque o objetivo é capturar regressões no próprio produtor; uma otimização futura precisa preservar todos os gates.
- A captura original afirmava que não havia configuração raiz — corrigido aqui como descoberta, sem preservar essa premissa falsa.
