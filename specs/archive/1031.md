## Problem

The Zensical documentation build treats `site/` as generated output and `.quenching/` as generated working state, and its current guidance checks both paths for ignore and tracking problems. The generated, bounded `site-source/` tree is also not an editable source, but the build contract does not inspect its ignore or tracking state, so a tracked generated input can pass without a dedicated finding even though `.gitignore` already declares `site-source/` as ignored.

## Proposal

- The authoritative documentation-build command explicitly checks `site/`, `.quenching/`, and `site-source/` for ignore and tracking state during its site-layer inventory.
- The findings table defines `site-source-tracked` for a missing ignore rule or an already-tracked generated `site-source/` tree, with an actionable ignore/removal disposition matching the existing generated-artifact findings.
- The Codex documentation-build skill is regenerated from the Claude command and carries the same contract without making the generated skill authoritative.
- A focused contract test fails when the source command loses the `site-source/` inventory or finding, and the translation check proves the Codex projection remains synchronized.

## Out of Scope

- Changing `.gitignore` in this repository; `site-source/` is already ignored and is evidence for the regression, not a missing fix here.
- Deleting or untracking an existing `site-source/` tree in a target repository; the build contract reports that remediation for the target owner.
- Changing `cq knowledge site-source` staging, its manifest, or the rendered `documentation-site-check.py`; those mechanisms answer content freshness and rendered-output integrity, not repository tracking policy.
- Changing the existing `site-artifacts-tracked` or `site-scratch-tracked` meanings, capability checks, or the work reserved by specs #1022 and #1025.

## Design

The build command remains the owner of the site-layer inventory because it already decides how generated output, scratch state, and the bounded Zensical input are handled before a build. Its inventory will name `.gitignore` and `git ls-files` over `site`, `.quenching`, and `site-source` together, so the check cannot silently omit the generated input. The new `site-source-tracked` row will use the established combined disposition: fix a missing ignore rule, and report an already-tracked path for the target owner to remove. It will not claim that an ignored path is tracked, and it will not mutate the target during the inventory.

The new finding is deliberately a contract-level finding rather than a change to `site_source.py`. That executable checker validates staging ownership, manifest freshness, and bounded content; adding Git queries there would mix source projection with repository policy and would also require a repository-root contract it does not currently have. The rendered checker likewise remains scoped to built `site/` output. The source command stays authoritative; the Codex skill is updated only through the existing deterministic translator and is proved with its `--check` mode.

## Alternatives Considered

- Extend only `.gitignore` — rejected because the rule already exists and cannot report a target that is already tracked.
- Reuse `site-artifacts-tracked` for `site-source/` — rejected because the input tree has a distinct lifecycle and needs a path-specific finding that tells the operator which generated boundary was violated.
- Add Git inspection to `cq knowledge site-source` or `documentation-site-check.py` — rejected because one owns source projection and the other owns rendered output; neither owns the build inventory or has the necessary repository-policy scope.
- Rely on prose in the validation reference without changing the command contract — rejected because the missing behavior is precisely the absence of an independently exercised finding.

## Open Decisions

- none — the path-specific finding name, owner, disposition, and source-to-Codex generation route are fixed by the existing `site-*` contract and the current repository layout.

## Risks

- A future caller may run the inventory outside the repository root, making `git ls-files` inspect the wrong tree — mitigated by retaining the build command's repository-root inventory contract and testing the exact command body alongside its existing path checks.
- The generated Codex skill may drift after a source edit — mitigated by regenerating it with the existing translator and requiring `components translate --check --json` to be green.
- An operator may interpret the finding as permission to delete generated input automatically — mitigated by wording the disposition as ignore fix plus human-reported removal, with no mutation in the inventory step.
- A later maintainer may add the same path to a content checker — mitigated by the design map and explicit out-of-scope boundary keeping Git tracking in the build contract.
