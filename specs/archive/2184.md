## Problem

The Specs panel shows what a spec is — stage, priority, progress, runner — and never where it sits
in the dependency graph. The fact is already in the store: the `dependsOn` key, `cq specs depends`
for one spec, `cq specs schedule` for dates, slip and the critical path, and the portal's Gantt
draws all of it. A reader inside the panel who wants to know whether a spec can run, or what its
delivery unblocks, leaves the session for a browser or for a second `cq` call.

Two gaps make a naive answer worse than it looks. The graph has one direction — `dependsOn`, "what I
wait for" — and nothing answers "who waits for me" without reading the whole store. And the
selection: `cq specs schedule` schedules the open specs that declare an edge plus their transitive
dependencies, so a dependent already archived (2136 waiting for 2133, in this repository) is in no
payload at all — a consumer inverting that graph would show a short answer without knowing it.

## Proposal

Two pieces, neither of them a new store:

1. **`cq specs schedule --all`** widens the selection to every spec in the store, archived and
   edge-less included — the read a consumer needs once it asks both questions of the graph. It
   writes nothing, keeps exit 1 with a payload on a cycle, and refuses `--all` together with
   `--spec` (`sp-conflicting-selection`, exit 2). In this repository it is one bulk read: ~0.9 s
   and 320 KB over 889 specs.
2. **A `Dependências` tab in the panel's detail**, beside the document's own tabs: *acima*, the
   specs this one's `dependsOn` names, and *abaixo*, the specs that name it — each row clickable to
   open that spec, carrying the archive state, the critical-path flag, the slip and the date window
   the schedule derives.

One read serves every spec: the graph is cached 30 s per checkout and shared in flight, so the tab
costs one `cq` process per window and not one per opening. A `cq` older than `--all` falls back to
the default schedule — the view degrades, it does not fail — and a cycle shows the alert with the
path, as the Gantt does, instead of an empty list.

## Out of Scope

- Drawing a Gantt in the panel. The portal owns that page (`docs/standards/architecture/specs-portal.md`); the panel stays a reader.
- The transitive closure as rows. The tab lists direct edges, and walking a chain is one click per hop.
- Task-level edges. `dependsOn` is a spec-level edge (`docs/standards/workflows/spec-dependencies.md`); `[P]` groups answer a different question.
- Writing `dependsOn` from the panel. `cq specs depends` stays the only writer.
- Tracker-native dependency links: the key is carried in the document and never projected.
- Any change to the Gantt, to `validate`'s four dependency findings or to the schedule derivation itself.

## Design

- **The widening.** `schedule(infos, ids)` already takes a selection; `--all` passes every id in the
  store instead of the default "open specs with an edge plus their closure". Dates, slip, critical
  flag and cycle detection are the same derivation, unchanged.
- **The inverse.** Upstream is the node's own `dependsOn`, in declaration order; downstream is every
  node whose `dependsOn` names it, by id. An id the store does not hold (`sp-dep-missing`) is
  dropped, never invented.
- **The payload.** `deps: {up, down, cycle}` on the `detail` RPC, with the neighbours carrying `id`,
  `title`, `phase`, `critical`, `slip`, `start` and `target`; `additionalProperties: false`, so a
  field added on the server without the schema fails loudly.
- **The read.** `cqJsonPartial` follows the exit code policy: `schedule` exits 1 on a cycle and still
  carries the payload, which is the datum the tab exists to show.
- **The tab.** It sits past the document's sections and renders only when there is an edge or a
  cycle; the Tasks list and the markdown of the current section are untouched.

## Alternatives Considered

- **A reverse flag on `cq specs depends`.** The panel would need a second call per spec and a join
  for titles and phases; the graph read answers both directions for the whole store at once, from a
  verb that already returns title, phase, dates and the critical path.
- **`dependsOn` on every `cq specs list` row.** A full list reads every document one by one — 10 s
  here against the schedule's sub-second bulk read — and the panel lists on every session.
- **Inverting the default schedule.** Silent gaps: an archived dependent is in no payload, and a
  view that cannot tell "nothing waits for this" from "I did not look" is a lie.
- **A lazy RPC for the tab.** Keeps `detail` at three reads but loses the counts in the tab label
  and adds a second loading state for a graph that is already cached and shared.

## Open Decisions

- none — both choices (a flag on `schedule`, the tab inside the document's tabs) follow from the
  constraints above and were settled at build.

## Risks

- **A `cq` older than `--all`.** The fallback shows the open graph, so an already-archived dependent
  may be missing until the target deploys again. Mitigation: the panel already offers
  Instalar/Atualizar, and the package README states the limit.
- **Cost grows with the store.** One bulk read per 30 s: ~0.9 s and 320 KB at 889 specs, inside the
  plugin's 15 s read and 8 MB output ceilings, but a store ten times larger presses both.
- **The 30 s cache is a snapshot.** A `dependsOn` written in the same window shows on the next read.
  The tab is a reader, never the authority: `cq specs validate` still owns the graph's errors.
- **New surface in a hand-written GUI with no unit tests.** Covered by `npm run bench` and the probe
  above rather than by a suite; a rendering regression is caught by a person opening the panel.

## Handoff

- **Built:** the three tasks below, in order; the last one refreshes the deployed surface and runs
  the whole gate.
- **Decisions taken at build:** `--all` on `schedule` rather than a reverse verb; the graph riding on
  the existing `detail` read instead of a second RPC; `cqJsonPartial` because a cycle exits 1 with
  the payload in hand.
- **Not done here:** the Gantt, task-level edges and any write path — all three are under Out of
