## Problem

The Specs panel and the quenching Settings page (`integrations/opencode-vitrine`) exist only for OpenCode Desktop, so a person who drives quenching from the Claude Desktop Code tab has the skills, agents, hooks and the `quenching` MCP server but no view of the specs the session touched, their dependencies, epics and configuration: reading a spec there means running `cq` by hand or calling MCP tools. Claude Desktop's mod surface (a hooks module that opens a pane through `$.ui.open` and draws it in `ui.render`, runs `cq specs …`/`cq config …` through `$.process.run`, sees `cq specs` calls through `tool.call` and re-reads the conversation through `$.session.messages`) can carry the same panel, and the mod must be installed separately from the skills: it never ships through `cq deploy` (targets that receive the skills by deploy keep doing so untouched) and has its own distribution.

Why now: the owner moved day-to-day quenching work to the Claude Desktop Code tab. It stops being worth it if OpenCode becomes the main harness again, or if the mod API churns enough to break the panel on every Claude release.

## Proposal

- A Claude Code plugin `quenching-vitrine` lives in `integrations/claude-vitrine/`, a hooks module in the shape of `integrations/claude-hud`, and is listed as the second entry of `.claude-plugin/marketplace.json`; it installs with `/plugin install quenching-vitrine@quenching`, separately from the skills, and `cq deploy` neither installs nor references it.
- A `/quenching-vitrine` slash command opens a pane that lists the specs the current session touched (cited in the conversation, a `cq specs …` Bash call, a `mcp__quenching__specs_*` tool call, the branch or commit the session is on), rebuilt from `$.session.messages` when the pane opens, so a reloaded mod keeps the list.
- Selecting a spec shows its whole document in tabs (Overview, Problem, Proposal, …) with the board signals in the header (stage, priority, complexity, age, task progress, runner state, block reason, assignee); a task or the whole spec is attached to the composer through `$.prompt.fill`.
- A Dependências tab shows who the spec waits for and who waits for it, the epic's "Specs deste épico" block and the member's "Parte de" block, read from `cq specs schedule --all` and `cq specs status --spec <id>` exactly as the OpenCode vitrine reads them.
- A Configuração tab inside the pane reads `cq config schema --values --json`, groups keys by task category with the layer badge and description, and writes only through `cq config set|unset --layer project|local`, with Restore default and structured catalogs read-only.
- The plugin joins the version lockstep (marketplace entry, `plugin.json`, `quenching/assets/modules.json` with `marketplace: true`), and the repository gate validates and tests it like the HUD.

## Out of Scope

- Installing quenching into a project from the mod: the OpenCode vitrine's `cq deploy --harness opencode` action (`src/quenching.ts:115-118`) is not ported; skills keep arriving by `cq deploy` (owner decision D6, 2026-11-20).
- A shared core between the OpenCode and Claude vitrines: a mod loads only files inside its own folder and the copy step was retired with ADR 0017, so the two keep separate code (D2).
- Folding the panel into `quenching-hud`: someone who wants only the band would get the panel too (D1).
- The Claude Desktop Chat tab: it has no hooks or panes; only the MCP server or uploaded skills could reach it.
- Any change to the OpenCode vitrine itself, its build, its bench or its `dist/`.
- Mutating spec verbs from the pane (record, task check, promote, push): the panel reads specs and writes configuration only, as the OpenCode vitrine does.

## Design

- **A separate marketplace plugin, in lockstep.** The panel reads JSON contracts the same release of `cq` defines (`test_config_schema.py`, `test_specs_deps_commands.py`, `test_specs_epics.py` pin them), so its version moves with `quenching/VERSION`; listing it in the marketplace is what puts it in the lockstep (`common/modules.py:98-127`, `specs/release.py:75-106`). Precedent: `quenching-hud`, the plugin ADR 0017 kept because it installs into no repository.
- **Own code, ported, not shared.** `cq.ts` (runner, `--json`, exit-code handling, concurrency cap), `specs.ts` (list/status/show/schedule/find reads, ledger) and `rpc.ts` (config schema/set/unset) are ported onto `$.process.run`; `gui.tsx` is redrawn with `$.ui.resolve(e)` elements (`Box`, `Text`, `Button`, `Select`, `Input`, `Markdown`, `Link`, `Svg`). A mod has no DOM or Node, and a module path outside the plugin folder is refused at load.
- **`cq` resolution.** Run `cq` from the session cwd (`$.session.cwd()`), as the HUD does (`integrations/claude-hud/hooks/register.tsx`), so the target's own `.agents/quenching/bin/cq` on PATH or a global `cq` answers; a missing `cq` renders an explicit empty state, never a crash.
- **Session ledger.** Kept in `$.state` (an `atom` declared in `types/index.d.ts`) and fed by `tool.call` on Bash commands matching `cq specs …` and on `mcp__quenching__specs_*` tools; rebuilt from `$.session.messages` when the pane opens, the counterpart of the OpenCode `absorbStorage` (`index.ts:17-23`).
- **Composer attach.** `$.prompt.fill({ text, mode: 'insert' })`, the counterpart of `composer.attach` (`gui.tsx:412-436`); `isFilled: false` under a dialog surfaces a toast.
- **Configuration as a tab.** Claude Desktop exposes no settings page to a mod and `userConfig` is a static field list, while the schema is dynamic; the tab writes only through `cq config set|unset`, so a value the registry refuses is refused here too and shown with `$.ui.toast`.
- **Opening.** A `/quenching-vitrine` command opens the pane; nothing opens it automatically.
- **Size limits.** A tree draws the first 100,000 characters of text; the detail renders the selected tab only.

## Alternatives Considered

- **Fold the panel into `quenching-hud`** — one install, but the band-only user carries the pane; rejected (D1 B).
- **Off-marketplace, unversioned, like the OpenCode vitrine** — nothing would flag a `cq` contract change against an installed panel; rejected (D1 C).
- **A shared core for both vitrines** — needs a copy step into both plugin folders, the mechanism ADR 0017 retired; rejected (D2 B).
- **An Artifact web page instead of a pane** — a page is a document to read or send, not a live view beside the session, and cannot see `tool.call` or fill the composer; rejected.
- **Panel only, configuration later** — the owner asked for parity in the first delivery; rejected (D3 B).

## Open Decisions

- none — D1–D6 answered by the owner on 2026-11-20; composer attach (`$.prompt.fill`) and the transcript re-read (`$.session.messages`) were verified in the mod API types of Claude Code 2.1.325

## Risks

- The mod API is young and may change between Claude releases → the README names the build the mod was tested on, the tests run against the engine through `claude plugin test`, and the gate validates on every run where `claude` exists. ACCEPTED — no stable-API promise exists yet.
- The gate skips the mod where `claude` is not on PATH (as for the HUD) → the release environment has `claude`; the skip is printed loudly.
- `cq` absent or older than the contract in the session's repository → an explicit empty state naming `cq --version`, never a broken pane.
- The audit treats `integrations/*/` hooks as loaded surface → keep hooks read-only except `cq config set|unset`, so the audit sees no grant beyond the HUD's plus config writes.
- A long spec document past 100,000 characters is cut → render only the selected tab.
- Two copies of the vitrine logic drift apart → each ports the same pinned JSON contracts, whose tests break both on a change. ACCEPTED (D2).

## Outcome

`integrations/claude-vitrine/` ships the Specs pane and the configuration view for Claude Desktop and the terminal as the `quenching-vitrine` mod, listed as the second marketplace plugin (`/plugin install quenching-vitrine@quenching`) and in the version lockstep (`plugin.json` at 7.8.0, `marketplace.json`, `quenching/assets/modules.json` with its deployed mirror). `/quenching-vitrine` opens the pane: the specs the session touched (conversation mentions, `cq specs ...` Bash calls, `mcp__quenching__specs_*` calls, the session's branch and commit), rebuilt from `$.session.messages` each time the pane opens; a spec's document in tabs with the board signals in the header; a Dependências tab (edges both ways, the epic's members, the member's "Part of"); task or whole-spec attach through `$.prompt.fill`; and a Configuração view reading `cq config schema --values --json` and writing only through `cq config set|unset --layer project|local`, with Restore default and read-only structured catalogues. The code is a port of the OpenCode vitrine onto `$.process.run` and `$.ui.resolve` elements, with its own tests (43, every UI test on `terminal` and `desktop`); the OpenCode vitrine is untouched and nothing is shared between them.

The gate validates and tests the mod beside the HUD (`quenching-vitrine plugin`, SKIPPED without `claude`), `test_deploy.py` asserts the two-plugin lockstep and that `cq deploy` installs nothing of either mod, and `docs/standards/architecture/source-layout.md` and `docs/project/layout.md` register the satellite.

Left out, as the spec said: the OpenCode `cq deploy --harness opencode` action, a shared core between the two vitrines, and any mutating spec verb in the pane. Not verified here: the visual rendering in Claude Desktop (the engine's `claude plugin test` mounts the pane on the terminal and desktop element tables, never the paint) and the manual install-and-use walk of the spec's Validation. No version bump: the lockstep moves at the release, as `versioning-release.md` says.

Engine constraints worth the next reader: a types contract must be import-free, so the shared shapes live in `types/index.d.ts`; `$` may be passed as an argument but never stored in an object; an atom must be declared with literal plugin and key in the file that updates it, so the pane's atoms and their writers live in `pane.tsx`.
