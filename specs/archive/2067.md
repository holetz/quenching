## Problem

Revisão do épico 2055 (2026-10-24), reproduzido pelo condutor. A 2054 neutralizou `core.fsmonitor`, `core.hooksPath` e `diff.external` (`scripts/run_evals.py:38`, `SAFE_GIT`). O comentário de `:37` diz que o snapshot "never runs its commands", mas um filtro de limpeza continua rodando. Num repositório com `git config filter.evil.clean 'printf FILTRO >&2; cat'`, `.gitattributes` com `f filter=evil` e `f` alterado, o comando `git -c core.fsmonitor=false -c core.hooksPath=/dev/null -c diff.external= status --porcelain` imprime `FILTRO` quatro vezes. O agente avaliado controla o `.git/config` e o `.gitattributes` do workspace, então consegue executar código pelo runner depois do kill por timeout, fora do perfil do harness. Também não foram neutralizados `filter.<driver>.process`/`smudge` e `gpg.program` sob `log.showSignature`. Fechar essas portas estreita a superfície.

## Proposal

- O snapshot do runner de evals nunca executa um filtro de limpeza, de smudge ou de processo declarado no `.git/config` do workspace avaliado, qualquer que seja o nome do driver.
- O snapshot nunca executa um `gpg.program` do workspace, mesmo com `log.showSignature` ligado no config do workspace.
- Um teste de regressão em `plugins/quenching/tests/test_run_evals.py` falha sem a correção e prova que um `filter.<driver>.clean` do workspace não roda durante `snapshot()`.

## Out of Scope

- Isolar o processo do agente avaliado: o snapshot roda depois dele e o contenimento do agente pertence ao perfil do harness. Fica fora porque o defeito é só o que o runner executa por conta própria.
- Trocar o snapshot por leitura sem `git status`: mudaria a evidência que o avaliador recebe.
- Neutralizar outras chaves hipotéticas além de `filter.*` e `gpg.program`: sem execução reproduzida, seria especulação.

## Impact

### Product code this spec expects to touch

- `scripts/run_evals.py` — `SAFE_GIT` e `snapshot()`

## Validation

- Num repositório com `filter.evil.clean 'printf FILTRO >&2; cat'` e `.gitattributes` com `f filter=evil`, `snapshot()` não imprime `FILTRO` nem toca o arquivo marca.
- `bash scripts/verify_repo.sh` sai 0.

## Design

- Regra durável: o `-c` vence o config do workspace, então cada comando que o git poderia executar a partir do config do agente é anulado por `-c` na linha do `git` do snapshot. O comentário de `SAFE_GIT` já declara essa regra.
- Os nomes de driver são dados do agente. `snapshot()` lê os nomes com `git config --name-only --list` (leitura, sem executar nada) e, para cada `filter.<driver>`, acrescenta `-c filter.<driver>.clean=`, `.smudge=`, `.process=` e `.required=false`. Valor vazio anula o comando; o driver sem comando passa o conteúdo sem filtro.
- `gpg.program=/bin/false` e `log.showSignature=false` entram em `SAFE_GIT`, valores fixos.
- Alternativa pesada por decisão: `GIT_ATTR_SOURCE` apontando para a árvore vazia dependeria de git recente; a enumeração funciona em qualquer versão.

### Mapa de dependências (2026-10-24)

- `scripts/run_evals.py` — único consumidor de `SAFE_GIT` (linha 263, `snapshot()`); nada fora dele importa a constante.
- `plugins/quenching/tests/test_run_evals.py` — `Containment` cobre o fsmonitor; o novo teste mora ao lado.
- Os espelhos `plugins/quenching-*/` não contêm `run_evals.py`: nada a regenerar.

## Alternatives Considered

- `GIT_ATTR_SOURCE` vazio: depende da versão do git e não cobre `filter` vindo do `.git/info/attributes`; rejeitado.
- Rodar o snapshot com `HOME`/config isolados: o config do repositório continua valendo; não resolve.

## Risks

- Um `-c filter.X.clean=` vazio pode alterar o status de um arquivo que dependia do filtro. ACCEPTED — o snapshot é evidência e precisa ser inerte; o desvio vai para o lado seguro.
- Nome de driver com caracteres estranhos quebrando o `-c`. Mitigação: cada nome vai como argumento único da lista, sem shell.
