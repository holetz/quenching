## Problem

An epic is a separate work-item type with its own grammar, its own verbs and a bidirectional link. A spec that is one task in size still has to become a full member spec, so it pays the whole thirteen-section flow; and the board separates the epic from the stories it coordinates. Composition should be a property of any spec, not a type.

## Proposal

- One `## Tasks` grammar: a task item carries a numeric id; a spec item carries `— spec: #<id>`; both may carry `after:`.
- A spec is composite iff it has at least one spec item. No `workItemType: epic` requirement, no `epic:` back-reference, no one-level or one-parent limits; a spec may join several composites and composites may nest.
- Item state is derived; the composite's progress counts tasks and members; the archive gate uses both.
- `cq specs link add|remove` is the verb; `cq specs epic add` remains an alias. `status --spec` and `next --spec` detect composition; `--epic` remains an alias.
- Presentation levels are `story`, `feature` and `epic`, derived recursively from the composition: a story has no spec members; a feature is one wave of stories and tasks; an epic is more than one wave, or contains a feature/epic. The Azure card keeps the project's standard work-item type; the level is card metadata (body and a `spec:feature`/`spec:epic` label), never an Azure type.
- Azure uses dependency links only (predecessor/successor), never parent-child; the composite's board column follows its members and its card lists the members.
## Out of Scope

- Moving the spec store to Azure Boards.
- Automatically changing the work-item type of an existing card when a spec grows from `story` to `feature`/`epic`; the first pass resolves the type at creation and warns on a later growth.
- GitHub card dependency links beyond the member list in the card body; a follow-up.
- Renaming the portal's `/api/epics` route and UI labels; the route keeps its name and changes its derivation in a follow-up.

## Design

### The grammar

```markdown
### 1. Foundations
- [ ] 1.1 Write the schema
- [ ] S1 Foundation — spec: #2138
### 2. Delivery
- [ ] S2 Migration — spec: #2139 — after: S1
- [ ] 2.1 Wire the job — after: S2
```

A task item is a checkbox whose text starts with a numeric id (`1.1`) and has no `— spec:`. A spec item is a checkbox whose text carries `— spec: #<id>` or `— spec: <owner>/<repo>#<id>`; its first token is the label (`S1`). `after:` is read on both. `### N.` headings are waves on both.

### The derivation

- A spec item's state is derived from the member document: `done`, `unmerged`, `dropped`, `blocked`, `waiting`, `ready`, `in-progress`, `not-ready`, `missing`, `unreadable`.
- A task item's state is `open`, `done`, `blocked`, or `waiting` when an `after:` item is not done.
- A composite's progress is the union: a task is done when checked, a spec item is done when its member is archived `done` and its PR is merged or unknown. The archive gate refuses `done` while any item is not done; `--force` keeps its meaning.
- A composite may contain another composite; the parent's member state is the child composite's document state. The archive gate makes the child finish before the parent, so one level of derivation is enough.
- `validate` adds a cross-spec cycle check over the graph of composites to their members, in addition to the existing `after:` cycle check inside one document.

### The commands

- `cq specs link add <composite> <spec> [--after S1,S2] [--group <wave>] [--label S9]` appends the item; idempotent when the member is already listed.
- `cq specs link remove <composite> <spec>` removes the item and refuses while another item waits `after` it.
- `cq specs epic add` is an alias for `link add`; `--move` is accepted as a no-op because a spec may belong to several composites.
- `cq specs status --spec <id>` includes the composition block when the spec has spec items; `--epic` forces the same view.
- `cq specs next --spec <id>` returns the first ready task, else the ready member set (`action: orchestrate`), else `promote`/`blocked`.
- `cq specs task` refuses an action on a spec item (`sp-link-derived-task`) and allows actions on the composite's ordinary tasks.

### The presentation levels

| Level | When | Board representation |
| --- | --- | --- |
| `story` | no spec items | the declared work-item type; no level label |
| `feature` | spec items, all in one wave (or no `###` wave) | the declared work-item type; `spec:feature` label and `Level: Feature` in the card body |
| `epic` | spec items in two or more waves | the declared work-item type; `spec:epic` label and `Level: Epic` in the card body |

- A wave is a `### N.` group that carries at least one spec item. A composite with no `###` group is one wave. An epic is more than one wave, and each wave is a feature.
- The level is a projection of the document's structure, never stored. It is recomputed on every card write.
- The Azure card type never changes with the level: `workItemType:` and the catalog's default resolve the project's standard type (`User Story`, `Technical Story`, …). The level is metadata for the human and for filters, not a work-item type.
- The `spec:feature`/`spec:epic` label reuses the already-reserved `spec:` prefix; `spec:story` is not written, so a leaf spec carries no extra label.

### Azure

- The composition is a dependency: the composite's card carries `System.LinkTypes.Dependency-Reverse` links to each member card, the same relation `dependsOn` already uses. `after:` stays local to the document and is not projected.
- No parent-child hierarchy is written: a spec may belong to several composites, and Azure discourages same-category parent-child links.
- The composite's board column follows its members: `executing` when any member is in progress, ready or unmerged, `reviewed`/`archived` as usual. The card body lists `Level: …`, `Specs n/N` and one line per member with id, title and state.
- The member card holds the project's standard work-item type; the composition never changes it.

### Compatibility

- Existing specs with `workItemType: epic` and `epic:` keys keep working: the links in `## Tasks` make them composites; the back-reference is ignored and `validate` reports it once as `sp-epic-key-deprecated` (warning).
- Existing `--epic`, `epic add` and `status --epic` invocations keep working as aliases.
- `sp-epic-*` findings are renamed to `sp-link-*`; the docs and skills quote the new codes.
## Alternatives Considered

- **Keep `workItemType: epic` and allow ordinary tasks inside it.** Does not remove the back-reference, the one-level rule or the one-parent limit, and a composite that is not an epic still needs a type.
- **Use parent-child hierarchy for composition.** Azure breaks backlog ordering on same-category parent-child links and allows one parent only; composition is many-to-many.
- **Make every task a spec.** Multiplies the thirteen-section flow by the number of tasks, which is the cost this change removes.
- **Store a `level:` field in the document.** It would go stale when the document changes; the level is a presentation projection.

## Open Decisions

- **The level label spelling.** `spec:feature`/`spec:epic` reuses the reserved `spec:` prefix and the existing read filter; a new `level:` prefix is clearer but costs a second reserved class. The first pass uses `spec:feature`/`spec:epic` and no label for a story.
- **The card title.** The level stays in the card body and the label; a `[Feature]`/`[Epic]` title prefix is not written unless the board proves it necessary.
## Risks

- **Parser regression.** `parse_tasks` feeds every backend and the card progress; the change is one detection helper and a split, covered by a fixture with mixed items.
- **Card type change.** Azure may refuse a work-item type change on an item with links; the first pass never changes a type, so the risk is contained to the warning.
- **Board visibility.** Dependency links are visible in the Links tab and the dependency view, not as a tree on the board; the human accepted this trade-off to keep composition many-to-many.
- **Existing epics.** Their `epic:` keys are ignored, not migrated; a half-written old link becomes a plain task, which `validate` can flag as an unidentified item.

## Outcome

Uma gramática só para `## Tasks`: um checkbox com `— spec: #<id>` nomeia outro documento e qualquer outro descreve trabalho. A composição virou propriedade (aninha, pertence a várias, mistura tarefas e membros), o nível passou a ser derivado das ondas (story/feature/epic) e o estado de um membro é lido do documento dele — nunca marcado na composta. `cq specs link add|remove` substitui `epic add`, que segue como apelido; os achados viraram `sp-link-*` e `epic:` no membro foi aposentado com aviso. No card, o tipo do projeto não muda: nível no corpo e no label, membros como predecessores, coluna seguindo os membros. `epics.md` foi removido e `spec-composition.md` é o contrato. Entregue no PR 47 (merge 7588d2209) e a superfície do databricks-risco-gold foi regerada a partir dessa main (PR 228603).
