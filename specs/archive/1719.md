## Problem

The autopilot queue step cannot identify open specs outside epics from its prescribed `cq specs list --lean --json` (`plugins/quenching/commands/specs/autopilot.md:63`). Independent verification in `../resume-map-prose-verify.json`, item 5, at 719ca3e5: lean rows have `id,path,phase,records,state,title`; full rows have `date,folder,id,legacy,outcome,path,phase,records,stage,tasks,title,unreadable`. Neither list form, status nor next-front projects `epic` or `workItemType`, though member and epic frontmatter already store them (e.g. `show --spec 1627 --full`).

Consequence: active epic members can reenter the loose queue, or the conductor must dump every document to classify the queue.

Scope, delegated owner decision: add `epic` and `workItemType` to each row of full and lean JSON listings by projecting existing metadata. `epic` uses the identifier type already used by `id`; `workItemType` is a string; absent values are null. Preserve all prior keys, ordering, selection and queue source/algorithm; do not edit autopilot.md. Files: `plugins/quenching/assets/bin/quenching/specs/commands/read.py`, backend only if needed to carry existing fields, corresponding generated `plugins/quenching-specs-reader/` mirrors via the existing sync, and `plugins/quenching/tests/test_specs_epics.py`. Do not widen scripts, grants or CI.

Acceptance: in both list forms a member projects its parent identifier, an epic projects `workItemType: "epic"`, and an ordinary loose spec projects both null; existing keys retain their values and types. Add regression coverage that fails on the base. `python3 -m unittest discover -s plugins/quenching/tests -p "test_specs_*.py"` and `bash scripts/verify_repo.sh` exit 0.

## Proposal

- Every row of `cq specs list --json` and `cq specs list --lean --json` carries `epic` and `workItemType`, projected from the existing frontmatter keys of the same names.
- A member projects its parent in `epic`, using the identifier type already used by `id`; an epic projects `workItemType: "epic"`; an ordinary loose spec projects both as `null`.
- Every prior key, its order, value and type, the selection, and the autopilot queue source and algorithm are unchanged.

## Out of Scope

- Editing `plugins/quenching/commands/specs/autopilot.md` or the queue algorithm: the owner decision limits this to additive projection.
- Projecting the fields through `status` or `next --front`: only the two list forms were requested.
- Carrying the fields on the GitHub and Azure lean indexes: their lean rows never read the document body; the fields are `null` there until a backend can supply them honestly.
- Scripts, grants, hooks, CI and protocol 1694.

## Design

- The backends already hold the parsed frontmatter when they build a lean row (git and memory call `derive_info`); they add `epic` and `workItemType` raw from it, and `read.py` normalizes in one helper shared by both list forms. The full form reads `info["frontmatter"]`.
- Normalization: an empty or missing value is `null`; `epic` is an `int` when the row's `id` is an `int` and the value is all digits, else a string; `workItemType` is the string as stored. This mirrors `id` and the frontmatter without inventing a type.
- Backends whose lean rows lack the document (github, azure) yield no key, which `read.py` renders as `null`.
- Binding: docs/standards/code/optional-payload-fields.md — absence is `null`, never a sentinel, and the key is always present.
- Generated mirrors are regenerated with `python3 scripts/generate_plugin_modules.py --write`, never hand-edited.

- Add the fields only to the lean form: rejected, the acceptance requires both forms.
