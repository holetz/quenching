## Overview

O git é uma das coisas que este plugin mais faz e não tem casa: 566 linhas de procedure moram numa
reference privada do front de specs, e operar git exige entrar por uma spec. Esta spec dá ao `git`
um pilar próprio — `/quenching:git:*` com sete comandos e um eixo `cq git` — e tira do front de
specs a *execução* de git: `develop` sugere a branch, `conclude` revisa, destila, arquiva e sugere
a rota, e o vínculo spec↔PR passa a ser lido do host no momento do PR quando a base é a branch
default do host — e continua carimbado, como hoje, quando não é (o caso deste próprio repositório,
que mergeia por `develop`).
## Problem

O plugin tem hoje 26 comandos em três namespaces — `/quenching:knowledge:*` (10),
`/quenching:specs:*` (9), `/quenching:components:*` (6) — mais a raiz `/align`. **Não existe
namespace `git`**, e mesmo assim o git é uma das coisas que o plugin mais faz.

Ele vive embutido no front de specs. Medido nesta árvore em 2026-08-16:

- `plugins/quenching/assets/references/specs-execute/git.md` tem **566 linhas** e é a única casa da
  procedure de git do plugin inteiro — nome de branch, worktree, subject de commit, as quatro
  estratégias de merge, a rota PR, a regra read-if-present.
- Menções a git/branch/worktree/PR/merge por corpo de comando: `conclude.md` 184, `execute.md` 75,
  `develop.md` 15, `orchestrate.md` 13, `continue.md` 12, `create.md` 9.
- `execute.md` **executa** a oferta de isolamento inline (worktree > branch > in place), carimba o
  registro `branch:` e reescreve `git config branch.<name>.description` com a linha
  `quenching-slugs:` depois de cada commit.
- `conclude.md` **executa** o merge (quatro estratégias), a rota PR (`git push -u`,
  `gh pr create --base <base>`, `gh pr merge`, e a asserção de que a base andou) e a remoção da
  worktree.
- `develop.md` não toca branch alguma: `git.md` §Isolation happens on the way into a build declara
  que `create` e `develop` "take no branch at all", uma narrowing deliberada de uma release atrás.

Duas consequências. A primeira é que **quem quer operar git com o plugin precisa entrar por uma
spec**: não há como pedir um commit no padrão da casa, abrir um PR, ou podar branches mortas sem
que exista uma spec viva no meio do caminho. A segunda é que a procedure de git está presa ao front
que a usa primeiro — `specs-execute/git.md` é citada por `conclude`, que não executa, e por
`orchestrate`, que conduz; o nome do arquivo já não descreve quem depende dele.

## Proposal

Duas mudanças acopladas, nesta ordem:

1. **Criar o pilar `git`** — `/quenching:git:*` mais o eixo `cq git` — absorvendo a procedure que
   hoje é privada do front de specs e ganhando os verbos que não temos.
2. **Tirar do front de specs a execução de git**, de `create` a `conclude`. Os comandos de specs
   deixam de executar git e passam a **sugerir** o comando do pilar no ponto em que a operação
   cabe: a branch ao concluir `/quenching:specs:develop`, e a rota (PR ou merge local) ao concluir
   `/quenching:specs:conclude`.

`/quenching:specs:conclude` passa a **revisar, destilar, arquivar e parar** — entregando
`/quenching:git:pr:create` ou `/quenching:git:merge`, e deixando a escolha com o humano. O que
sustenta essa parada é que **o vínculo spec↔PR é do host, não do carimbo**: sob `github` o corpo do
PR carrega `Closes #<n>` e o vínculo é lido de volta por `gh pr view --json
closingIssuesReferences`; sob `azure-boards`, `az repos pr create --work-items <id>` o atrela ao
work item. Onde o host vincula, `pr:` e `merge:` deixam de ser carimbos obrigatórios e viram
leitura sob demanda.

O critério do pedido continua valendo: a sugestão é sugestão. Nada passa a ser executado sem
palavra humana — com uma exceção declarada, `/quenching:specs:orchestrate` na engrenagem mínima,
onde a autorização única já cobre publicar e não há humano no meio do fluxo para receber sugestão.

## Design

### O pilar

`git` é um pilar no sentido que o glossário já dá ao termo — um eixo que `cq` roteia. Ele ganha
`cq git` com quatro subcomandos determinísticos, e **nenhum `doctor`/`validate`**: não há artefato
que um verificador possa validar, e inventar um seria preencher tabela. Por isso a coluna do
`align-surface.md` passa a 1×5 com a quarta linha declarando *sem align, e por quê*.

| `cq git` | O que resolve |
| --- | --- |
| `base` | a cadeia `integrationBranch` → `origin/HEAD` → `init.defaultBranch` → `main`, hoje reimplementada em prosa — e se essa base resolvida é a branch default do host, o fato que decide se `pr:`/`merge:` viram leitura sob demanda ou seguem carimbo obrigatório (§Quando o vínculo é lido de volta, e quando não é) |
| `slugs <branch>` | lê e reescreve a linha `quenching-slugs:` da branch description — hoje um bloco `python3 -c` de 18 linhas colado à mão de dentro da reference |
| `stale` | branches merged/gone e worktrees órfãs, alimentando `cleanup` |
| `conventions` | read-if-present: diz qual convenção governa, a do alvo ou o default |

### Os sete comandos

`branch`, `commit`, `pr:create`, `merge`, `sync`, `cleanup`, `pr:review` — 26 → 33 comandos. Os
quatro primeiros absorvem o que já fazemos hoje (a oferta de isolamento, o subject de commit, a
rota PR, as quatro estratégias com o caveat do squash); os três últimos são o que o pedido chamou
de inspiração além do que temos. `merge` existe ao lado de `pr:create` porque `fast-forward` não
tem equivalente em `gh` e porque um repo sem host precisa de saída.

Os dois verbos de PR seguem o padrão de objeto/verbo que o repo já usa em
`components/command/new.md`: `commands/git/pr/create.md` e `commands/git/pr/review.md`.

### O que `conclude` passa a fazer

Revisa a branch, escreve o `/.knowledge/` que o trabalho revelou, arquiva, destila — e **para**,
entregando `/quenching:git:pr:create` ou `/quenching:git:merge`. Isso reescreve dois contratos que
hoje existem por escrito, e a reescrita é deliberada, não um contorno:

- **"O merge é a última ação do run"** existia para que nada fosse commitado na base depois dele.
  Com `conclude` terminando antes do merge, nada é commitado depois porque o run acabou — a
  propriedade sobrevive por outro caminho.
- **"Arquivar como `done` com PR aberto asseriria o que não aconteceu"** deixa de valer nos termos
  em que foi escrita: `## Outcome` passa a asserir o que o run **entregou** — revisado, destilado,
  pronto para merge — e o merge é um fato do host, legível de lá.

`/quenching:specs:cycle` na engrenagem mínima é a exceção declarada: ele **executa** o PR,
porque é o único ponto onde a autorização única já cobre publicar num remote, onde não há humano no
meio do fluxo para receber uma sugestão, e onde a revisão humana já vive no PR que o run abre.

### Quando o vínculo é lido de volta, e quando não é

**Medido (task 1.1): `closingIssuesReferences` fica vazio quando a base da PR não é a branch
default do repositório — mesmo com `Closes #<n>` no corpo.** A keyword ainda cria um
cross-reference visível na timeline da issue, mas não fecha nem popula o vínculo que um caller
poderia ler de volta. Medido contra duas PRs mergeadas neste próprio repositório
(`holetz/claude-quenching` #925 e #926, ambas com base `develop`, default `main`) — o achado
completo está em
[external/tools/github-cli-measured-behaviour.md](/.knowledge/external/tools/github-cli-measured-behaviour.md).

Isso derruba a premissa lisa da seção anterior para exatamente o caso que
[standards/git/branching.md](/.knowledge/standards/git/branching.md) prescreve e este repositório já
segue: toda spec mergeia via `develop`, nunca diretamente em `main`. Um repo sem `integrationBranch`
declarado não tem esse problema — sua base já é a branch default, e a leitura sob demanda funciona
como desenhado.

**A regra passa a ser condicional pela base, não incondicional pelo backend:**

| A base resolvida (`cq git base`) é a branch default do host? | `pr:`/`merge:` |
| --- | --- |
| Sim | leitura sob demanda — como desenhado, sem carimbo obrigatório |
| Não | carimbo obrigatório — o comportamento de hoje, inalterado |

`cq git base` passa a resolver e expor os dois fatos juntos: a branch a usar como base, e se essa
base é a branch default do host (`gh repo view --json defaultBranchRef` sob `github`;
`az repos show --query defaultBranch` sob `azure-boards`; o backend `files` não tem host e cai
sempre na coluna "Não"). Todo comando que hoje leria o vínculo de volta — `/quenching:git:pr:create`,
`/quenching:git:merge`, `/quenching:specs:conclude` — consulta esse segundo fato antes de decidir se
carimba.

**A mesma regra vale para `azure-boards` até que a task 1.2 prove o contrário.** O mecanismo do
Azure DevOps é estruturalmente diferente — `--work-items` cria um link explícito via API, não
depende de parsing de keyword em texto — o que sugere que a restrição por branch pode não se
aplicar lá. Mas essa é uma hipótese não medida, e desenhar em cima dela repetiria exatamente o erro
que este achado corrigiu; a task 1.2 permanece bloqueada (criar ou minerar artefatos no org
corporativo real configurado no ambiente de execução não é uma ação que uma execução autônoma toma
sem autorização humana) e é o que abriria a exceção para Azure, com evidência, quando alguém a
rodar.

### Profile e coexistência

`git` entra em `profiles.installed` como quarto profile, ligado por padrão. Profile é **residência
de description**, não instalação: desligado, os comandos seguem invocáveis por nome, e como o
handoff do front de specs cita o comando pelo nome, ele continua funcionando — só o roteamento por
fala some. É a única alavanca que existe contra o custo permanente de 33 descriptions residentes.

A categoria `git` de um repo-alvo (`/git:commit`, o exemplo canônico da `taxonomy.md`) e o pilar
`git` do plugin (`/quenching:git:commit`) coexistem: os prefixos já os separam, e
`§Three citation forms` existe exatamente para isso. A taxonomy ganha a linha que registra a
coexistência; o exemplo continua válido, porque é sobre o alvo.

### A casa da procedure

`assets/references/git/` com quatro arquivos por assunto — `isolation.md`, `commit.md`, `merge.md`,
`pr.md` — mais um quinto, `conventions.md`, para as duas seções que os quatro compartilham (a regra
read-if-present e `§What is never done`). O quinto existe para não duplicar as proibições em quatro
arquivos, que é exatamente o custo pelo qual o corte por consumidor foi descartado.

## Alternatives Considered

- **Deixar como está e só extrair a reference.** Move o arquivo de casa e resolve o nome errado,
  mas não entrega nada ao humano que quer operar git sem uma spec no meio — que é metade do pedido.
- **Fazer o pilar `git` ser um quarto front, com seu próprio align.** Um align existe para forçar um
  artefato a uma forma canônica, e git não tem artefato no repositório para alinhar; o verificador
  que todo align abre (`cq knowledge validate`, `cq specs doctor`, `cq components doctor`) não teria
  equivalente. Seria um align vazio para satisfazer uma tabela.
- **Vendorizar os comandos de git no `.claude/commands/` de cada alvo** em vez de shippar no plugin.
  Perde o upgrade path do plugin e duplica a procedure em cada repositório.

## Risks

- **A premissa do vínculo caiu para GitHub com base não-default — e `## Design` já reabriu e
  fechou.** Medido (task 1.1): `closingIssuesReferences` fica vazio quando a PR não mira a branch
  default, o caso canônico deste próprio repositório (`develop` integra, per
  `standards/git/branching.md`). A regra virou condicional pela base — ver `## Design` §Quando o
  vínculo é lido de volta, e quando não é. **Residual:** Azure DevOps segue não medido (task 1.2
  bloqueada — exigiria artefatos num org corporativo real); a mesma regra conservadora se aplica lá
  até alguém medir e, com evidência, abrir a exceção.
- **Arquivar antes do merge.** Uma spec arquivada como `done` cujo PR nunca é mergeado fica
  mentindo, e nada neste desenho fecha esse buraco — o host sabe, mas ninguém pergunta. O
  `## Outcome` reescrito reduz a asserção; não a elimina.
- **A agnosticidade vira fricção.** Trocar uma oferta inline por um handoff em segundo turno
  acrescenta um round-trip por spec construída. A régua é a oferta de isolamento de hoje: uma
  confirmação e nenhuma digitação.
- **Breaking para alvos instalados.** `/quenching:specs:execute` deixa de cortar a branch e
  `conclude` deixa de mergear; quem depende do comportamento atual sente no upgrade.
- **33 descriptions residentes.** O profile é a mitigação, e ele só ajuda quem souber desligá-lo.
