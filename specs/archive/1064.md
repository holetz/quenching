## Problem

Several fronts read the same configuration file without a declared owner for each key, so `pyproject.toml` and the workflow directory can drift while different readers silently disagree. The plugin needs a key-level arbiter contract, including the rule that a read-only pillar does not own a key.

## Proposal

- Publish `docs/standards/architecture/configuration-arbitration.md` as the normative contract for a shared configuration artifact: each mutable key or semantic section has one arbiter that may write or repair it, while other fronts may read it only.
- Apply the contract first to `pyproject.toml` with a key-level declaration: `[project.scripts]` is arbitrated by `ops`; pytest and coverage configuration are arbitrated by `proof`; the declaration records the existing reader paths and does not treat a read-only observer as an owner.
- Use the operations registry's delimited generated-zone and SHA-256 precedent for the `pyproject.toml` arbiter declaration, preserving all configuration outside the owned block and making stale or duplicated ownership detectable.
- Record the admitted future ownership boundary without claiming unbuilt fronts exist: dependencies, locks, language version, lint and build-backend settings belong to the future `toolchain` owner; workflow triggers, jobs and stages belong to the future `delivery` owner; CI-as-gate evidence belongs to `proof`; a `security` pillar reading workflow permissions receives no arbiter row.
## Out of Scope

- Renaming or migrating `.claude/quenching.json`, extracting its shared loader, or defining per-front configuration namespaces. That is A5's configuration-home contract and would mix a key-owner rule with the later envelope migration.
- Minting or implementing the `toolchain`, `delivery` or `security` command surfaces, including their routers, verifiers, command bodies, Codex translations and goldens. Their existence and implementation belong to the child specs named by umbrella 1057.
- Settling the exact ownership partition and generated representation for `.github/workflows/**`. The umbrella identifies the boundary and its conflict with `proof`, `delivery` and `security`, but leaves the exact table to evidence from a real target.
- Changing `ops/inventory.py`, `proof/inventory.py` or any other reader to implement enforcement. This spec defines the contract and the first declaration; consumer-specific checks belong with the front that owns the relevant tree.
- Adding `arbiter` to `/docs/glossary.md` or creating a separate knowledge/spec item. The standard will define the term locally; a reusable glossary entry is a later knowledge decision.

## Design

### Contract

A shared configuration artifact is a file or directory read by more than one front or pillar. Its arbiter is the one front authorized to define, write or repair a particular semantic key or section in that artifact. Ownership is by key path, not by the containing file: assigning all of `pyproject.toml` to one reader would reproduce the drift this spec is repairing. A key may have one arbiter or an explicit pending state while its future owner is not yet built; it must never have two writers silently competing.

Readers are recorded separately from the arbiter. A front that reads a key to produce its own evidence may not thereby claim ownership. A pillar is read-only by shape: `security` may report workflow permissions and other live facts, but it never receives an arbiter row and never repairs the observed key. This follows the `git` precedent and the aligned-front boundary in `align-surface.md`.

### Declaration shape

The first declaration is carried in `pyproject.toml` as a generated comment block so the artifact and its ownership contract travel together:

```toml
# quenching-arbiters-start
# quenching-arbiters-sha256 <64 lowercase hexadecimal digits>
# quenching-arbiters-end
```

The generator owns only the lines between the delimiters and preserves the rest of the file. The SHA-256 is over UTF-8 bytes of a canonical compact JSON object containing the artifact identity and sorted `{key, arbiter}` entries, serialized with sorted keys, compact separators and no trailing newline, following the existing operations-registry precedent. The reader set remains explanatory metadata in the standard, not a second writer declaration.

A verifier may therefore detect a duplicate owner, a missing owner for a claimed mutable key, or a stale declaration without deciding which formatter, ruleset or upgrade policy a repository should choose. Those semantic judgements remain outside this contract.

### First application: `pyproject.toml`

| Configuration key or section | Arbiter | Evidence / readers | Status |
| --- | --- | --- | --- |
| `[project.scripts]` | `ops` | `ops/inventory.py:32,140` | current owner |
| pytest configuration | `proof` | `proof/inventory.py:177-180` | current owner |
| coverage configuration | `proof` | `proof/inventory.py:177-180` | current owner |
| dependencies, lock, language version, lint and build backend | future `toolchain` front | the umbrella's admitted ownership boundary; no unbuilt front is claimed as shipped | pending future owner |

The standard also records the adjacent workflow boundary for later application: triggers, jobs and stages are delivery-owned; CI used as proof evidence is proof-owned; workflow permissions observed by `security` are read-only and have no security arbiter row. The exact key granularity and whether that directory receives the same generated block remain open until a real target supplies the evidence.

### Binding boundaries

`align-surface.md` distinguishes a front, which converges a local tree through a verifier, from a pillar, which answers live questions without a tree or an align. `ops-front.md` supplies the generated registry's delimiter/hash mechanism. `shared-mold-keys.md` supplies the ownership test: a shared declaration may carry only keys every legitimate writer can set. This spec applies those contracts to ownership by configuration key and does not turn a read-only report into a repair surface.

## Alternatives Considered

- **Assign the whole `pyproject.toml` to one front.** Rejected because the measured `ops` and `proof` readers already consume different semantic sections; file ownership would hide the conflict rather than arbitrate it.
- **Let every reader own the keys it currently consumes, with no central declaration.** Rejected because the problem is precisely that multiple readers can silently disagree; a reader is not automatically a writer, and future readers would have no admission contract.
- **Make `security` the arbiter for cross-cutting configuration.** Rejected because the aligned-front standard and the umbrella's measurement define `security` as a read-only pillar; giving it ownership would create a repair surface for an axis that converges nothing.
- **Put the ownership table only in a sidecar standard.** Rejected for the first `pyproject.toml` application because the declaration could drift away from the shared artifact. The in-file delimited block with the registry's hash precedent keeps the artifact-local claim detectable while the standard owns the rule.
- **Extract or replace the shared configuration loader in this spec.** Rejected because that is A5's `.claude/quenching.json` migration and would expand this contract repair into a separate configuration-home change.
## Open Decisions

- **The exact arbiter table for `.github/workflows/**` remains open.** Decide it during the A4 execution against a real target's workflow keys and all current readers, then choose whether the directory uses the same delimited block or only a declared key-ownership table; this is the umbrella 1057 decision and is not guessed here.
- **The activation rule for future owners remains open.** Decide in C1/C3, after the `toolchain` or `delivery` route exists, whether its planned rows may enter an existing artifact declaration before the front ships or must remain pending until its first implementation; use the live reader inventory and the declaration verifier as the deciding evidence.
- **Whether a standalone verifier belongs in A4 or in each consuming front remains open.** The standard is settled here; decide during execution by checking whether one neutral checker can prove key ownership without duplicating `ops`, `proof` or future-front semantics. If no such checker is evidenced, keep enforcement in each owning front and retain the standard as the shared contract.
- **Why this contract must be prioritized in this pass rather than after the new axes.** The tree proves the unowned `pyproject.toml` readers and umbrella 1057 places A4 in Phase A before `toolchain`, `delivery` and `security`; the remaining prioritization judgement is decided at human review of the issue, not invented by this pass.
- **What would make the work not worth building.** Decide at approval against whether the current readers can be assigned without changing their semantics and whether the declaration can be checked without a tautological test; if either condition fails, stop this spec and return the finding to the umbrella rather than silently widening it.
- **Whether `arbiter` needs a glossary entry remains open.** Once the standard's wording is stable, decide through `quenching-knowledge-define` against glossary reuse and cross-spec occurrence; this spec does not write `/docs/glossary.md`.
## Risks

- **The declaration can become a second source of truth.** A hand-edited table may disagree with the readers it describes. Mitigate with the generated delimiters, canonical payload and SHA-256 freshness check, while preserving non-owned text outside the block.
- **Key granularity can be wrong.** Treating a whole manifest or workflow directory as one key recreates the original collision. Mitigate by naming semantic key paths and reviewing one owner per path against the measured reader locations.
- **A reader can be mistaken for an arbiter.** `proof` reads CI/configuration evidence and `security` reads permissions, but neither observation grants ownership of unrelated keys. Mitigate with separate reader metadata and the explicit no-arbiter rule for read-only pillars.
- **A future owner can be declared before its front exists.** This can create false authority or an empty route. Mitigate with `pending future owner` status and the activation decision delegated to C1/C3.
- **The workflow directory may have overlapping legitimate readers.** `proof`, `delivery` and `security` inspect adjacent facts in the same tree. Mitigate by leaving the exact table open until a target inventory identifies semantic keys and writer capabilities.
- **The standard may cite a command or precedent that later moves.** Mitigate with `knowledge validate` and the citation check in the task-level validation, and keep the standard's citations pointed at the owning documents.
