## Problem

O comando de PR ainda depende de intervenção para definir o título e a descrição, e o commit incremental solicita aprovação humana antes de prosseguir. Isso torna o fluxo de entrega mais manual do que o necessário e precisa ser ajustado para gerar os dados do PR automaticamente e executar o commit incremental sem essa solicitação.

## Proposal

- When `/quenching:git:pr:create` receives a spec id, it will derive the pull request title and description from the provider-owned spec and the branch facts already required by the command. The generated description will carry the problem, proposal, task summary, validation state, and provider-native issue or work-item link without asking the human to author those fields.
- The command will still show the resolved remote, base, title, description, and native link effect and ask once before pushing or opening the pull request. Automating metadata does not authorize an external write.
- When `/quenching:git:commit` is invoked without a subject during an incremental spec build, it will derive a subject from the current spec/task context and the target's declared convention. It will execute the commit after the existing staged-diff and hygiene checks, without a confirmation question. An absent or ambiguous spec/task context remains a refusal, never an invented generic subject.
- Explicit subjects remain accepted and continue to win over derivation. The command still commits only the existing index, never stages files, amends history, bypasses hooks, or force-pushes.
- The Claude source remains authoritative; the Codex mirror, command references, tests, functional checks, and relevant workflow documentation will be regenerated or aligned in the same change.

## Out of Scope

- Removing the confirmation required before `git push`, `gh pr create`, or `az repos pr create`.
- Choosing a merge strategy, merging a pull request, deleting a source branch, or changing the `pr:` and `merge:` record ownership.
- Staging files, changing the target repository's commit convention, inventing a subject when no spec/task can be resolved, or rewriting existing commits.
- Deriving PR metadata for a free-text PR invocation with no spec; that path may continue to require an explicitly supplied description.
- Changing provider APIs, GitHub/Azure authentication, or the provider-owned spec schema.

## Design

The PR path has one deterministic payload builder. Given a spec id, it reads the provider-owned status once, takes the title from the spec title, composes the description from the canonical Problem, Proposal, Impact and Validation sections, appends the task/branch facts that exist, and adds the provider-native locator according to the configured backend. Missing optional sections are reported as absent rather than fabricated. The payload is shown once and then travels unchanged into the provider command after the existing confirmation.

The incremental commit path resolves its context in this order: an explicit subject argument; a uniquely resolved spec on the current branch's `quenching-specs:` mark and its next actionable task; or a uniquely resolved current spec/task supplied by the execution caller. If more than one spec or task can supply a subject, or if no task can be resolved, it refuses with the exact missing/ambiguous fact and names the caller that must provide it. A resolved subject is shown in the final report, but no confirmation question is inserted between the staged-diff check and `git commit`.

The command remains a thin orchestrator over the existing provider, specs, and git rails. No new metadata store is introduced: PR text is derived from the spec at the moment of publication, and the commit subject remains the target convention's anchor. The tests use throwaway repositories and provider fixtures to prove both positive derivation and refusal boundaries.

## Alternatives Considered

- Keep asking the human for PR title and description. Rejected because those fields are already derivable from a canonical spec and the prompt adds repeated manual work without improving the external-write confirmation.
- Remove all PR confirmation once metadata is automatic. Rejected because push and PR creation are external writes with review and branch effects that remain human-owned.
- Always use a generic incremental subject such as `chore: incremental commit`. Rejected because it loses task traceability and can create an anchor that no spec task resolves.
- Require an explicit subject forever. Rejected because the execution flow already has a unique spec/task context and can derive the same convention-safe subject without another question.
- Read the staged diff with a model to invent a subject. Rejected because the subject is a lifecycle anchor, not a prose summary; ambiguity must refuse rather than become an unreviewable guess.

## Open Decisions

- The exact section ordering and Markdown template for a generated PR description should follow the current spec sections and existing provider length limits. Resolve during execution by the focused tests and the command's existing status payload; keep the template deterministic and omit absent optional sections.
- A branch carrying multiple specs must not silently choose one for an incremental commit. Resolve by refusing and naming the explicit spec/task argument as the caller-owned remedy.
- Whether free-text PR creation should gain the same derivation is intentionally deferred because it has no canonical spec source. If requested, capture it as a separate spec rather than weakening the spec-id contract.

## Risks

- A generated PR description may be too long for a provider. Mitigate with a deterministic bounded rendering that preserves the title, problem, proposal, validation, and native locator, and report truncation rather than silently dropping the locator.
- A branch mark can be stale or contain multiple specs. Mitigate with the existing resolver and an explicit refusal on ambiguity; never choose by recency.
- Removing the commit question could make an unintended staged diff easier to commit. Mitigate by retaining the non-empty-index check, exact staged-file report, target convention read, hook execution, and no-staging invariant.
- Claude and Codex bodies can diverge after a source edit. Mitigate with generated translation, translation check, citation check, and focused surface tests.
- Provider fixtures may prove payload assembly without proving a live PR. Mitigate by keeping the external-write confirmation and reporting live provider execution as outside the offline suite.
