## Problem

Num repositório sem `.claude/quenching.json` e com remote no GitHub, o store efetivo é o backend `github`, que o README dá como deprecated. Mesmo assim, `cq specs doctor` devolve `findings: []` e `backend: null`, então o aviso `sp-backend-deprecated` nunca aparece no caso em que um projeto novo cai no modo errado.

Reprodução (quenching 6.4.0, `holetz/my-career` em 2026-10-17, antes de declarar a config):

- `cq specs config --json` → `"backend": "github"`, `"present": false`
- `cq specs list --lean --json` → `"backend": "github"`
- `cq specs doctor --json` → `{"ok": true, "backend": null, "findings": []}`

Causa: `plugins/quenching/assets/bin/quenching/specs/commands/doctor.py:92` testa `cfg["backend"] in ("github", "azure-boards")` sobre o backend **declarado**. Sem arquivo, esse valor é `None`. Já `list` e `config` usam o backend **efetivo**, inferido do remote em `specs/config.py:164-173` (`detect_provider`). O doctor e o resto do CLI discordam sobre qual é o store.

Consequência: o autopilot e o `/quenching:specs:create` gravam specs completas em issues sem nenhum sinal, e o único comando que existe para perguntar "o que está errado no workspace" diz que está tudo certo. O problema só apareceu porque o humano esperava a branch `quenching`.

Relação: a #1654 trata a causa (tornar a branch obrigatória e nunca inferir um tracker). Esta spec é o conserto estreito e imediato: enquanto existir inferência, o doctor precisa acusar o backend efetivo deprecated, e dizer que ele foi inferido, sem config declarada. Quando a #1654 fechar, este finding vira o guarda contra regressão.

## Proposal

- Num repositório sem `.claude/quenching.json`, o finding `sp-backend-deprecated` de `cq specs doctor` diz que o backend foi inferido do remote e que nenhuma config o declara.
- O remedy desse caso inclui declarar o backend em `.claude/quenching.json` (`backend: git`) além do `migrate --to git`.
- Com a config declarando `github` ou `azure-boards`, o finding mantém a mensagem e o remedy de hoje.
- Um teste prova os dois textos e fica como guarda contra regressão enquanto a inferência existir (#1654).

## Out of Scope

- Remover a inferência de backend pelo remote: é a #1654.
- Mudar `cq specs config` ou `list` para expor um campo "inferido": o `present: false` já o diz.
- Mudar o código, a severidade ou o gatilho do finding: ele já dispara sem config (verificado no `cq` 6.6.0).

## Design

- Regra: o finding de backend deprecated nomeia a origem do backend. `load_config` devolve `present: false` quando o backend vem do remote; o doctor ramifica nisso e só no texto. Alternativa pesada (campo novo `inferred` no `load_config`) foi descartada: `present` já carrega a informação e mudar o payload alcança todos os chamadores.
- Contrato: os espelhos em `quenching-specs`, `quenching-specs-reader` e `quenching-codex` são gerados por `scripts/generate_plugin_modules.py` e `scripts/sync_codex_plugin.py`; o diff os inclui.

### Mapa de dependências

- `doctor.py` (fonte) → 3 espelhos gerados + `.generated-files.json` do codex; sem outros leitores do texto do finding além de `test_specs_doctor.py` (que só testa o código e o remedy `migrate --to git`).
- `docs/standards/architecture/spec-backend.md` e `specs-align/conformance.md` citam só o código `sp-backend-deprecated`, que não muda.

## Alternatives Considered

- Novo finding `sp-backend-inferred` separado: rejeitado, duplicaria o aviso no mesmo caso e o deprecated já dispara.
- Esperar a #1654: rejeitado, a #1654 é maior e este finding vira o guarda dela.
