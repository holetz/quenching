## Problem

Não há jeito direto de abrir um slot no editor (`code -n`, um `.code-workspace` com os slots ativos) nem tarefas em `.vscode/tasks.json` para o gate, `cq deploy --check`, `cq specs status` e `cq git worktree slots`, que custariam zero tokens. A limpeza de worktrees do VS Code commita alterações e apaga arquivos ignorados; não está verificado que ela respeita slots travados, e apagar o `.venv` reaproveitado anularia o ganho dos slots.

## Proposal

- **O slot livre continua travado.** `release` devolve o slot ao pool com o lock `quenching: available` em vez de destravá-lo, e `acquire` reivindica um slot livre trocando o lock (unlock → lock); o perdedor da corrida cai no próximo. `git worktree lock` é a proteção: a Git extension do VS Code remove um worktree com `git worktree remove <path>` sem `--force` em todos os pontos de exclusão (fonte consultada em 2026-11-25), e o git recusa um worktree travado — o `.venv` ignorado do slot nunca é apagado.
- **O relatório e a limpeza conhecem o lock livre.** `cq git worktree slots` classifica `free`/`held` pelo motivo do lock; `cq git stale` não trata o lock livre como bloqueio (o piso `shared.worktreeSlots.min` continua protegendo os primeiros slots); `cq git prune` destrava um slot livre elegível antes de removê-lo e o re-trava se a remoção falhar.
- **Uma projeção de workspace com os slots ativos.** `cq git worktree workspace [--write] [--all] [--output PATH]` monta um `.code-workspace` JSONC com o checkout primário e os slots travados (todos os slots e os outros worktrees com `--all`), imprime `code -n <path>` e, com `--write`, grava `.vscode/quenching-slots.code-workspace` no checkout primário — máquina-local, coberto pelo `.vscode/*` do git.
- **Tarefas de zero token no VS Code.** O deploy semeia `.vscode/tasks.json` quando `shared.workspace.vscode` é verdadeiro, com as tarefas do gate, do `cq deploy --check`, do `cq specs status`, do `cq git worktree slots` e do workspace dos slots. O arquivo é semente como o `settings.json`: criado só quando ausente, nunca reescrito, nunca comparado por drift.
- **O doctor reporta os dois seeds.** `cq doctor` ganha a linha do tasks e `cq doctor --workspace` imprime o estado e o bloco dos dois arquivos, sem escrever nada.
- **Este repositório adota a semente.** `.vscode/tasks.json` versionado, `.gitignore` reabrindo só ele e o `settings.json`, e o `cq deploy --target . --write` regenerando a superfície.

## Out of Scope

- Provar a metade ao vivo no cliente (abrir o workspace, rodar as tarefas, tentar excluir um slot pela UI) — nenhuma sessão de CI tem VS Code; o protocolo fica no `## Handoff` e o que o git garante é provado por teste.
- Uma extensão ou plugin do VS Code — a 466 avalia, e "não" é um resultado válido.
- Travar worktrees que o harness cortou: a 458 decidiu que a adoção não toma lock e o ciclo de vida é do cliente; esta spec os torna visíveis com `--all`, não os protege.
- Editar um `.vscode/tasks.json` existente — semente criada só quando ausente, como o `settings.json` da 457.
- `files.watcherExclude` e `search.followSymlinks` — outra medição, não esta.
- Uma chave de configuração nova: `shared.workspace.vscode` já liga as duas sementes; não há `shared.workspace.tasks`.
- Um modo `--harness copilot` ou uma projeção ramificada por nome de cliente.

## Design

### O lock livre do slot

- `release` termina com `_lock(path, FREE_REASON)` em vez de `_unlock`; `FREE_REASON = "quenching: available"` não tem o formato `quenching: <spec> · <session> · <host> · <date>`, então `parse_reason` continua devolvendo `None` e nenhum holder é inventado.
- `survey` lê um worktree travado com `FREE_REASON` como `state: free` e mantém o motivo em `lock`; um slot travado por qualquer outro motivo é `held`; um slot legado sem lock continua `free`.
- `_take` reivindica um slot livre com `_claim`: se o lock é o livre, `unlock` e em seguida `lock --reason <holder>`; se não há lock (legado), só o `lock`. `git worktree lock` falha quando o arquivo de lock existe, então dois takers nunca vencem o mesmo slot; quem perde tenta o próximo. A criação (`worktree add --lock --reason`) não muda.
- A janela entre `unlock` e `lock` é o único ponto em que o slot fica destravado; um terceiro taker que a vença leva o slot e o primeiro cai no próximo, nunca os dois.
- `release` também tem essa janela ao trocar o motivo: um acquire concorrente pode levar o slot; o release reporta `released` e o slot segue o novo holder. O lock final é o mutex.
- `stale._assess_worktrees` deixa de marcar `locked` quando o motivo é `FREE_REASON`; o slot livre continua elegível acima do piso `min`, e `_keep_the_slot_floor` preserva os primeiros. `prune` destrava um slot livre antes do `worktree remove` sem `--force` e, se a remoção falhar, re-trava; o relatório fresco já garante que o slot não virou held entre a leitura e a ação.
- `retire` não muda: um slot travado já é recusado pelo `worktree remove` sem `--force`, e slot se dá por `release`.

### A projeção do workspace

- `cq git worktree workspace [--write] [--all] [--output PATH] [--json]` lê `survey` e monta um documento JSONC: `folders` é o primário (`quenching`) seguido de cada slot `held` (`slot <n> — <branch>`); `--all` soma os slots `free` e os outros worktrees registrados.
- Sem `--write` o verbo imprime o documento; com `--write` grava o caminho (default `<primary>/.vscode/quenching-slots.code-workspace`), cria o diretório e a saída humana termina com `code -n "<path>"`. O payload `--json` carrega `folders`, `path`, `written`, `command` e o `document` como texto.
- O arquivo é máquina-local (caminhos absolutos), coberto pelo `.vscode/*` do `.gitignore` quando o repositório reabre só `settings.json` e `tasks.json`; nunca é versionado nem drift-checked.

### As tarefas do VS Code

- `common/workspace.py` ganha `TASKS_PATH`, o documento e `tasks_report`: cinco tarefas (`gate`, `deploy check`, `specs status`, `worktree slots`, `slots workspace`) mais `open slots`, com o input `specId`; cada tarefa usa `.agents/quenching/bin/cq` (o gêmeo `cq.cmd` na sobrescrita `windows`), `options.cwd: ${workspaceFolder}`, `problemMatcher: []` e um painel dedicado. O gate é `bash scripts/verify_repo.sh` no grupo `test`.
- O deploy semeia o arquivo quando `shared.workspace.vscode` é verdadeiro e ele não existe, exatamente como o `settings.json`; `--check` reporta `seed`; a remoção nunca o apaga; uma sugestão nomeia a chave quando o alvo tem `.vscode/` sem ela. `cq doctor` reporta os dois arquivos e `--workspace` imprime os dois blocos.
- As duas sementes são um opt-in só: a chave da 457 governa `settings.json` e `tasks.json`, e não há chave nova.

### Contratos que o desenho não contradiz

- 457: `shared.workspace.vscode` continua a única chave, escopo `project`, lida do documento do repositório; a semente nunca é reescrita nem listada no manifesto.
- 458: a adoção de worktree do harness continua sem lock; a projeção o mostra com `--all`, não o protege.
- 459: os grants de `Bash(cq …)` e o acesso aos slots não mudam; as tarefas rodam no terminal do cliente, sem turno de modelo.
- O invariante do épico 453: nada ramifica por nome de cliente; `vscode` é uma chave de repositório e as tarefas são um artefato do cliente, não um harness.
- `plan-git-record.md`: um slot travado é reportado à parte; o lock livre é do próprio slot e nunca um `foreign-lock`.
- O gate: `cq deploy --check` continua verde neste repositório depois do `--write`, e a semente é o mesmo mecanismo do `AGENTS.md`.

### Assumptions

- A Git extension do VS Code é o único caminho de limpeza do cliente medido, e ela remove com `git worktree remove` sem `--force`; uma versão que passe `-f -f` derrotaria o lock — depende do `## Design` e do lock livre.
- `git worktree lock` grava o motivo como texto e o aceita no Windows; o separador `·` e os dois-pontos não são caracteres proibidos — depende do lock livre.
- Um `.code-workspace` aceita caminhos absolutos de pastas irmãs sem uma segunda confiança além da pasta — depende da projeção.
- O cliente honra a sobrescrita `windows` de uma tarefa e o launcher `cq.cmd` existe em todo alvo deployado — depende das tarefas.
- O lock livre não muda o comportamento de um `cq` antigo que compartilhe o pool: ele lê o slot como held e, no teto, recusa; o deploy atualiza a superfície do mesmo repositório — depende do `## Risks`.

## Alternatives Considered

- **Deixar o slot livre destravado e confiar no `git worktree remove` limpo** — o comando apaga ignorados sem reclamar, e o `.venv` do slot é ignorado; recriá-lo é o custo que o slot existe para evitar.
- **Um lock comum e o mutex num arquivo de claim separado** — o `O_EXCL` já serializa a criação, mas reivindicar exigiria um segundo protocolo e um journal de crash; o unlock → lock mantém um só mutex (o próprio git) e o perdedor cai no próximo.
- **Um `.code-workspace` versionado com caminhos relativos `../<repo>-slot-*`** — o VS Code não expande curinga em `folders.path`; um valor fixo por máquina viraria drift, e a projeção sob demanda lê a mesma fonte do `slots`.
- **Uma extensão do VS Code que desenhe a lista** — uma segunda superfície e um dono de release; a 466 avalia, e as tarefas e o workspace usam o cliente que já existe.
- **Semear `tasks.json` numa chave nova** — duas chaves para o mesmo opt-in; a 457 já declarou a chave do workspace e a semente é a mesma decisão.
- **Não fazer nada** — o slot livre é removível pelo editor e o `.venv` desaparece sem aviso; o usuário só descobre no próximo acquire.

## Open Decisions

- **A versão do VS Code que a limpeza observa** — a metade ao vivo do `## Handoff` grava a versão e o resultado; a fonte consultada em 2026-11-25 é a `main` da Git extension, e uma mudança para `-f -f` reabre a proteção.
- **Incluir slots livres por padrão no workspace** — o default são os ativos; `--all` é a decisão do humano quando quer ver o pool. O teste fixa o default.
- **O caminho do `cq` nas tarefas** — `.agents/quenching/bin/cq` e o gêmeo `cq.cmd` no Windows; um alvo que instale o payload em outro lugar ajusta a tarefa, que é semente e não drift.
- **O destino do `code -n`** — a tarefa abre uma janela nova com o workspace; quem preferir a janela atual troca a tarefa, sem mudança de código.

## Risks

- **Um cliente que passe `-f -f` ao remover worktree** derrota o lock; a fonte atual não passa `--force` e a metade ao vivo grava a versão observada.
- **Um `cq` antigo lê o lock livre como held** e, no teto, recusa um acquire; o deploy atualiza a superfície do mesmo repositório, e o pool compartilhado por máquinas com versões diferentes é o caso a nomear no `## Handoff`.
- **A janela do unlock → lock** deixa o slot destravado por um instante; o lock seguinte falha se outro taker venceu, então nenhum dois vencem, mas o primeiro pode perder para um terceiro.
- **O `prune` destrava antes de remover**: se a remoção falhar e o re-lock falhar, o slot fica destravado; o payload nomeia o fato e o próximo `slots` mostra `lock: null`.
- **A semente `tasks.json` divergir da CLI** — o arquivo não é drift-checked, como o `settings.json`; um teste fixa os comandos e a sugestão nomeia a chave.
- **O `.vscode/tasks.json` versionado neste repositório** receber uma edição do usuário e o deploy nunca reescrevê-lo; a adoção é uma seed, não um manifesto.
- **O workspace com 12 slots** abrir uma janela pesada; o default são os ativos, e `--all` é explícito.
