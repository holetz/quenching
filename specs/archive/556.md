## Problem

O `cq deploy` só escreve dentro do repositório alvo, mas parte do que o quenching precisa para funcionar vive fora dele e hoje é feita à mão, máquina a máquina, guiada por prosa de doc: o lançador `~/.local/bin/cq`; a configuração global do OpenCode quando ela tem um bloco `experimental` que substituiria o do projeto (`subagent_depth`); os plugins que não instalam em repositório (HUD e claude-cache do Claude Code, a vitrine do OpenCode); as extensões e configurações de usuário do VS Code/Copilot; e a aprovação do servidor MCP em cada cliente. Um usuário novo num repo com quenching não tem um caminho único e verificável para isso.

Pedido (riscos-plataforma, 26/11/2026): o quenching deve gerar no alvo, em `.quenching/`, bootstraps que o usuário roda para instalar os plugins/mods no OpenCode, no VS Code e no Claude Code e aplicar as configurações que o projeto não pode aplicar por ele — idempotentes, com `--check`, por harness declarado e por sistema (POSIX e Windows).

**Insumos**

- `docs/project/quenching.md` do riscos-plataforma: §O `cq` no PATH, o `subagent_depth` da 7.16.0, o `enabledMcpjsonServers`
- `integrations/claude-hud/`, `integrations/claude-cache/`, a vitrine do OpenCode
- o `scripts/bootstrap/{windows,linux}/` do riscos-plataforma, que já faz parte disso para o próprio repo

## Proposal

O `cq deploy` passa a GERAR, em `.quenching/bootstrap/`, três arquivos que o usuário roda à mão: `bootstrap.py` (a lógica, um só código para os dois sistemas) e os dois lançadores finos `bootstrap.sh` (POSIX) e `bootstrap.cmd` (Windows). O deploy só escreve esses arquivos; nunca os executa.

O script cobre, por harness declarado no manifesto, o que o deploy não pode configurar pelo usuário:

- **sempre:** o lançador `cq` do usuário (`~/.local/bin/cq`, ou `%USERPROFILE%\.local\bin\cq.cmd`), que sobe a árvore de diretórios até achar o `.agents/quenching/bin/cq` mais próximo e cai no deste repo; mais o aviso (POSIX) ou a entrada no PATH de usuário (Windows) para o diretório do lançador;
- **`opencode`:** `experimental.subagent_depth: 4` no bloco `experimental` da config global, quando ela já tem esse bloco (um bloco de projeto substitui o global, anomalyco/opencode#60410, e o deploy por isso não escreve o valor no projeto); e a vitrine na lista `plugins` da config global, apontando o checkout do quenching;
- **`claude`:** o marketplace `holetz/quenching` e os plugins `quenching-hud` e `quenching-cache` no escopo de usuário, pela CLI `claude plugin`;
- **VS Code/Copilot** (quando o repo declara `shared.workspace.vscode` ou a projeção `github`): `chat.agent.maxRequests >= 100` nas configurações de usuário e as extensões `GitHub.copilot` e `GitHub.copilot-chat`.

Contrato do script: `--check` (padrão, só leitura; exit 0 tudo em dia, 1 pendente ou manual, 2 erro) e `--write` explícito. Idempotente: reexecutar com tudo em dia não escreve nada. Antes de qualquer escrita fora do repo, `--write` imprime a lista completa do que vai escrever e rodar; cada arquivo que ela altera é copiado antes para `.quenching/bootstrap/backups/<data-hora>/`. Um arquivo JSON com comentários (JSONC) nunca é reescrito: vira item `manual` com o trecho exato a colar.

## Out of Scope

- Rodar o script: o deploy não o executa, nenhum hook, passo de CI, grant ou `allowed-tools` novo o chama.
- Aprovação do servidor MCP: o Claude Code já a recebe do deploy (`enabledMcpjsonServers` em `.claude/settings.json`, `settings.py`), o OpenCode não pede aprovação e a confiança do VS Code é interativa. Nada a gerar.
- Editar `~/.bashrc`, `~/.zshrc` ou o registro além da entrada de PATH do usuário no Windows.
- Reescrever JSONC preservando comentários; instalar a vitrine do Claude Code, o `opencode-cache` e o `opencode-quota`.
- `.gitignore` do alvo: `.quenching/` já é o destino efêmero declarado pelo `AGENTS.md`.

## Design

### Decisões

- **Um código Python, dois lançadores.** O `cq` já exige Python, então a lógica é um só `bootstrap.py`, testado em Linux; `bootstrap.sh` e `bootstrap.cmd` só acham o interpretador (`python3`/`python`; `py -3`/`python`) e repassam os argumentos.
- **Fora do manifesto `files`.** `.quenching/` é ignorado pelo git; se os três arquivos entrassem em `files`, o `cq deploy --check` do CI (sem `.quenching/`) acusaria `create`. A chave `bootstrap` do manifesto lista os caminhos (determinístico, igual em toda máquina); o `--check` do deploy só acusa `update` num arquivo presente cujo conteúdo difere, e a ausência não é drift. O `--write` do deploy os (re)grava sempre e o `--remove` os apaga.
- **O script nasce de um modelo em `quenching/assets/bootstrap/bootstrap.py`**, copiado para o payload (`.agents/quenching/assets/bootstrap/`) como o resto de `assets/`; o gerador substitui só o bloco `CONFIG` (versão, harnesses, se há VS Code). Um alvo que roda o deploy a partir do payload vendorizado gera o mesmo arquivo.
- **Itens por harness e por sistema:** lançador (sempre), `opencode-depth` e `opencode-plugin` (harness `opencode`), `claude-plugins` (harness `claude`), `vscode` (declarado). Cada item é um par plan/apply; o plan classifica `ok`, `todo`, `manual` ou `n/a`.
- **Escritas fora do repo, todas nomeadas:** o lançador; `~/.claude/plugins/known_marketplaces.json`, `~/.claude/plugins/installed_plugins.json` e `~/.claude/settings.json` (o que `claude plugin` altera, com os comandos listados); a config global do OpenCode; as configurações de usuário do VS Code; a entrada de PATH de usuário no Windows (o valor antigo vai para `backups/<data-hora>/user-path.txt`). Cada arquivo existente é copiado antes de ser alterado.
- **JSONC nunca é reescrito.** `jsonc_loads` lê; a escrita exige JSON estrito (`json.loads` aceita o texto). Com comentários, o item é `manual` e imprime o trecho.
- **Sem rede e sem execução implícita:** `--check` só lê arquivos e consulta `PATH`; `--write` roda apenas os comandos que listou (`claude plugin …`, `code --install-extension …`).

### Assumptions

- A CLI `claude plugin marketplace add <fonte>` e `claude plugin install <plugin>@<marketplace> --scope user` existem na versão instalada (conferido por `--help` em 2026-11-26) — a task de teste fixa a linha de comando, não a execução.
- As extensões `GitHub.copilot` e `GitHub.copilot-chat` são as do pedido "extensões do VS Code/Copilot" — constante única no script, fácil de ajustar.

## Alternatives Considered

- **Dois scripts independentes (sh e PowerShell).** Duplica a lógica de JSON e de plugins em duas linguagens e só um lado seria testável no CI Linux. Descartada: um só Python.
- **Entrar os arquivos em `files` do manifesto.** Faria o `--check` do CI acusar drift porque `.quenching/` não é versionado. Descartada.
- **Um hook de SessionStart que roda o `--check`.** Nada roda sozinho: limite do pedido do humano. Descartada.
- **Editar JSONC preservando comentários.** Risco de corromper o arquivo do usuário; o trecho manual é seguro. Descartada.

## Open Decisions

- none — a lista de extensões do VS Code e os plugins do Claude Code são constantes do script, ajustáveis sem mudar o contrato.

## Risks

- **Windows sem execução em CI Linux.** O ramo `winreg` e o `cq.cmd` não rodam aqui. Mitigação: o código do ramo é guardado por `os.name == "nt"`, a manipulação da lista de PATH é função pura testada, e o conteúdo do `cq.cmd` é teste de texto; o primeiro uso real num Windows é a prova que falta e fica dito no relato.
- **A CLI `claude plugin` muda de forma.** O item falha com mensagem e o resto segue; `--check` não a executa (lê `installed_plugins.json`).
- **Sobrescrever um `~/.local/bin/cq` do usuário.** Listado antes, com backup; um arquivo diferente exige `--write` explícito e o backup precede a troca.

## Handoff

- none — spec de uma sessão; o contexto está no `## Design`.
