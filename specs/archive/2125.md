## Problem

`cq specs release <version>` bumps the version surfaces and regenerates the copies through
`_REGENERATE_STEPS` (plugins/quenching/assets/bin/quenching/specs/release.py:115-123: the Claude
modules, Codex, OpenCode and Omnigent), then commits and tags, promising that `verify_repo.sh` is
green on the tag (docs/standards/ci-cd/versioning-release.md). Since this repository installs its own
surface with `cq deploy` (`.agents/.quenching-deploy.json`) and the gate checks it ("deployed surface
lockstep"), a bump leaves that surface stamped with the old version: release 6.12.0 (commit 18b7ed9)
left 147 files under `.agents/`, `.claude/` and `.opencode/` at "generated by cq deploy 6.11.0", and
CI failed on the release commit at `FAILED: deployed surface lockstep`.

## Proposal

Add a final regenerate step that runs the bundled `plugins/quenching/assets/bin/cq deploy --target .
--write` when the repository holds `.agents/.quenching-deploy.json`, so the release commit carries
the redeployed surface and the tag is green; skip it where the repository has no deploy manifest.
Redeploy this repository's surface at 6.12.0 in the same change, so `main` is green again.

## Out of Scope

- Changing the CI workflow or the `deployed surface lockstep` check itself: the check is right, the release was incomplete.
- Redeploying any repository other than the one being released (`--target .` only).
- Changing what `cq deploy` installs or how it stamps files.

## Impact

### Code
- plugins/quenching/assets/bin/quenching/specs/release.py — the deploy step, guarded by the manifest.
- plugins/quenching/tests/test_specs_release.py — a test that the step runs when the manifest exists and is skipped otherwise.
- The regenerated copies of release.py and the redeployed surface (`.agents/**`, `.claude/**`, `.opencode/**`, plugins/claude/**, codex/opencode/omnigent copies).

### Standards
- docs/standards/ci-cd/versioning-release.md — the list of regenerated copies.

## Validation

- `python3 -m unittest discover -s plugins/quenching/tests -p "test_specs_release.py"` passes.
- `python3 plugins/quenching/assets/bin/cq deploy --target . --check` exits 0 on the final tree.
- `bash scripts/verify_repo.sh` exits 0.

## Design

`_REGENERATE_STEPS` entries today are `(name, argv)`, and `regenerate_copies` skips a step whose
`argv[0]` file is absent. Each entry gains an optional third element: the guard paths, all of
which must exist under the repository for the step to run. It defaults to `(argv[0],)`, so the
four existing steps behave exactly as before.

The new last step is `("deploy_surface", ("plugins/quenching/assets/bin/cq", "deploy", "--target",
".", "--write"), ("plugins/quenching/assets/bin/cq", ".agents/.quenching-deploy.json"))`, run with
`sys.executable` like the others. It runs after the module and package generators, so the deployed
surface copies sources that already carry the new version. A non-zero exit fails the release
through the existing `sp-release-regenerate-failed` path (bump uncommitted, no commit, no tag), and
the `git add -A` that follows already stages whatever the deploy rewrote.

Tests in `test_specs_release.py` (`CmdReleaseCommit` fixture): a stub `plugins/quenching/assets/bin/cq`
that writes a marker runs when `.agents/.quenching-deploy.json` is committed, and does not run
when it is absent.

## Alternatives Considered

- **A CI step that redeploys after the tag**: rejected, since the tag would still point at a red commit, and the standard promises `verify_repo.sh` is green on the tag.
- **Having `cq specs release` refuse when the surface would drift**: rejected, since it would only report the problem, and the maintainer would still have to run the deploy by hand.
- **Guarding on the script file like the other steps**: rejected, since the bundled `cq` exists in every checkout of this repository, including ones without an installed surface. The manifest is what says a surface was deployed.

## Open Decisions

- none — the evidence settles the guard, the order and the failure path (see `## Design`)

## Risks

- **Mode-only drift under umask 0002**: the deploy write normalizes file modes, so a lockstep report with only `"change": "mode"` entries is fixed by re-running the write before committing.
- **A deploy that fails mid-release**: leaves a partially rewritten surface in an uncommitted tree. This is the same contract as a failing generator today: no commit, no tag, and the maintainer inspects the tree.
- **Release time grows** by one `cq deploy` run (seconds).
