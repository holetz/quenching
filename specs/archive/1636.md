## Problem

The plugin has no list of what an open source project needs, or which front owns each item. A new front could duplicate what security, delivery, toolchain, knowledge and proof already measure, or leave gaps.

Public references overlap: OpenSSF OSPS Baseline 2026.08.28 has eight families (AC, BR, DO, GV, LE, QA, SA, VM) and three maturity levels; OpenSSF Scorecard includes branch protection, token permissions, pinned dependencies, security policy, licensing, signed releases, SAST, dependency updates and binary artifacts. GitHub community profiles cover README, license, conduct, contribution and security policies and contribution templates. REUSE covers per-file licensing and copyright using SPDX. Contributor Covenant, DCO, Keep a Changelog/SemVer, CITATION.cff and FUNDING.yml supply additional conventions.

A versioned, machine-readable catalog is missing: each control needs its OSPS ID and applicable levels, related references, the evidence that answers it, whether it can be measured without a provider, and exactly one front or pillar owner. Epic 1627 Design D5 supplies the initial allocation. A verifier must reject missing or multiple owners. Baseline version and date belong in the data because upstream changes over time. Primary-source inspection resolves the capture's approximate count into 41 controls and a separate assessment-requirement inventory, including retired requirements.

## Proposal

Ship an offline JSON catalog and pinned OSPS assessment inventory, with one scalar owner per control, explicit evidence and provider dependencies, related external references, and a deterministic checker integrated into the repository gate. This is shared data for specs 1637, 1638 and 1639, not a new assessment front.

## Out of Scope

Do not implement opensource commands, maturity scoring, provider access, target alignment, community files in this repository, module extraction, or new features in security, delivery, toolchain or proof. Do not choose the final front name or dogfood level. Do not treat related framework references as proof of equivalent compliance.

## Design

Store one record per OSPS control and embed its assessment requirements with exact applicability and active/retired state. A separate source snapshot freezes only IDs, levels, states and family-source SHA-256 digests at tag v2026.08.28; do not copy the normative requirement prose. The checker compares catalog coverage and applicability against this snapshot. Sources carry authoritative URLs, versions where available, and inspection dates; moving Scorecard/GitHub references are inspection snapshots, not release claims.

Each catalog record has one scalar owner from opensource, security, delivery, toolchain, knowledge, proof or git; evidence distinguishes local artifacts from provider assertions and human interpretation. Per-requirement provider flags handle mixed controls such as CI permission defaults and workflow permissions. Missing provider data must remain not-measured; a file's existence is never proof of the complete requirement. Retired requirements remain visible and are excluded from active maturity evaluation by future consumers. Optional conventions have no OSPS level unless linked to a real OSPS requirement.

Follow epic D5's allocation: LE/GV opensource; VM, AC-04, BR-01/07 security; BR-02..06 delivery; QA-02/05 toolchain; QA-06 proof; DO/SA knowledge; AC-01..03, QA-03/07 git. Assumption: QA-01 (public code/history) belongs to git and QA-04 (security requirements on auxiliary code) to security, completing D5's omitted rows by subject. This only routes metadata. Reuse related framework references on the matching control; add supplemental records when no OSPS control covers the practice, without claiming exact equivalence. The verifier owns schema and routing integrity, not whether a target complies.

## Alternatives Considered

A prose-only table cannot enforce owner cardinality or stable requirement IDs. Loading upstream over the network in every gate would make validation nondeterministic. Flattening controls and requirements loses exact level applicability and retired state. Reusing existing front probes now would cross the reserved 1638 decision. Separate JSON routing plus a frozen identifier snapshot supplies offline integrity without implementing assessment.

## Open Decisions

- The owner must decide in spec 1638 whether frozen non-core fronts receive new checks; until then only this catalog metadata names their intended owners.
- Spec 1637 decides the new front's final name and consumption interface; opensource remains the provisional owner ID from epic D5.
- Spec 1640 decides the dogfood maturity target. Catalog membership alone does not impose any maturity level or optional convention on targets.
- Primary-source matching of related frameworks remains interpretive; future consumer development must decide any stronger equivalence or scoring rules from requirement evidence.

## Risks

Upstream changes can invalidate mappings: pin baseline version, source digests, requirement state and levels, and validate offline. File-presence evidence can overclaim compliance: document assessment criteria and human/provider requirements explicitly. Some D5 families contain mixed evidence: provider dependency is recorded per requirement. Optional conventions must not silently become baseline obligations. Catalog routing to a frozen front grants no exception to its maintenance policy.
