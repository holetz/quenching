## Problem

Medido no autopilot 2026-11-25, épico 483 (16 merges em série): os PRs #493 (281, duas vezes), #498 (341), #506 (467), #508 (299) e #510 (473) ficaram DIRTY depois do merge de um irmão, quase sempre em `.agents/.quenching-deploy.json` e no bloco gerado de `quenching/README.md`; o GitHub não roda CI num PR em conflito, então cada um esperou um slot e um spawn de runner só para `merge origin/main` + regenerar — o orchestrator contou ~8 spawns extras (de ~45 no épico). A spec 354 (arquivada, épico 358) deveria ter eliminado o conflito do manifesto entre PRs paralelos; a 499 (#516) cobre só a perda do `opencodeConfig` no lado da base, não o conflito em si.

Consequência: custo de tokens e de relógio proporcional ao número de membros do épico (cada merge invalida todos os PRs abertos), e merges após sync sem verifier novo (281, 299, 467, 479 no relatório do orchestrator).

Pista a provar no develop: o que a 354 entregou (merge driver? manifesto sem campo volátil?) e por que o README gerado e o manifesto ainda divergem a cada merge; medir com dois PRs que só regeneram o deploy.

## Proposal

Tirar dos dois arquivos gerados o valor que muda em ambos os lados de quase todo par de PRs, sem merge driver, sem `.gitattributes` e sem hook:

1. **Manifesto do deploy (`.agents/.quenching-deploy.json`).** Quando o alvo é a própria fonte do plugin (carrega `quenching/assets/modules.json`), cada entrada de `files` registra o valor fixo `"source"` no lugar do sha256 do arquivo gerado. O conjunto de arquivos possuídos continua o mesmo; só o valor deixa de variar com o conteúdo, então dois PRs que mudam o mesmo arquivo deixam a linha idêntica dos dois lados. `_edited` lê `"source"` como edição desconhecível (o mesmo caminho de uma entrada sem hash: `update`). Alvos comuns seguem com o sha256 e a detecção de edição em três vias.
2. **Bloco gerado do README de prova (`quenching/README.md`).** O bloco deixa de carregar a contagem `Test modules: N` e o digest deixa de incluir `tests`/`testPaths`: o bloco passa a refletir só as declarações (camadas, alcance, orçamento, obrigatoriedade, fixtures e o contrato de custo), que mudam raramente.

## Out of Scope

- Merge driver em `.git/config`, `merge=` em `.gitattributes` ou hook novo — superfície que executa código; o épico 524 manda parar com needs-human se o desenho exigir, e este não exige (o GitHub também não roda driver customizado ao calcular a mesclabilidade).
- O manifesto do bridge (`.claude/skills/.generated-files.json`): conflitou 2 vezes em 150 syncs; fica como discovery.
- Conflitos reais nos arquivos-fonte e nas cópias implantadas deles (≤3 por arquivo em 150 syncs): são conflitos de conteúdo, não de valor derivado.
- O fluxo de sync do conclude para zonas geradas (`conclude.md` §mechanical conflicts) — continua válido para o que sobrar.

## Validation

- Medido no develop (2026-11-25), `git merge-tree --write-tree` sobre os pais dos 150 últimos merges `Merge remote-tracking branch 'origin/main'` de `origin/main`: 54 conflitos em `.agents/.quenching-deploy.json` e 26 em `quenching/README.md`, contra ≤3 em qualquer outro arquivo. Todo hunk do README é a linha `quenching-proof-readme-sha256` (52) ou `- Test modules: N` (30); todo hunk do manifesto é uma linha `"<path>": "<sha256>"` de um arquivo mudado dos dois lados (top: `.claude/skills/.generated-files.json` 11, `deploy/cli.py` 11, `plugin-configuration.md` 9).
- Teste: para um alvo com `quenching/assets/modules.json`, o manifesto construído tem os mesmos bytes antes e depois de mudar o conteúdo de um arquivo-fonte; para um alvo comum, segue o sha256. `_edited` devolve `False` para `"source"`.
- Teste: acrescentar um módulo de teste a uma camada não muda o bloco gerado do README; mudar uma declaração de camada ou o contrato de custo continua mudando.
- Superfície real: `python3 quenching/assets/bin/cq deploy --target . --check` e `python3 quenching/assets/bin/cq proof readme --check` saem 0 depois do `--write`.
- Remedição no execute: dois commits soltos (`git commit-tree`, sem ref) que mudam o mesmo arquivo de `quenching/references/` em lados diferentes e regeneram o deploy fazem `git merge-tree` sem conflito no manifesto.

## Design

### Causa (medida)
A 354 entregou `dumps_hash_manifest`: uma linha em branco entre as entradas de `files`, de modo que mudanças em arquivos diferentes não sejam vizinhas. Isso não cobre o caso dominante: os dois PRs mudam o **mesmo** arquivo implantado (os hunks do arquivo se mesclam limpos, mas o sha256 dele difere em cada lado). Arquivos agregados agravam: `.claude/skills/.generated-files.json` muda sempre que qualquer skill muda. No README, o digest inclui `testPaths` e a linha `Test modules: N` muda a cada teste novo — e dois PRs que acrescentam um teste cada se mesclam limpos com a contagem errada (209→210 dos dois lados), deixando a main com `pf-readme-stale`.

### Desenho
- `tree.py`: `SOURCE_DERIVED = "source"` e `self_hosted(target)` = `(target / "quenching" / "assets" / "modules.json").is_file()` — critério pelo alvo, não por qual cópia do `cq` roda, para que o deploy pela fonte e pela cópia vendorizada escrevam o mesmo manifesto. Em alvo hospedado, `document["files"] = {rel: SOURCE_DERIVED for rel in sorted(tree)}`.
- `cli.py`: `_edited` devolve `False` quando o registrado é `SOURCE_DERIVED`. `_recorded_hashes` já aceita qualquer string, então o conjunto possuído não muda. O `--check` segue pegando cópia velha pelos bytes (`_same`), que é o que o gate usa.
- `proof/readme.py`: `_layers_payload` sem `tests`/`testPaths`; `render_readme_block` sem `Test modules`.

### Assumptions
- Na fonte hospedada, editar uma cópia gerada à mão nunca é trabalho a preservar (o cabeçalho diz "edit the source, not this file") — `## Risks`.
- A contagem de módulos de teste no README não é lida por nenhuma ferramenta (grep em `quenching/`, `scripts/`, `docs/`: só o próprio gerador) — `## Proposal` item 2.

## Alternatives Considered

- **Merge driver (`.gitattributes merge=` + `.git/config`)** — recusado: executa código, fica fora da autorização do épico e o GitHub não o usa para calcular a mesclabilidade, então o PR continuaria DIRTY.
- **Manifesto sem hash para todo alvo** — recusado: a detecção de edição em três vias protege o trabalho de quem edita uma cópia num alvo comum.
- **Hash do arquivo-fonte em vez do gerado** — recusado: muda nas mesmas condições.
- **Resolver o sync no próprio orchestrator, sem spawn** — não elimina o DIRTY nem o CI parado; só barateia. Fica possível depois, se sobrar conflito.

## Open Decisions

- none — o desenho é resolvido pela medição e pelo código; nada depende do humano

## Risks

- Na fonte hospedada, uma edição manual numa cópia gerada passa a aparecer como `update` (não `edited`) e o `--write` a sobrescreve; o `--check` do gate continua reprovando. `--remove` aqui apagaria a cópia editada. Aceito: o repositório-fonte nunca guarda trabalho nas cópias.
- Um alvo que por acaso tenha `quenching/assets/modules.json` sem ser a fonte perde a detecção de edição. Improvável; o caminho é o layout da fonte (`docs/standards/architecture/source-layout.md`).
- O primeiro `--write` reescreve as 552 linhas do manifesto: um PR irmão aberto antes do merge conflita uma última vez.
