## Problem

`cq git stale` reports orphaned worktrees in exactly one direction.
`plugins/quenching/assets/bin/quenching/git/stale.py:52-66` (`_orphan_worktrees`) walks
`git worktree list --porcelain` and keeps the entries whose `path` is not a directory on disk —
**git remembers it, the directory is gone**. That is the harmless direction: nothing was lost, and
the remedy (`git worktree prune`, which `/quenching:git:cleanup` performs) is a registry tidy-up.

The direction that loses data is the opposite one: **the directory is on disk, git no longer
registers it.** It holds every ignored file that was ever written there — the venv, the build
output, and the irreproducible material that motivates the two sibling specs — and no command of
the repository can see it. `git status` does not reach it, no glob covers it, and `cq git stale`
reports the repository as clean.

This is measured, not hypothetical. `~/.claude/plans/estamos-com-um-problema-warm-floyd.md`
records a live repository in exactly this state: `<repo>.worktrees/refactor-schemas-bundle`,
already absent from `git worktree list`, holding **4.2 GB** in `notebooks/`, plus a second such
directory at 70 MB. Both were found by inspecting the filesystem by hand, which is the only way
they can be found today.

The way in is ordinary: a human deletes a worktree directory with `rm -rf` and later runs
`git worktree prune` — or `/quenching:git:cleanup` runs it — and the registry entry disappears
while a *sibling* directory, deleted incompletely or recreated, stays behind. After the prune, the
common repository holds no record at all; the only remaining evidence is inside the orphan itself,
in the `.git` file whose `gitdir:` still points back.

## Proposal

Extend `cq git stale` with a second worktree class and report it distinctly.

**The detection is exact, not heuristic.** A directory is an unregistered worktree of *this*
repository when it contains a `.git` **file** (not a directory) whose `gitdir:` line resolves under
this repository's own `git rev-parse --path-format=absolute --git-common-dir`, and whose path is
absent from `git worktree list --porcelain`. No name matching, no guessing: the orphan itself
carries the pointer that identifies its parent. The absolute path format is required — the bare
form returns a relative `.git` from the primary checkout, which no comparison can use.

**The scan set is the repository's siblings** — the directory holding the common `.git`, one level
— because that is where this plugin puts worktrees by its own contract
(`assets/references/git/isolation.md`: "A worktree goes beside the repo, never inside it",
`git worktree add ../<repo>-<handle>`). A worktree a human placed elsewhere is out of reach of a
bounded scan, and saying so plainly beats an unbounded one.

**The report carries what makes the finding actionable**: the path, the branch the `.git` file's
`gitdir` resolves to where readable, and the **directory's size on disk** — 4.2 GB and 40 KB are
the same finding structurally and completely different decisions for the human.

**It stays a report, and this class is reported without an action.** `git/__init__.py`'s docstring
fixes the first half: the `git` pillar has "no `doctor` and no `validate`", and `stale.py`'s own
header says "a REPORT only". The second half is specific to this class and is the correction the
refine pass made: **the new class does NOT join `/quenching:git:cleanup`'s prune multi-select.**

Two independent reasons, both measured:

- `git worktree remove <path>` (`commands/git/cleanup.md:44-48`, the only worktree verb that command
  has) operates on a **registered** worktree. Against a directory git does not know, it fails — so
  offering the class for selection buys the human a confusing refusal and an invitation to reach for
  `--force`.
- The premise of the finding is that the directory may hold the only copy of something. Reclaiming
  it is a human act with a human's own `rm -rf`, after they looked.

What `/quenching:git:cleanup` gains instead is the **report row and its stop condition**.
`cleanup.md:25` currently reads "All three lists empty → say so and stop"; with a fourth list that
sentence makes the command stop silently while holding a finding. It becomes four lists, and the
new one is printed even when nothing is prunable.
## Out of Scope

- **Deleting, archiving or merging what is found.** The report ends at naming the path, its branch
  and its size. Reclaiming the content is the human's, on the human's word.
- **Registering the orphan back as a worktree.** `git worktree add` against an existing directory
  and repairing `.git/worktrees/<name>` is a recovery procedure with its own failure modes and no
  demonstrated demand.
- **Unbounded filesystem search.** No `find /`, no configurable root list in this spec. See §Open
  Decisions for the one case that argues for widening it.
- **Any change to the registered-but-missing class.** It keeps its current shape and its current
  key in the JSON.

## Design

### Why the `.git` file's `gitdir` and nothing else

Three weaker tests were available. Name matching (`<repo>-*`) breaks the moment anyone renames a
directory and produces false positives on unrelated siblings. Presence of a `.git` entry alone
cannot distinguish a worktree from a clone. Reading `.git/worktrees/**` in the common repository
finds nothing, because a prune is what removed those entries and a prune is the normal way this
state is reached. The `gitdir:` pointer is the only artefact that both survives the prune and names
the parent, and matching it against `--git-common-dir` makes the attribution exact.

### Why size is part of the finding, not a follow-up

The action a human takes differs by three orders of magnitude of content, and the number is one
`du -s` away at the moment the path is already known. A finding that makes the human run a second
command to decide anything is a finding that gets ignored.

### Why this is not a `doctor`

The `git` pillar answers questions git already has answers for; it converges nothing and has no
artefact to validate — `git/__init__.py`'s own docstring, and the reason spec 1057 records for the
pillar having no align. An unregistered directory is a fact about the filesystem, not drift from a
declared form. It is a row in a report, and the report already exists.

## Alternatives Considered

- **Fold it into the existing `orphanWorktrees` list with a `reason` field.** One list is simpler to
  render, and it is wrong: the two conditions have opposite remedies — prune the registry versus
  do not touch the directory until a human decides — and a consumer branching on a string inside a
  shared list will eventually treat "may hold your only copy" as "safe to prune".
- **Detect it in `/quenching:git:cleanup` instead of in `cq git stale`.** Rejected on the pillar's
  existing split: `stale` reports, `cleanup` acts on what it reported. Detection in the command body
  would be logic no test can reach.
- **Warn at worktree-removal time instead of reporting after the fact.** Worth doing and not
  sufficient: the directories that already exist were created by paths this plugin does not control
  (`rm -rf` by hand, an external tool, a crashed process), and a warning cannot find them.

## Open Decisions

- **Whether the scan follows a wider root than the repository's siblings.** The motivating
  repository keeps its live worktrees under `~/orca/workspaces/<repo>/<slug>`, which a sibling scan
  never reaches — so the bounded scan would have found one of that plan's two orphans, not both.
  Widening means either a declared list of roots (another configuration key) or reading the host
  tool's own configuration, and neither is obviously worth it for a report.
- **Whether size is computed always or behind a flag.** `du -s` on a 4.2 GB tree is fast on a warm
  cache and can be slow on a cold one over a network mount, and `cq git stale` is called in flows
  where latency is noticed.
- **What the JSON key is called.** `unregisteredWorktrees` describes the mechanism;
  `abandonedWorktrees` describes the consequence. The key is consumed by `/quenching:git:cleanup`
  and is cheap to change only before that consumer ships.

## Risks

- **A false positive invites a destructive action.** The finding's whole purpose is to point a human
  at a directory holding unique content; pointing at the wrong directory in a report that leads to
  a cleanup command is the dangerous failure. The exact `gitdir`-matching test and the three
  negative fixtures are the mitigation, and the class carries no action at all.
- **A reported directory may be in active use by another session.** An agent or a human working in a
  checkout that was unregistered mid-flight sees it reported as abandoned. Mitigation is the same
  one: no action is offered, so the worst case is a confusing row rather than a deletion. Reporting
  the most recent mtime alongside the size would help and is not required for this spec.
- **The scan runs where the repository has many siblings.** A checkout inside a large workspace
  directory means stat-ing every sibling. Bounded to one level and to a `.git` entry check, this is
  cheap, but it is not free and it grows with the parent directory. `cq git stale` is called in
  flows where latency is noticed.
- **Reporting a directory does not make it recoverable.** The branch a `gitdir` names may be long
  gone, so the content is identifiable but no longer attributable to any work. That is inherent to
  finding it late, and it is the argument for the two sibling specs, which prevent the loss rather
  than reporting it.
- **Accepted: the bounded scan will miss worktrees placed outside the repository's siblings.** The
  motivating repository keeps live worktrees under `~/orca/workspaces/<repo>/<slug>`, so the scan
  would have found one of that plan's two orphans, not both. Widening means a declared list of roots
  — another configuration key for a report — and the bounded scan covers exactly what this plugin
  itself creates. Recorded as a limitation the report states in its own output, so a human reading
  "none found" knows what was searched.
