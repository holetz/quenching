## Problem

`proof-front-contract` publishes eleven finding codes and a two-part contract, and nothing can run
either. As with `ops`, the align surface's probe rule means the front cannot have an align until a
program answers "is there work?" with an exit code.

This front's verifier faces a constraint the `ops` one did not. Three of its eleven codes are about
*numbers a run produces* — coverage over a measured surface, a floor that must only rise, an
order-independence pass that either happened or did not. The obvious implementation runs the target's
suite. On the measured target that is 21.5 seconds today and unbounded tomorrow, it requires the
target's full environment, and it makes a read-only verifier the most expensive thing in the plugin.
Worse, a probe that runs the suite fails the very rule it exists to serve: the no-op case must cost a
couple of tool calls.

So the verifier has to be split, and the split has to be principled rather than a workaround.

## Proposal

Add `proof` as the seventh route in `assets/bin/cq`, with four subcommands and one hard rule
dividing them: **`doctor` grades the gate's configuration and the suite's shape; it never runs the
suite. `ratchet` grades a run's output, and only ever reads an artifact a run already produced.**

**`cq proof inventory [--json]`** — the read model: the declared proof root, the declared layers with
their reach and budget, every test module with its layer, every fixture with where it is defined,
the `conftest.py` files with what they hold, the gate's declared configuration
(`addopts`, markers, `--strict-markers`, coverage source and floor), and the CI definitions that
invoke it.

**`cq proof doctor [--json]`** — the eight configuration-and-shape codes over that inventory:
`pf-unlayered`, `pf-unmarked`, `pf-loose-fixture`, `pf-fat-conftest`, `pf-unmeasured-surface`,
`pf-no-floor`, `pf-stop-first`, `pf-empty-layer`, plus `pf-no-ci` and `pf-order-unproven`, which are
also decidable from the CI definition without running anything. Exit `0`/`1`/`2`, the frozen `cq`
contract.

**`cq proof ratchet [--check|--raise] [--json]`** — reads a coverage artifact the target's own gate
produced (`coverage.json`, or `.coverage` via `coverage json`), compares each measured root against
its floor, and either reports (`--check`, the CI gate) or raises the floor to the achieved value
(`--raise`, never downward). A floor never falls; `--raise` on a regression is a refusal, not a
lowering.

**`cq proof status [--json]`** — the fold: layers with test counts and budgets, fixture-library
health, measured roots with floors and last achieved values, and findings by code.

`pf-untested-entrypoint` fires only where `ops` is configured, consuming `cq ops inventory` rather
than re-deriving what an entry point is.

## Out of Scope

- **Running the target's test suite, ever, in any subcommand.** `ratchet` reads an artifact; it does
  not produce one.
- **Any command body.** `commands/proof/**` is the next two specs'.
- **Writing anything into a target**, except the ratchet file under `--raise`, which is the one
  write this pillar owns and the one the CI gate needs.
- **Auto-fixing findings.** No `--fix`.
- **Parsing test *bodies* for assertion quality.** Whether a test asserts anything meaningful is out
  of reach of a static check and belongs to review; the front grades shape and gates.
- **Supporting test runners other than pytest.** The contract's rules are stated over pytest
  constructs; a repository using something else gets a refusal that says so.

Verified when:

1. On a fixture tree violating each code, `doctor` reports exactly those codes; on the conformant
   tree it reports none and exits `0`.
2. Every code carries a mutation proof — the tripping fixture, minimally corrected, stops tripping —
   per `/docs/standards/quality/selftest-mutation.md`.
3. **No subcommand runs the suite:** a test patches `subprocess.run`, `os.system` and
   `importlib.import_module` to raise, then runs `inventory`, `doctor`, `ratchet --check` and
   `status` against a fixture target, and none raises.
4. `ratchet --raise` on a higher value writes the higher value; on a lower value it refuses with
   exit `1` and leaves the file byte-identical. Proven by a property test over a random sequence of
   values: the floor is non-decreasing for every ordering.
5. `pf-untested-entrypoint` is silent, and says it is silent, on a target where `ops` is not
   configured — asserted rather than assumed.
6. Run against `databricks-risco-gold`, the doctor reproduces the nine measured facts in
   `proof-front-contract`'s `## Problem`, and every code's fire rate over the 108 test modules is
   recorded in `## Discoveries`.
7. The four payloads match their golden fixtures byte for byte, and `cq --version` still equals
   `VERSION`.

## Design

**The split is the design.** `doctor` answers questions whose evidence is in files: is `--maxfail`
in `addopts`, is there a floor, is every marker registered, does a CI definition invoke the gate,
does any invocation randomize order. `ratchet` answers the one question whose evidence is a run's
output, and it consumes that output rather than producing it. Neither ever executes the target's
tests. This keeps the probe cheap, keeps the verifier runnable in a checkout with no environment,
and keeps the front honest: it never claims a suite passes, only that the gate is shaped to mean
something when it does.

**How each code is decided:**

| Code | Decided by |
| --- | --- |
| `pf-unlayered` | a test module under the proof root inside no declared layer directory |
| `pf-unmarked` | a derived marker absent from `[tool.pytest.ini_options].markers`, or `--strict-markers` not set |
| `pf-loose-fixture` | AST: the same fixture name defined in two or more test modules |
| `pf-fat-conftest` | AST: a `@pytest.fixture` defined in a `conftest.py` that is not the fixture library |
| `pf-unmeasured-surface` | a source root the project declares that the coverage configuration does not name |
| `pf-no-floor` | coverage configured with no `fail_under` and no `--cov-fail-under` |
| `pf-stop-first` | `--maxfail` present in `addopts` |
| `pf-order-unproven` | no discovered invocation passes a randomizing plugin or seed |
| `pf-no-ci` | no CI definition invokes the gate |
| `pf-empty-layer` | a declared layer directory holding no test module |
| `pf-untested-entrypoint` | an `ops` entry point that no test module imports — conditional on `ops` being configured |

**Why `pf-loose-fixture` is about duplication and not about sharing.** The contract's first wording
said "a fixture used by more than one module". pytest cannot do that: a fixture defined in a test
module is visible only inside it. So the defect the rule was reaching for never appears as sharing —
it appears as a **copy**, the same fixture name written out in two or three modules because there was
nowhere to put it once. That is decidable by AST and it is exactly the shape the measured target's
40 scattered fixtures are in. The contract's rule 4 was corrected to say so before this spec was
written.

**Why the ratchet is a separate artifact and not a number in configuration.** A floor stored in
`pyproject.toml` is edited by whoever is annoyed by it, in either direction, and the history of that
edit is buried in unrelated diffs. A dedicated file with one job makes every movement a visible,
reviewable, one-line change — and makes "it only ever went up" a property a test can assert.

**Why `--raise` refuses on a regression rather than lowering.** Lowering is a decision with a reason,
and a tool that does it silently converts a regression into a new normal. Refusing puts the decision
where it belongs: a human edits the file, and the diff records that they did.

**Why CI detection is its own module.** Recognizing a gate invocation across GitHub Actions, Azure
Pipelines, GitLab CI and a pre-commit configuration is pattern work that will keep growing, and it is
the part most likely to be wrong on a repository nobody anticipated. Isolating it means
`pf-no-ci`'s false negatives are one module's problem and the other ten codes are unaffected.

**Why the no-execution invariant is asserted by a test.** Same reasoning as the `ops` doctor's, with
a sharper edge: here the temptation is real and specific — one `subprocess.run(["pytest", ...])` would
make three codes trivial. The test that patches `subprocess.run` to raise is what makes that
temptation fail loudly.

## Alternatives Considered

- **Run the suite once and derive everything from the result.** Rejected: it breaks the probe rule,
  needs the target's environment, and makes the verifier's cost the suite's cost — on a repository
  whose suite is slow, the front becomes unusable exactly where it is most needed.
- **Fold `ratchet` into `doctor` and read the coverage artifact opportunistically.** Rejected: it
  makes `doctor`'s output depend on whether somebody happened to run the suite recently, so the same
  command gives different answers on the same tree. The split is what makes both deterministic.
- **Store the floor in `pyproject.toml` under `[tool.coverage.report] fail_under`.** Rejected under
  §Why the ratchet is a separate artifact — though the front still *reads* that key, because a
  repository that has one is declaring a floor and `pf-no-floor` must not fire on it.
- **Detect order-independence by running the suite twice with different seeds.** Rejected: it is
  execution, and it is the most expensive possible form of it. What the front can decide is whether
  the gate ever asks for randomized order, which is the actual contract rule.
- **Make `pf-untested-entrypoint` unconditional and report every entry point as untested when `ops`
  is unconfigured.** Rejected under `/docs/standards/quality/empty-response-honesty.md`: a check that
  never looked must say so, not report a clean or a dirty result it did not measure.

## Open Decisions

- **Where the ratchet file lives.** Carried from the contract spec. Resolved at task 1 against what
  the config loader reads without a second parser, with `<proofRoot>/../.coverage-floor.json` and a
  key inside `.claude/quenching.json` as the two candidates.
- **What counts as "the fixture library" for `pf-fat-conftest`.** A `fixtures/` package is the
  declared shape, but `fixtures/conftest.py` is a legitimate place for fixtures. Resolved at task 3
  by exempting conftest files *inside* the library and no others.
- **Whether `pf-unmeasured-surface` reads the project's declared packages or the repository's
  top-level source directories.** The measured target declares `safra` and ships four more source
  trees, so the two answers differ by everything that matters. Resolved at task 2, against which
  answer reproduces the measured fact without needing a hand-maintained list.
- **Whether a repository using a non-pytest runner gets a refusal or a partial report.** Resolved at
  task 2; the bias is refusal with a message naming the constraint, since a partial report over
  rules stated in pytest terms would be a report about nothing.

## Risks

- **CI detection will be wrong on some repository.** *Mitigation:* `ci.py` is isolated so the blast
  radius is one code, `pf-no-ci` carries the paths it searched so a human sees immediately what it
  missed, and the align's spec puts CI wiring in the judgement band where a false negative costs a
  report line rather than an unwanted change.
- **The measured target has no CI at all, so `pf-no-ci` cannot be proven against a true negative
  there.** *Mitigation:* the fixture set carries a conformant CI definition for each of the four
  providers, and task 4 records which providers are proven and which are pattern-only.
- **`pf-unmeasured-surface` could fire on directories that are deliberately unmeasured** — vendored
  code, generated code, a notebooks tree. *Mitigation:* configuration carries an exclusion list, the
  finding names it, and the exclusion is a declaration the repository makes rather than a heuristic
  the tool applies.
- **The ratchet's `--raise` writes into the target.** It is the only write in the pillar.
  *Mitigation:* it is upward-only, it refuses on regression, the property test pins monotonicity over
  random orderings, and the file's whole content is one object a human can read at a glance.
- **Two new pillars land in the same `PILLARS` table and the same golden-fixture directory.**
  *Mitigation:* the `ops` specs land first by dependency, and this spec's task 1 updates the
  pillar-count assertion against whatever is there rather than against a remembered number.
