## Problem

Os checkers de capabilities e catálogo protegem somente uma parte da forma declarada: capability desconhecida vira no-op e o catálogo não verifica unicidade, rotas ou valores úteis de lineage. Fixtures saudáveis isoladas não impedem essas regressões.
## Proposal

- Fortalecer o checker de catálogo para validar unicidade dos links, rotas existentes e os campos de lineage contra valores não vazios e coerentes.
- Fortalecer o checker de capabilities para rejeitar nomes desconhecidos e exigir o efeito HTML declarado de toda capability habilitada.
- Adicionar fixtures negativas que demonstram cada falha sem depender do site real.
- Integrar os self-tests ao gate de CI da spec 1024.

## Out of Scope

- Inventar novas capabilities do Zensical.
- Alterar o schema ou os dados do catálogo para fazer um fixture passar.
- Validar conteúdo semântico livre das descrições; o checker protege a forma e a linhagem declaradas.

## Design

O catálogo de capabilities é fechado no dicionário EXPECTED: nome fora dele é erro, não silêncio. Cada capability conhecida conserva seu token de efeito HTML e o checker avalia o conjunto de HTMLs gerados.

O checker de catálogo deve normalizar links relativos a partir do índice, rejeitar links duplicados e exigir que cada detalhe contenha campos REQUIRED com valores não vazios. A lineage deve apontar para uma origem existente ou para o marcador de origem permitido pelo contrato; nenhuma validação deve aceitar um detalhe meramente porque contém os nomes das chaves.

## Alternatives Considered

- Manter nomes desconhecidos como no-op — rejeitado porque uma configuração inválida pareceria suportada.
- Exigir somente a presença textual das chaves — rejeitado porque não prova rotas nem lineage.
- Testar apenas o fixture saudável — rejeitado porque não protegeria os achados que motivaram a spec.

## Open Decisions

- none — o catálogo EXPECTED existente e a lista REQUIRED existente continuam sendo as autoridades, apenas com validação mais forte.

## Risks

- Fixtures atuais podem revelar contratos históricos incompletos — mitigado corrigindo a fixture fonte ou documentando explicitamente o valor permitido.
- Checagem excessiva de lineage pode rejeitar conteúdo legítimo — mitigado limitando-a às rotas relativas declaradas e aos campos requeridos.
- O espelho Codex pode ficar atrasado — mitigado pelo gate de sync.

## Discoveries

- O checker de catálogo recusava a ausência de reference/catalog/index.md, mas o standard do bundle permite que repositórios sem dados não tenham catalog/. A ausência deve ser válida por padrão e a exigência deve ser uma opção explícita.
