## Problem

O campo body dos gêneros promete Markdown compatível, mas o renderer atual transforma tudo em texto escapado e perde listas, tabelas, ênfase, links, código e títulos. Isso torna o conteúdo editorial principal inconsistente ou inutilizável nas mídias HTML e Typst.

## Proposal

- Parse the supported CommonMark subset once into deterministic blocks and inline nodes.
- Render the same body value as equivalent safe HTML or Typst markup, covering headings, paragraphs, emphasis, links, inline/code blocks, unordered and ordered lists, and pipe tables.
- Keep non-body fields escaped as plain text while making a `read` genre's Markdown body semantic instead of decorative.

## Out of Scope

- Full CommonMark compliance, raw HTML passthrough, arbitrary Typst execution, footnotes, plugins, or network fetching.
- Replacing Markdown in the knowledge front; this parser serves editorial genre bodies only.
- A browser or Typst process in the parser itself.

## Impact

- `plugins/quenching/assets/bin/quenching/design/markdown.py` — block/inline parser and dual renderers.
- `plugins/quenching/assets/bin/quenching/design/genre.py` — body dispatch and register-aware rendering.
- `plugins/quenching/tests/test_design.py` — equivalent HTML/Typst fixture coverage.
- `docs/standards/code/canonical-set-parsing.md` — deterministic membership and parser boundary.
- `docs/standards/architecture/design-front.md` — one genre, multiple destinations.

## Validation

- A body containing each supported construct renders to semantic HTML tags and valid Typst constructs, with no escaped Markdown punctuation.
- Literal text containing HTML/Typst metacharacters remains escaped when it is not Markdown syntax.
- Link destinations are escaped and restricted to safe relative, `http`, and `https` URLs.
- The same fixture renders without unresolved placeholders in both media; the existing genre and golden tests remain green.

## Design

- `parse_markdown` returns a small immutable-friendly AST of blocks; inline parsing is performed only inside text-bearing blocks. Blank lines delimit paragraphs, ATX headings use levels 1–6, fenced backticks create code blocks, and a contiguous pipe row plus delimiter row creates a table.
- HTML uses escaped text, `<strong>`, `<em>`, `<a>`, `<code>`, `<pre><code>`, `<ul>/<ol>/<li>`, `<hN>`, and `<table>`; no raw HTML is emitted.
- Typst uses escaped text, `#strong`, `#emph`, `#link`, `#raw`, heading syntax, list markers, and table syntax. Code blocks become `#raw(block: true)[...]`.
- The renderer rejects malformed links/tables into plain escaped text instead of guessing. The parser is deterministic and has no external dependency.
- `register: read` selects Markdown body rendering; other register values retain plain-field semantics unless they explicitly supply a body contract. Generated templates still call the same body placeholder.
- Dependency map (2026-08-30): `markdown.py` owns AST and escaping → `genre.py` selects it for body fields and keeps scalar fields escaped → `test_design.py` exercises both adapters; `build.py` is untouched because generated projections do not contain body content.

## Alternatives Considered

- Escaping the complete body and documenting Markdown as unsupported: rejected because it preserves the defect.
- Adding a third-party Markdown dependency: rejected because output stability and installation footprint matter for a plugin.
- Rendering HTML and converting HTML to Typst: rejected because it introduces an unbounded intermediate dialect and loses deterministic control.

## Open Decisions

- none — the supported syntax, safety boundary, and dual output forms are fixed; implementation may choose internal node classes without changing the contract.

## Risks

- The subset may surprise users who expect full CommonMark; unsupported constructs are escaped predictably and the genre contract names the subset.
- Typst syntax evolves independently; tests assert the generated source shape and compilation is left to the existing PDF gate.
- Complex nested Markdown is intentionally not promised; simple blocks remain safe and deterministic.
