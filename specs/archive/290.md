## Problem

`claude plugin test integrations/claude-cache` (the `quenching-cache tests` check of `scripts/verify_repo.sh`) fails 12 of 81 tests on Windows, on a clean LF checkout of origin/main (bcabc2258): 69 pass, 12 fail. The failures are the handoff tests (`h.calls.writes[0].text` undefined, `expect().toBe()` mismatches), `the checkout's shared.cache block and main budget reach the bar`, `a pt-BR root harness speaks Portuguese` and `stats: this chat and this project, from cq components session cache --usd`. Reproduced during the spec 275 conclude in the base worktree `.quenching/red` (detached at origin/main, core.autocrlf=false); the spec 275 diff does not touch `integrations/`. It keeps the repository gate red (GATE_EXIT 1) for every Windows run. The cause is not diagnosed; the first suspects are POSIX path or shell assumptions in the plugin's cq calls.

Minimal fix proposed: diagnose the first failing handoff test on Windows and make the plugin's cq invocation path-agnostic.

## Proposal

- `claude plugin test integrations/claude-cache` passes 81/81 on Windows, with no test disabled, skipped or loosened.
- The test engine's fakes (`fs.stat`, `fs.read`, the `fs.write` assertions) match paths by their meaning, not by the POSIX separators the Linux/macOS engine happens to hand them.
- The `quenching-cache tests` check of `scripts/verify_repo.sh` stops being a Windows-only red.

## Design

**Root cause (diagnosed, reproduced).** The `claude plugin test` engine hands each hook event the host's own path form: `C:\Users\x\proj\.agents\quenching\bin\cq` on Windows (observed by logging the `fs.stat` event path). The fakes in `tests/bar.test.tsx` matched with `endsWith('.agents/quenching/bin/cq')` and `endsWith('/hooks/handoff-brief.md')`, so on Windows `fs.stat` threw ENOENT, the plugin concluded `cq` was absent (`runCq` ? null), and every handoff and stats path that needs `cq` failed, along with the `shared.cache` bar test and the pt-BR harness test that read `AGENTS.md` through the same fakes.

**Decision: fix the fakes, not the plugin.** The plugin joins `<cwd>/<rel>` with `/`, which every Windows API accepts; the only brittle side was the test's string matching. A single `slashed()` helper normalizes the event path before matching. Draft-path assertions drop the drive prefix, because the engine echoes the `fs.write` path in host form while the plugin passes `cq` the form it built.

**Alternative weighed:** changing `inCwd` to emit host separators. Rejected: the plugin cannot know the host form, and the same fakes would still need to match.

### Assumptions

- The engine always normalizes event paths to the host form on Windows (observed on this machine; `Impact` depends on it).
