## Problem

O eixo git consegue abrir e revisar pull requests, mas não oferece uma leitura única e somente de consulta do estado atual de um PR. Isso força o agente a combinar manualmente provedor, checks, reviews, mergeabilidade e vínculo com a spec, aumentando o risco de decidir com estado incompleto ou desatualizado.

## Proposal

- Criar `/quenching:git:pr:status` e sua skill Codex correspondente para produzir um snapshot read-only de um pull request.
- Resolver a entrada por id de spec, número/URL de PR ou PR associado à branch atual; validar provider e remote antes de consultar.
- Reportar, quando disponível, provedor, PR, origem e base, estado, checks, aprovações, threads não resolvidas, mergeabilidade, vínculo com a spec e próximo passo recomendado.
- Preservar a diferença entre estado ausente, desconhecido, falha de autenticação e PR inexistente; nunca transformar uma falha de consulta em status verde.

## Out of Scope

- Abrir, fazer push, mesclar, fechar ou editar um PR.
- Resolver comentários, alterar a spec ou criar registros derivados do snapshot.
- Implementar suporte a provedores além de GitHub e Azure DevOps nesta entrega.

## Validation

- `python3 -m unittest discover -s plugins/quenching/tests` deve passar, incluindo fixtures de GitHub/Azure, branch sem PR, PR inexistente, CLI não autenticada e status desconhecido.
- `python3 scripts/validate_codex_plugin.py` deve validar a skill gerada e sua origem.
- `python3 plugins/quenching-codex/scripts/bin/cq --root .agents components doctor --json` deve retornar `ok: true` para a superfície local.
- `python3 plugins/quenching-codex/scripts/bin/cq knowledge validate docs` deve permanecer sem erros.
- O corpo deve conter uma única rota de consulta por provider e nenhuma operação de escrita, push, merge ou resolução.

## Design

- Usar o mesmo `cq specs config --json`, resolução de base e seleção de provider já adotados por `git:pr:create` e `git:pr:review`.
- Fazer uma coleta delimitada por provider: GitHub via `gh`/API e Azure via `az`, somente após confirmar que o remote corresponde ao provider configurado.
- Tratar campos que o provider não consegue responder como `unknown`, com a causa reportada; recomendações só podem ser emitidas quando os fatos necessários estiverem presentes.
- A skill deve ser read-only, não escrever frontmatter e terminar com um próximo comando textual, como `git:pr:review`, `git:sync`, `git:merge` ou nenhuma ação.

## Alternatives Considered

- Acrescentar o diagnóstico em `git:pr:create` ou `git:pr:review` — rejeitado porque esses comandos têm efeitos e momentos diferentes; misturá-los amplia escopo e torna o status difícil de invocar isoladamente.
- Inferir o status apenas de `git log` e branches locais — rejeitado porque checks, reviews e mergeabilidade pertencem ao provider.
- Consultar sempre GitHub — rejeitado porque o eixo já declara suporte equivalente a Azure DevOps.

## Open Decisions

- O conjunto mínimo de campos que possui equivalência fiel entre GitHub e Azure será fechado com as respostas reais dos CLIs e fixtures, sem inventar uma correspondência para campos ausentes.
- A forma final da entrada sem argumento — branch atual, PR único detectável ou pergunta — será definida a partir do contrato de seleção já usado por `git:pr:review`.
- O texto exato das recomendações será alinhado à superfície existente depois que os campos e recusas forem medidos.

## Risks

- Shapes e disponibilidade de campos podem variar entre versões de `gh` e `az`; mitigar registrando comportamento medido, fixtures e recusas explícitas.
- Permissões podem ocultar checks ou threads; mitigar reportando desconhecido e a mensagem do provider, nunca inferindo aprovação.
- Gatilhos podem colidir com `git:pr:create`, `git:pr:review` e `git:merge`; mitigar com descrições e limites `Not for` mutuamente claros.

## Outcome

Implementada e revisada a entrada `/quenching:git:pr:status` para produzir um snapshot somente de leitura, provider-aware, de pull requests GitHub e Azure DevOps. A entrega inclui a referência compartilhada de fatos e consultas, a tradução Codex, testes de contrato para roteamento, normalização e estados desconhecidos, e os registros nas superfícies Claude, Codex e no catálogo de projeto. Todas as 7 tarefas foram concluídas; os gates determinísticos passaram com 540 testes, tradução sem drift, plugin Codex validado, doctor/lint local limpos, `git diff --check` limpo e docs com 0 erros.

A revisão do branch não encontrou divergência de desenho nem conhecimento novo que justificasse documento em `/docs/`; a destilação, portanto, foi um harvest vazio. A funcionalidade de abertura, push, merge, edição ou resolução de threads permanece fora do escopo e continua pertencendo às entradas existentes. O harness funcional real permaneceu inconclusivo porque a primeira sessão externa não respondeu em 45 segundos; seus guards estático e sintético passaram, nenhum processo ficou ativo e isso não foi tratado como sinal verde.

A spec está revisada, arquivada e pronta para merge. O próximo agente deve preservar os commits `dffe9019` e `afe9bf8b`, confirmar o gate novamente no branch e usar o fluxo Git do repositório para publicar e mesclar a mudança.
