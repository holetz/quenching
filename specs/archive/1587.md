## Problem

Encontrado pelo mapa da rodada 11 do autopilot (2026-10-12) e reproduzido pelo condutor em `main` 0fac8801. Num repo
descartável com `pyproject.toml` `[dependency-groups] dev=["pytest==8.0.0"]` e sem lock, `cq toolchain doctor --json`
emite `tc-tool-unpinned`: "development tools lack exact pins: pytest==8.0.0". `toolchain/inventory.py:126` guarda o
item inteiro (`pytest==8.0.0`) como especificador, e o `package.json` (`:181`) guarda a faixa crua (`8.0.0`). Já a
checagem em `toolchain/checks.py:119-124` faz fullmatch de `\s*(==|=)\s*\d+(\.\d+){1,2}\s*`, que nenhuma das duas
formas casa. `test_toolchain.py:84-93` só testa o caso sem pin (`ruff>=1.0`).

Consequência: um achado estrutural, com exit 1, num repo cujas ferramentas estão corretamente fixadas, e a única
saída é acrescentar um lock. A correção separa nome e extras do especificador no inventário e aceita a versão crua
exata do npm.

## Proposal

- `cq toolchain doctor` no longer emits `tc-tool-unpinned` for a Python dev dependency written `name==X.Y.Z` (or `name[extras]==X.Y.Z`) when no lock exists.
- The same holds for an npm `devDependencies` entry whose range is the bare exact version `X.Y.Z`.
- The inventory records, per dev dependency, the bare name as key and the specifier alone as value.
- Genuinely unpinned entries (`ruff>=1.0`, `^8.0.0`, `~8.0.0`, `*`) are still flagged.

## Out of Scope

- Requiring a lock or judging lock freshness: `tc-lock-stale` and `_has_lock` stay as they are.
- Pins with environment markers or direct URLs (`name==1.0 ; python_version<'3.12'`, `name @ url`): the marker is dropped from the specifier; a URL stays unpinned. Not widened here.
- Other epic 1590 members (1586, 1588, 1589): they share no file.

## Impact

### Product code this spec expects to touch

- `plugins/quenching/assets/bin/quenching/toolchain/inventory.py` — split name and extras from the specifier in `_pyproject`
- `plugins/quenching/assets/bin/quenching/toolchain/checks.py` — `check_tool_unpinned` accepts npm's bare exact version
- `plugins/quenching/tests/test_toolchain.py` — regression tests

## Validation

- `python3 -m unittest discover -s plugins/quenching/tests -p 'test_toolchain.py'` exits 0.
- The new tests fail on the base (red) and pass after the fix.
- `bash scripts/verify_repo.sh` exits 0.

## Design

Decisions follow epic 1590 ## Design: 1587 separates the name and extras from the specifier, and accepts npm's bare exact version.

- Python: `_pyproject` parses each dev dependency string with a regex capturing the name, an optional `[extras]` group and the rest; the key is the name, the value is the rest with any `; marker` removed and whitespace stripped. The check keeps its `==`/`=` pattern, which now matches `==8.0.0`.
- npm: `check_tool_unpinned` accepts a bare `\d+\.\d+\.\d+` only for `ecosystem == "node"`. A bare version in Python (`pytest 8.0.0`) is not valid PEP 508, so it is not accepted there.
- Rule: a pin is exact when the specifier is `==X.Y[.Z]`, or for npm `X.Y.Z` with an optional leading `=`.

## Alternatives Considered

- Normalising in the check only (parsing the whole `pytest==8.0.0` string there): rejected, the inventory would keep a wrong name key and extras would stay glued to the name.
- Accepting any bare version for every ecosystem: rejected, it would mask a malformed Python entry.

## Open Decisions

- none — the epic's Design settled both choices.

## Risks

- A requirement string the regex does not parse (e.g. `-r file`) yields an odd name: ACCEPTED — it stays unpinned, which is the previous behaviour.
- Renaming keys of `devDependencySpecs` changes `devDependencies` output for specifiers like `ruff>=1.0` (the name was the whole string before): ACCEPTED — the old value was a bug; no other consumer reads it.
