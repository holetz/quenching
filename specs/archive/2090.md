## Problem

quenching assumes a POSIX workstation, so a developer on Windows without administrator rights cannot run `cq` at all. Three fronts block it: `git/worktree.py:63,77` link the shared store with `os.symlink`, which needs admin or Developer Mode on Windows — fall back to a directory junction; `codex/probe.py:43` kills the child's process group with `os.killpg`, and `implement.py`, `probe.py` and `review.py` start it with `start_new_session=True` — use the Windows equivalents (`CREATE_NEW_PROCESS_GROUP` and a tree kill) behind one helper; and `cq` has no Windows launcher — ship a `cq.cmd` shim and document the admin-free prerequisites (Python, git, gh from user-scope installers). A `windows-latest` job joins the PR gate, by the human's decision of 2026-10-24.

Member S30 of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent).

## Proposal

- `cq git worktree link` and `cq git worktree add` materialise the shared paths on Windows without administrator rights: a directory junction replaces the symlink when `os.symlink` is refused, and every reader of those links (re-link, removal audit) treats a junction as a link.
- One helper in `quenching.codex.probe` owns "start a child in its own process group" and "stop the whole tree" for POSIX and Windows; `probe.py`, `implement.py` and `review.py` call it and none of them names `os.killpg`, `signal.SIGKILL` or `start_new_session` any more.
- The plugin ships `bin/cq.cmd` beside `bin/cq`, so a bare `cq` resolves on a Windows PATH; the generator copies it to the module that owns the PATH shim and refuses its absence.
- A standard in `docs/standards/platform/` states the admin-free prerequisites (Python 3.11+, git, gh from user-scope installers) and what the Windows port covers.
- The PR gate gains one `windows-latest` job that runs the Windows-sensitive unit tests; it is the only CI widening this spec makes.

## Out of Scope

- `scripts/run_evals.py` (`start_new_session`, `os.killpg`): a maintainer tool for the repository's own eval runs, not shipped to users; parked as a discovery.
- Running the whole `scripts/verify_repo.sh` gate on Windows: it needs bash, uv and the doctors, and there is no Windows host here to prove it; the job runs the focused tests instead.
- A native PowerShell port of the hooks and `scripts/githooks`: not touched.
- Any grant, `allowed-tools`, hook or CI change beyond the one `windows-latest` job goes to epic 2045.
- Making the `windows-latest` job a branch-protection required check: a repository setting the human owns, not a file in the tree.

## Design

**Process helper lives in `codex/probe.py`.** `implement.py` and `review.py` already import `stop` from it, so the helper adds no module and no mirror. `group_kwargs()` returns `{"start_new_session": True}` on POSIX and `{"creationflags": subprocess.CREATE_NEW_PROCESS_GROUP}` on Windows; `stop(process)` keeps `os.killpg` on POSIX and runs `taskkill /F /T /PID <pid>` on Windows, then `process.wait()`. The platform test is `os.name == "nt"`, read at call time so a test can patch it.

**Junction fallback.** `_make_link(store, link)` tries `os.symlink(store, link, target_is_directory=True)`; on `OSError` under `os.name == "nt"` it creates a junction with `cmd /c mklink /J`, which needs no privilege and needs the store to be an existing directory (it is: `_materialise` creates it first). `_is_link(path)` is `os.path.islink(path)` or `os.path.isjunction(path)` where the latter exists (3.12+) and a reparse-point test on `os.lstat` for 3.11. Removal of a junction is `os.rmdir`, of a symlink `os.unlink`; both live in `_remove_link`. `_ignored_files` and the repointing branch use `_is_link`.

**Launcher.** `cq.cmd` resolves `..\assets\bin\cq` from `%~dp0`, runs it with `py -3` when the launcher exists and with `python` otherwise, and forwards `%*` and the exit code. It does not use the POSIX `bin/cq` re-exec, whose `os.execv` does not hand back the exit code on Windows.

**CI.** One job `windows`, `runs-on: windows-latest`, with the same pinned `actions/checkout` and `actions/setup-python` as the other jobs, running `python -m unittest discover -s plugins/quenching/tests -p <file>` for the three Windows-sensitive files. It carries `permissions: contents: read` from the workflow and no new grant.

## Alternatives Considered

- **Require Developer Mode or administrator on Windows**: rejected, it is the exact barrier the spec removes.
- **Copy the shared directory instead of linking on Windows**: rejected, the store would diverge between worktrees and the removal audit would delete real data.
- **Always use junctions, even on POSIX**: rejected, junctions do not exist there.
- **Run the full repository gate on `windows-latest`**: rejected for now, it needs bash and uv and cannot be proved from here; revisit once the focused job is green.
- **A new `common/proc.py` module**: rejected, it would add a mirror in every module that carries `common/` for a helper only the codex pillar uses.

## Open Decisions

- Whether `scripts/run_evals.py` gets the same helper: decided when an eval run on Windows is wanted; parked as a discovery.

## Risks

- No Windows host is available to this build, so the Windows branches are proved by patched unit tests only and the real proof is the CI job: ACCEPTED — the human asked for the job exactly for this; a red first run is fixed in a follow-up commit on the same PR.
- A focused job can pass while other tests would fail on Windows: ACCEPTED — the standard states the covered scope, and widening is an open decision.
- `mklink /J` could be blocked by a policy on a locked-down machine: the error is surfaced as the existing link refusal with the OS message, never swallowed.
- `taskkill` could miss a grandchild that detached itself: mitigated by `/T`, and the same limit already applies to a POSIX process that left its group.
