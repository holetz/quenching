## Problem

Evidência (scout ses_de7f04b5, 2026-11-26): specs/portal_docs.py:14 aponta para quenching/README.md e :16 para docs/standards/workflows/plugin-configuration.md, caminhos que só existem no repositório-fonte; o deploy não os copia (.agents/quenching/ tem VERSION, agents, assets, bin, references). Consequência: em qualquer alvo a aba mostra 'ausente' para 2 dos 3 links. Proposta: resolver pela árvore instalada (ou link para o site publicado quando o arquivo local não existe), com teste em quenching/tests/test_specs_portal.py (classe Docs, :846) cobrindo um alvo sem os arquivos da fonte.

## Proposal

- Each Docs link resolves through an ordered list of candidate paths in the target, and the payload names the one that exists: the configuration standard is found at its installed copy `.agents/quenching/references/specs-align/plugin-configuration.md` when the source path is absent.
- A link with no candidate on disk and a published copy carries a `url` fallback, so the manual (`quenching/README.md`, source-repository only) points to its published page instead of reading "ausente".
- The tab renders the fallback as an external link and keeps "ausente" only for a link with neither a local file nor a url.
- The route stays read-only: no file content is served.

## Out of Scope

- Copying `quenching/README.md` or the configuration standard into the deploy payload — widens what every target installs; the installed reference copy and a published link already cover it.
- Serving file content through the portal — the route is read-only by contract (`docs/standards/architecture/specs-portal.md`).
- Changing `docs/index.md` resolution — it is the target's own OKF index, legitimately absent in a target without one.

## Design

- **Links resolve through candidates, never one hardcoded source path.** `LINKS` rows carry an ordered tuple of candidate paths; the first that is a file wins and its path is reported. With none present, the first candidate is reported with `exists: false`. Rationale: the fix must hold in an installed target, where only the deployed tree exists; the source repo's own path stays first so the source repo is unchanged.
- **The installed copy of the configuration standard is `.agents/quenching/references/specs-align/plugin-configuration.md`** (verified present in the deployed tree).
- **The manual has no installed copy, so it carries a published fallback `url`** (`https://github.com/holetz/quenching/blob/main/quenching/README.md`, the repository the deploy already pins in `deploy/tree.py`). A `url` is added only when the link is not present locally and only when `http(s)`; the UI applies the same scheme check the app already uses.
- Alternative weighed — ship the README in the deploy: rejected, it widens every install for one tab link.
- decision: reading the site URL from the target's `zensical.toml` is unchanged — a target without one keeps the existing "sem site_url" line.

## Alternatives Considered

- Deploy `quenching/README.md` and the standard into targets — rejected: grows the installed payload and its manifest for a navigation link.
- Hide links whose file is absent — rejected: the tab's point is to say what is missing in the target; hiding loses that.

## Open Decisions

- none — the manual's fallback is the repository page; if a published docs site is later declared, its URL replaces the constant under a new spec.

## Risks

- A hardcoded repository URL goes stale if the repository moves — ACCEPTED: the deploy already pins the same repository in `deploy/tree.py`, and the tab only links to it.
- A relative candidate path outside the target — mitigated: candidates are fixed constants, never user input.
