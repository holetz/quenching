## Problem

O `cq deploy` só registra o servidor MCP `quenching` no repositório-alvo quando o repositório declara `shared.mcp` (`deploy/cli.py:57-87`, `_mcp_option`: ausente é ausência; `deploy/tree.py:298-315`, `_mcp_tree`). Sem a declaração, nenhum harness (Claude Code via `.mcp.json`, Codex via `.codex/config.toml`, OpenCode via `opencode.json`) enxerga as tools do quenching, e todo uso do cq passa pela shell, um processo Python por chamada (custo medido na 231). Em 2026-11-22 este próprio repositório estava assim: a sessão OpenCode não expunha nenhuma tool `quenching`.

Decisão do humano (2026-11-22): retirar a necessidade de declarar `shared.mcp`. O deploy passa a adicionar sempre o MCP ao projeto. `shared.mcp` continua existindo só para sobrescrever o mount e o prefixo de Python.

Pontos a resolver no develop:
- prefixo padrão do Python quando nada é declarado: hoje os hooks usam `python3` (`deploy/settings.py:22`), que pode não existir no Windows; aplicar a decisão do humano da 231 (nunca travar numa versão ausente; fallback automático);
- `--runtime` diferente de `vendor` hoje recusa `shared.mcp` (`deploy/cli.py:388`): o padrão precisa de um comportamento definido nesse caso, sem recusar o deploy;
- `.mcp.json` ou `opencode.json` já existentes do usuário: preservar as entradas alheias (o deploy hoje trata o arquivo como inteiro dele);
- os testes de `test_deploy.py` que afirmam a ausência do MCP sem a declaração (por exemplo `:444`) passam a afirmar o contrário; o README (`quenching/README.md:334-336`) muda junto.

**Insumos**
- `quenching/assets/bin/quenching/deploy/cli.py:22,30-87,388` e `deploy/tree.py:289-315,431-437`
- `quenching/assets/bin/quenching/deploy/settings.py:22`
- `quenching/tests/test_deploy.py:411-500`
- spec 234 (aviso do plugin OpenCode quando o MCP não está registrado), que fica mais simples com o MCP sempre presente

## Proposal

- `cq deploy` registra sempre o MCP `quenching` nos harnesses selecionados (`.mcp.json`, `.codex/config.toml`, `opencode.json`), sem exigir `shared.mcp`.
- `shared.mcp` continua existindo apenas para sobrescrever o mount e o prefixo de Python.
- Sem declaração, o prefixo de Python é resolvido sem travar versão: o do manifesto anterior, senão o primeiro entre `python3`, `python` e `py -3` que roda um Python >= 3.11 nesta máquina, senão `python3`. Os hooks de `.claude/settings.json` usam o mesmo prefixo.
- Com `--runtime uvx` e sem declaração, o deploy não escreve MCP e emite um aviso, sem recusar.
- Os arquivos MCP deixam de ser do manifesto e passam a ser mesclados: as entradas alheias do usuário são preservadas e só a entrada `quenching` é do deploy; o `--remove` tira só ela.
- Testes de `test_deploy.py`, README, schema e padrões em `docs/standards/` afirmam o novo comportamento.

## Out of Scope

- Ativar o MCP neste repositório (PR de configuração separado, branch `ativar-mcp-neste-repo`).
- Aviso do plugin OpenCode quando o MCP não está registrado (spec 234).
- Escrever `enabledMcpjsonServers`: a aprovação do servidor segue sendo passo humano.
- Parsear JSONC de `opencode.json`: um arquivo que não é JSON puro não é tocado; vira aviso.

## Design

Decisões como regras duráveis:

- **O MCP é sempre registrado.** `build_tree` não coloca mais os arquivos MCP na árvore própria; a mescla ocorre em `cli`, como a de `.claude/settings.json`: o arquivo é do usuário, o deploy é dono só da entrada `quenching`, e o manifesto registra `mcp` e `mcpFiles` (a lista de caminhos mesclados), nunca o hash do arquivo.
- **Prefixo de Python (decisão da 231: nunca travar numa versão ausente, fallback automático).** Precedência: `shared.mcp.command` > `mcp.command` do manifesto anterior (estável entre máquinas, sem drift) > sonda desta máquina (`python3`, `python`, `py -3`, o primeiro que executa Python >= 3.11, o piso do `pyproject.toml`) > `python3`. Nenhuma versão é fixada.
- **Runtime diferente de `vendor`.** O comando gerado aponta para o ponto de entrada vendorizado, que o uvx não carrega; sem declaração o deploy não escreve MCP e avisa. Com `shared.mcp` declarado a recusa `ct-deploy-mcp` permanece.
- **Entradas alheias.** JSON: preserva as chaves, troca só `mcpServers.quenching` / `mcp.quenching` (e `$schema` só se ausente). TOML: troca textualmente o bloco `[mcp_servers.quenching]` e seus subblocos, ou o acrescenta ao fim. Arquivo que não é JSON puro, ou de forma inesperada, não é tocado e vira aviso. Na remoção, o arquivo é apagado só se sobrar vazio (JSON: `{}` ou só `$schema`).
- **Migração.** Um manifesto antigo que listava esses arquivos em `files` deixa de os ter como donos: `_recorded_hashes` os ignora, e a mescla reescreve a mesma entrada sem churn.

### Assumptions

- A ordem `python3`, `python`, `py -3` cobre Linux, macOS e Windows; o usuário sobrescreve com `shared.mcp.command` (Tasks 1).
- Reformatar um JSON do usuário com indentação de 2 espaços na primeira mescla é aceitável.

## Alternatives Considered

- Um launcher que acha Python sozinho como `command`: exigiria um executável por SO no arquivo comitado; o `.mcp.json` é um só. Perdeu.
- `sys.executable` do processo de deploy: varia por máquina e grava um caminho absoluto no arquivo versionado. Perdeu.
- Manter o arquivo inteiro como do deploy e só avisar do alheio: é o comportamento atual, que o humano pediu para mudar.

## Risks

- A sonda escolhe um Python que o colega não tem: mitigado pela precedência do manifesto e pela sobrescrita em `shared.mcp.command`. ACCEPTED — o custo é um MCP que não sobe até a sobrescrita.
- A mescla textual do TOML engana-se com um bloco exótico: o escopo é só o cabeçalho `[mcp_servers.quenching`; fora dele nada é tocado.
- Reformatação de um JSON do usuário: ACCEPTED — ocorre uma vez, com o conteúdo preservado.
