## Problem

Revisão de correção do épico 2042 (2026-10-24), achados do Codex reproduzidos pelo condutor no código da 2036:

- `commands/epic.py:210-211` com `:179`: `epic add` normaliza o membro para a chave local (`local_key`), mas `_without_item` compara literalmente com o `i["spec"]` do épico antigo. Um item gravado como `owner/repo#3`, apontando para o próprio repositório, não é encontrado: `epic add 2 3 --move` reporta sucesso, deixa o membro também no épico 1 e pula a recusa `sp-epic-move-dependents`.
- `parse/epics.py:53` e `:309`: `is_remote` olha só a sintaxe. Uma referência qualificada ao próprio repositório escapa da checagem `sp-epic-divergent`, e `validate` aceita o item mesmo com a spec local declarando outro `epic:` ou nenhum.
- `portal.py:439` com `members.py:87`: o portal passa a `read_members` um `_SnapshotStore` sem `name`, e `getattr(backend, "name", "git")` o trata como git. Num backend de tracker, o portal resolve membros estrangeiros que a CLI declara `unreadable`, e as duas superfícies divergem.

Consequência: um épico entre repositórios mostra e valida membros errados justamente no caso da referência qualificada que a 2036 introduziu.

## Proposal

- `cq specs epic add <epic> <spec> --move` finds the member in the old epic when its item is written as a qualified reference to this same repository (`owner/repo#3`), takes it out, and runs the `sp-epic-move-dependents` refusal when another item waits on it.
- `cq specs validate` treats a qualified reference to the own repository as a local member: `sp-epic-divergent` is raised when the member's `epic:` is unset or names another epic.
- The portal resolves epic members through the same rule as the CLI: on a tracker backend (any backend not in `git`/`memory`) a foreign member is `unreadable` in both surfaces.

## Out of Scope

- Normalizing the stored `spec:` value of an existing item to the bare id (a rewrite of epics already on disk): the readers accept both forms, so no migration is needed.
- Changing how an epic item referencing another repository is resolved or displayed: only the own-repository and tracker-name cases are wrong.
- A tracker backend resolving foreign members: it stays `unreadable` by contract, the portal just stops disagreeing.

## Design

- **Own-repository references collapse through `local_key`.** `epic add` already normalizes the member with `local_key(member_key, own_repo(origin_url(root)))`; every other reader of an item's `spec:` must apply the same function with the same `self_repo`, never compare the raw string or call `is_remote` on it. `is_remote` stays purely syntactic.
- `_without_item(old, spec_id, args, out, self_repo)` matches `local_key(i["spec"], self_repo) == spec_id`.
- `epic_findings(info, members, unreadable=None, self_repo=None)` skips the back-reference check only when `is_remote(local_key(i["spec"], self_repo))`; `epic_sweep` computes `self_repo` once and passes it to both finding functions. The members map is still keyed by the raw item value (`read_members` already keeps the original key).
- **The snapshot store declares its backend.** `_SnapshotStore(infos, name)` exposes `name` from `snap["backend"]`, so `read_members`' tracker rule (`getattr(backend, "name", "git")`) sees the real backend instead of defaulting to git.

## Alternatives Considered

- Make `is_remote` repository-aware (take `self_repo`): rejected, it is called in places with no repository known and a hidden second meaning would hide the next such bug; the explicit `local_key` pass is the existing convention.
- Rewrite stored `spec:` values to bare ids on read or write: rejected, it turns a reader fix into a data migration (see Out of Scope).
- Give the portal a real backend object instead of the name: rejected, the snapshot already exists to avoid a second read and only the name decides the tracker rule.

## Open Decisions

- none — the three defects are fully determined by the code read above.

## Risks

- The members map is keyed by the raw item value while the checks use the collapsed key: mitigated by looking members up with the raw key (as `read_members` returns) and collapsing only for the remote test and the move comparison; the regression tests cover both forms.
- A mirror edited by hand and drifting from its source: mitigated by regenerating with the generators and the gate's `--check` runs.
