## Problem

Em 2026-11-25, na spec 466 (slot-8, execute autônomo), o `cq specs reconcile --write` falhou com exit 2: `error: could not fetch branch 'quenching' from 'origin': error: cannot lock ref 'refs/remotes/origin/quenching': is at 99d57d92951a799637eb75c04b83125441eaa58a but expected 1a3a9cc2928ba4d73bc963ec7e76c792817607b4`. A segunda execução, segundos depois, fechou com `count: 0`. O ref `refs/remotes/origin/quenching` vive no `.git` comum aos 12 slots, e a mensagem é uma atualização com compare-and-swap: um fetch concorrente atualizou o ref entre a leitura e a escrita do outro. O verbo devolve exit 2, e o conclude não distingue essa corrida transitória de um remoto inalcançável — a spec 466 seguiu sem o `reconcile` e repetiu às cegas.

A melhoria tem de fazer o fetch do store repetir a atualização do ref remoto quando perde a corrida, sem esconder um erro real de rede ou de permissão: a segunda tentativa relê o ref e, se também falhar, o exit 2 continua.

Minimal fix proposed: no fetch do store, uma atualização de `refs/remotes/<remote>/<branch>` que falhe com "cannot lock ref" é repetida uma vez depois de reler o ref; o exit 2 só sai quando a segunda tentativa também falha.

**Insumos**

- `cq specs reconcile --write` — exit 2, `sp-...`/`could not fetch branch 'quenching'` com a mensagem citada; segunda execução exit 0, `count: 0`
- o `.git` comum e `refs/remotes/origin/quenching`, compartilhados pelos 12 slots
- spec 466, `/quenching-specs conclude` step 1, 2026-11-25

## Proposal

- Um `fetch` do store que perde a corrida de compare-and-swap do ref `refs/remotes/<remote>/<branch>` (`cannot lock ref`) é repetido uma vez, e a repetição devolve o tip lido de novo.
- Um erro real (rede, permissão, remoto ausente) e uma segunda falha de corrida continuam saindo como `sp-git-fetch-failed` (exit 2), com a mensagem do git.

## Out of Scope

- Mais de uma repetição ou espera com backoff: uma segunda falha seguida não é a corrida transitória descrita, e o exit 2 deve continuar visível.
- Serializar os fetches dos slots com lock próprio: o git já serializa por ref, e o lock só adicionaria um ponto de falha.
- Mudar o `conclude` para distinguir a corrida: com o retry no fetch ela deixa de chegar ao conclude.

## Impact

### Product code this spec expects to touch

- `quenching/assets/bin/quenching/specs/backends/git.py` — `GitBackend._fetch` repete a atualização do ref quando o git recusa com `cannot lock ref`
- `quenching/tests/test_specs_git_backend.py` — a prova da repetição e da falha que persiste

## Validation

- `python3 -m unittest discover -s quenching/tests -p test_specs_git_backend.py` sai 0, com os dois casos novos: uma falha `cannot lock ref` seguida de sucesso devolve o tip, e duas falhas seguidas levantam `sp-git-fetch-failed`.
- Um erro que não é `cannot lock ref` (por exemplo rede) não é repetido: o teste conta as chamadas de `fetch` e espera uma.
- `QUENCHING_TEST_SCOPE=affected bash scripts/verify_repo.sh` fecha verde no conclude.

## Design

- **A repetição mora em `_fetch`.** É o único ponto que escreve o tracking ref; `reconcile`, `sync` e as leituras passam por ele, e todos ganham a repetição sem mudar de chamador.
- **Só `cannot lock ref` repete, e uma vez.** É a assinatura do compare-and-swap perdido para outro clone do mesmo `.git` comum. A segunda tentativa roda o mesmo `git fetch`, que relê o valor esperado do ref; o que também falha sai como hoje. Alternativa pesada: reler o ref à mão e comparar — rejeitada, o próprio fetch já relê.
- **Sem espera entre as tentativas**: o ref que venceu já está gravado quando o git recusa, então a releitura imediata vê o valor novo.

## Alternatives Considered

- Repetir qualquer falha do fetch: esconderia erro real de rede ou de permissão, que é o que o exit 2 existe para mostrar.
- Tratar a corrida no `conclude` (rodar o `reconcile` de novo): deixa cada chamador com a mesma lógica e o `reconcile` do store continua falhando fora do conclude.

## Open Decisions

- none — a repetição única e a assinatura `cannot lock ref` vêm da própria spec 532.

## Risks

- Uma mensagem do git com outro texto para a mesma corrida (outra versão ou idioma) não seria repetida: o exit 2 atual continua, sem regressão. ACCEPTED — o texto `cannot lock ref` é estável no git e é o que o relato registrou.
- Duas corridas seguidas ainda falham: ACCEPTED — é o contrato pedido, o exit 2 segue visível.
