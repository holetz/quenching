## Problem

O deploy registra só o servidor de specs: o conjunto de mounts admite apenas `specs` (`quenching/assets/bin/quenching/deploy/cli.py:23`), o mount padrão é `"specs"` (`cli.py:474`) e o argv é `[python, .agents/quenching/assets/bin/cq, specs, mcp]` (`deploy/tree.py:313-315`); o `.mcp.json` e o `opencode.json` deste repositório mostram isso. O servidor completo `cq mcp` (`quenching/assets/bin/quenching/mcp/cli.py`, 78 tools: components, knowledge, git, ops, proof… mais specs) já existe e ninguém o registra. Feedback de usuário: "o MCP (cq specs mcp) nem conectou na minha sessão (timeout de 30 s) e só cobre specs. Git, components e knowledge não existem por MCP." O timeout vem do prefixo `uv run python` declarado em `shared.mcp.command` (sync do projeto no arranque); `tools/list` também reconstrói ~60 `build_parser()` sem cache (`mcp/catalog.py:111-113,209-215`, 0,35 s aqui).

Medido em 2026-11-24 (Linux): `cq specs status --spec 305 --json` pela CLI 0,58 s; o mesmo via MCP `specs_status` 0,024 s.

**Consequência:** toda chamada fora de specs paga um processo Python novo, e no Windows com antivírus isso é a maior parte do tempo da sessão.

Proposta: mount padrão `all` → `cq mcp` nos arquivos de cada harness (`.mcp.json` para Claude Code e Copilot, `opencode.json`, `.codex/config.toml` se ainda existir); `specs` fica como opção declarada; o comando nunca é `uv run` (mesma regra dos hooks); `tools/list` com parsers em cache; um teste de arranque mede `initialize`+`tools/list` abaixo de 1 s.

## Proposal

- `cq deploy` registra, por padrão, o servidor completo: o argv gerado em `.mcp.json` (Claude Code e Copilot), `opencode.json` e `.codex/config.toml` termina em `.agents/quenching/assets/bin/cq mcp`, com as 78 ferramentas (components, knowledge, git, ops, proof… e specs).
- `shared.mcp.mount` aceita `all` (o padrão) e `specs` (o mount só de specs, opt-in declarado); qualquer outro valor continua recusando com `ct-deploy-mcp`.
- O prefixo do servidor MCP é sempre um interpretador direto, a mesma regra dos hooks (`mcpfiles.direct_prefix`): um `shared.mcp.command` que passa por `uv`/`uvx` gera um aviso e o MCP roda o interpretador direto, nunca `uv run`.
- `tools/list` do `cq mcp` constrói cada `build_parser()` de pilar uma vez por processo (cache), e um teste de arranque prova `initialize` + `tools/list` abaixo de 1 s.
- Este repositório passa a registrar `cq mcp` nos três arquivos de harness, e os standards que descrevem o registro dizem o novo padrão.

## Out of Scope

- Tornar o MCP obrigatório nas skills e subagentes (chamar as ferramentas no lugar da CLI) — é a spec 310.
- Novas linhas no catálogo MCP para verbos ainda sem ferramenta — spec 309.
- Aprovar o servidor no harness (`enabledMcpjsonServers`, permissões do OpenCode, profundidade de subagentes) — spec 314; o deploy continua sem escrever aprovação.
- O lançador `cq.cmd` do Windows em processo único — spec 313.
- Um arquivo próprio para o Copilot (`.vscode/mcp.json`): o Copilot já lê `.mcp.json` (README §The GitHub Copilot harness).
- Remover o mount `cq specs mcp`: continua existindo como opção declarada e como comando.

## Design

- **O mount é uma palavra do router, `all` é a ausência dela.** `mcp_argv` acrescenta `*mount.split()` antes de `mcp`; `all` acrescenta nada, gerando `cq mcp`. `MCP_MOUNTS = {"all", "specs"}`; o padrão sem declaração passa de `specs` a `all`. Um manifesto antigo com `mcp.mount: specs` gravado não prende o mount: o mount vem só da declaração, nunca do registro (o registro só fixa o prefixo).
- **Um só prefixo direto para hooks e MCP.** `direct_prefix(python, recorded_hooks)` já escolhe o interpretador dos hooks; o MCP usa o mesmo valor. O aviso deixa de dizer "the MCP server keeps the declared prefix" e passa a valer para qualquer harness selecionado (o MCP vai a todos), não só `claude`. O manifesto grava em `mcp.command` o prefixo direto efetivo.
- **Cache por processo no catálogo.** `_pillar_parser` e `resolve` são memoizados (`functools.lru_cache` por pilar e por `Row`): o parser só é lido (schema, argv), nunca mutado, e o despacho real passa pelo `main` do router, que constrói o seu próprio parser.
- **O teste de arranque mede o servidor real** por stdio (`sys.executable quenching/assets/bin/cq mcp`), com limite de 1 s sobre `initialize` + `tools/list`; medido aqui em 0,30–0,60 s antes do cache.

### Assumptions

- O `tools/list` com 78 ferramentas cabe no limite do cliente de cada harness (Claude Code, OpenCode, Codex) — `## Risks` depende disso.
- O runner Linux do CI arranca `cq mcp` abaixo de 1 s (medido 0,30–0,60 s nesta máquina) — o teste de arranque depende disso.

## Alternatives Considered

- **Manter `specs` como padrão e tornar `all` opt-in** — perdeu: o feedback é exatamente que ninguém tem git/components/knowledge por MCP; um opt-in repete a situação atual em todo alvo que não leia o standard.
- **Registrar dois servidores (`quenching` completo e `quenching-specs`)** — perdeu: duplica as 16 ferramentas de specs com o mesmo nome sob dois servidores e dobra o arranque.
- **Pré-gerar o catálogo (JSON com os schemas) no deploy** — perdeu por ora: o cache por processo já leva `tools/list` abaixo do limite e não cria um artefato que pode divergir do parser.

## Open Decisions

- O limite de 1 s no runner Windows do CI (antivírus, disco mais lento) — decidido pela primeira execução do teste lá; hoje o job Windows roda só testes focados e não inclui este, então o limite vale para o gate Linux.

## Risks

- Um alvo já deployado vê drift `mcp` no próximo `--check` e troca o argv no próximo `--write` — ACCEPTED: é a mudança pedida; o arquivo continua do usuário e só a entrada `quenching` muda.
- Um alvo que declarou `uv run` como prefixo para achar dependências do projeto perde isso no MCP — mitigação: o `cq` é só stdlib (`pyproject.toml` sem dependências), e o aviso nomeia o interpretador escolhido.
- Um cliente com teto de ferramentas recusa 78 — mitigação: `shared.mcp.mount: specs` continua disponível como opção declarada.
- Teste de tempo instável em máquina carregada — mitigação: mede só `initialize` + `tools/list` de um processo, sem rede, e o limite tem ~2× de folga sobre o medido.

## Outcome

**Shipped.** `cq deploy` now registers the whole MCP server (`cq mcp`) in every harness by default — `shared.mcp.mount` accepts `all` (the new default) or `specs` (the old pillar-only mount) — and the registration runs under the same direct interpreter the hooks use, so a `uv run`/`uvx` prefix never starts the server (`deploy/cli.py`, `deploy/tree.py::mcp_argv`, `deploy/mcpfiles.py::direct_prefix`, with its warning now naming both). `tools/list` builds each pillar parser once per pass and memoises the described tools for the life of the process (`mcp/catalog.py::described`), bringing `initialize`+`tools/list` from 0,30–0,60 s to ~0,13 s on Linux; `quenching/tests/test_quenching_mcp_startup.py` guards the 1 s limit over real stdio. The standards (`deploy-mode.md`, `mcp-server.md`, `hooks.md`, `plugin-configuration.md`) and the README describe the whole-server default and the direct prefix, and this repository's own `.mcp.json`, `opencode.json` and `.codex/config.toml` register `cq mcp`.

**Left out.** No change to the uvx runtime (still skipped, with its warning); no per-tool lazy loading beyond the per-pass parser cache; the startup test is a regression guard and is not red on the base (measured, recorded in Discoveries).

**For the next reader.** The branch merged `origin/main` (MCP catalog coverage rows from a sibling spec) cleanly apart from the generated manifest and proof README, which were regenerated; the startup test still passes with the larger catalog.
