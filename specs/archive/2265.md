## Problem

Achado pelo autopilot 2026-11-21 rodada 8 (scout read-only sobre origin/main 0574813c1), reproduzido em repositório descartável.

`quenching/assets/bin/quenching/common/leak.py:258-265` roda `rev-list <local> --not <remote_sha>`; `common/identity.py:88` herda. Reprodução: remoto avançado por outro clone, sem fetch; `echo "refs/heads/main <HEAD> refs/heads/main <remote_sha>" | cq security leak --pre-push --generic-only --remote origin` → `refused: git failed while scanning: fatal: bad object 8921fe5…`, exit 2.

Consequência: um push (ex.: `--force`) sem fetch é recusado por motivo que nada diz sobre vazamento. Falha fechada; a correção (descartar `remote_sha` desconhecida e cair no recorte `--remotes=`) não pode estreitar o que é varrido em relação ao caso sem remote_sha.

Arquivos prováveis: `common/leak.py`, `common/identity.py`, `quenching/tests/test_leak_scan.py`.

## Proposal

`_commits_to_push` (`common/leak.py`) passa a tratar uma `remote_sha` que não resolve para um commit no clone local como se fosse `ZERO_SHA`. O push cai no recorte já usado para ref nova: `--not --remotes=<remote>` quando o hook conhece o destino, e o histórico inteiro do tip local quando não conhece. `cq security leak --pre-push` e `cq git identity --pre-push`, que herda a função, deixam de recusar com exit 2 (`fatal: bad object`) e passam a julgar os commits.

## Out of Scope

- `local_sha` desconhecida ou malformada. O git só a envia quando ela existe; o recorte dela não muda.
- O desligamento do pre-push por `cq git push` (`core.hooksPath=/dev/null`). É a spec 2268, no épico 2206.
- Fazer fetch automático do remoto antes de varrer.

## Design

- **Conhecida ou não.** Uma `remote_sha` diferente de `ZERO_SHA` só entra em `--not` quando é hexadecimal de 40 ou 64 dígitos e `git cat-file -e <sha>^{commit}` sai 0. Caso contrário, a função a trata como `ZERO_SHA`. A checagem hexadecimal também impede que um campo começando com `-` vire opção do `rev-list` e encolha a varredura (por exemplo, `--all` depois de `--not`).
- **A varredura nunca encolhe.** O recorte conhecido exclui `remote_sha` mais `--remotes=<remote>`. O recorte desconhecido exclui só `--remotes=<remote>`, ou nada sem `remote`. O resultado é igual ao do caso sem remote_sha, como pede a decisão de 2026-11-21 do épico 2270.
- **Um ponto só.** `identity.push_findings` importa `_commits_to_push`, então a correção vale para as duas verificações sem duplicar código.

### Assumptions

- Um remoto com tip desconhecido não tem como ser excluído do recorte. Supor que nada dele está publicado é a opção conservadora: varre mais. Depende disso: `## Design`, `## Risks`.

## Alternatives Considered

- **Fazer fetch antes de varrer.** Rejeitado: o hook fica dependente de rede e muta refs dentro de um pre-push.
- **Continuar recusando, com mensagem melhor.** Rejeitado: o push segue bloqueado por um motivo que não é vazamento, e a decisão do épico 2270 manda cair no recorte `--remotes=`.
- **Excluir só `--remotes=` e ignorar a `remote_sha` sempre.** Rejeitado: volta a julgar commits que o remoto já tem quando a sha é conhecida e regride o caso do merge de base publicada.

## Open Decisions

- none — o épico 2270 (Design, 2026-11-21) decidiu o recorte e o invariante.

## Risks

- **Varredura maior em push sem fetch.** Commits já publicados por outro clone podem ser julgados de novo e gerar um falso positivo já conhecido. É aceitável: falha fechada por motivo de vazamento, que o operador entende.
- **Estreitar sem perceber.** Mitigado pelo teste de igualdade com o caso `ZERO_SHA` e pela revisão de segurança.

## Discoveries

- decision: remote_sha só entra em --not quando é hex de 40/64 dígitos e git cat-file -e <sha>^{commit} sai 0; senão cai no recorte de ZERO_SHA — épico 2270 Design 2026-11-21; o teste afirma igualdade com o caso ZERO_SHA para remote None e origin
- decision: revisão de segurança feita à mão sobre git diff origin/main...HEAD (a skill /security-review não está disponível neste runtime): sem achado; o conjunto varrido com tip desconhecido é igual ao do caso sem tip, e um campo não-hex (ex.: --all, que antes depois de --not zerava a varredura) já não chega ao rev-list como opção
- local_sha do stdin do pre-push segue sem validação hex em _commits_to_push (um campo como --all chegaria ao rev-list como opção); e em repositório sha256 o ZERO_SHA de 64 zeros não é reconhecido como delete — fora do escopo da 2265
- promoted: 2275 — local_sha sem validação hex e delete sha256 não reconhecido
## Outcome

Entregue: `_commits_to_push` (`quenching/assets/bin/quenching/common/leak.py`) só usa a `remote_sha` como corte (`--not <sha>`) quando ela é um nome de objeto hex completo (40 ou 64 dígitos) que este clone resolve como commit (`git cat-file -e <sha>^{commit}`). Um tip remoto ausente do clone — o remoto andou e nada foi buscado — ou um campo não-hex cai no mesmo recorte de ref nova (`ZERO_SHA`), então `cq leak --pre-push` e `cq identity --pre-push` julgam em vez de recusar com exit 2, e a varredura nunca fica menor do que no caso sem tip. Testes: `test_leak_scan.py::test_an_old_tip_this_clone_lacks_is_judged_as_a_new_ref` (igualdade com o caso `ZERO_SHA`, com e sem `--remote`, para sha desconhecida, `--all` e `HEAD~1`) e `test_identity_cli.py::test_pre_push_over_an_old_tip_this_clone_lacks_judges_instead_of_refusing`.

Ficou de fora (capturado como spec à parte): `local_sha` do stdin do pre-push segue sem validação hex, e em repositório sha256 o delete de 64 zeros não é reconhecido como `ZERO_SHA`.

Para o próximo leitor: a regra é "tip desconhecido ⇒ julgar como ref nova", nunca "tip desconhecido ⇒ recusar"; revisão de segurança registrada em `## Discoveries`. Revisada, destilada (nada a cruzar para `/docs/`: correção local sem decisão nova de padrão), pronta para o merge.
