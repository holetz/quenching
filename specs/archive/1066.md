## Problem

The `design`, `ops` and `proof` fronts repeat a stabilized mold across roughly 44 versioned files, while the conductor and its test encode front order through a literal list and section ordinals. The plugin needs one shared mold bounded by legitimate membership and one declared ordering source that the conductor test can verify without transcription drift.

## Proposal

- One canonical front mold will define the minimum contract for a front declaration, its cq front route, its disposition bands, its align and status command bodies, and its Codex translation. It will separate shared invariants from per-front deltas and will not invite any key that only one writer may set.
- The design, ops and proof fronts will each declare their mold-covered fields and their deliberate deltas without changing the meaning of their existing source, inventory, verifier, or repair contracts. Any design-specific exception will be explicit and testable.
- The root align conductor will carry one ordered declaration of its currently shipped local fronts and a distinct applicability stage before front inventory. Its contract test will derive the order from that declaration rather than from section ordinals or duplicated literal call lists.
- The plugin source and Codex mirror will remain in lockstep for every changed command body and front reference, with a measured baseline and a reported reduction in duplicated front-shape work for the first consumer after this extraction.
## Out of Scope

- Minting or implementing toolchain, delivery, or security. Those are the Phase C child specs named by umbrella 1057; this spec may establish the insertion rule but creates none of their routes.
- Changing the domain semantics of design projections, ops entry points and registries, proof layers and gates, or any finding vocabulary. This spec extracts their common shape; their owners remain responsible for meaning.
- Extracting a generic Python implementation or dispatcher for the three fronts. Their payloads and domain models differ; the shared artifact is the contract and authoring shape, not a second runtime authority.
- Rewriting README command counts, install profiles, the operating model, command catalogs, or other broad surface claims. Those are A2, A3 and C6 work in umbrella 1057.
- Touching product code, release/version files, the provider-owned document of any other spec, or any file under docs/ that is not declared in ## Impact.
- Resolving the pre-existing docs warnings that are unrelated to the front mold or conductor order. They are parked as a discovery for the owning knowledge alignment.

## Design

### Common mold and deliberate deltas

The mold has one binding minimum and leaves domain content to the front owner:

| Artifact | Minimum contract | Permitted delta |
| --- | --- | --- |
| Front declaration | owned tree, boundary, configuration home, applicability, read model, verifier, align, status, and finding ownership | the tree, configuration keys, verifier payload, and domain-specific boundaries |
| cq front route | normalized cq front entry point, help, JSON output, typed exits 0/1/2, explicit refusal, and stable status/doctor verbs | extra verbs such as build, render, inventory, readme, or ratchet when that front owns them |
| bands.md | mechanical, structural, and judgement disposition mapping, with evidence and the command that closes a human-owned item | a front may declare no mechanical code, but must make that absence explicit rather than inventing a repair |
| align body | probe before inventory, applicability classification, one plan/authorization, bounded ownership-safe writes, the same closing verifier, and a report with residuals | design source arbitration, ops registry/entry-point repair, or proof layer/floor/CI treatment |
| status body | read-only payload, explicit missing/refused/not-applicable states, finding codes and bands, and the closing owner for actionable residue | the front's authoritative evidence rows |
| translation | the source command/reference remains canonical and the Codex surface mirrors its contract | only the language/harness spelling and generated path required by the Codex front |

The rule from shared-mold-keys.md is applied to front configuration and metadata: a key that only one front or command may write stays in that owner's contract. The mold is not a second configuration schema. The report-mold standard remains the separate owner of emitted report shape.

The current evidence supports the common minimum. design has a DTCG source and generated projections, optional Impeccable input, and human source arbitration; ops has a declared root/router, inventory, generated registry, and typed entry-point checks; proof has a declared test root, layers, fixtures, measured roots, floors, CI and order evidence. Their differences are payload and decision ownership, not permission to omit the common probe/status/align boundary.

### Runtime reference and source of truth

The canonical binding mold must have one host. The target-facing architecture standard and the executor-facing front-align reference may divide audience-specific explanation, but neither may restate a competing binding contract. The host choice remains in Open Decisions until the reader-call and maintenance-cost measurement is made. A mirror under plugins/quenching-codex/references/front-align/ is translation/projection only and is checked as such.

No shared Python module is introduced. design/cli.py exposes source/build/render/doctor/status operations, ops/cli.py exposes inventory/doctor/status and registry writes, and proof/cli.py exposes inventory/doctor/status/readme/ratchet. The mold therefore specifies the common route floor and declares extra verbs as front-owned deltas.

### Conductor order and applicability

The executable declaration is the ordered front table in plugins/quenching/commands/align.md, because it is the body that conducts the fronts. docs/standards/architecture/align-surface.md records membership, dependency edges and alignless pillars without becoming a second executable list.

The current declaration remains:

knowledge -> design -> components -> ops -> proof

The 1057 dependency graph reserves the future insertion rule:

knowledge -> design -> components -> toolchain -> ops -> proof -> delivery

but this spec does not write toolchain, delivery, or security command names into the current conductor. A future consumer inserts a front by editing the one declaration and its dependency edges, then regenerates its translation and contract evidence.

The workflow uses named stages rather than numeric front ordinals:

1. applicability probe for every declared front;
2. one run plan and authorization;
3. one named stage per applicable front in declaration order;
4. re-probe and bounded convergence decision;
5. consolidated report.

An absent or unconfigured front is reported as not applicable only when its applicability probe supplies no signal. A present front with no findings is conformant; an explicitly scoped front is skipped; neither state is turned into drift. The conductor invokes each front body and does not reimplement its verifier or repair logic.

The order test parses the declaration table, extracts the named front routes, and asserts that the named workflow stages follow that sequence, including ops before proof. It must not rely on strings such as Front 4 or Front 5, section ordinals, or a second literal list. Because the conductor is a Markdown instruction surface rather than an executable dispatcher, the test claims structural contract evidence only; an actual invocation harness is an Open Decision, not an invented runtime proof.

### Decisions the design makes

- The mold is a minimum contract, not a cloned template. A front-specific field is added only when that front owns its meaning and closure.
- The root conductor owns one order declaration; the architecture standard explains why, and the test consumes the declaration instead of transcribing it.
- Applicability is a first-class conductor stage. It precedes inventory and distinguishes unavailable, skipped, conformant, and findings-bearing fronts.
- Design, ops and proof keep their existing domain references. The shared mold is cited by the six source command bodies and their Codex mirrors; it does not erase the domain references they already need.
- The first consumer after extraction measures its footprint against the current roughly 44-file baseline. A smaller number is evidence of reuse; a green static test alone is not.
- The only frontmatter record this pass earns is refined mode compose. The existing per-section verification policy remains in force; approval and complexity remain outside this autonomous sub-agent's authority.
## Alternatives Considered

- Keep one manually maintained front list and patch the order test whenever a front changes. Rejected because the current test asserts ["ops", "ops", "proof", "proof"] and section ordinals; the same transcription drift would recur when the next front is added.
- Extract a generic Python conductor or a shared front runtime. Rejected because the root conductor is a Markdown instruction surface and the three routes expose materially different payloads and extra verbs; a runtime dispatcher would become a second authority.
- Give each front its own complete mold with no common contract. Rejected because design, ops and proof already repeat a stabilized shape across roughly 44 versioned files per front and the next two fronts would reproduce it before being unwound.
- Put applicability logic inside each front's numbered workflow and leave the root workflow as prose. Rejected because applicability is a dependency decision owned by the conductor and must be observable before inventory; distributed copies invite a front to be inventoried when it is unavailable.
- Mint the new axes while extracting the mold and ordering proof. Rejected because 1057 explicitly makes B1 and B2 Phase B prerequisites for Phase C; this spec must not create routes whose child specs have not built them.
- Place every front-specific field into the common mold with a note explaining who writes it. Rejected by shared-mold-keys.md: an annotation does not stop a fill-in invitation, so a single-writer key remains in its owner's contract.

## Risks

- The mold may overfit three existing fronts and constrain the fourth. Mitigation: make the contract a minimum with explicit deltas, record the design exception if needed, and require the first new consumer to measure a smaller footprint rather than accept analogy.
- The target-facing standard and executor-facing reference may become two authorities. Mitigation: decide one binding host by reader/maintenance measurement, make the other a projection, and add a structural test for duplicated binding markers.
- The order test may prove only Markdown shape while the model still invokes a front incorrectly. Mitigation: inspect the existing session harness; add runtime evidence only if it observes real Skill invocation, and otherwise state the static boundary rather than claiming more.
- Promoting applicability to a stage may accidentally turn an absent front into a failure or an installed clean front into not-applicable. Mitigation: preserve the explicit states and test each branch against the existing root conductor wording.
- Codex translation can drift after the English source changes. Mitigation: source files remain canonical, translate/check runs after source changes, and the affected skill/reference pairs are named in task metadata.
- Generated architecture indexes can omit the new standard or preserve stale descriptions. Mitigation: update their generated zones as an explicit final task and run the docs validator, retaining the known baseline warnings.
- The work can grow into README counts, installation profiles, or future front implementations. Mitigation: those surfaces are explicitly out of scope and belong to 1057's named sibling specs.
- The measured roughly 44-file baseline is approximate and may be stale. Mitigation: task 1.1 records the exact git-tracked baseline and the validation report carries both the source and the date.
- Existing docs validation warnings can mask a newly introduced error. Mitigation: compare the before/after error set, require no new errors, and do not call the warning-bearing baseline clean.
