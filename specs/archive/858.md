## Overview

`/quenching:specs:conclude` empurra o branch, abre o PR e mergeia — hoje, sem nunca perguntar ao
GitHub se os checks do PR estão verdes. Esta spec faz essa rota esperar, num orçamento que ela
mesma controla em vez do `--watch` sem limite do `gh`, por um estado real dos checks antes de
mergear por cima dele. `## Problem` explica por que a spec original deixou isso sem medir;
`## Design` explica por que branch protection não pode ser usado no lugar disso; `## Impact` e
`## Tasks` levam a mudança para dentro de `conclude.md` e de `plan-git-record.md`, com o orçamento
do poll e o filtro `--required` decididos nas próprias tasks (`## Open Decisions`), porque nenhum
repositório ao alcance desta spec tem CI de verdade para medir contra.
## Problem

A rota pull request de `/specs:conclude` mergeia com `gh pr merge` sem consultar os checks do PR.
A spec `rework-specs-isolate-flow`, que construiu a rota, registrou isto como Decisão Aberta 1 e a
deixou **sem medir** — aquela passada escolheu a rota local, então a rota PR embarcou na 4.11.0 sem
nunca ter rodado ponta a ponta.

As duas pontas continuam como estavam:

- `gh pr checks --watch` bloqueia a run por minutos e **pode não terminar nunca** num repositório
  sem CI;
- ignorar os checks mergeia por cima de um vermelho que o humano veria na tela seguinte — e o gate
  `## Validation` que roda na branch não substitui isso, porque mede o que o repo declara e não o
  que o host executou.

**Como a spec original dizia que se decide:** medindo numa run real deste repositório, que tem
remote GitHub e nenhum workflow de CI hoje. Se `gh pr checks` responde "no checks" de imediato,
esperar é grátis quando não há o que esperar, e a decisão cai sozinha para esperar. Essa medição
ainda não foi feita.

Nota de escopo herdada: `## Out of Scope` da spec original exclui **deixar o CI do PR substituir o
gate `## Validation`**. O gate continua rodando na branch, antes do merge, porque é lá que uma falha
ainda tem onde ser consertada. A pergunta aqui é se o status dos checks do PR **também** bloqueia,
nunca se ele vira o gate.

## Proposal

- A rota PR de `/quenching:specs:conclude` deixa de chamar `gh pr merge` às cegas: antes do merge,
  ela pergunta ao GitHub o estado dos checks do PR e só segue quando eles permitem.
- Essa espera nunca trava o run para sempre: ela nunca usa `gh pr checks --watch` — que não tem
  flag de timeout e pode não terminar nunca, exatamente o risco que `## Problem` nomeia — e sim um
  poll do formato sem `--watch`, num orçamento (intervalo e prazo total) que o próprio `conclude`
  controla.
- Num repositório que não reporta nenhum check (este repositório, hoje — medido: `gh pr checks
  <PR>` responde em bem menos de um segundo com "no checks reported", exit code 1), a espera
  adicionada custa uma chamada, não uma pausa: a previsão da própria spec original — "esperar é
  grátis quando não há o que esperar" — se confirma, medida.
- Um check ainda `pending` quando o orçamento acaba, ou um check que já reporta falha, interrompe o
  run do mesmo jeito que um estado inesperado do PR já interrompe hoje depois do merge
  (`conclude.md:404-407`) — reportado como finding, nunca reparado chamando `gh pr merge` de novo
  às cegas.
- O gate `## Validation` continua correndo primeiro, na branch, sem mudança — exatamente como a
  nota de escopo herdada exige.

## Out of Scope

- Os checks do PR substituírem o gate `## Validation` — herdado, verbatim, da spec que abriu esta
  decisão (`rework-specs-isolate-flow`); `## Validation` continua rodando na branch, antes deste
  passo, porque é lá que uma falha ainda tem onde ser consertada.
- A rota local de merge (`git merge`/`rebase`/`fast-forward` dentro de `conclude.md`) — ela nunca
  chama `gh pr merge` e não tem checks de PR para ler; esta spec só toca o merge da rota PR.
- Configurar, instalar ou recomendar CI num repositório-alvo — se um repositório tem algum workflow
  é decisão dele; esta spec só muda como `conclude` reage ao que `gh pr checks` reportar, inclusive
  "nada".
- Confiar em branch protection / required status checks do GitHub como o mecanismo de proteção —
  medido como indisponível neste próprio repositório (privado, plano gratuito: `gh api
  repos/holetz/claude-quenching/branches/develop/protection` responde 403 "Upgrade to GitHub Pro or
  make this repository public to enable this feature") e não garantido em nenhum repositório-alvo
  onde `conclude` roda, então o check que esta spec adiciona não pode ser dispensado sob a teoria de
  que o GitHub já garante isso.
- Reformular a própria máquina de política do `## Validation` (`per-task`/`per-section`/
  `end-of-plan`) — a espera pelo CI é um gate novo e separado, no momento do merge, não um valor a
  mais para aquele campo.

3. `cq specs validate --spec wait-for-pr-checks-before-merge` fecha em 0 erros, 0 avisos, com

4. O ramo `pending` → poll → orçamento esgotado → reportar como finding sem mergear não pode ser

   repositório-alvo com CI de verdade).

## Design

1. **Nunca `gh pr checks --watch`.** `gh pr checks --help` não documenta nenhuma flag `--timeout`;
   `--watch` faz poll até os checks terminarem ou para sempre — exatamente o risco "pode não
   terminar nunca" que `## Problem` nomeia. A espera que esta spec adiciona precisa ser limitada por
   um orçamento que o próprio `conclude` controla, não pelo watch do `gh`.
2. **Poll limitado sobre a forma sem `--watch`.** `gh pr checks <number>` sem `--watch` é uma
   leitura pontual, com exit code próprio para o caso pendente (`gh help exit-codes` mais o help do
   próprio comando: exit `8` = "Checks pending", distinto de `0` passou / `1` falhou-ou-nada-a-
   reportar). Medido neste repositório (PR #958, #956 — ambos mergeados sem CI configurado): a
   chamada volta em ~0,7s reportando "no checks reported" em exit `1`. Fazer poll dessa forma num
   intervalo que `conclude` controla, e parar o loop no orçamento do próprio `conclude`, dá uma
   espera limitada sem a espera ilimitada do `gh`: `0` → segue para o merge, `1` → para e reporta
   (uma falha real, ou nada a checar — mesmo tratamento de um repositório sem CI, então os
   repositórios de hoje pagam uma chamada), `8` → dorme e faz poll de novo até o orçamento acabar,
   depois para e reporta em vez de mergear às cegas.
3. **Branch protection não é substituto.** `gh pr merge --help` documenta `--admin` como "use
   administrator privileges to merge a pull request that does not meet requirements" — o que implica
   que, num repositório com required status checks configurados via branch protection, um `gh pr
   merge` simples (sem `--admin`, que não é passado aqui) já se recusa a mergear antes deles
   passarem, e a asserção pós-merge que `conclude.md` já faz (o estado precisa ler `MERGED`) já
   captura essa recusa como finding. Mas este repositório — privado, GitHub no plano gratuito — nem
   consegue configurar branch protection (`gh api
   repos/holetz/claude-quenching/branches/develop/protection` → 403 "Upgrade to GitHub Pro or make
   this repository public to enable this feature"), então, exatamente no tipo de repositório onde
   este plugin roda hoje, essa rede de segurança não existe e `gh pr merge` mergeia sobre vermelho
   sem condição nenhuma. O check que esta spec adiciona não é redundante com branch protection; é a
   única proteção disponível num repositório que não pode comprar a outra.
4. **Onde entra.** Dentro do bloco "Every other run → merge now" de `conclude.md` (o par `cq specs
   record ... merge` / `gh pr merge`, `conclude.md:377-382`) — depois do PR criado, antes de `gh pr
   merge` ser chamado. A parada da rota PR sob o minimal-gear do cycle (`conclude.md:372-375`, que
   nunca chama `gh pr merge` e espera revisão humana) fica intocada: não há o que fazer poll para um
   run que nunca tenta o merge.

## Alternatives Considered

- **`gh pr checks --watch [--fail-fast]` antes do merge** — rejeitado: sem limite para a espera
  quando os checks ficam pendentes e nunca resolvem (`--fail-fast` só encurta o caso de falha, não
  o caso "pendente para sempre"), exatamente o risco com que `## Problem` abre.
- **Uma única leitura pontual de `gh pr checks` logo depois de abrir o PR, sem repetir** —
  rejeitado: o comportamento medido mostra os checks quase sempre ainda `pending` (exit 8) nos
  segundos seguintes à abertura do PR, então uma única leitura quase nunca veria um resultado real
  e compraria quase nada sobre não checar de jeito nenhum.
- **Confiar em branch protection / required checks do GitHub em vez de adicionar um check aqui** —
  rejeitado: este repositório nem consegue habilitar branch protection no plano atual (medido: 403
  na API de proteção), então o mecanismo de que esta alternativa depende está indisponível
  exatamente nos repositórios onde `conclude` mais roda; ver `## Design` ponto 3.
- **Não fazer nada (manter como está)** — rejeitado: deixa a lacuna que `## Problem` nomeia, e a
  rota PR não é hipotética — ela já mergeou PRs reais neste repositório (#958, #956, entre outros)
  sem nunca checar o status.

## Open Decisions

- O intervalo do poll e o orçamento total (quantos segundos entre polls, quanto tempo até
  `conclude` desistir e reportar "ainda pendente" em vez de mergear) não têm precedente em nenhum
  lugar deste repositório — grep em `assets/references/` e `README.md` não achou nenhuma convenção
  de timeout/intervalo para `gh` ou CI, e este repositório não tem CI para medir. A própria política
  do `## Validation` (`per-task`/`per-section`/`end-of-plan`) é deliberadamente declarada por cada
  spec, e não fixa, pela razão já registrada de que "the spec's author is the only party who knows
  whether this repo's suite takes four seconds or forty minutes" (`execution.md`, "Why the spec's
  author declares the policy") — a mesma razão vale aqui: nenhuma passada desta spec tem, ainda, a
  duração real do CI de um repositório-alvo para medir contra. **Decidido em** `## Tasks` 2.1,
  durante `/quenching:specs:execute` — ancorado numa amostra real de duração `pending` de `gh pr
  checks --json` de um repositório que rode CI de fato por esta rota, se houver um disponível no
  momento; na falta dessa amostra, task 2.1 adota a mesma forma declarada-e-não-fixa que
  `## Validation` já usa em vez de inventar um número que ninguém mediu, e crava o valor e a razão
  no próprio bloco.
- Se o poll deve respeitar `--required` (só os checks marcados como obrigatórios) ou ler todos os
  que `gh pr checks` reportar, inclusive os informativos/não-obrigatórios — nenhum repositório ao
  alcance desta passada tem um conjunto misto de checks obrigatórios/opcionais para medir a
  diferença. **Decidido em** `## Tasks` 2.2, na mesma execução, junto com a questão do orçamento
  acima.
## Risks

- Os valores de intervalo e orçamento do poll (tasks 2.1/2.2) são decididos sem uma amostra real de
  duração de CI, porque nenhum repositório ao alcance desta spec roda CI hoje — um orçamento curto
  demais interrompe uma suíte legitimamente lenta, um orçamento longo demais devolve o custo que
  `## Proposal` promete evitar num repositório sem CI. ACCEPTED — os valores e a razão ficam
  escritos ao lado do bloco (task 2.1), documentados como provisórios via `## Open Decisions`, e
  revistos assim que um repositório-alvo com CI de verdade exercitar a rota.
- O ramo `pending` → timeout nunca roda ao vivo nesta spec, por falta de CI neste repositório.
  ACCEPTED — mitigado por inspeção de código linha a linha contra os exit codes documentados (`0`
  passou, `1` falhou-ou-nada-a-reportar, `8` pendente) e revalidado ao vivo na primeira vez que a
  rota rodar contra um repositório-alvo com CI (ver `## Validation` ponto 4).
- Um branch feito por prosa/string matching (por exemplo, procurar o texto "no checks reported" na
  saída) quebraria silenciosamente se uma versão futura do `gh` mudar essa mensagem. Mitigação:
  branch estritamente pelos exit codes documentados (`0`/`1`/`8`), nunca por texto — task 1.1 é
  escrita e revisada contra essa regra.
- Adicionar uma chamada (e, num repositório com CI lenta, possíveis sleeps) ao passo de merge da
  rota PR aumenta o tempo de parede de `/quenching:specs:conclude` nesse caminho. Mitigação: o
  orçamento é próprio e explícito (`## Design` ponto 2), então o teto que isso soma a qualquer
  `conclude` é conhecido de antemão — ao contrário de `gh pr checks --watch`, que não oferece teto
  nenhum.

## Discoveries

- artifacts.md's worked example for `## Impact`'s parsed sub-heading reads '### Standards this spec will write into knowledge/standards/' (no leading /.), but schema.json's actual parsedSubheading is '### Standards this spec will write into /.knowledge/standards/' — a spec that copies the doc's example verbatim gets an anchor regex that never matches, so parse_impact_standards silently returns nothing and sp-impact-uncovered never fires for it.

## Outcome

Abandonada. A premissa era um poll de `gh pr checks` antes de `/quenching:specs:conclude` mergear pela
rota PR — protegendo o `gh pr merge` que a spec `rework-specs-isolate-flow` deixara sem essa
checagem. Esse `gh pr merge` não existe mais no lugar que esta spec mirava: o `conclude.md` de hoje
para no passo 6 depois de provar o gate `## Validation` verde na branch, e só recomenda
`/quenching:git:pr:create` ou `/quenching:git:merge` na sequência — nunca os invoca. Nenhum comando
do plugin chama `gh pr merge` hoje; `git/merge.md` é merge local puro e `git/pr:create.md` abre o PR
e para, deixando o merge (e portanto os checks do PR) inteiramente para fora da automação.

Sem um `gh pr merge` automático em algum ponto da superfície, não há mais o que proteger com um
poll de checks — o mecanismo que esta spec queria interpor desapareceu junto com o alvo que
protegia. A decisão aberta de intervalo/orçamento de poll (`## Open Decisions`) fica sem objeto.

Se um comando voltar a chamar `gh pr merge` automaticamente no futuro, a pergunta original —
esperar os checks antes de mergear — deve ser reaberta como spec nova, contra o desenho que existir
então.
