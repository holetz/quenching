## Problem

Spec 2185 gave an epic the list of its members. The other end stayed silent: open `1025690` in the
SAFRA store and the panel shows a spec with no edges, no composition and no tab — nothing says it is
`S1` of epic `1025689`.

The store cannot answer that today without reading every document. Composition lives in the
composite's `## Tasks`, and `epic_ref` — the `epic:` frontmatter key a member could carry — is
documented in `parse/epics.py` as *deprecated and ignored*. So `cq specs list --lean` reports
`epic: null` even for a member (verified on `1025690`), and there is no verb that reads the link from
the member's end.

Composition is a property, not a type: a spec may belong to several composites and composites may
nest. Whatever answers this must render a list, not a single parent.

## Proposal

Two pieces, and one bulk read that was already being made:

1. **`cq specs schedule --all` also emits `composites`** — a reverse index from a member's id to the
   composites that name it, each entry carrying the composite's id, the member's label and its group.
   The verb already reads every document through `_infos`; the index is a pure derivation over the
   `## Tasks` it has in hand, so it costs no second read of the store.
2. **A "Parte de" block in the panel's Dependências tab**, above the composition and the two edge
   lists: every composite that names this spec, with the composite's title from the graph and the
   label it gave the member (`1025689 · S1`), each row one click away.

The tab appears for a member too: `hasView` gains membership, so `1025690` opens on a tab that says
`S1 de 1025689` where today it shows nothing. A member of several composites lists all of them.

## Out of Scope

- Writing membership from the panel. `cq specs link add|remove` stays the only writer.
- Making `epic:` authoritative again. The key stays deprecated; the link is read from the composite.
- The forward view's data path: the composition still rides `status --spec`, and the epic's member
  block is unchanged.
- Cross-repository members (`owner/repo#id`) in the reverse index: the panel reads one store, and an
  item whose id is not in this store's payload is skipped rather than shown as a broken row.
- Task-level edges and the portal's own epics page.

## Design

- **The derivation.** `reverse_index(infos)`: for every spec in the store, `parse_items` its `## Tasks`
  and, for each item whose `spec` is a key of `infos`, append `{epic, label, group}` under that id.
  Pure, no I/O, ordered by the composite's id so two reads of the same store always agree.
- **The payload.** `composites: { "<id>": [{epic, label, group}] }`, emitted only with `--all`: the
  default selection is a subset of the store and an index over a subset would lie about the whole.
- **The panel.** `Detail.epics` is `{epic, title, label, group}[]`, resolved against the graph's nodes
  so the title comes free; an id the graph does not hold is dropped, as `neighbors` already does for
  `dependsOn`.
- **The wording.** "Parte de" — composition again, never a dependency. The label is the composite's
  own (`S1`), which is how the epic's Tasks read.

## Alternatives Considered

- **A `status --member <id>` verb.** Symmetrical with `status --epic`, and it would read the whole
  store once per opened spec — the panel's cost model is built on one cached bulk read, not one per
  open.
- **A second bulk verb (`cq specs map`).** Cleaner separation, and a second 0.9 s process for data the
  schedule already has in memory.
- **Reading `status --epic` for every composite.** `load_epic` is cheap per composite, but the panel
  would pay N processes per cache window as the number of epics grows.
- **Reviving the `epic:` frontmatter key on the member.** It would be free to read and wrong: it is
  deprecated, it holds one parent where composition allows several, and it would drift from the
  composite's own `## Tasks` the moment either side changed.

## Open Decisions

- none — the index rides `--all`, the panel resolves titles from the graph it already has, and the
  block sits above the composition. All three follow from the cost model stated above.

## Risks

- **Payload growth.** A store with many composites grows the schedule by a few hundred bytes per
  member, inside the 8 MB ceiling by orders of magnitude at this repository's scale.
- **A composite whose member moved.** The index skips an id the store does not hold, so a stale
  reference disappears from the member's side instead of pointing nowhere; `validate` owns reporting
  the broken reference from the composite's side.
- **Two sources of the same fact.** The epic's block comes from `status --spec`, the member's from the
  graph; both derive from the same `## Tasks`, and the bench reads both from one stub to keep them
  honest.

## Handoff

- **Built:** the three tasks below; the last refreshes the deployed surface and runs the gate.
- **Decisions taken at build:** the index emitted by `schedule --all` rather than a new verb; titles
