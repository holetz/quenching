## Problem

Medido em 2026-11-25, no épico 453. `specs_next(epic=453)` devolveu `count 0, readyTotal 0, remaining 12` com **oito membros executáveis** sob autonomia (455, 456, 457, 458, 459, 461, 462, 465) — porque nenhum estava em `ready`/`approved`: todos estavam `captured` e o develop autônomo é passo do worker. O passo 1 do protocolo do `spec-orchestrator` diz "Build a DAG from `specs_next(epic=<id>)`"; uma execução literal veria um épico sem nada a fazer e devolveria `blocked`. O condutor montou a DAG pelo `epic_progress`, que mostra os membros, o `after:` e o estado derivado.

## Proposal

`cq specs next --epic <id>` (e a ferramenta MCP) lista os membros cujo `after:` já foi mesclado e cujo stage está abaixo de `approved` como **`needs-develop`**, desde que a chamada declare autonomia (`autonomous`/`--autonomous`), mantendo o comportamento atual sem ela. O protocolo do `spec-orchestrator` passa a citar `specs_next(epic=, autonomous=true)` e a manter `epic_progress` como a fonte do `after:`/grupos.

Prova: um teste do store com um épico de membros capturados — sem autonomia 0 prontos, com autonomia os membros sem dependência pendente.

## Out of Scope

- Changing what `ready`/`approved` mean or what `epic_progress` reports: the status derivation stays; only the `next --epic` listing gains the opt-in view.
- Developing the members: the worker's autonomous develop does that; the listing only says which members are eligible for it.
- A new verb: the flag rides on the existing `next --epic`.

## Impact

`quenching/assets/bin/quenching/specs/` (o verbo `next`), o adaptador MCP de specs, `quenching/agents/spec-orchestrator.md` (passo 1) e o teste do store.

## Validation

- `python3 -m unittest discover -s quenching/tests -p test_specs_epics.py` passes, including a test where an epic of captured members yields 0 ready without `autonomous` and, with it, exactly the members whose `after:` is done, each flagged `needsDevelop`.
- `bash scripts/verify_repo.sh` (scoped to the affected diff when closing) stays at zero errors.

## Design

- **A flag on the existing verb.** `cmd_next_epic` reads `getattr(args, "autonomous", False)`; the default keeps every current caller and test untouched. Per epic 515's decision, the word becomes the optional parameter `autonomous=true` / `--autonomous`.
- **Eligibility.** With the flag, the listing also takes the items `derive_epic` marks `not-ready` (open, no pending `after:`, not approved, ready gate not met); each row carries `needsDevelop: true` and the same `status`/`stage` fields as before. Items `waiting`, held or done never appear. `readyTotal` and `count` include them; ordering is unchanged.
- **No derivation change.** `derive_epic` and `epic_progress` stay as they are, so the portal and status do not move.
- **Binding contracts.** MCP tool names and verbs stay in lockstep with the CLI (`mcp/coverage.py`): the new parameter has the CLI flag's own name, so no coverage exemption is needed.

### Assumptions

- A member that is `not-ready` is eligible for develop whatever the reason (captured, proposed, designed) — section: Proposal.

## Alternatives Considered

- Make `ready` include captured members always: rejected, the non-autonomous caller would hand a worker a spec nobody developed.
- Teach the orchestrator to derive the DAG from `epic_progress` alone: rejected, it leaves `next --epic` returning a misleading zero and duplicates the ready derivation in prose.

## Open Decisions

- none — the parameter name is decided by epic 515 (2026-11-25): `autonomous=true` / `--autonomous`.

## Risks

- A caller passes `autonomous` without really running develop: the rows say `needsDevelop`, so the mismatch is visible. ACCEPTED — the flag is the caller's declaration, as everywhere else.
- The extra row field breaks a strict consumer: ACCEPTED — additive, no consumer in the repo reads exact keys.
