## Problem

Achado de segurança reproduzido pela revisão do 594 (ses_de77e503). Em quenching/assets/bootstrap/bootstrap.py:447-453, o laço faz backup e aplica um item por vez. O nome do backup vem só do caminho de origem (:405) e o copy2 acontece em :407. Quando opencode-depth (:239) e opencode-plugin (:262, target = existing[0]) estão ambos todo no mesmo opencode.json global, o segundo backup sobrescreve o primeiro com o arquivo já editado. O original some, o que quebra a promessa de docs/standards/architecture/deploy-mode.md:366-367. Correção: fazer o backup de cada caminho uma vez só, antes de qualquer apply (o primeiro backup vence), com um teste de dois itens no mesmo arquivo provando que o backup guarda o conteúdo original.

## Proposal

- `bootstrap --write` backs up every path it will change exactly once, before the first apply; when two items write the same file, the backup holds the file as it was before the run (the first backup wins).
- A test with two `todo` items on the same global `opencode.json` (`opencode-depth` and `opencode-plugin`) proves the single backup carries the ORIGINAL content.
- The deployed copy under `.agents/quenching/assets/bootstrap/bootstrap.py` matches the source.

## Out of Scope

- Changing the backup directory layout or the file-name scheme of `back_up` — the name already comes from the source path, and a stable name is what makes "once per path" checkable.
- Merging `opencode-depth` and `opencode-plugin` into one item — it would fix this collision but not the class (any two items on one path), and changes the report's items.
- Rolling back applied items when a later item fails — a separate promise that `deploy-mode.md` does not make.

## Impact

### Product code this spec expects to touch

- `quenching/assets/bootstrap/bootstrap.py` — the `--write` loop in `main` (backup pass before the apply pass)
- `quenching/tests/test_bootstrap_script.py` — the two-items-one-file regression test

- Invariant still holding: `--check` writes nothing; a second `--write` with everything done writes nothing.

## Design

- **Backups are a pass of their own, before any apply.** `main` first walks every `todo` item's `writes`, backing up each path once (keyed by `str(Path(path))`), and only then runs the applies. The first backup of a path wins, so it always holds the content before this run — the promise of `docs/standards/architecture/deploy-mode.md` ("backs up each existing file it will change … then applies").
- **The key is the normalized path, not the backup name.** Two writes naming the same file through a `str` and a `Path` collapse to one key; the backup file name keeps coming from `back_up` unchanged.
- **Binding contracts:** `docs/standards/architecture/deploy-mode.md` §bootstrap (`--write` lists, backs up, then applies); the deploy regenerates `.agents/quenching/assets/bootstrap/bootstrap.py` from the source, so the source is the only edit.

### Assumptions

- `item["writes"]` already lists every file an apply changes (true for the current items; checked by reading `plan_*`) — `## Design`, `## Tasks` 1.1.

## Alternatives Considered

- **Skip a backup when the target backup file already exists** (guard inside `back_up`) — rejected: it would still interleave backup and apply, so the guard is the only thing standing between a later item and an already-edited file; a separate pass makes "before any apply" structural.
- **Timestamped/suffixed backup per item** — rejected: keeps every intermediate state but leaves the user to guess which copy is the original.

## Open Decisions

- none — the epic 616 `## Design` fixes the shape (one backup per path, before any apply) and the code answers the rest.

## Risks

- A future item whose `apply` writes a file it does not declare in `writes` would escape the backup pass — ACCEPTED: the same gap exists today; the declaration is the contract the listing already prints.
- The test depends on both OpenCode items targeting `opencode_files()[0]` — mitigated: the test builds exactly that machine (global `opencode.json` with an `experimental` block and a vitrine checkout) and asserts both items are `todo` on it.
