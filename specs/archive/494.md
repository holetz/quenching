## Problem

No spec-runner autônomo da 189 (2026-11-25), `specs_validate(spec=189)` foi recusado pelo schema MCP com "spec: Expected string", enquanto `specs_status`, `specs_section_write` e `specs_record` aceitam `spec: string | number` na mesma sessão. O mesmo vale para `specs_parallel`, `specs_claim_acquire(claim_id)` e `specs_next`, que pedem string. Um execute() que encadeia a escrita e o validate perdeu a chamada inteira e teve de ser repetido. O conjunto de tools `specs_*` tem de aceitar o id do spec no mesmo tipo em todas.

Minimal fix proposed: declarar `spec: string | number` (coagido para string) em todas as tools `specs_*` que recebem um id.

**Insumos**

- Catálogo MCP do servidor `quenching`: assinatura de `specs_validate` (`spec: string`) versus `specs_status` (`spec: string | number`)
- Erro: `Invalid arguments for tool "quenching_specs_validate": - spec: Expected string`
- Spec 189, passo 7 do develop autônomo

## Proposal

- Toda tool do catálogo `quenching` cujo argumento é um id de spec (`spec`, `spec_id`, `claim_id`) aceita string ou inteiro, como `specs_status` já aceita.
- `specs_validate(spec=494)` deixa de ser recusada pelo schema; o id inteiro chega ao verbo como a string equivalente.
- Nenhuma outra tool muda de tipo: argumentos que não são id de spec continuam estritos.

## Out of Scope

- Tools do adaptador `specs/mcp.py` (`specs_status`, `specs_section`, `specs_record`, …) — já declaram `SPEC` como string|integer.
- Aceitar outros formatos (referência `proj:id`) — o validador de id do verbo continua dono disso.

## Impact

### Product code this spec expects to touch

- `quenching/assets/bin/quenching/mcp/catalog.py` — schema e checagem dos argumentos de id de spec
- `quenching/tests/test_commands_catalog.py` — teste do schema e da coerção

## Validation

- `python3 -m unittest discover -s quenching/tests -p test_commands_catalog.py` sai 0, com um teste que afirma `type == ["string","integer"]` em `specs_validate.spec`, `specs_parallel.spec` e `specs_claim_acquire.claim_id`, e que o argv gerado para `spec=494` carrega `"494"`.
- `python3 -m unittest discover -s quenching/tests -p test_quenching_mcp_coverage.py` continua verde.

## Design

- 2026-11-25 — regra: o catálogo é gerado do argparse de cada verbo; a correção mora num ponto só, `_property`/`_check`/`argv` de `mcp/catalog.py`, e não em cada verbo. Um conjunto fixo `SPEC_ID_DESTS = {"spec","spec_id","claim_id"}` marca os destinos; um argumento escalar string, sem `enum`, com esse destino vira `["string","integer"]`, e o inteiro é coagido a `str` antes do argv. Alternativa descartada: mudar `type=int` nos parsers — quebraria ids com prefixo de projeto.
- 2026-11-25 — política do épico 515: nenhuma camada nova além do conjunto e da coerção.

## Alternatives Considered

- Declarar o tipo em cada linha de `CATALOG` — rejeitada: um campo por tool a esquecer de novo, o atrito que a spec relata.

## Open Decisions

- none — o conjunto de destinos é o que o catálogo imprime hoje (`spec`, `spec_id`, `claim_id`); um verbo novo com outro nome de id decide-se no seu próprio teste.

## Risks

- Um argumento chamado `spec` que não seja id ficaria permissivo demais — mitigação: o teste lista todos os destinos `spec*`/`claim_id` do catálogo e confere que são ids.

## Handoff

Catálogo `mcp/catalog.py` publica `SPEC_ID_DESTS` como string|integer e coage para string; testes em test_commands_catalog.py e test_quenching_mcp.py; mirrors .agents regenerados com cq deploy.
