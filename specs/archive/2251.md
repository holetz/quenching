## Problem

Reproduzido em 2026-11-21 (autopilot, conclusão do PR #89 / spec 2177): no worktree de `plan/2177-sharedpaths-ponto-e-descricao-pr-azure`, `git merge --no-ff origin/main` (merge 2a064d07b, gate verde) e `git push` foi recusado pelo hook pre-push `cq security leak --pre-push` com 30 findings — e-mails de autor/committer fora da lista permitida (`noreply@anthropic.com` em 14 commits, o e-mail do mantenedor em `fadfd9075`, o commit do release 7.6.0). Todos os commits apontados já estão em `origin/main`; o merge commit em si passou na checagem do staged.

Causa: `_commits_to_push` (`quenching/assets/bin/quenching/common/leak.py:249-261`) só exclui o que o remoto já tem quando a ref é nova (`remote_sha == ZERO_SHA` → `--not --remotes=<remote>`). Numa ref existente usa `remote_sha..local_sha`, que inclui os ~357 commits da main trazidos pelo merge — commits já publicados, cujo reexame não protege nada.

Consequência: toda branch de spec que sincroniza com a main por merge (o caminho de `/quenching-git sync` e da conclusão de um PR em conflito) fica impedida de dar push sem `--no-verify`, que o protocolo proíbe. O PR #89 está parado nisso.

Correção esperada: excluir também `--remotes=<remote>` quando a ref já existe (`local_sha --not remote_sha --remotes=<remote>`), com teste da branch existente que recebe um merge da main. Estreita só o que já está publicado; não altera os padrões nem a lista permitida.

## Proposal

Numa ref que já existe no remoto, `_commits_to_push` (`quenching/assets/bin/quenching/common/leak.py:249-261`) passa a listar `rev-list <local_sha> --not <remote_sha> --remotes=<remote>` quando o nome do destino é conhecido: o que o remoto já tem — a ponta antiga da ref e as refs de rastreamento do destino — sai do reexame. Sem `remote`, o intervalo fica `remote_sha..local_sha`, como hoje. Ref nova e ref apagada não mudam. Um teste prova o caso do problema: uma branch existente que recebe um merge da main com um commit que já está em `refs/remotes/<remote>/main` não é mais acusada por esse commit, e um commit novo da própria branch continua acusado.

## Out of Scope

- Os padrões, a denylist, a lista permitida (allowlist) e a ligação dos hooks `pre-commit`/`pre-push` — ficam iguais (épico 2252, Design de 2026-11-21).
- O caminho sem `--remote` (o hook sem o primeiro argumento): continua julgando `remote_sha..local_sha`, porque um commit em outro remoto ainda pode ser novo para este.
- O `--staged` e o `--all` do leak, e os e-mails que o `git config user.email` assina.
- Destravar o PR #89 em si: é de outro agente; esta spec só remove a causa.

## Design

```
hoje   ref existente: rev-list remote_sha..local_sha            → merge da main traz ~357 commits publicados
depois ref existente: rev-list local_sha --not remote_sha --remotes=<remote>   (com --remote)
                      rev-list remote_sha..local_sha                           (sem --remote)
       ref nova:      rev-list local_sha --not --remotes=<remote>  | local_sha  (inalterado)
```

`remote_sha..local_sha` é o mesmo que `local_sha --not remote_sha`; acrescentar `--remotes=<remote>` só remove commits — o conjunto julgado é sempre um subconjunto do atual, nunca maior.

### Assumptions

- As refs de rastreamento do destino refletem o que o remoto tem (o `git fetch` que `/quenching-git sync` e o merge fazem antes do push). Uma ref de rastreamento desatualizada só deixa entrar no reexame mais commits, nunca menos do que hoje. — `## Risks`

## Alternatives Considered

| Abordagem | Custo | Ganho | Fecha |
| --- | --- | --- | --- |
| `local_sha --not remote_sha --remotes=<remote>` (escolhida) | uma linha e um teste | só o que o destino já publicou sai do reexame | nada |
| Julgar só os commits do primeiro pai (`--first-parent`) | pouco | ignora a main trazida pelo merge | perde commits novos que entram por um merge de uma branch não publicada |
| Allowlist de e-mails do `noreply` | config | silencia o caso observado | alarga o que passa e não cobre a denylist de conteúdo |

## Risks

- Uma ref de rastreamento do destino que aponta para um commit que o remoto não tem mais (force push alheio, ref local forjada) tiraria esse commit do reexame. É o mesmo pressuposto que a ref nova já faz hoje (`--not --remotes=<remote>`), e esse commit já esteve no destino.
- `remote_sha` ausente localmente faz `rev-list` falhar como hoje falha com `remote_sha..local_sha`; o comportamento de erro não muda.

## Outcome

**Done — reviewed, distilled, ready for merge.**

What shipped:

- `_commits_to_push` (`quenching/assets/bin/quenching/common/leak.py`) judges an existing ref as `local --not <old tip>` and, when the destination is named (`--remote`, the `pre-push` hook's `$1`), also `--not --remotes=<remote>`. A branch that merged an already published `main` no longer has the base's commits rescanned, so a historic match on the base stops blocking the push. Without `--remote` the range is byte-for-byte the old `old..new`.
- `cq git identity --pre-push` inherits the same range through the shared function (no change of its own).
- Regression test `test_existing_ref_merging_a_published_base_judges_only_what_the_remote_lacks` in `quenching/tests/test_leak_scan.py`: with `origin` only the new work commit is reported; without it both the base and the work commit are.
- `docs/standards/architecture/security-pillar.md` documents the existing-ref range; the deployed copy was regenerated.

Security review (asked by epic 2252): the change only **narrows** the scanned set, never widens what escapes it. `rev-list X --not A B` is a subset of `rev-list X --not A`, and the only added exclusion is commits already reachable from the destination's own remote-tracking refs — the same trust the new-ref case already took. A `--remote` that is a URL or unknown matches no ref and degrades to the old range; `--remotes=<name>` without glob characters implies `/*`, so it is not a prefix match on another remote. A stale tracking ref (branch deleted remotely, not fetched) could exclude a commit the remote no longer has — the accepted limitation shared with the new-ref path; `--all` in the repository gate and CI still scan every tracked file.

Left out: nothing from the Proposal. No release obligation at conclude (`ci-cd/versioning-release.md`: the bump happens only at release).
