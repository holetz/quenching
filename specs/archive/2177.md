## Problem

`cq git worktree link` deriva a pasta-irmã de um `sharedPath` começado por ponto com dois pontos (`.tmp` → `<repo>..tmp`), nome feio e fácil de confundir com `..`. E `cq git pr create` no Azure DevOps manda o corpo inteiro em `--description`, que a API recusa acima de 4000 caracteres ("A description for a pull request must not be longer than 4000 characters"): um corpo de spec longo derruba a criação do PR.

## Proposal

1. `_store_for` tira o(s) ponto(s) iniciais do nome derivado: `.tmp` → `<repo>.tmp`; `a/b` continua `<repo>.a.b`. No `link`, quando a pasta-irmã antiga (`<repo>..<nome>`) existe e a nova não, renomeia a antiga para a nova (mesmo disco, `os.rename`) antes de linkar e informa `migratedFrom` no item; quando ambas existem, recusa com finding claro (`git-worktree-store-conflict`) sem mexer em nada. Um link que aponta para a antiga é repontado pelo `_materialise` atual.
2. `_open_azure`: corpo acima de 4000 caracteres → a descrição leva o corpo cortado na última fronteira de seção (`\n## `) que cabe, mais a nota "Corpo completo no primeiro comentário deste PR." (tudo ≤ 4000); depois de criado o PR, o corpo inteiro vira thread de comentário (markdown, status closed) via `az devops invoke --area git --resource pullRequestThreads ... --http-method POST --in-file <json>`, argv montado no módulo. Falha do comentário não desfaz o PR: vira finding (`commentFinding`) no JSON de saída.
3. `cq specs config` passa a expor `sharedPaths` (hoje `_read_scalars` só lê `worktreeSetup`).

## Out of Scope

- Release ou bump de versão: a versão sobe só na release, no branch primário (`docs/standards/ci-cd/versioning-release.md`).
- Migrar pastas-irmãs de repositórios alvo: cada alvo roda `cq git worktree link` depois de atualizar o quenching.
- Corte do corpo no GitHub, que não tem esse limite prático.

## Design

- O nome novo é `name.lstrip(".") or name`: o fallback evita nome vazio. Só os pontos iniciais do nome inteiro saem, como pedido; `a/.b` segue `<repo>.a..b` (raro, fora do pedido).
- A migração vive no `_link` (ou numa função chamada por ele), antes de `_materialise`, para valer tanto no `link` quanto no `add`. `os.rename` é atômico no mesmo disco, e a pasta-irmã fica sempre ao lado do common dir.
- Outros worktrees com link para a pasta antiga ficam com link pendente até rodarem `link`; o `_materialise` já reponta link pendente (realpath ≠ store).
- O corte usa `rfind("\n## ", 0, limite)` sobre o espaço que sobra depois da nota; sem fronteira que caiba, corta no limite bruto. O limite é contado em caracteres (`len`), o que a mensagem da API declara.
- O thread recebe `project` e `repositoryId` do próprio JSON de resposta do `az repos pr create` (`repository.project.name`/`id`, `repository.id`); o JSON vai num arquivo temporário apagado logo depois. Falta de ids ou exit ≠ 0 → `commentFinding` no payload; o PR segue `ok`.

## Alternatives Considered

- Truncar sem comentário: perde o corpo, que é a revisão humana do PR.
- Mandar o corpo via `az repos pr update`: o mesmo limite vale.
- Mudar a pasta-irmã para dentro do common dir: muda o contrato de isolamento e quebra todos os alvos de uma vez.

## Open Decisions

- none — o pedido do humano fixou os nomes, a migração, a recusa e o formato do thread.

## Risks

- Renomear uma pasta-irmã com dado em uso por outro worktree: o link desse worktree fica pendente até o próximo `link`; mitigado pelo reponte automático e citado no relatório.
- `az devops invoke` com a org não detectada: vira `commentFinding`, nunca falha do PR.

## Handoff

- none — trabalho começa do zero no worktree da spec.

## Discoveries

- decision: `cq specs config` não expunha `sharedPaths` (`_read_scalars` só lia `worktreeSetup`); corrigido na 1.2 por ser trivial e da mesma área: chave `sharedPaths` no JSON (lista, padrão []) e linha no texto; os goldens provider-*-config ganharam a chave na 3.1.
- decision: falha do thread de comentário no Azure sai com exit 0, `ok: true` e `findings: [git-pr-azure-comment-failed]` — o PR existe e o record é carimbado; exit 1 faria quem chama ler o PR como não aberto.
- test_session_context (4 testes) falha quando o gate roda dentro de uma sessão OpenCode: `OPENCODE_SESSION_ID` do ambiente vence o `CLAUDE_CODE_SESSION_ID` do teste. Falha também sem este diff; o gate passou com `env -u OPENCODE_SESSION_ID -u OPENCODE -u OPENCODE_CLIENT -u OPENCODE_TERMINAL`. Os testes deveriam isolar as variáveis OPENCODE_*.
- A migração renomeia a pasta-irmã antiga na primeira execução de `link`; outros worktrees ficam com link pendente até o próprio `link` (repontado automaticamente). Um nome com ponto no meio (`a/.b`) segue com `..` (fora do pedido).

## Outcome

Entregue:

- `cq git worktree link` nomeia a pasta-irmã sem os pontos iniciais (`.tmp` → `<repo>.tmp`; `a/b` → `<repo>.a.b`). Na primeira execução renomeia a pasta antiga `<repo>..<nome>`, se ela existir sozinha, e reponta o link (`migratedFrom` no item). Se as duas existem, recusa com `git-worktree-store-conflict` sem mexer em nada.
- `cq git pr create` no Azure corta a descrição acima de 4000 caracteres na última `\n## ` que cabe, com a nota "Corpo completo no primeiro comentário deste PR.". Depois publica o corpo inteiro como thread fechado via `az devops invoke` (`pullRequestThreads`). Se o comentário falha, o PR fica de pé e a saída traz `findings: [git-pr-azure-comment-failed]` com exit 0.
- `cq specs config` expõe `sharedPaths`.
- As referências `pr-create.md`, `git/pr.md` e `git/isolation.md` estão atualizadas, com testes para nome novo, migração, recusa, corte, thread e falha do thread.

Fora do pedido: nomes com ponto no meio (`a/.b`). Também ficou de fora o isolamento dos testes de `test_session_context` contra as variáveis `OPENCODE_*` (ver Discoveries).
