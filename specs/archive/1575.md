## Problem

Encontrado pelo mapa da rodada 9 do autopilot (2026-10-12) e confirmado pelo condutor na leitura, em `main` 8d747f48.
`cq git prune --remote-branch <b>` apaga o branch no servidor com um `push --delete` cru
(`plugins/quenching/assets/bin/quenching/git/prune.py:43`). A única checagem é o branch constar do relatório
`stale` (`prune.py:41`), que lê só os `refs/remotes/<remote>/*` locais com `--merged <base>`, e
`git/stale.py:36-38` declara que não faz fetch. Não há fetch, `ls-remote` nem lease com o sha esperado no
momento do delete.

Entrada que quebra: o ref de rastreio de `feat-x` foi buscado quando sua ponta era ancestral de `main`, e depois um
colaborador empurrou commits novos para `origin/feat-x`. O `/quenching:git:cleanup` mostra `feat-x` como mesclado, o
humano confirma (`commands/git/cleanup.md:39`) com base nesse dado velho, e o `push --delete` remove o branch vivo.
Os commits novos ficam só no clone do colaborador, e um PR aberto com esse head é fechado.

Consequência: trabalho perdido no servidor, por um verbo que se apresenta como seguro ("never `-D`", `prune.py:5`).
A correção estreita o delete: ele leva o sha reportado como lease (`--force-with-lease=refs/heads/<b>:<sha>`) ou
confere o remoto com `ls-remote` e recusa se a ponta mudou.

## Proposal

- `cq git prune --remote-branch <b>` deletes the server branch only when the server's tip still equals the sha the stale report read from the tracking ref.
- A branch whose server tip moved after the last fetch is refused (exit 1, git's own stale-info message) and stands on the server.
- The delete keeps the safe-only shape: no `-D`, no plain `--force`, no caller-written refspec.

## Out of Scope

- Fetching inside `prune` or `stale`: `/quenching:git:cleanup` deliberately owns the no-fetch rule; the lease makes a fetch unnecessary.
- Changing `cleanup.md` wording: the exact action shown to the human stays `git push <remote> --delete <branch>`; the lease only narrows it.
- Local `--branch` and `--worktree` deletes: `branch -d` already refuses unmerged work.

## Design

- Decision: lease on the reported sha, not an `ls-remote` re-check. `git push --delete --force-with-lease=refs/heads/<b>:<sha>` makes the comparison atomic on the server, where a separate `ls-remote` leaves a race window between check and delete. The sha is `rev-parse refs/remotes/<remote>/<b>`, the same ref the report listed.
- Durable rule: a destructive remote verb carries the sha it saw as its lease and never acts on a snapshot without it.
- Contract: the delete stays inside `audit.SAFE` and never `-D`/`--force`; a lease is a refusal mechanism, not a force.
- If the tracking ref cannot be resolved the verb refuses (exit 1) rather than deleting unleased.

## Alternatives Considered

- `ls-remote` then plain `push --delete`: rejected, check-then-act race and one extra network call.
- Fetch before delete: rejected, contradicts the cleanup no-fetch contract and still races.

## Open Decisions

- none — the lease form is settled by the Design; nothing is left to decide.

## Risks

- A server that rejects `--force-with-lease` on delete would refuse every prune: ACCEPTED — git has supported it since 1.8.5, and the failure is closed (nothing deleted).
- A branch already deleted on the server makes the lease fail: ACCEPTED — the message is surfaced and nothing is lost.
