## Problem

Depois que um PR é mergeado, a branch principal do checkout local continua no commit antigo, e o trabalho seguinte parte de uma base vários commits atrás do remoto — no próprio checkout deste repositório a main local estava 16 commits atrás da origin. O fechamento do ciclo (merge do PR ou conclude) deveria trazer a atualização à branch principal local por um pull seguro, só fast-forward, sem descartar alterações locais não commitadas nem trocar a branch de quem está trabalhando no checkout.

## Proposal

- `cq git refresh` existe: busca `<remote>/<base>` e leva a branch principal local até ele **somente por fast-forward**.
- Nenhum commit é descartado (base divergida ou à frente é reportada e não tocada), nenhuma alteração não commitada é perdida (o merge `--ff-only` do git a preserva ou recusa) e nenhuma branch é trocada.
- Onde a base está em outra worktree, o fast-forward corre nela; onde nenhuma worktree a mantém, o ref anda por `update-ref` contra o tip lido.
- O fechamento do ciclo chama o verbo em `conclude` (passo 8) e em `/quenching-git merge` (passo 4); `diverged`/`merge-refused` é reportado e nunca forçado. O `spec-orchestrator` fica de fora: ampliar o `tools:` dele é um grant novo, decisão humana (ver `## Discoveries`).
## Out of Scope

- Atualizar branches de trabalho (é `/quenching-git sync`, por merge, nunca rebase).
- Fazer `cq git pr merge` ou `cq specs reconcile` rodarem o verbo sozinhos: a mutação do checkout principal fica explícita no corpo que fecha o ciclo, não escondida num verbo de merge.
- Resolver divergência ou forçar (`reset`, `--force`): sempre decisão humana.

## Design

- **Regra durável:** a base local só anda por fast-forward; qualquer outra relação com o remoto (divergida, à frente) é reportada e deixada como está.
- **Quem move:** onde uma worktree tem a base, `git merge --ff-only` roda nela (o git já preserva mudanças sem colisão e recusa as que colidem; nada de stash/reset). Sem worktree, `update-ref` com o valor antigo como guarda (compare-and-swap). Evidência: `git fetch origin main:main` recusa quando a base está checada em outra worktree, o caso normal de quem trabalha em slots.
- **Onde é chamado:** nos três corpos que terminam um merge (todo caminho de merge termina em `reconcile --write`, e o verbo vem logo depois), não dentro de `pr merge`/`reconcile`, para que o único write no checkout principal seja visível e o orquestrador o tenha no `tools:` por verbo.
- Hooks desligados (`SAFE`), como nos demais verbos de git.

### Assumptions

- O checkout que roda o verbo vê a worktree da base em `git worktree list` (dependência: o fast-forward em outra worktree).
- Um merge `--ff-only` com sujeira não colidente é aceito pelo git (dependência: o teste de sujeira preservada).

## Alternatives Considered

- `git pull --ff-only` direto nos corpos: falha dentro de worktree (`main` já usada) e faz fetch+merge sem relatório estruturado.
- Embutir no `reconcile --write`: acopla o fechamento de spec a uma mutação do checkout principal e a todos os testes de reconcile.
- `git fetch origin main:main`: recusa quando a base está checada em outra worktree.

## Open Decisions

- none — o nome do verbo (`refresh`, já que `sync` é o rebase da branch de trabalho) e o ponto de chamada ficaram decididos no `## Design`.

## Risks

- Mutar o checkout principal a partir de um slot: mitigado por `--ff-only` (recusa colisão, preserva o resto) e por reportar sem forçar. ACCEPTED — uma sujeira não colidente continua no lugar após o avanço.
- Fetch lento ou sem rede: o verbo sai 1 com `fetch-failed` e o fechamento segue, reportado.

## Outcome

It fast-forwards the local base to `<remote>/<base>` and nothing else: it never discards a commit or an uncommitted change and never switches a branch. **Pending human decision — the spec-orchestrator grant.** The `spec-orchestrator` does NOT call `cq git refresh`. Until the human decides, the route that merges through the orchestrator leaves the local base unrefreshed. The conclude and `/quenching-git merge` routes do refresh it.
