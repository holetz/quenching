## Problem

O quenching não tem definição de um host de trabalho: build de imagens, cargo/npm/uv, testes pesados, deploy de containers e cargas com GPU rodam na máquina de desenvolvimento, que trava durante reuniões, embora exista na rede um host com GPU acessível por SSH (192.168.15.199, contexto Docker `gpu-host`, helper `~/.local/bin/remote-run`) que só o eclume usa, por runbook próprio (`~/Projetos/eclume/docs/project/host-setup.md`). O humano quer que todos os seus projetos possam ser direcionados a esse host para processamento pesado, com uma definição única por usuário em vez de cada projeto reinventar alvo, sincronização e as armadilhas já conhecidas (mtime do rsync, arquivos gerados que não voltam, disco cheio, serviços pessoais do host que nunca são tocados).

## Proposal

- O host de trabalho tem uma definição única por usuário: o bloco `shared.workHost`, lido pelo loader comum (camada do usuário `~/.config/quenching/config.json`, o repositório vence chave a chave), sem chave nova no loader.
- `cq config host [--json]` mostra o host efetivo (alvo SSH, contexto Docker, runner, raiz remota, flags de sincronização, globs de retorno, caminhos protegidos, mínimo de disco livre) e os avisos de cada valor ignorado; ausente o bloco, o host está desabilitado e nada muda.
- `cq config host --plan -- <comando>` imprime, sem executar nada, os passos de despacho (checagem de disco, envio, execução remota, retorno dos gerados) já com as armadilhas conhecidas embutidas: sincronização por checksum e não por mtime, globs de retorno dos arquivos gerados, mínimo de disco livre e recusa de qualquer comando que toque um caminho protegido.
- Um standard `docs/standards/workflows/work-host.md` define o bloco, o contrato do plano e as armadilhas, e diz que o quenching nunca abre uma conexão SSH por conta própria.

## Out of Scope

- Executar SSH, rsync ou docker a partir do `cq`: seria um grant novo; o plano é só texto, quem o roda é o humano ou o runner dele (`remote-run`). Qualquer permissão de SSH a um agente é uma proposta `needs-human:` à parte.
- Provisionar ou configurar o host (runbook do eclume, `host-setup.md`): fica no projeto que o possui.
- Editar `bin/quenching/common/config.py` e `docs/standards/workflows/plugin-configuration.md` (da 1910): a tabela de chaves ganha a linha de `shared.workHost` depois, por descoberta.
- Semear `workHost` em `cq config init` e listá-lo no `--effective` com default: a semente só lista chaves de default ajustável, e este bloco nasce desabilitado.
- Roteamento automático de tarefas pesadas ao host dentro de execute/autopilot: depende deste bloco existir primeiro.

## Design

**Onde vive.** `shared.workHost` é lido por `load_config` + `namespace(..., "shared")`, o mesmo caminho de `shared.codex` (`codex/config.py`); o loader já mescla a camada do usuário (1907), então a definição por usuário não exige código de camada. A leitura mora no pilar `config` (`config/host.py`), que já está habilitado em todos os módulos que carregam `config`; nenhum pilar novo.

**Chaves e defaults.** `target` (alias ou `usuário@host` SSH; sem default), `dockerContext` (sem default), `runner` (caminho do helper do usuário, p.ex. `~/.local/bin/remote-run`; sem default), `remoteRoot` (`~/work`), `syncFlags` (`["-az", "--checksum"]`: o checksum evita que o mtime do rsync dispare reenvio ou esconda mudança), `syncExclude` (`[".git", "node_modules", ".venv", "target"]`), `pullBack` (globs dos arquivos gerados a trazer de volta; default `[]`, e o plano avisa quando vazio), `protectedPaths` (caminhos/serviços pessoais do host que o plano recusa tocar; default `[]`), `minFreeGb` (`10`). `enabled` é derivado: verdadeiro só com `target` válido. Valor de forma errada cai no default com aviso, como em `shared.codex`.

**O plano é texto.** `build_plan(settings, project, command)` é função pura que devolve passos `{step, argv}`: `df` remoto contra `minFreeGb`, `rsync` de envio, execução (pelo `runner` se houver, senão `ssh <target>`), `rsync` de retorno por `pullBack`. Recusa (exit 2) quando desabilitado ou quando o comando cita um `protectedPaths`. Nada abre conexão: manter o `cq` sem grant de SSH é a razão de o plano ser inerte. Alternativa por descoberta: executar com `--run`, rejeitada em Alternatives.

**Binding.** Segue `docs/standards/workflows/plugin-configuration.md` (um só lar, namespaces) sem editá-lo; `shared.codex` é o modelo de leitura com avisos.

## Alternatives Considered

- **Executar o despacho (`cq host run`)** — perdeu: exige grant de SSH que nenhuma política concede; o humano já tem o `remote-run`.
- **Pilar `host` novo** — perdeu: um pilar novo move atribuição de módulos e mirrors por um bloco de sete chaves; o pilar `config` já é a visão de leitura das camadas.
- **Chave por projeto em `.claude/quenching.json` apenas** — perdeu: é a reinvenção por projeto que o Problem descreve; a camada do usuário (1907) resolve.

## Open Decisions

- Quais globs `pullBack` e `protectedPaths` o usuário declara no seu host: decide-se no `~/.config/quenching/config.json` do humano, com o runbook do eclume em mãos; o default vazio com aviso é deliberado.
- Linha de `shared.workHost` na tabela de chaves de `plugin-configuration.md`: decide-se depois do merge da 1910, que é dona do arquivo.

## Risks

- O plano pode divergir do que o `remote-run` faz de fato: mitigação, o plano é sugestão impressa e o standard diz que o runner do usuário é a autoridade; ACCEPTED — o custo é um comando a ajustar.
- `--checksum` torna o envio mais lento em árvores grandes: mitigação, `syncFlags` é configurável; ACCEPTED.
- Contenção com a 1910 em `effective.py`/`config.py`: mitigação, este desenho não os edita.
