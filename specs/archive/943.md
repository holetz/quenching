## Overview

Este defeito não é de um comando: é do contrato de resolução da ferramenta, e ele atravessa as três
frentes. Todo corpo que trabalha — `knowledge`, `specs`, `components` — chega ao `cq` em algum
passo, e a superfície inteira herda o mesmo ponto cego. A correção tem duas vias que se cobrem: uma
faz o `cq` nu funcionar de verdade (o shim na vaga que o Claude Code já reserva no PATH), a outra
mantém a resolução correta onde o PATH não vale (a citação do contrato nos corpos que executam a
ferramenta). Nenhuma das duas sozinha fecha o buraco; juntas, fecham.

## Problem

Todo corpo de comando do plugin invoca `cq` — 22 dos 26 o fazem — mas nenhuma sessão consegue
resolver esse nome. O sintoma medido nesta investigação: `which cq` sai 1, `type cq` responde
`cq: não encontrado`. São três camadas, todas confirmadas por evidência coletada contra o ambiente
vivo.

**A. 10 dos 22 corpos que invocam `cq` não citam `assets/references/align/tool-resolution.md`.**
O contrato de resolução existe e é explícito, mas esses corpos nunca o citam — então a invocação
nua se lê literalmente e o agente executa `cq` no shell. Auditoria completa (invocações de
`cq <pillar>` × citações de `tool-resolution`):

O caso que quebrou a sessão de origem: `commands/specs/orchestrate.md` passo 2 traz um bloco
` ```bash ` literal com `cq specs status --spec <slug> --json` e `cq specs config --json`.

**B. `${CLAUDE_PLUGIN_ROOT}` chega vazio no Bash.** Medido: `CLAUDE_PLUGIN_ROOT=[]` no ambiente da
ferramenta Bash. A variável é expandida apenas no texto do corpo de comando injetado no prompt — as
citações do `orchestrate` chegaram já expandidas em caminho absoluto. Quem alcança o snippet
**lendo o reference com a ferramenta Read** recebe `${CLAUDE_PLUGIN_ROOT}` cru, e
`python3 "${CLAUDE_PLUGIN_ROOT}/assets/bin/cq"` vira `python3 "/assets/bin/cq"` → falha.
O `tool-resolution.md` declara *"There is no fallback and no manual rung"* e não oferece
recuperação para raiz vazia.

**C. O Claude Code anexa `<pluginRoot>/bin` ao PATH e o quenching não entrega nada lá.** A cauda do
PATH medida tem exatamente dois diretórios, um por plugin habilitado, e **nenhum dos dois existe**:

```
/home/unicred/.claude/plugins/cache/claude-plugins-official/context7/unknown/bin
/home/unicred/Projetos/claude-quenching/plugins/quenching/bin
```

O executável do quenching mora em `plugins/quenching/assets/bin/cq` e sequer tem bit de execução
(`-rw-rw-r--`). `git log --all -- plugins/quenching/bin` volta vazio: o diretório nunca existiu.
Ou seja, o Claude Code já reserva ao plugin uma vaga no PATH que o plugin nunca ocupou.

## Proposal

- `cq` digitado nu resolve em qualquer sessão com o plugin habilitado: o Claude Code já anexa
  `<pluginRoot>/bin` ao PATH e o quenching passa a ocupar essa vaga com um shim executável.
- Os **sete** corpos que mandam executar `cq` e hoje não citam `align/tool-resolution.md` passam a
  citá-lo, de modo que a resolução continue correta onde o PATH não vale — sub-agentes com
  `allowed-tools` restrito, hooks, e o próprio repositório de desenvolvimento, cujo PATH aponta
  para o checkout instalado e não para o worktree.
- `align/tool-resolution.md` deixa de declarar *"There is no fallback and no manual rung"* e passa
  a descrever **duas vias de resolução em ordem**, cobrindo o caso hoje não tratado:
  `${CLAUDE_PLUGIN_ROOT}` chega vazio no shell, então o snippet que o reference ensina falha
  silenciosamente para quem o alcança lendo o arquivo em vez de recebê-lo expandido num corpo.
- `/.knowledge/standards/architecture/plugin-layout.md` nomeia `bin/` como a **terceira** árvore que o
  Claude Code lê por convenção — o próprio standard já previu que uma terceira apareceria.
- O shim é coberto por teste no suite existente: existe, é executável, `--version` concorda com
  `VERSION`, e os exit codes 0/1/2 atravessam intactos.

## Out of Scope

- **Mover `assets/bin/cq` para `bin/`.** Quebraria todas as citações da superfície, os testes e os
  goldens congelados. O shim entrega o mesmo resultado sem tocar em nenhum deles.
- **Dar bit de execução a `assets/bin/cq`.** Toda a superfície o invoca via `python3` por contrato,
  então o `+x` ali é cosmético; ele é obrigatório apenas no shim, que o PATH precisa executar.
- **Uma regra de lint que force a citação** (um `sk-*` novo em `cq components lint`). É a prevenção
  durável contra o buraco regredir, mas está além da direção aprovada nesta corrida — parkada em
  `## Discoveries`.
- **Os dois corpos que apenas MENCIONAM `cq knowledge hook` em prosa** — `commands/knowledge/add.md`
  e `commands/knowledge/learn.md`, ambos na forma "o `cq knowledge hook` instalado (se ligado)
  verifica na escrita". Não mandam executar nada, então uma citação ali é custo de leitura sem
  retorno. Dos 10 corpos sem citação, estes 2 ficam de fora deliberadamente; os outros 7 entram.
- **O bump de versão, o lockstep e o release.** Obrigação de merge — `/quenching:specs:conclude` as
  liquida quando o que a release *é* fica conhecível.

## Design

**O shim é um arquivo Python, não um symlink nem um script `sh`.** Um symlink `bin/cq ->
../assets/bin/cq` dependeria de o CPython resolver o link antes de fixar `sys.path[0]` — uma
sutileza que não se declara em lugar nenhum e quebra em silêncio quando muda; e symlinks não
sobrevivem a todo fluxo de cópia/arquivo. Um script `sh` precisaria de `readlink -f` para achar a
própria raiz, e o `readlink` do BSD (macOS, um alvo real deste plugin) não tem `-f`. Um arquivo
Python resolve pelas duas: `os.path.realpath(__file__)` é portátil e o repositório já é
stdlib-only, sem build step.

**O shim re-executa com `os.execv`, nunca com `runpy.run_path`.** Esta é a decisão que não pode ser
invertida por engano. `assets/bin/cq` não manipula `sys.path` nem lê `__file__`: ele importa o
pacote `quenching` **contando com o `sys.path[0]` que o Python monta a partir do diretório do
script**, e o pacote mora em `assets/bin/quenching/`. Sob `runpy` o `sys.path[0]` seria `bin/`, e
`import quenching` falharia. `os.execv(sys.executable, [sys.executable, <real>, *argv[1:]])`
reproduz literalmente a invocação que toda a superfície já faz — `python3 assets/bin/cq …` — então
o comportamento é idêntico por construção, sem desvio possível. O `execv` também substitui o
processo, o que faz os exit codes 0/1/2 chegarem intactos sem o shim precisar tratá-los: o código
que o shell vê é o do próprio `cq`.

**A raiz vem de `__file__`, nunca de `${CLAUDE_PLUGIN_ROOT}`.** Regra durável: *nenhum executável
do plugin pode depender de `${CLAUDE_PLUGIN_ROOT}` para achar a si mesmo.* A variável é expandida
apenas no texto de um corpo de comando injetado no prompt; no ambiente do Bash ela chega vazia, e
um shim que a lesse resolveria para `/assets/bin/cq`.

**O contrato passa a ter duas vias, e a ordem é parte do contrato.** `align/tool-resolution.md`
hoje declara *"There is no fallback and no manual rung"* — uma frase escrita contra um risco real
(um alvo instalando uma cópia própria da ferramenta) que acabou proibindo também a redundância
legítima. A nova redação mantém a proibição onde ela vale — **nunca uma cópia no alvo, nunca um
merge no `settings.json` do alvo** — e declara duas vias sobre a MESMA ferramenta:

1. `cq …` nu, quando o PATH o resolve (o shim, em qualquer sessão com o plugin habilitado);
2. `python3 "<pluginRoot>/assets/bin/cq" …` com o caminho **escrito por extenso e expandido**,
   quando não resolve.

E acrescenta o caso que hoje não está em lugar nenhum: **`${CLAUDE_PLUGIN_ROOT}` chega vazio no
shell.** Quem recebe o caminho já expandido dentro de um corpo de comando pode copiá-lo literal;
quem alcança o snippet lendo o reference com a ferramenta Read recebe a variável crua e produz
`python3 "/assets/bin/cq"`, que falha. O reference precisa dizer isso, porque hoje ele ensina
exatamente o snippet que falha.

**`bin/` é a terceira árvore de convenção, e o standard já a previu.**
`/.knowledge/standards/architecture/plugin-layout.md` §`hooks/hooks.json` is the second tree fecha com:
*"A third such path added by Claude Code later inherits this paragraph without amending the
`assets/` inventory below."* `bin/` é exatamente esse terceiro caminho — o nome é fixado pelo host,
não escolhido por nós, e o parágrafo o cobre sem mexer no inventário de `assets/`. A mudança no
standard é registrar o terceiro caminho e a evidência que o estabelece, não reabrir a regra.

**O PATH aponta para o checkout instalado, não para o worktree — e isso é correto para um alvo e
armadilha aqui.** Medido: o PATH traz `/home/unicred/Projetos/claude-quenching/plugins/quenching/bin`,
o checkout principal, enquanto esta sessão trabalha em
`/home/unicred/orca/workspaces/claude-quenching/cq-inacessivel`. Para qualquer repositório-alvo isso é
o comportamento certo — o `cq` do plugin instalado é o que deve rodar. Ao desenvolver o próprio
quenching é o contrário: o `cq` nu roda o código instalado, não o que está sendo escrito. Por isso
a via 2 não é um fallback degradado — é a via **correta** quando se trabalha no próprio plugin, e
o reference precisa dizê-lo com essas palavras.

**A evidência que sustenta a via 1.** A cauda do PATH medida neste ambiente traz exatamente dois
diretórios, um por plugin habilitado, e nenhum dos dois existe:
`…/claude-plugins-official/context7/unknown/bin` e `…/claude-quenching/plugins/quenching/bin`. O
Claude Code anexa `<pluginRoot>/bin` incondicionalmente, exista ou não. O mecanismo é **medido, não
documentado** — o que `## Open Decisions` e `## Risks` registram, e é a razão de a via 2 existir.

## Alternatives Considered

- **Symlink `bin/cq -> ../assets/bin/cq`.** A forma mais curta possível. Perdeu porque depende de
  o CPython resolver o link antes de fixar `sys.path[0]` — comportamento que nenhum contrato
  declara e que, se mudar, quebra em silêncio — e porque symlinks não sobrevivem a todo fluxo de
  distribuição. O shim explícito custa dez linhas e não depende de sutileza nenhuma.
- **Mover o executável de `assets/bin/cq` para `bin/cq`.** Elimina a indireção inteira. Perdeu por
  raio de explosão: quebraria todas as citações da superfície, os testes, os goldens congelados e
  o `hooks/hooks.json`, para comprar exatamente o que dez linhas de shim compram sem quebrar nada.
- **Só as citações, sem shim.** A correção mínima e conforme à doutrina atual. Perdeu porque deixa
  a vaga que o Claude Code reserva no PATH permanentemente vazia e mantém toda a superfície
  pagando prosa de resolução em cada corpo, para sempre. Descartada pelo humano no plano de
  marchas desta corrida.
- **Só o shim, sem as citações.** Tornaria as citações desnecessárias — se o PATH sempre valesse.
  Perdeu porque não vale: o PATH aponta para o checkout instalado, não para o worktree em
  desenvolvimento, e um sub-agente com `allowed-tools` restrito ou um hook pode não ter o PATH da
  sessão. Descartada pelo humano no plano de marchas desta corrida.

## Open Decisions

- **O mecanismo `<pluginRoot>/bin` → PATH é contrato público do Claude Code ou detalhe de
  implementação?** A evidência atual é medição direta deste ambiente, não documentação: dois
  diretórios `bin` inexistentes na cauda do PATH, um por plugin habilitado. **Como se decide:** a
  primeira sessão aberta depois do merge e do reload do plugin — `which cq` sai 0 e
  `cq --version` imprime a versão instalada, ou não. Se não sair, a via 2 (as citações) já
  sustenta a correção sozinha e o shim vira custo morto a remover numa spec de limpeza; não há
  cenário em que a decisão bloqueie a construção.

## Risks

- **O mecanismo do PATH é medido, não documentado.** Se o Claude Code deixar de anexar
  `<pluginRoot>/bin`, a via 1 morre em silêncio. **ACEITO** — é exatamente por isso que a correção
  tem duas vias: as citações fazem a resolução funcionar mesmo se o shim nunca resolver, e o
  `## Validation` separa o que esta sessão prova do que só uma sessão futura prova.
- **Nada nesta corrida consegue provar que o `cq` nu resolve.** O PATH aponta para o checkout
  instalado e o registro de plugins é montado no início da sessão, então a asserção só é
  mensurável depois do merge, numa sessão nova. Mitigação: `## Validation` declara essa asserção
  como diferida e nomeia o comando exato, em vez de fingir que o gate a cobriu.
- **Um shim que engolisse o exit code quebraria o contrato 0/1/2 de toda a superfície** — todo
  corpo ramifica no código de saída, nunca na prosa. Mitigação: `os.execv` substitui o processo,
  então o código que o shell vê é o do próprio `cq`, e a task 1.2 o prova com um caso de recusa
  (exit 2).
- **Um shim que resolvesse o `sys.path` errado faria `import quenching` falhar** em toda invocação
  pelo PATH — e a falha só apareceria em sessões futuras, não aqui. Mitigação: a task 1.1 verifica
  com `components doctor`, que só responde se o pacote importou.
- **Ao desenvolver o próprio quenching, o `cq` nu roda o código instalado, não o do worktree.**
  Risco de alguém medir a correção contra o binário errado e concluir que funciona (ou que não).
  Mitigação: `tool-resolution.md` declara isso explicitamente e manda usar a via 2 ao trabalhar no
  próprio plugin.
- **`os.execv` custa um processo a mais por invocação** (~30 ms). **ACEITO** — a via 2, que é a que
  os corpos usam hoje, não passa pelo shim e não paga nada.
