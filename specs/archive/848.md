## Overview

Esta spec mexe em duas coisas: como o trabalho de uma spec é isolado no git, e como ele volta para a
branch principal. As três mudanças que ela propõe vêm todas do mesmo fato — as specs deste
repositório deixaram de morar na mesma branch que o código. Elas são issues do GitHub agora, então a
branch de trabalho não precisa mais ser reconhecível pelo nome para que as ferramentas achem a spec.

`## Problem` conta de onde vem esse fato e o que ele deixou obsoleto. `## Proposal` lista o que passa
a ser verdade depois: nome de branch livre, isolamento como passo de quem constrói em vez de comando
próprio, e conclusão por pull request onde existe um.

`## Design` decide cada uma das três em detalhe, junto com as regras que elas não podem contrariar —
em especial a de que o registro `branch` guarda o único fato que o git esquece no merge, que é de
onde a branch saiu. `## Alternatives Considered` guarda o que foi cogitado e por que perdeu,
incluindo a leitura da segunda proposta que o autor descartou. `## Out of Scope` marca o vizinho mais
fácil de confundir com escopo — o prefixo `plan/<slug>:` das mensagens de commit, que fica
exatamente como está.

O resto é o que torna a spec construível. `## Impact` declara os três standards que ela promete
escrever e o código que espera tocar. `## Validation` diz como qualquer pessoa confirma que
funcionou, e é onde estão os dois números que carregam o argumento inteiro: `doctor` dizendo 25
comandos em vez de 26, e `budget` estritamente abaixo de 14898. É também onde estão as duas exceções
que o gate teve de nomear para poder ser honesto: as quatro linhas de narrativa histórica que citam
o comando aposentado sem apontar para ele — o grep não distingue história de ponteiro vivo, e
reescrever a história para calá-lo seria pior — e os dois erros pré-existentes de `specs.py
selftest`, que são de carregamento de config e não desta spec. `## Risks` lista o que pode dar
errado — sendo o mais provável que o merge feito pelo GitHub deixe a checkout local para trás e
quebre a asserção final de `conclude`. `## Tasks` é a lista ordenada, em cinco grupos, verificada ao
fim de cada um; o quinto existe porque a verificação final descobriu o que a decomposição não tinha
previsto — citações que nenhuma tarefa declarava, entre elas o manual do operador que ainda ensina o
comando aposentado, e um caso em que `execute` construiria em silêncio sobre a branch base.
`## Open Decisions` guarda o que ainda não tem resposta e o que vai decidir cada uma, e
`## Discoveries` guarda o que a execução achou, cada linha com sua resolução em cima.
## Problem

A skill `/quenching:specs:isolate` rastreia o trabalho isolado pelo nome da branch de execução — um desenho pensado para uma proposta que este projeto já não segue. Os backends que armazenam as specs (ex.: github) já não residem na branch de desenvolvimento, então o tracking por nome deixou de ser necessário e pode até atrapalhar o fluxo.

Três propostas a avaliar: (1) parar de exigir o padrão de nome da branch — propô-lo apenas quando estivermos na `main`, mas sempre carimbar a branch de execução na spec; (2) incorporar a etapa de isolamento à skill de desenvolvimento, já que criação e desenvolvimento não precisam mais se preocupar com branches, reduzindo chamadas de skill dentro do contexto; (3) na conclusão, aproveitar melhor os recursos do backend (como o GitHub), finalizando o processo com um PR em vez de merge direto, e expondo o link do PR quando possível.

## Proposal

Depois desta spec, no fluxo de specs deste plugin:

- **O nome da branch deixa de ser contrato.** `plan/<slug>` segue sendo o nome *sugerido* quando o
  fluxo se oferece para cortar uma branch, mas qualquer nome já em uso é adotado como está — nada
  renomeia, nada recusa.
- **Uma branch só é proposta quando a sessão está parada na branch base do repositório.** Em
  qualquer outra branch o fluxo adota a branch corrente como `work` e segue direto para a
  construção.
- **Todo trabalho feito fora da branch base carimba `branch: {base, work}`**, inclusive quando a
  branch não foi criada pelo quenching. Hoje só carimba quem cortou a branch, então uma spec
  construída numa branch que o humano já tinha aberto não deixa registro nenhum de onde foi
  construída.
- **`/specs:isolate` deixa de existir.** A etapa vira um passo inline de `/specs:execute`, que é o
  único comando que hoje a invoca. A pergunta read-only ("estou isolado?") continua respondida por
  `/specs:continue`, que já lê o ref vivo e o reporta.
- **`/specs:execute` para de gastar uma chamada `Skill` por run**, e a superfície devolve 614
  caracteres de budget sempre-ligado — medido hoje em 14898/14898, exatamente no teto.
- **`/specs:conclude` passa a oferecer uma rota, além da estratégia**: pull request ou merge local.
  A rota PR empurra a branch, abre o PR, mostra o link e conclui o merge com `gh pr merge` na mesma
  run.
- **O link do PR vira fato durável** — `merge: {strategy, subject, pr}` — e é repetido em
  `## Outcome`, que é o que um leitor humano abre.
- **Nada disso vira dependência obrigatória.** Sem remote GitHub, sem `gh` no PATH ou sem
  autenticação, `/specs:conclude` oferece exatamente as quatro estratégias locais de hoje, em
  silêncio.

## Out of Scope

- **Renomear o prefixo dos subjects de commit** (`plan/<slug>: <id> <título>`). É o vizinho mais
  fácil de confundir com escopo, e a confusão é justa: o prefixo *parece* nomear uma branch. Ele
  nomeia a **spec** — é o que faz `git log --grep` por slug devolver exatamente os commits daquela
  spec — e renomeá-lo quebraria o campo `subject:` de toda spec já arquivada em troca de nada. O que
  muda é a documentação do que o prefixo significa, não o prefixo.
- **Trocar o âncora tarefa→commit.** Com backend externo o âncora já é `commit: <sha>`, lido do
  próprio git; nome de branch não o toca.
- **Deixar o CI do PR substituir o gate `## Validation`.** O gate continua rodando na branch, antes
  do merge, porque é lá que uma falha ainda tem onde ser consertada. O status dos checks do PR é
  reportado e pode bloquear, mas nunca *é* o gate — um repositório sem CI não pode ficar sem gate.
- **Suportar PR em `azure-boards`, ou em qualquer host que não seja GitHub.** A rota é oferecida só
  onde `gh` resolve o repositório. Um segundo host é outra spec.
- **Fazer backfill de specs arquivadas.** Nenhum registro `branch` ou `merge` já escrito é
  reescrito — ver `## Design`.
- **Remover o fallback `plan/<slug>` de `_work_ref`** em `specs.py`. Ele continua servindo o caso de
  uma branch cortada à mão sem registro nenhum, que é justamente o caso que "sempre carimbar" não
  alcança.
- **Mexer nos fronts `docs/` e `.claude/` além do que esta spec tornou falso.** As duas entradas de
  `docs/knowledge/glossary.md` que dizem que `/specs:isolate` carimba o registro `branch` (linha 87)
  e roda o `worktreeSetup` (linha 336) não são citações vizinhas: descrevem comportamento que **esta**
  spec mudou de dono, e deixá-las é publicar uma regra errada. Entram na tarefa 5.3. O resto do
  glossário — as entradas sobre `plan/<slug>` como convenção de nome, que continua sendo o default
  sugerido — segue trabalho roteado (`/docs:define`), não desta spec.

Tudo abaixo roda de `plugins/quenching/`, salvo onde o caminho diz outra coisa.

**O esqueleto e o lockstep** — `VERSION` e os três scripts embarcados têm de concordar:

```bash
cat VERSION
python3 assets/bin/specs.py --version
python3 assets/bin/skills.py --version
python3 assets/hooks/okf-validate.py --version
```

**A superfície de comandos**, que é onde a proposta 2 é medida:

```bash
python3 assets/bin/skills.py --root . doctor --json    # 25 commands, nenhum finding
python3 assets/bin/skills.py --root . lint --json      # exit 0
python3 assets/bin/skills.py --root . budget --json    # exit 0, e `total` < 14898
```

abaixo de 14898 é o que prova que a saída devolveu budget em vez de ser reabsorvida pelas
descrições novas de `execute` e `conclude`. Um `budget` que volte a empatar no teto é falha, não
empate.

**Nenhuma referência pendurada** a um comando e a uma pasta que deixaram de existir:

```bash
grep -rn "specs:isolate" --include='*.md' plugins/quenching/ docs/ CLAUDE.md
grep -rn "specs-isolate/" --include='*.md' plugins/quenching/ docs/
```

Ambos devem sair vazios fora de `specs/archive/` e do corpo desta própria spec. Uma citação restante
é um ponteiro para lugar nenhum, que é o modo de falha que
`docs/standards/naming/command-surface.md` §Three citation forms já mediu 687 vezes.

**As quatro linhas que ficam, e por quê.** O grep acima não distingue ponteiro vivo de narrativa
histórica, e estas quatro são história — verdadeiras sobre o passado, sem apontar para nada que se

| Linha | O que ela narra |

| `docs/standards/automation/session-evidence.md:10` e `:51` | a evidência de sessão que uma vez creditou 5 escritas a `/specs:isolate` |

O gate mede **ponteiro vivo pendurado**, não a substring: qualquer hit fora dessas quatro linhas, de
`specs/archive/` e do corpo desta spec é falha. As duas entradas de `docs/knowledge/glossary.md` que

`worktreeSetup`, que é comportamento que esta spec mudou, e por isso são consertadas na tarefa 5.3.

**As regras compartilhadas, cada tool contra a mesma lista canônica de casos:**

```bash
python3 assets/bin/specs.py selftest
python3 assets/bin/skills.py selftest
python3 assets/hooks/okf-validate.py selftest
python3 assets/hooks/okf-validate.py assets/docs        # 0 error(s), 0 warning(s)
python3 assets/hooks/okf-validate.py ../../docs         # 0 error(s), 0 warning(s)
```

`specs.py selftest` é o gate da tarefa 3.1: o campo `merge.pr` só está certo quando existe um caso
provando que uma conclusão local **sem** `pr` continua válida e um provando que `pr` presente com
estratégia `fast-forward` é recusado.

**E o gate dele aqui é _sem regressão nova_, não exit limpo.** Neste checkout `specs.py selftest`
devolve **2 erros pré-existentes** de `sp-config-default-drift`, que não são desta spec:
`load_config` ignora o root que recebe e resolve a partir do cwd real, achando o
`.claude/quenching.json` deste repositório em vez do caminho inexistente que o check passa. Medido
nos dois sentidos — rodado de `/tmp`, o mesmo comando devolve **0 erros**; rodado de dentro do
repositório, **2**. Enquanto o conserto não sai (promovido a `fix-load-config-root-argument`, ver
`## Discoveries`), o gate é: exatamente 2 erros, ambos `sp-config-default-drift`. Um terceiro erro,
ou um de outro código, é falha.

**Que a superfície de fato CARREGA** — nada acima testa isso, porque o registro é montado no início
da sessão e nenhuma mudança sob `commands/**` é testável na sessão que a escreve:

```bash
./assets/checks/functional-checks.sh
```

`exit 0` todas as asserções medidas passaram · `1` uma falhou · `2` nada pôde ser medido, que **não
é** um passe.

**O que esta spec deliberadamente NÃO usa como gate:** `python3 assets/bin/specs.py validate`. Neste
repositório ele devolve 219 erros falsos — um por spec — porque lê o documento pelo caminho de
arquivo do descritor, que no backend `github` é uma URL de issue. Enquanto isso não for consertado
(follow-up roteado, ver `## Open Decisions` e o relatório desta passagem), `validate` não distingue
"falhou" de "não pôde ser medido", que é precisamente a condição que
`docs/standards/quality/surface-verification.md` chama de inconclusiva.

**Pela mão, depois de editar os corpos:** `/skill:new` sobre `execute.md` e `conclude.md`, e
`/skill:eval` se alguma `description` tiver sido ajustada — o contrato do front de skills, não uma
obrigação deste repositório inteiro.
## Design

### A branch só é proposta a partir da branch base

A oferta de isolamento (worktree · branch · aqui mesmo) aparece quando, e só quando, `HEAD` está na
branch base do repositório. Em qualquer outra branch a pergunta já foi respondida pelo humano no
momento do checkout, e repeti-la é atrito.

A branch base é resolvida nesta ordem, parando na primeira que responde:

1. o registro `branch.base` da spec, quando já existe;
2. `git symbolic-ref refs/remotes/origin/HEAD` — o default declarado pelo remote;
3. `git config init.defaultBranch`, e então `main`.

As três são leitura pura e cabem na mesma chamada que `/specs:execute` já faz no seu passo 2, então
a regra não custa uma chamada nova — que é a condição que
[align-surface.md](docs/standards/architecture/align-surface.md) §Probe before the inventory impõe a
qualquer coisa que rode antes do trabalho.

### Uma branch adotada tem seu `base` inferido, e a inferência é mostrada antes de carimbar

`base` existe porque **depois do merge o git não sabe mais de onde a branch saiu**
([plan-git-record.md](docs/standards/workflows/plan-git-record.md) §Two frontmatter records). Quando
o quenching corta a branch, `base` é um fato observado: era o que estava em checkout. Quando ele
adota uma branch pré-existente, não é — é inferência.

A regra: inferir pela cadeia acima, **mostrar a inferência na mesma linha da confirmação**
(`base: main — inferido; esta branch não foi cortada por este comando`) e carimbar depois do OK. O
registro é write-once, então aquele é o único momento em que discordar é barato.

Nunca derivar `base` de `git merge-base` ou de `--fork-point`: os dois respondem um commit, não um
nome de branch, e um commit ancestral compartilhado por três branches não identifica nenhuma delas.

### `/specs:isolate` é aposentado, não esvaziado

`commands/specs/isolate.md` é removido. Um comando que sobrevive como casca continua pagando a sua
`description` no budget sempre-ligado em toda sessão
([context-budget.md](docs/standards/automation/context-budget.md)), que é metade do ganho medido
desta mudança.

O que precisava continuar existindo, e onde passa a morar:

| O que `/specs:isolate` fazia | Onde fica |
| --- | --- |
| oferecer worktree · branch · aqui mesmo | passo inline de `/specs:execute` |
| rodar o `worktreeSetup` declarado, com o comando exibido verbatim | idem, com o mesmo bloco de consentimento |
| carimbar `branch: {base, work}` | idem |
| responder "estou isolado?" sem escrever nada | `/specs:continue`, que já lê o ref vivo |

`/specs:status` **não** cobre a última linha: ele lê os registros de frontmatter, não o git. Isso é
deliberado ([read-only-views.md](docs/standards/architecture/read-only-views.md)) e não muda aqui —
quem pergunta pelo ref pergunta a `/specs:continue`.

### `git.md` muda de casa junto com o comando que o possuía

`assets/references/specs-isolate/git.md` passa a `assets/references/specs-execute/git.md`, ao lado
de `execution.md`. A pasta de referências é nomeada pelo comando que a possui
([plugin-layout.md](docs/standards/architecture/plugin-layout.md),
[command-surface.md](docs/standards/naming/command-surface.md) §The path IS the identity), e uma
pasta com o nome de um comando aposentado é um ponteiro para lugar nenhum.

`/specs:conclude` continua citando o arquivo: possuir não é exclusividade de leitura.

### A rota PR conclui o merge; ela não para no PR aberto

`/specs:conclude` oferece a **rota** (pull request · merge local) e a **estratégia** separadamente.
Na rota PR a run empurra a branch, abre o PR, mostra o link e **conclui o merge com `gh pr merge`**
antes de terminar.

Parar no PR aberto seria mais simples e está errado por duas razões, ambas contratos já escritos:

- `## Outcome` é escrito no passo 4, antes do merge, e afirma **o que entregou**. Com o PR aberto e
  não mergeado, a spec estaria arquivada como `done` afirmando algo que ainda não aconteceu — que é
  exatamente a mentira que a doutrina "concluding as done refuses to lie" existe para impedir.
- A ordenação "o merge é a última ação"
  ([plan-git-record.md](docs/standards/workflows/plan-git-record.md) §Every record is written before
  the thing it describes) só vale se o merge acontece. Uma run que termina antes dele deixa `merge`
  carimbado e nada mergeado — que hoje é um estado *recuperável*, não um estado final.

`gh pr merge --merge|--squash|--rebase` mapeia um-para-um em três das quatro estratégias já
existentes, então a rota PR não inventa vocabulário: `MERGE_STRATEGIES` fica exatamente como está.

`fast-forward` não tem equivalente no `gh`. Escolhida essa estratégia, a rota PR não é oferecida, e
a razão é dita em uma linha em vez de a opção aparecer e falhar.

### O link do PR entra no registro `merge`, e não só na prosa

`merge: {strategy, subject}` vira `merge: {strategy, subject, pr}`, com `pr` opcional e ausente em
toda conclusão local.

Passa no mesmo teste de admissão dos outros registros
([plan-lifecycle.md](docs/standards/workflows/plan-lifecycle.md)): é um fato que nenhuma derivação
reproduz. Depois de um squash com a branch deletada, o PR é a única coisa que ainda carrega a
revisão, a discussão e os checks — e procurá-lo por `gh pr list --search` depende de o título ainda
conter o slug, que é uma string que qualquer pessoa pode ter editado no navegador.

### Empurrar a branch e abrir o PR tem confirmação própria

As duas publicam a branch num host remoto. A escolha da rota no passo 4 **não** é o OK para elas: o
bloco que as executa mostra o remote, o nome sob o qual a branch será empurrada, o título e o corpo
do PR, e pede o OK ali.

Isso não contradiz o consentimento único do `worktreeSetup`
([worktree-setup.md](docs/standards/workflows/worktree-setup.md) §Its consent is the isolation
offer): aquele é um comando local que o humano lê na mesma tela em que escolhe. Este publica.

### Nada é backfillado

Um registro `branch` ou `merge` já escrito é lido e nunca reescrito, pela mesma razão que
[plan-git-record.md](docs/standards/workflows/plan-git-record.md) §Both forms are read, forever dá
para o âncora: reescrever uma spec arquivada falsifica quando o registro foi feito. Specs antigas
sem `branch` continuam sem `branch`.

## Alternatives Considered

- **Não fazer nada.** O fluxo funciona hoje: `/specs:isolate` corta `plan/<slug>` e `conclude`
  mergeia local. O que se paga por não mexer são quatro coisas medidas — 614 caracteres de budget
  sempre-ligado num teto que já empata em 14898/14898; uma chamada `Skill` por run de
  `/specs:execute`; uma spec construída numa branch que o humano já tinha aberto não deixando

## Open Decisions

- **Se `/specs:conclude` espera os checks do PR antes de mergear.** `gh pr checks --watch` bloqueia
  a run por minutos e pode não terminar nunca num repositório sem CI; ignorar os checks mergeia por
  cima de um vermelho que o humano ia ver na tela seguinte. *Como se decide:* medindo numa run real
  deste repositório, que tem remote GitHub e nenhum workflow de CI hoje — se `gh pr checks` responde
  "no checks" de imediato, esperar é grátis quando não há o que esperar, e a decisão cai sozinha
  para esperar.

- **O que acontece com a branch remota depois do merge por PR.** `gh pr merge --delete-branch` apaga
  a local e a remota de uma vez, o que colide com a ressalva do squash (`git.md` §The squash
  caveat), que existe justamente para **não** apagar. *Como se decide:* na redação da tarefa que
  escreve o passo, herdando a regra que já existe — a oferta de não apagar aparece sob squash, e a
  rota PR não muda isso.

- **Se a oferta inline de `/specs:execute` mantém o worktree como recomendado incondicionalmente.**
  `git.md` §The worktree is the preferred form recomenda worktree sem heurística. Adotar a branch
  corrente quando não estamos na base reduz quantas vezes essa recomendação chega a ser vista.
  *Como se decide:* deixa de existir se o texto da oferta for transplantado verbatim; vira decisão
  real apenas se a redação inline mudar a ordem ou a recomendação, e nesse caso é uma pergunta do
  banco adversarial, não desta spec.

## Risks

- **`gh pr merge` mergeia no host, e a checkout local da base fica para trás.** Hoje `conclude`
  fecha comparando `git -C <base> log -1 --format=%s` com o `subject` carimbado. Depois de um merge
  feito pelo GitHub esse commit não existe localmente, e a asserção falharia sempre — reportando um
  achado falso no exato passo desenhado para não reparar nada. *Mitigação:* na rota PR a asserção
  passa a ser sobre o próprio PR (`gh pr view --json state,mergeCommit`), e a checkout local é
  trazida com um `git -C <base> pull --ff-only` **antes** dela, cujo resultado é reportado, nunca
  forçado. É o risco mais provável desta spec e o mais fácil de descobrir tarde.

- **`base` inferido errado numa branch adotada, num registro write-once.** Uma branch cortada de
  outra branch — não da base — recebe `base: main` e não há segunda chance de corrigir.
  *Mitigação:* a inferência é mostrada na mesma linha da confirmação, antes do carimbo, com a
  palavra "inferido". *Resíduo:* ACEITO — um humano que aprove sem ler carimba errado, e a
  alternativa (perguntar sempre) devolve o atrito que a proposta 1 existe para remover.

- **Uma branch cortada à mão com nome livre e sem registro fica invisível para `next --front`.**
  Hoje `plan/<slug>` é encontrado mesmo sem registro, pelo fallback de `_work_ref`. Com nomes
  livres, `feature/foo` sem carimbo não é vista, e `/specs:continue` não a reporta em voo.
  *Mitigação:* o fallback fica onde está (`## Out of Scope`), e "sempre carimbar" cobre todo caminho
  que passa pelo quenching. *Resíduo:* ACEITO — só atinge quem corta a branch por fora **e** nunca
  roda `/specs:execute`, que é o caso em que o plugin não foi usado.

- **Aposentar um comando quebra repositórios adotantes que o citam.** Um repo que vendorizou
  `isolate.md` no seu `.claude/commands/`, ou que o cita numa spec sua, passa a apontar para nada.
  *Mitigação:* a nota de release e o `README.md` nomeiam a substituição (`/specs:execute` toma o
  isolamento, `/specs:continue` responde "estou isolado?"). Não há como detectar do lado do plugin.

- **O corpo que roda pode não ser o que está no repositório.** O cache do plugin fica atrás da
  fonte, então uma run de `/quenching:specs:*` pode executar um corpo antigo — sem os estágios novos
  — e reportar sucesso. *Mitigação:* `./assets/checks/functional-checks.sh` está em `## Validation`
  exatamente por isso, e nenhuma mudança sob `commands/**` é considerada provada na sessão que a
  escreveu.

- **`specs.py validate` não serve de gate neste repositório.** São 219 erros falsos, um por spec,
  então o verificador próprio do front `specs/` está indisponível enquanto esta spec é construída —
  e `/specs:align` sonda por ele. *Mitigação:* `## Validation` declara explicitamente que não o usa
  e diz por quê; o conserto é follow-up roteado, fora do escopo. *Resíduo:* ACEITO — nada nesta
  spec depende de `validate`, e consertá-lo aqui misturaria duas mudanças sem relação no mesmo
  merge.

- **A superfície pode voltar a empatar no teto.** Dobrar o isolamento em `execute` e a rota PR em
  `conclude` tenta engordar as duas `description`s, reabsorvendo os 614 caracteres devolvidos.
  *Mitigação:* `budget` estritamente abaixo de 14898 é uma asserção de `## Validation`, não uma
  esperança — e `budget` é o único instrumento que responde isso, nunca a estimativa.

## Outcome

A spec entregou o que propôs, nas três frentes.

**O comando de isolamento foi aposentado** e sua oferta dobrada para dentro de `/specs:execute`,
disparando **só quando a sessão está na branch base** — em qualquer outra, a pergunta já foi
respondida no checkout e `execute` **adota** a branch corrente, seja qual for o nome. `plan/<slug>`
passou de contrato a sugestão. A correção mais importante veio de uma discovery da própria
construção: *isolado* passou a significar **estar no work ref**, não o ref existir — o
curto-circuito antigo, que decidia pela existência do ref, mandava o loop construir e commitar
sobre a própria base no caso ordinário de estar na base com a branch parada ao lado.

**`branch:` passou a ser carimbado para toda branch fora da base**, inclusive uma que o plugin não
cortou, senão `/specs:conclude` fica sem saber contra o que mergeia. Numa branch adotada o `base` é
**inferido** — o registro `branch.base` existente, depois `git symbolic-ref refs/remotes/origin/HEAD`,
depois `git config init.defaultBranch`, depois `main` — e a inferência é mostrada na mesma linha da
confirmação, antes do carimbo, porque o registro é write-once e aquele é o único momento em que
discordar sai barato. Nunca por `git merge-base` ou `--fork-point`: ambos respondem um commit, não
um nome de branch, e um commit ancestral de três branches não identifica nenhuma.

**`/specs:conclude` ganhou a rota pull request** ao lado da estratégia, e o registro `merge` ganhou
o campo `pr`. Três das quatro estratégias mapeiam um-para-um em `gh pr merge --merge|--squash|--rebase`;
`fast-forward` não tem equivalente, então a rota nunca é oferecida sob ela e `specs.py record`
recusa `pr:` ali (`sp-merge-pr-no-route`), com `validate` avisando sobre um já escrito. Na rota PR o
carimbo do `merge:` se move para depois do `gh pr create` — é o único jeito de `pr:` caber no único
write que o registro tem — e continua acontecendo na branch, antes do merge.

**Ficou de fora, deliberadamente:** renomear o prefixo `plan/<slug>:` dos subjects (ele nomeia a
**spec**, não a branch, e é o que faz `git log --grep` por slug devolver os commits daquela spec);
trocar a âncora tarefa→commit; deixar o CI do PR substituir o gate `## Validation`, que continua
rodando na branch porque é lá que uma falha ainda tem onde ser consertada; PR em qualquer host que
não seja GitHub; backfill de specs arquivadas; e remover o fallback `plan/<slug>` de `_work_ref`,
que ainda serve a branch cortada à mão sem registro nenhum.

**O que o próximo leitor precisa saber.** Mergeada por **merge commit, rota local** — os 22
`subject:` das tasks resolvem da base para sempre, e a branch pode ser apagada sem custo (o que um
squash teria mudado). Dois commits além das tasks: a **revisão da branch** achou que a rota PR
entrou no código, no corpo de `conclude.md`, em `specs-execute/git.md` e em `plan-lifecycle.md`, mas
**quatro sítios de prosa** continuavam soletrando `merge: {strategy, subject}` — um standard, o
manual do operador que `specs.py` instala em cada repo adotante (mais a cópia gerada), o README do
produto e o glossário; e os **docs emergentes** mintaram
`docs/standards/quality/schema-key-prose-fanout.md` sobre exatamente essa classe de falha, mais a
correção de uma afirmação medida como falsa na `CLAUDE.md` (`assets/docs` dá 0 errors e 1 warning,
não 0 e 0).

Uma discovery virou spec própria: **`fix-load-config-root-argument`** — `load_config` ignora o root
que recebe e resolve a partir do cwd real, o que produz 2 erros de `sp-config-default-drift` em
`specs.py selftest` **só** de dentro deste repositório (de `/tmp` o mesmo comando dá 0). Por isso o
gate desta spec é *sem regressão nova*, e não exit limpo. O `## Validation` também nomeia quatro
linhas de narrativa histórica que os greps acham e que ficam como estão, e recusa
`specs.py validate` como gate: neste repo ele devolve 219 erros falsos por ler o documento pelo
caminho de arquivo do descritor, que no backend `github` é uma URL de issue.

**Destilado no conclude.** A passagem de destilação colheu duas coisas, e o resto ficou no arquivo
por não sobreviver à spec:
