## Problem

`.agents/quenching/bin/cq` (gerado por `cq deploy`) re-executa `assets/bin/cq` com
`os.execv(sys.executable, [sys.executable, REAL, *sys.argv[1:]])`. No Windows, `os.execv` monta a
linha de comando sem citar os argumentos, então todo argumento com espaço vira vários:
`.agents/quenching/bin/cq specs new x --title "dois termos"` sai com
`cq specs: error: unrecognized arguments: termos` (reproduzido em Windows 11, Python 3.14, Git Bash,
2026-11-22). Toda chamada de corpo que passa um título, um `--group "<wave>"` ou uma mensagem
quebra em alvo Windows; `python .agents/quenching/assets/bin/cq …` funciona.

## Proposal

No Windows (`os.name == "nt"`), o lançador usa `subprocess.run([...])` e `sys.exit(returncode)`
(que cita via `list2cmdline`) em vez de `os.execv`; nos demais mantém `execv`. Um teste unitário
chama o lançador com um argumento com espaço e confere o `argv` recebido.

## Out of Scope

- O `cq.cmd` gerado (`_VENDOR_CMD`) — já repassa `%*` e o código de saída; não usa `execv`.
- O shim `uvx` (`_uvx_shim`) — usa `exec` do sh e `%*` do cmd, não passa pelo `os.execv`.
- O despachante `assets/bin/cq` e a codificação do stdio (spec 228) e `subprocess` sem encoding (spec 229).

## Impact

### Product code this spec expects to touch

- `quenching/assets/bin/quenching/deploy/tree.py` — `_VENDOR_SH`, o texto do lançador `bin/cq` gerado
- `quenching/tests/test_deploy.py` — `TargetLauncher`, o teste do argumento com espaço

### Process surface this spec expects to touch

Teste do lançador com argumento contendo espaço; `bash scripts/verify_repo.sh` verde, incluindo
`deployed surface lockstep` após `cq deploy --target . --write`.

## Design

O lançador gerado ramifica em `os.name`: no Windows (`nt`) importa `subprocess` e termina com
`sys.exit(subprocess.call([sys.executable, REAL, *sys.argv[1:]]))`; `subprocess` monta a linha de
comando com `list2cmdline`, que cita cada argumento, e herda stdin/stdout/stderr, então a saída e o
código 0/1/2/3 chegam ao shell como hoje. Nos demais sistemas mantém `os.execv`, sem processo extra.
A docstring passa a nomear as duas formas.

O teste copia o lançador gerado (`bin/cq` de um alvo implantado pelo `setUpClass`) para um diretório
temporário com um `assets/bin/cq` falso que imprime `json.dumps(sys.argv[1:])` e sai com 3, e roda
`[sys.executable, <lançador>, "dois termos", "x"]`: confere o `argv` recebido e o código de saída.
Roda em qualquer SO; no Windows sem a correção falha (o `argv` chega como `["dois", "termos", "x"]`).

### Assumptions

- `subprocess.call` herda os descritores padrão, então pipes de stdin (corpos via heredoc) continuam chegando ao `assets/bin/cq` — Design, Tasks 1.1.

## Alternatives Considered

- Citar os argumentos à mão antes do `os.execv` (`subprocess.list2cmdline`) — rejeitada: `execv` no Windows não espera o filho e o shell recebe o código antes do fim; `subprocess` resolve as duas coisas.
- Importar `assets/bin/cq` em processo — rejeitada pelo próprio `TargetLauncher`: `sys.path[0]` apontaria para `bin/`.

## Open Decisions

- none — a forma (subprocess só no `nt`) já vem da Proposal e o código a confirma.

## Risks

- Ctrl-C no Windows chega aos dois processos; o filho trata e o pai sai com o código dele ou com `KeyboardInterrupt` — aceitável para um CLI curto.
- O gate local no Windows tem cerca de 295 falhas de plataforma; a prova é o CI.
