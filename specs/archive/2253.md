## Problem

A metade 2 de `quenching/assets/checks/citation-check.sh` lê só `source_roots = ("quenching/skills/", "quenching/references/")` (linha 506; filtro na 747). Uma citação `§` escrita dentro de um standard do bundle (`docs/standards/**`) nunca é conferida contra os títulos do alvo, nem quando o alvo é o próprio arquivo. Foi assim que a autocitação morta de `docs/standards/naming/command-surface.md:138` (`§Three citation forms`, depois que o título virou `### Two citation forms, and the condition on each`, linha 31) passou verde no gate: a spec 2246 só a achou à mão, e a spec 2249 (21/11/2026), que endureceu a resolução de alvos `§` e pôs a parte `cited cq calls`, deixou o bundle fora de escopo de propósito (`## Discoveries` da 2249: "follow-up: a parte 'cited sections' de citation-check.sh não varre docs/standards/**").

A melhoria tem de tornar impossível que um `§` morto num standard de `docs/standards/**` (autocitação ou citação de outro arquivo do bundle ou de `quenching/`) passe verde em `bash scripts/verify_repo.sh`. Medir antes o que a varredura acha hoje no bundle: as constatações existentes se corrigem na mesma spec ou entram como remanescente nomeado, nunca como exceção silenciosa.

**Insumos**

- `quenching/assets/checks/citation-check.sh:506` (`source_roots`) e `:747` (seleção dos arquivos lidos pela parte `cited sections`)
- `docs/standards/naming/command-surface.md:31` (o título atual) e `:138` (a autocitação, já corrigida à mão)
- spec 2249 (`## Outcome`, `## Discoveries`), spec 2246 (achou a autocitação à mão)
- o fix vive no checkout do quenching (`quenching/assets/checks/`), chega aos alvos via `python3 quenching/assets/bin/cq deploy --target . --write`

## Proposal

- A `§` written inside `docs/standards/**` is checked by the `cited sections` half of `citation-check.sh` against the headings of the file it names, or of the citing file itself.
- No dead `§` is left in the bundle: each finding the widened scan raised is corrected in place (a wrong heading or file name fixed, a link and its address joined on one line, a non-citation `§` such as a provenance note reworded), and none is excused by an exception list.

## Out of Scope

- A `§` inside `docs/concepts/**`, `docs/external/**` or the glossary: the standards are the bundle part that cites headings as binding addresses; widening further is a separate decision with its own measurement.
- Making the scanner follow a citation across a hard line break: the address rule already requires the file and the address on one line, so the docs are fixed instead.
- The Windows-only findings the same probe raises over `quenching/skills/**` and `quenching/references/**`: they pre-exist on the base and are not this spec's.

## Design

### The scope is the source_roots tuple, and nothing else

`source_roots` is the one declaration of what the cited-sections half reads; adding `docs/standards/` to it reuses the whole resolution (the heading index already covers `docs/`, target resolution already resolves bundle-relative paths). No new code path, no exception list.

### A finding is corrected, never excused

A `§` that is not a citation (a provenance line, a step number, a placeholder) is reworded so the section sign no longer appears; a citation that is wrong is pointed at the heading that exists. The scanner stays strict, which is what makes a later dead self-citation fail the gate.

## Alternatives Considered

- An allowlist of known-benign lines in the check: rejected, it is the silent exception the Problem forbids.
- A second scanner for the bundle: rejected, a second implementation of the same address rule would drift from the first.

## Open Decisions

- none — every item was settled from evidence (the probe's own output).

## Risks

- A future standard that uses `§` as a plain symbol fails the gate: ACCEPTED — the failure names the file and line, and rewording is a one-line edit; that is the strictness the spec buys.
- The Windows run of the check cannot prove the Linux result: mitigated by the CI gate being the proof of record.
