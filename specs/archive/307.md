## Problem

Feedback de usuário (2026-11-24, alvo Windows com antivírus Trend analisando cada processo): os hooks do `.claude/settings.json` rodam a cada comando de shell, cada um como `uv run … python`; são pelo menos 8 processos antes de qualquer git, e com a `.venv` principal sem `pyvenv.cfg` eles falham e travam tudo.

Evidência no código: `quenching/assets/bin/quenching/deploy/settings.py:41-55` gera uma entrada `PreToolUse` por hook declarado (`modules.json:27-33,82-88`: deny-claude-coauthor e warn-git-add-all, mesmo matcher `Bash|PowerShell|bash|powershell`), e o prefixo é `shared.mcp.command` (`settings.py:22`); um alvo que declara `uv run python` paga o `uv` (resolução/sync do projeto) duas vezes por comando, e o `uv` sai **2** em erro, que o Claude Code lê como bloqueio do tool. O Copilot lê o mesmo arquivo.

**Consequência:** cada comando de shell paga ≥2 interpretadores (≥4 processos com uv), e um ambiente quebrado bloqueia toda chamada de shell da sessão.

Proposta mínima: um único hook despachante (um processo `-I`, uma leitura de stdin) que roda todos os corpos declarados no mesmo matcher; o prefixo dos hooks é um interpretador direto (o mesmo resolvido pelo probe de `deploy/mcpfiles.py:20-46`), nunca `uv run`/`uvx`; um prefixo declarado com `uv run` é trocado pelo interpretador direto ou recusado com aviso; e o hook falha aberto (`{}`, exit 0) em qualquer erro do próprio despachante. O `--check` acusa entradas antigas (duas entradas) como drift e a escrita converge numa passada.

## Proposal

- Cada par `(event, matcher)` declarado em `owned.hooks` vira **uma** entrada no `.claude/settings.json`: um único processo Python (`-I`), uma leitura de stdin, que roda todos os corpos daquele matcher e devolve uma saída combinada (deny vence; `systemMessage` e `additionalContext` concatenados).
- O prefixo dos hooks é sempre um interpretador direto: um `shared.mcp.command` (ou prefixo gravado) que começa com `uv`/`uvx` é trocado pelo primeiro de `python3`, `python`, `py -3` que roda Python ≥ 3.11 na máquina, com um aviso no payload do deploy; o MCP continua com o prefixo declarado.
- O despachante falha aberto: qualquer erro dele ou de um corpo imprime `{}` (ou a saída dos corpos que funcionaram) e sai 0; nunca sai 2.
- `cq deploy --check` acusa as entradas antigas (uma por hook) como drift `settings`, e uma única `--write` converge para a entrada única; uma segunda `--write` não muda nada.
- `docs/standards/automation/hooks.md` descreve o despachante e a regra "nunca `uv run`" como contrato `current`.

## Out of Scope

- O prefixo do servidor MCP (`.mcp.json`, `opencode.json`, `.codex/config.toml`) — fica com a spec 308, que registra o MCP com interpretador direto; aqui só os hooks deixam de usar `uv`.
- Reescrever os corpos `deny-claude-coauthor.py` e `warn-git-add-all.py`: o contrato deles (`decide(raw) -> dict`) é reaproveitado como está.
- Proteger contra um interpretador que nem inicia (binário ausente, venv sem `pyvenv.cfg` no PATH): o Claude Code lê saída ≠ 2 como erro não bloqueante, e nada dentro do Python roda antes de ele iniciar — ver `## Risks`.
- Um arquivo `.github/hooks/` próprio do Copilot (já descartado pelo padrão: rodaria cada hook duas vezes).
- O lançador `cq.cmd` do Windows (spec 313).

## Design

- **Um despachante por `(event, matcher)`, nunca um por hook.** O Claude Code roda em paralelo todos os hooks que casam e cada um paga uma partida de interpretador; o custo escala com o número de corpos. O despachante é um arquivo próprio, `assets/hooks/dispatch.py`, chamado pela mesma linha poliglota (`<prefixo> -I -c "<código>" <nome> <nome>…`): os nomes viajam em `sys.argv`, que bash, PowerShell e cmd passam sem expandir porque são `[A-Za-z0-9_-]+` (validado em `desired_entries`; outro nome é recusado). O código `-c` continua sem `$`, crase, `%`, `!` nem aspas internas.
- **Contrato dos corpos: `decide(raw: str) -> dict`.** O despachante carrega cada `<nome>.py` com `importlib.util.spec_from_file_location` (não como `__main__`) e chama `decide`. Ordem = ordem de declaração em `modules.json`. Combinação: o primeiro `permissionDecision: deny` vence e as razões de todos os deny se juntam; `systemMessage` junta com `"; "`, `additionalContext` com `" "`. Corpo ausente, sem `decide`, ou que levanta exceção → ignorado; erro do próprio despachante → `{}`. Sempre `exit 0`. Corpos continuam executáveis sozinhos (`__main__`), o que mantém os testes existentes.
- **O marcador continua sendo o caminho.** A entrada nova contém `.agents/quenching/assets/hooks/dispatch.py`, então `_own_name` a reconhece como `dispatch`; as entradas antigas (`deny-claude-coauthor.py`, `warn-git-add-all.py`) continuam reconhecidas como do quenching, não estão em `pending` e saem — é isso que faz `--check` acusar drift e uma `--write` convergir. `timeout` da entrada = maior `timeout` dos corpos do grupo.
- **O prefixo dos hooks nunca é `uv`.** `uv run` resolve/sincroniza o projeto a cada chamada e sai **2** em erro, que o Claude Code lê como bloqueio do tool. `mcpfiles.direct_prefix(prefix)` devolve o prefixo inalterado quando o basename do primeiro elemento (sem `.exe`, minúsculo) não é `uv`/`uvx`; senão o primeiro de `CANDIDATES` que roda Python ≥ 3.11, senão `python3`, mais um aviso. O prefixo escolhido fica em `claudeSettings.command` no manifesto e é reaproveitado no próximo deploy (mesmo antiflap do MCP).
- **O MCP não muda aqui.** `mcp_argv` continua com o prefixo declarado; a spec 308 cuida dele.
- **Autorização.** O épico 306 (`## Design`, decisão do humano de 2026-11-24) autoriza juntar os hooks num processo sem `uv run`; nada além disso.

### Assumptions

- O Claude Code trata saída ≠ 0 e ≠ 2 de um hook como erro não bloqueante — sustenta `## Risks` (interpretador que não inicia).
- `runpy.run_path` preserva `sys.argv` do `-c`, então `dispatch.py` lê os nomes de `sys.argv[1:]` — sustenta `## Design`, verificado no teste poliglota.

## Alternatives Considered

| Forma | Custo | Ganho | Fecha | Veredito |
| --- | --- | --- | --- | --- |
| Despachante em arquivo (`dispatch.py`) + nomes em argv | um arquivo novo instalado | um processo por matcher, corpos intactos, falha aberta num lugar só | nada | **escolhida** |
| Fundir os dois corpos num só arquivo | reescrever dois módulos de donos diferentes (`quenching-specs`, `quenching-git`) | um processo | quebra a posse por módulo: um deploy só com `git` levaria o corpo do `specs` | rejeitada |
| Laço inteiro dentro do `-c` (sem arquivo) | linha poliglota longa, sem `try` possível numa expressão | nenhum arquivo novo | a falha aberta fica fora do alcance; testes difíceis | rejeitada |
| Manter um processo por hook e só trocar `uv` | nenhum | conserta o travamento | o custo de N interpretadores por comando continua | rejeitada: resolve metade do problema |

## Risks

- **Interpretador que não inicia** (binário ausente, `.venv` quebrada no PATH): nada dentro do Python roda. ACCEPTED — o prefixo deixa de ser `uv` (que sai 2); um `python3` ausente sai 127 e um Python que aborta na inicialização sai 1, ambos não bloqueantes no Claude Code. No Copilot do Windows uma falha pode negar o tool; a mitigação é o probe escolher um interpretador que roda.
- **Um corpo lento atrasa os outros** (antes rodavam em paralelo). ACCEPTED — os dois corpos são regex + parse sob demanda, milissegundos; o timeout da entrada é o maior dos corpos.
- **Uma exceção num corpo esconde a saída de outro.** Mitigado: cada corpo roda no seu `try`; só o corpo que falhou é ignorado.
- **Alvo com entradas antigas editadas à mão** (timeout trocado): a convergência as remove e cria a nova. ACCEPTED — entradas do quenching são do deploy, o padrão já diz que o merge as reescreve.
- **Flap do prefixo entre máquinas** quando `shared.mcp.command` é `uv`: mitigado gravando o prefixo escolhido em `claudeSettings.command` no manifesto.
