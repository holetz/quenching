## Problem

No release 6.5.0 (2026-10-17), `cq specs release` exigiu a entrada `## 6.5.0` no `CHANGELOG.md` mas deixou o arquivo fora do commit do bump (o condutor emendou antes do push), e não regenerou `common/version.py` nas cópias dos módulos, do Codex e do specs-reader, o que quebrou `test_specs_reader_plugin.test_its_payload_is_in_lockstep_with_the_source` e exigiu o commit `30bc0c86` depois da tag — o mesmo aconteceu no 6.4.0 ("Regenerate the Codex and specs-reader copies for 6.4.0"). A tag `6.5.0` aponta para o bump com as cópias ainda em 6.4.0.

## Proposal

- `cq specs release <version>` regenera, depois do bump e antes do commit, as cópias geradas dos módulos, do Codex e do specs-reader (`generate_plugin_modules.py --write` e `sync_codex_plugin.py --write`), quando esses scripts existem no repositório alvo.
- O commit `release: X -> Y` carrega o `CHANGELOG.md`, os artefatos do bump e todas as cópias regeneradas; a tag aponta para um commit em que `verify_repo.sh` já passa.
- O verbo recusa (exit 2, nada escrito) quando a árvore tem alterações fora do `CHANGELOG.md`, para que o commit só contenha o release.
- `docs/standards/ci-cd/versioning-release.md` descreve a regeneração e a inclusão do CHANGELOG.

## Out of Scope

- Escrever a entrada do CHANGELOG: continua do condutor do release; o verbo só a exige e a commita.
- Push do commit ou da tag: continua do comando `release`.
- Mudar a lista de artefatos de `modules.json` ou o gate `verify_repo.sh`.

## Impact

### Standards this spec will write into docs/standards/

- `docs/standards/ci-cd/versioning-release.md` — o release regenera as cópias geradas e commita o CHANGELOG junto

### Product code this spec expects to touch

- `plugins/quenching/assets/bin/quenching/specs/release.py` — helpers de regeneração e de árvore limpa
- `plugins/quenching/assets/bin/quenching/specs/commands/release.py` — usa os helpers e stageia o CHANGELOG
- `plugins/quenching/tests/test_specs_release.py` — cobertura do novo comportamento
- cópias geradas de `specs/release.py` e `specs/commands/release.py` em quenching-specs, quenching-specs-reader e quenching-codex

## Validation

- `python3 -m unittest discover -s plugins/quenching/tests -p test_specs_release.py` passa, incluindo os testes novos que rodam `cmd_release` num repositório git descartável.
- `bash scripts/verify_repo.sh` sai com 0 depois do trabalho (cópias geradas em lockstep).
- Num repositório descartável com scripts geradores falsos, o commit do release contém `CHANGELOG.md`, os artefatos e o arquivo regenerado; `git status` fica limpo.

## Design

Regra durável: o commit de release é autocontido — contém tudo o que o gate exige para estar verde na tag.

- `specs/release.py` ganha `dirty_paths(repo)` (lê `git status --porcelain`) e `regenerate_copies(repo)`, que roda, com `sys.executable` e cwd no repositório, `scripts/generate_plugin_modules.py --write` e `scripts/sync_codex_plugin.py --source plugins/quenching --target plugins/quenching-codex --write`, cada um só se o script existir. Falha de um script é erro com o nome do passo.
- `cmd_release`: antes do bump, recusa com `sp-release-dirty` (exit 2) se houver caminhos sujos além de `CHANGELOG.md`; depois do bump, regenera; faz `git add -A` (a árvore estava limpa salvo o CHANGELOG, então tudo o que está sujo é do release) e commita.
- Se a regeneração falha depois do bump, o erro diz que o bump está não commitado na árvore; nenhum commit nem tag são feitos.

### Mapa de dependências

- `specs/commands/release.py` é o único chamador de `bump_release_artifacts`; `cli.py` só o registra.
- As cópias em `plugins/quenching-specs`, `quenching-specs-reader` e `quenching-codex` espelham o código e são regeneradas pelos próprios scripts; `.generated-files.json` do Codex muda com elas.

## Alternatives Considered

- Fazer o comando `release` (prosa) rodar os geradores e emendar: rejeitado, é o que o condutor já faz à mão e esquece; a regra mecânica pertence ao verbo.
- Só `git add CHANGELOG.md` no verbo: resolve metade; a tag continua apontando para cópias em lockstep quebrado.

## Open Decisions

- none — a recusa por árvore suja é decidida aqui (necessária para o `git add -A` ser seguro) e não depende de evidência futura.

## Risks

- `git add -A` stagearia lixo alheio: mitigado pela recusa de árvore suja antes do bump.
- Regeneração falha com o bump já escrito: o erro nomeia o passo e o estado; o humano corrige e commita à mão, sem tag. ACCEPTED — o bump é determinístico e idempotente na releitura.
- Repositórios alvo sem os scripts: os passos são pulados em silêncio.
