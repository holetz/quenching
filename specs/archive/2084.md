## Problem

`cq specs migrate` moves a tracker backend onto the `quenching` branch (`--to git`) with an equality check, but nothing moves the other way, so a team whose store is a git branch cannot leave it once the branch's commit volume floods the repository's global view (1,644 commits in seven days on this repository's own branch). Add `--to azure`: create one work item per spec with the whole document in `System.Description` as Markdown, carry the records, dates and dependencies, prove equality spec by spec before switching `backend`, and stay a dry run unless `--write`.

Member S28 of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent).

## Proposal

- `cq specs migrate --to azure` exists beside `--to git`. The source is the `git` store of the repository; the destination is the Azure Boards backend already configured for it.
- It is a dry run unless `--write`. The dry run reads the whole front and the destination, writes nothing, and reports the count, the creation order, the planned id map shape, and every reason a write would refuse.
- A write creates one work item per spec, the whole canonical document in `System.Description` as Markdown, through the backend's own `create_spec`. Open specs are created in the declared active state and archived ones in the declared closed state. Tags, assignee, `start`, `target`, the records and `dependsOn` travel with the document.
- Azure allocates the work item ids, so the spec ids change. The command prints the map from each source id to its new id, and rewrites the references that are ids: `dependsOn` (which becomes the predecessor links of 2083), and the `— spec: #<id>` of an epic's member items.
- Equality is proved spec by spec before anything says the move is done: each created item is read back and must equal the source modulo locator and id, with the references remapped. A difference is reported per spec and makes the exit 1.
- `backend` is never switched by the command. It prints the `.claude/quenching.json` change the human applies after the equality holds, as `--to git` already does.
- The command refuses (exit 2, nothing written) a destination that already lists specs, a reference to an id the front does not hold, and a document over the description ceiling.

## Out of Scope

- The real migration of the quenching store onto `https://dev.azure.com/holetz/quenching`. Epic 2096 makes it a separate step after parity; this spec proves `--to azure` against an in-memory double only and no test or worker writes to a real organisation.
- Rewriting ids that appear in prose, commit messages, PR bodies or the branch history. Only the structured references listed above are remapped; the id map is printed so a human can search the rest.
- Rollback of a partial write. A work item deletion is destructive and the backend has no delete primitive; a failed batch reports what it created and stops.
- Moving between trackers (`github` to `azure`) or `azure` back to `git`. Only the git store is a source.
- Any change to `grant`, `allowed-tools`, hook or CI. Those belong to epic 2045.
- Retiring the git backend (2093), the GitHub adapter (2091) and the adapter location work (2092).

## Design

**Rules the design must not contradict.** `docs/standards/architecture/spec-backend.md`: five primitives, the whole canonical document is the work item description, a backend derives nothing, every write passes the leak guard. Epic 2096 `## Design`: the quenching organisation is reached through `AZURE_CONFIG_DIR`, no test or worker writes to it, the real migration is a later step, and no grant, hook or CI widening goes in this spec.

**Decisions.**

1. *The migration drives the backend's public primitives, never `az`.* `create_spec(phase, text)` and `write_spec` already carry the Markdown description, native fields, state, column, parent and predecessor links (2083). The command adds ordering, id remapping and the equality; nothing in the Azure transport changes. This is also what makes the double honest: the same code path runs against any `SpecBackend`.
2. *Ids are remapped, never preserved.* Azure assigns the ids. The creation order is topological over numeric `dependsOn` (dependencies first, ties by source id), so each item is created once, already carrying its predecessors as links. Epics are the exception: an epic's member items name ids that do not exist yet, so after the batch the command rewrites each epic's `— spec: #<id>` lines with one `write_spec` per epic.
3. *Unresolvable references fail closed.* A numeric `dependsOn` or epic member that the front does not hold, or a dependency cycle, is listed as `unresolved` and the write refuses before creating anything. A non-numeric dependency (a slug, an `owner/repo#id` reference) is carried untouched, as `azure_predecessor_ids` already ignores it.
4. *Equality is per source spec.* The expected document is the source text, reassembled with its native fields and with ids remapped. It is derived under the new id and compared with the item read back through the same `comparable` and `diff_fronts` the git direction uses, and the document itself is compared with the native-field keys stripped and the native values compared apart (the backend stores those natively). The ids in the report are the new ones, with the source id beside each.
5. *A re-run never duplicates.* The tracker has no idempotent create, so `--write` refuses a destination that already lists specs (`sp-migrate-target-not-empty`, exit 2). The dry run reports the same condition as `occupied` and a non-ok result.
6. *Partial failure is reported, not hidden.* A refusal from the backend mid-batch stops the loop and returns the created ids and the failing source id with `ok: false`. The caller keeps the git store untouched, so nothing is lost, and the report names the items to remove by hand.
7. *The source must be the git store.* Any other declared backend refuses with `sp-migrate-source-not-git`; the destination is resolved by the existing `open_azure_backend`, whose refusals (`azureStates`, `areaPath`, default organisation) arrive unchanged.

## Alternatives Considered

| Shape | Why it lost |
| --- | --- |
| Preserve the git spec ids in Azure by creating items and renaming ids | The work item id is allocated by the server and cannot be chosen; a translation table plus remapped references is the only shape the service allows. |
| Create every item first, then add `dependsOn` links in a second `write_spec` pass | Two revisions per dependent spec and a window where the store holds specs with no links; the topological order creates each item once with its links. Only epics, whose member ids are unknowable before the batch, take a second write. |
| Call `az boards work-item create` directly from the migration | Duplicates the field mapping, state, column and leak-guard logic of `AzureBoardsBackend` and escapes the double; the backend's primitives are the single path. |
| Put a roll-back on failure | Needs a delete primitive and a destructive call on someone's board; a report of what was created is the safe equivalent. |

**Reference projects (epic holetz/forge#1, read 2026-10-25).**

- *automazeio/ccpm* (MIT): adapts. Its sync of PRD and epics into a tracker with a dependency mapping is the same problem; the id mapping from a local file to the tracker's id is taken, and its one-issue-per-task shape is rejected because here the whole spec, tasks included, is one work item.
- *microsoft/azure-devops-mcp* (license to confirm): adapts nothing in code, rejects as a transport. The adapter keeps the `az` CLI behind `AzureBoardsBackend`; the MCP shapes are the concern of the read and write surface specs (2085, 2086). It stays the model for tool and auth shapes only.

- *`cq specs serve` portal*: reuses nothing; the migration has no UI.

## Risks

- A parent or epic reference outside `dependsOn` and the epic members keeps its old id, so it points at the wrong item after the move. Mitigation: the id map is printed, and the dry run reports unresolved references (missing id, self, cycle, missing epic member); prose and other keys are not scanned. ACCEPTED for prose; the structured ones are covered.
- The first write against a real board can fail halfway and leave items behind. Mitigation: the destination must be empty before a write, so leftovers are the only items and are listed in the report; the git store is never touched. ACCEPTED — no delete primitive exists and this spec adds none.
- The double proves the migration logic, not Azure's own behaviour (Markdown description, state names). Mitigation: those paths are the backend's own and are exercised by its existing tests and by 2083's round trip; the real run is a separate step after parity.
- A document over the description ceiling would fail at write time. Mitigation: the dry run measures every document against `AZ_DESCRIPTION_MAX` and the write refuses before creating anything.

## Outcome

`cq specs migrate --to azure` now moves a `git` spec store onto Azure Boards. It is a dry run unless `--write`. It refuses a source that is not `git`. It creates specs through the destination's `create_spec` in dependency order, then rewrites epic `— spec: #<id>` lines with a second write. It reads every item back and compares it to its source modulo the natively stored keys, and it prints the `.claude/quenching.json` change instead of applying it. Nothing is created when the destination is non-empty, a spec is unreadable, a reference is unresolved or a document passes `AZ_DESCRIPTION_MAX`.

Shipped in `migrate.py` and `cli.py` (with the five mirrors regenerated), proved by `test_specs_migrate_azure.py` against the memory-backed double, and documented in `docs/standards/architecture/spec-backend.md` under the Migration rule.

Left out: no delete primitive, so a failure halfway leaves the created items listed in the report. Azure assigns new ids, the printed id map is the only record of the old ones, and prose or other keys naming an old id are not scanned. The config switch stays with the human.
