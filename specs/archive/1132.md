## Problem

A skill de criação e status de pull requests lê o campo `url` do JSON do Azure sem distinguir o endpoint REST do endereço navegável. Como `az repos pr create --output json` retorna `url` em `/_apis/...` e `repository.webUrl` para o repositório, o relatório pode expor o endpoint técnico no lugar do link da revisão.

## Proposal

- Normalizar a resposta dos providers em `id`, `webUrl` e `apiUrl`.
- No Azure, construir sempre o link de revisão a partir de `repository.webUrl + /pullrequest/{pullRequestId}`.
- Proibir no relatório um link humano contendo `/_apis/`.
- Aplicar a mesma normalização ao `quenching-git-pr-status`.
- Rotular claramente no contrato a diferença entre `Link para revisão` e `API URL`.

## Out of Scope

- Não alterar os endpoints REST usados para criar ou consultar PRs.
- Não normalizar URLs de GitHub que já sejam navegáveis nem esconder a API URL necessária ao diagnóstico.
- Não criar um novo provider.

## Impact

### Product code this spec expects to touch

- plugins/quenching/assets/bin/quenching/git/pr.py e adapters Azure/GitHub
- plugins/quenching/commands/git/pr/create.md e pr/status.md
- plugins/quenching/assets/references/git/pr.md
- plugins/quenching/tests/test_git.py e test_specs_backends.py

### Standards this spec will write into docs/standards/

- none — é normalização de payload e relatório, sem standard novo.

## Validation

- Resposta Azure produz repository.webUrl/pullrequest/id como webUrl e mantém url REST somente como apiUrl.
- Relatórios nunca exibem /_apis/ como Link para revisão e diferenciam Link para revisão de API URL.
- GitHub e Azure continuam passando seus fixtures existentes.
## Design

Cada adapter retornará um modelo com id, webUrl e apiUrl. O status e o relatório usarão webUrl para o link humano e rotularão apiUrl como endpoint técnico. No Azure, webUrl será derivado de repository.webUrl e pullRequestId quando a resposta não trouxer um link navegável; nunca será construído a partir do campo url que contém /_apis/.

### Mapa de dependências

Atualizado em 2026-09-02. git/pr/create e git/pr/status consomem respostas de GitHub/Azure e produzem records/relatórios; skills Codex e referências git/pr descrevem os campos. Fixtures de test_git e testes de provider congelam a forma.

## Alternatives Considered

| Forma | Custo | Benefício | O que fecha | Decisão |
| --- | --- | --- | --- | --- |
| Expor o campo url bruto do Azure | zero | preserva resposta | entrega endpoint REST ao humano | rejeitada |
| Remover API URL do payload | baixo | evita confusão visual | perde diagnóstico e automação | rejeitada |
| Separar webUrl/apiUrl no modelo e relatório | pequeno | cada consumidor usa o endereço correto | exige fixture de regressão | escolhida |

## Open Decisions

- Se repository.webUrl estiver ausente, o adapter deixará webUrl nulo e reportará API URL separadamente; não inventará domínio.

## Risks

- A forma do JSON do Azure pode variar entre versões do CLI; mitigação: aceitar aliases conhecidos e testar a resposta mínima.
- Consumidores antigos podem ler url; mitigação: manter apiUrl explícito durante a transição e atualizar os dois caminhos de PR.

## Handoff

Executar junto da camada git após 1130 e antes da publicação do PR agregado. O link humano só pode ser afirmado quando o adapter tiver evidência navegável.

## Outcome

- Entregue: os adapters de pull request agora normalizam `id`, `webUrl` e `apiUrl`; Azure deriva o link navegável de `repository.webUrl` e `pullRequestId`, mantendo o endpoint `/_apis/` como API URL.
