## Problem

The security pillar asks "Are workflow and job permissions explicit and bounded?" but `workflow_permissions` only counts `permissions:` lines, so a workflow that declares `permissions: write-all` reports `present` — the question's own "bounded" half is never measured.

## Proposal

Read the value of each workflow-level and job-level `permissions:` declaration. A literal `write-all` is the one grant that is unbounded by definition: it moves the question to a new state, `unbounded`, with the offending paths and levels as evidence. Per-scope `write` grants are reported as evidence (`writeScopes`) without changing the state, because whether a specific write is safe stays the target owner's call.

## Out of Scope

- Judging individual write scopes, `id-token`, or SHA pinning of actions.
- Reading `.claude/settings.json` or `.mcp.json`.
- Any write to the target repository.

## Impact

### Product code this spec expects to touch

- `quenching/assets/bin/quenching/security/probe.py` — `workflow_permissions`
- `quenching/tests/test_security.py` — `write-all` at both levels and write scopes as evidence
- `quenching/skills/quenching-security/references/status.md` — the state column names `unbounded`
- `docs/standards/architecture/security-pillar.md` — the question's evidence names the `write-all` reading

## Validation

`python3 -m unittest discover -s quenching/tests -p test_security.py` passes; `cq security --json` on this repository still reports `present`; `bash scripts/verify_repo.sh` shows no new failure.

## Design

- A line-based reader keeps today's YAML-free approach: for each `permissions:` line, an inline value (`write-all`, `read-all`) is read from the same line; a block value is the following lines indented deeper, each `<scope>: <level>`.
- Evidence per workflow adds `writeAll: [<"workflow"|"job:<line>">...]` and `writeScopes: [<scope>...]`.
- State precedence: `refused` > `unbounded` > `present` > `missing`.
- Precedent: equin's release workflow sets `contents: read` at the top and raises scopes per job only (`.github/workflows/installer-release.yml`).

## Alternatives Considered

- Flag every write scope as unbounded: contradicts the standard's boundary that the target owner decides whether a permission is safe. Rejected.
- Parse YAML: the probe is stdlib-only and line-based by design. Rejected.

## Open Decisions

- none — `write-all` is unbounded by its own definition, so no owner judgment is substituted.

## Risks

- A consumer that enumerates the states sees a new value; the status reference and the standard are updated in this spec, and the controls block does not read this question's state.

## Outcome

Shipped: `workflow-permissions` reads the value of every workflow- and job-level `permissions:` declaration (inline, flow mapping or block). A `write-all` grant moves the question to the new state `unbounded`, located in `writeAll` as `workflow` or `job:<line>`; scopes granted `write` are listed in `writeScopes` as `<where>:<scope>` and never change the state, since whether a scoped write is safe stays the target owner's call.
