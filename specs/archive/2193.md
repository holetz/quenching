## Problem

`cq git preflight` answers `store` and `push` by dry-running the local branch onto its own name (`ref:ref`). A branch that is merely behind or diverged from the remote is rejected as non-fast-forward, so the check reports `fail` exactly like a remote that refuses writes, and the autopilot turns that `fail` into a "fix the push" spec for a capability that is intact.

## Proposal

Probe write capability against a ref the remote does not have: dry-run `<source>:refs/heads/quenching-preflight-probe` with `--force`, so no fast-forward rule can reject it, and classify a failure by git's own stderr into `read-only` or `no-credentials` (status `fail`, a capability the human must fix) versus `unreachable` or `probe-failed` (status `unknown`, never promoted to `fail`). Every `store` and `push` check carries the `reason` it was classified under. The autopilot contract is unchanged: it already opens a fix spec only on `fail`.

## Out of Scope

- Changing the `ghAuth` or `ci` checks.
- Making the probe ref name configurable — a dry-run never creates it, so no forge sees it.
- Any change to `cq git push`, which performs the real push.

## Impact

### Product code this spec expects to touch

- `quenching/assets/bin/quenching/git/preflight.py` — `_dry_push`, `_store`, `_push` and the module docstring
- `quenching/tests/test_git_preflight.py` — the behind-the-remote case and the stderr classification

## Validation

`python3 -m unittest discover -s quenching/tests -p test_git_preflight.py` passes, including a branch behind its remote reporting `push: ok` and the store behind its remote reporting `store: ok`; then `bash scripts/verify_repo.sh` shows no new failure.

## Design

- `_dry_push(cwd, remote, source)` runs `git push --dry-run --porcelain --force -- <remote> <source>:refs/heads/quenching-preflight-probe` under the existing `GIT_TERMINAL_PROMPT=0` environment, and returns `(status, why, reason)`.
- Classification reads lower-cased stderr: `permission`, `denied`, `403`, `not allowed`, `protected` → `read-only`; `could not read username`, `authentication`, `terminal prompts disabled`, `401` → `no-credentials`; `could not resolve`, `unable to access`, `connection`, `timed out` (and exit 124/127) → `unreachable`; anything else → `probe-failed`.
- The store's existence checks (local ref, then `ls-remote`) are kept; only the dry-run inside them changes.
- Precedent: equin's remotes probe (`plugins/infra/plugins/git/plugins/remotes`) — probe a nonexistent ref with `--force` and no prompts, four outcomes, only the definitive ones acted on.

### Assumptions

- A dry-run push still opens the remote's receive-pack and so exercises authentication and write authorization on HTTPS forges — Design.

## Alternatives Considered

- Parse the porcelain `!` line for `non-fast-forward`/`fetch first` and map it to `ok`: keeps `ref:ref`, but a diverged store branch would still be probed with the wrong question, and every other failure stays one undifferentiated `fail`. Rejected.
- Fetch before probing: costs a network round and still fails on a diverged branch. Rejected.

## Open Decisions

- none — the classification set and the `unknown` mapping follow the module's own rule that an unanswerable check is `unknown`, never `ok` or `fail`.

## Risks

- A forge that phrases a refusal outside the keyword set lands in `probe-failed` (`unknown`) instead of `fail`; that errs toward no spurious fix spec, and the `why` text is still reported.

## Discoveries

- the leak patterns derive from HOME: the home-slug is the HOME path with each slash turned into a dash, so on a host whose HOME is the root user's home (a root container or CI runner) the slug is the five characters dash-r-o-o-t and matches every double-dash "root" CLI flag in the repository — 644 leak-gate findings on a clean tree — and the spec store's write sanitizer rewrites any word ending in dash-r-o-o-t into a project placeholder (it mangled "temp" + dash-r-o-o-t in spec 2197 and the flag spelled in this very line); a short HOME needs a boundary on the left as well as the right
- decision: added task 1.2 to refresh the deployed surface — cq deploy copies preflight.py into .agents/quenching/assets/bin, which the spec's tasks had not declared
## Outcome

Shipped: `cq git preflight` now asks write capability of a ref the remote does not have (`refs/heads/quenching-preflight-probe`, dry-run with `--force`), so a branch or store that is behind or diverged from its remote reports `ok` instead of a false `fail`. A failed probe carries `reason`: `read-only` and `no-credentials` stay `fail` (the autopilot's fix-spec trigger is unchanged), `unreachable` and `probe-failed` are `unknown`. Credentials and refusals are matched before "unable to access", because a forge's 401/403 arrives wrapped in it.

Left out: the probe ref name is fixed, not configurable; `ghAuth` and `ci` are untouched.

Next reader: the keyword sets live in `_NO_CREDENTIALS`, `_READ_ONLY` and `_UNREACHABLE` in `quenching/assets/bin/quenching/git/preflight.py`; a forge wording outside them lands in `probe-failed`, which never opens a fix spec.
