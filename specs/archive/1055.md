## Problem

O comando `git cleanup` do plugin atualmente cobre apenas branches locais e worktrees órfãos, embora a sessão tenha exigido verificar e podar também branches publicados no remoto. A spec deve revisar esse comando para que seu fluxo alcance o remoto com a mesma seleção explícita e as exclusões seguras usadas nesta sessão.

## Proposal

- Extend `cq git stale --json` with a deterministic `remoteBranches` list for `origin` branches whose fetched tips are already merged into the resolved base. Each entry carries the remote name, branch name, and reason; `origin/HEAD`, the base branch, and the current branch are protected.
- Keep `cq git stale` read-only. It reports the remote-tracking facts already present locally and does not fetch, prune refs, or delete anything on the server.
- Extend `/quenching:git:cleanup` to show remote branches beside local branches and orphan worktrees in its one multi-select offer. A selected remote branch is deleted only after that offer with `git push origin --delete <branch>`; the exact external action is shown and its refusal is reported verbatim.
- Preserve the existing local-branch `-d` and worktree no-`--force` boundaries. A remote branch not present in the fresh stale report is never eligible, and an empty selection remains a no-op.
- Update the source tests, command surface, generated Codex mirror, and durable git workflow guidance together. The target's own git conventions continue to govern when declared.

## Out of Scope

- Deleting branches from remotes other than `origin`, deleting the default/base/current branch, or deleting a remote-tracking ref without deleting its server branch.
- Fetching or pruning stale remote-tracking refs automatically; the report uses only facts already available in the checkout.
- Changing merge, PR, branch-isolation, authentication, or provider APIs.
- Adding a force-delete path, silently selecting every branch, or broadening cleanup to branches not reported by `cq git stale`.
- Retrofitting remote-branch cleanup into repositories whose target conventions explicitly prohibit it; those conventions remain the governing contract.

## Design

`cq git stale` remains a facts-only command. It resolves the base once, reads the `origin` remote-tracking refs already in the local repository, and selects refs whose tips are reachable from that base. The report excludes `origin/HEAD`, the base branch, and the checked-out branch before returning the branch name and reason. The new JSON field is additive, so existing local `staleBranches` and `orphanWorktrees` consumers remain valid.

`/quenching:git:cleanup` consumes one fresh report and presents one explicit multi-select containing local branches, remote branches, and orphan worktrees. The selected remote item retains its `{remote, branch}` identity through the action; it is never reconstructed from display text. After the human's selection, local branches use `git branch -d`, worktrees use `git worktree remove`, and remote branches use `git push origin --delete`. Each refusal leaves that item standing and is reported with the command's own message.

The implementation deliberately does not fetch first: a fetch changes the checkout's remote-tracking facts and can prune local refs before the human sees them. A caller that needs a fresh remote view can fetch explicitly and rerun `cq git stale`; the cleanup command then acts only on the new report.

## Alternatives Considered

- Use `git remote prune origin`. Rejected because it deletes only local remote-tracking refs and does not remove the published branch on the server.
- Delete every branch merged into the base automatically. Rejected because cleanup is destructive and branch retention is a human decision.
- Fetch immediately before deletion. Rejected because it changes the facts behind the displayed selection and can prune refs before confirmation; an explicit fetch followed by a fresh report is clearer.
- Support every configured remote in this change. Rejected because the repository's base and PR route resolve through `origin`; adding independent remote-selection semantics would enlarge the destructive surface without a current use case.
- Reuse local `git branch -d` for remote names. Rejected because it cannot delete the server branch and could confuse a remote-tracking ref with a local branch.

## Open Decisions

- Whether future multi-remote support should offer one remote at a time or carry a remote selector belongs to a separate spec; this change fixes `origin` explicitly.
- Whether a host provider's protected-branch policy should be queried before the push is deferred; the base/current exclusions and the provider's own refusal remain the safety boundary here.

## Risks

- A fetched remote-tracking tip can become stale between report and deletion. Mitigation: no implicit fetch, a fresh report is required for every run, and the exact destructive command is shown in the one selection confirmation.
- A remote branch deletion is an external write with broader impact than deleting a local ref. Mitigation: it is opt-in per item, never preselected, limited to `origin`, and reports refusal without escalation.
- Adding a JSON field can drift the Codex mirror or downstream consumers. Mitigation: additive payload tests, translation parity, citation checking, and generated-surface review.
- A branch named `origin/HEAD` or the base could be displayed as stale if protection is incomplete. Mitigation: protect symbolic HEAD, resolved base, and current branch in the inventory fixture.
