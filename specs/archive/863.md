## Overview

`plugins/quenching/README.md` §Upgrade still describes the pre-`specs.py release` world: a manual
version bump, and an "installing align compares versions" claim that plugin-first resolution
already retired. This spec rewrites that one opening paragraph (§Upgrade's changelog list below it
is untouched) to describe what actually happens today — plugin-first resolution with
`skills.py drift` catching legacy copies, and `specs.py release`, run by this repository's own
`/release` command at the `develop → main` merge, mechanizing the bump and the tag — citing
`docs/standards/ci-cd/versioning-release.md` and `docs/standards/git/branching.md` for the detail
rather than duplicating it. `## Alternatives Considered` weighs why a full rewrite beats a
pointer-only edit or doing nothing; `## Design` carries the drafted replacement text; `## Tasks` is
the single edit that lands it.

## Problem

Descoberto durante a revisão da branch de `plan/configurable-branch-strategy` (2026-08-04):
`plugins/quenching/README.md` §Upgrade ainda descreve o bump de versão como um passo manual
("Bump version in .claude-plugin/plugin.json and VERSION on each release") — não menciona
`specs.py release` nem o fluxo `develop`/`main` que essa spec introduziu. Fora do escopo da task
4.1 daquela spec, que declarava apenas o `README.md` da raiz.

## Proposal

Reescrever §Upgrade de `plugins/quenching/README.md` para descrever o release mecanizado:
`specs.py release <version>` bumpa os sete artefatos e cria a tag, disparado pelo comando
`/release` sob o fluxo `develop → main` (`docs/standards/git/branching.md`,
`docs/standards/ci-cd/versioning-release.md`) — não mais um passo manual.

## Design

**Decision — replace the whole opening paragraph, not just add a sentence.** Reading
`docs/standards/ci-cd/versioning-release.md` and `docs/standards/git/branching.md` (both
`authority: current`, dated 2026-08-04) surfaced a second stale claim beyond the one `## Problem`
named: the current §Upgrade text still says an "installing align compares" a target repo's
installed copy's `--version` against the shipped one — the pre-plugin-first model. Resolution and
the release trigger both changed since that sentence was written, so a sentence-level patch would
leave the newer claim standing next to the older one it contradicts. Alternative weighed: patch
only the release-trigger sentence and leave the install-comparison claim alone, since `## Problem`
didn't name it — rejected, because shipping a paragraph that still asserts a mechanism
`versioning-release.md` says no longer exists ("nothing installs them any more") is the same class
of staleness this spec exists to fix, one sentence later in the same paragraph.

**Decision — cite the two standards for the artifact-by-artifact detail, restate only the shape.**
Matches this README's own existing citation convention (it already links
`docs/standards/automation/context-budget.md` elsewhere rather than restating it) — the paragraph
names the mechanism and links out for the table, rather than reproducing
`versioning-release.md`'s six-row table inline.

**Decision — name `/release` as this repository's own tooling, not the plugin's.** `/release` lives
at `.claude/commands/release.md`, outside `plugins/quenching/`, so it is never installed by a
target repo. The paragraph says so explicitly, to head off a reader who installed the plugin
looking for a command that ships with it.

**The drafted replacement** (final wording may tighten at execute time; the facts and citations are
fixed):

> Resolution is **plugin-first, with no install and no fallback** — every command reaches its tool
> at `${CLAUDE_PLUGIN_ROOT}/assets/{bin,hooks}/<tool>` — so a version bump reaches every consumer
> the moment Claude Code applies the plugin upgrade; there is nothing installed to compare against
> and nothing to sync. What each front's align (`/docs:align`, `/specs:align`, `/skill:align`)
> still does is offer to **remove** a legacy copy a repo installed before resolution went
> plugin-first — `skills.py drift` is what finds one, reading the leftover's own `VERSION` constant
> against the shipped tool's.
>
> Publishing the bump itself is mechanized, not a manual edit. `specs.py release <version>` moves
> the seven version-carrying files together and creates the tag in one act:
> `.claude-plugin/plugin.json`, `VERSION`, the marketplace manifest's plugin entry, the three tool
> scripts' own `VERSION` constants (`assets/hooks/okf-validate.py`, `assets/bin/specs.py`,
> `assets/bin/skills.py`), and `assets/bin/session.py`, which carries the same constant though no
> consumer reads it back. This repository's own `/release` command
> (`.claude/commands/release.md` — not shipped by the plugin) drives it: run once, deliberately, at
> the **`develop → main` merge**, never at a spec's own conclude, it reads what accumulated on
> `develop` since the last release, proposes a patch/minor/major bump with its reasoning, and gates
> on one confirmation before merging, bumping, tagging and pushing. See
> [docs/standards/ci-cd/versioning-release.md](/docs/standards/ci-cd/versioning-release.md) for why
> each half of the lockstep matters, and
> [docs/standards/git/branching.md](/docs/standards/git/branching.md) for the `develop`/`main`
> split `/release` publishes into.

## Alternatives Considered

| Approach | Cost | Benefit | Forecloses |
| --- | --- | --- | --- |
| Do nothing | zero | none | leaves §Upgrade wrong on two counts — no mechanized flow, no plugin-first/no-install framing — for as long as anyone reads it |
| One-line pointer only ("see `/release` and `versioning-release.md`") instead of describing the mechanism | smallest edit | fast, low risk of drifting later | README stops being the operator manual CLAUDE.md itself says it is — a reader has to leave the file to learn anything |
| **Full rewrite, citing the standards for depth (chosen)** | one paragraph, kept in sync via links rather than duplicated tables | README stays the practical manual; the mechanism lives here, the "why" is one link away | none material — the paragraph can always be trimmed further later |
| Delegate entirely to `docs/standards/` (no prose in README, just links) | least prose to maintain | single source of truth, no duplication at all | crosses README's own stated role — CLAUDE.md draws the line as README owning the "how", `docs/standards/` owning the "why we build it this way" |

**Recommendation:** keep the full rewrite (the choice in `## Proposal`) — README is the operator
manual by this repo's own division of labor against `docs/standards/`; a pointer-only edit would
under-serve that role, and doing nothing leaves two separate stale claims standing.
