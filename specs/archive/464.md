## Problem

O agente de nuvem do Copilot trabalha numa branch própria, num ambiente montado por `copilot-setup-steps.yml`, que hoje não instala Python nem roda o `worktreeSetup`. Não há caminho para entregar uma spec a ele respeitando `plan/<id>-<handle>` e o registro da spec, nem para o code review do Copilot ler os padrões do projeto.

## Proposal

- `cq deploy` projeta `.github/workflows/copilot-setup-steps.yml` quando o repositório declara `shared.projections: ["github"]`: o job único `copilot-setup-steps`, disparado por `workflow_dispatch` e pelas mudanças do próprio arquivo, com `contents: read`, checkout, o Python que o alvo declara (`.python-version`, senão o `requires-python` do `pyproject.toml`, senão o piso 3.11), `uv` quando o runtime é `uvx`, e o `shared.worktreeSetup` executado verbatim. O arquivo é gerado: `--check` acusa drift, `--write` recusa edição e retirar a chave o apaga no `--write` seguinte.
- O deploy semeia `REVIEW.md` na raiz quando o alvo declara a projeção `github` e tem `docs/standards/index.md`: é o arquivo que o code review do Copilot lê, e ele aponta `/docs/standards/index.md` e `/docs/glossary.md` em vez de copiar os padrões. É seed como o `AGENTS.md` — criado só quando ausente, nunca no manifesto, nunca checado por drift —, e um `REVIEW.md` do alvo é preservado.
- `cq specs delegate <id>` é o caminho de entrega: recusa uma spec não `approved`, sem `branch:`, sem a projeção `github`, sem `provider: github` ou cuja branch não está no `origin`; emite o briefing de delegação com o protocolo e o ponteiro para a spec.
- `--send` entrega o briefing com `gh agent-task create -F - --base <branch.work> --custom-agent quenching-spec-runner`; a pull request do agente tem a branch da spec como base, nunca `main`, e o agente lê a spec do store, commita uma task por vez, exige o `verify:` verde antes do tick e não mergeia, não conclui e não arquiva.
- `cq specs delegate` entra no catálogo de verbos CLI-only; nenhum harness novo é criado e `--harness copilot` continua recusado.
- Os padrões `deploy-mode.md`, `plugin-configuration.md`, `agents.md`, `worktree-setup.md` e o novo `spec-delegation.md` descrevem o setup, a semente de review, a chave e o contrato de delegação.

## Out of Scope

- Um harness `copilot` ou `--harness copilot` — decisão do dono do épico (H13 da 452); a projeção é um artefato do alvo, nunca um modo de deploy.
- Um agente de nuvem que não o GitHub: `gh agent-task` é a invocação desta rota; Azure Boards, outro provedor ou outro cliente de nuvem são outra spec.
- Editar `quenching/agents/spec-runner.md` para um modo nuvem: o briefing é a camada de adaptação e o corpo do agente continua o do runner local.
- Medir ao vivo se o Copilot Cloud Agent honra a base `plan/<id>-<handle>` e se o code review carrega `REVIEW.md`: a metade estática é provada aqui; a live fica no `## Handoff` e vira spec de continuação se o formato estiver errado.
- `.github/skills/` e `.github/prompts/*.prompt.md`: a skill continua no diretório único que a 455 decidir; uma segunda cópia em `.github/` é a superfície que o épico recusa.
- Reexecutar a bancada da 452 ou reescrever o artefato `copilot-bench.md`: a sonda muda só o path do formato do setup; a matriz histórica fica datada.
- Release e changelog — o `conclude` os carrega.

## Design

**Quatro artefatos, uma chave e um verbo.** A projeção `github` passa a escrever quatro coisas, todas opt-in pela mesma chave de repositório e todas derivadas do que o alvo declara:

| Artefato | Natureza | Fonte | Gate |
| --- | --- | --- | --- |
| `.github/workflows/copilot-setup-steps.yml` | gerado, no manifesto | o Python do alvo, o runtime do deploy e `shared.worktreeSetup` | `github` em `shared.projections` |
| `REVIEW.md` | seed, fora do manifesto | a existência de `docs/standards/index.md` | `github` em `shared.projections` |
| `.github/agents/quenching-<nome>.agent.md` | gerado, no manifesto | `quenching/agents/*.md` (456) | `github` em `shared.projections` |
| `.github/instructions/<nome>.instructions.md` | gerado, no manifesto | `.agents/rules/<nome>.md` (463) | `github` em `shared.projections` |

**O setup é uma projeção de declarações, não um modo de harness.** O workflow não conhece o Copilot: ele instala o Python que o alvo já declara, instala `uv` quando o deploy escolheu o runtime `uvx` (porque o launcher `uvx` o exige) e executa o `shared.worktreeSetup` verbatim — o mesmo hook que o corte de worktree já roda. O path `.github/workflows/copilot-setup-steps.yml` e o job `copilot-setup-steps` são fato datado do cliente (GitHub Docs, 2026-11-25): o job único é o que o cliente descobre, e só `steps`, `permissions`, `runs-on`, `services`, `snapshot` e `timeout-minutes` são personalizáveis. O arquivo gerado usa `permissions: contents: read` e não carrega segredo.

**Gerado é do manifesto; seed é do alvo.** O workflow é uma projeção: entra no `files` do manifesto, o `--check` acusa drift, o `--write` recusa edição (`ct-deploy-edited`) e retirar a chave o apaga. O `REVIEW.md` é uma instrução de raiz que o alvo edita, como o `AGENTS.md`: o deploy o cria só quando ausente, nunca o lista no manifesto, nunca o checa por drift e nunca o remove. A diferença é deliberada — o workflow é mecânico e não deve ser editado; a política de review é do repositório e o deploy entrega o ponteiro uma vez.

**O code review lê o `REVIEW.md`, e o `AGENTS.md` continua a instrução compartilhada.** O code review do Copilot lê `.github/copilot-instructions.md`, `.github/instructions/**/*.instructions.md`, `AGENTS.md`/`CLAUDE.md`/`GEMINI.md` e `REVIEW.md` (GitHub Docs, 2026-11-25). A 463 já entrega as regras por caminho em `.github/instructions/`; o `AGENTS.md` é o contrato compartilhado de todos os agentes; o `REVIEW.md` é a superfície específica do revisor e aponta os padrões em vez de copiá-los. Nenhum `.github/copilot-instructions.md` é gerado: seria um segundo registro do `AGENTS.md` e não acrescentaria um leitor.

**A delegação é um comando determinístico, não um agente.** `cq specs delegate` não chama modelo: lê a spec, valida os fatos e emite o briefing. O cliente entra por uma função única (`gh agent-task create`), fácil de adaptar quando a prévia mudar. As recusas são antes de qualquer escrita remota: `approved` ausente, `branch:` ausente, projeção ausente, `provider` que não é GitHub, branch fora do `origin` e agente customizado ausente. A branch é a do registro: o verbo não inventa nome nem deriva handle do título.

**A branch da spec é a base da PR, nunca a head.** O agente de nuvem trabalha numa branch própria e abre uma PR por task; `--base <branch.work>` faz essa PR mirar a branch da spec, que continua sendo a branch de integração e o valor de `branch.work`. O `branch:` não muda, a PR do agente não vira o `pr:` da spec (esse continua sendo o da branch para a base, escrito por `pr-create`/`conclude`) e o agente não tem permissão de merge, de conclusão ou de arquivamento. O briefing repete o contrato: uma task, um commit, `verify:` verde antes do tick, `cq specs task --check --subject` depois do commit, e o relatório fixo no fim.

**O setup roda a partir da branch padrão.** O cliente só executa o `copilot-setup-steps.yml` que está na branch padrão (GitHub Docs, 2026-11-25): o repositório que declara a projeção precisa mergear o arquivo antes de delegar; a branch da spec herda o setup do base. O `## Handoff` registra a ordem — mergear o setup, depois delegar.

**O piso do contrato do cliente muda de fato, não de forma.** O teste que hoje afirma `.github/copilot-setup-steps.yml` ausente passa a afirmar o workflow no path real e o job único; a sonda da 452 mede `.github/workflows/copilot-setup-steps.yml` em vez do path antigo. Nenhum teste novo nasce verde sobre um comportamento inexistente: cada um é copiado para um worktree de `origin/main` e falha lá antes de passar aqui.

- O piso 3.11 é o piso que o CI deste plugin já prova; o alvo que declara outro Python o declara em `.python-version` ou no `requires-python`. (`## Design`)

## Alternatives Considered

- **Gerar `.github/copilot-instructions.md` em vez de `REVIEW.md`.** Seria o arquivo repo-wide clássico, mas o `AGENTS.md` já é lido pelo code review e é a instrução compartilhada; gerar o `copilot-instructions.md` criaria um segundo registro da mesma coisa, contra a regra que a 456 deixou escrita. O `REVIEW.md` é a superfície específica do revisor e não duplica o `AGENTS.md`. Perde.
- **Um harness `copilot` ou um `--copilot` no deploy.** Decisão do dono e prova da 452 (H13): o deploy teria duas superfícies e o alvo ficaria amarrado ao cliente. Perde.
- **Um `scripts/delegate.py` em vez de um verbo do specs.** A delegação depende do store, do `branch:` e do `approved:`; um script fora do front repetiria a resolução de backend e de root. O verbo é o lugar do contrato. Perde.
- **Entregar a spec inteira no corpo da task.** O agente pode ler o store com `cq specs show --full`; copiar o documento custaria tokens e criaria uma segunda verdade que drifta do store. O briefing aponta e não copia. Perde.
- **Semear o `REVIEW.md` no manifesto e checá-lo por drift.** O alvo precisa editar a política de review; um arquivo gerado transformaria toda edição em `ct-deploy-edited`. A semente segue o precedente do `AGENTS.md`. Perde.
- **Atribuir a issue ao Copilot em vez de `gh agent-task`.** A atribuição é interativa e não escolhe a base da PR; o `gh agent-task --base` é a invocação documentada e testável. Perde.

## Open Decisions

- **Se o cliente parar de ler o `REVIEW.md`** — a metade live do `## Handoff` decide depois do merge; se o arquivo não for lido, a spec de continuação troca a superfície para `.github/copilot-instructions.md` mantendo o mecanismo (a semente e o ponteiro).
- **Se o `gh agent-task` mudar as flags da prévia** — a invocação vive numa função só; a mudança é uma linha em `delegate.py` e no teste, sem tocar no briefing nem na branch.
- **Se o agente de nuvem ignorar a base `plan/<id>-<handle>`** — a metade live mede; se ignorar, a rota cai para `--base main` e a spec de continuação decide onde o `branch:` é carimbado. O registro não é reescrito por esta spec.

## Risks

- **A head da PR ser a branch do cliente, não `plan/<id>-<handle>`** — a branch da spec é a base da PR e o valor de `branch.work`; o nome da head nunca vira registro. ACCEPTED — é o contrato do cliente, e o `--base` é o que a rota controla.
- **O `worktreeSetup` rodar no runner de nuvem com a confiança do repositório** — o workflow tem `contents: read`, não carrega segredo, e o comando é a declaração rastreada do próprio alvo, a mesma que o corte local já executa. ACCEPTED.
- **O setup só disparar da branch padrão** — o repositório precisa mergear o workflow antes de delegar; o `## Handoff` e o padrão registram a ordem, e o verbo recusa a delegação quando o agente customizado não está no checkout.
- **Um `REVIEW.md` do alvo ser preservado e a semente não nascer** — a política de review do alvo governa; o deploy não sobrescreve uma instrução de raiz que não é dele. Documentado no padrão.
- **A prévia do `gh agent-task` mudar** — a invocação é uma função e o teste a fixa; uma mudança é uma linha.
- **Os paths novos não estarem no manifesto da base** — a task da superfície deste repositório declara o workflow, o `REVIEW.md` e o manifesto; o verifier cobra os três.
- **A metade live do code review e da base da PR** — `unmeasured-live` no `## Handoff`; o formato é provado estaticamente e a spec de continuação corrige o formato, não o mecanismo.

A spec delegável ao agente de nuvem do Copilot: o deploy entrega o ambiente e o review, e `cq specs delegate` leva a spec à branch de trabalho.
