## Problem

At base c1519678, `plugins/quenching/assets/bin/quenching/delivery/inventory.py:256-257` scans every job line for a false condition, including step-level `if: false`. A disabled step therefore sets the entire Job.active to false. `delivery/checks.py:89-95` then skips checkout and runtime setup diagnostics for commands in other, active steps.

The same parser at `inventory.py:201-223` stores GitHub Actions `run: |` as commands `('|',)` and Azure Pipelines `bash: |` as `()`, dropping their indented bodies. Runtime and release classification cannot see those commands. Read-only scouts reproduced both cases by calling `_job` and `_workflow_findings` on in-memory lines; the fixture commands were never executed.

## Proposal

Correct the existing delivery parser's condition scope and multiline command extraction, preserving current supported providers and interfaces. Cover active jobs with disabled steps and literal/folded command blocks in the existing `plugins/quenching/tests/test_delivery.py`. Synchronize generated Codex mirrors through the existing generation process. No new execution capability or grants.

## Out of Scope

A complete YAML parser, new providers, workflow execution, step-level activity modeling, and changes to permissions or executable surfaces are excluded. Preserve the existing static inventory interface.

## Impact

- `plugins/quenching/tests/test_delivery.py` — parser-only regression fixtures.

The binding contract is `docs/standards/architecture/delivery-front.md` §Pipeline shape contract and §Boundary with delivery implementation. No standard changes are declared. The generator manifest has no delivery Python mirror; verify lockstep without inventing generated copies.

## Validation

Use parser-only regression fixtures: disabled step conditions must not disable their parent job; actual disabled job conditions must remain disabled. Multiline GitHub `run` and Azure `bash`/`script`/`pwsh` commands must preserve runtime/release evidence and produce missing checkout/setup diagnostics where applicable. Run the existing delivery tests, mirror verification, and root `bash scripts/verify_repo.sh`. Do not execute fixture commands.

## Design

Only a condition at the direct job-property indentation can disable the job. Conditions nested under steps must not change its activity. Top-level Azure steps are a synthetic job and have no job condition.

Literal and folded command scalar bodies are inventoried as command evidence lines, bounded by their owning key indentation. Support block modifiers while preserving inline commands and GitLab script lists. This is static evidence extraction, not YAML interpretation or shell execution.

## Alternatives Considered

- Introduce a YAML dependency: disproportionate scope for two bounded extraction errors and changes deployment requirements.
- Patch diagnostics to ignore inactive flags or markers: loses legitimate inactive-job handling and leaves inventory evidence wrong.

## Open Decisions

- Owner appetite for timing and a broader abandonment threshold remain owner decisions; this pass relies on the already authorized, reproduced correctness defects, and makes no wider product decision.
- Folded scalars provide static evidence per source command line rather than attempting shell/YAML evaluation; fixtures will establish that required runtime and publish evidence survives.

## Risks

A broad indentation rule could consume following steps or unrelated YAML values; bound each block by its owning indentation and cover adjacent steps. Preserve existing single-line and GitLab command behavior.
