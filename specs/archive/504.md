## Problem

Na spec 455 (2026-11-25), o develop autônomo rodou sem o servidor MCP e carimbou o `approved` pelo fallback de CLI — `cq specs record 455 approved --set by=orchestrator-forced` —; o registro ficou `approved: {by: orchestrator-forced}`, sem `date`. O tool `specs_record` grava a data sempre (`_w_record` injeta `--set date=<hoje>`), então a mesma decisão produz dois registros diferentes conforme a rota: MCP com data, CLI sem. Como `approved` é `writeOnce: true`, a omissão não tem conserto depois — um leitor que exija a data lê o spec como incompleto para sempre. A melhoria tem de fazer a rota de CLI nunca gravar um `approved` incompleto, recusando ou carimbando a data, para que as duas rotas convirjam.

Minimal fix proposed: em `cq specs record`, exigir `date` no registro `approved` (exit 2 com um código próprio) ou carimbar `today()` quando ausente, como `_w_record` já faz; um teste cobre `approved` por CLI com e sem `--set date`.

**Insumos**

- `quenching/assets/bin/quenching/specs/mcp.py:328-334` — `_w_record` sempre passa `--set date={date.today().isoformat()}`; a rota de CLI não tem esse default
- `quenching/assets/bin/quenching/specs/schema.py:66-68` — `approved` declara `fields: [date, by]` e `writeOnce: true`, sem campo required na rota de CLI
- `cq specs status 455 --json` em 2026-11-25: `"approved": {"by": "orchestrator-forced"}`, sem `date`; `cq specs show 455 --full` idem
- spec 455, `## Discoveries`: "o fallback de CLI do specs_record não grava o date do approved (o tool do MCP grava); ... o record é write-once"

## Proposal

- `cq specs record <id> approved` por CLI grava sempre um `approved` com `date`: sem `--set date=…` o comando carimba a data de hoje, como o tool `specs_record` já faz; um `date` informado é preservado.
- As duas rotas (MCP e CLI) produzem o mesmo registro `approved` para a mesma decisão.
- Um teste cobre `approved` por CLI com e sem `--set date`.

## Out of Scope

- Recusar (exit 2) o `approved` sem `date` — descartado: o fallback de CLI é a rota de quem roda sem MCP e a recusa a deixaria sem como aprovar; carimbar converge sem custo.
- Reparar o `approved` de specs já gravados sem data (ex.: 455) — o registro é write-once e a correção é do humano, fora desta spec.
- Mudar o `_w_record` do MCP ou o schema: a rota de MCP já grava a data.

## Impact

### Product code this spec expects to touch

- `quenching/assets/bin/quenching/specs/commands/fields.py` — `cmd_record` carimba `date` quando `approved` chega sem ele
- `quenching/tests/test_specs_record_approved_date.py` — teste novo: CLI com e sem `--set date`

## Validation

- `python3 -m unittest discover -s quenching/tests -p test_specs_record_approved_date.py` sai 0: `approved` sem `--set date` fica com `date` igual a hoje; com `--set date=2026-01-02` mantém essa data.
- O mesmo comando falha na base (sem o fix) no caso sem data.

## Design

- `cmd_record` já monta `merged` a partir de `args.set`; para `name == "approved"` sem `date` em `merged`, define `merged["date"] = today` antes da ordenação pelos campos do schema. Regra durável: um registro `approved` nunca é gravado sem `date`, qualquer que seja a rota.
- Carimbar (e não recusar) escolhido porque o `_w_record` já carimba: a convergência vem da mesma regra nas duas rotas, sem código de recusa novo (guidance de tokens: nenhuma camada nova).
- Sem alteração de schema.

### Assumptions

- A data de hoje usa `datetime.date.today()`, o mesmo relógio do MCP (`## Validation` depende disto).
