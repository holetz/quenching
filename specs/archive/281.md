## Problem

Visto pelo condutor em 2026-11-23 no verifier da 274 (PR #279). Com `shared.ci.enforce` em `off` ou `when-present`, o merge exige `--gate-exit 0` no lugar do CI. Só que esse valor é declarado por quem chama: o `cq` não roda o gate nem confere nenhuma evidência de que ele rodou. Um agente pode passar 0 sem ter rodado nada. O padrão `required` não é afetado.

Direções a pesar no develop, sem camada cara: o merge aceita só um registro de gate gravado pelo próprio `verify_repo.sh`, por exemplo um arquivo em `.quenching/` com o sha do HEAD, o exit e a data, e confere que o sha bate com a cabeça do PR. Ou o próprio merge roda o gate afetado quando o CI está relaxado.

**Insumos**
- `quenching/assets/bin/quenching/config/ci.py` (`judge`) e o `cq git pr merge`
- spec 274 (Outcome) e `scripts/verify_repo.sh`

## Proposal

- With `shared.ci.enforce` other than `required`, `cq git pr merge` accepts a PR without green CI only when `.quenching/gate/record.json` is a record of the PR's head sha, with exit 0, that ran on a clean tree.
- `scripts/verify_repo.sh` writes that record itself when it ends (pass or fail) and removes the old one when it starts, so a gate that did not finish leaves no record.
- `--gate-exit` stops counting: it stays accepted for old callers, is ignored, and a refusal names the record as the proof.
- The merge never runs the gate again.

## Out of Scope

- Making the merge run the gate itself (the other direction in the Problem): the human chose the record; a second run costs minutes the CI relaxation exists to save.
- Signing or hashing the record against a hand-written file: ACCEPTED, see Risks.
- `shared.ci.enforce: required`: unchanged, it never reads the record.

## Validation

- `python3 -m unittest discover -s quenching/tests -p test_ci_enforce.py` ? a relaxed merge without a record, with a record of another sha, a failing record or a dirty one refuses `gate-proof-required`; with a matching clean exit-0 record it merges, on GitHub and on Azure; `--gate-exit 0` alone never merges.
- `python3 -m unittest discover -s quenching/tests -p test_gate_record.py` ? the writer's record is read back by the merge's reader; a failing exit, a dirty tree and a moved head all fail the read.
- `bash scripts/verify_repo.sh` leaves `.quenching/gate/record.json` with the HEAD sha and its own exit.

## Design

- **Record, not flag.** The caller's claim is replaced by a file only the gate script writes: `{"schema": 1, "head": <HEAD sha>, "exit": <int>, "scope": "full|affected", "dirty": <bool>, "date": <UTC ISO>}` at `.quenching/gate/record.json` in the worktree root (`.quenching/` is already gitignored). The merge reads it from the repo root of its cwd, the checkout where the gate ran.
- **Writer in Python, called from the script's EXIT trap.** `python3 -m scripts.toolchain.gate_record write --exit $rc` ? the exit comes from the trap, so a `set -e` abort records its real code; the start of the gate calls `clear`. Python keeps the JSON and the atomic write (temp + replace) testable without bash.
- **Reader in `quenching/config/ci.py`** (`proven_exit(root, head)`): returns the record's exit only when schema, head equality, `dirty: false` and an integer exit all hold, else `None`. `judge` is unchanged: the caller passes `proven_exit(...)` where it passed `args.gate_exit`.
- **Head compared is the PR's head** (`headRefOid` on GitHub, `lastMergeSourceCommit` on Azure), already read before the judgement.
- **`scope: affected` counts.** AGENTS.md makes the affected gate the close of a spec; the record states the scope in the payload (`ciRelaxed.gate`) so the report shows what was proven.
- **Dirty means any `git status --porcelain` output** at the end of the gate (ignored paths do not show).

## Alternatives Considered

- The merge runs the affected gate when CI is relaxed: rejected by the human, slow and duplicates the close's gate run.

## Open Decisions

- none ? the human decided the record in `## Discoveries`; scope and dirty handling are settled in `## Design`.

## Risks

- A caller can hand-write the record file. ACCEPTED ? it is the same trust as the gate's own exit, one step harder than a flag, and the record carries head and date for the verifier to audit.
- The record's head is a branch tip that moves after a rebase or a sync: the merge refuses with `gate-proof-required` and the gate must run again. Intended.
- A gate run in another checkout leaves its record there, and the merge reads the one of its own cwd. Intended: the proof lives with the tree it ran on.
