## Problem

The router `assets/bin/cq` finds the other enabled `quenching-*` modules through `PATH`: it reads
every `<pluginRoot>/bin` entry the host appended (`enabled_module_paths`, plugins/quenching/assets/bin/cq:83-104),
on the premise, written in its docstring and in docs/standards/architecture/plugin-layout.md §One `cq`,
owned by `quenching-specs`, that Claude Code appends that entry for every enabled plugin "whether or
not the directory exists". Claude Code 2.1.312 appends it only when the directory exists, and only
`quenching-specs` ships a `bin/` (it is the `cqPathOwner`). Measured with `claude -p --plugin-dir
plugins/claude/quenching-specs --plugin-dir plugins/claude/quenching-align`: `PATH` carries only
`quenching-specs/bin`. So with the marketplace plugins, a bare `cq knowledge …` or `cq components …`
refuses with "belongs to module quenching-align, which is not enabled", and `cq modules --json`
reports every module but `quenching-specs` as disabled.

The opt-in surface-load gate shows it: functional check 2 ("a conductor invokes its stage by
registry name") fails on `main` and on the 6.11.0 tag alike — the conductor runs `cq modules`, sees
`quenching-align` disabled and stops before invoking `quenching-align:knowledge:align`. The release
gate (`QUENCHING_FUNCTIONAL=1 QUENCHING_DISTRIBUTION=1 bash scripts/verify_repo.sh`) therefore cannot
pass, which blocks the next release. The deploy mode (`cq deploy`) is not affected: it vendors every
selected module under one `.agents/quenching/` root.

## Proposal

Every published module that is not the `cqPathOwner` ships a `bin/` directory holding one
non-executable marker file and no `cq`, so the host puts `<pluginRoot>/bin` on `PATH` and the router
discovers the module, while `quenching-specs` stays the only module whose `bin/` carries the `cq`
shim (two shims would still shadow each other). The generator writes the marker, its check reports a
missing or extra one as drift, and the router docstring and plugin-layout.md stop claiming the host
appends absent directories.

## Out of Scope

- `quenching-hud` gets no marker: it is hand-authored (neither `owned` nor `generated` in the manifest) and ships no `assets/bin/quenching`, so the router has nothing to discover in it.
- `quenching-specs-reader` gets no marker: it already ships `bin/cq-specs-read`, so the host already puts its `bin/` on `PATH`, and it carries no router packages.
- The deploy mode (`cq deploy`) is not changed by design: it vendors every selected module under one `.agents/quenching/` root and never resolves modules through `PATH`. It changes only if a test or the gate shows otherwise (see `## Open Decisions`).
- Making the router discover modules by any channel other than `PATH` (see `## Alternatives Considered`).

## Design

- **The marker is `bin/README`, mode 0644, synthesized by the generator.** `principal_tree` adds it for every principal (`owned`) module whose `cqPathOwner` is false, the same way it synthesizes `VERSION` and `.generated-from.json`, so the source plugin `plugins/quenching` carries no extra file. Its text states why the directory exists and that `cq` lives only in `quenching-specs`. A visible, extension-less, non-executable name: not a dotfile a packager may drop, not a `.md` the doc linters and `closure_findings` would scan, and not resolvable as a command on `PATH` (no execute bit, no `PATHEXT` extension on Windows).
- **The check names the rule, not only the bytes.** `differences` already reports a missing generated file as drift; `published_findings` adds explicit findings beside the existing `PATH cq ownership drift`: a principal non-owner without `bin/README`, and the owner carrying one. A `cq` in a non-owner `bin/` stays reported by the existing ownership finding.
- **One `cq` stays the invariant.** `quenching-specs` remains the only `bin/cq`/`bin/cq.cmd`; the marker makes the directory exist, never a second shim.
- **Binding contracts:** docs/standards/architecture/plugin-layout.md §`bin/` is the second tree… and §One `cq`, owned by `quenching-specs` are corrected to the measured host behaviour (Claude Code 2.1.312 appends `<pluginRoot>/bin` only when the directory exists); the router docstring of `enabled_module_paths` says the same.

## Alternatives Considered

- **A `cq` shim in every module's `bin/`.** Lost: two shims on `PATH` shadow each other, and the first one found (in host order) decides which router runs, which is exactly what `cqPathOwner` exists to prevent.
- **An empty `bin/` directory.** Lost: git does not track empty directories, so the marketplace clone would not carry it.
- **Discovering sibling modules through the host's plugin cache or settings instead of `PATH`.** Lost: it couples the router to host-private file layouts that change between releases, and `PATH` is the one channel the host documents for plugin `bin/`.

## Open Decisions

- Whether `cq deploy` (the vendored deploy mode) or the release verb's artifact list must know about `bin/README` — decided during task 1.1 by the plugin-module tests and `bash scripts/verify_repo.sh`: they change only if one of them fails because of the marker.

## Risks

- **A host release stops appending a `bin/` that holds no executable.** Mitigation: functional check 2 and the `PATH` probe of task 2.1 are the live proof, and the opt-in release gate re-runs check 2 every release.
- **The marker gains an execute bit** (umask, a copy tool) and becomes a command named `README` on `PATH`. Mitigation: the generator writes mode 0644 and `differences` reports a mode mismatch as drift.
- **A packaging step drops the file** (an export filter, an artifact list). Mitigation: the name is visible, not a dotfile; the gate's distribution checks run over the generated tree. ACCEPTED for external packagers outside this repo.
