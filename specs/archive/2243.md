## Problem

Evidência reproduzida (rodada 6, origin/main 7bb9bc8ef): `quenching/assets/bin/quenching/git/refresh.py:55` faz fetch de `+refs/heads/<base>`; quando o remoto não tem essa branch, falha antes da linha 65, onde fica o ramo `no-remote-base`. Num repositório novo sem push, `cq git refresh --base main --json` devolve `"action": "refused", "reason": "fetch-failed"` com `fatal: couldn't find remote ref refs/heads/main`, exit 1.

Consequência: um repositório cuja base ainda não foi enviada recebe exit de achado onde o código pretendia um skip bem-sucedido; um condutor que leia exit 1 como recusa para o fechamento do ciclo. O ramo `no-remote-base` é código morto.

## Proposal

- `cq git refresh` num repositório cujo remoto não tem `refs/heads/<base>` devolve `"action": "skipped", "reason": "no-remote-base"` com exit 0, sem tocar ref nenhuma.
- Qualquer outra falha de fetch (remoto inalcançável, URL inexistente, autenticação) continua `"action": "refused", "reason": "fetch-failed"` com exit 1.
- Um teste em `quenching/tests/test_git_refresh.py` prova o ramo `no-remote-base` contra um remoto bare vazio, e o teste de fetch falho existente continua verde.

## Out of Scope

- Mudar a semântica dos demais resultados (`current`, `ahead`, `diverged`, `merge-refused`, `update-refused`, `no-local-base`) — estão corretos e cobertos.
- Remover uma `refs/remotes/<remote>/<base>` velha quando a branch sumiu do remoto — limpar tracking refs é de `cq git prune`/`cleanup`, não do refresh.
- Os corpos `conclude.md` e `merge.md` — já tratam qualquer resultado não forçado como relato; um skip com exit 0 não pede texto novo.

## Design

- **Diagnóstico só no caminho de falha.** O fetch continua sendo a primeira chamada; quando ele falha, `git ls-remote --exit-code --heads <remote> refs/heads/<base>` decide: exit 2 (nenhuma ref casou, remoto respondeu) é `no-remote-base` → skip, exit 0; qualquer outro código mantém `fetch-failed` com a mensagem do fetch original. O caminho feliz não paga uma ida extra à rede.
- **Imitar `prune.py`.** `quenching/assets/bin/quenching/git/prune.py:126` já usa exatamente esse sinal (`ls-remote --exit-code --heads`, exit 2 = sumiu) para tratar uma branch remota ausente; o refresh adota a mesma regra em vez de casar texto de `stderr`, que depende de locale.
- **O ramo de skip existente permanece** para `no-local-base` (remoto tem a base, o clone local não); o rótulo `no-remote-base` passa a ser emitido pelo novo diagnóstico.
- Contrato preservado: exit 0 ok · 1 achado · 2 recusa (`docs` do próprio módulo); hooks desligados por `SAFE` também na chamada `ls-remote`.

## Alternatives Considered

- **Casar `couldn't find remote ref` no stderr do fetch** (como `specs/backends/git.py:283`) — rejeitado: depende do idioma do git; o exit code do `ls-remote --exit-code` é contrato estável.
- **`ls-remote` antes do fetch, sempre** — rejeitado: duas idas à rede em todo fechamento de ciclo para cobrir um caso raro.
