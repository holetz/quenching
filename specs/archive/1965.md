## Problem

O `guion` é um repositório público do dono: um dashboard de RPA em Flask com tema AdminLTE. Ele foi publicado já alinhado pela frente opensource, mas três itens de vitrine ficaram de fora e só foram notados numa revisão manual em 2026-10-18:

1. **Sem imagem da interface.** O README não tem nenhum print ou GIF. Para um produto com UI, é o que mais convence quem avalia o repo.
2. **Estatística de linguagem errada.** O GitHub classificava o projeto como JavaScript (~11,6 MB) por causa do tema e dos plugins vendorizados em `apps/static/assets/`, quando o código próprio é Python. Isso foi corrigido à mão com `.gitattributes` (`linguist-vendored` nos assets e `linguist-detectable=false` nos templates HTML), em holetz/guion#1.
3. **Sem topics no forge.**

O alinhamento do projeto já pergunta pela identidade visual: o `design:align` converge `/.design/`, o brand pack e os assets. Mas nenhuma frente fecha esses itens no README público. O README como documentação é da frente `knowledge`, porque o catálogo de controles dá a ela os controles DO, e `knowledge:documentation:plan` já lê o README como fonte. Descrição e topics são fatos do forge, e a 1962 os propõe como advisories do readiness.
## Proposal

- **Imagem da interface (design + knowledge)**: quando o projeto tem UI, o `design:align` pede ao dono um print ou GIF demonstrativo feito com **dados sintéticos** e o guarda como asset da marca. O `knowledge` (documentation plan/write) passa a exigir que o README público o referencie. Sem o asset, o achado é um advisory com a ação do dono, nunca uma imagem inventada.
- **Estatística de linguagem honesta**: um achado (dono a definir no `develop`: toolchain ou knowledge) quando diretórios vendorizados ou templates dominam a estatística de linguagem do forge. A correção proposta é um `.gitattributes` com `linguist-vendored` e `linguist-detectable`, aplicado com autorização.
- **Descrição e topics**: ficam com os advisories de vitrine da 1962 (opensource readiness, via provider), para que o mesmo controle não tenha dois donos. Esta spec só garante que o align do projeto chame aquele relatório.
- **Aceitação**: um alvo sintético no formato do `guion` (Flask + tema vendorizado + README sem imagem) produz os três achados. Depois da correção, nenhum achado sobra.

## Out of Scope

- **Descrição e topics do forge.** São advisories de vitrine da 1962 (`cq opensource readiness`, via provider). Esta spec não lê o forge e não cria um segundo dono para o mesmo controle.
- **Produzir a imagem.** Nenhuma frente gera, captura ou inventa um print ou GIF. O achado nomeia a ação do dono (print com dados sintéticos) e para aí.
- **Escrever o `.gitattributes`.** O achado traz as linhas exatas a propor. Quem aplica é o dono, por fora do `cq opensource apply`, que só escreve templates pinados.
- **Reproduzir o Linguist.** A medição é uma heurística por extensão sobre os arquivos versionados. Não é a tabela de linguagens do GitHub e não promete o mesmo percentual.
- **Passo novo em corpo de comando.** `design:align` e `knowledge:documentation:*` não ganham pergunta nova. O achado sai no payload que o align do projeto já lê (`cq opensource doctor`).

## Design

### O que o código faz hoje

- `cq opensource status` (`opensource/aggregate.py`) monta os blocos de controle de cada dono e emite `advisories` (`info`, sem mudar o exit code) para controles opcionais e artefatos que nenhum controle nomeia (`ARTIFACT_CODES`). README e SECURITY já saem como hand-off para os donos (`LANGUAGE_HANDOFFS`). Nada olha imagem no README nem a estatística de linguagem.
- O align do projeto (`quenching-align`) já roda `cq opensource doctor --json` para todo alvo com `LICENSE*`. O doctor embute o `status`. É o único ponto que já vê "projeto público" sem passo novo.
- `design/doctor.py::_orphan_assets` procura referências a `.design/assets/**` só em `.design/` e `docs/standards/design/`. Um print guardado como asset e citado só pelo README seria `design-asset-orphan`. Isso empurraria o dono a tirar a imagem do lugar certo.

### O desenho

```
cq opensource status
  ├─ blocos de controle (inalterado)
  ├─ advisories de controle opcional / artefato (inalterado)
  └─ advisories de vitrine (novo; um `git ls-files` por chamada)
       ├─ os-readme-media-missing  há UI versionada e o README da raiz não tem imagem
       │    → owner: knowledge, command: /quenching-knowledge align,
       │      action: print ou GIF com dados sintéticos em .design/assets/, citado no README
       └─ os-language-skew         a linguagem dominante por bytes cai quando os diretórios
            vendorizados/templates saem da conta
            → language, honest, paths, gitattributes: ["<dir>/** linguist-vendored", …]
```

- **Arquivos versionados.** Um `git -C <root> ls-files -z`. Fora de um repositório git, ou com git ausente, os dois advisories ficam de fora, porque o forge só vê o que está versionado.
- **Atributos honrados.** Um `git check-attr -z --stdin linguist-vendored linguist-generated linguist-documentation linguist-detectable` sobre a lista. Um arquivo com `vendored`/`generated`/`documentation` setado, ou `detectable` unset, sai da conta. É isso que faz o achado sumir depois da correção.
- **Linguagem por extensão.** Uma tabela curta (Python, JavaScript, TypeScript, CSS, SCSS, Less, HTML, Vue, Svelte, Go, Rust, Java, Ruby, PHP, C, C++, C#, Kotlin, Swift, Shell). O que não está nela não conta, como texto e dados não contam no forge. Também saem da conta os padrões que o Linguist já trata como vendorizados por padrão (`node_modules/`, `vendor/`, `bower_components/`, `*.min.js`, `*.min.css`), para não acusar o que o forge já descarta.
- **Skew.** O diretório suspeito de um arquivo é o prefixo até o primeiro segmento em `static`, `assets`, `plugins`, `vendors`, `lib`, `libs`, `third_party`, `external` (vendorizado), ou `templates` (template). Há skew quando a linguagem dominante com esses arquivos difere da dominante sem eles. O advisory lista os prefixos que carregam bytes da linguagem dominante, com `linguist-vendored` para os vendorizados e `linguist-detectable=false` para os templates.
- **UI e mídia.** Há UI quando algum arquivo versionado tem extensão `.html`, `.htm`, `.jinja`, `.jinja2`, `.j2`, `.vue`, `.svelte`, `.jsx` ou `.tsx`. O README da raiz (`README*`) tem mídia quando traz `![…](…)`, `<img`, `<video` ou `<picture` que não seja badge (`shields.io`, `badge`). README ausente é assunto do OSPS-DO-01 e não gera este advisory.
- **Design.** `_orphan_assets` passa a ler também os `README*` da raiz como texto de referência.

### Assumptions

- `cq opensource doctor` é o ponto que o align do projeto já lê para alvos públicos. Depende disto: `## Out of Scope` (sem passo novo em corpo).

## Risks

- **Falso positivo de skew.** Um projeto com JavaScript próprio em `static/` ou `lib/` recebe a sugestão de marcar como vendorizado código que é dele. Mitigação: é `info`, não muda o exit code, e a ação fica com o dono. O texto do advisory diz que é proposta.
- **Falso negativo.** Um tema vendorizado fora dos segmentos conhecidos não é visto. Aceito: a lista é curta de propósito e cresce com caso real.
- **Custo do status.** Dois subprocessos git por chamada. Num repo grande, `ls-files` + `check-attr` são lineares no número de arquivos, sem ler conteúdo além dos tamanhos e do README.
