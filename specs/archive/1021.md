## Problem

O build local do site retorna exit 0 mesmo quando o Zensical não carrega nenhum Markdown e deixa o site sem páginas HTML ou com sitemap.xml contendo o template Jinja cru. Assim, o repositório pode declarar o próprio site saudável sem ter produzido uma saída navegável.
## Proposal

- Criar uma entrada única de build para o site dogfooded, usada pelo README e pelos gates de CI.
- Executar o Zensical com --clean --strict e com o fallback ZENSICAL_POLL_WATCHER=1, pois o watcher recomendado reproduziu a corrida que encerra o build antes de carregar os Markdown.
- Validar imediatamente que o site contém páginas HTML reais, que index.html existe e que sitemap.xml não contém o template Jinja cru; um processo Zensical que sai 0 sem renderizar deve falhar no gate.
- Manter a escolha do watcher explícita, documentada e limitada ao build do repositório; não alterar o runtime externo nem esconder falha atrás de retry ilimitado.

## Out of Scope

- Publicar o site em GitHub Pages ou qualquer host externo; a publicação exige destino e credenciais próprios.
- Corrigir o runtime upstream do Zensical neste repositório.
- Fazer a verificação profunda de links, glossário, capabilities e catálogo; esses contratos pertencem às specs irmãs.

## Impact

### Product code this spec expects to touch

- scripts/build_documentation.py (new) — entrada reprodutível do build e guardas contra saída vazia.
- README.md — receita oficial deve chamar a entrada única.
- pyproject.toml e uv.lock — apenas se a implementação precisar fixar a versão já resolvida.
- plugins/quenching/tests/test_documentation_build.py (new) — testes das decisões observáveis do wrapper.

## Validation

- uv run python scripts/build_documentation.py — exit 0 e gera site/index.html e um sitemap.xml XML válido.
- O mesmo comando em um diretório de saída vazio — não pode terminar 0 com zero páginas.
- python3 plugins/quenching/assets/checks/documentation-site-check.py site --local --remote-policy error — sem findings de estrutura.
- uv run pytest plugins/quenching/tests -q — toda a suíte passa.

## Design

O wrapper usa subprocess.run para chamar o runner uv do projeto, injeta ZENSICAL_POLL_WATCHER=1 somente se o chamador não o definiu e inspeciona a saída após o processo. O polling é necessário neste ambiente porque a implementação oficial ainda deixa o diretório de configuração entrar no scheduler antes da documentação; a variável é um fallback documentado pelo próprio crate de watcher. O wrapper não tenta adivinhar páginas nem materializa HTML alternativo: ausência de páginas é erro.

A guarda mínima verifica site/index.html, a existência de pelo menos uma página HTML além de assets e a possibilidade de parsear o sitemap sem tokens {{, {% ou {#. A análise de links e projeções fica nos verificadores especializados.

## Alternatives Considered

- Rodar zensical build diretamente em cada workflow — rejeitado porque reproduz o falso sucesso e espalha a correção de ambiente.
- Fazer retry ilimitado até aparecer HTML — rejeitado porque mascara uma falha persistente e torna o tempo do gate indeterminado.
- Trocar Zensical por MkDocs — rejeitado porque diverge do site layer que o plugin publica.

## Open Decisions

- none — o escopo desta spec é o build local e seu gate; publicação remota é explicitamente excluída.

## Risks

- O fallback de polling é mais lento — mitigado por uso apenas no build de verificação e por manter a versão no lock.
- Uma futura versão do Zensical tornar a variável obsoleta — mitigado pelo teste de saída real e pela atualização explícita da spec quando a dependência mudar.
- A checagem mínima não provar todos os links — mitigado pelas specs de cobertura e CI.
