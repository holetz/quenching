## Problem

After the eight preceding specs, `ops` and `proof` each have a standard, a `cq` axis, an align, a
status and a minting command — and neither is part of the plugin. `/quenching:align` conducts three
fronts in a fixed dependency order and knows nothing about the two new ones, so the command whose
whole promise is "align the repo" would leave a repository's operations and verification surfaces
untouched while reporting a converged repository.

The surface claims are worse than merely incomplete. `/docs/index.md` says "four surfaces" and lists
four rows. `align-surface.md`'s column is described as widened to 1×5 by the spec that minted `git`.
`command-surface.md` enumerates five namespaces. `README.md` states a command count. Every one of
those is a load-bearing `authority: current` claim that the eight specs invalidate, and
`command-surface.md` itself records why that matters: two current standards disagreeing about what
exists is worse than either being merely out of date.

There is also a question none of the eight answered, because none of them could: **when should a
repository adopt these two fronts?** `/docs/` is what the plugin installs, so front 1 always runs.
`/.design/` runs conditionally. `ops` and `proof` are conditional in a new way — a repository can
genuinely have no operations surface, and a repository with no tests has a `proof` front whose
every rule is vacuous. The conductor needs a probe that tells "absent" from "drifted", and getting
that wrong in either direction is expensive: run them always and every documentation repository pays
for two fronts it does not have; run them never and adoption never happens.

## Proposal

Make the two new fronts first-class: conducted, counted, documented, translated, and adoptable.

**1. The conductor.** `/quenching:align` gains two rows and the dependency order becomes
`/docs/` → `/.design/` → `.claude/` → `ops` → `proof`. The two new fronts go last and in that order
for a stated reason: `ops` and `proof` both write standards into the bundle front 1 established, and
`proof`'s `pf-untested-entrypoint` consumes `ops`'s inventory, so `proof` cannot precede `ops`
without reporting a conditional check as silent.

**2. The applicability probe.** Each new front is conducted only when it applies, decided by one
cheap signal before anything is read:

| Front | Runs when | Skipped with a stated reason when |
| --- | --- | --- |
| `ops` | `opsRoot` is declared, **or** an undeclared conventional root (`scripts/`, `tools/`, `bin/`, `script/`) holds an executable entry point | neither — reported as *not applicable*, with the one-line invitation to declare it |
| `proof` | `proofRoot` is declared, **or** a conventional root (`tests/`, `test/`) holds a test module | neither — same |

The distinction the conductor must preserve is **absent** versus **drifted**. An absent front is not
a finding; an undeclared-but-present one is an invitation, printed once, never a plan item.

**3. The surface claims.** Every count and enumeration the eight specs invalidated is corrected in
one pass, with `citation-check.sh` as the proof: `/docs/index.md`'s surface table and its "four
surfaces" prose, `align-surface.md`'s column and pillar count, `command-surface.md`'s namespace list,
`docs/explanation/operating-model.md`, `docs/project/index.md` and `layout.md`, the README's catalog
and its command count, and `docs/tutorials/getting-started.md` if its path now omits two fronts.

**4. The adoption path.** `docs/how-to/adopt-quenching.md` gains the two fronts, and a new how-to
covers the sequence that actually converges a legacy repository — declare the roots, run `ops`
first, close its judgement band, then `proof`, then the floor — because the order matters and
nothing else says so.

**5. The proof of the whole.** `assets/checks/functional-checks.sh` gains a surface-load check for
both fronts, and `assets/translation/codex-adaptation.json` carries all seven new bodies so the
translated surface does not lag by two whole fronts.

## Out of Scope

- **Any change to either front's behaviour.** Bodies, checks and payloads are settled by the eight
  preceding specs. A defect found here is recorded and fixed in its own spec.
- **The version bump and the tag.** `/quenching:specs:conclude` and the release own them; a task
  scheduling a bump would collide with whatever else merges first.
- **Converging `databricks-risco-gold`.** The adoption how-to is written *from* that repository's
  measured shape, and running the fronts against it is that repository's own work.
- **Making either front unconditional.** Applicability is the point of task 2.
- **A sixth conductor stage or a new conductor.** `/quenching:align` gains rows; it does not change
  shape.

## Design

**Why `ops` and `proof` go last, and in that order.** Both write standards into the `/docs/` bundle,
so front 1 must precede them — the same reason `/.design/` does. Between the two, `proof`'s
`pf-untested-entrypoint` consumes `cq ops inventory`; running `proof` first would make that check
report itself silent on a repository where `ops` is configured, which is a true statement about a
wrong ordering. The dependency is real, so it is stated as one rather than left as a habit.

**Why applicability is a probe and not configuration.** Requiring a repository to declare "I have no
operations surface" is ceremony for the common case. Requiring it to declare a root before the front
will look at all is the opposite failure — the repositories that most need `ops` are precisely the
ones that never declared anything. The probe splits the difference: a conventional root with content
is enough to earn an invitation, and the invitation is printed, not planned. That distinction is the
one thing this spec must not get wrong, because a conductor that turns "you might want this" into a
plan item is a conductor people stop running.

**Why the invitation is printed once and never becomes a finding.** `align-surface.md` already binds
this shape for stages a probe cannot price. An undeclared `scripts/` folder is not drift — the
repository never adopted the front — and reporting it as a finding would make every repository on
earth non-conformant with a contract it never agreed to.

**Why the count claims are corrected in one pass rather than eight.** Each of the preceding specs
touches the two standards it must, and none of them can see the final numbers, because the final
numbers depend on all eight landing. Correcting counts incrementally means eight passes each writing
a number that the next invalidates. One pass at the end, with `citation-check.sh` as the proof, is
the only version that ends correct.

**Why the legacy how-to is new rather than a section in the existing one.**
`adopt-quenching.md` answers "how do I start using this in a repository", and its reader has a
repository that is mostly fine. The order that converges a legacy operations and verification surface
— declare the roots, run `ops`, close its judgement band before the registry means anything, then
`proof`, and only then the floor — has a different reader with a different problem, and folding it in
would make the adoption guide longer for everyone to serve one case.

**Why the functional check matters more here than usual.** Two fronts is seven new bodies, and a body
that fails to load is invisible to `components lint`, which reads files rather than loading them.
`functional-checks.sh` is the only thing that witnesses the surface as Claude Code sees it, and its
exit-2 inconclusive result is treated as inconclusive rather than green — the repository's own
operating contract already says so.

## Alternatives Considered

- **Conduct the two new fronts unconditionally.** Rejected: every documentation repository would pay
  for two fronts it has no tree for, and the no-op case the probe rule protects would stop being
  free.
- **Require both roots to be declared before either front is conducted.** Rejected under §Why
  applicability is a probe: it excludes exactly the repositories the fronts were written for.
- **Put `ops` and `proof` before `.claude/`.** Rejected: the components front's registry is a
  `/docs/` listing and both new fronts write standards, so placing them earlier creates a second
  cross-front edge for no gain.
- **Correct each count claim in the spec that invalidated it.** Rejected under §Why the count claims
  are corrected in one pass — it guarantees eight successive wrong numbers.
- **Add the legacy sequence as a section of `adopt-quenching.md`.** Rejected under §Why the legacy
  how-to is new.
- **Skip the Codex projection until both fronts have been used in anger.** Rejected: a translated
  surface that lags by two whole fronts is the translation drift the repository already has a
  standard about.

## Open Decisions

- **Whether the conventional-root list is fixed or configurable.** `scripts/`, `tools/`, `bin/`,
  `script/`, `tests/`, `test/` covers the common cases; a repository with an unconventional name gets
  no invitation. Resolved at task 1, with the bias toward a fixed list plus the declaration path,
  since a configurable probe that must be configured defeats its own purpose.
- **Whether `/quenching:align`'s report distinguishes "not applicable" from "skipped".** The existing
  report has one skip vocabulary. Resolved at task 1 against
  `/docs/standards/quality/empty-response-honesty.md`, which already governs this distinction
  elsewhere.
- **Whether the legacy how-to belongs in `/docs/how-to/` or in the plugin's references.** It is
  guidance for a human, not payload a command loads, which argues for `how-to/`. Resolved at task 4
  once its length is known.
- **Whether `functional-checks.sh` gains two checks or one parameterized over both fronts.**
  Resolved at task 3 against how the existing checks are shaped.

## Risks

- **The applicability probe misfires on a repository with a `scripts/` folder that is not an
  operations surface** — a front-end build directory, say. *Mitigation:* the signal is a conventional
  root holding an **executable entry point**, not merely a directory of that name, and the outcome of
  a misfire is one printed invitation rather than a plan item.
- **Five fronts under one OK is a long run.** A conductor that takes a long time is a conductor people
  interrupt halfway. *Mitigation:* each front's align is itself probe-first, so the marginal cost of
  the two new fronts on a clean repository is four tool calls; the applicability probe cuts even that
  where a front is absent.
- **The count corrections are exactly the kind of sweep that misses one.** *Mitigation:*
  `citation-check.sh` runs in the validation set, and validation item 1 greps for the specific stale
  phrasings rather than trusting the sweep.
- **This spec depends on all eight predecessors.** If one is abandoned, the counts corrected here are
  wrong in a new way. *Mitigation:* task 5 re-derives every count from the tree as it stands at
  execution time rather than from the numbers written into this spec.
- **`functional-checks.sh` returning 2 could be read as passing.** *Mitigation:* validation item 6
  states the treatment explicitly, matching the repository's own operating contract.

## Handoff

This spec runs last. Before starting, re-derive every count from the tree as it actually stands —
how many fronts have aligns, how many namespaces exist, how many command bodies ship — rather than
trusting the numbers written here. If one of the eight predecessors was abandoned, that changes the
answers and the correction pass must reflect what shipped, not what was planned.

`commands/align.md` is a conductor: it invokes each front's align under its registry name and
reimplements none of them. Read §Order is a dependency, not a preference before touching the table,
and add the two rows in the same voice.

The applicability probe is the only genuinely new mechanism here. Write it into `commands/align.md`'s
step 1 alongside the existing three probes, in the same form, and keep the absent-versus-drifted
distinction visible in the report vocabulary — it is the thing most likely to be lost in a later
edit.
