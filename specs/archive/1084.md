## Problem

`git:pr:create` publica a branch como parte da abertura de um pull request, mas o eixo git não oferece uma operação independente para enviar checkpoints ou preparar uma branch para revisão futura. Sem essa skill, o agente tende a executar `git push` cru, criar um PR prematuramente ou misturar publicação com decisões de integração.

## Proposal

- Criar `/quenching:git:push` e sua skill Codex correspondente para publicar a branch atual, ou uma branch explicitamente nomeada, sem abrir ou alterar pull requests.
- Resolver remote, branch, upstream, divergência e estado local antes da escrita; mostrar o refspec exato e pedir confirmação sobre remote e branch.
- Usar `-u` somente quando necessário para estabelecer upstream; tratar branch sem commits novos como no-op informativo e recusar detached HEAD, remote ausente, base protegida por política e divergência que exigiria uma decisão humana.
- Preservar a separação: a skill publica apenas, e entrega o próximo passo textual quando a pessoa quiser abrir um PR ou sincronizar a branch.

## Out of Scope

- Abrir, atualizar ou mesclar pull requests.
- Staging, commit, fetch, rebase, reset, alteração de worktree ou exclusão de branch remota.
- Push forçado, `--force`, `--force-with-lease` ou qualquer bypass de proteção.
- Resolver divergência automaticamente ou escolher um remote quando a intenção não estiver determinada.

## Validation

- `python3 -m unittest discover -s plugins/quenching/tests` deve passar com repositórios temporários cobrindo upstream ausente, branch atrás ou divergente, detached HEAD, remote inexistente, branch base e push normal.
- `python3 scripts/validate_codex_plugin.py` deve validar a skill e a origem Claude correspondente.
- `python3 plugins/quenching-codex/scripts/bin/cq --root .agents components doctor --json` deve retornar `ok: true`.
- `python3 plugins/quenching-codex/scripts/bin/cq knowledge validate docs` deve permanecer sem erros.
- O contrato textual e os testes devem provar que nenhum caminho usa `--force`, `--force-with-lease`, `--no-verify`, staging implícito ou criação de PR.

## Design

- Fazer uma leitura local delimitada com `git status --short --branch`, `git branch --show-current`, `git remote -v`, `git rev-parse` e consultas de upstream; nenhuma consulta ao provider é necessária para a operação de push em si.
- O default seguro é a branch atual no remote `origin`; quando não há `origin`, há mais de um remote ou o argumento nomeia outra branch, a intenção deve ser explicitada antes da confirmação.
- Mostrar remote, branch, upstream, commits a enviar e o refspec antes de executar `git push`; a confirmação cobre exatamente esse destino.
- Usar push normal e `--set-upstream` apenas para upstream ausente. Divergência, detached HEAD, branch base ou falha do remote interrompem o fluxo e deixam a resolução para a pessoa.
- A skill não grava spec, não altera histórico local e não encadeia `git:pr:create`; o relatório pode indicar esse comando como próxima ação quando apropriado.

## Alternatives Considered

- Reutilizar `git:pr:create` para toda publicação — rejeitado porque checkpoint e abertura de PR são decisões distintas e o primeiro não deve exigir título, corpo ou vínculo de issue.
- Delegar ao agente um `git push` sem comando dedicado — rejeitado porque perde precondições, confirmação auditável e proibição explícita de push forçado.
- Automatizar force-push em branches de trabalho — rejeitado por reescrever histórico e conflitar com a higiene comum do eixo git.

## Open Decisions

- A sintaxe final para remote e branch nomeados será escolhida entre argumentos posicionais e opções, seguindo o padrão de entrada das demais skills git.
- A política de recusa de branch base será ajustada às evidências de `cq git base` e às convenções já declaradas, mantendo a proteção como default.
- O nível de detalhe dos commits ahead/behind será limitado ao que o Git local responde sem transformar a skill em uma operação de sincronização.

## Risks

- Um remote correto pode apontar para um fork inesperado; mitigar exibindo URL e destino exatos antes da confirmação.
- Um upstream divergente pode levar a uma recusa confusa; mitigar separando ahead, behind e divergent e nomeando a ação posterior (`git:sync` ou decisão humana).
- Descrições podem colidir com `git:pr:create`; mitigar destacando “publica sem abrir PR” nos gatilhos e em `Not for`.
- Um push normal pode ser rejeitado por política do servidor; mitigar reportando a mensagem do Git sem tentar bypass.

## Outcome

Implementada e revisada a entrada `/quenching:git:push` para publicar uma branch local em um remote e refspec explícitos, sem abrir ou alterar pull requests. O comando resolve remote, branch, base, upstream, ahead/behind e commits a enviar; recusa árvore suja, HEAD destacado, branch base, remote ausente, atraso/divergência, force e qualquer operação de histórico; mostra o destino e pede uma confirmação única antes do push normal. A entrega inclui a skill Codex gerada, testes de contrato e registros nos catálogos Claude, Codex e de projeto.

Todas as 7 tarefas foram concluídas. A revisão do branch não encontrou divergência de desenho nem conhecimento novo que justificasse documento em `/docs/`; a destilação foi um harvest vazio. O gate passou com 542 testes, tradução sem drift, plugin Codex validado, doctor local limpo, lint sem findings novos, `git diff --check` limpo e docs com 0 erros. Os guards estático e sintético do harness funcional passaram; a sessão funcional real não foi repetida porque o mesmo harness já havia bloqueado por timeout e não oferece um veredito confiável neste ambiente.

A spec está revisada, arquivada e pronta para merge. O próximo leitor deve manter a separação entre publicar (`/quenching:git:push`), abrir PR (`/quenching:git:pr:create`) e sincronizar divergência (`/quenching:git:sync`), sem introduzir bypass de proteção.
