## Problem

Configuration lives in each repository's `.claude/quenching.json`, which the platform wants to serve centrally through the quenching specs service instead. Put configuration reading behind a provider interface — file today, the specs service when declared — with a compatibility read of the existing file, and a migration path that lets the file disappear. Depends on the specs service serving configuration (`holetz/quenching#2087`, forge epic S8).

Member S10 of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent).

## Proposal

- Reading the repository configuration goes through a `ConfigProvider` interface in `common/config.py`; every front that reads `.claude/quenching.json` today reaches the document through it.
- The `file` provider is the default and is the compatibility read: with nothing declared, every value, refusal and `cq config show --effective` row is what it is today, the file included.
- A provider is chosen by the `QUENCHING_CONFIG_PROVIDER` environment variable (absent means `file`); a name no provider answers to is a refusal (exit 2) naming the registered providers, never a silent fallback to the file.
- A repository can run with no `.claude/quenching.json` when a non-file provider answers: `present` means "the active provider returned a document", `cq doctor` stops asking for the file, and `cq config show --effective` names the provider as the repository layer's source.
- `cq config export [--json]` prints the repository layer as the envelope a service would hold, so the file can be loaded into the service and then deleted; it only reads.
- The plugin README documents the provider, the variable, the compatibility read and the migration path.

## Out of Scope

- The service provider itself (its wire form, its credential, its cache): it needs the HTTP specs service of the forge epic (S14) and the credential rule of S32, neither of which exists in this repository. This spec delivers the seam and a registered test double; the provider is parked in `## Open Decisions`.
- Writing configuration through the service (`cq config init` stays a file write, `cq config check` stays a file check): the write port is S7 (`holetz/quenching#2086`).
- Changing any key, namespace or default of the envelope: the schema is untouched.
- The user layer (`~/.config/quenching/config.json`) and the `quenching` branch's `quenching.json`: they are per-person and per-store layers, not the repository file, and stay as they are.
- Deleting this repository's own `.claude/quenching.json`: it holds the hooks and subjects this repository runs on, and the retirement waits for a service that answers.
- Swapping any `Bash(cq …)` grant for an MCP tool: no grant, `allowed-tools`, `tools:`, hook, script or CI file changes here.

## Design

**Decision 1 — a provider returns the repository layer, nothing more.** `ConfigProvider.read(repo_root)` returns `(document | None, info)`: the parsed repository envelope and `{name, path, present, unparseable}`. Everything the loader does after the read (user layer merge, legacy refusal, unknown keys, namespaces) stays where it is, so a provider cannot change the interpretation of a value, only its origin. The same shape `config/effective.py` already builds for its repository layer.

**Decision 2 — selection is by environment, not by the file.** A repository that wants the file to disappear cannot name its provider inside the file. `QUENCHING_CONFIG_PROVIDER` is read once per load; absent means `file`. The user layer is not used for selection because it is read after the repository layer.

**Decision 3 — `find_repo_root` keeps locating the repository by the file and falls back to git's top level.** With no file the walk already ends at `git rev-parse --show-toplevel`, so the root is the same checkout; the fallback is the existing code path, now the normal one.

**Decision 4 — mutation stays a file concern.** `cq config init`, `cq config check` and `prepare_minimal_config` write or audit the file and keep reading it directly; they refuse (exit 2, message names the provider) when a non-file provider is active, because a write the service did not receive is a silent divergence.

**Decision 5 — the compatibility read is the default and the proof.** Existing tests are the compatibility test: none changes. A doctor line and the `export` verb are the only user-visible additions on the default path.

Binding contracts: `/docs/standards/` has no configuration standard this spec contradicts; the layer precedence documented in `config/effective.py` (`default` < `user` < `repository` < `branch`) is preserved; no grant, `allowed-tools`, `tools:`, hook, script or CI change.

## Alternatives Considered

Whole-shape alternatives:

- **Delete the file and read only a service.** Rejected: no service answers in this repository yet, and every repository without one (the open projects) would lose its configuration.
- **A network client in the loader now (HTTP or MCP).** Rejected: the wire form, the credential (S32) and the HTTP service (S14) are not decided; the only in-tree server is the stdio one, which serves the derived `cq specs config` payload and would read the same file, a circle.
- **Keep reading the file and add a service layer above it.** Rejected: that is a fourth layer, not a replacement, and the file could never disappear.

Reference projects (forge epic, §Reference projects, read 2026-10-25):

- **MrLesk/Backlog.md** (MIT): adapted as a direction only. It keeps one store with an MCP server over it, which is the shape this spec follows by putting configuration behind the same service as the specs; no code is taken and no dependency is added.
- **automazeio/ccpm** (MIT): rejected. It syncs specs into a tracker; it has no configuration-provider concern.
- **microsoft/azure-devops-mcp** (MIT, to confirm): rejected here, kept for later. Its read-only headers and Entra ID auth are the shapes a service provider would mirror, but the credential is S32's, so nothing is taken now.
- **`cq specs serve` portal** (this repository): rejected. It is a loopback board with a per-run token; configuration needs a non-interactive read, not a board.
- **`quenching://config` of spec 2087** (this repository): reused as the read-model a future service provider consumes after the envelope is fetched; this spec does not touch it.
- Backlog.md's SVAR/frappe Gantt rows and the forge, hallmark rows: not applicable to configuration.

## Open Decisions

- The service provider's wire form (HTTP resource or MCP resource carrying the raw envelope, since `quenching://config` serves the derived payload and not the envelope), its credential and its cache: decided when S14 (the HTTP service) and S32 (the credential rule) land; this spec leaves `register_provider` as the seam and proves it with a double.
- Whether `QUENCHING_CONFIG_PROVIDER` should also be declarable per user in `~/.config/quenching/config.json`: decided with the first adopter that needs it; assumption here is the environment alone.
- Why now and what would make this not worth doing: the problem states the dependency (S8 is merged) and the epic orders this member next; no human answer is recorded, so the assumption is that the epic order stands.

## Risks

- A reader the sweep missed keeps opening the file and diverges under a provider. Mitigation: the dependency map above lists every `CONFIG_FILE` use outside the loader, and the test double runs the loader with no file on disk so a missed reader fails visibly.
- An environment variable is invisible state: a stale export silently changes the repository layer. Mitigation: `cq config show --effective` and `cq doctor` print the active provider, and an unknown name refuses.
- The mirrors are many: a generator that is not rerun leaves a copy on the old behaviour. Mitigation: task 3.2 regenerates and the gate checks the copies.
