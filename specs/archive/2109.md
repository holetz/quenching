## Problem

Dois defeitos se repetiram em 2026-10-25.

1. **O spec-runner carimba `verifier=pass` no registro `run` antes de qualquer verifier.** Aconteceu na 2040, na 2041 (re-spawn) e na 2107. O conclude ou o condutor regravou o registro como `not-run`. É o comportamento que a 2075 deveria impedir, então a trava atual (prosa ou teste) não cobre o caminho do execute.
2. **`records.merge` fica `null` depois de um merge real.** Aconteceu na 2102, na 2103 e na 2107. O GitHub mostra o PR integrado e o registro `pr` é gravado, mas o `merge` não.

Done when: (1) `cq specs record <id> run` recusa `verifier=pass` quando nenhum verifier está associado ao run, ou o corpo do spec-runner proíbe o carimbo, com teste de contrato que trava a regra; (2) `cq git pr merge` grava `merge` (sha e data) no spec ligado ao PR quando o merge sai, com teste; gate verde. Nenhum grant muda.

## Proposal

- `cq specs record <id> run` recusa `verifier=pass` e `verifier=fail` quando a mesma chamada não traz `by=verifier`; o campo `by` é novo no registro `run` (nível fechado `verifier`), e um carimbo `verifier=not-run` descarta um `by` guardado.
- `cq git pr merge --spec <id>` grava o registro `merge` do spec (`strategy=merge-commit`, `subject`, `pr`) quando o merge sai no GitHub, inclusive quando o PR já estava integrado; um `merge` já gravado é reportado, nunca regravado.
- O corpo do `spec-runner` e do `orchestrator` declaram `by=verifier` só no carimbo do veredicto de um verifier; o `git-steward` passa `--spec <id>` ao merge quando o prompt nomeia o spec.

## Out of Scope

- Mudar grants de agentes ou permissões (nenhum muda).
- Gravar `merge` no caminho Azure de `cq git pr merge`, e o merge local de `git:merge`.
- Reescrever o `merge` de specs já integrados (backfill) e o spec 2108.

## Design

A causa do defeito 1: a regra de 2061 existe só em prosa, e o runner executa a cópia em cache do plugin, anterior à regra; a prosa não alcança esse caminho, então a trava passa para o código. `cq` não sabe quem chama, por isso a guarda exige uma declaração explícita (`by=verifier`) em vez de inferir o chamador: um carimbo `pass` sem ela, como o dos runners antigos, é recusado (exit 2, `sp-run-verdict-unattested`).

A causa do defeito 2: nenhum caminho grava `merge` após `gh pr merge`; `git:merge` só cobre o merge local. O verbo que de fato integra é `cq git pr merge`, então ele grava, usando o mesmo `cmd_record` que o `pr` usa. A escolha de `--spec` explícito (e não de descobrir o spec pelo PR) evita que um merge de teste ou de PR sem spec grave em specs reais. O subject segue o que o GitHub escreve, sem o `#` (`Merge pull request N from <dono>/<branch>`), porque o frontmatter lê ` #` como comentário e truncaria o registro. O schema do `merge` não tem campo de sha ou data; o payload do verbo devolve o sha do merge.

Suposição nomeada: o registro `merge` é write-once; um carimbo repetido vira aviso (`merge.stamped=false`), não falha do merge.
## Alternatives Considered

- Só reforçar a prosa do spec-runner: já existe (2061) e não alcançou o runner em cache; descartada.
- `verifier=pass` só com sha ou nome de agente verificado: o `cq` não vê o agente; `by=verifier` é a declaração mais barata que o código consegue exigir.
- Descobrir o spec pelo número do PR: arriscado em testes e em PRs sem spec; descartada.

## Open Decisions

- none — as escolhas acima são do pass sob a política do epic 2096; o `verification` fica no padrão.

## Risks

- Runners e orquestradores em cache sem `by` passam a ter o carimbo `pass`/`fail` recusado: é o efeito desejado, mas o orquestrador antigo perde o carimbo do verdict até atualizar o plugin.
- `merge` gravado com subject reconstruído, não lido do commit: se o GitHub mudar o formato, o subject diverge; baixo, pois o campo é informativo.

## Outcome

Shipped: `cq specs record <id> run` now refuses `verifier=pass|fail` unless the same call carries `by=verifier` (`sp-run-verdict-unattested`; new `by` field in the `run` schema, dropped on a `not-run` stamp), and `cq git pr merge --spec <id>` stamps the `merge` record (merge-commit, subject, pr) on GitHub, including for an already-merged PR, keeping an existing record. The spec-runner, orchestrator and git-steward bodies carry the new flags, and the mirrors were regenerated; the gate is green.

Left out: the Azure merge path does not stamp `merge` (parked in Discoveries); no backfill of old specs. The subject omits GitHub's `#` because frontmatter reads ` #` as a comment. The `merge` record has no sha/date fields in the schema, so the verb's payload carries the stamp but not the commit sha.

Next reader: the runner in the plugin cache predates 2061 and 2109 until the plugin is updated; its pass/fail stamps are refused by `cq` after the update, which is intended.
