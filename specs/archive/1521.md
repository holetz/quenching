## Problem

Substitui a 1485 (achados da sessão a6cdaa4e). Consultar o estado do front (spec ativa, task corrente, worktree) custa tool calls e tokens a cada vez, e o plugin não tem nenhuma superfície de mods: não há `register.tsx`, `hooks/hooks.json` nem plugin HUD no `.claude-plugin/marketplace.json`.

**Decisão do humano (2026-10-11): um plugin `quenching-hud` mínimo.** Ela autoriza exatamente esta superfície nova:
- um plugin separado no marketplace, com um painel de specs somente leitura (spec ativa, task, worktree), lido via `cq` sem escrever nada;
- o gate (`scripts/verify_repo.sh`) passa a validá-lo com `claude plugin validate`, ou com o equivalente que existir na versão instalada; a sintaxe se mede antes de entrar.

Fora do escopo, cada um como spec futura que exige nova decisão humana: a detecção de worker travado pelo mtime do jsonl; o custo por comando; o hook nativo no lugar de `warn-git-add-all.sh`; o seletor interativo; e o gate em background.

## Proposal

- O marketplace publica um terceiro plugin, `quenching-hud`, em `plugins/quenching-hud/`, instalável separado do `quenching`.
- Com o plugin ativo, uma faixa acima do prompt mostra numa linha a spec ativa da worktree (id, estágio, tasks marcadas/total) e o nome da worktree, lidos via `cq specs status --spec <id> --json`; fora de um branch `plan/<id>-...` a faixa não aparece.
- O plugin é somente leitura: só executa `git branch --show-current` e `cq specs status --spec <id> --json`, e nunca escreve em spec, branch ou disco.
- `scripts/verify_repo.sh` valida o plugin com `claude plugin validate`, e o gate falha se a validação falhar.
- O plugin tem ao menos um teste (`claude plugin test`) sobre a derivação da linha.

## Out of Scope

- Detecção de worker travado pelo mtime do jsonl: precisa de nova decisão humana, spec futura.
- Custo por comando: idem.
- Hook nativo no lugar de `warn-git-add-all.sh`: idem; este plugin não toca `hooks.json` do `quenching`.
- Seletor interativo (botões, ações): o painel só mostra; `Button` e qualquer escrita ficam fora.
- Gate em background: o gate só ganha o passo síncrono de validação.
- Painel lateral (`Pane`) e comando de barra: a faixa cobre a consulta barata; o pane só assenta com 110 colunas ou mais e exige abrir.
- Novo verbo `cq`: o plugin consome `cq specs status` como está.

## Design

**Superfície: faixa `AbovePrompt`, não `Pane`.** Um `ui.render` em `{ component: 'AbovePrompt' }` devolve uma linha ou `next(e)`. Um `Pane` assenta só a partir de 110 colunas e só depois de aberto; a faixa custa zero tool calls e é o painel mínimo que a decisão autoriza. Alternativa pesada: `Pane` com `$.ui.open`.

**Leitura: dois argv fixos via `$.process.run`, sem shell.** `["git","branch","--show-current"]` e `["cq","specs","status","--spec",<id>,"--json"]`. O id vem de `/^plan\/(\d+)-/` sobre o branch, então só dígitos entram em argv. Nenhum outro comando é montado. O `cq` vem do PATH, posto pelo plugin `quenching` quando ativo; sem ele a faixa some, sem erro. Premissa assumida: `cq` está no PATH quando o `quenching` está ativo (o `bin/` do plugin entra no PATH).

**Quando atualizar:** em `session.start` e `turn.complete`, e o resultado vai para `$.state` (`atom`), que a faixa lê ao desenhar. Sem timer: o front muda por turno, não por segundo.

**Lógica pura separada.** `hud.ts` exporta `specIdFromBranch(branch)` e `formatLine({id, stage, checked, total, worktree})`; `register.tsx` só liga eventos. Isso torna o teste do plugin independente do engine.

**Lockstep de versão.** `test_specs_release` exige a mesma versão em toda entrada do marketplace, então a entrada e o `plugin.json` do HUD nascem em `6.4.0`. O `cq specs release` hoje bumpa a entrada do marketplace mas não o `plugin.json` do HUD: está no Open Decisions.

**Gate.** Passo `run_check "quenching-hud plugin" claude plugin validate plugins/quenching-hud`. Como o gate já trata `coverage` ausente, `claude` ausente pula o passo com aviso explícito e não passa em silêncio; a sintaxe do comando é medida na task 1.1 antes de entrar no gate.

Contratos que o design respeita: `docs/project/layout.md` (um plugin gerado, `quenching-specs-reader`, é regenerado por inteiro; o HUD é escrito à mão e não entra em `sync_specs_reader_plugin.py`).

## Alternatives Considered

- **`Pane` com `$.ui.open` e comando de barra.** Perdeu: assenta só com 110 colunas e exige abrir; a consulta barata é a que fica sempre à vista.
- **Linha de status via `$.ui.status`.** Perdeu: uma única entrada de texto, sem estrutura, disputada com outros plugins.
- **Estender o plugin `quenching` com o HUD.** Perdeu: a decisão humana autoriza um plugin separado, e misturar acopla a superfície nova ao release do `quenching`.
- **Usar `cq-specs-read` (o plugin leitor) como porta de leitura.** Perdeu: exigiria o leitor ativo; `cq specs status` com argv fixo já é somente leitura e o `quenching` é o pré-requisito natural.

## Risks

- `cq` fora do PATH: a faixa some. ACCEPTED — degradação silenciosa é o comportamento desejado; o README do plugin declara o pré-requisito.
- `claude` ausente no gate local: o passo pula com aviso. ACCEPTED — o mesmo tratamento do `coverage`; o CI e o release têm `claude`.
- Deriva de versão do `plugin.json` do HUD no próximo release: mitigada pelo teste de lockstep do marketplace, que cobre a entrada; o arquivo do plugin fica no discovery.
- A API de mods muda entre versões do Claude Code (2.1.296 medida): o passo do gate é o que denuncia isso, e é por isso que ele existe.
- Alargamento de superfície executável: o plugin executa dois argv. Coberto pela decisão humana de 2026-10-11 desta spec; qualquer outro argv é alargamento e exige nova decisão.
