## Problem

After `ops-inventory-and-doctor` there is a verifier that grades a target's operations surface and
nothing that acts on it. A finding a human has to read out of a JSON payload and then fix by hand is
not a front — it is a linter with no home. Every other front in this plugin pairs its verifier with
exactly two bodies: one `align` that converges the tree on one OK, and one `status` that reports
without writing. `ops` has neither, so the eight codes reach nobody.

The convergence this front owes is also not the kind a program can do alone. Generating a registry
is mechanical. Deciding that `revalidacao_gold/` is one-shot code that belongs in `_archive/`,
that `clone_to_dev.py` needs a `--run` flag before anyone touches it again, or that six commented
checks in `ci/deploy.py` should come back on rather than be deleted — those are judgements a human
makes once, on a plan they can see whole. That shape is precisely what `align/sweep-doctrine.md` and
`align/convergence.md` already specify, and what this spec has to obey rather than reinvent.

## Proposal

Mint the front's two bodies, one file per entry point.

**`/quenching:ops:align`** — converge the operations surface. It opens on the probe rule: run
`cq ops doctor --json` and branch on the exit code. Clean exits report "conformant, nothing to
align" and stop, at a cost of two tool calls. Findings produce one consolidated plan, grouped by
what the fix actually is, and one OK authorizes the whole run.

The plan separates three bands, and the separation is the body's main job:

| Band | Example finding | How it closes |
| --- | --- | --- |
| **Mechanical** | `op-registry-stale`, `op-undocumented` | regenerated; no per-item question |
| **Structural** | `op-adhoc-root`, `op-untyped-exit`, `op-no-router` | applied under the one OK, one edit per entry point |
| **Judgement** | `op-unarmed-write`, `op-disabled-check`, `op-orphan` | **reported with the command that closes it, never driven** |

The third band is the one that keeps the front honest. Arming a destructive entry point changes what
that entry point does in production; moving code to `_archive/` is a claim that nobody runs it; and
turning six commented checks back on is a decision with a blast radius the align cannot price. Those
are reported with their evidence and their closing command, exactly as
`align-surface.md` §Probe before the inventory requires of any stage the probe cannot price.

**`/quenching:ops:status`** — read the whole front and report, writing nothing: root and router,
entry points by package, the lifecycle split, findings by code and band, and the registry's
freshness. It never repairs, and it never calls a missing optional thing healthy.

## Out of Scope

- **Any change to `cq ops`.** The programs exist; this spec writes bodies that run them. A defect
  found in a check is recorded and fixed in its own spec, not patched from a command body.
- **Minting entry points.** `/quenching:ops:entrypoint:new` and `cq ops registry --write` are the
  next spec's.
- **Arming, archiving or re-enabling anything unattended.** The judgement band is reported. This
  spec adds no verb that performs it.
- **Wiring `ops` into `/quenching:align`.** The conductor gains its row in the integration spec,
  after both new fronts have their aligns.
- **Converging the measured target.** Running the finished align against `databricks-risco-gold` is
  what proves the bodies work; the resulting changes belong to that repository, not to this spec.

## Design

**The bands are the contract, not a presentation choice.** `align-surface.md` already draws the line
between what an align may do unattended and what it must report: a stage the probe cannot price is
offered, never run to find out. Applied to this front the line falls between changes whose blast
radius ends at the repository (a regenerated registry, a shared bootstrap import) and changes whose
blast radius reaches production (an armed entry point, a re-enabled deploy gate, a claim that code
is dead). Publishing the split in `bands.md` rather than deciding it inside the body is what lets
`status` report the same three bands without restating the rule.

**Why the judgement band is reported and not merely confirmed per item.** The plugin has a
confirm-each-irreversible-item pattern and it is the wrong one here. Confirming "arm
`clone_to_dev.py`?" inside an align run asks a human to decide a production question in the middle of
a housekeeping sweep, with none of the context that decision needs. Reporting it with its evidence
and its closing command lets the decision be made when it is actually being made.

**Why `op-disabled-check` is judgement and not structural.** Six commented calls in `ci/deploy.py`
have two honest resolutions — turn them back on, or declare them off — and the align cannot know
which, because the reason they were commented is not in the file. Guessing either way is worse than
reporting: turning them on could break the deploy the repository depends on; deleting them destroys
the only trace that they existed.

**Why `status` gets its own body rather than a flag on the align.** Every other front does this and
the reason survives here: an align's description carries convergence triggers ("fix the drift", "set
this up"), and a read-only question ("what is the state of the scripts folder") routes to it only by
accident. Two descriptions route two intents. The bodies share the reference files and duplicate
none of the doctrine.

**What the align may write, and where.** Only inside the declared operations root and its registry
document. `align-surface.md` §No sweep records itself binds the rest: the run's own account lives in
the report, never in a log file the sweep appends to.

## Alternatives Considered

- **One body with a `--dry-run` flag instead of two.** Rejected: it is the `align-and-update` shape
  the surface already deleted once, and it makes a read-only question reach a convergence
  description.
- **Let the align fix the judgement band under a per-item confirmation.** Rejected under §Why the
  judgement band is reported — the confirmation would be asked at the worst possible moment, and the
  align would become the place production decisions get made by default.
- **Fold the band table into `entrypoint-contract.md` and skip `bands.md`.** Partly adopted: the
  contract file gains a band column so there is one source of truth per code, and `bands.md` carries
  only the disposition rules and the closing commands, which are the align's business and not the
  contract's.
- **Have the align regenerate the registry silently, outside the plan.** Rejected: a sweep that
  writes before the OK breaks the one-confirmation contract even when the write is harmless, and the
  regenerated registry is exactly the evidence that makes the rest of the plan legible.

## Open Decisions

- **Whether `op-no-router` is structural or judgement.** Adding a router to a repository that has
  none is a real change to how everybody invokes everything. Resolved at task 1, against whether the
  align can propose a router that only *wraps* what already exists — if it can, it is structural; if
  installing one requires choosing a mechanism, it is judgement.
- **Whether the align offers to converge a target that has declared no `opsRoot`.** `cq ops doctor`
  refuses with exit `2`. The body can stop there, or offer to declare the root. Resolved at task 1
  against `sweep-doctrine.md`'s handling of an unconfigured front elsewhere.
- **Whether `status` reports the registry's staleness when no registry exists.** The check is inert
  by the previous spec's design; whether the body says "no registry" as a state or as a finding is
  resolved at task 2 against `/docs/standards/quality/empty-response-honesty.md`.

## Risks

- **The bands can be read as severity.** A judgement finding is not more severe than a structural
  one; it is differently owned. *Mitigation:* `bands.md` states the axis as *who decides*, and the
  report is required to print the band label with that gloss rather than ordering by band.
- **A body that reports rather than fixes reads as unfinished.** The judgement band will look to
  some readers like the align refusing to do its job. *Mitigation:* each judgement finding names its
  closing command, so the report is a routing decision with a next step, not a shrug — the same
  contract the other aligns already meet for their unpriceable stages.
- **Two more bodies widen the always-loaded description surface.** *Mitigation:* both descriptions
  are written to the surface's own length doctrine and measured by `components lint`, and the spec's
  validation includes the surface-count assertion rather than leaving it to be discovered.
- **The align could be run before `cq ops` exists in an installed copy.** *Mitigation:*
  `tool-resolution.md` already owns that failure, and the body cites it rather than adding a second
  resolution path.
