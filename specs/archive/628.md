## Problem

O CI deste repositório leva em média ~7 min de parede por commit (mediana 416 s, faixa 245–712 s nos últimos 30 runs bem-sucedidos do workflow CI), e o tempo de parede é sempre o do job `Gate (Python 3.11)`: os demais jobs (Ruff ~8 s, Functional ~6 s, Windows ~40 s, Gate 3.13 ~115–280 s) terminam antes.

Dentro desse job, ~90% é a suíte medida por coverage: no run 45870560616 a suíte levou 608 s em 3.11 sob `pytest-cov` (tracer C, porque `COVERAGE_CORE=sysmon` só se aplica em Python ≥ 3.12), enquanto a mesma suíte, no mesmo commit, levou 170 s em 3.13 sem coverage; todo o resto do gate (ruff, doctors, citation checks, build do site) somou ~60 s. O custo dominante é medir coverage no interpretador mais lento para isso, não a quantidade de verificações.

## Proposal

- A célula da matriz que roda `scripts/verify_repo.sh` (suíte medida, piso de coverage, doctors, builds) passa a ser a do Python mais novo (3.13), onde o gate já liga `COVERAGE_CORE=sysmon`; o tracer C de 3.11 deixa de estar no caminho crítico.
- A célula 3.11 (o mínimo de `requires-python`) continua rodando a suíte inteira, randomizada e paralela, sem coverage, em todo push e PR — a detecção de incompatibilidade com 3.11 não perde nada.
- O passo do gate no CI declara `QUENCHING_TEST_SLOTS` igual às CPUs lógicas do runner: o runner é dedicado a um gate, então o orçamento compartilhado não deve cortar os workers pela metade (hoje: `[slots] 2 of 2`, 2 workers num runner de 4 vCPUs).
- O piso `.coverage-floor.json` continua aplicado em todo push e PR sobre o mesmo artefato; o gate completo continua em main, em PR e no `/release`.
- `docs/standards/ci-cd/test-cost.md`, `docs/standards/ci-cd/index.md` e o `README.md` descrevem o novo papel de cada célula e o orçamento do runner dedicado.

## Out of Scope

- Fatiar a suíte em vários jobs com `coverage combine` — mais runners, artefatos e um caminho de merge de dados de coverage para ganhar menos do que trocar o tracer; reavaliar só se o gate em 3.13 continuar acima de ~5 min.
- Rodar o gate (ou o piso) só no main — proibido pela delegação: o piso e o gate completo continuam em todo PR.
- Mudar `requires-python` para 3.12 (o que daria sysmon a todas as células) — é uma quebra para alvos instalados.
- Separar os ~60 s de checks não-teste do `verify_repo.sh` em outro job — quebra o contrato de gate único e o ganho é pequeno.
- Acelerar testes individuais lentos ou a camada Windows (~40 s, fora do caminho crítico).

## Design

- **Coverage se mede onde é barato.** O gate já escolhe `sysmon` em Python ≥ 3.12 e o comentário dele registra que os totais são idênticos; o caro é o tracer C de 3.11 (608 s medidos contra 170 s da mesma suíte sem coverage em 3.13 no run 45870560616). Regra: a célula que carrega o piso é a do Python mais novo da matriz.
- **Compatibilidade se prova com a suíte, não com coverage.** A célula do mínimo suportado roda a suíte inteira, `-n auto`, randomizada com a semente do run — o mesmo comando que a 3.13 roda hoje.
- **Runner dedicado = orçamento inteiro.** `scripts/toolchain/slots.py` dá a um gate sozinho metade dos núcleos físicos para deixar espaço a um par concorrente; no runner do CI não há par, então o workflow exporta `QUENCHING_TEST_SLOTS=$(nproc)` no passo do gate. Nenhuma linha do plugin muda; o default local continua o mesmo.
- Contratos que não podem ser contrariados: `docs/standards/ci-cd/test-cost.md` §Three tiers, one gate (CI paga a suíte inteira, piso aplicado); o teste `test_windows_job_fails_a_step_that_runs_zero_tests`; `permissions: contents: read` no topo.

### Assumptions

- O total de coverage em 3.13 com sysmon fica acima do piso 76.5 — depende `## Proposal` (1º item); provado pelo benchmark local e pelo `coverage floor` do run do PR.
- O runner `ubuntu-latest` de repositório público tem 4 vCPUs com 2 núcleos físicos reportados — depende o item de `QUENCHING_TEST_SLOTS`; provado pela linha `[slots] N of N` do log do PR.

## Alternatives Considered

- **Rebaixar a 3.11 a smoke (compileall + import) em PR e suíte completa só no main/`/release`** — permitido pelo humano; perde detecção de API de stdlib exclusiva de 3.12+ que só um teste exercita. Só compensa se a célula 3.11 completa virar o caminho crítico — decidido pela medição (`## Open Decisions`).
- **Fatiar a suíte em N jobs com combine de coverage** — ver `## Out of Scope`.
- **Gate só no main** — proibido (piso e gate completo em todo PR).

## Open Decisions

- none — a única decisão aberta (manter a suíte completa na 3.11 em todo PR ou rebaixá-la) foi fechada pelo run 45896048389: a célula 3.11 (181 s) termina antes do gate 3.13 (189 s), então fica completa; registrada em `## Discoveries`.
## Risks

- Um ramo de código só alcançado em 3.11 deixa de ser contado no coverage, ou o inverso — mitigação: o benchmark compara os totais nos dois interpretadores antes do merge, e o piso continua aplicado.
- `sysmon` mede diferente do tracer C em algum caso de borda e o total cai abaixo do piso — o `coverage floor` do PR falha alto, nunca em silêncio.
- Com 4 workers em 2 núcleos físicos o ganho de `QUENCHING_TEST_SLOTS` pode ser menor que 2× — ACCEPTED: a célula 3.13 já roda com `-n auto` = 4 sem problema; o número real vem do run do PR.
- A variância do runner (245–712 s antes) mascara o ganho num só run — mitigação: comparar a duração do passo da suíte e a soma por etapa, não só a parede.

## Discoveries

- decision: o gate completo (verify_repo.sh, coverage + piso) passa para a célula 3.13 (COVERAGE_CORE=sysmon) e a 3.11 roda a suíte inteira sem coverage — medido: suíte com coverage em 3.11 = 608 s vs mesma suíte sem coverage em 3.13 = 170 s no run 45870560616; resto do gate ~60 s; parede mediana 415,5 s (30 runs, faixa 245–712 s).
- decision: o passo do gate no CI exporta QUENCHING_TEST_SLOTS=$(nproc) — medido: o plugin slots deu ao gate 3.11 só 2 workers ('[slots] 2 of 2', núcleos físicos) num runner de 4 vCPUs, enquanto a célula 3.13 sem o plugin usou -n auto; o runner é dedicado a um gate.
- decision: specs_claim_acquire falhou com sp-claim-git (push de refs/quenching/claims/628 recusado); a build segue sem reserva, conforme execute.md exit 2.
- decision: benchmark local (slot 5, -n 4, mesma semente 12345): coverage total idêntico em 3.11/tracer C e 3.13/sysmon — 85,537% (26668/31177 linhas), 0 arquivos divergentes, piso 76,5; tempo local 502,7 s vs 362,8 s (ruidoso: máquina com load ~11 e o 3.13 esperou slots). Medir no Python mais novo não muda o piso.
- decision: a célula 3.11 continua com a suíte inteira em todo PR (não rebaixada a smoke nem a main/release) — medido no run 45896048389 do PR #634: Gate 3.13 189 s (suíte medida 135,2 s, 4 workers '[slots] 4 of 4', piso OK), Gate 3.11 181 s (suíte 167,1 s), parede 191 s; a 3.11 termina antes do gate, então rebaixá-la não economiza parede e perderia detecção (ex.: commit 'Path.read_text(newline=) (Python 3.11)' da spec 556 só a suíte completa pegou).

## Outcome

Entregue: o gate completo (`verify_repo.sh`: suíte medida, piso, doctors, builds) roda na célula 3.13 com `COVERAGE_CORE=sysmon` e `QUENCHING_TEST_SLOTS=$(nproc)`; a célula 3.11 roda a suíte inteira sem coverage em todo push/PR. Piso e gate completo continuam em todo PR, no main e no `/release`. Teste novo em `test_surface_listings.py` fixa o papel das células; `docs/standards/ci-cd/test-cost.md` ganhou §Coverage is measured where it is cheap e a regra do runner dedicado.

Medido: antes, parede mediana 415,5 s (30 runs, faixa 245–712 s), suíte medida em 3.11 = 608 s com 2 workers. Depois (run 45896048389, PR #634): parede 191 s; suíte medida em 3.13 = 135,2 s com 4 workers; célula 3.11 = 181 s, terminando antes do gate. Coverage idêntico nos dois interpretadores (85,537%, benchmark local, mesma semente).

Fora: fatiar a suíte em jobs, acelerar testes individuais, mexer no job Windows. A decisão sobre rebaixar a 3.11 foi fechada pela medição: não compensa. Revisado e pronto para merge.
