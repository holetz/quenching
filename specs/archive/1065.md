## Problem

The target configuration stores front keys in an unscoped shape and the shared loader lives in the `specs` pillar even though `ops`, `proof` and `git` import it, allowing a configured front to disappear silently during migration. The contract must namespace keys, extract the loader to `common/`, and refuse a flat-only configuration with an explicit migration error.

## Proposal

- The target configuration has an explicit envelope: front-owned settings live under `specs`, `ops` and `proof`, while settings that belong to no single front have an explicit non-front home. The binding contract is ownership by consumer, not a flat global key list.
- A shared loader lives in `quenching.common.config`. It owns configuration-home discovery, JSON parsing, provider metadata, envelope-level shape and legacy-shape diagnostics; each front adapter owns the defaults, validation and meaning of its own namespace.
- `specs`, `ops`, `proof` and `git` retain their current effective defaults, provider selection and front-specific refusals. `ops`, `proof` and `git` no longer depend on a loader owned by the `specs` pillar, and their resolved payloads remain behaviorally equivalent for a valid namespaced configuration.
- A flat or mixed configuration containing front-owned legacy keys is refused with exit 2, names the keys and their destination namespaces, and gives a migration instruction. It is never read as absent and never merged with the namespaced form, so a configured front cannot disappear silently.
- The Claude and Codex projections express the same namespace contract in their respective homes (`.claude/quenching.json` and `.agents/quenching.json`), with their generated references, fixtures and import graph kept in parity.
## Out of Scope

- Automatically rewriting an installed target's configuration, adding a migration verb, or selecting a release/version boundary for the breaking flat-to-namespaced change. This spec defines the refusal and its migration message; the release treatment is parked below.
- Changing provider derivation, GitHub/Azure Boards storage, specs lifecycle semantics, worktree isolation, hook execution, profile interpretation, bundle roots, or the meaning of any `ops` or `proof` key.
- Giving `security` or another axis a new front, changing front ownership, or applying A4's shared-file arbiter to `pyproject.toml` or workflow files.
- Keeping a compatibility fallback that silently reads root-level front keys, creating a second configuration file per front, or copying configuration into `/docs/`.
- Implementing the change during definition. This spec records the executable work; code, tests, standards and generated projections belong to `quenching-specs-execute`.

## Validation

The implementation is valid only when all of the following are true:

- A fixture with the namespaced envelope loads the same effective `specs`, `ops`, `proof` and `git` behavior currently measured from valid flat settings; `cq specs config --json`, `cq ops doctor --json` and `cq proof doctor --json` expose the owning namespace rather than a cross-front flat key list.
- A missing file or missing optional namespace preserves its documented default. In particular, absent `ops` declarations still produce the existing `op-config-missing` refusal, while proof keeps its documented `tests/` and ratchet defaults; absence is not confused with a legacy flat configuration.
- A fixture with root-level front-owned keys (`opsRoot`, `router`, `registry`, proof keys, or specs-owned keys), and a fixture mixing such keys with namespaced keys, both exit 2 before a front reports `not applicable` or `missing`; the structured result names the unscoped keys, their namespace destinations and the migration action.
- Unknown top-level namespaces and malformed values retain the existing diagnostic boundary: they are reported by the owning health command, never silently discarded, and never cause a valid namespace to be replaced by a default.
- The import graph proves that `ops`, `proof` and `git` do not import `quenching.specs.config` for shared loading, while specs-only helpers remain available to specs callers; the normalized payloads and refusal codes for valid inputs remain compatible.
- The source and Codex projections use their correct configuration homes and identical namespace semantics. The Codex projection does not regress to the source `.claude` path, and its references no longer document flat keys.

## Design

### Ownership and envelope

The recommended envelope is:

```json
{
  "backend": "github",
  "shared": {
    "worktreeSetup": "...",
    "hooks": {"after_specs_execute_task": [{"command": "/my:security-review"}]},
    "profiles": {"installed": ["knowledge", "specs", "components"]}
  },
  "specs": {
    "specsBranch": "specs",
    "azureStates": {"plans": "New", "archive": "Closed"},
    "azurePlacement": {},
    "azureColumns": {},
    "subjects": {},
    "tagCatalog": {},
    "workItemTypes": {},
    "fanoutMinComplexity": "medium"
  },
  "ops": {
    "opsRoot": "scripts",
    "router": "pyproject.toml",
    "registry": "scripts/registry.md"
  },
  "proof": {
    "proofRoot": "tests",
    "layers": {},
    "measuredRoots": [],
    "proofExclusions": [],
    "ratchetPath": null
  }
}
```

`backend` remains a root-level legacy/refusal input because provider selection is derived from `origin` and it is not a front-owned setting. The exact home for `worktreeSetup`, `hooks` and `profiles` is the one shared-envelope decision parked below; the invariant is that these cross-front settings have one explicit owner and are not mistaken for `specs`, `ops` or `proof` keys. `registry` is included under `ops` because the current `ops` adapter already owns its meaning even though the shared flat key table does not recognise it.

### Current and proposed flow

```text
Today:
.claude/quenching.json
        -> specs.config.load_config (file + provider + every front key)
        -> specs / ops / proof / git callers

After A5:
.claude/quenching.json or .agents/quenching.json
        -> common.config.load_config (home + envelope + provider + migration diagnostics)
        -> one front adapter (specs | ops | proof | git)
        -> the owning caller
```

`common.config.load_config` reads the one configuration file and returns a normalized envelope plus path, presence, parse, provider and legacy-shape metadata. It does not decide what an `opsRoot`, a proof layer or a specs placement means. `specs/config.py` keeps specs-only helpers and a thin compatibility boundary where existing specs callers need it, but the shared file read and the cross-front key registry leave that module. `ops/config.py`, `proof/config.py` and `git/base.py` consume the common loader or a front-neutral accessor directly; none imports the specs pillar to obtain shared configuration.

The source projection's home is `.claude/quenching.json`; the Codex projection's home is `.agents/quenching.json`. The translation step must preserve that existing projection rule in code, docstrings, references and fixtures, including the current Codex constant/reference mismatch.

### Refusal and default contract

- The loader classifies any root-level front-owned key as unscoped legacy configuration. A namespaced configuration containing any such key is also refused: there is no precedence rule between two sources of truth.
- The CLI returns a dedicated `sp-config-unscoped` exit-2 refusal with the config path, every offending key, its destination namespace and a direct migration instruction. The implementation may split the code for pure-flat and mixed forms only if the existing CLI taxonomy proves that distinction useful; both cases must remain refusals and must carry the same actionable information.
- The loader never interprets a flat key as an absent namespace. A repository with no front-owned declarations is the ordinary absent case and keeps current defaults/refusals. An `ops` namespace without its required keys still reaches `op-config-missing`; a malformed proof namespace still reaches proof's existing invalid-config boundary.
- Unknown namespace and key diagnostics remain visible at the layer that owns them. The common loader reports envelope violations; front adapters report their own values. No layer silently drops a key merely because another layer does not understand it.
- The migration is diagnostic, not automatic. The loader does not write the target file, choose a version, or run a release action.

### Contracts the design must not contradict

- `docs/standards/workflows/plugin-configuration.md` keeps `.claude/quenching.json` as the one target configuration home, derives provider from the remote, refuses provider conflicts and never merges a legacy store.
- `docs/standards/architecture/ops-front.md` requires an unambiguous operations root and router and refuses `op-config-missing` rather than guessing.
- `docs/standards/architecture/proof-front.md` owns proof-root, layer and measured-surface meaning and keeps the target's default proof shape conditional.
- `docs/standards/ci-cd/versioning-release.md` makes the version bump the release's deliberate act; this spec must not put a version bump or release mutation into `## Tasks`.
- The current tree proves the dependency seam: `specs/config.py` carries `CONFIG_KEYS`, `PROOF_CONFIG_KEYS` and the file reader; `ops/config.py` and `proof/config.py` call it, and `git/base.py` imports `load_config` and `infer_base_branch`. The change must preserve the latter behavior while relocating ownership.

### Execution decisions

Every task that can be delegated declares `files:`; `pattern:` names the closest existing implementation or fixture; `verify:` is scoped to the files it may break. No `[P]` marker is declared: the loader, adapters, docs and projection have semantic dependencies even where their file sets are disjoint, and serial execution is the evidence-backed safe order.
## Alternatives Considered

**Keep the flat root keys and only move the loader.** Rejected: the loader's location would change while ownership would remain ambiguous; adding a third reader for `toolchain` or `delivery` would reproduce the measured `pyproject.toml` seam and let a front disappear on migration.

**Use one configuration file per front.** Rejected: `docs/standards/workflows/plugin-configuration.md` establishes one configuration home at the repository root, and multiple files create discovery, precedence and partial-installation questions without removing the ownership problem.

**Read namespaced keys first and fall back to flat keys.** Rejected: the problem is specifically the silent disappearance of a configured front. The bundle also rejects merging competing configuration homes because no safe precedence rule exists; the same rule applies inside this envelope.

**Move every meaning into `common.config`.** Rejected: extracting a shared loader must not create a new god module. The common layer can parse the envelope and expose metadata; `specs`, `ops`, `proof` and `git` retain their own defaults, validation and semantics.

**Rewrite flat targets automatically during this spec.** Rejected: the change is breaking, the release standard says the version/release act is decided over the accumulated primary state, and an automatic rewrite would alter user configuration without a separately evidenced migration decision. Runtime refusal plus an explicit instruction is the safe boundary for this spec.
## Open Decisions

- **The canonical home for `worktreeSetup`, `hooks` and `profiles`.** Evidence proves they are not owned by `ops` or `proof`, while their current consumers are execute isolation, event owners and the cross-front conductor. Recommended direction: put them under one explicit `shared` namespace so the envelope has no ambiguous root-level front keys. Decide during the first execution task by tracing the three consumers against `plugin-configuration.md`, `extension-points.md` and `install-profiles.md`; retain root-level placement only if those contracts show that a shared namespace would misstate ownership.
- **How the flat-to-namespaced refusal reaches an already-installed target.** The refusal and no-fallback rule are settled by the problem and umbrella; the release mechanics are not. Decide after the implementation's compatibility matrix, against `docs/standards/ci-cd/versioning-release.md`, whether the change needs a release boundary, a migration verb or documentation-only guidance. This spec must not choose a version or add that release action.
- **Whether pure-flat and mixed configuration deserve distinct refusal codes.** The evidence requires the same exit-2 behavior and actionable migration data, but does not distinguish the taxonomy. Decide in the refusal-test task by the existing `sp-config-*` vocabulary, preferring one code unless separate codes improve machine-readable remediation without changing the contract.
- **The human go/no-go threshold for breaking installed targets.** The repository evidence proves the current silent-loss failure and the compatibility checks that can prevent it, but it does not state how much upgrade friction is acceptable. Decide at the approval/release review after the matrix is green, using the number and kinds of affected flat consumers as the evidence; until then the recommendation is to stop with the decision open.
## Risks

- **Installed targets break when flat keys stop being read.** Mitigation: refuse before any front falls back to a default, list every offending key and destination, and test pure-flat, mixed and already-namespaced fixtures. ACCEPTED only as an explicit, reviewable migration boundary; not accepted as silent loss.
- **A partial migration creates two sources of truth.** Mitigation: classify any mixture as a refusal, never merge values, and make the refusal payload machine-readable enough for a caller to show the exact move required.
- **The extracted loader becomes a second cross-front god module.** Mitigation: keep common responsibilities to home discovery, parse, envelope and provider metadata; keep defaults/meaning in front adapters; assert the import graph in tests.
- **Moving keys changes defaults or provider behavior.** Mitigation: snapshot valid namespaced outputs against the current valid behavior, cover absent namespaces separately, and rerun specs backend tests plus ops/proof fixtures.
- **The Codex projection continues to read `.claude/quenching.json` or documents flat keys.** Mitigation: update the projection through the translation path, add a Codex-home fixture, and require `components translate --check --json`.
- **Standards and command prose keep teaching the old shape.** Mitigation: update the three declared standards, the specs-facing references and all flat-key citations found by the citation sweep; run `citation-check.sh --half 2` and inspect the residuals.
- **The undocumented `registry` override is lost while the `ops` keys move.** Mitigation: include `registry` in the operations namespace contract and add an explicit fixture for the override and its default.
- **A release decision is smuggled into implementation tasks.** Mitigation: leave versioning, release and automatic migration out of `## Tasks`; decide them only at the release moment defined by the versioning standard.
