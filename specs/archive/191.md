## Problem

quenching/assets/bin/quenching/codex/guard.py:50: status() usa o git() tolerante, que devolve "" quando o git falha, então touched() volta vazio e implement.py:213 calcula outside = []. Reprodução (reproduzida 2 vezes): um codex falso cria OUTSIDE.py fora de files: e corrompe .git/index; o resultado é exit 0, ok True, outside [], reason 'codex wrote the task', com git status respondendo 'fatal: .git/index: index file smaller than expected'. Consequência: a guarda, que roda com --dangerously-bypass-approvals-and-sandbox e deveria provar que o diff ficou dentro de files:, aceita uma escrita fora deles. O docstring diz 'the guard fails closed', mas isso só vale para a leitura da base. A correção esperada é falhar fechado (recusar) quando git status falha, o que só estreita a guarda.

## Proposal

- `guard.status()` (e com ele `touched()`) lê o `git status` pelo caminho estrito: um `git status` que falha levanta `GuardError` em vez de devolver uma lista vazia.
- `cq codex implement` recusa com exit 2 `codex-git-guard` quando o `git status` falha antes da execução (o Codex nunca é iniciado) ou depois dela; o payload carrega `statusUnreadable: true`, não carrega `discard` e a mensagem manda parar a tarefa como `needs-human`.
- A reprodução do `## Problem` (codex falso que escreve `OUTSIDE.py` e corrompe `.git/index`) deixa de terminar em exit 0 / `ok: true` e passa a terminar em exit 2, com prova executável.
- O contrato que o chamador segue (`execution-delegation.md`) e o padrão `docs/standards/architecture/codex-pillar.md` dizem que um `git status` ilegível é tratado como `outside` desconhecido: `needs-human`, sem descartar nada.

## Out of Scope

- Tornar estritas as leituras de `refs()` (`rev-parse HEAD`, reflog, stash) e o `rev-parse --show-toplevel` de `implement.py` — continuam no `git()` tolerante; ficam registradas em `## Discoveries` como achado à parte, porque a política do épico 196 decidiu só o caso do `git status`.
- Mudar o flag `executor.enabled`, qualquer grant ou o argv do Codex — a decisão do épico 196 é explícita: a correção só estreita a guarda.
- Reparar o índice corrompido ou limpar o worktree — a guarda só lê; limpar continua sendo do humano.
- As specs 192 e 193, que também tocam `codex/implement.py` e rodam depois desta, em série.

## Design

- **Falhar fechado no `git status`.** `status()` passa a usar `git_strict`, o mesmo leitor que `base_state` já usa: uma falha do git nunca é um valor vazio. É a decisão registrada no épico 196 (2026-11-21): recusar quando o `git status` falha, o que só estreita a guarda.
- **O código de recusa continua `codex-git-guard`, com `statusUnreadable: true`.** O chamador já ramifica em `codex-git-guard`; o campo novo diz que `outside` é desconhecido, não vazio. Sem `discard`, porque descartar dentro de `files:` e reescrever a tarefa — o ramo de `outside` vazio — deixaria para trás uma escrita fora de `files:` que ninguém viu. A mensagem carrega o `needs-human` do `WAY_OUT`.
- **Antes da execução**, um `git status` ilegível recusa sem iniciar o Codex (como a leitura da base antes da execução já faz) e remove o diretório da execução, se já criado; a checagem de árvore suja vem antes de criar o diretório, então não há o que remover.
- **Depois da execução**, o payload mantém `guard` com `moved` acrescido de `worktree status unreadable (<erro>)`, `runDir`, `exitCode` e tokens, para o relatório.
- Contratos que não podem ser contrariados: `docs/standards/architecture/codex-pillar.md` §The git guard (uma leitura que falha é `GuardError`, nunca valor vazio) e `quenching/references/specs-execute/execution-delegation.md` (exit 2 com `outside` não vazio → `needs-human`).

### Assumptions

- O `git status` com `.git/index` truncado sai com código diferente de 0 (`fatal: .git/index: index file smaller than expected`), como o `## Problem` reproduziu — sustenta as provas de `## Validation`.

## Alternatives Considered

- **Um código novo (`codex-git-status`) em vez de `codex-git-guard` + `statusUnreadable`** — perdeu: o chamador e o padrão já ramificam em `codex-git-guard`; um código novo exigiria um ramo inteiro novo e, sem ele, cairia num exit 2 sem rota.
- **Pôr um marcador em `outside` (ex.: `<git status unreadable>`)** — perdeu: `outside` é uma lista de caminhos; um não-caminho ali seria nomeado ao humano como arquivo a limpar.
- **Tornar todo o `git()` tolerante estrito de uma vez** — perdeu: amplia o escopo além da decisão do épico e muda a semântica de `refs()` (HEAD destacado, sem stash) que hoje é estado; fica como achado.

## Open Decisions

- none — a política do épico 196 decidiu o comportamento (falhar fechado), e o formato do payload é decidido pela evidência do contrato existente (`codex-git-guard`, ramo `needs-human`).

## Risks

- Um `git status` que falha de forma transitória passa a recusar uma tarefa que antes seguia. ACCEPTED — recusar é o lado seguro sob `--dangerously-bypass-approvals-and-sandbox`, e o chamador cai em `needs-human`, não em perda de trabalho.
- O chamador que não conhece `statusUnreadable` e só olha `outside` vazio descartaria e reescreveria. Mitigação: sem `discard` no payload e `needs-human` na mensagem, e a tarefa 2.1 atualiza o contrato no mesmo PR.
