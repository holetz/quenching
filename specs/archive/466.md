## Problem

O VS Code permite que uma extensão contribua skills (`chatSkills`), registre servidores MCP sem depender do prefixo Python em `.mcp.json`, mostre estado na status bar (spec atual, slot, custo e cota, como fazem `claude-hud` e `opencode-quota` em outros harnesses) e ofereça uma visão de slots. Também há plugins de agente, instaláveis por deep link. A ADR 0017 aposentou a distribuição por plugins em favor do `cq deploy`, então falta avaliar o que uma extensão acrescenta sem virar uma segunda superfície, e quais extensões de terceiros (GitHub Pull Requests, gerenciadores de worktree) o fluxo deveria só recomendar.

Por que agora: a bancada da 452 mediu o que o cliente recebe e confirmou, no Linux, que ele lê as skills, os agentes, os hooks e o MCP deployados (H1, H2 e H4); a 460 adiou a extensão para esta avaliação. Sem ela, o épico 453 fecharia com a pergunta aberta. A decisão precisa separar o que o cliente já lê do que só uma extensão desenha — e o preço de manter essa extensão.

## Proposal

- Um registro de decisão (ADR 0021) declara que o quenching não publica extensão nem plugin de agente para o VS Code: a superfície deployada, o built-in de worktrees do cliente e as tarefas do workspace cobrem o fluxo; a status bar fica aceita como lacuna de apresentação, com o gatilho que reabre a decisão.
- Um guia de uso (`docs/how-to/work-in-vs-code.md`) documenta o cliente VS Code + GitHub Copilot: o que ele lê, as tarefas de zero token, a projeção dos slots, o fluxo de worktree do próprio cliente e a recomendação de terceiros.
- O artefato `vscode-extension-evaluation.md` carrega a matriz das candidatas (status bar, MCP provider, `chatSkills`/plugin, GitHub Pull Requests, gerenciador de worktree) com a fonte e a data de cada leitura, o inventário instalado e os números da marketplace.
- A sonda H9 passa a reportar ids únicos de extensão e diretórios de versão, em vez de contar diretórios de versão como se fossem extensões.
- O README apresenta o VS Code + GitHub Copilot como cliente da superfície e aponta o guia.

## Out of Scope

- Construir, empacotar ou publicar uma extensão do VS Code ou um plugin de agente: nada em `integrations/`, nenhum publisher, nenhum VSIX, nenhuma entrada nova no lockstep de release.
- Implementar a status bar; a lacuna é aceita, e o `## Open Decisions` nomeia a evidência que a reabre.
- Instalar ou configurar as extensões de terceiros recomendadas; o fluxo recomenda, a pessoa instala.
- Um `--harness copilot` ou qualquer modo de deploy por cliente: o invariante do épico 453 e a H13 da 452 continuam valendo; o cliente lê a camada existente.
- Medir ao vivo o comportamento das extensões recomendadas; a fonte é a documentação do cliente, datada no artefato, e as metades ao vivo da 452 que já foram medidas.
- As metades ainda abertas do épico (455, 462, 464, 465) e a sétima onda (488 a 492); esta avaliação lê a evidência mesclada ou publicada e não depende delas.

## Design

### A decisão

O quenching **não publica** extensão do VS Code nem plugin de agente nesta rodada. A superfície que o cliente já lê cobre skills, agentes, hooks, MCP, regras por caminho, settings e tarefas; o built-in de worktrees do cliente cobre criar, abrir, comparar, migrar e apagar; a projeção `cq git worktree workspace` cobre o pool. A única capacidade que só uma extensão desenha é a status bar persistente (spec atual, slot, custo e cota), e ela é **apresentação**, não um fluxo que o cliente não alcança. O custo de uma extensão é uma segunda superfície de release: publisher, VSIX, harness de teste do editor, lockstep e um dono de release — sem uma demanda medida que o pague.

O critério da avaliação é o da H9: uma candidata só passa se cobre um fluxo que o quenching não alcança **e** não vira uma segunda superfície. Nenhuma das cinco passa nos dois critérios; a status bar passa no primeiro e falha no segundo, e fica registrada como lacuna aceita, com gatilho.

A sonda passa a reportar `count` (ids únicos), `directories` (diretórios de versão) e `installed` (ids), e a observação nomeia os dois números. ### A recomendação de terceiros

- **GitHub Pull Requests** — oficial, 37.641.537 instalações, versão 0.183.2026112504 em 2026-11-25; é a UI de revisão dos PRs que `cq git pr create` abre. Recomendada, opcional.
- **Built-in de worktrees** — a rota do pool: Source Control Repositories → Worktrees; o `cq git worktree workspace --write` abre os slots ativos num `.code-workspace`. Nenhuma extensão necessária.
- **Git Worktree Manager** — não recomendada para o pool: duplica o built-in e um `remove` forçado pode apagar um slot livre ou held, vencendo o lock que protege o `.venv` (460). Fora do pool, é escolha da pessoa.

### Contratos que o desenho não contradiz

- **ADR 0017** — o quenching chega ao repositório só pelo `cq deploy`; uma extensão de editor não instala superfície no repositório, e a decisão não a publica.
- **`deploy-mode.md`** — as sementes `.vscode/settings.json` e `.vscode/tasks.json` são do alvo e opt-in por `shared.workspace.vscode`; a extensão não as substitui.
- **`plugin-configuration.md`** — `shared.workspace.vscode` e `shared.projections` continuam as únicas chaves; nenhuma chave nova.
- **`versioning-release.md`** — uma extensão seria mais um artefato de release; a decisão evita o lockstep novo.
- **455** — o cliente lê as duas cópias de skills e desduplica; a publicação única é da 455, e a extensão não é necessária para isso.
- **460** — o lock livre do slot protege o pool; o guia nomeia o risco de um cliente que force a remoção, e a recomendação evita um gerente que o faça.
- **452** — a sonda é a fonte do inventário; a correção do H9 é uma medição mais honesta, não uma mudança de hipótese.
- **Épico 453** — nenhuma ramificação do deploy por cliente; a decisão não cria `--harness copilot`.

## Alternatives Considered

- **Construir agora uma extensão fina e somente-leitura (status bar, provider MCP e visão de slots)** — o único acréscimo real é a status bar; o resto duplica o que o cliente já lê e o que o deploy já escreve. Uma extensão é uma segunda superfície de release (publisher, VSIX, teste do editor, lockstep) sem demanda medida. Fica como gatilho no `## Open Decisions`.
- **Publicar um plugin de agente por deep link, com skills, agentes e MCP** — é uma segunda cópia da superfície, com trust prompt e release próprio; a ADR 0017 aposentou essa distribuição, e a 455 já publica as skills no diretório que o cliente lê.
- **Recomendar um gerenciador de worktree de terceiros para o pool** — o built-in do cliente cobre criar, abrir, comparar, migrar e apagar; um segundo gerente pode forçar a remoção de um slot e vencer o lock livre da 460, apagando o `.venv` que o pool existe para preservar.
- **Não documentar o cliente e deixar a recomendação só no ADR** — o ADR é para quem mantém; quem usa o VS Code precisa do guia com as tarefas, os slots e as extensões, e o README fica incompleto sem o VS Code na lista de clientes.
- **Criar um `--harness copilot` ou um modo de deploy por cliente** — o invariante do épico 453 e a H13 da 452 recusam; o cliente lê a camada que o deploy já escreve.

## Open Decisions

- **A status bar no VS Code fica aceita como lacuna de apresentação, não resolvida.** Decide-se por demanda medida: uma segunda solicitação de um alvo, ou o uso repetido de `cq specs status`/`cq git worktree slots` no terminal, abre uma spec de `integrations/quenching-vscode` somente-leitura, instalada à parte e nunca pelo `cq deploy`. Nenhuma spec é criada agora; a evidência que reabre é a demanda, não a existência da API.

## Risks

- **As fontes externas envelhecem** — a versão do cliente, as APIs e os números da marketplace são de 2026-11-25; o artefato carrega a data e a consulta, e uma mudança é uma nova medição, não uma reescrita. (Mitigação: o artefato é datado e a validação fixa os números.)
- **Um gerenciador de worktree de terceiros pode remover um slot com `-f -f`** — o lock livre da 460 não vence um force remove; o guia recomenda o built-in e nomeia o risco. ACCEPTED — o lock protege o fluxo normal, e o force remove é uma ação explícita de quem opera.
- **O guia pode prometer uma metade não medida** — H6, H7, H11 e H12 continuam `unmeasured-live`; o guia separa o que foi medido do que é esperado e nomeia o protocolo, e a validação não trata `unmeasured-live` como passe.
- **O README passa a listar o VS Code e um alvo sem `shared.projections`/`shared.workspace.vscode` não recebe `.github/` nem `.vscode/`** — a frase fala do que o cliente lê da camada e da ponte, e o guia nomeia as chaves opt-in; a promessa não inclui as projeções que o alvo não declarou.
- **A decisão de não construir pode ser lida como "nunca"** — o ADR nomeia o gatilho e a forma admitida (integração opcional, somente-leitura, fora do deploy), e o `## Open Decisions` repete a regra de decisão.
