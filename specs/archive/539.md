## Problem

Achado reproduzido da revisão do épico 524 (autopilot 2026-11-25), sobre o merge dacb70f9b (PR #537, spec 520). Com quenching/assets/modules.json presente (repositório-fonte), tree.py:557 grava SOURCE_DERIVED no hash de cada arquivo hospedado, e cli.py:302 `_edited` devolve False quando o registro é SOURCE_DERIVED — então cli.py:445 (saída da seleção) e cli.py:827 (--remove) classificam um arquivo possuído editado à mão como `delete` em vez de `edited`. Contradiz cli.py:818 ("an edited one is kept and reported") e docs/standards/architecture/deploy-mode.md:120 ("an `edited` file is **kept** and reported ... unless `--force`"); o parágrafo novo deploy-mode.md:99-100 só cobre o caminho de update, e o teste novo também.

Consequência: baixa — só no repositório-fonte, onde os arquivos são rastreados e o git os recupera; mas o contrato documentado mente. Correção esperada: no caminho delete/--remove, comparar bytes com a fonte quando o registro é SOURCE_DERIVED (como o --check já faz) ou documentar a exceção; teste para saída da seleção e --remove.

## Proposal

No repositório-fonte, o registro `"source"` não guarda os bytes que o último deploy escreveu, mas o commit guarda: no caminho de exclusão (arquivo possuído que sai da árvore e `--remove`), `_edited` passa a comparar o arquivo com o `HEAD` do git quando o registro é `SOURCE_DERIVED`. Um arquivo com mudança não commitada (ou não rastreado) é `edited` e fica, como deploy-mode.md:120 promete; um arquivo igual ao `HEAD` sai como antes. O caminho de update (deploy-mode.md:99-100) não muda: lá a fonte é a verdade e o `--check` já compara bytes.

## Out of Scope

- O caminho de update no repositório-fonte — continua `update`, como deploy-mode.md:99-100 documenta.
- Alvos comuns (com sha256 no manifesto) — o três vias deles já está certo.
- Reconstruir a árvore de um módulo desselecionado para comparar com a fonte — os arquivos que saem da árvore no repo-fonte são justamente os que não têm mais fonte.

## Impact

### Standards this spec will write into docs/standards/

- `docs/standards/architecture/deploy-mode.md` — o três vias e §Remove dizem que, no repositório-fonte, o caminho de exclusão lê a edição contra o `HEAD` do git

### Product code this spec expects to touch

- `quenching/assets/bin/quenching/deploy/cli.py` — `_edited` ganha o caminho de exclusão contra o `HEAD`; `plan` (saída da seleção) e `remove_plan` o usam
- `.agents/quenching/assets/bin/quenching/deploy/cli.py` — espelho regenerado pelo deploy
- `quenching/tests/test_deploy.py` — provas da saída da seleção e do `--remove` no repositório-fonte

### Process surface this spec expects to touch

- none — nenhum corpo de comando nem reference muda; só o espelho do código é regenerado

## Validation

- Reproduzido no develop (2026-11-25), por leitura: cli.py:302 devolve `False` para `SOURCE_DERIVED` e cli.py:445/:827 classificam como `delete`; tree.py:557 grava `"source"` quando `quenching/assets/modules.json` existe.
- Teste: num alvo com `quenching/assets/modules.json`, depois de commitar o deploy, um arquivo possuído editado à mão sai em `--remove` como `edited` (`kept`) e sobrevive ao `--remove --write`; um não editado sai como `delete`.

## Design

### Mapa de dependências (2026-11-25, varredura inline: executor sem Task)

| Arquivo | Relação | O que quebra se mudar |
| --- | --- | --- |
| `quenching/assets/bin/quenching/deploy/cli.py` `_edited` | chamado por `plan` (:438 update, :445 saída) e `remove_plan` (:827) | o caminho de update não pode mudar (deploy-mode.md:99-100) |
| `quenching/assets/bin/quenching/deploy/tree.py:557` | grava `SOURCE_DERIVED` via `self_hosted` | nada — só lido |
| `quenching/tests/test_deploy.py:254` | prova do update na fonte | deve continuar verde |
| `docs/standards/architecture/deploy-mode.md:90-100,115-124` | contrato do três vias e do Remove | texto ajustado |

### Decisão
- `_edited` ganha um parâmetro `deleting: bool = False`. Com `deleting` e registro `SOURCE_DERIVED`, pergunta ao git: `git -C <target> status --porcelain -- <rel>` com saída não vazia (modificado, staged ou não rastreado) → `edited`. Git ausente ou alvo fora de repositório → `False` (comportamento anterior). O update continua chamando sem `deleting`.
- O `HEAD` é o registro honesto no repositório-fonte: o que está commitado o git recupera; o que só está no disco não, e é isso que o contrato protege.

### Assumptions
- O repositório-fonte é sempre um checkout git (`self_hosted` exige `quenching/assets/modules.json` rastreado) — Design §Decisão.

## Alternatives Considered

- Documentar a exceção (o repo-fonte apaga editados) — rejeitada: uma edição não commitada se perde de verdade; o git só recupera o commitado.
- Comparar com os bytes da fonte — rejeitada para a saída da seleção: o arquivo saiu da árvore porque não tem mais fonte; para `--remove` exigiria construir a árvore inteira.
- Tratar todo `SOURCE_DERIVED` como `edited` na exclusão — rejeitada: travaria toda remoção legítima atrás de `--force`.

## Open Decisions

- none — o desenho decide pelo HEAD do git; nenhuma escolha depende do humano

## Risks

- Um arquivo que o próprio deploy acabou de escrever e ainda não foi commitado sai como `edited` (fica) na exclusão — lado seguro; o `--force` o leva.
- Uma chamada `git status` por arquivo candidato à exclusão — só no repo-fonte e só para os que saem, custo desprezível.

- Execução completa (2/2): `_edited(deleting=True)` lê `git status --porcelain` contra o HEAD quando o registro é `"source"`; deploy-mode.md atualizado. Falta só o conclude.
