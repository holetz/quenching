## Problem

The `proof` align reports `pf-unlayered` and stops, because declaring a layer is a taxonomy
judgement it must not make. That is right, and it leaves the front with a gap in exactly the place
its whole model depends on: **nothing helps a human declare a layer, and declaring one correctly
touches five things at once.**

A layer is not a directory. It is a directory, plus a marker registered in
`[tool.pytest.ini_options].markers`, plus an entry in the collection hook that derives that marker
from the path, plus a declared reach and wall-clock budget, plus a home in the fixture library. Miss
any one and the front reports a finding: an unregistered marker is `pf-unmarked`, a directory the
hook does not know is `pf-unlayered` for every test inside it, an empty one is `pf-empty-layer`.
Asking a human to get five coupled edits right by hand, and then verifying that they did, is the
same defect the `ops` front closed by shipping a mold.

The second gap is the front's own registry. `proof-front-contract` declares a generated `README.md`
describing what each layer proves, and no command writes one. The measured target has no
`tests/README.md` and no `tests/CLAUDE.md` at all — while its `scripts/` folder has both — so
nothing anywhere says what its 24 test packages are for, which is how a suite with 1,495 tests
becomes a suite nobody can navigate.

## Proposal

**`cq proof readme --write|--check`** — generate the proof root's `README.md` from the inventory,
into a `BEGIN/END GENERATED` block under `/docs/standards/architecture/generated-listings.md`'s
existing rules. One section per declared layer: what it proves, what it may reach, its budget, its
marker, its test count, and its fixture module. Prose outside the block is never touched.
`--check` compares without writing.

**`/quenching:proof:layer:new`** — mint ONE layer. It asks four things, and each answer binds part of
the contract:

| It asks | It binds |
| --- | --- |
| what this layer proves, in one line | the README section and the marker's registered description |
| what it may reach — nothing · the tree · a session · the workspace | the declared reach, and which fixtures it may use |
| its wall-clock budget | the declared budget, and whether the layer belongs in the fast gate |
| whether existing tests move into it | the migration list, proposed and never applied unasked |

Then it performs the five coupled edits as one unit: creates the directory, registers the marker with
its description, adds the path→marker rule to the collection hook (installing the hook if the target
has none), creates the layer's fixture module in the library, and regenerates the README. It closes
by running `cq proof doctor` so the new layer is proven conformant before the command reports.

The fourth question is the one that keeps this command from becoming a migration tool. It produces a
**proposed** list of tests whose current location suggests they belong in the new layer, with the
count and the paths. Moving them is the human's own confirmation, taken separately, and declining
leaves a layer that is legitimately empty until somebody fills it — which is why
`pf-empty-layer`'s severity was left as a stated question rather than an assumed answer.

## Out of Scope

- **Deciding a repository's layer taxonomy.** The command mints the layer a human named; it proposes
  no set and it does not infer one from existing directories.
- **Moving tests unasked.** The migration list is a proposal with its own confirmation.
- **Writing tests, or filling a new layer.** An empty new layer is the normal outcome of minting one.
- **Retiring a layer.** Removing a layer means deciding what happens to its tests, which is a
  different judgement with a different blast radius.
- **Non-pytest runners.** The five edits are stated over pytest constructs.
- **A second generated document.** One README, one block, one hash.

## Validation

```bash
cd plugins/quenching
python3 assets/bin/cq --root . proof readme --check --json
python3 assets/bin/cq --root . proof doctor --json
python3 assets/bin/cq --root . components lint --json

```

Verified when:

1. `cq proof readme --write` run twice is byte-identical the second time, and `--check` on the result
   exits `0`.
2. Prose outside the generated block survives regeneration byte for byte, proven by a fixture whose
   surrounding text includes a hand-written section and a heading shaped like a generated one.
3. A layer minted through the body passes `cq proof doctor` with zero findings **on a target that had
   no collection hook**, proving the hook installation path.
4. A layer minted on a target that **already has** a hook adds its rule and leaves every existing rule
   untouched, proven by a byte comparison of the other rules.
5. The migration proposal is never applied without its own confirmation — proven by a run that
   declines it and leaves every test file's path unchanged.
6. The five edits are atomic in effect: a mint interrupted after the directory is created leaves the
   target with no partially-registered layer, or leaves one the doctor names precisely.
7. `pf-empty-layer` does not fire on a layer minted in the same session, per its resolved severity.

## Design

**Why the five edits are one command and not five.** They are coupled by the contract: a directory
with no marker rule makes every test inside it `pf-unlayered`; a registered marker with no directory
is dead configuration. A human doing this by hand gets a partially-declared layer, and the front then
reports three findings that all describe one incomplete action. Performing them together is what
makes the contract satisfiable in one step.

**Why the collection hook is installed rather than assumed.** The contract's rule 1 — the directory
declares the layer, the marker is derived — has no meaning without a hook that derives it. On a
target with no hook, minting the first layer is also the moment the mechanism arrives, and shipping
it as a template means every adopting repository gets the same one rather than each writing its own
subtly different version.

**Why the migration proposal exists but is not applied.** Minting a layer into an existing suite and
leaving it empty is technically correct and practically useless — the tests that belong in it already
exist somewhere. But moving a test file changes what runs in which gate, and on the measured target
the plausible proposal would move hundreds of files. Proposing with a count and paths, and applying
only on a separate confirmation, is the same restraint the align applies to its judgement band.

**Why `pf-empty-layer`'s severity resolves here.** The contract deliberately left it as a stated
question. This spec answers it, because minting a layer produces exactly that state on purpose: an
empty layer immediately after a mint is the intended outcome, and an empty layer months later is
forgotten scaffolding. The resolution keys on evidence the front already has — whether the layer is
declared with a reach and a budget, and whether the README describes what it proves — rather than on
a timestamp.

**Why the README is generated and the layer's purpose is authored.** The one-line answer to "what
does this layer prove" comes from the human at mint time and is stored in the marker's registered
description, which is where pytest already keeps it. The generator reads it back. Nothing is written
twice, and `--strict-markers` makes the description a field the test runner itself validates.

**Why `--check` and not a separate verb.** Same reasoning as the `ops` registry: the align, the
doctor and a human all run the same code, and one flag on one subcommand keeps that honest.

## Alternatives Considered

- **Let the align mint layers as part of closing `pf-unlayered`.** Rejected: it is the taxonomy
  judgement the align exists not to make, and it would ask the four questions in the middle of a
  sweep.
- **Derive markers by convention without a hook** (for instance, requiring `test_unit_*.py` names).
  Rejected: it puts the layer in the filename, so moving a test between layers renames it, and it
  cannot express a layer that spans a subtree.
- **Ask the human to apply the five edits from a printed checklist.** Rejected under §Why the five
  edits are one command: a checklist produces partially-declared layers, which is what the front then
  reports three findings about.
- **Generate the whole `tests/README.md` rather than a block.** Rejected: a proof root's README
  carries real prose worth keeping — how to run one layer, what the session fixture costs, which
  tests need a workspace — and a generator that owns the file either destroys it or reimplements the
  block rule.
- **Apply the migration proposal by default and let the human revert.** Rejected: reverting a
  hundred-file move is not symmetric with declining it, and the align's judgement-band doctrine
  already settles this class of choice.

## Open Decisions

- **Whether README staleness gets its own code (`pf-readme-stale`) or is folded into an existing
  one.** The `ops` front minted `op-registry-stale` for the same job, which argues for symmetry;
  eleven codes is already a lot, which argues against. Resolved at task 1, and whichever way it goes
  the contract spec's published code list is amended rather than silently extended.
- **Where the layer's declared reach and budget are stored.** The marker's registered description can
  carry them as structured text, or they can live in `.claude/quenching.json` beside the layer list.
  Resolved at task 1 against which one `cq proof inventory` already reads.
- **Whether the mint offers to create the fixture library when the target has none.** Creating
  `fixtures/` is harmless; creating it and leaving it empty adds a directory nobody asked for.
  Resolved at task 3, with the bias toward creating it only when the layer's declared reach implies a
  fixture.
- **Whether the migration proposal is computed at all on a target with no declared layers.** With
  nothing to compare against, every test is a candidate. Resolved at task 3 by suppressing the
  proposal for the first layer minted in a repository and saying why.

## Risks

- **The collection hook is written into the target's `conftest.py`, a file the target owns.**
  *Mitigation:* the hook is added as a named block the generator can recognize, existing rules are
  byte-compared after the edit (validation item 4), and the mint runs `cq proof doctor` before
  reporting.
- **A partially completed mint leaves a half-declared layer.** *Mitigation:* validation item 6
  requires either atomic effect or a doctor finding that names the exact incomplete state — the
  front's own verifier is the recovery path, and the spec proves it works rather than assuming it.
- **The migration proposal can be confidently wrong.** A test's directory is weak evidence of what it
  proves. *Mitigation:* it is a proposal with paths and a count, never a default, and it is
  suppressed entirely for the first layer in a repository, where it would be pure guesswork.
- **`pf-empty-layer`'s resolution could make the code useless.** If an empty layer is never a finding,
  forgotten scaffolding never gets reported — and the measured target's empty `tests/workflow/` is
  exactly that. *Mitigation:* the resolution keys on the layer's declaration completeness rather than
  on emptiness alone, so an undeclared empty directory still fires and a freshly minted one does not.
