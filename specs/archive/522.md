## Problem

Achado reproduzido da revisão do épico 483 (autopilot 2026-11-25), sobre a 281 (PR #493). scripts/verify_repo.sh:40 grava o registro com `--scope "${TEST_SCOPE:-unknown}"`, mas quenching/assets/bin/quenching/config/ci.py:43-44 aceita o registro conferindo só head, dirty e exit — o campo `scope` nunca é lido. Um gate `QUENCHING_TEST_SCOPE=affected` (que pula piso de coverage, build do site e integrações: verify_repo.sh:204) autoriza o merge sob CI relaxado, enquanto a mensagem diz que "o gate local substitui o CI". test_gate_record.py grava scope affected e não há teste que o recuse.

Consequência: sob CI relaxado o merge é autorizado por um gate parcial. Correção esperada (ESTREITA a aceitação): exigir scope full (e recusar unknown) em ci.py, com teste que recusa affected.

## Proposal

- Sob `shared.ci.enforce` relaxado, `cq git pr merge` só aceita o registro de gate (`.quenching/gate/record.json`) cujo `scope` é `full`; um registro `affected`, `unknown`, ausente ou de qualquer outro valor não prova nada (`proven_exit` devolve `None` → `gate-proof-required`).
- A mensagem de recusa diz que o gate que substitui o CI é o gate completo (`QUENCHING_TEST_SCOPE=full`).
- Um teste recusa `affected` e `unknown` e um teste de leitura da referência de configuração cita o escopo exigido.

## Out of Scope

- Mudar `scripts/verify_repo.sh` — ele já grava `--scope "${TEST_SCOPE:-unknown}"` e `QUENCHING_FULL_GATE=1` já força `full`; nada nele precisa mudar para estreitar a aceitação (o épico 524 só o permite se necessário).
- Subir `GATE_RECORD_SCHEMA` — o campo `scope` já existe no schema 1; registros antigos sem `scope` passam a ser recusados, que é o estreitamento pedido.
- Mudar `judge()` ou os valores de `shared.ci.enforce` — o problema é só a leitura do registro.

## Impact

### Product code this spec expects to touch

- `quenching/assets/bin/quenching/config/ci.py` — `proven_exit` exige `scope == "full"`; `proof_message` nomeia o gate completo
- `quenching/tests/test_gate_record.py` — testes que recusam `affected`, `unknown` e registro sem `scope`

### Process surface this spec expects to touch

## Design

### Mapa de dependências

### Decisão
- O registro só prova o gate quando `scope == "full"` — regra durável: o gate que substitui o CI é o mesmo que o CI roda; um subconjunto (`affected`) pula piso de coverage, site e integrações e nunca autoriza um merge sem CI. Qualquer outro valor, inclusive ausente, falha fechado.
- A verificação fica em `proven_exit` (o leitor), não em `judge`: o contrato de `proven_exit` já é "None quando nenhum registro prova", e o chamador em `pull.py` não muda.

### Assumptions
- Nenhum consumidor depende de `proven_exit` aceitar `affected` (grep: só `pull.py:202` e testes) — Design/Risks.

## Alternatives Considered

- Recusar só `affected` e aceitar `unknown` — perdeu: `unknown` é um gate que saiu antes de fixar o escopo, ou um escritor sem `--scope`; aceitar seria falhar aberto.
- Mudar o `verify_repo.sh` para não gravar registro em `affected` — perdeu: o registro com `exit` e `scope` serve de prova para outros leitores; estreitar no leitor é a mudança mínima e não mexe no script do gate.

## Open Decisions

- none — o épico 524 fixou o desenho (exigir `full`, recusar `unknown`/`affected`) e o código responde o resto.

## Risks

- Um merge autônomo sob CI relaxado que hoje passa com `affected` passa a ser recusado até rodar o gate completo — ACCEPTED — é exatamente o estreitamento pedido; a mensagem de recusa diz o que rodar.
- Registros antigos sem `scope` deixam de provar — ACCEPTED — basta rodar o gate de novo.
