## Overview

Hoje o fluxo separa integração de publicação: as specs mergeiam numa branch `develop` e o release é um merge manual `develop → main`. Este ajuste elimina a branch de integração: cada spec abre um PR direto na branch primária (`main`), onde a revisão já acontece. O release vira um ato deliberado local na `main` — bumpar, tagear e publicar o que ela acumulou — sem merge e sem segunda branch. Uma branch a menos, uma etapa a menos, nada de revisão se perde.
## Problem

O fluxo de git deste repositório hoje passa por uma branch de integração intermediária (`integrationBranch: develop`), contra a qual o ciclo de specs abre os PRs, e ancora o release numa `releaseBranch: main` separada — uma etapa de meio do caminho que não adiciona revisão nem segurança à entrega. O fluxo oficial deve ser abrir o PR diretamente contra a branch primária (`main`), tornando `integrationBranch` e `releaseBranch` desnecessárias no `.claude/quenching.json` e em todo o ciclo.

## Proposal

- O ciclo de specs — `/quenching:specs:cycle`, `/quenching:specs:execute`, `/quenching:specs:execute-queue` — abre PRs diretamente contra a **branch primária** (`origin/HEAD`, degradando para `init.defaultBranch` e `main`), nunca contra uma `integrationBranch`.
- `integrationBranch` e `releaseBranch` deixam de existir no `.claude/quenching.json` e em toda a superfície que as lia: `specs/config.py`, `release.py`, `git/stale.py`, `doctor.py`, os standards e o glossário.
- A cadeia de inferência de `base` de uma spec não carimbada passa a ser `origin/HEAD → init.defaultBranch → main`, sem o degrau `declared integrationBranch`.
- O ato de publicar vira um release **deliberado local na branch primária**: `cq specs release <version>` bumpe, commita e tageia na `main` e faz push — sem merge `develop → main`, sem segunda branch de longa duração.
- A mitigação contra o hábito sobrevive: quando a `main` carrega exatamente **um** PR mergeado desde a última tag, o comando de release pergunta se aquilo é uma release ou um hábito.
- `branching.md`, `plugin-configuration.md`, `versioning-release.md` e o glossário descrevem o fluxo de **uma branch só**.

## Out of Scope

- **Migração de PRs, merges ou histórico existentes**: o que já foi concluído fica como está — esta spec não reescreve o passado, só o fluxo a partir de agora.
- **Mudança da branch default do GitHub**: `main` continua sendo a default e o canal de publicação.
- **Os backends de specs** (`files`, `github`, `azure-boards`): esta spec mexe no fluxo de git, não em como uma spec é armazenada.
- **Renomear branches em repositórios-alvo já instalados**: a remoção das chaves é `breaking` para quem as declarou, e o upgrade exige ação humana — documentada na tag, nunca aplicada em silêncio.
- **A política de versionamento** (patch/minor/major): continua sendo julgamento humano conduzido pelo comando de release.

## Design

1. **Alvo dos PRs do ciclo — a branch primária.** `infer_base_branch` e `cq git base` perdem o primeiro degrau (`declared integrationBranch`) e passam a resolver `origin/HEAD → init.defaultBranch → main`. Alternativa pesada: manter o degrau com default `main` — descartada, porque o próprio degrau é a chave que esta spec remove. Contrato vinculante: a cadeia já vive em `plugins/quenching/assets/bin/quenching/specs/config.py` (§`infer_base_branch`) e `git/base.py`; só a origem muda.
2. **Release deliberado local na main.** O guard `sp-release-wrong-branch` passa a exigir a **branch primária** em vez da integration branch; o bump+tag acontece na `main` e o push a publica. A regra de `versioning-release.md` se preserva: o bump é contido na branch publicada e a tag aponta para ele. Alternativa pesada: release por PR — descartada: a publicação permanece um ato local deliberado, porque a revisão de cada spec já aconteceu no PR de entrada.
3. **A pergunta "release ou hábito".** O análogo sem `develop`: contar PRs mergeados na `main` desde a última tag — um PR só → perguntar, dois ou mais → publicar. A mitigação de `branching.md` §O gatilho é a demanda sobrevive, só muda a fonte do acumulado.
4. **Remoção das chaves.** `specs/config.py` deixa de reconhecer/nomear `integrationBranch`/`releaseBranch`; `git/stale.py` perde a branch protegida de release (a primária já é `base`); `doctor.py` deixa de exibi-las; `plugin-configuration.md` e o glossário as removem da documentação. `releaseBranch` tem um único consumidor fora do release — `stale.py` — que volta a depender só de `base`.

## Alternatives Considered

- **Forma B — PR na primária por padrão, chaves mantidas como override opcional.** Rejeitada: o dono declarou que as chaves "não são mais necessárias"; manter o fluxo de duas branches como opção preserva exatamente o processo que esta spec existe para eliminar.
- **Release por PR** — cada release bumpe num branch de release e passa por revisão antes do merge. Rejeitada: a publicação local deliberada é o que permite "publico agora" sem depender de revisão externa; a revisão de cada mudança já aconteceu no PR de entrada.
- **Status quo — manter develop/main.** Rejeitado no go/no-go: a branch de integração não adiciona revisão (a revisão vive no PR) nem segurança (a `main` já é o canal deliberado); custa uma branch a mais e um merge manual por release.

## Open Decisions

- none — nenhuma decisão ficou em aberto: o destino da branch `develop` existente é deixá-la órfã (não-apagar, fora de escopo) e o mecanismo do novo release (bump+tag+push na main com a pergunta "release ou hábito") está definido no Design; ambas decididas nesta spec.

## Risks

- Breaking para repositórios-alvo que declararam `integrationBranch`/`releaseBranch` — o config deixa de ler as chaves. Mitigação: tag `breaking` aplicada na captura e upgrade documentado na release que carregar esta spec.
- Regressão do verbo de release — o bump/self-check quebra silenciosamente. Mitigação: os testes existentes e o self-check `rev-parse <versão>^{commit}` permanecem no novo fluxo.
- Specs em flight com `base: develop` carimbada — seguiriam uma branch que deixa de ser usada. Mitigação: o registro `branch.base` é write-once e segue em vigor; a transição não reescreve nenhum registro.
- A branch `develop` fica órfã após a mudança. Mitigação: documentado no `branching.md` reescrito; apagá-la é decisão humana fora de escopo.
- Redação inconsistente nos citadores (cadeia de base em 5 lugares, PR route em 4). Mitigação: verificação `end-of-plan` + revisão do PR; os greps de ausência cobrem os citadores.
