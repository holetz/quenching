## Problem

`quenching/assets/bin/quenching/toolchain/cli.py:27-30` and `:46-48`: `_human_doctor` and `_human_status` print only root, applicability and artifacts, never the findings.

Reproduced (autopilot 2026-11-21 round 4, origin/main c29ba1e46): a node package.json with `eslint: ^9.0.0` → `cq toolchain doctor` prints `toolchain doctor — … (applicable); artifacts: package.json`, rc=1; with `--json` → `findings: [tc-tool-unpinned … eslint]`. `cq toolchain status` → `controls: 4 present, 0 missing`, rc=1.

Consequence: a clean-looking line with a failing exit; whoever runs it in a terminal or a gate has no clue what to fix. Fix direction: one line per finding (code, subject, remedy), like `proof doctor`, with a test.

## Proposal

- A saída humana de `cq toolchain doctor` lista cada finding em uma linha própria: severidade, caminho, mensagem e código (`tc-…`), no mesmo formato de `cq proof doctor`; sem findings, imprime uma linha `OK — no findings`.
- A saída humana de `cq toolchain status` lista os mesmos findings, uma linha cada, depois da linha de cabeçalho e antes do resumo de controles.
- O cabeçalho de `doctor` passa a carregar a contagem de findings, de modo que exit 1 nunca acompanha uma saída que pareça limpa.
- O payload `--json` e os códigos de saída (0 limpo, 1 com findings, 2 recusa) ficam inalterados.
- Um teste em `quenching/tests/test_toolchain.py` prova que a saída humana de `doctor` e de `status` nomeia o código e o caminho de cada finding (o caso reproduzido: `eslint: ^9.0.0` em `package.json` → `tc-tool-unpinned`).

## Out of Scope

- Um campo `remedy` novo no `Finding` do toolchain — o modelo comum (`common/front.py`) não o tem e a `message` de cada check já diz o que está errado; acrescentar campo mudaria o contrato JSON de todos os fronts.
- A detecção dos checks (`toolchain/probe.py`, `checks.py`, `inventory.py`) — é a spec 2228, onda 2 do épico 2224.
- Unificar o renderizador humano entre fronts (proof, delivery, ops) em `common/` — refatoração transversal sem bug que a peça; este conserto imita o formato de `proof doctor` localmente.
- Os corpos de comando `/quenching-toolchain` — leem `--json`, não a saída humana.

## Design

- **Formato da linha de finding = o de `proof doctor`.** `  [<severity>] <path> — <message> (<code>)`, com `-` quando o finding não tem caminho. Evidência: `quenching/assets/bin/quenching/proof/cli.py:56-63` já é o formato que o operador lê em outro front; repetir o formato mantém um só modo de ler findings no terminal.
- **Regra durável: uma saída humana que sai com código 1 por findings nomeia cada finding.** Exit não-zero sem dizer o quê é o defeito; o cabeçalho de `doctor` carrega a contagem.
- **`status` reaproveita o mesmo renderizador de linhas** — um helper `_finding_lines(findings)` em `toolchain/cli.py`, usado pelas duas funções; `status` mantém `summary_line(controls)` como última linha.
- **JSON e exit codes intocados** — `emit` recebe o mesmo payload; só a string humana muda. Nenhum leitor de máquina é afetado.
- **Contratos vinculantes:** `common/front.py` (`Finding.as_dict`: `code`, `severity`, `message`, `path` opcional, `band` opcional) — o renderizador lê só essas chaves, com `.get` para as opcionais.
