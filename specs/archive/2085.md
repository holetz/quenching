## Problem

Agents and people on the platform need to read specs and backlog without shelling out to `cq`, from any harness and from the web UI. Ship the quenching specs service's MCP read surface — list, status, show, section read, next and epic progress — as a second port of the same rules core `cq specs` runs on, in the same process, never reimplementing the store. The same server runs over stdio locally, with no infrastructure, and over streamable HTTP on forge; quenching never requires forge for it. A tool result never carries a whole spec: reads go by section and by task, as `cq specs section` and `show --task` already do, so no answer crosses the harness's MCP output ceiling (Claude Code truncates around 25,000 tokens; the largest quenching spec is about 32,000). The stdio port comes first. References: Backlog.md's MCP server and `microsoft/azure-devops-mcp`'s tool shapes (epic §Reference projects).

Formerly holetz/tempering#1.

Member S4 of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent).

## Proposal

- `cq specs mcp` starts a stdio MCP server (JSON-RPC 2.0, newline-delimited, stdlib only) that is a second port of the same core `cq specs` runs on: every tool dispatches in-process through `quenching.specs.commands.cli.main`, so the backend, CAS, refusals and exit codes are the CLI's, and the server holds no store logic of its own.
- Six read-only tools exist: `specs_list`, `specs_status`, `specs_show`, `specs_section`, `specs_next` and `specs_epic_progress`. No tool writes, and no write verb is reachable from the server.
- No tool answer carries a whole spec or an unbounded listing: reads go by section and by task, listings are paged, and any answer above the output ceiling is cut with an explicit `truncated` marker instead of crossing the harness limit.
- The plugin registers the server through a `.mcp.json` at its root, shipped by `quenching` and by the `quenching-specs` module, so enabling the plugin makes the tools appear with no forge and no infrastructure.
- The server is documented in the plugin README (tools, arguments, size policy, the read-only guarantee), and the mirrors carry it.

## Out of Scope

- Streamable HTTP and forge hosting: this spec is the stdio port only; the HTTP port is a later member and must reuse the same tool table.
- Any write tool (`section --write`, `record`, `task`, `discover`): the write surface belongs to 2086.
- Swapping `Bash(cq specs ...)` for the MCP tools in agents and commands, and any `allowed-tools`, `tools:`, grant, hook, script or CI change: the 1:1 swap is authorized but needs the human's review in the PR before merge, so no member of this round does it; every other widening goes to epic 2045.
- Azure and GitHub adapters: the server sits on whatever backend `open_backend` resolves; adapter work is 2083 onward.
- Using the third-party `mcp` Python SDK: it is not installed and the plugin ships no third-party dependency.

## Design

**Decision 1 — one core, in-process dispatch.** Each tool builds the argv of the CLI verb it mirrors (`list --lean`, `status --spec`, `show --task`, `section`, `next`, `status --epic`) with `--json`, calls `quenching.specs.commands.cli.main(argv)` with stdout and stderr captured, and returns the parsed JSON. The server owns protocol, argument validation, paging and the size ceiling, and nothing about the store. This is what makes it "a second port of the same core": a rule fixed in the CLI is fixed in the server. Alternatives: (a) shell out to `cq` per call — a second process per read and a PATH dependency, rejected; (b) call `open_backend` directly as `portal.py` does — a parallel read path that can drift from the CLI verbs, rejected.

**Decision 2 — hand-rolled stdlib JSON-RPC.** The plugin ships no third-party dependency and the `mcp` SDK is not installed. The server implements `initialize` (echoing a supported protocol version, declaring only the `tools` capability), `notifications/initialized`, `ping`, `tools/list` and `tools/call`. stdout carries protocol lines only; every verb runs under `redirect_stdout`/`redirect_stderr`, diagnostics go to stderr. A tool failure is a result with `isError: true` and the CLI's refusal `code`, never a JSON-RPC protocol error.

**Decision 3 — size is a contract.** Claude Code truncates MCP output near 25,000 tokens and the largest spec is about 32,000. Hence: no `--full` anywhere; `specs_section` takes headings (and optional `moment`), `specs_show` takes task ids or returns the map; `specs_list` and `specs_next` page with `limit` (default 50, max 200) and `offset` over the already-lean payload, reporting `count`, `returned`, `nextOffset`; and a final guard cuts any serialized answer above 60,000 characters (about 15,000 tokens) with `truncated: true` and a `hint` naming the narrower call. The guard is the last line of defence and is tested separately from the paging.

**Decision 4 — read-only by construction.** The tool table is a closed map from tool name to a fixed verb; there is no generic "run cq" tool and no argv passthrough, so a prompt-injected argument cannot reach a write verb. Argument values are passed as separate argv elements, never through a shell.

**Decision 5 — registration.** `.mcp.json` at the plugin root declares one server, `specs`, with `command: python3` and `args: ["${CLAUDE_PLUGIN_ROOT}/assets/bin/cq", "specs", "mcp"]`; the root is the working directory, so `find_repo_root` resolves the project. The generator ships it only for modules declaring `owned.mcp: true` (`quenching-specs`). Registering a server is the one widening authorized for this member; it adds no permission, grant or allow-list, so the tools still go through the normal permission prompt.

Binding contracts: exit codes 0/1/2 and `--json` payloads stay frozen by the golden fixtures; `docs/standards` on naming for new modules applies to the file and tool names; the CLI `--help` golden must be regenerated when the verb is added.

## Alternatives Considered

Reference projects read from the forge epic 1 §Reference projects on 2026-10-24:

- **MrLesk/Backlog.md (MIT) — reused in shape.** One store with an MCP server started by one local command (`backlog mcp start`) and no infrastructure: here `cq specs mcp` over stdio, registered by the plugin. Its tool set is wider and writes; ours is the read half only.
- **microsoft/azure-devops-mcp (MIT, to confirm) — adapted.** The `domain_verb` tool naming (`specs_list`, `specs_status`) and the read-only toolset idea are taken; the remote endpoint and Entra ID auth are rejected here (stdio, local) and belong to the HTTP port.
- **automazeio/ccpm (MIT) — rejected for this member.** It is about syncing specs into a tracker, which is the adapter members (2083 onward), not a read surface.
- **`cq specs serve` / `portal.py` (MIT) — rejected as the transport, kept as a reference.** It is an HTTP board with cookies and tokens; the MCP port shares its principle (reuse the CLI layer, never a second store) but not its code. Its refusal-to-HTTP mapping is the model for mapping refusals to `isError` results.
- **SVAR Gantt / frappe gantt — not applicable** (rendering).
- **Whole-shape alternatives rejected:** wrapping the third-party `mcp` SDK (new dependency, not installed); one generic `cq` tool taking argv (opens the write surface and breaks the size contract); waiting for the forge HTTP port (the stdio port needs no infrastructure and is the first deliverable).

## Open Decisions

- Why now / what makes this not worth doing: `## Problem` states the need (reads without shelling out, from any harness and the web UI); whether the 1:1 `Bash(cq specs ...)` swap follows is decided by the human at the PR review before merge, with epic 2045 holding any grant change.
- Ceiling value: 60,000 characters is an assumption (about 15,000 tokens at 4 chars per token, comfortably under the 25,000 ceiling); it is decided by measuring the largest `specs_section` answer in the tests and may be lowered, never raised past 80,000.
- Whether `quenching-specs-reader` also registers the server: decided at task 2.2 by what its generator copies; if it needs a reader-only manifest change it becomes a Discoveries line, not part of this spec.

## Risks

- A `.mcp.json` in a plugin makes the harness spawn `python3` at session start; a Python below 3.11 fails the server and not the session. Mitigation: the server prints one clear line to stderr and exits 2; `cq` already refuses below 3.11.
- Payload keys the pager relies on (`specs`, `candidates`) are CLI contract, not MCP contract. Mitigation: the tests assert them through the real verbs, so a CLI change fails here first.
- In-process dispatch means a verb that calls `sys.exit` or writes to stdout directly could corrupt the protocol stream. Mitigation: captured stdout/stderr, `SystemExit` caught per call, tested with a refusal.
- Generated mirrors drift (five copies). Mitigation: a dedicated regeneration task and the gate's `--check`.
- ACCEPTED — the hand-rolled protocol covers the tools capability only (no resources, prompts, sampling or notifications): those are not needed by a read surface and adding them is additive.
