## Overview

O plugin ainda oferece um armazenamento local de specs, mas esse caminho não é mais desejado. Ele mantém uma segunda forma de trabalhar e espalha regras por código, comandos, testes e documentação.

Depois da mudança, o plugin reconhecerá o provedor do repositório: GitHub usará GitHub Issues e Azure DevOps usará Azure Boards. O caminho local será removido, e configurações ou provedores não reconhecidos falharão de maneira explícita.
## Problem

O plugin ainda oferece o backend local `files`, embora o repositório determine qual backend externo deve ser usado. Isso mantém uma capacidade não desejada, uma segunda forma de armazenar specs e uma superfície de worktree, parser, comandos e documentação que não corresponde ao produto adotado.

A remoção é necessária agora porque o plugin passou a operar com provedores externos: repositórios GitHub usam GitHub Issues e repositórios Azure DevOps usam Azure Boards. Manter `files` preserva uma rota antiga e contraditória, além de aumentar o risco de configurações novas caírem em armazenamento local.

## Proposal

- Depois da mudança, o plugin suportará apenas os backends externos correspondentes ao provedor do repositório: GitHub → GitHub Issues e Azure DevOps → Azure Boards.
- O backend local `files` deixará de ser uma capacidade selecionável, instalada ou documentada pelo plugin.
- Repositórios sem um provedor reconhecido serão recusados de forma explícita, sem fallback para armazenamento local.
- A implementação local, os caminhos de configuração, o worktree persistente, o parser, os comandos exclusivos, os testes, fixtures, referências, standards e arquivos gerados relacionados a `files` deixarão de fazer parte da superfície ativa.
- As superfícies Claude e Codex permanecerão equivalentes após a remoção.
- Registros históricos de `/.knowledge/` que documentam diretamente o backend `files` serão removidos ou ajustados; históricos não relacionados permanecerão intactos.

## Out of Scope

- Migração automática de repositórios existentes configurados com `backend: "files"`; isso exige uma decisão e uma operação próprias sobre dados locais já existentes.
- Alteração de comportamento dos backends GitHub Issues ou Azure Boards; eles devem continuar funcionando como antes.
- Criação de um novo backend local ou de um substituto para o armazenamento em arquivos.
- Remoção de registros históricos em `/.knowledge/` que não sejam diretamente sobre `files`; eles não fazem parte desta retirada.
- Mudança de contratos ou capacidades do provedor externo além da detecção necessária para selecionar o backend correto.

## Design

A escolha do backend será derivada do provedor do repositório, e não de um default local: GitHub seleciona GitHub Issues; Azure DevOps seleciona Azure Boards; qualquer provedor ausente ou não reconhecido recusa a operação com uma mensagem acionável. Uma configuração antiga que ainda declare `files` também será recusada, sem migração implícita e sem criar uma store local.

A retirada será aplicada em lockstep às duas superfícies publicadas. Os arquivos diretamente ligados ao backend local e os consumidores que só existem para sustentá-lo serão removidos ou desacoplados, enquanto as interfaces compartilhadas necessárias aos backends externos serão preservadas. A documentação normativa e os registros históricos diretamente ligados a `files` serão alinhados ao novo contrato durante a execução.

## Alternatives Considered

- **Bloquear somente no runtime:** rejeitada porque deixaria implementação, testes e documentação de uma capacidade que o produto não suporta mais.
- **Manter `files` apenas para migração ou fixtures:** rejeitada porque prolongaria a superfície local, manteria dois modelos de armazenamento e não entregaria a retirada integral.
- **Escolher GitHub como novo default:** rejeitada porque o provedor correto é uma propriedade do repositório; um default fixo pode selecionar o backend errado.
- **Retirar somente a implementação e manter a documentação histórica sem ajuste:** rejeitada porque deixaria contratos, referências e cópias Codex contraditórios.

## Open Decisions

## Risks

- Existing repositories configured with `files` will stop working; mitigate with an explicit refusal naming the removed backend and the external provider configuration required.
- Repository-provider detection may be ambiguous or unavailable; mitigate by refusing unknown cases and covering GitHub, Azure DevOps, and refusal paths with tests.
- The Claude and Codex surfaces may drift during removal; mitigate by translating/regenerating the Codex surface and running doctor/lint plus mirrored runtime tests.
- A shared helper may be removed while still needed by GitHub or Azure Boards; mitigate by running the external-backend test suite and reviewing each dependency in the map before deletion.
- Historical cleanup may erase context beyond this change; mitigate by limiting edits to records directly about `files` and leaving unrelated history untouched.
