## Problem

Two things are missing after the align ships, and they are the same problem seen from both ends.

**The registry has no generator.** `op-undocumented` and `op-registry-stale` both compare the tree
against a registry document, and no command writes one. The measured target shows what happens when
a human owns that document: `scripts/README.md` describes 8 of 13 packages, and the folder's own
`CLAUDE.md` calls it "o mapa completo". It was not written carelessly — it is long, precise, and
carries an invocation and a purpose for every module it names. It drifted because five packages
were added by people who were doing something else at the time, which is how every hand-maintained
index drifts. Detecting the drift and then asking a human to close it by editing prose is the same
chore with a check bolted on.

**Minting has no mold.** The seven-rule entry-point contract is enforceable only after a module
exists. Nothing helps write a conformant one, so every new entry point starts from whatever the
author last copied — which on the measured target is how 13 modules ended up deriving the repository
root by hand while a shared helper sat in `cli_bootstrap.py` with two callers, and how two modules that deep-clone
production schemas ended up with no argument parser at all. A contract with no mold is a contract
that is met by accident.
## Proposal

**`cq ops registry --write`** — generate the registry document from the inventory, into a
`BEGIN/END GENERATED` block under
`/docs/standards/architecture/generated-listings.md`'s existing rules. One row per entry point:
purpose, canonical invocation, lifecycle, and whether it writes outside the repository. Everything
outside the block is the repository's own prose and is never touched. `--check` compares without
writing, which is what `op-registry-stale` runs.

**`/quenching:ops:entrypoint:new`** — mint ONE entry point under the contract. It asks the few
things that cannot be inferred, in this order, and each answer binds a rule:

| It asks | It binds |
| --- | --- |
| what the entry point does, in one line | the registry row and the module docstring |
| which domain package it belongs in | rule 1 — reachable, and grouped by domain |
| whether it writes outside the repository | rule 5 — an arming flag, mandatory, not offered |
| active or one-shot | rule 7 — lifecycle, and `_archive/` from birth for one-shot work |

Then it scaffolds from a template that carries the other three rules for free: the shared bootstrap
import (rule 2), a `main() -> int` whose value the `__main__` block carries out (rule 3), and a
parser whose data goes to stdout and diagnostics to stderr with `--json` honoured (rule 4). It
registers the entry point in the declared router, regenerates the registry, and re-runs
`cq ops doctor` so the new module is proven conformant before the command reports.

The arming question is not a preference. If the answer is that the entry point writes outside the
repository, the scaffold **has** an arming flag and a preview path; there is no branch that produces
the unarmed shape.

## Out of Scope

- **Rewriting existing entry points into the mold.** The align reports; a human converges. This
  command mints new ones.
- **Choosing the router.** The mechanism is declared configuration. The command registers into
  whichever is declared, and refuses when none is.
- **Generating the entry point's actual logic.** The scaffold carries the contract, not the work.
- **A second generated document.** One registry, one block, one hash.
- **Non-Python entry points.** Shell and `.cmd` entry points are inventoried and appear in the
  registry; minting them is not offered, because the seven rules are stated over Python constructs.

## Design

**Why generation and not a better check.** The measured drift is five packages in a document written
by somebody who clearly cared about it. A check turns that into a recurring editing chore; a
generator turns it into a state that cannot be reached. `generated-listings.md` already carries the
plugin's rule for this and its delimiters, so the registry is a new instance of an existing pattern
rather than a new pattern.

**Why the check calls the generator.** Two implementations of "does this document match the tree"
drift, and the drift is silent — the writer and the checker each think they are right. Making
`op-registry-stale` a call to `registry --check` means one comparison exists. The test that patches
the generator and expects the check to break is what keeps that true after somebody optimizes.

**Why the arming answer has no unarmed branch.** Offering an unarmed shape as an option makes rule 5
a preference. The measured target's two deep-clone modules are what a preference produces. The
question decides *whether the entry point writes outside the repository* — a fact about what it
does — and the shape follows from the fact.

**Why one-shot work gets `_archive/` from birth.** A migration script is written knowing it will run
a handful of times, and it is never moved afterwards because moving it is nobody's task. The
measured target has four such packages sitting beside daily tooling. Asking the lifecycle question at
mint time, when the author knows the answer, is the only moment the answer is cheap.

**Why the mold carries three rules and asks about four.** Rules 2, 3 and 4 have exactly one
conformant shape, so a template satisfies them with no question asked. Rules 1, 5 and 7 depend on
facts only the author has, and rule 6's example depends on what the entry point is for. Asking about
what the template can supply is the ceremony `/quenching:components:command:new` already avoids.

**Why `--check` and not a separate verb.** The align runs it, the doctor runs it, and a human runs
it. One flag on one subcommand keeps the three honest about running the same code.

## Alternatives Considered

- **Keep the registry hand-written and lean on `op-registry-stale`.** Rejected under §Why generation
  and not a better check: it is the current state of the measured target plus a nag.
- **Generate the registry as a whole file rather than a block.** Rejected: the measured target's
  `scripts/README.md` carries real prose worth keeping — how to invoke from the repository root, why
  `bundle_cli.py` is not called `databricks.py` — and a generator that owns the whole file either
  destroys it or has to be taught to preserve it, which is the block rule with extra steps.
- **Offer the mint as `cq ops new` rather than a command body.** Rejected: the four questions need a
  conversation and a judgement about which domain package is right, which is what a body is for. The
  deterministic half — scaffold, register, regenerate — stays in the tool and the body calls it.
- **Let the mint also convert an existing module.** Rejected: conversion is a judgement about code
  somebody else wrote and is already routed by the align's judgement band. Folding it in here would
  give one command two audiences and two failure modes.
- **Template the router registration instead of shipping snippets.** Rejected: the three mechanisms
  have genuinely different registration shapes and one of them (`[project.scripts]`) edits a file the
  repository's packaging owns. Snippets a body applies are honest about that; a template that edits
  `pyproject.toml` blind is not.

## Open Decisions

- **Whether the registry lives in the operations root's `README.md` or in its own file.** The
  measured target's prose argues for the `README.md` block; a repository with no such README argues
  for a dedicated file. Resolved at task 1 by letting configuration name the path and defaulting to
  `<opsRoot>/README.md`.
- **Whether the generated row carries the entry point's flags.** They are in the inventory and they
  are useful; they are also the fastest-moving field, so a row carrying them regenerates constantly.
  Resolved at task 1 against how often the measured target's parsers changed over its history.
- **Whether minting into `_archive/` is allowed at all.** Writing one-shot code straight into the
  archive is honest but reads oddly. Resolved at task 3 after the first mint is exercised both ways.

## Risks

- **A generator that touches a file humans also edit can destroy work.** *Mitigation:* the block
  rule is `generated-listings.md`'s, already proven elsewhere in this plugin, and validation item 2
  pins prose survival with a fixture that includes a heading shaped like a generated row.
- **The mold can encode this plugin's taste rather than the target's.** A repository with its own
  entry-point conventions will find the template foreign. *Mitigation:* the template carries only
  what the seven rules require and nothing stylistic, and rule 6's example is authored, not
  generated.
- **`op-registry-stale` becoming live changes what every existing target reports.** A repository that
  was clean gains findings the moment this spec ships. *Mitigation:* that is the honest report — the
  registry now exists as a concept, and the finding's remedy is one command — but the spec's own
  `## Discoveries` records the count on the measured target so the change is not a surprise.
- **The router snippet for `[project.scripts]` asks a body to edit packaging metadata.** *Mitigation:*
  the snippet is applied on the human's own confirmation as an ordinary edit, and the mint's
  re-verification catches a registration that did not take.
