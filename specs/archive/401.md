## Problem

Medido em 2026-11-24 (condutor do autopilot; wrapper de `git` no PATH contando cada execução por `PYTEST_CURRENT_TEST`, e `strace -f -e execve` no mesmo arquivo): `python3 -m scripts.toolchain.test --with-integration` abre **36.769** processos `git` pelo PATH (3.477 testes, 4m04s, 1m35s de sys), mais ~25% de reexecuções internas (`/usr/lib/git-core/git`, `receive-pack`, `upload-pack`, `maintenance run --auto`). Os 133 mil do scout de antivírus (rounds.md 2026-11-24) contam também os `execve` que falham com ENOENT na busca do PATH (32.751 execve para 6,5 mil processos em `test_specs_epics.py`).

Os maiores consumidores são suítes que exercitam o backend git de specs: `test_specs_epics.py` 5.254, `test_specs_git_backend.py` 4.758, `test_specs_epic_members.py` 3.700, `test_specs_push.py` 2.367, `test_specs_cards.py` 1.086, `test_specs_artifacts.py` 893. Cada escrita do store (`quenching/assets/bin/quenching/specs/backends/git.py:1237-1304`, `_guard_identity` + `_commit`) roda `git var GIT_AUTHOR_IDENT` e `git var GIT_COMMITTER_IDENT` (sem cache por processo, :1247), `read-tree`, `hash-object`, `update-index`, `write-tree`, `commit-tree`, `update-ref`, além de `rev-parse --verify`, `for-each-ref`, `remote get-url origin` (:267, repetido a cada leitura: 544 vezes em test_specs_epics+test_git) e `rev-parse --show-toplevel` (588).

**Consequência:** cada processo é um exec que o antivírus do desenvolvedor inspeciona e um fork que o sys do gate paga; o mesmo custo existe em produção, em toda `cq specs` que escreve (create, section --write, promote, link), multiplicado pelos workers do autopilot. Meta: no mínimo metade dos processos git por escrita do store e por suíte, medida antes/depois com o mesmo wrapper, sem mudar asserção nenhuma e sem enfraquecer a guarda de identidade (ela continua lendo as duas identidades, só não relê dentro do mesmo processo).

## Proposal

- Cada escrita do store git de specs abre pelo menos metade dos processos `git` de hoje, e a suíte que o exercita (`test_specs_epics`, `test_specs_git_backend`, `test_specs_epic_members`, `test_specs_push`, `test_specs_cards`, `test_specs_artifacts`) também, medido antes/depois com o wrapper de `git` no PATH por `PYTEST_CURRENT_TEST`.
- Nenhuma asserção de teste muda; a guarda de identidade continua lendo as duas identidades (`GIT_AUTHOR_IDENT`, `GIT_COMMITTER_IDENT`) e julgando-as em toda escrita, só não as relê dentro da mesma instância.

## Out of Scope

- Mudar o que o store grava (árvores, mensagens de commit, refs, protocolo de push/fetch): só o modo de montar e de ler muda.
- O audit (`git/audit.py`), que é a spec 402.
- Os processos de montagem dos repositórios de teste (`init`, `clone`, `push` de setUp).

## Design

- **Commit sem índice**: `_commit` lê a listagem completa da base (`ls-tree -r`, uma vez por commit, memorizada), aplica `changes` em memória, escreve blobs e árvores como objetos soltos (mesmo formato do git: cabeçalho, zlib, `objects/xx/yyyy`, escrita ao lado e `rename`) e só chama `commit-tree`. Somem `read-tree`, `hash-object`, `update-index` e `write-tree`. O formato do hash (sha1/sha256) sai do tamanho de um id já conhecido, ou de uma pergunta única.
- **Imutáveis memorizados por instância**: árvore e pai de um commit, `show -s` de um commit (a mensagem do commit recém-criado já é conhecida), identidades de `git var` (o julgamento da allowlist e do leak roda em toda escrita sobre o valor guardado), URL do remote lida para o espelho.
- **Heads reaproveitados**: o `for-each-ref` que já leu o pending serve à escrita local (CAS do `update-ref` continua guardando) e o commit que acabou de ser escrito deixa o par (tip, pending) na memória por `TIP_MEMO_S`, que o sync seguinte usa sem reler.
- **Sem processo para o que o disco responde**: `find_repo_root` sobe até um `.git` em vez de `rev-parse --show-toplevel`; `origin_url` não pergunta onde não há repositório, nem de novo enquanto o `.git/config` do repositório não mudar.
- Cada instância pergunta uma vez o diretório de objetos (`rev-parse --git-path objects`).

### Mapa de dependências (2026-11-24)

- `specs/backends/git.py` é o único escritor do store; `common/config.py:find_repo_root` e `common/git.py` são lidos por muitos verbos, e a mudança neles só evita um processo cujo resultado o disco já dá (bare repo mantém o caminho do git).

## Alternatives Considered

- **`git fast-import`**: reduz a montagem a um processo, mas escreve uma ref sem compare-and-swap e exigiria uma ref de rascunho no repositório do usuário; perdida.
- **Cache global de identidade por processo**: cada teste tem repositório e config próprios; ganho nulo e risco de identidade velha; perdida.

## Open Decisions

- none — o corte e a forma da medição estão na régua da épica 403.

## Risks

- Objetos soltos escritos sem passar pelo git: mitigado por seguir o formato exato (cabeçalho, zlib, nome por hash, rename, 0444) e por todo o resto do store lê-los pelo próprio git (suíte, `cat-file`, `push`).
- Heads em memória por 1 s podem estar velhos se outro processo mexer nos refs: a escrita local é guardada pelo CAS do pending, e o sync trata um push rejeitado e o `update-ref -d` com valor esperado como antes.
- `find_repo_root` por `.git` difere do git só com `GIT_DIR`/`GIT_WORK_TREE` (mantêm o caminho do git) ou `core.worktree` exótico.

## Outcome

O backend git de specs abre 60% menos processos `git` por escrita: nos seis arquivos de teste que o exercitam, 18.058 → 7.184 processos, sem mudar nenhuma asserção (258 testes verdes, 58s → 34s).

- `_commit` monta blobs e árvores em Python e grava objetos soltos no formato do git; sobra só o `commit-tree` (somem `read-tree`, `hash-object`, `update-index`, `write-tree`).
- Árvore, pai, `show -s` de cada commit e as identidades de `git var` ficam em memória por instância (a guarda segue lendo e julgando as duas identidades em toda escrita); o `for-each-ref` de uma leitura serve a escrita e o sync seguinte; `find_repo_root` e `origin_url` não abrem processo quando o disco já responde.
- Fora: `detect_provider` não ganhou cache de remote (um teste troca o remote do mesmo caminho); o audit é a spec 402.
