## Problem

O doctor só distingue assets citados de assets órfãos e não sabe se uma identidade precisa de variantes para superfícies ou orientações específicas. O brand pack precisa registrar papel semântico e o doctor precisa reportar ausências relevantes.

## Proposal

- Add an optional manifest for each design asset's semantic role, ink variant, and orientation.
- Include role/variant metadata in doctor status and findings.
- When the source palette or declared usage requires a light/dark variant, report the missing counterpart before a production artifact is rendered.

## Out of Scope

- Image recognition, recoloring, automatic SVG manipulation, or judging whether artwork is visually correct.
- Requiring variants for projects whose assets do not declare a role or whose palette has no contrasting surface.
- Replacing orphan detection; semantic checks complement citation checks.

## Impact

- `plugins/quenching/assets/bin/quenching/design/doctor.py` — manifest parsing, role validation, and variant findings.
- `plugins/quenching/assets/bin/quenching/design/model.py` — manifest entry contract and role enums.
- `plugins/quenching/assets/design/brand-pack/.design/assets/manifest.json` — generic starter manifest.
- `plugins/quenching/tests/test_design.py` — role and missing-variant coverage.
- `docs/standards/architecture/design-front.md` — assets remain portable source inputs.
- `docs/standards/quality/parse-honesty.md` — malformed manifests are findings, not skipped data.

## Validation

- A valid manifest appears in doctor payload with role, ink, and orientation.
- A dark surface plus a dark-only lockup produces a stable missing-light-variant error naming the role and orientation.
- A matching light variant clears that finding; unrelated roles or orientations do not satisfy it.
- Malformed paths, duplicate asset entries, invalid roles, and missing files are reported without crashing or hiding orphan findings.

## Design

- The optional `.design/assets/manifest.json` contains `assets`, an array of entries with `path` relative to `.design/assets/`, `role` in `lockup|mark|wordmark|icon|illustration`, `ink` in `dark|light|any`, and `orientation` in `horizontal|vertical|square|any`.
- Manifest paths are normalized under the asset root and must point to files. One path may have multiple entries only when their role/variant tuples differ.
- A palette requires a light ink variant for a role/orientation when a color token named `surface` or `surface-dark` resolves to luminance below 0.5 and a dark/light ink entry for that role exists. The required counterpart has the same role and orientation and `ink: light`.
- Doctor reports `design-asset-variant-missing` as an error with the surface token and required role/orientation; manifest parse problems use stable errors. Existing orphan warnings still apply to unlisted files.
- Dependency map (2026-08-30): `model.py` validates manifest data and path safety → `doctor.py` combines manifest variants with palette luminance and orphan scan → `brand-pack/manifest.json` demonstrates the portable contract → `test_design.py` asserts the complete report.

## Alternatives Considered

- Inferring roles from filenames such as `logo-light.svg`: rejected because filenames are not a semantic contract.
- Making every project provide a complete variant matrix: rejected because only declared roles and relevant surfaces create a requirement.
- Using image analysis to detect ink color: rejected because it is non-deterministic and outside a source validator.

## Open Decisions

- none — manifest shape, enums, trigger condition, and finding severity are fixed.

## Risks

- A surface's luminance can be affected by context or overlays; the doctor uses the declared token as a deterministic floor.
- A generic asset may work on both surfaces but be declared as a single ink variant; `ink: any` is available to opt out.
- Existing projects have no manifest; the feature remains optional and cannot make old installations invalid.
