## Problem

Achado reproduzido pela revisão de correção do épico 306 (2026-11-24, PR #325, spec 313): `quenching/assets/bin/quenching/deploy/tree.py:245-247` (cópia `.agents/quenching/bin/cq:21-23`) faz `sys.exit(runpy.run_path(REAL)["main"](sys.argv[1:]))` no Windows; `runpy.run_path` roda o arquivo com `run_name="<run_path>"`, então o bloco `if __name__ == "__main__":` de `quenching/assets/bin/cq:367-369`, o único que chama `force_utf8_streams()`, nunca roda, e `main()` (`cq:315-351`) não o chama. O commit da 228 (c0b30df) já é ancestral do merge da 313 (ff5cc6a).

**Consequência:** no Windows (`os.name == "nt"`), toda chamada `cq` volta aos streams cp1252: corpos de spec acentuados gravados como mojibake e bytes inválidos no `--json` — o defeito que a docstring de `force_utf8_streams` (`cq:357-359`) descreve. POSIX não é afetado (`os.execv` roda como `__main__`).

Proposta: o lançador Windows chama `force_utf8_streams()` antes de `main` (ou `main` passa a chamá-lo, ou o runpy usa `run_name="__main__"` preservando o exit code); teste que simula `os.name == "nt"` e prova os streams UTF-8 e o exit code.

## Proposal

- O lançador Windows gerado (`bin/cq`, ramo `os.name == "nt"` de `_VENDOR_SH` em `tree.py`) chama `force_utf8_streams()` antes de `main`, então os streams do `cq` voltam a ser UTF-8 no Windows.
- O exit code de `main` continua sendo o do processo, e o ramo continua sem segundo interpretador.
- Um teste simula `nt` com locale cp1252 e prova que a saída sai UTF-8 válida, com o exit code preservado.

## Out of Scope

- `runpy.run_path(..., run_name="__main__")`: rodaria o bloco `__main__` do `cq`, que termina em `sys.exit` e mataria o retorno do exit code que o lançador repassa; descartado.
- Mover a chamada para dentro de `main()`: muda o contrato do ponto de entrada compartilhado (`quenching_launch.py`, testes que importam `main`); descartado.
- `quenching/assets/bin/quenching_launch.py` (console scripts do plugin empacotado) tem o mesmo padrão `run_path(...)["main"]`; fica como achado separado.

## Impact

- `quenching/tests/test_deploy.py` — teste do ramo `nt`

## Design

- Regra durável: todo caminho que entra no `main` do `cq` sem passar pelo bloco `__main__` precisa chamar `force_utf8_streams()` antes. O lançador Windows guarda o namespace de `runpy.run_path(REAL)` e chama `ns["force_utf8_streams"]()` e depois `ns["main"](sys.argv[1:])`.
- Evidência: `cq:367-369` é o único chamador; `runpy.run_path` usa `run_name="<run_path>"`, então o bloco nunca roda.
- O teste existente `test_the_windows_branch_runs_cq_in_the_same_process` exige a substring `["main"](sys.argv[1:])` no ramo; a forma escolhida a preserva.

## Alternatives Considered

- `run_name="__main__"`: o bloco chama `sys.exit` dentro do `run_path`, que sai do processo no meio do lançador; só funcionaria capturando `SystemExit`, mais frágil que uma chamada explícita.
- `main()` chamar `force_utf8_streams()`: afeta todo importador de `main`, inclusive testes, sem ganho sobre o ponto único do lançador.

## Open Decisions

- none — a correção é única e a evidência a fixa.

## Risks

- O teste roda a sonda `nt` em POSIX: reconfigurar streams é idêntico em ambos, então prova o comportamento. Risco residual de uma diferença real do console do Windows: ACCEPTED — a função já tem teste próprio (`test_cq_stdio_utf8.py`) e o defeito é a chamada ausente.
