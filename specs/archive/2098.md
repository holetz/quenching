## Problem

A distribuição OpenCode da 2038 (`plugins/quenching-opencode/`, gerada por `scripts/sync_opencode_plugin.py`) não traz manifesto de plugin, e o `cq` empacotado recusa todos os pilares. Reprodução de 2026-10-24 em `59e1e3f1a`: copiar `plugins/quenching-opencode/quenching` para um diretório vazio com `git init` e rodar `python3 quenching/scripts/cq specs config` dá `cq: specs belongs to module quenching-specs, which is not enabled; enable it beside quenching-specs` e exit 2. O spike H1 (`holetz/forge#2`) só conseguiu rodar o quenching no OpenCode porque a imagem dele grava um `.codex-plugin/plugin.json` como contorno. Consequência: fora desse contorno, nenhum comando que chama `cq` funciona na distribuição OpenCode, e a S12 do épico `holetz/forge#1` depende dela. O gerador precisa emitir o manifesto que habilita os módulos empacotados, com um teste que rode o `cq` empacotado num diretório limpo.

## Proposal

- The OpenCode payload (`plugins/quenching-opencode/quenching/`) carries a plugin manifest at `.claude-plugin/plugin.json`, named `quenching` and versioned from the source `VERSION`, emitted by `scripts/sync_opencode_plugin.py` and listed in `.generated-files.json`.
- The bundled `cq` run from a clean directory reaches every pillar it ships: `cq modules` lists all nine modules `enabled`, and `cq specs config` exits 0 there instead of 2.
- A unit test writes the generated tree to a temporary directory and runs the bundled `cq` in an empty working directory, so a regression of the manifest fails the repository gate.
- The OpenCode section of `docs/standards/architecture/surface-translation.md` states the manifest and why `cq` needs it.

## Out of Scope

- Changing `cq`'s module detection (`_plugin_name` in `plugins/quenching/assets/bin/cq`) to learn an OpenCode manifest name: it would touch the source and every translated mirror of `cq`; deferred until a second consumer needs it.
- Any permission, allow-pattern, hook, script or CI the distribution does not already generate: the manifest is declarative data and widens nothing.
- A marketplace entry or `distributions` row for the OpenCode payload: installing stays a copy into the OpenCode configuration directory.
- Running the spike H1 image or the eval runner: this spec only removes the need for the image's `.codex-plugin/plugin.json` workaround.

## Impact

### Standards this spec will write into docs/standards/

- `docs/standards/architecture/surface-translation.md` — the OpenCode distribution ships the manifest `cq` reads to enable its modules

### Product code this spec expects to touch

- `scripts/sync_opencode_plugin.py` — emits the manifest in `generated_tree`
- `plugins/quenching/tests/test_sync_opencode_plugin.py` — the clean-directory `cq` test
- `plugins/quenching-opencode/quenching/.claude-plugin/plugin.json` and `plugins/quenching-opencode/.generated-files.json` — generated output

## Validation

- `python3 -m unittest discover -s plugins/quenching/tests -p test_sync_opencode_plugin.py` exits 0; without the manifest the new test fails with `cq: specs belongs to module quenching-specs, which is not enabled` (exit 2).
- `python3 scripts/sync_opencode_plugin.py --check --json` reports no drift after `--write`.
- Copying `plugins/quenching-opencode/quenching` to an empty directory and running `python3 quenching/scripts/cq modules` prints every module `enabled`.
- `bash scripts/verify_repo.sh` exits 0.

## Design

**Root cause.** `cq` enables a pillar only when the plugin root that owns the package carries a manifest (`.claude-plugin/plugin.json` or `.codex-plugin/plugin.json`) whose `name` is the owning module, `quenching` or `quenching-codex` (`package_root`/`_plugin_name` in `plugins/quenching/assets/bin/cq`). The root of the bundled `cq` is `quenching/scripts/..`, the payload directory, and the generator emits no manifest there; the Codex translation has one, so the carried-verbatim `cq` works on Codex.

**Decision.** Emit `quenching/.claude-plugin/plugin.json` with `name: quenching` (the monolithic source's name, which `package_root` already accepts for a root carrying every module), `version` read from `plugins/quenching/VERSION` so the release lockstep needs no new step, and a short description. Durable rule: the OpenCode payload root always carries a manifest `cq` accepts; the generator owns it and the lockstep version comes from the source `VERSION`.

**Contracts.** `docs/standards/architecture/surface-translation.md` (generated trees are never edited by hand; nothing flows back); the generator's `--check` compares bytes, so the manifest is regenerated, not hand-written; no new permission or allow-pattern (`cq *` stays the only one).

## Alternatives Considered

- **Reference projects (forge Design, 2026-10-24).** Backlog.md, ccpm, azure-devops-mcp, the Gantt libraries, the MCP gateways, LiteLLM/Langfuse, OPA/Presidio/gitleaks and the hallmark catalogs address the specs service, routing, policy and catalog members; none treats plugin-manifest discovery of a bundled CLI, so there is nothing to reuse from them. Reused/adapted: the in-repo precedent, the Codex translation's `.codex-plugin/plugin.json` (`plugins/quenching-codex`), whose manifest-names-the-owner contract `cq` already honours. Rejected: vendoring any external project.
- **Teach `cq` an OpenCode manifest (`.opencode-plugin`).** Rejected for now: it edits the source `cq` and every translated mirror and widens the generator's contract for no behaviour the existing manifest does not already give.
- **Emit `.codex-plugin/plugin.json` named `quenching-codex`** (the spike H1 workaround). Rejected: it labels an OpenCode payload as the Codex plugin.
- **Document the workaround and leave the generator alone.** Rejected: every OpenCode adopter, S12 included, would repeat it.

## Open Decisions

- Whether `cq` should read a dedicated OpenCode manifest name instead of `quenching`: decided when a second consumer or a lockstep check needs to tell the payloads apart, by that consumer's spec.

## Risks

- A future `cq` change that stops accepting the name `quenching` for a non-source root silently disables the pillars again; mitigation: the clean-directory test runs the bundled `cq`, so the gate fails first.
- The `.claude-plugin` directory inside an OpenCode payload could be mistaken for a Claude plugin; ACCEPTED — the payload is copied under the OpenCode configuration directory, which Claude Code does not scan, and the README and standard say what it is for.
