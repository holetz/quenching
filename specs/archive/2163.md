## Problem

Execução real do `/quenching-specs-autopilot --until-dry` no repo `holetz/jornada` (epic 3, 2026-11-03, cq 7.0.1): a spec 5 consumiu 5 spec-runners, 4 spec-verifiers e 3 spec-orchestrators para um único merge (PR #11). Cada relançamento começa com contexto frio e relê spec, protocolo e código. Quase todos tinham causa evitável no protocolo:

1. **Task operacional sem commit reprovada.** A task 3.2 (redeploy local, `verify: systemctl --user is-active jornada && jornada today`) não gera commit. O verifier deu FAIL ("7/7 tasks marcadas, 6 com commit"). Não há como declarar isso: `files: (nenhum)` gera o erro `sp-files-annotation` no `cq specs validate`, porque só `(new)` é reservado.
2. **Exit code do gate ausente no relatório do runner.** O verifier deu FAIL só porque o worker não reportou o exit code do gate. Para fechar a lacuna, foi preciso um runner extra que apenas rodou o gate.
3. **Autorizações vivem só no brief.** O runner parou com `needs-human` no deploy do meio do épico e em `pytest -m desktop` local. A política no `## Design` dizia "deploy ao fim do épico", e a decisão do condutor ficou só no brief, que se perde a cada relançamento.
4. **Relançamento em vez de retomada.** O passo 5 do autopilot manda relançar o orquestrador, e ninguém indica `SendMessage` ao mesmo agente quando a parada é `needs-human` resolvida rapidamente (dentro do TTL do cache). Foram 3 orquestradores frios.
5. **Checkout base sujo descoberto tarde.** A etapa 1 detectou 117 arquivos não commitados (upgrade de deploy do humano), mas o caminho "fix spec" é inviável quando o humano proíbe specs novas. O bloqueio só apareceu quando `/quenching-git-git branch` recusou cortar a worktree da spec 6, e um runner foi gasto à toa.
6. **Escopo de `files:` sem os testes.** O primeiro FAIL veio de `tests/test_db.py` tocado sem estar em nenhum `files:`. O develop não declarou os testes afetados.

Consequência: mais ou menos o dobro de tokens sonnet e de launches (13 de 40 antes da spec 6) para trabalho já pronto, e paradas que exigem decisão do condutor.

## Proposal

- **Anotação reservada para tasks operacionais** em `files:` (por exemplo, `(operational)`), aceita pelo validate. O spec-verifier passa a aceitar task marcada sem commit quando o `verify:` é operacional.
- **`GATE_EXIT:` obrigatório** no relatório fixo do spec-runner. O verifier o lê, em vez de reprovar por ausência, e o runner nunca retorna sem ele.
- **Decisões do condutor persistidas no store.** O autopilot grava toda decisão do dono delegado no `## Design` do épico (`cq specs section --write`) antes de relançar, e os briefs a referenciam em vez de repeti-la.
- **Retomada por `SendMessage`** no autopilot (passo 5) quando o orquestrador volta com `needs-human` e o condutor decide em minutos. Relançamento frio fica só para `budget:`, que exige contexto limpo.
- **Checkout base sujo na etapa 1.** Quando o fix-spec não é permitido, o condutor decide de imediato cortar worktrees de `origin/<base>` e grava isso no `## Design`, ou para. A skill de branch aceita o corte autorizado sem exigir checkout limpo.
- **Briefs com prefixo estável.** Texto fixo primeiro, variáveis (id, worktree) no fim, para agentes do mesmo tipo compartilharem cache.
- **O develop inclui os testes tocados** no `files:` das tasks.
- **O PR é aberto no modo autônomo.** O `conclude` com `autonomous` e outcome `done` abre o PR ele mesmo (`/quenching-specs:git:pr:create <id> autonomous`) depois do gate verde, em vez de apenas nomear o handoff; o `spec-orchestrator` adota o PR já aberto, nunca abre um segundo, e só mescla com PASS do `spec-verifier`.

## Out of Scope

- **Retomada do spec-runner no modo econômico.** O `needs-human` que o runner devolve em modo econômico continua com o tratamento de hoje; a retomada por `SendMessage` é do orquestrador, como o problema descreve.
- **Um canal de retomada para o harness OpenCode.** Este repo é Claude Code; o host que não exponha `SendMessage` cai no relançamento frio já especificado, e nada é medido no OpenCode.
- **Erro de validate para toda task sem `files:`.** Seria retroativo sobre specs já escritas; a regra fica na doutrina do develop.
- **O verifier executando o gate.** Ele continua lendo um claim; a certificação continua sendo o CI no merge.
- **Automatizar a decisão do checkout sujo.** O condutor (ou o humano) decide; a spec só dá o caminho autorizado e o registro.
- **Qualquer anotação além de `(operational)`.** `(new)` fica como está e o conjunto reservado não cresce além do par.

## Design

### D1 — `(operational)` é gramática fechada e exclusiva

`files: (operational)` declara que a task não escreve arquivo do repositório: o proof dela é o `verify:`. O parser é o único dono do conjunto reservado (`(new)`, `(operational)`); nenhum consumidor reimplementa a checagem. A anotação é **exclusiva**: ao lado de qualquer caminho, `validate` recusa com `sp-files-operational`, e uma task operacional sem `verify:` recebe `sp-operational-no-verify` (warn) — sem proof, o marcador não prova nada. Alternativa rejeitada: aceitar `files: (nenhum)` ou comentário livre, que exigiria interpretar texto.

### D2 — O consumidor entrega a task operacional como `files: []`, nunca com a anotação

`cq specs next` devolve `files: []` e `operational: true`; `cq specs show --task` normaliza igual; `estimate` a exclui do sizing e de `unresolved`; `parallel` a trata como não declarada, então o grupo `[P]` fica inelegível; `cq codex eligible` a recusa com o motivo nomeado. A cadeia "sem `files:` → tick sem commit" já existe em `execute`/`execution.md`; a anotação acrescenta a **declaração** que o verifier lê, nunca um segundo caminho de execução.

### D3 — O verifier lê a declaração, e o scope continua pegando o que ela esconderia

Check 2 (commits): uma task marcada `(operational)` não exige sha; qualquer outra task marcada sem sha é FAIL. Check 4 (scope) continua comparando `changed` com a união dos `files:`; uma task operacional não contribui com caminho, então um arquivo que ela escreveu fica **fora** da união e é FAIL. A anotação não pode esconder diff — é por isso que ela é segura. Check 3 passa a ler `GATE_EXIT:`; ausente ou `not-run` é inconclusivo, nunca FAIL.

### D4 — `GATE_EXIT:` é campo próprio do relatório

`GATE:` carrega o veredito e o comando; `GATE_EXIT:` carrega o código (ou `not-run`). O runner nunca retorna sem a linha, em nenhum STATE. O orquestrador repassa a linha verbatim ao verifier, que a lê como claim. Alternativa rejeitada: manter o código dentro de `GATE:` — obrigaria o verifier a parsear prosa, que é o defeito que o problema mede.

### D5 — Decisão do condutor mora no `## Design` do épico, não no brief

Toda decisão do dono delegado (abandonar, mandar ao épico humano, cortar de `origin/<base>`, não rodar um proof) é escrita no `## Design` do compósito **antes** do lançamento que depende dela, em um bullet datado com a evidência. `cq specs section --write` substitui a seção: o condutor lê, apenda e regrava em uma chamada; o brief nomeia o épico e o bullet em vez de repetir a decisão. Antes de o épico existir (passo 1), o registro da rodada (`rounds.md`) carrega a decisão, e o passo 4 a copia para o `## Design` junto da política de autonomia.

### D6 — Retomada por `SendMessage` dentro da janela medida; relançamento frio fora dela e por `budget:`

O condutor guarda o `agentId` que o resultado do `Agent` devolve. Um `blocked` com `needs-human:` resolvido (pelo humano ou pelo condutor como dono delegado) é retomado no **mesmo** orquestrador por `SendMessage({to: <agentId>})`, depois de a decisão entrar no `## Design`. Relançamento frio permanece para `budget:`, para um host que não exponha a retomada, para um `agentId` perdido, fora da janela de cache medida e quando a decisão repete uma que já está no `## Design` — a repetição manda o épico ao humano com as duas notas, nunca a uma segunda retomada. **A janela não é constante**: o corpo manda ler `cq components session cache` (boundaries por harness e modelo) e cita a lifetime documentada de 5 min do subagente Claude Code como o caso medido em `context-discipline.md`. Uma retomada não é um lançamento: não conta em `launches` e fica registrada como `resumes:` no bloco da rodada.

### D7 — O checkout base sujo é decidido no passo 1, não descoberto no corte

O passo 1 separa "o run sujo" de "o humano sujo": um checkout sujo que o run não causou tem duas saídas imediatas — a spec de fix, quando spec nova é permitida, ou o corte de toda worktree da rodada a partir de `origin/<base>`, autorizado pela invocação, com a decisão no registro da rodada e no `## Design` do épico; sem nenhuma das duas, para. A worktree cortada de `origin/<base>` nunca carrega os arquivos não commitados da base, e a skill de branch aceita o corte autorizado sem exigir checkout limpo, reportando os caminhos sujos que ficaram na base.

### D8 — Brief com prefixo estável

O texto fixo (a palavra `autonomous`, a base, o modelo, a frase que proíbe `stash`/`checkout`/`reset`) abre o brief; as variáveis (id da spec, worktree, épico, decisão) fecham. Agentes do mesmo tipo compartilham então o prefixo. **Assume-se** que o ganho de cache entre agentes distintos não está medido neste repo — a tabela mede gerações dentro de um agente —; a ordem é a mudança e `cq components session cache` é a medição que a confirmaria ou a refutaria.

### D9 — O PR é aberto pelo próprio run no modo autônomo

Sob `autonomous` e outcome `done`, o `conclude` invoca `/quenching-specs:git:pr:create <id> autonomous` depois do gate verde, como o caminho `low` já faz, em vez de apenas nomear o handoff: a publicação deixa de depender de existir um orquestrador. O `spec-verifier` continua sendo a aceitação — o orquestrador **adota** o PR já aberto (nunca abre um segundo) e só mescla com PASS. Um FAIL posterior não apaga o PR: o re-spawn empurra para o mesmo branch e o PR se atualiza; sem PASS não há merge. Fora do modo autônomo nada muda: o handoff continua nomeado e não invocado.

### D10 — A doutrina de autoria nomeia os testes no `files:`

`artifacts.md`, a casa do grammar, ganha a regra: o `files:` de uma task inclui todo teste cujo diff a task produz, porque o verifier acusa um teste alterado fora da união. `develop.md` acrescenta a pergunta ao compose — *quais testes esta task toca?* — ao lado de `[P]`, `files:` e `pattern:`.

### Contratos que o desenho não pode contradizer

- `docs/standards/automation/context-discipline.md` §The prompt cache is a per-harness measurement — nenhuma lifetime é constante; a regra cita a medição do harness e do modelo.
- `docs/standards/automation/agents.md` §Plugin-shipped agents — relatório fixo, e nenhum haiku para quem escreve código de produto.
- `docs/standards/automation/skills.md` §`allowed-tools` is always scoped — o grant declara, não restringe; `SendMessage` é o canal de retomada, não shell, e o `Bash` da autopilot continua justificado no corpo.
- `docs/standards/architecture/surface-translation.md` — o Codex descarta `allowed-tools` e reescreve ferramentas do host; `translate.py` já faz isso com `TaskStop`, e fará com `SendMessage`.

### Assumptions

- `SendMessage({to: agentId})` existe no Claude Code ≥ 2.1.77 e devolve o subagente ao próprio transcript; num host sem ela, o protocolo cai no relançamento frio. Depende de D6.
- O ganho de cache do prefixo estável entre agentes distintos não está medido neste repo; a regra ordena o texto e a medição que a confirma é `cq components session cache`. Depende de D8.
- A anotação é aditiva: nenhuma spec existente usa `(operational)`, então não há migração nem leitura retroativa. Depende de D1 e D2.
- Abrir o PR antes do PASS do verifier não aceita nada: o merge é o que o PASS libera, e o orquestrador nunca mescla sem ele. Depende de D9.

## Alternatives Considered

- **Aceitar `files: (nenhum)` como o problema tentou.** Rejeitada: um texto livre é comentário que o parser teria de interpretar; um token reservado é gramática fechada.
- **Inferir operacional da ausência de `files:`.** Rejeitada: a segunda metade do problema é justamente que a ausência era uma omissão real (os testes), então inferir apagaria o fato que a anotação existe para declarar.
- **Uma marca própria no checkbox (`- [ ] (op) 3.2 …`).** Rejeitada: o grammar já tem um lugar para a declaração de caminhos, e duas posições para a mesma pergunta divergem.
- **Manter o exit code dentro de `GATE:`.** Rejeitada: obrigaria o verifier a parsear prosa para achar um número; um campo é uma fato.
- **Retomar com um `Agent` novo carregando o relatório anterior.** Rejeitada: é exatamente o relançamento frio que o problema mede.
- **Persistir a decisão num arquivo efêmero que o brief referencia.** Rejeitada: o `## Design` do épico é a casa durável que a rodada seguinte e o humano leem.
- **Recusar o checkout sujo e parar.** Rejeitada: a rodada pode seguir com segurança a partir de `origin/<base>`, e parar custa um turno humano por nada.
- **Erro de validate para toda task sem `files:`.** Rejeitada: falharia retroativamente specs já escritas; a pergunta fica no compose do develop.
- **Manter o PR nomeado e não invocado sob `autonomous`.** Rejeitada pela direção do dono em 2026-11-03: sem orquestrador não há PR, e a publicação não pode depender de um agente que talvez não exista.

## Risks

- **A anotação vira escape hatch para uma task que deveria declarar arquivos.** Mitigação: o check 4 continua comparando `changed` com a união dos `files:` — o arquivo escrito por uma task operacional fica fora e é FAIL —, e `parallel`, `estimate` e o Codex a recusam. ACCEPTED com essa guarda.
- **`SendMessage` no `allowed-tools` amplia um grant.** Mitigação: é o canal de retomada, não shell; a mudança é uma linha revisada no PR; host sem a ferramenta cai no relançamento frio. ACCEPTED.
- **Um orquestrador retomado repete a pergunta que o condutor já respondeu.** Mitigação: a decisão está no `## Design` antes da retomada, e a repetição manda o épico ao humano com as duas notas.
- **O corte autorizado com a base suja esconde trabalho não commitado do humano.** Mitigação: os arquivos da base nunca entram na worktree, nunca são stageados nem commitados, os caminhos são reportados, e o merge continua recusando base suja.
- **O PR existe antes do PASS e o verifier reprova o build.** Mitigação: nenhum merge sem PASS; o re-spawn empurra para o mesmo branch e o PR se atualiza; o PR fica visível para o humano em vez de um branch invisível.
- **Os dois standards mudam e divergem dos corpos dos comandos.** Mitigação: uma cláusula cada, citando o protocolo em vez de repeti-lo, e o gate roda `docs bundle` e `docs doctor`.
- **O Codex herda uma menção a `SendMessage`.** Mitigação: `translate.py` reescreve a ferramenta e o `manual_review` a nomeia; o check de distribuição falha se o bundle regenerado ficar velho.

## Outcome

- **`files: (operational)` é gramática reservada e exclusiva.** O parser a normaliza uma vez para
  `files: []` mais `operational: true`; `validate` recusa a forma mista (`sp-files-operational`) e
  avisa a operacional sem `verify:` (`sp-operational-no-verify`); `next`, `estimate`, `parallel` e

  porque a lista vazia sozinha não distingue a operacional de uma task sem `files:`.

  claim, aceita a task operacional sem sha e mantém o check de escopo cobrando qualquer arquivo que

- **O PR é aberto pelo próprio run sob `autonomous`.** O `conclude` com outcome `done` invoca
  `pr-create <id> autonomous` depois do gate verde, e o `spec-orchestrator` adota o PR existente em
