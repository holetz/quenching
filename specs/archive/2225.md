## Problem

`quenching/assets/bin/quenching/deploy/tree.py:107` builds `known` as a `set` and `:116` iterates it to expand `all`, so `normalize_modules(['all'])` returns a different order per process (`PYTHONHASHSEED`). The list goes to `manifest["modules"]` (`tree.py:414`) and `cli.py:219` compares the whole manifest with `!=`.

Reproduced (autopilot 2026-11-21 round 4, origin/main c29ba1e46), fresh `git init` target: `PYTHONHASHSEED=1 cq deploy --target . --modules all --write`, then `--modules all --check` → seed=1 exit 0; seed=2 and seed=3 exit 1, `changes: 1 manifest .agents/.quenching-deploy.json`.

Consequence: a target installed and checked with `--modules all` (e.g. in CI) fails intermittently with no real change, and every `--modules all --write` rewrites the manifest only reordering the list. Without the flag the recorded order is reused (`cli.py:393`). Fix direction: expand `all` in a deterministic order (the manifest's/registry's), plus a test across two hash seeds.

## Proposal

- `normalize_modules(["all"], manifest)` returns the owned modules in the order `assets/modules.json` lists them, identical in every process whatever `PYTHONHASHSEED` is.
- `cq deploy --modules all --write` followed by `--modules all --check` exits 0 under any hash seed; a second `--write` no longer rewrites the manifest just to reorder `modules`.
- A regression test proves the expansion is the same under two different hash seeds.

## Out of Scope

- Rewriting the `modules` list already recorded in an installed manifest (this repository's own `.agents/.quenching-deploy.json` included): without `--modules` the recorded order is reused (`cli.py:393`), so an existing install stays green; reordering it would be a manifest churn with no behaviour.
- Making the manifest comparison order-insensitive (`cli.py:219`): the manifest is a byte-stable record, and the order of an explicit `--modules a,b` stays the caller's.
- Any other `set` iteration in `deploy/` — none feeds the manifest today; a found one is a discovery, not this spec.

## Impact

### Product code this spec expects to touch

- `quenching/assets/bin/quenching/deploy/tree.py` — `normalize_modules` expands `all` from the registry list, not a set.
- `quenching/tests/test_deploy.py` — regression test across two hash seeds.
- `.agents/quenching/assets/bin/quenching/deploy/tree.py`, `.agents/.quenching-deploy.json` — the deployed mirror refreshed by `cq deploy --target . --write`.

## Validation

- `bash scripts/verify_repo.sh` (affected scope) green, including the deployed-surface lockstep check.

## Design

- 2026-11-21 — **`all` expands in registry order.** The owned modules are taken as a list comprehension over `manifest["modules"]` (the order of `assets/modules.json`), and membership checks keep a set built from that list. Rule: anything written to the deploy manifest is derived from an ordered source, never from a `set`'s iteration.
- 2026-11-21 — **The test spawns child interpreters.** Hash randomization is fixed at interpreter start, so the test runs `normalize_modules(["all"], load_modules(source_root()))` in two subprocesses with `PYTHONHASHSEED=1` and `=2` (sys.path pointing at `quenching/assets/bin`) and asserts equal output, also equal to the registry order. Pattern: the subprocess style already used in `test_deploy.py`.

### Assumptions

- The registry order of `assets/modules.json` is a stable, deliberate order (specs first) — `## Proposal` depends on it.

## Alternatives Considered

- **`sorted(known)`** — deterministic, but alphabetical puts `quenching-components` first and diverges from the registry order every other listing uses; rejected for the registry order.
- **Compare `modules` as a set in `--check`** — hides the symptom but leaves `--write` churning the manifest; rejected.

## Open Decisions

- none — the fix direction is stated in `## Problem` and the code settles the order.

## Risks

- Targets already installed with `--modules all` hold a hash-ordered list; their next `--modules all --write` rewrites the manifest once into registry order. ACCEPTED — one-time, and it is exactly the stabilization this spec delivers.
- The subprocess test inherits the environment; mitigation: the test sets `PYTHONHASHSEED` explicitly per child.
