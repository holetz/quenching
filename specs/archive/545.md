## Problem

Achado reproduzido (leitura) da revisão do épico 541 (autopilot 2026-11-25), sobre o merge c2fe07614 (PR #542, spec 539). quenching/assets/bin/quenching/deploy/cli.py:314-322 `_uncommitted` devolve False em OSError (git ausente), SubprocessError (timeout) e returncode != 0 (128: alvo não é repositório, HEAD ilegível); com `deleting=True` e registro "source", `_edited` (:305) devolve esse False e os chamadores :460 e :842 classificam o arquivo como `delete`. O mesmo em .agents/quenching/assets/bin/quenching/deploy/cli.py. Os testes novos (quenching/tests/test_deploy.py:277-306) rodam só num repositório git funcional.

Consequência: a proteção que a 539 trouxe (manter edição não commitada) some exatamente quando o git não consegue responder, e o deploy apaga a edição. Correção esperada: falha do git = mantido (`edited`), com teste para git ausente e para alvo fora de repositório; ajustar deploy-mode.md:100-103.

## Proposal

Fechar o caminho de exclusão do repositório-fonte: em `quenching/assets/bin/quenching/deploy/cli.py`, `_uncommitted` passa a devolver `True` (a edição é mantida, `edited`) quando o git não responde — `OSError` (git ausente), `SubprocessError` (timeout) ou `returncode != 0` (alvo fora de repositório, HEAD ilegível). Só um `git status --porcelain` bem-sucedido e vazio libera o `delete`. Dois testes provam git ausente e alvo fora de repositório; `docs/standards/architecture/deploy-mode.md` registra a regra.

## Out of Scope

- O caminho de atualização (`deleting=False`) e o registro com hash: não consultam o git e ficam como estão.
- Diagnosticar por que o git falhou ou emitir aviso próprio: o arquivo mantido já aparece como `edited`/`kept` no relatório, e `--force` continua sendo o descarte deliberado.
- A seleção do escopo affected que não pega `test_subprocess_text_encoding.py` — spec 543.

## Impact

### Standards this spec will write into docs/standards/

- `docs/standards/architecture/deploy-mode.md` — no caminho de exclusão do repositório-fonte, falha do git é `edited`

### Product code this spec expects to touch

- `quenching/tests/test_deploy.py` — provas de git ausente e alvo fora de repositório

## Validation

- Reproduzido por leitura (2026-11-25): cli.py:320-322 devolve `False` em `OSError`/`SubprocessError`/`returncode != 0`, e cli.py:460 e :842 classificam o arquivo como `delete`.
- Teste: alvo com `quenching/assets/modules.json`, deploy commitado, `subprocess.run` do git levantando `FileNotFoundError` → `--remove` lista o arquivo possuído em `kept` (change `edited`), e nada sai como `delete` entre os arquivos possuídos.
- Teste: mesmo alvo com `.git` removido depois do deploy → `--remove` mantém o arquivo possuído como `edited`.
- Os dois testes da 539 (repositório funcional) continuam verdes: não editado é `delete`, editado é `edited`.
- `python3 quenching/assets/bin/cq deploy --target . --check` sai 0 depois do `--write`; `python3 -m pytest quenching/tests/test_subprocess_text_encoding.py` verde.

## Design

- `_uncommitted(target, rel)`: `except (OSError, subprocess.SubprocessError): return True`; depois, `if done.returncode != 0: return True`; senão `bool(done.stdout.strip())`. A docstring diz que uma resposta ausente do git é tratada como edição a manter.
- Teste de git ausente: `mock.patch("quenching.deploy.cli.subprocess.run", side_effect=FileNotFoundError)` só em volta do `run_deploy("--remove")`, depois do deploy commitado.
- Teste fora de repositório: apagar `self.target / ".git"` (shutil.rmtree) depois do deploy e chamar `--remove`; `git -C` sai 128.
