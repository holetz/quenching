## Problem

The open projects' specs belong in GitHub Issues, not on a git branch that floods the repository's history, and the quenching specs service has no GitHub adapter. Add a GitHub Issues store adapter behind the specs service — the whole spec as the issue body, records and stages as labels or body fields, and `after:` carried as GitHub's native "blocked by / blocking" issue dependencies (GA since August 2025, with REST and webhooks) — reaching parity with the Azure Boards adapter on the store contract and the equality check of `cq specs migrate`. Issues only; GitHub Projects stay out until a later decision.

Member S31 of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent).

## Proposal

- A spec's numeric `dependsOn` ids are carried on its GitHub issue as native issue dependencies ("blocked by"): one `blocked_by` relation per dependency that is an issue of the same repository, never the spec's own number and never a slug or an `owner/repo#id` reference.
- A write that changes `dependsOn` adds the relations the spec now names and removes the ones it no longer names, diffed by issue, never by position; a write that leaves `dependsOn` unchanged sends no dependency request at all.
- A spec born with `dependsOn` gets its relations right after the issue is created, inside `create_spec`, so a creation that fails while linking keeps the existing "issue was ALREADY created" refusal.
- The relations read back: `GitHubBackend.predecessor_links(spec_id)` returns the sorted issue numbers the issue is blocked by, equal to the spec's numeric `dependsOn` after a write. This is the same name and the same meaning as on Azure Boards (2083).
- `cq specs migrate --to github` exists beside `--to git` and `--to azure`, with the same contract as `--to azure` (2084): a dry run unless `--write`, a `git` source only, an empty destination, creation in dependency order, the id map printed, `dependsOn` and the `— spec: #<id>` lines of epic members remapped, the per-spec equality check, and the `.claude/quenching.json` change printed but never applied.
- The equality check of a tracker migration also compares, for each spec, `predecessor_links` with the remapped numeric `dependsOn` whenever the destination provides `predecessor_links`. Both GitHub and Azure Boards provide it.
- The GitHub adapter sits behind the specs service: a read tool of the stdio MCP server (2085) answers from a spec held by `GitHubBackend`, which a test proves over the offline `gh` double.
- `docs/standards/architecture/spec-backend.md` gives the GitHub mapping in the `dependsOn` bullet and the `--to github` direction in the Migration rule.

## Out of Scope

- **GitHub Projects** (fields, iterations, views): left out until a later decision, as `## Problem` says.
- **Dependencies across repositories.** GitHub allows a dependency on an issue in another repository, but a spec's `owner/repo#id` reference is an epic member of another store (2036), and that store's own adapter answers for it. Mapping it natively needs that store's credential and is a separate decision. Here a non-numeric dependency is ignored, as on Azure Boards.
- **Removing the `sp-backend-deprecated` flag from `github` and `azure-boards`.** Epic 2096 moves both trackers behind the specs service and retires `git` last (S33, 2093). Undoing the deprecation in `cq specs doctor` and in the standard's "Legacy tracker backends" heading is a change of framing that belongs to that retirement. It is parked as a discovery.
- **Webhooks, a local cache and sync** (S11, 2089), and **the MCP write surface** (S7, 2086). This spec proves only that the read port reaches the GitHub adapter.
- **Moving quenching's own store to GitHub Issues.** The command is proved against doubles, and no real repository's issues are written (the epic's policy).
- **New grants, hooks or CI steps, and swapping `Bash(cq …)` for MCP.** These go to epic 2045 (2096 §Design).

## Design

**Dependencies are written through the REST issue-dependencies endpoints, over `gh api`, like every other call this backend makes.** Assumption, named: GitHub's GA (August 2025) exposes `GET /repos/{owner}/{repo}/issues/{number}/dependencies/blocked_by` (lists the blocking issues, each with `number` and `id`), `POST …/dependencies/blocked_by` with `{"issue_id": <the blocking issue's REST id>}`, and `DELETE …/dependencies/blocked_by/{issue_id}`. Task 1.1 encodes exactly these shapes in the offline double. A different live shape is a fixture correction, not a design change. The GraphQL `addBlockedBy` mutation was rejected because every call of this backend is REST through `gh api`, and a second protocol would add a second error path.

**The diff is by issue number, and the REST id is resolved only for an add.** The current set is the `number` field of the `blocked_by` listing. For an add, one `GET repos/{repo}/issues/{n}` reads the blocking issue's `id`. A removal uses the `id` the listing already returned. A dependency the repository does not hold (404) refuses with the dependency's number named.

**Only a write that changes `dependsOn` reads or writes dependencies.** As on Azure Boards (2083), the wanted set is compared with the pre-write `info`. If they are equal, no request is made. The cost of a dependency change is one GET of the listing, one GET per add, then one POST per add and one DELETE per removal.

**The relations are written BEFORE the body PATCH in `write_spec`.** GitHub cannot carry both in one request, so the order decides what a retry sees. If linking fails, the body still holds the old `dependsOn`, the retry still sees a change, and it re-diffs against the live relations. If linking succeeds and the PATCH fails, the retry re-reads the live relations, finds nothing left to do, and writes the body. The order makes the write convergent, though not atomic. The CAS test on `updated_at` stays first, before both. In `create_spec` the issue must exist before it can be linked, so linking runs inside `_finish_create`, and the refusal that names an already-created issue covers it.

**A cap is checked before any request.** Assumption, named: GitHub caps one relation type at 50 issues per issue. A spec whose numeric `dependsOn` exceeds the cap refuses with `sp-gh-dependency-limit` (exit 2), and nothing is written.

**The ids that count are the ones `azure_predecessor_ids` already keeps**: numeric only, never the spec's own id, in declaration order, deduplicated. The selection is shared, and only the transport differs.

**`migrate --to azure` becomes one tracker migration with a destination profile**: its name, its description ceiling (`AZ_DESCRIPTION_MAX` for Azure; none for GitHub, whose body spills into part comments), the refusal wording and the config change (`{"backend": "azure-boards"}` / `{"backend": "github"}`). `migrate_to_azure` stays a wrapper with the same report, so 2084's tests do not move. GitHub, like Azure, allocates its own numbers (shared with pull requests), so the id map, the creation order and the second write for epics are the same code. The `document_matches` check is unchanged: `tags`/`assignee` are native on GitHub, and `start`/`target` stay in the body and compare equal on both sides.

**The binding contracts** are `docs/standards/architecture/spec-backend.md`: a native mapping is valid only when it is the same fact and something reads it back (`predecessor_links` and the migration equality read it back), every store write passes the leak guard (`guard_store_write` stays the first line of both write paths), and the fake is how "identical" stays true (the GitHub double is strict and request-driven, like `GithubRemoteFixture`).

## Alternatives Considered

Reference projects from the epic `holetz/forge#1` §Reference projects (read 2026-10-24), lines for the specs service:

- **MrLesk/Backlog.md — rejected for this member.** Its store is its own markdown folder with an MCP server and a board over it, and it has no tracker adapter. 2085 already took the shape it shows (one store, an MCP port over it), and nothing in it maps `after:` onto a tracker's native dependencies.
- **automazeio/ccpm — adapted.** It is the closest precedent: it syncs PRD/epic tasks into GitHub Issues with dependency mapping over the `gh` CLI. This spec adapts the idea of a frontmatter dependency becoming tracker state, but rejects its mechanism: ccpm keeps dependencies in issue text and task lists, while the GA native `blocked_by` relation is the same fact GitHub's own UI and API read. It also rejects its one-way sync: here the issue body is the store, not a copy.
- **microsoft/azure-devops-mcp — rejected here.** It is Azure-only. Its tool shapes inform the Azure adapter and the MCP write surface (2086), not a GitHub adapter.
- **SVAR Gantt / frappe/gantt — rejected here.** They render, and they have no bearing on storage. The schedule they will draw reads `dependsOn` from the document, never from the tracker relations.
- **`cq specs serve` (`portal.py`) — reused unchanged.** It reads through `open_backend`, so a `github` store reaches it with no change.

Whole-shape alternatives:

- **Sub-issues or a task list in the body for `dependsOn`** — rejected: sub-issues were retired from this backend (HYBRID SERIALISATION, `github.py`), and a task list would be a second encoding of a field the frontmatter already holds.
- **A `spec:after-<id>` label per dependency** — rejected: it fails the standard's rendering test (it is not the same fact as GitHub's dependency, nothing reads it back, and it floods the label registry).
- **GraphQL instead of REST** — rejected in `## Design`.

## Open Decisions

- **Whether the live endpoint shapes and the cap of 50 match the double.** They are decided by the first real run against a scratch repository, which a human runs outside this spec, since no worker writes to a real repository's issues. Until then the double encodes the documented shapes, and `## Risks` carries the mismatch.
- **Why now, and what would make this not worth doing.** `## Problem` gives the why: the git store floods the repository history. It also places this spec in the epic's adapter wave. Only a human can judge whether parity is still worth it if the Azure path alone carries the epic's adopter. The orchestrator's priority order in 2096 §Design is taken as that answer for this pass.

## Risks

- **The live REST shape differs from the double** (path, `issue_id` vs number, response fields). Mitigation: the shapes are one helper and one fixture, and the first live run fixes both. ACCEPTED — no worker may write to a real repository.
- **A write is not atomic across the relations and the body.** Mitigation: links go first, so every retry converges (Design). ACCEPTED — GitHub has no single request that carries both.
- **The migration's predecessor-link equality adds a read per spec.** It is one GET per migrated spec, inside a command run once per store. ACCEPTED.
- **Changing `migrate_to_azure` into a wrapper regresses 2084.** Mitigation: `test_specs_migrate_azure.py` runs unchanged in task 2.1's `verify:`.
- **An undeclared mirror is an out-of-scope diff.** Mitigation: task 3.2 declares every mirror and reruns the generators' `--check` inside the gate.

## Outcome

Shipped. The `github` backend now stores `dependsOn` as native GitHub issue dependencies: one `blocked_by` relation per numeric id. The relations are diffed by issue number and written before the body PATCH, and only when `dependsOn` changed. `predecessor_links` reads them back, and a spec over the 50-issue cap refuses with `sp-gh-dependency-limit` before any request. An MCP `specs_section` read was proved to answer from `GitHubBackend` over the offline double. `cq specs migrate --to github` reuses the Azure tracker migration through a destination profile: no description ceiling, a dependency cap checked in the preflight (`sp-migrate-dependency-limit`), and `{"backend": "github"}` as the printed config change. On both trackers the equality also compares `predecessor_links` with the remapped `dependsOn`. `docs/standards/architecture/spec-backend.md` states the mapping and the new migration direction. The mirrors are regenerated.

The conclude review (Claude plus Codex, every Codex finding reproduced by reading) led to one more commit. A refusal during the read-back now keeps the id map in the report. The cap is refused before the revision-check GET and in the migration dry run. Blocked-by issues from other repositories are no longer read as local ids.

Left out: when an issue is created and a `blocked_by` POST then fails, a later write does not complete the links. This is recorded in Discoveries as a follow-up design choice. The "deprecated" framing of the tracker backends stays until the git store retirement (2093).
