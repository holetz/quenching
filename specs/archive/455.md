## Problem

O deploy grava as mesmas skills em `.agents/skills` e na ponte `.claude/skills`, e o Copilot CLI lê os dois (o VS Code lista nomes duplicados), dobrando o catálogo de descrições (~9,3 mil caracteres) e arriscando corpos divergentes. Além disso, o Copilot ignora em silêncio uma descrição acima de 1024 caracteres, e `quenching-knowledge` já está em 1010 sem que o lint avise.

## Proposal

O deploy publica cada skill que ele gera **uma vez**, no conjunto mínimo de diretórios que cobre os harnesses declarados:

- `--harness claude` (sozinho, ou com `opencode`) gera as skills só em `.claude/skills`. O Claude Code lê apenas esse diretório, e o OpenCode — que lê os dois — encontra a skill ali. Hoje o mesmo alvo recebe duas cópias, e um cliente que lê os dois diretórios (Copilot, OpenCode) as encontra duas vezes na descoberta antes de desduplicar por nome.
- `--harness opencode` (sozinho) e `none` geram em `.agents/skills`, a camada genérica.
- O harness `codex` foi removido pela 287 (ADR 0020); um cliente que leia só `.agents/skills` forçaria essa cópia se voltasse a ser um harness, e hoje nenhum harness declarado está nessa posição.

A ponte `.claude/skills` deixa de espelhar as skills geradas pelo deploy. Ela passa a cobrir só as skills do próprio alvo, e `.claude/skills/.generated-files.json` lista só essas; as geradas são do deploy, hasheadas em `.agents/.quenching-deploy.json`, e `cq deploy --check` as prova.

`release` volta à lista. O `argument-hint` dele é a única sequência de fluxo YAML não citada de toda a superfície; ele passa a ser uma string citada, e `cq components lint` ganha o aviso `sk-frontmatter-strict` para esse formato, para que um cliente que lê YAML nunca receba uma lista onde espera texto.

O orçamento de descrições não muda: as 17 descrições do catálogo publicado cabem no corte de 1.024 que o VS Code trunca (a maior, `quenching-knowledge`, tem 1.010), e o lint na fonte é o guarda das 6 geradas, que não vivem mais em `.agents/skills`.
## Out of Scope

- Link simbólico ou junção para uma cópia física única — o git não versiona a junção, e um symlink quebra o checkout no Windows sem privilégio; [windows-support.md](../docs/standards/platform/windows-support.md) recusa link na ponte, e o deploy não ganha uma exceção. A cobertura mínima resolve o caso sem link.
- Um harness `copilot`, ou detecção de `copilot` em tempo de execução — invariante do épico 453: o cliente é o conjunto de diretórios que ele lê, e o Copilot já lê `.claude/skills` e `.agents/skills`.
- Uma terceira projeção em `.github/skills` — o Copilot já lê os dois diretórios publicados; uma terceira cópia multiplica o que o problema reduz.
- Encurtar as 17 descrições para um orçamento abaixo de 1.024 — a maior tem 1.010 e o lint já avisa acima do corte; não há violação a corrigir, e o corte não muda a lista de skills.
- Mover as skills do próprio alvo para fora de `.agents/skills` — é o lar editável delas; a ponte continua sendo a projeção quando o Claude Code é declarado.
- Provar no CI o catálogo do VS Code — o CI não tem o cliente; a leitura do seletor `/` fica no protocolo ao vivo e no `## Open Decisions`.

## Design

**A publicação é uma cobertura sobre os harnesses declarados, não uma lista de cópias.** Cada cliente é o conjunto de diretórios que lê; o deploy escreve em um diretório apenas quando um harness declarado depende dele.

| Cliente | Diretórios que lê | Fonte |
| --- | --- | --- |
| Claude Code 2.1.332 | `.claude/skills` | sonda `claude -p` num checkout descartável: uma skill só em `.agents/skills` não aparece na lista |
| OpenCode 1.18.35 | `.agents/skills` e `.claude/skills`, o `.agents` ganhando o empate | deploy-mode.md §Verified facts |
| VS Code + Copilot Chat 0.77 | `.agents/skills`, `.github/skills` e `.claude/skills`; desduplica por nome depois | `customizationsDebug.log` de 2026-11-25 11:07:27: 34 locais (17 × 2) antes da desduplicação |
| Codex 0.165.0 | `.agents/skills` | `codex debug prompt-input`; o harness `codex` foi removido pela 287 (ADR 0020), então a linha é limite de cliente, não opção do deploy |

A regra, com `H` o conjunto de harnesses:

- `.claude/skills` é publicado se e somente se `claude` ∈ `H`.
- `.agents/skills` é publicado se e somente se `claude` ∉ `H`.

| Harnesses | Diretórios publicados |
| --- | --- |
| `claude` | `.claude/skills` |
| `claude`, `opencode` | `.claude/skills` |
| `opencode` ou `none` | `.agents/skills` |

A cobertura é mínima porque só `claude` força `.claude/skills`; o OpenCode lê os dois e nunca força um terceiro, e `none` recebe a camada genérica. A desduplicação por nome de um cliente que lê os dois (H1 da 452, `confirmed`) não é mais necessária para o catálogo gerado, porque só um diretório o recebe.

**A ponte pertence ao alvo; as skills geradas pertencem ao deploy.** `.agents/.quenching-deploy.json` já lista em `skills` os nomes que o deploy gera. `bridge.plan` subtrai esses nomes do `expected_tree` e do conjunto de órfãos, e `.claude/skills/.generated-files.json` passa a listar só as skills do próprio alvo. As geradas são escritas pelo deploy com o mesmo marcador e hasheadas no manifesto do deploy. A separação é necessária porque um alvo só-`claude` não tem a fonte gerada em `.agents/skills` — a ponte não pode responder por ela —, e um manifesto compartilhado reportaria as geradas como órfãs da ponte.

**Nenhum link.** Uma cópia física compartilhada exigiria symlink (quebrado em checkout Windows sem privilégio) ou junção (não versionada pelo git). A cobertura resolve o mesmo problema com diretórios que o git carrega; [windows-support.md](../docs/standards/platform/windows-support.md) já recusa link na ponte.

**A descrição cabe no corte do cliente.** O VS Code trunca a `description` em 1.024 caracteres (`truncateAgentSkillDescription` no bundle do cliente), não ignora a skill. O lint já avisa acima do corte (`sk-description-portable`) na fonte de cada skill, e a maior descrição medida tem 1.010; nenhum orçamento novo é necessário. O `## Problem` dizia "ignora em silêncio": o fato medido é "trunca", e a diferença importa porque a skill continua listada com o texto cortado.

**Um campo escalar que o cliente lê por um getter de string precisa ser string.** `argument-hint: [version — optional, …]` sem aspas é uma sequência YAML: o parser deste repositório a lê como o literal, mas um cliente que lê YAML recebe uma lista. `release` é a única skill da superfície com esse formato; a correção é citar o valor, e `_frontmatter_strict_issues` passa a reportar `unquoted-flow-sequence` nesse campo. `migrate.py` já gera o formulário citado — a mão única se alinha ao gerador.

**O upgrade é uma remoção normal.** Passar um alvo antigo para uma cobertura menor reporta as cópias que saem como `delete` em `deploy --check`; `--write` apaga as que ainda têm os bytes registrados e recusa (`ct-deploy-edited`) a que alguém editou, exatamente como qualquer update de três vias. O padrão documenta a mudança de layout; nada é apagado sem `--write`.

### Assumptions

- O alvo do Copilot declara `claude` (para `.claude/settings.json`, hooks e MCP); a publicação em `.claude/skills` o atende, e `opencode` não força a segunda cópia. (`## Proposal`, `## Design`)
- A descoberta do VS Code lê `.agents/skills`, `.github/skills` e `.claude/skills` e desduplica por nome; com o harness `codex` removido, um alvo `claude` publica o gerado só em `.claude`, e `.agents/skills` carrega só as skills do próprio alvo. (`## Design`)
- O `release` ausente na lista do modelo é o único achado de frontmatter desta superfície; a causa ao vivo não está provada e a leitura do seletor a fecha. (`## Open Decisions`)

## Alternatives Considered

- **Link simbólico ou junção para uma cópia física única** — o symlink quebra o checkout no Windows sem privilégio e a junção não é versionada; o padrão de plataforma já recusa link na ponte. A cobertura mínima entrega a publicação única sem tocar no sistema de arquivos.
- **Uma terceira projeção em `.github/skills`** — o Copilot já lê `.agents/skills` e `.claude/skills`; a terceira cópia aumenta o catálogo que o problema reduz e cria mais um registro para manter.
- **Uma ponte magra, com o `SKILL.md` do `.claude` carregando só o frontmatter e um caminho para `.agents`** — o Claude Code leria a descrição e precisaria de um segundo `Read` para o corpo, um turno a mais em toda invocação; o corpo é a skill, não um anexo dela.
- **Publicar sempre só em `.claude/skills`** — um alvo com `opencode` e sem `claude` perderia as skills, porque o OpenCode lê `.claude` **e** `.agents` e o harness não declara Claude; `.agents` é a camada genérica desses alvos.
- **Publicar sempre só em `.agents/skills`** — o Claude Code 2.1.332 não lê esse diretório (sonda `claude -p`); um alvo `claude` perderia todas as skills.
- **Um modo de deploy por cliente (`--harness copilot`, detecção de `copilot`)** — o invariante do épico 453 proíbe ramificar o deploy por nome de cliente; o Copilot é coberto pelos harnesses existentes.
## Open Decisions

- **O `release` reaparece na lista do VS Code depois da citação do `argument-hint`?** Decidido por uma leitura do seletor `/` numa sessão real (o protocolo do `## Validation`), na próxima sessão do cliente. A enumeração de 2026-11-25 é do modelo, não do catálogo do cliente, e a causa da ausência não está provada.
- **Um alvo que declara `claude` e `codex` deve abrir mão de um deles para o Copilot ver uma cópia só?** Decisão do dono do repositório, não do deploy; mede-se com `scripts/copilot_bench.py --target .` e muda-se o `--harness` do alvo, nunca o artefato.

## Risks

- **Um alvo só-`claude` perde a skill se o cliente parar de ler `.claude/skills`** — a sonda de 2.1.332 e o piso `test_deploy_client_contract` prendem o fato; uma versão nova do cliente é re-probada antes de a regra mudar.
- **O upgrade apaga a cópia `.agents` que alguém editou** — a regra de três vias do deploy já recusa `edited` sem `--force`, e a task de teste cobre o caso.
- **A ponte deixa de provar as skills geradas** — `deploy --check` hasheia as duas cópias geradas; a ponte prova as do alvo. `translation-drift.md` nomeia as duas.
- **A ausência do `release` tem outra causa** — ACCEPTED: a correção remove o único campo do tipo na superfície e o lint impede a classe; se persistir, a leitura do seletor reabre a causa (Open Decision).
- **A publicação única muda o layout de um alvo existente** — `deploy --check` reporta a cópia que sai como `delete` e o padrão documenta o upgrade; nada muda sem `--write`.
- **A sonda da 452 mede só as descrições de `.agents/skills`** — as 6 geradas agora vivem só em `.claude`; o corte delas é provado pelo lint na fonte, e a sonda permanece o medidor das skills do alvo.
