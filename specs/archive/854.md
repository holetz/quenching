## Problem

O backend `github` não tem lock entre processos, e o ciclo de escrita é read-modify-write: cada
verbo que escreve (`section --write`, `task`, `record`, `verification`, `discover`, `promote`) lê o
documento inteiro, altera uma parte e faz PATCH do corpo inteiro de volta.

Duas sessões do Claude Code no mesmo repo — o que múltiplos worktrees tornam rotina — podem portanto
sobrescrever uma à outra sem que nenhuma das duas veja nada. Não há ETag, não há `If-Match`, e nada
compara o que foi lido com o que está lá no momento do PATCH.

**Observado**, não hipotético: durante a execução da `evaluate-spec-creation-flow`, um `refined:`
apareceu em `rework-specs-isolate-flow` entre o snapshot da frente e a migração — escrito por outro
worktree deste mesmo repo, na mesma sessão de trabalho.

O backend `files` não tem o problema da mesma forma: ali o git é o árbitro, e uma escrita concorrente
vira conflito visível em vez de sobrescrita silenciosa.

Vale considerar o custo antes de decidir: a API do GitHub devolve ETag por issue, então uma
verificação condicional no PATCH é possível — mas o efeito sobre o número de chamadas e sobre a
recusa que o usuário passa a ver é desenho, não detalhe.

## Outcome

Abandonado a pedido do humano em 2026-08-06, durante o banco shape do /quenching:specs:develop,
na run de /quenching:specs:orchestrate que o conduzia. Nada foi construído: sem branch, sem
tarefa, sem `## Tasks`. Arquivado no estágio `captured`, com o `## Problem` que tinha.

**O problema segue verdadeiro** — o abandono é decisão sobre construir, não sobre o diagnóstico.
Verificado no código durante a interrogação, registrado aqui para quem reler:

- `writer_lock` (`plugins/quenching/assets/bin/specs.py`) isenta os dois backends externos do
  `SpecsLock` com a justificativa *"GitHub and Azure Boards serialise on their own server"*. A
  premissa vale para **um PATCH** e não para o ciclo **read-modify-write**, que é a unidade de
  consistência real da ferramenta — é por essa fresta que a escrita se perde, sem rastro.
- Os workspaces deste repo são worktrees do mesmo clone (`--git-common-dir` comum), que é
  exatamente a topologia do incidente observado na `evaluate-spec-creation-flow`.

A forma que estava na mesa quando o humano parou, com as decisões já tomadas: reinstalar o
`SpecsLock` para backend externo, chaveado no slug do tracker em tempdir
(`<tempdir>/quenching-specs-<uid>-<owner>-<repo>.lock`), mantendo os 10s de espera limitada,
para os dois backends externos — zero chamadas de API. Ficou por decidir se `migrate` entraria
em `command_writes`. Nada disso foi escrito no spec.

Quem retomar: abrir spec nova em vez de desarquivar esta, para que a decisão de abandono
continue legível.
