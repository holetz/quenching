## Problem

After the toolchain contract exists, the plugin still has no `cq toolchain` route, align or status bodies, Codex translation, or goldens to inspect and converge that tree. The first consumer must prove the extracted mold lowers the measured cost of a front while preserving read-only reporting and structural verification boundaries.

## Proposal

- Add the `cq toolchain` route with the probe, inventory, bands and JSON reporting needed to inspect a target toolchain tree.
- Add align and status command bodies that distinguish not-applicable, conformant, mechanical, structural and judgement findings.
- Translate the route into the Codex mirror and add goldens and tests for the new behavior.
- Measure the first consumer's implementation against the front-mold file baseline and a second repository before treating the front as general.

## Out of Scope

- Redesigning the toolchain architecture contract or bands vocabulary belongs to C1; this spec consumes it.
- Automatically choosing a formatter, package manager, lock strategy or language upgrade is out of scope.
- Converging CI pipeline stages or deployment paths belongs to `delivery`; reading CI only for toolchain evidence does not transfer ownership.
- Refactoring unrelated `ops`, `proof` or shared configuration code is out of scope unless a failing test proves the route cannot preserve its declared boundary.

## Design

The route follows the front mold: probe applicability first, inventory only when the tree exists, classify findings through `bands.md`, and expose a structured result before prose. A target with no recognized manifest is not silently clean; it is not applicable according to the declared profile. The route reports judgement findings without choosing for the target.

The first implementation is deliberately read-mostly. It can identify stale or contradictory declarations, but any repair that changes a manifest, lock or tool policy remains an execution task decided by the target owner. The implementation measures its own file count and records the second-repository probe result as evidence for or against the mold.

## Alternatives Considered

- **Implement toolchain as a single shell command.** Rejected because the front needs reusable probe, inventory and finding data for JSON consumers and tests.
- **Make `cq toolchain` an alias of `ops`.** Rejected because manifests and locks have different ownership and lifecycle from entry-point inventory.
- **Auto-repair every structural finding.** Rejected because a lock update, language upgrade or backend choice can be destructive or policy-laden.
- **Ship only the plugin implementation and defer Codex.** Rejected because the mirror is a gated published surface, not optional documentation.

## Open Decisions

- Whether the first route should expose separate `doctor` and `status` verbs or share one read-only result is decided by the front mold's command-body contract and existing route conventions.
- The second repository used for generalization is selected from an available target with a materially different manifest/lock pair; the measurement is recorded with the implementation.

## Risks

- **A static probe reports ecosystem policy as a defect.** Mitigation: keep policy in judgement and only emit mechanical or structural findings when the verifier can decide them.
- **The route becomes a fourth reader of shared manifest keys.** Mitigation: consume A4's arbiter table and treat `security` as a read-only pillar.
- **The first implementation inflates the mold rather than validating it.** Mitigation: measure versioned files and require a second-target probe before C6 integration.
