## Problem

`cq git audit` builds `rewrites.head` from the whole reflog of the worktree's `HEAD` (`quenching/assets/bin/quenching/git/audit.py:984`, `_rewrites(worktree, "HEAD", …)`). A slot worktree is reused across specs (`git/slots.py`), so its `HEAD` reflog still holds the previous branch's life. The `checkout: moving from <previous branch> to <audited branch>` entry moves `HEAD` between unrelated tips. That is not a fast-forward, so `_rewrites` lists it, and the spec-verifier's check 7 (history) fails a clean branch.

Observed twice on 2026-11-20 in a target repository: one spec built in slot-5 (its branch reflog held only commits plus a merge of the base) and an earlier spec whose branch had been ported between repositories. Both got `VERDICT: FAIL` on check 7 for a branch switch, not a rewrite of the audited branch. `rewrites.branch` was empty both times. The conductor had to explain it by hand, and a false FAIL on history trains people to wave history FAILs through.

The fix must keep the guarantee the check exists for: a worker that resets or rebases the audited branch is still caught, through `rewrites.branch` or the `HEAD` moves made while the audited branch was checked out. A `HEAD` move that only switches branches, and everything before the last switch onto the audited branch, are evidence about other branches and not about this spec's work.

## Proposal

- `cq git audit` lists in `rewrites.head` only the `HEAD` moves made since the last switch onto the audited branch; the switch itself and everything before it are no longer reported.
- A worker that resets or rebases the audited branch, with that branch checked out in a reused slot, is still listed in `rewrites.head` and `rewrites.branch`.
- The spec-verifier's check 7 states this reading.

## Out of Scope

- `reflog.head` (the plain move list) keeps the whole `HEAD` history: it is evidence, not a verdict, and judging it stays the verifier's.
- Cleaning or resetting a slot's reflog when it is reused: touching reflogs is the destructive move the audit exists to notice.
- Detecting a worker that deletes or expires reflog entries: already a documented limit of the audit.

## Design

- **Boundary**: in `_rewrites(…, branch=)`, for `HEAD`, find the newest reflog entry whose subject is `checkout: moving from <x> to <branch>` and whose sha the audited branch's own reflog held; keep only the entries newer than it, with the switch as the oldest anchor (never listed). No such entry keeps all entries.
- **Why the sha condition**: a forged subject whose sha the branch never held is no boundary, so a hand-made move cannot hide what precedes it. A forged one that does move the branch is also in `rewrites.branch`, which is unchanged.
- **Binding contract**: `rewrites` and `reflog` are evidence, not proof (`audit.py` docstring); the guarantee kept is the one in `spec-verifier.md` check 7.
- Decision: leave `rewrites.branch` as is; the branch ref's reflog never carries the previous spec's life.

## Alternatives Considered

- Ignore every `checkout:` entry in `HEAD`: rejected, a forged subject then hides a rewrite.
- Drop `rewrites.head` and rely on `rewrites.branch`: rejected, a detached rewrite or a move while `HEAD` was elsewhere would pass.

## Open Decisions

- none — the boundary rule is settled by the Design.

## Risks

- A slot switched A→B→A hides the moves made on A before leaving it from `rewrites.head`. ACCEPTED — `rewrites.branch` still lists any move of the branch ref, and `ancestry` of every `SHAS` entry is still checked.
