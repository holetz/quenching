## Problem

Achado reproduzido pela revisão do épico 404 (2026-11-24). `cmd_claim` chama `claims.machine_id(root)` para toda ação, `list` incluída (`quenching/assets/bin/quenching/specs/commands/claim.py:44`). Essa função gera o id e grava `git config --local quenching.machineId` (`specs/claims.py:63-73`), em vez de usar o leitor que não gera (`_existing_machine`, `claims.py:218`, "a read never generates it"). `specs_claim_list` está na classe MCP `read` (`mcp/catalog.py:107`). Em escopo remoto ele também roda `ls-remote`/`fetch` (`claims.py:113,124`) com `openWorldHint: false`.

**Consequência:** uma leitura escreve no config do clone, e a dica de mundo fechado está errada.

## Proposal

No `list`, usar `_existing_machine` (`mine` fica falso quando não há id), e marcar `openWorldHint` corretamente para os verbos que fazem fetch. Teste: `claim list` num clone sem id não muda `git config --local --list`.

## Out of Scope

- The mirror refs `list` fetches into `refs/quenching/remote-claims/*` (`Store._fetch`) — a local cache of the remote, the same one `claims.snapshot` already writes on every read; it is not configuration and the finding does not name it.
- Changing `acquire`/`renew`/`release`/`take` — they write by definition and keep generating the machine id.
- Reclassifying `specs_claim_list` out of `read` — it stays `read` (`readOnlyHint`); only its `openWorldHint` changes.

## Impact

### Standards this spec will write into docs/standards/

- `docs/standards/architecture/mcp-server.md` — the class table states that a `read` row may carry `openWorldHint: true` when its verb reads the remote

### Product code this spec expects to touch

- `quenching/assets/bin/quenching/specs/claims.py` — a public reader of the clone's machine id that never generates it
- `quenching/assets/bin/quenching/specs/commands/claim.py` — `list` uses that reader
- `quenching/assets/bin/quenching/mcp/catalog.py` — a per-row `open_world` flag, set on `specs_claim_list`
- `quenching/tests/test_specs_claims.py` — `claim list` on a clone without an id leaves `git config --local --list` unchanged
- `quenching/tests/test_quenching_mcp.py` — the annotation of `specs_claim_list`

### Process surface this spec expects to touch

- none — no command body or reference changes; the deployed mirror of the source is regenerated by the deploy.

- `python3 -m unittest discover -s quenching/tests -p test_quenching_mcp.py` — exit 0, including the assertion that `specs_claim_list` is `readOnlyHint: true` and `openWorldHint: true` while `specs_status`-class read tools stay `openWorldHint: false`.
- `QUENCHING_TEST_SCOPE=affected bash scripts/verify_repo.sh` — exit 0 at conclude.

## Design

- **`list` reads the id, never generates it.** `claims.py` already owns the reader for this ("a read never generates it", `_existing_machine`); it becomes public as `existing_machine` and `cmd_claim` calls it for `list`. With no id, `me` is empty: the payload's `holder` is `null` and every row is `mine: false` (`view` already requires `bool(me)`). The other four verbs keep `machine_id(root)`.
- **The open-world hint is a property of the row, not of the class.** `Row` gains `open_world: bool = False`; `annotations()` ORs it into the class annotations. `specs_claim_list` is `Row(..., "read", open_world=True)`: it keeps `readOnlyHint`, because in remote scope it runs `ls-remote` and `fetch`. Precedent: 421 hid the write probe from `git_preflight` rather than reclassifying it.
- **Binding contracts:** `docs/standards/architecture/mcp-server.md` (a `read` row is `readOnlyHint: true`; annotations grant no permission), and the `mcp/coverage.py` exceptions stay as they are.

### Assumptions

- `acquire`/`renew`/`release` already sit in `external` with `openWorldHint: true`, so only `list` needs the flag (Design; Tasks 1.2).

## Alternatives Considered

- Reclassify `claim list` as `external`: rejected — it does not write to the remote, and a read grant for the orchestrator's sweep would then need a wider class.
- A `--no-generate` flag on the verb: rejected — a flag the caller must remember is how a read wrote in the first place; the read verb simply never generates.

## Open Decisions

- none — the finding names the fix and the evidence answers every choice above.

## Risks

- A clone without an id sees `holder: null`; a consumer reading `holder` as a string breaks. Mitigation: the only consumers are `autopilot.md` step and the orchestrator, which read `claims[].mine` and `holder` per row; the test pins the payload shape.
- ACCEPTED — `list` in remote scope still fetches the mirror refs into the clone's ref store; that is a cache of the remote, not configuration, and is out of scope.

## Outcome

`claim list` no longer writes `quenching.machineId`: it reads the clone's id through the public `claims.existing_machine` (empty id → `holder: null`, every row `mine: false`), while `acquire`/`renew`/`release`/`take` still generate it. The catalog `Row` gained `open_world`, set on `specs_claim_list`, so the tool stays `readOnlyHint` and now carries `openWorldHint: true`; `docs/standards/architecture/mcp-server.md` records the class note. Tests: a clone without an id keeps `git config --local --list` byte-identical after `claim list` (fails on the base), and the MCP annotation test pins the hints. The mirror refs `list` fetches stay as they were (out of scope). Reviewed, distilled into the standard, ready for merge.
