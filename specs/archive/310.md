## Problem

Feedback de usuário: "o quenching chama tudo pelo cq na linha de comando. São 503 chamadas a .agents/quenching/bin/cq nas skills e nos subagentes, e nenhuma ao MCP." Medido aqui: 702 ocorrências de `bin/cq` em `.agents/skills`, `.opencode/agents` e `.claude/agents`. A regra de `quenching/references/align/tool-resolution.md:26-29` só diz "prefira" a ferramenta MCP; nenhum grant de agente ou skill nomeia ferramenta MCP (`deploy/translate.py:92-104,166-188` só reescreve `Bash(cq…)`); as classes read/write/external do catálogo (`mcp/catalog.py:11-13`) não chegam a grant nenhum.

**Consequência:** mesmo com o servidor conectado, o modelo segue o texto e paga um processo Python por chamada (0,58 s vs 0,024 s medidos em specs status), e os subagentes não teriam permissão para chamar as ferramentas.

Proposta: tool-resolution.md torna obrigatório chamar a ferramenta `<pilar>_<verbo>` quando o servidor `quenching` está conectado (mapa mecânico `cq <pilar> <verbo>` → nome da ferramenta), e a CLI só quando a ferramenta não existe ou o servidor não conectou (dizendo isso no relatório); os grants dos agentes e das skills ganham as ferramentas MCP por classe, traduzidas por harness (Claude Code `mcp__quenching__<tool>`, OpenCode `quenching_<tool>` em `permission`, Copilot pelo mesmo `.mcp.json`); os corpos de mais uso (specs, git, components read) passam a citar a ferramenta. Absorve as specs 2111, 2112, 2113 e 2114 (escritas para o quenching-mcp por uvx e os nomes antigos dos comandos).

## Proposal

- `quenching/references/align/tool-resolution.md` §Resolving the tool torna **obrigatório** chamar a ferramenta MCP `<pilar>_<verbo>` (o mapa mecânico `cq <pilar> <verbo…>` → `<pilar>_<verbo…>` com `-` e espaço virando `_`) quando o servidor `quenching` está conectado; a CLI fica como fallback declarado só para verbo sem ferramenta ou sessão sem servidor, e o relatório diz qual dos dois.
- `quenching.mcp.catalog` responde, para um prefixo de verbo `cq`, os nomes de ferramenta que o cobrem (linhas do catálogo mais os tools escritos à mão de `specs.mcp.COVERS`), e ganha as linhas dos verbos que `quenching/references/**` cita sem ferramenta (`specs doctor`, `specs schedule`, `specs title`, `specs depends`, `config schema`, `config set`).
- A varredura de cobertura (`quenching/mcp/coverage.py`) cobre também `quenching/references/**`; `specs migrate` e `specs export` entram em `EXCEPTIONS` com o motivo.
- `cq deploy` traduz cada grant `Bash(cq …)` também em grants MCP: no Claude Code, `mcp__quenching__<tool>` em `tools:` dos agentes e em `allowed-tools` das skills (o grant sem escopo vira `mcp__quenching` nas skills); no OpenCode, `quenching_*: deny` seguido de `quenching_<tool>: allow` em `permission`, ou `quenching_*: allow` para quem tem `Bash` inteiro.
- Os onze roteadores `quenching/skills/quenching-*/SKILL.md` dizem, no próprio `## Resolving the tool`, que a ferramenta vem primeiro e a CLI é o fallback.

## Out of Scope

- Reescrever as ~700 citações `cq …` dos corpos para nomes de ferramenta — o mapa mecânico da regra resolve qualquer citação; reescrever cada corpo é churn sem ganho de comportamento.
- GitHub Copilot e Codex: leem o mesmo `.mcp.json`/`.codex/config.toml` que o deploy já escreve e não têm grant por ferramenta que o deploy traduza hoje.
- Registrar o servidor ou mudar o mount (`shared.mcp`) — feito pela 308.
- Hooks sem `uv run` (307) e grants Bash/`external_directory` do OpenCode (2240, 314) — specs irmãs do épico 306.
- Ferramentas MCP novas para `specs migrate`/`specs export` — operações de operador, ficam como exceção declarada.

## Design

- 2026-11-24 — **o grant MCP segue o prefixo do grant `cq`, nunca mais largo.** `Bash(cq specs status:*)` concede exatamente as ferramentas cujo caminho de verbo começa por `specs status` (`specs_status`, `specs_epic_progress`); `Bash(cq git history:*)` concede `git_history_log/show/diff`. A classe read/write/external continua nas anotações e na descrição de cada ferramenta; ela não alarga um grant que a fonte não deu. `Bash` inteiro ou `Bash(cq:*)` concede todas.
- 2026-11-24 — **nomes por harness:** Claude Code `mcp__quenching__<tool>` (agentes: lista enumerada, porque `tools:` de subagente é lista de nomes; skills com grant sem escopo: `mcp__quenching`, a regra de servidor inteiro); OpenCode `quenching_<tool>` como chave de `permission`, avaliada por último-casamento, por isso `quenching_*: deny` vem antes dos `allow` (opencode.ai/docs/permissions, consultado 2026-11-24: "MCP tools … each is checked under its own `<server>_<tool>` name").
- 2026-11-24 — **tradução idempotente:** o deploy local relê o payload já traduzido, então um `mcp__quenching__…` já presente não é duplicado e a segunda passada é byte-idêntica.
- 2026-11-24 — o mapa `cq <pilar> <verbo>` → ferramenta mora em `catalog.tool_names`, a mesma união (`CATALOG` + `specs.mcp.COVERS`) que `coverage.covered()` já usa; uma fonte, dois consumidores (deploy e cobertura).
- Contratos que não se contradizem: `tool-resolution.md` §Resolving the tool (a CLI continua a única forma escrita nos corpos), `docs/standards/agents/communication.md` (pt-BR nas specs).

### Assumptions

- O servidor registrado se chama `quenching` em todo harness (`deploy/mcpfiles.py` `NAME`) — sustenta os prefixos de `## Design`.
- Grant para ferramenta de pilar não deployado é inofensivo: a ferramenta simplesmente não existe — sustenta enumerar a partir do catálogo inteiro.

## Alternatives Considered

- **Grant por classe (todo agente read-only ganha todas as ferramentas `read`)** — rejeitada: alarga o que a fonte concede hoje (o verifier passaria a ler `components session live` etc.) sem decisão humana; o épico autoriza tornar o MCP obrigatório e nada além.
- **Reescrever os corpos para citar `specs_status` no lugar de `cq specs status`** — rejeitada: centenas de edições, e a CLI continua necessária como fallback; o mapa mecânico na regra cobre todos.
- **Wildcard `mcp__quenching__*` nos agentes do Claude** — rejeitada: não é garantido que `tools:` de subagente aceite curinga; nomes enumerados são verificáveis.

## Open Decisions

- none — o mapa, os nomes por harness e o alcance do grant foram decididos por evidência em `## Design`.

## Risks

- Uma versão do OpenCode que não aplica último-casamento entre chaves de topo deixaria `quenching_*: deny` vencer — mitigação: as chaves saem na ordem deny→allow que a documentação prescreve; ACCEPTED — verificação em campo fica com o uso real.
- Linhas novas no catálogo podem conflitar com um parser que exige argumento fora do schema — mitigação: os testes de catálogo descrevem todas as linhas (`described`).
- `allowed-tools` das skills cresce — ACCEPTED: o grant sem escopo vira uma única entrada `mcp__quenching`.
