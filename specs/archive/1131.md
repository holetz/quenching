## Problem

`specs/execute.md:269-290` reimplementa a tabela de precedência do subject de commit de que `commands/git/commit.md:26-42` é dono, e roda `git commit -m` cru em vez de invocar `/quenching:git:commit`. A cadeia `verify && task --check && git add <files> <the spec file> && git commit` (`execute.md:289`, `execution.md:171,180`) assume um arquivo de spec no working tree; sob o backend GitHub a spec é o corpo de uma issue e o `--check` é uma escrita remota, então a garantia "o box viaja dentro do commit" é falsa e o desfazer é outra chamada de rede. O hook `after_specs_execute_task` é anunciado e nunca executado (`execute.md:310-321`), e este repositório o declara. `specs.fanoutMinComplexity` é documentado como chave reconhecida (`plugin-configuration.md:31`), não está em `CONFIG_KEYS`, e `test_specs_doctor.py:199` afirma que é descartado: declarar a chave produz silêncio. `spec-driven.md:34` promete que `low` termina "opening a pull request", mas `conclude.md:270` nunca invoca `pr:create`; `execute → branch` usa `Skill`, `conclude → pr:create → merge` usa prosa. Uma task `[!]` conta como aberta em `promote.py:77` e só `--force`, que o corpo proíbe usar por iniciativa, fecha a spec: não há verbo de descope.

## Proposal

- `execute` delega o commit a `/quenching:git:commit` por `Skill` (ou os dois chamam o mesmo verbo `cq git subject`), apagando a duplicata.
- Reescrever a cadeia para backends externos: `git add <files> && git commit` primeiro, `task --check --subject` depois, com recuo explícito e reportado se a escrita remota falhar; a reference deixa de citar "the spec file".
- Decidir o hook: executá-lo sob a flag `optional`, com relatório, ou retirar a chave da configuração reconhecida.
- `fanoutMinComplexity`: implementar a leitura na seleção de fan-out com finding no doctor, ou retirar da tabela de chaves reconhecidas.
- `low`: encadear `conclude → pr:create` por `Skill` sob essa gear, cumprindo a promessa; `medium` e acima mantêm a oferta.
- `cq specs task --descope <id> --reason`, aceito por `promote` sem `--force`, com a razão em `## Outcome`.

## Out of Scope

- Não redesenhar o backend GitHub/Azure além do protocolo necessário para gravar a task após o commit.
- Não escolher política de hooks, fanout ou descope em silêncio: cada uma será uma decisão explícita e testável.
- Não alterar a semântica de aprovação, revisão, PR ou merge; apenas corrigir os handoffs que esta integração promete.

## Validation

- A cadeia para backend externo faz commit antes da confirmação remota e relata o recuo quando `--check` falha.
- Não há `git commit -m` cru em `specs/execute.md`, e o subject usado por execute é o mesmo do verbo de commit.
- Hook e fanout têm comportamento coberto; nenhuma configuração reconhecida é descartada silenciosamente.
- Uma task descopada aparece fechada com razão, sem `--force`, e não é oferecida novamente por `specs next`.
## Design

O executor separará os dois lados da operação externa. Primeiro executará a verificação, o self-review, o staging e o commit no checkout; somente depois confirmará a task no provider com o subject e a referência do commit. Se a confirmação remota falhar, o commit permanece preservado e o relatório mostra recuo recuperável, sem fingir que a task foi fechada.

A precedência de subject será resolvida por um único helper compartilhado pelo verbo `git:commit` e pelo executor. O corpo de execute citará o verbo responsável por produzir o commit, sem duplicar sua tabela. O arquivo local da spec será opcional: backend externo não exigirá um path que não existe no working tree.

Hooks declarados serão executados somente quando a configuração os habilitar e com a condição/optionalidade reportada; falha de hook não reescreve a task já commitada. `fanoutMinComplexity` será removido se não houver consumidor verificável, em vez de permanecer como chave silenciosa. O descope será um estado explícito, com razão armazenada no Outcome e sem `--force`.

## Alternatives Considered

| Forma | Custo | Benefício | O que fecha | Decisão |
| --- | --- | --- | --- | --- |
| Manter `git commit` e `task --check` antes do commit | pequena alteração textual | conserva o fluxo atual | não representa o provider externo e perde a âncora se a escrita falhar | rejeitada |
| Fazer a task remota carregar o commit por SHA depois | uma leitura/reconciliação extra | tolera subject duplicado | cria um segundo caminho de identidade e muda o contrato de registros | rejeitada |
| Commit local primeiro, confirmação remota depois, com recuo explícito | exige estado intermediário reportado | preserva a verdade em backends externos | requer retry/reconciliação humana quando o provider falha | escolhida |

## Open Decisions

- O hook opcional será considerado informativo: o resultado será reportado e não desfará um commit já realizado; a task 2.1 deve confirmar os códigos de falha com teste.
- O fanout será removido da configuração caso a varredura não encontre uma seleção de executor que o consuma; a decisão será fechada pelo teste de doctor e pelo código de seleção.

## Risks

- Uma falha de rede entre commit e confirmação pode deixar código commitado e task aberta; mitigação: payload com commit/subject e caminho de retry idempotente.
- Dois comandos podem produzir subjects diferentes enquanto compartilham o mesmo commit; mitigação: um resolvedor de convenção e teste de igualdade.
- Um hook destrutivo pode alterar o checkout após o commit; mitigação: hooks declarados só são executados sob a política registrada e nunca integram o resultado silenciosamente.
- `[!]` pode esconder trabalho parcialmente feito; mitigação: descope exige razão persistida e promote só aceita estado fechado explícito.

## Handoff

Executar na branch `holetz/goal`, após validar o tree limpo. O backend desta spec é GitHub; a confirmação de task pode falhar depois do commit, portanto o executor deve preservar o commit e registrar o recuo antes de tentar novamente.
