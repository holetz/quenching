## Problem

Regressão reproduzida pela revisão de correção do épico 1576 (2026-10-12), em `main` df11a0dc, introduzida pela
#1577 (spec 1575). Agora o delete remoto do `cq git prune --remote-branch` leva lease
(`--force-with-lease=refs/heads/<b>:<sha>`), e isso tem dois efeitos:

1. **Um branch que já sumiu do remoto falha para sempre.** Antes, o delete era um no-op com exit 0 e limpava o ref
   de rastreio. Agora sai com exit 1 e o ref de rastreio fica. Como o cleanup proíbe fetch implícito, `cq git stale`
   continua listando o branch, e cada nova tentativa falha com a mesma mensagem, até alguém rodar `fetch --prune` à mão.
   É o caso mais comum: o GitHub com "delete branch on merge" apaga o head de todo PR mesclado.
2. **A recusa chega sem o motivo.** `prune.py:57` descarta o stdout e `:60` reporta só o stderr. Com `--porcelain`, o
   motivo (`!	(delete):refs/heads/m1	[rejected] (stale info)`) sai no stdout, e o JSON fica só com
   `"message": "error: failed to push some refs to '../remote.git'"`. Quem decide não sabe se o branch se moveu ou se
   já sumiu.

Reprodução (bare repo local): apagar `m1` no bare e rodar `cq git prune --remote-branch m1` → exit 1 com a mensagem
genérica. Na base 8d747f48, o mesmo dava exit 0.

Consequência: o `/quenching:git:cleanup` falha justamente nos branches que deveria limpar, e o humano não tem como
distinguir "o branch se moveu" (recusa certa) de "o branch já sumiu" (resultado desejado). A correção distingue os
dois: branch ausente no remoto → ok, com o ref de rastreio removido; lease rejeitado → recusa que cita o motivo do
`--porcelain`.

## Proposal

- `cq git prune --remote-branch <b>` on a branch already absent from the remote exits 0, removes the tracking ref `<remote>/<b>` and says the branch was already gone.
- A lease rejection (the remote tip moved) stays exit 1, the item stands, and the payload message quotes the reason from the `--porcelain` stdout, not only the generic stderr line.
- A regression test per behavior, each red on the current base.

## Out of Scope

- Any `fetch`: the cleanup contract forbids implicit fetch; absence is probed with `ls-remote` on the named branch only.
- Changing `stale.py` or the `/quenching:git:cleanup` body: the verb's fix is enough.

## Design

- Decision: after a failed leased delete, probe `git ls-remote --exit-code <remote> refs/heads/<b>`. Exit 2 (no such ref) means the branch is already gone: remove only the tracking ref with `git branch -dr <remote>/<b>` and report ok. Any other outcome stays a refusal. Alternative rejected: probing before the push (racy, adds a network read on the happy path).
- Decision: the refusal message is the porcelain stdout rejection line (`[rejected] (stale info)`) joined with stderr, so the reason is never dropped.
- Rule: the lease on the reported sha stays; the fix never weakens it. Only local git commands under `audit.SAFE`; no grant, hook or CI change.

## Alternatives Considered

- Drop the lease: rejected, it reopens the #1575 hole (deleting a moved branch).
- `fetch --prune`: rejected, implicit fetch is forbidden by the cleanup contract and touches every ref.

## Open Decisions

- none — the problem statement fixes both behaviors; the wording of the "already gone" message is a task detail.

## Risks

- `ls-remote` unreachable (exit other than 2) must not be read as absent: it stays a refusal. Mitigated by matching exit 2 only.
- ACCEPTED — a branch deleted between the failed push and the probe is treated as gone, which is the desired outcome.
