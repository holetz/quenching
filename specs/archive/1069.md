## Problem

The repository's CI and release pipeline is a repairable tree, but the candidate ledger is stale and its ownership boundary with `proof`, `ops` and the `security` pillar is undefined. The `delivery` front needs an architecture contract, bands and vocabulary that make the pipeline's triggers, jobs and stages convergable without absorbing proof evidence or the plugin's own release command.

## Proposal

- Declare `delivery` as a front whose bounded tree is `.github/workflows/**` or the target provider's equivalent plus release configuration.
- Define mechanical, structural and judgement bands for pipeline triggers, jobs, stages and release reachability.
- Set the ownership boundary with `proof`'s CI evidence, `ops`'s `deploy` entry point, `toolchain`'s runtime declarations and the `security` pillar's read-only permissions audit.
- Record that the front is admitted because its pipeline tree has statically verifiable drift and repairable artifacts.

## Out of Scope

- Implementing the `cq delivery` route, command bodies, tests and Codex translation belongs to C4.
- Taking ownership of proof results, test execution or CI as evidence is out of scope; `proof` remains the gate consumer.
- Taking ownership of deployment entry-point semantics is out of scope; `ops` owns the target's operational route.
- Absorbing the plugin's own `.claude/commands/release.md` or `cq specs release` is out of scope because delivery converges a target pipeline, not the plugin's publication cycle.

## Design

The delivery front owns the pipeline's shape: triggers reach declared jobs, jobs have setup and checkout provenance, stages are reachable, runtimes agree with toolchain declarations, and release paths are reachable from the pipeline. It does not decide which provider, environment or promotion policy a target should choose. Those are judgement findings.

| Band | Examples | Disposition |
| --- | --- | --- |
| Mechanical | generated matrix or manifest stale against its source | report fixable drift |
| Structural | unreachable stage, missing checkout/setup, runtime contradiction, unreachable release path | report conformance failure |
| Judgement | provider, environment, promotion policy, publish scope | report for human choice |

`proof` may read CI output as gate evidence; `ops` may name deploy as an operational entry point; `security` may read permissions. None of those reads gives another axis ownership of the pipeline tree. A4's arbiter-by-key rule governs any shared generated configuration.

## Alternatives Considered

- **Make delivery a pillar.** Rejected because the pipeline is a local tree with statically decidable drift and repairable artifacts.
- **Let proof own all CI files.** Rejected because proof consumes CI as evidence while delivery owns the pipeline's own shape.
- **Fold delivery into ops.** Rejected because deployment entry points and pipeline reachability are different contracts with different verifiers.
- **Treat release configuration as a separate front.** Rejected because it is part of whether the pipeline can reach a release, bounded here with the explicit plugin-release exclusion.

## Open Decisions

- Whether the target tree includes every release configuration file or only files directly reachable from the workflow is decided by C4 against a real target and the pipeline's provider conventions.
- Whether generated job matrices need a delimiter-plus-hash zone or only key ownership is decided with A4's arbiter contract when the first generated workflow is measured.

## Risks

- **Delivery and proof both report the same CI defect.** Mitigation: classify pipeline shape under delivery and execution evidence under proof, with cross-front references rather than duplicate ownership.
- **The front overfits GitHub Actions.** Mitigation: define the provider-equivalent boundary and prove a second provider or target before broadening the implementation claim.
- **Release configuration overlaps the plugin's own release path.** Mitigation: explicitly exclude `.claude/commands/release.md` and `cq specs release` from the target front.
