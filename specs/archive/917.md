## Overview

O ciclo de uma spec (`create` → `develop` → `execute` → `conclude`) já registra parte da ligação entre a spec e o código que a implementa: o record `branch: {base, work}`, o texto livre `subject:` em cada task, e o record `merge: {strategy, subject, pr}` no fechamento. Esta spec fecha as lacunas que sobram — um build sem isolamento não deixa nenhum rastro de branch, o sha de cada commit por task existe no schema mas nunca é escrito, o PR só é conhecido depois que já foi mergeado, e não há como partir de uma branch, um commit ou um PR e achar a spec dona.

Onde o backend (`github`, `azure-boards`) já guarda o mesmo fato nativamente, a spec passa a guardar lá também — nunca duplicando o que o documento já diz, no mesmo padrão que `tags`/`assignee` já seguem. A correção de `/quenching:specs:conclude` para não mergear a PR junto com abri-la, sob o gear mínimo do orchestrate, entra no mesmo esforço porque é exatamente o momento em que o novo record de PR aberto precisa existir.

## Problem

O fluxo de desenvolvimento de specs não registra, na própria spec, o vínculo com a branch que a está desenvolvendo, nem os commits e o PR associados a ela. Isso dificulta rastrear — partindo de uma spec — qual branch, quais commits e qual PR implementam sua proposta, e vice-versa.

## Proposal

- `/quenching:specs:execute` muda seu próprio invariante: quando o humano recusa isolamento, stampa `branch: {base: <base>, work: <base>}` em vez de deixar o record totalmente ausente — uma spec construída in-place deixa de ficar muda sobre onde o código está.
- Um novo record write-many, `pr: {number, url, date}`, guarda o PR assim que ele é aberto — distinto do `merge:` write-once, que só é stampado quando o merge de fato acontece.
- `/quenching:specs:conclude`, ao rodar sob a autorização de gear mínimo do `/quenching:specs:orchestrate`, abre a PR, stampa `pr:` e PARA sem chamar `gh pr merge` — o merge fica esperando revisão humana, como a doutrina do orchestrate já promete e o código hoje não cumpre. Fora do gear mínimo, o comportamento atual (abre e mergeia num bloco só) continua.
- No backend `github`, o PR aberto/mergeado aparece no painel Development da issue de graça, a partir do corpo do `gh pr create` — `branch.work`, antes da PR existir, fica documento-apenas: a API do github não tem como vincular uma branch já existente (só cria uma nova), medido ao vivo (## Design).
- No backend `azure-boards`, uma nova chave declarada `azurePlacement.repository` (sem default, como `areaPath` — sua ausência só significa "sem link nativo", nunca uma recusa) diz qual repositório Azure Repos guarda o código; quando declarada, `branch.work` e o commit de cada task (resolvido pelo `subject:` via `git log --grep`, nunca por um sha novo guardado no documento) aparecem como Linked Work Item (`ArtifactLink`) no work item. O PR fica de fora do nativo do azure-boards — `pr`/`merge.pr` sempre guardam uma PR do **github** (é o `gh pr` que `conclude.md` sabe abrir), e o tipo de artifact link `PullRequestId` do Azure Repos só existe para PRs que são do Azure Repos, então não há mapeamento válido.
- Um novo verbo, `cq specs find (--branch <name> | --commit <sha> | --pr <number-or-url>)`, resolve de volta ao slug da spec dona — para `--commit`, resolve o sha ao subject do commit (`git show -s --format=%s`) e casa contra o `subject:` que cada task já grava, sem nenhum campo novo no documento.
## Out of Scope

- Retrofit de specs já arquivadas — nenhuma spec do passado ganha os novos links retroativamente.
- Backend `files` fica documento-apenas — não há tracker nativo para nativizar nada nele.
- `cq specs find` resolve por igualdade/prefixo exato (mesma resolução do git para sha, número/URL exato de PR, nome exato de branch) — sem busca fuzzy.

## Design

Contratos vinculantes: `spec-driven.md` §Frontmatter (semântica de records), `spec-backend.md` §A native value is the same fact, or it is not a mapping at all (teste que decide o que pode virar mapeamento nativo) e §Placement is declared, and reaffirmed on every write (custo por chamada), `orchestration-gears.md` §Re-evaluating a gear, `specs-execute/git.md` §The subject is the anchor, `plugin-configuration.md` §`azurePlacement`, and the one sub-key with no default (o padrão que `repository` segue).

- **O anchor do commit continua sendo o `subject:`, nunca reativa `--commit` (sha).** `git.md` §The subject is the anchor já documenta por quê: um rebase real deixou specs arquivadas com `commit:` apontando para commits que não existem mais, e foi exatamente essa a razão pela qual o sha foi aposentado em favor do subject, que resolve por `git log --grep` e sobrevive a rebase. `cq specs find --commit <sha>` resolve o sha ao seu próprio subject (`git show -s --format=%s`) e casa contra o `subject:` já gravado em alguma task — sem nenhum campo novo no documento.
- **`branch` em build in-place (`work == base`).** Alternativa: deixar ausente, como hoje. Rejeitada pelo humano — muda o invariante hoje escrito em `execute.md` ("stamp branch: only when isolation was actually taken"), mas fecha a lacuna que o próprio `spec-driven.md` documenta como aceita.
- **`pr: {number, url, date}` novo, write-many, separado de `merge:`.** Alternativa: stampar `merge.pr` mais cedo. Rejeitada — `merge` é write-once e narra que o merge *aconteceu*; stampar antes seria a mesma classe de mentira que este spec corrige em `branch`.
- **`conclude` divide a rota PR em abrir-PR (stampa `pr:`) e mergear (stampa `merge:`)**, o segundo pulado quando a run carrega a autorização de gear mínimo do orchestrate. Alternativa: o orchestrate pular a chamada de merge por fora do conclude. Rejeitada — viola "conduct, never reimplement" do próprio `orchestrate.md`; a correção pertence ao stage que já é dono do merge.
- **Nativo `github` fica só no PR, nunca na branch isolada — medido, não suposto.** A introspecção do próprio schema GraphQL do github confirma: `createLinkedBranch.oid` é "the commit SHA to base the **new** branch on" e `.name` é "the name of the **new** branch" — não existe API pública (REST ou GraphQL) para vincular uma branch que já existe, que é sempre o nosso caso (`execute` já criou ou adotou a branch antes de `branch:` existir). Testado ao vivo contra a issue #917: a mutação recusa (`UNPROCESSABLE`) tanto para um nome novo quanto para o nome já existente; o porcelain `gh issue develop --name <já-existente>` não recusa, mas também não vincula — cria uma branch NOVA e divergente no remoto com o mesmo nome (reproduzido e limpo com `git push origin --delete` no mesmo teste). A visibilidade nativa do github vem só da PR: uma vez aberta com `Refs #<issue>` no body (abaixo), a branch e a PR aparecem de graça no painel Development da issue, sem nenhuma chamada dedicada.
- **Nativo `azure-boards` exige saber QUAL repositório Azure Repos guarda o código — declarado, nunca adivinhado.** `resolve_azure_project` já documenta o porquê, textualmente: "an Azure DevOps remote URL carries an organization and a REPOSITORY, and the repository is not the project" — o board e o código são conceitos independentes neste backend, e não havia, até este spec, nenhuma declaração de qual repositório é o do código. Nova chave `azurePlacement.repository`, sem default (mesmo padrão de `areaPath`), documentada em `plugin-configuration.md`; sua ausência nunca é uma recusa — só significa que este alvo não tem link nativo (a maioria dos alvos `azure-boards` não tem o código no Azure Repos, este próprio repositório incluído: o código deste spec mora no github, então esta run não consegue provar o caminho fim a fim contra a própria issue — só contra um repositório sintético do mesmo org, ver ## Validation).
- **`ArtifactLink` cobre branch e commit, nunca PR, no azure-boards.** O tipo de artifact link `PullRequestId` do Azure Repos só representa uma PR que É do Azure Repos — os records `pr`/`merge.pr` deste plugin sempre guardam uma PR do **github** (é `gh pr create`/`gh pr merge` que `conclude.md` sabe operar; não existe rota `az repos pr` aqui). Vincular um `PullRequestId` do Azure a uma URL do github não é um mapeamento válido — falha o teste do "mesmo fato" de `spec-backend.md` na cara: não é o mesmo artefato.
- **A relação nunca viaja na MESMA chamada PATCH que o documento.** Ao contrário de `parent` (um `System.Parent` só, comparável por leitura normal), um `ArtifactLink` exige `$expand=relations` pra ser lido de volta e diferenciado — custo que este backend não paga em toda leitura. Em vez disso, o link é tentado **uma vez**, só quando o `branch`/commit que o write acabou de gravar for diferente do que o `info` (pré-write) já tinha — comparação interna do próprio documento, nunca uma segunda leitura do Azure. Uma chamada `az boards work-item relation add` separada, que pode falhar e propagar como recusa (mesmo padrão que `GitHubBackend._set_type` já usa: o documento principal já foi escrito com sucesso antes dessa chamada rodar, então uma recusa aqui é reportada alto, nunca engolida — mas nunca desfaz o que já foi gravado).
## Alternatives Considered

- Só documento, sem nativo em nenhum backend — rejeitada; o humano quis nativo nos dois backends externos.
- Nativo só no `github` — rejeitada; o humano quis nos dois backends, provado ao vivo em ambos.
- Separar a correção do PR-vs-merge do orchestrate/conclude para outra spec — rejeitada; o humano decidiu incluir aqui, já que ambas mexem na mesma rota PR de `conclude.md`.

## Open Decisions

- Se o Linked Work Item de branch/commit do `azure-boards` funciona de verdade — **resolvido, ao vivo (task 5.4)**: funciona, contra o work item descartável 965914/965916 no projeto `unicredbr`/TI, usando o repositório sintético `hello-world-java` como alvo (o código deste spec mora no github, não no Azure Repos). Achado que faltava: cada relation `ArtifactLink` também exige `attributes.name` ("Branch"/"Fixed in Commit") — sem isso, a API recusa com 400 mesmo com a URL vstfs correta. `## Design` e o comentário de `AZURE_ARTIFACT_LINK_NAME` registram o achado.
- Se `5.3` (o `Refs #<issue>` no corpo do PR) precisa de prova ao vivo separada — não: é o comportamento de cross-reference já documentado e extensivamente estabelecido do github, não uma API nova; abrir uma PR descartável só para provar isso teria um custo/ruído desproporcional ao que resta a aprender.
## Risks

- O artifact link do `azure-boards` pode não existir para um remoto que não é Azure Repos. MITIGAÇÃO: cair para documento-apenas nesse campo e reportar o achado, em vez de falhar a escrita inteira.
- A chamada nativa do `github` (linked branch) pode exigir um escopo de token que esta sessão não carrega. MITIGAÇÃO: mesmo fallback documento-apenas, achado reportado.
- Dividir a rota PR do `conclude` em abrir-PR e mergear cria um estado intermediário resumível (`pr:` estampado, `merge:` ainda não). MITIGAÇÃO: a própria doutrina de resumability do conclude já lê os records para decidir onde retomar — um re-entry com `pr:` presente e `merge:` ausente lê como "PR aberto, esperando merge ou revisão", nunca reabre um segundo PR.
- `verification: per-task` numa task que chama um sistema externo ao vivo pode falhar por instabilidade transitória de rede. ACEITO — o mesmo risco que qualquer spec `per-task` já carrega; retry é do humano, como qualquer task falha.

## Handoff

- **Armadilha de resolução de root:** sempre invoque `cq` com o caminho explícito a partir da RAIZ do repositório (`python3 plugins/quenching/assets/bin/cq ...`, CWD = raiz). Rodar de dentro de `plugins/quenching` faz o `cq` resolver `root` como `plugins/quenching/.specs` (errado, silencioso) em vez da raiz do repo — já mordeu esta run várias vezes, inclusive dentro de `find.py` (`_commit_subject` rodava `git show` com `cwd=root`, que sob backend github nem existe como diretório — corrigido pra usar `os.getcwd()`, igual `release.py` já fazia). Testes (`unittest discover -s tests`) precisam rodar de dentro de `plugins/quenching`; separe os dois CWDs, nunca deixe um `cd` persistir para a chamada seguinte do `cq`.
- **Backend é `github`:** não existe arquivo local de spec sob `.specs/plans/` — o documento vive no corpo da issue #917. Nunca tente `git add` um arquivo de spec; os commits de cada task só adicionam os arquivos de código/doc declarados em `files:`.
- **`verify:` de teste usa `unittest discover -s tests -p "<arquivo>.py"`, nunca `unittest tests.<módulo>`** — o segundo formato falha (`ModuleNotFoundError: _paths`).
- **O anchor de commit por task é o `subject:`, nunca reative `--commit` (sha)** — `git.md` §The subject is the anchor documenta que o sha foi deliberadamente aposentado (rebase real quebrou specs arquivadas). Ver `## Design`.
- **NUNCA reescreva `## Tasks` inteira sem reler a seção atual primeiro.** `cq specs section ... --write` substitui a seção INTEIRA — já apagou as linhas `subject:` de tasks já commitadas uma vez nesta run porque a reescrita foi feita de memória em vez de a partir de uma releitura. Sempre `cq specs section <slug> Tasks` (ler) imediatamente antes de qualquer `--write` que toque `## Tasks` depois que a primeira task tiver sido commitada.
- **Github não tem API para vincular uma branch já existente a uma issue** (só cria uma nova — `createLinkedBranch`/`gh issue develop` são "create", não "attach"). Medido ao vivo contra a issue #917 nesta run; ver `## Design`. A task de link nativo de branch no github foi derrubada — só a PR (via `Refs #<issue>` no body) dá visibilidade nativa ali.
- Ao tocar `assets/specs/schema.json`, o schema embutido em `assets/bin/quenching/specs/schema.py` (`DEFAULT_SCHEMA`) precisa do mesmo edit (checado por `test_specs_assets.py`), e um record/chave nova que muda a saída de `cq specs list`/`record` precisa de uma entrada nova em `tests/test_golden.py`'s `UNROUTED` (padrão: `specs-status-alpha`/`beta`).

## Outcome

**done** — uma spec agora aponta para a branch, os commits e a PR que a construíram, e a busca
reversa existe. Cinco entregas:

1. **O record `pr`** (`{number, url, date}`, write-many) declarado no schema e documentado —
   distinto de `merge.pr`, que só é stampado quando o merge já foi decidido.
2. **`execute.md` stampa `branch` também em build in-place** (`work == base`), onde antes deixava
   silêncio: registro ausente e "isolamento recusado" passam a ser afirmações diferentes.
3. **`conclude.md` separa abrir a PR de mergear** — sob a marcha mínima do `orchestrate`, a run
   para na PR aberta e deixa o merge para a revisão humana, que é como aquela marcha paga por
   rodar o ciclo inteiro numa autorização só.
4. **`cq specs find (--branch | --commit | --pr)`** — a direção reversa que `list`/`status` nunca
   responderam, sem índice novo: casa contra `branch.work`, `pr`/`merge.pr` e o `subject:` que cada
   task já grava.
5. **O nativo, medido por backend e não assumido.** `github` não tem mapeamento para uma branch já
   existente — `createLinkedBranch` só cria uma nova, medido contra a issue 917 — mas a PR traz a
   branch de graça pelo `Refs #<issue>`. `azure-boards` mapeia branch e commit como `ArtifactLink`
   quando `azurePlacement.repository` é declarado, e recusa a PR no mesmo teste gêmeo:
   `PullRequestId` nomeia uma PR do próprio Azure Repos, não a do github.

**O que a construção revelou.** Uma relação `ArtifactLink` com `url` vstfs correta ainda responde
400 sem um segundo campo independente — `attributes.name`. Nada na ajuda do `az` diz isso; provado
ao vivo (org `unicredbr`, projeto `TI`, work item descartável contra `hello-world-java`).

**O que a revisão de branch revelou, e que a spec não sabia ao ser escrita.** Mudar o *significado*
de um record é uma mudança de contrato: três consumidores de `branch` ainda liam "isolamento foi
tomado". O pior era `cq specs next` — a base está sempre viva, então toda spec in-place ranqueava
como permanentemente em voo. A generalização entrou em `plan-git-record.md`: **uma condição de
expiração que o valor sentinela nunca satisfaz não é guarda, e falha em silêncio na direção do
sempre-verdadeiro.**

**Merge:** estratégia `merge-commit`, rota **pull request** contra `develop`.

**Obrigações de release: nenhuma.** O lockstep move-se uma vez por release, em `develop`, sob
`cq specs release` — nunca no conclude de uma spec.

**Ficou de fora.** `branch.work` fica documento-apenas no `github` em definitivo, não pendente de
API futura. O backend `files` não nativiza nada. `cq specs find` resolve por igualdade exata, sem
busca fuzzy.
