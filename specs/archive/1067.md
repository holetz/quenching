## Problem

The repository has a repairable toolchain tree spanning manifests, locks, language pins and tool configuration, but no architecture contract or finding vocabulary that defines what this front owns. The `toolchain` front must be admitted from measured structural evidence, distinguish mechanical, structural and judgement bands, and stay separate from `.claude/quenching.json` configuration.

## Proposal

- Admit `toolchain` as a named local aligned front for the repository's repairable build-toolchain surface: manifests, locks, language pins, and the tool-configuration blocks those artifacts carry.
- Publish the front's architecture standard in `docs/standards/architecture/toolchain-front.md`, with the front-versus-pillar boundary, the canonical cross-file tree, ownership seams, and the relationship to the shared front mold.
- Publish the front's disposition reference in `plugins/quenching/assets/references/toolchain-align/bands.md` and its Codex counterpart, carrying the mechanical, structural, and judgement bands and the complete stable `tc-*` finding vocabulary.
- Keep `toolchain` separate from `.claude/quenching.json` configuration and from the `ops`, `proof`, `delivery`, and `security` surfaces whose ownership or read-only relationship is declared by the umbrella's measured arbiter proposal.
- Leave policy choices and unmeasured heuristics as reported or open decisions; the declaration does not create a route, verifier, inventory, align body, or target repair.
## Out of Scope

- The `cq toolchain` route, `doctor`, inventory, `bands` command, `align`, `status`, command bodies, and their implementation are C2's build work; this spec declares the contract they will consume.
- Repairs in a target repository, lock regeneration, language-version selection, dependency upgrades, build-backend selection, formatter or ruleset selection, upgrade cadence, and the decision to adopt a lock remain outside this declaration and are settled by the built front or its target owner.
- `.claude/quenching.json` and its shared loader remain configuration work owned by the umbrella's A4/A5 line; the toolchain front names the boundary but does not move keys.
- `[project.scripts]` and operations entry points remain `ops` territory; pytest/coverage and CI gate evidence remain `proof` territory; workflow triggers, jobs, and stages remain `delivery` territory; permission reads remain the `security` pillar's territory. The exact arbiter rows are not re-decided here.
- Conductor ordering, install profiles, public README/catalog claims, and generated bundle index updates remain downstream surface work owned by the siblings named in 1057. This spec writes its standard and runtime reference, not those published listings.
- Product code, domain-specific trees, and a new spec for any parked decision remain outside this spec.

## Design

### Front admission and name

`toolchain` is a front, not a pillar. The umbrella measured a local tree that a probe can find drifted and a verifier can judge statically: `pyproject.toml` declares Python `>=3.11` while two CI workflows say `3.x` and no `.python-version` exists; the development group declares `pytest>=8.0` while `CLAUDE.md` runs `unittest`; and `pyproject.toml` is read by `ops` and `proof` without an arbiter. These are structural seams in repairable artifacts, not only live questions. The name is `toolchain`, not `config`, because `.claude/quenching.json` already owns configuration and `command-surface.md` requires a namespace to name the surface rather than an incidental file home.

The `tc-` code prefix is an explicit assumption, chosen because the shipped `ops` and `proof` vocabularies use short owner prefixes (`op-` and `pf-`) and because `toolchain` must not collide with the configuration subject. C2 must retain or overturn that assumption only with a concrete namespace collision or a target-side naming contract.

### Canonical cross-file tree

The front is a virtual cross-file surface, not a new directory:

```text
toolchain surface
├── manifests: pyproject.toml, setup.cfg, package.json, Cargo.toml
├── locks: uv.lock, poetry.lock, package-lock.json
├── language pins: .python-version, .nvmrc
└── tool-configuration blocks carried by those manifests
```

The list is the candidate family established by 1057, not a promise that every ecosystem exists in every target. C2 decides any extension against a real target corpus before it adds an artifact to the verifier. `.claude/quenching.json` is never a member of this tree: it is the plugin configuration home, and treating it as a toolchain source would recreate the two-source-of-truth seam the umbrella is repairing.

### Ownership boundary

The toolchain contract covers dependencies, locks, language versions, lint configuration, and build-backend declarations. It consumes the arbiter-by-key rule from A4 rather than inventing a second ownership table. The umbrella's measured proposal gives `[project.scripts]` to `ops`, pytest and coverage configuration to `proof`, workflow triggers/jobs/stages to `delivery`, and read-only permission inspection to `security`; the standard must preserve those seams and identify ambiguous shared keys instead of silently claiming them.

CI runtime declarations are evidence for toolchain version agreement, while CI gate invocation is `proof` evidence. A workflow file can therefore be read by more than one front without becoming two owners: the arbiter is about who may write the key, and a pillar that only reads does not receive an ownership row.

### Disposition bands

A band says who may decide closure, not how severe the finding is:

| Band | Decider | Allowed closure |
| --- | --- | --- |
| Mechanical | deterministic source and generated artifact | regenerate or normalize without a per-item policy question |
| Structural | the declared contract under one run authorization | apply a bounded shape repair and re-run the verifier |
| Judgement | the human who owns the target's build risk | report evidence and an executable closing action; never drive the policy change |

The initial vocabulary uses `error` for the seven statically decidable contract violations. No `warn` code is introduced for an unmeasured heuristic. A later warning must carry evidence that the measured thing is exactly what the code names, following the bundle's finding discipline; band and severity remain independent.

### Finding vocabulary

| Code | Band | Severity | Meaning | Closure shape |
| --- | --- | --- | --- | --- |
| `tc-lock-stale` | Mechanical | `error` | A lock artifact is desynchronized from the manifest declarations it records. | Regenerate the lock from the declared ecosystem source and re-run the verifier. |
| `tc-config-duplicate` | Mechanical | `error` | The same toolchain key is declared in more than one configuration home. | Apply the already-declared arbiter and remove the duplicate source; do not choose an owner from file order. |
| `tc-generated-stale` | Mechanical | `error` | A generated tool-configuration block no longer matches its deterministic source. | Regenerate the block from its source while preserving authored text outside the generated zone. |
| `tc-runtime-drift` | Structural | `error` | A language version disagrees across the manifest, CI, pin file, or container declaration. | Align the declarations under the target's chosen version source, or hand the version choice to the target owner when no source is declared. |
| `tc-tool-unpinned` | Structural | `error` | A declared development tool has no reproducible version pin. | Add the pin in the declared toolchain home; selecting a version where none is evidenced remains a target-owner decision. |
| `tc-build-backend-missing` | Structural | `error` | A buildable manifest lacks the build-backend declaration required by its ecosystem contract. | Add or repair the backend declaration only when the target's build contract identifies it; otherwise report the missing decision. |
| `tc-key-unarbitered` | Structural | `error` | A manifest or toolchain key is read by multiple fronts without one declared owning writer. | Apply the shared arbiter-by-key contract; ambiguous ownership is reported rather than selected by the front. |

The complete mapping is intentionally closed:

| Band | Codes |
| --- | --- |
| Mechanical | `tc-lock-stale`, `tc-config-duplicate`, `tc-generated-stale` |
| Structural | `tc-runtime-drift`, `tc-tool-unpinned`, `tc-build-backend-missing`, `tc-key-unarbitered` |
| Judgement | none — policy choices such as formatter, ruleset, upgrade policy, or adopting a lock are not verifier findings until a target contract declares them |

The remedies are capability-shaped, not desired-state prose. C2 must prove the concrete command or handoff named by each closure before presenting a finding; a declaration that says "fix the lock" without an available action is incomplete under `finding-remedy-applicability.md`.

### Artifact split and mold boundary

The bundle standard owns the rule this repository is graded against: what `toolchain` is, what tree it covers, which keys belong to neighbouring fronts, and how admission and bands are interpreted. The plugin reference owns the runtime-facing vocabulary, disposition table, report-ready closure shapes, and the full mapping consumed by future command bodies. The source reference is the authority; the Codex copy is its translated/mirrored form and may differ in platform form only, never in contract meaning.

The references follow B1's front mold and the shared-mold rule: a key or field that only one writer may set stays in that writer's own contract, rather than entering a shared fill-in block. The reference files are installed plugin assets cited by future command bodies with the plugin's absolute reference path; this spec does not create those bodies.

### Ordering and evidence boundary

The standard is written from 1057's measured main-repository evidence, not from the implementation it hopes C2 will create. It does not assert that every target has a Python toolchain, a lock, or a build backend. It asserts that where the candidate artifact exists and a static relation is contractually declared, the front may report or repair that relation; where the target owner must select policy, the result stays in the judgement band or `## Open Decisions`.
## Alternatives Considered

- **Admit `toolchain` as a pillar.** Rejected because 1057 measured a repairable manifest/lock/pin/configuration tree and statically decidable cross-file drift. A pillar would only answer the live state and would leave the convergent artifact shape without an owner.
- **Name the axis `config`.** Rejected because `.claude/quenching.json` already makes configuration a distinct subject; `command-surface.md` also requires the namespace to name what it acts on, not a generic file category.
- **Use one generic `tc-drift` code.** Rejected because the existing `op-*`/`pf-*` vocabularies give one stable code per closure path, and a generic code would force the reader to rediscover whether the issue is a stale generated artifact, a cross-file mismatch, or unarbitered ownership.
- **Absorb `.claude/quenching.json`, workflow ownership, or proof/ops declarations into the front.** Rejected because 1057's arbiter proposal already distinguishes configuration from toolchain and gives neighbouring fronts their write ownership; a broad front would reproduce the shared-file failure it is meant to repair.
- **Publish only the bundle standard and omit the runtime `bands.md`.** Rejected because a standard is the rule this repository grades while a plugin reference is the runtime procedure a command body loads; collapsing the halves would either leave C2 without a mold or make the bundle standard restate command procedure.
- **Publish only the Claude-side reference.** Rejected because the plugin carries a Codex translation surface; a missing mirror would let the two installed forms teach different finding codes or dispositions.
## Open Decisions

- **Whether the front admission holds for targets whose ecosystem already owns the toolchain.** Decide in C2 after probing a second real repository and measuring whether the candidate tree has repairable drift plus a static verifier; if it has only ecosystem-owned policy and no decidable repair surface, return the axis to the umbrella for reclassification rather than building an align by analogy.
- **Which manifest, lock, language-pin, and tool-configuration families the first implementation supports beyond the candidate set measured in 1057.** Decide in C2 against the target corpus and B1's mold before adding an artifact reader; a family without a real target and a static contract remains outside the first implementation.
- **When a lock, pin, backend, or duplicate-key finding is safe for automatic structural closure rather than report-only handoff.** Decide in C2 with a falsification fixture and the remedy-applicability rule: if the target tool, source of truth, or command is not declared, the finding stays judgement/open and the front does not invent one.
- **The exact arbiter table for overlapping manifest and workflow keys.** Decide in A4 against a real target and the ops-registry precedent; C1 consumes that table and must not override it. If A4's result conflicts with this boundary, update this standard before C2 is built.
- **Whether the `tc-` prefix remains the canonical code namespace.** Decide during C2's first vocabulary self-check against the repository's command/finding catalogues; a collision or existing naming rule is the only evidence that reopens the explicit assumption above.
## Risks

- **The ecosystem-owner assumption is false.** `uv`, `poetry`, `cargo`, or a CI provider may already be the strongest owner of a target's build policy, making a plugin front overreach. Mitigation: C2 measures a second repository and requires a repairable tree plus static verifier before building the route. ACCEPTED for this declaration only as an open decision, not as proof that every target should adopt the front.
- **Shared files acquire contradictory owners.** `pyproject.toml` and workflow files are already read by `ops` and `proof`, and later `delivery`/`security` work increases the overlap. Mitigation: consume A4's arbiter-by-key contract, keep read-only pillar access distinct from write ownership, and let `tc-key-unarbitered` report ambiguity instead of choosing by path order.
- **A mechanical band implies an unsafe network or policy action.** Lock regeneration and adding a pin can change dependency resolution or the supported runtime. Mitigation: mechanical closure is permitted only when the deterministic source and target command are declared; otherwise the code remains report-only/judgement and C2 must show the refusal or handoff.
- **The seven codes are over-generalized from one Python repository.** The live evidence is strong for this checkout but not for every ecosystem. Mitigation: keep the candidate family explicit, park extensions as open decisions, and validate each new code against a real target fixture before it enters the complete mapping.
- **The bundle standard and plugin mold drift.** The standard and runtime reference have different owners and validators, so one can appear healthy while the other teaches a changed contract. Mitigation: write the source and mirror in the same pass, compare their seven-code mapping, and run the translation check before C1 closes.
- **A remedy teaches an action the surface does not offer.** This would make the finding output permanently untrustworthy. Mitigation: require C2 to prove every concrete closure command or state an honest manual/target-owner handoff; no C1 prose will invent a `cq toolchain` command before C2 ships it.
