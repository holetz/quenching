## Problem

Security questions about workflow permissions, secret coverage, advisory dependency configuration and access ownership are live facts, but their candidate trees belong to other fronts or are not independently convergable. The plugin needs a read-only `cq security` pillar on the `git` precedent, with no align, doctor, bands file or conductor row.

## Proposal

- Declare `security` as a pillar that answers live target questions without converging a tree.
- Add a read-only `cq security` route and one status/audit body with structured results.
- Cover workflow permissions, secret and ignore coverage, advisory dependency configuration and access ownership as live questions.
- Translate the pillar route into the Codex mirror and explicitly ship no align, doctor, bands file or conductor row.

## Out of Scope

- Building a security front with an owned tree is out of scope because each candidate tree belongs to another front or is not independently convergable.
- Repairing workflow permissions, ignore rules, dependency configuration or access policy is out of scope; the pillar reports and the human decides.
- Adding `security` to the conductor or giving it `doctor`, `validate` or `bands.md` is out of scope by definition.
- Replacing existing hygiene rules in knowledge or component references is out of scope; the pillar reports their live presence where relevant.

## Design

A pillar answers questions about current state and does not promise to repair a canonical tree. `security` reports which workflow grants which permissions, which secret classes are covered by ignore rules, whether advisory dependency configuration exists, and who may touch the relevant surface. The output is read-only JSON with question-specific evidence and an honest not-measured result where a target does not expose a comparable source.

The pillar has no bands file because bands classify drift a front can converge; it has no doctor because doctor is a front verifier; and it has no conductor row because the conductor runs converging fronts. It may read delivery and toolchain evidence without taking their ownership.

## Alternatives Considered

- **Mint `security` as a front.** Rejected because its candidate trees are keys or artifacts owned by other fronts and its useful result is a live answer.
- **Distribute security findings without a command.** Rejected because a pillar exists to let a human ask the question directly, as `git` already does.
- **Make security write fixes.** Rejected because permissions, secrets and access policy are irreversible or judgement-laden human decisions.
- **Add front-style bands and doctor for symmetry.** Rejected because symmetry would invent convergence for an axis that has none.

## Open Decisions

- Whether the first route exposes one audit verb or one verb per question is decided by the `git` pillar's report mold and the number of independent live answers a target can provide.
- Whether secret coverage includes only ignore rules or also environment/pipeline injection is decided by the target evidence, with unsupported sources reported as not measured.

## Risks

- **Users mistake a report for a security guarantee.** Mitigation: label each answer with evidence and never claim conformance or remediation from absence of a finding.
- **The pillar drifts into front behavior.** Mitigation: test for no align, doctor, bands file and conductor row and keep the architecture boundary normative.
- **Reading secrets leaks them.** Mitigation: report secret classes and paths, never values, and preserve the existing no-ingest hygiene rule.
