## Problem

Visto em 2026-11-24 nos épicos 306, 326 e 335 (autopilot, 3 orchestrators em paralelo): segundo o relatório do orchestrator do 326, todo merge deixou um PR irmão DIRTY ou UNKNOWN, e o único conflito, todas as vezes, foi `.agents/.quenching-deploy.json` (o manifesto do deploy, regenerado por `cq deploy --target . --write` em toda spec que toca a fonte). Cada conflito custou um spawn de runner para fazer merge da main (332, 330, 336, 331, 315, 309…), mais uma espera de 1–3 min pelo check "Gate (Python 3.11)".

**Consequência:** com specs em paralelo, o custo de merge cresce com o número de membros: um spawn extra e uma rodada de CI por PR, por um arquivo que é derivado.

Proposta: tornar o manifesto mesclável ou derivado no merge — uma linha por arquivo em ordem estável (sem campos agregados que mudam a cada deploy), um merge driver `.gitattributes` que regenera o arquivo, ou tirar do manifesto rastreado o que muda a cada deploy. Provar com dois branches que tocam fontes diferentes e fazem merge sem conflito.

## Proposal

- Os dois manifestos de hash que o deploy grava e o git rastreia (`.agents/.quenching-deploy.json` e `.claude/skills/.generated-files.json`) passam a separar cada entrada de `files` por uma linha em branco: duas specs que mudam entradas vizinhas fazem merge textual sem conflito, inclusive no merge feito pelo GitHub.
- Os três pontos que gravam esses manifestos usam um único serializador, que continua JSON válido e com o mesmo conteúdo lido de volta.
- Um teste prova com `git merge-file` que duas mudanças em entradas adjacentes mesclam sem conflito, e que o formato antigo (sem separador) conflita nas mesmas condições.
- O padrão sobre o manifesto (`docs/standards/architecture/deploy-mode.md`) registra a regra.

## Out of Scope

- Merge driver de `.gitattributes` que regenera o arquivo: o merge do GitHub (`gh pr merge`, o botão, o cálculo de DIRTY/UNKNOWN do PR irmão) não executa drivers customizados e o driver depende de `git config` local, não rastreado.
- Tirar os hashes do manifesto rastreado: o `cq deploy` os usa para distinguir edição do usuário de atualização upstream.
- Conflito real, quando duas specs editam o mesmo arquivo fonte (mesma entrada de hash): continua conflito, e o arquivo implantado conflita junto.

## Impact

### Standards this spec will write into docs/standards/

- `docs/standards/architecture/deploy-mode.md` — o manifesto separa cada entrada de `files` por linha em branco, para o merge textual

### Product code this spec expects to touch

- `quenching/assets/bin/quenching/common/deploy.py` — o serializador único `dumps_hash_manifest`
- `quenching/assets/bin/quenching/deploy/cli.py` — grava `.quenching-deploy.json` pelo serializador
- `quenching/assets/bin/quenching/deploy/tree.py` — o `.generated-files.json` embutido na árvore pelo serializador
- `quenching/assets/bin/quenching/components/commands/bridge.py` — o mesmo manifesto, gravado pelo `cq components bridge`
- `quenching/tests/test_deploy.py` — a prova do merge

### Process surface this spec expects to touch

- none — a mudança é no gerador do manifesto; os espelhos (`.agents/`, `.claude/`, `.opencode/`, `.agents/.quenching-deploy.json`, `.claude/skills/.generated-files.json`) são regenerados por `python3 quenching/assets/bin/cq deploy --target . --write`.

## Validation

- `python3 -m unittest discover -s quenching/tests -p test_deploy.py` — o teste novo mescla duas mudanças adjacentes sem conflito (`git merge-file` exit 0) e o JSON lido de volta é igual ao do formato antigo.
- `python3 quenching/assets/bin/cq deploy --target . --check` — exit 0 depois do redeploy: o manifesto novo é o que o gerador produz.
- `QUENCHING_TEST_SCOPE=affected bash scripts/verify_repo.sh` — gate verde, inclusive `deployed surface lockstep`.

## Design

- **Decisão: uma linha em branco entre as entradas de `files`.** O git trata duas mudanças encostadas (linhas vizinhas) como conflito; com uma linha intacta entre elas o merge é limpo. Medido com `git merge-file`: base `a b c d e`, mudanças em `b` e `c` → exit 1; com linha em branco entre cada par → exit 0. JSON admite espaço em branco entre pares, então `json.loads` lê igual e nenhum leitor muda.
- **Decisão: um serializador em `common/deploy.py`, usado pelos três escritores.** O `.generated-files.json` é gravado por `deploy/tree.py` (bytes comparados pelo `deployed surface lockstep`) e por `cq components bridge`; todos precisam dos mesmos bytes.
- **Por que não driver:** o conflito aparece no PR irmão calculado pelo GitHub, que não roda driver; só o formato textual resolve ali.
- Binding: `docs/standards/architecture/deploy-mode.md` (layout do alvo) e o contrato LF de `.gitattributes`.

### Assumptions

- Conflito restante só quando duas specs editam a mesma entrada (mesma fonte), o que também conflita no arquivo implantado — `## Out of Scope`.

## Alternatives Considered

- Merge driver `.gitattributes` que regenera o manifesto: perdido, porque o merge do GitHub ignora drivers e o driver exige `git config` local.
- Remover os hashes do manifesto rastreado: perdido, porque o deploy os usa para detectar edição do usuário.
- Um arquivo de hash por arquivo implantado: perdido, 450+ arquivos de ruído por um problema que um separador resolve.

## Open Decisions

- none — o formato e o escopo estão decididos pela medição em `## Design`.

## Risks

- Um leitor que dependa dos bytes do manifesto: o `check` compara o JSON lido (`current != built["manifest"]`) e o `deployed surface lockstep` compara o resultado do gerador com o disco, ambos regenerados pelo mesmo serializador; o teste de `.generated-files.json` roda no gate.
- Alvos com manifesto no formato antigo: o primeiro `cq deploy --write` o reescreve no novo formato (um diff único); `json.loads` lê os dois.
