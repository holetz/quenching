## Problem

Medido em 2026-11-24 (cProfile): `cq specs list` leva 2,1–2,5 s, ~2 s de CPU: `cmd_list` (`quenching/assets/bin/quenching/specs/commands/read.py:71`) chama `backend.read_spec` 1048 vezes e cada `read_spec` (`specs/backends/git.py:528`) refaz `list_specs()` (`:509`) inteiro — 1049 × `_index` (`:490`, 1,37 s) e 1,1 M `_descriptor`. O backend já tem o caminho em lote `read_specs(ids)`. Toda leitura fora da janela de `FETCH_TTL_S = 30` (`git.py:50`) paga um fetch de ~0,45 s (`git.py:278`). O backend azure é importado com backend git (8 ms por chamada).

**Consequência:** list, validate, next --front e toda varredura do autopilot pagam segundos por chamada, e crescem com o store.

Proposta: varreduras por `read_specs` (ou `_index` memorizado por tip); TTL de fetch maior para leitura, fetch obrigatório mantido antes de escrita; import do azure sob demanda. Meta: `specs list` ≤ 0,6 s com 1000+ specs.

## Proposal

`cmd_list` lê todas as specs com uma única chamada `backend.read_specs(ids)` (um índice, um carregamento em lote dos blobs) em vez de `read_spec` por spec, que refaz o índice inteiro a cada chamada. Meta: `specs list` ≤ 0,6 s com 1000+ specs.

## Out of Scope

- none — o TTL de fetch (`FETCH_TTL_S`) e o import do azure ficam como estão: testes fixam `FETCH_TTL_S` e `open_azure_backend`, e `cards.py` importa o azure de qualquer modo. Registrado em `## Discoveries`.

## Impact

- `quenching/assets/bin/quenching/specs/commands/read.py` — `cmd_list`.
- `quenching/tests/test_specs_git_backend.py` — teste do caminho em lote.
- Process surface this spec expects to touch: none — mudança de código do CLI, sem comando, referência ou padrão.

## Validation

- `python3 -m pytest quenching/tests/test_specs_git_backend.py -q` verde, com o teste novo.
- `cq specs list` no store real devolve as mesmas linhas de antes, em ≤ 0,6 s.

## Design

`cmd_list` chama `backend.read_specs([s["id"] for s in specs])` uma vez; a linha de uma spec sem retorno (`None`) mantém o fallback `derive_info(s, "")` com `unreadable`. O backend base já implementa `read_specs` por `read_spec`, então github, azure e memory seguem corretos.

### Assumptions

- Chaves de `read_specs` são `str(id)` — confirmado em `git.py` e `base.py`.

## Alternatives Considered

- Memorizar `_index` por tip: corrige todas as varreduras, mas mexe no backend e na invalidação; a varredura em lote já existe e basta.

## Open Decisions

- none — TTL e import lazy do azure adiados, ver Discoveries.

## Risks

- Backend sem `read_specs` próprio cai no default do base (mesmo custo de antes); sem regressão.

## Outcome

Shipped: `cmd_list` in `quenching/assets/bin/quenching/specs/commands/read.py` now reads the whole front with ONE `backend.read_specs(ids)` call instead of `read_spec` per spec, which re-listed the store each time (O(n²)). A regression test in `quenching/tests/test_specs_git_backend.py` fails if `list` goes back to a per-spec read. The deployed mirror was refreshed (the lockstep check requires it). Reviewed, distilled (nothing crosses to /docs/), ready for merge.

**Target not met.** The spec aimed at `cq specs list` ≤ 0.6 s on the real store; measured 2.3 s → 1.5 s. The remaining ~1.5 s is `derive_info`/`parse_sections` over 1058 docs, which only a parse cache can cut to ≤ 0.6 s. The validation line "≤ 0,6 s" is therefore NOT satisfied; the O(n²) loop is gone but the latency target is open.

Left out (decided, recorded in Discoveries): fetch TTL and lazy azure import — tests pin `FETCH_TTL_S`/`open_azure_backend` and `cards.py` imports azure anyway. Follow-up captured as a new spec through the step-6 sweep: a parse cache for `derive_info`/`parse_sections`.
