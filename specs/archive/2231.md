## Problem

`quenching/assets/bin/quenching/common/config.py:401-408` computes only top-level `unknownKeys`; unregistered leaves inside known namespaces (`shared`, `specs`, …) are never checked. `config/__init__.py:133-155`: `cq config check` lists only missing seeded keys.

Reproduced in a temp repo (autopilot 2026-11-21 round 4, origin/main c29ba1e46): `{"backend":"git","shared":{"autonomy":{"maxWorker":8}}}` → `cq config check --json` only reports `shared.autonomy.maxWorkers` missing, `cq specs doctor` says `OK — workspace conforms`, `cq config show` has no trace of it. Worse: `{"specs":{"backend":"git"}}` → `cq specs config` shows `backend: github`, doctor OK, and `cq specs new` tried to create a GitHub issue via `gh`.

Consequence: a hand-edited typo silently yields the default — another worker ceiling, merge policy, or specs going to GitHub Issues instead of the `quenching` branch — contradicting the `setting()` docstring (`common/config.py:543-548`, "a typo never changes a limit silently"). Fix direction: compare leaves against the registry/schema and report unknown leaves in `config check` and `specs doctor` (a warning; free-form namespaces such as subjects and hooks exempt). Reporting only — no grant or executable surface changes.

## Proposal

Add one reader, `unknown_leaves(document)` in `quenching/assets/bin/quenching/config/schema.py`, that walks the five known namespaces (`shared`, `specs`, `ops`, `proof`, `delivery`) of the **repository** document and returns, sorted, every dotted leaf that nothing reads:

- a leaf is **known** when `scope_of(key)` finds it or an ancestor in `REGISTRY` (a registered `object` catalog — `shared.hooks`, `specs.subjects`, `proof.layers`, … — exempts its whole subtree, as `registry_leaves` already cuts there);
- a leaf whose first segment under `shared` or `specs` is one of the keys `quenching/specs/config.py` reads from the **merged** `shared`+`specs` view (`CONFIG_KEYS` without `backend`, plus `BRANCH_CONFIG_KEYS`) is known, subtree included — so `specs.worktreeSetup` or `shared.subjects` stay silent, because the code reads them;
- `specs.store` is known, subtree included: `specs/store.py` reads it and already owns `sp-store-unknown-key`;
- top-level keys are out of this reader: they are `unknownKeys`, already reported as `sp-config-unknown-key`.

Two reporters consume it, both **reporting only**:

- `cq config check` adds `unknown: [...]` to its payload and a `keys nothing reads:` block to the human text; `ok` is false and the exit is 1 (findings) when `missing` or `unknown` is non-empty — the same findings exit `missing` already uses;
- `cq specs doctor` emits one `sp-config-unknown-leaf` finding at level `warn` per leaf, naming the key and the remedy (the registry key it most likely meant is not guessed; the remedy points at `cq config schema`).

`shared.autonomy.maxWorker` and `specs.backend` — the two reproductions in `## Problem` — are both reported by both commands.

## Out of Scope

- `cq doctor` (`common/doctor.py`) and its `config` block: it keeps printing only the missing seeded keys. The nearest lookalike, parked as a discovery.
- The user layer (`~/.config/quenching/…`) and the local layer: they already carry `ignoredKeys` / `ignored`; this spec reads only the repository document.
- Any refusal: an unknown leaf never stops a command, never changes a default and never changes what `load_config` returns.
- Guessing the intended key (`maxWorker` → `maxWorkers`): a suggestion is a UX nicety, not the silent-typo fix.
- Grants, hooks, executables and CI: epic 2224 §Boundaries — reporting only.
- `quenching/README.md`'s one-line description of `cq config check` (still true, only less complete) — parked as a discovery for conclude.

## Design

- 2026-11-21 — **One reader, two reporters.** The leaf comparison lives beside `REGISTRY` (`config/schema.py`), the one registry `cq config set` already validates against, so `check` and `doctor` cannot disagree on what is known. `common/config.py` stays untouched: it sits below `config/` and must not import the registry (which imports `codex`, `session`, `config.autonomy`).
- 2026-11-21 — **Known = what the code reads, not only what the registry lists.** `specs/config.py:load_config` merges `shared` and `specs` (`for name in ("shared", "specs"): values.update(...)`) and reads `CONFIG_KEYS`/`BRANCH_CONFIG_KEYS` from that merge; `specs/store.py` reads `specs.store`. Flagging those would be a false warning on a key the code honours. `backend` is excluded because `_read_backend` reads it only at the top level — which is exactly why `specs.backend` is the reproduction.
- 2026-11-21 — **The specs keys are imported, not restated.** `unknown_leaves` imports `CONFIG_KEYS`/`BRANCH_CONFIG_KEYS` from `quenching.specs.config` inside the function (deferred, as `specs/config.py` itself defers its own imports), so the two lists cannot drift.
- 2026-11-21 — **Exit code.** `cq config check` already exits 1 (findings) on a missing key; an unknown leaf is the same kind of finding, so it shares the exit. `doctor`'s finding is `warn`, so `doctor`'s exit (1 only on errors) does not move.

### Assumptions

- Every leaf the code reads inside a namespace is either in `REGISTRY`, under a registered catalog, in the specs merged read, or `specs.store` (checked by grep of `namespace(…).get(…)` and `shared.get(…)` across `quenching/assets/bin/quenching`). Depends on it: `## Validation`'s "this repository's config reports `[]`" test, which is the tripwire if it is wrong.

## Alternatives Considered

| Approach | Cost | Buys | Forecloses |

| **A (chosen):** reader in `config/schema.py` against `REGISTRY` plus the specs merged read; reported by `check` and `doctor` | one function, two call sites | one definition of "known", reused by both reporters | nothing |
| B: compute it in `common/config.py:load_config` as `unknownLeaves` | an import of the registry into `common/` | every consumer sees it | `common/` importing `config/` inverts the layering (`config.schema` imports `codex`, `session`) |
| C: compare against `seed_document` (as `missing_keys` does) | none | trivial | the seed omits every optional key (`workHost.target`, `ops.*`, `proof.*`, catalogs) — dozens of false warnings |
| D: refuse unknown leaves | a breaking change | strictness | breaks every hand-edited config with a stray key; epic 2224 §Boundaries says reporting only |
