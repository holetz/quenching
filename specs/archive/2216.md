## Problem

Durante a execução da spec 2209 (2026-11-20) observou-se que `acquire` libera um slot tomado cuja branch já foi mergeada (`quenching/assets/bin/quenching/git/slots.py:238-247`, `_take`) apenas trocando a branch. Os arquivos ignorados de `.quenching/handoff/` continuam no slot e vazam para a spec seguinte, em vez de irem para o checkout principal.

A 2209 fez `cq git worktree release` mover `.quenching/handoff/` para o checkout principal (`_move_handoffs`, sem sobrescrever, sufixo `-<slot>-<n>`); o caminho de `_take` não passa por esse release. A melhoria precisa tornar impossível que um slot reaproveitado entregue à próxima spec um handoff da anterior, sem perder o handoff.

**Insumos**

- quenching/assets/bin/quenching/git/slots.py:238-247 (`_take`) e `_move_handoffs` / `release` no mesmo arquivo
- spec 2209, `## Discoveries`, segunda linha; tarefa 1.1 (release move o handoff)
- a correção vive no checkout do quenching e chega aos alvos por `cq deploy`

## Proposal

- `cq git worktree acquire` that reuses a slot (free or a merged holder) moves that slot's `.quenching/handoff/` to the primary checkout before handing it over.
- The move never overwrites and never discards: a name already taken gets the `-<slot>-<n>` suffix, the same rule as `release`.
- The acquire payload reports what moved under `handoff`, and the human output prints one line per file.

## Out of Scope

- `.quenching/codex/` — `release` archives it; extending acquire to it is a separate decision (parked, not requested).
- Changes to `release` or `_move_handoffs` themselves — already correct (spec 2209).

## Impact

### Process surface this spec expects to touch

- `quenching/assets/bin/quenching/git/slots.py` — `_take` and `acquire` move the handoff on reuse
- `quenching/tests/test_git_worktree_slots.py` — tests for both reuse paths
- `.agents/quenching/assets/bin/quenching/git/slots.py` — deployed mirror regenerated by `cq deploy`
- `.agents/.quenching-deploy.json` — deploy manifest re-stamped by the same deploy

## Validation

- `cd quenching/tests && python3 -m unittest test_git_worktree_slots test_git_slot_reclaim` passes.
- A merged holder reacquired at the ceiling leaves its `.quenching/handoff/next.md` in the primary checkout and none in the slot.
- A free slot reacquired with a handoff, with a same-named file already in the primary, keeps the primary's file and receives the other under a suffixed name.
- `bash scripts/verify_repo.sh` (affected scope) is green, including `deployed surface lockstep`.

## Design

- Decision: the move lives in `_take`, at the two points where an existing slot is handed over (free-and-clean, merged holder after re-lock), reusing `_move_handoffs` — the single implementation `release` uses. Evidence: epic 2223 Design 2026-11-21 (moved, never discarded).
- The move runs only after the clean check and the lock succeed, so a taker that loses the race moves nothing.
- Durable rule: a slot handed to a new spec carries no handoff of the previous one.

### Assumptions

- The slot's `.quenching/handoff/` is ignored content, so `_dirty` does not see it and the clean check cannot already block on it — Design, Validation.

## Alternatives Considered

- Route the merged-holder path through `release`: rejected, `release` detaches and deletes the branch, which `acquire` then redoes; a two-line reuse of `_move_handoffs` is smaller.
- Refuse to reuse a slot that holds a handoff: rejected, it would shrink the pool for a recoverable situation.

## Open Decisions

- none — the epic Design settled move-not-discard and the scope.

## Risks

- A handoff moved while the previous spec's session still reads it: the merged-holder precondition (branch merged, tree clean) already says that spec is done. ACCEPTED — same precondition as `release`.
- A move failure mid-way raises out of `acquire` with the slot locked: ACCEPTED — the files are moved one by one, none deleted before moved, and the lock names the taker for `release`.
