## Overview

Esta spec muda como `/quenching:specs:execute` fecha uma seção do `## Tasks` de um plano: hoje
cada task tickada gera seu próprio commit (chain `verify && tick && commit`). A proposta mantém
essa chain intacta task a task, mas ao fechar a última task de uma seção sem tasks bloqueadas, faz
um squash local (`git reset --soft` + recommit) que colapsa os commits daquela seção em um só, com
o subject nomeando a seção em vez de uma task. A garantia de retomada task-a-task durante a
execução de uma seção em andamento não regride — só o commit final que sobrevive no histórico
muda.

## Problem

Reduzir a quantidade de commits para 1 commit por seção. Hoje /quenching:specs:execute
tica cada task com o assunto do commit correspondente, produzindo um commit por task
concluída — a proposta é agrupar esses commits para que cada seção do plano gere um
único commit.

## Proposal

- Cada seção (`### N. <Título>`) executada por `/quenching:specs:execute` passa a corresponder a
  exatamente 1 commit no branch, em vez de 1 commit por task.
- O subject desse commit único nomeia a seção, seguindo a mesma convenção declarada em
  `specs-execute/git.md` para subjects de task.
- Cada task continua sendo verificada e tickada individualmente antes do squash — a rede de
  segurança de retomada task-a-task, durante uma seção ainda em andamento, não regride.
- Uma seção com uma task bloqueada (`[!]`) não é squashada — os commits individuais dela
  permanecem visíveis até a seção fechar de verdade.
- A política `verification` (`per-task` / `per-section` / `end-of-plan`) continua decidindo quando
  `verify:` roda; nada nela muda.

## Out of Scope

- A política `verification` — quando `verify:` roda não muda, só o agrupamento do commit
  resultante.
- As convenções gerais de commit messages em `specs-execute/git.md` — só a subject line do commit
  squashado por seção é decidida aqui.
- O squash pré-merge de `/quenching:specs:conclude` — permanece fora; conclude continua revisando
  e mergeando o branch exatamente como hoje, sem ganhar lógica de squash própria (considerado e
  rejeitado como formato — ver `## Alternatives Considered`).

## Design

**A chain por task não muda.** Cada task continua verificando (`verify:`, sob a política
`verification` já declarada), tickando sua caixa e commitando individualmente — exatamente a chain
`verify && cq specs task --check && git add && git commit && git log -1` que já existe hoje, com o
subject `plan/<slug>: <id> <título>`. É essa chain, inalterada, que preserva a retomada task-a-task
enquanto a seção ainda está em andamento.

**O gatilho do squash é o limite de seção que já existe.** No mesmo evento hoje anunciado como
"limite de seção" (a última task de uma `## N.` seção acabou de commitar, e nenhuma task da seção
ficou `[!]`), roda um squash local:

```
git reset --soft <commit imediatamente ANTERIOR à primeira task desta seção> \
  && git commit -m "plan/<slug>: <N> <título da seção>"
```

O alvo do `reset --soft` é o commit **anterior** à primeira task da seção — nunca o commit da
própria primeira task — porque `git reset --soft <sha>` move HEAD para `<sha>` preservando o índice
tal como ele está no momento do reset; resetar para o commit da primeira task deixaria as mudanças
dela já "consumidas" pelo reset e de fora do novo commit. O alvo é o commit squashado da seção
anterior (ou a base do branch, na primeira seção do plano).

**Subject da seção.** Segue a convenção de `specs-execute/git.md` §Commit messages trocando o
identificador de task pelo identificador da seção: `plan/<slug>: <N> <título da seção>` (ex.:
`plan/reduzir-commits-por-secao: 3 Ajustar a chain de commit`).

**O commit record de cada task é reparado, não perdido.** Antes de seguir para a próxima seção, e
para CADA task que acabou de ser squashada, repontar seu anchor para o commit squashado — a mesma
chamada `task --check`, sem argumento novo no CLI:

```
cq specs task --check <id> --spec "<slug>" --subject "plan/<slug>: <N> <título da seção>"
```

(mais `--commit "$(git rev-parse HEAD)"` quando a task já carregava `commit:`, no backend que usa
esse anchor). `cq specs task --check` não recusa numa task já tickada — ela apenas reflipa a mesma
marca e UPSERTA a metadata `subject:`/`commit:` na posição já existente (medido em
`quenching/specs/commands/task.py::cmd_task`), então esse reparo é idempotente e seguro de repetir.
O `## Commit record` de cada task passa a resolver, pelo `git log --grep` (ou pelo sha), para o
MESMO commit squashado que as demais tasks da sua seção — a granularidade do anchor estreita de
task para seção, exatamente a troca que esta spec propõe.

**Seção com task bloqueada.** Se qualquer task da seção fica `[!]`, o squash não roda — os commits
individuais da seção continuam existindo, um por task, exatamente como hoje, até a seção realmente
fechar (todas as tasks tickadas ou explicitamente resolvidas). Uma seção parcialmente bloqueada
nunca fica com um squash parcial.

**O hook `after_specs_execute_task` não muda de cadência.** O evento que ele anuncia — "uma task
terminou" — é sobre a task, não sobre o commit que sobrevive no histórico; continua anunciado após
cada task individual, antes do squash, exatamente como hoje.

**A pausa de limite de seção roda DEPOIS do squash.** A oferta de parar (`execution.md` §The
section boundary) continua no mesmo evento, mas agora o branch já está no estado final — 1 commit
por seção — no momento em que a pausa é oferecida.

**Falha do squash.** Se o `reset --soft` ou o recommit falhar (hook de commit rejeitando, nada
staged), a seção permanece com seus N commits individuais — o estado anterior ao squash — nunca um
estado parcialmente reescrito. Reporta como finding, nunca força (`--no-verify` continua proibido).
Nenhuma task é reaberta (`--uncheck`) por uma falha do squash: as tasks já foram verificadas e
commitadas individualmente antes dele rodar.

**Por que isso não colide com "never rewrite an earlier task's commit".** A regra protege contra
reescrever o histórico de uma seção (ou sessão) ANTERIOR já fechada — o que continua absolutamente
proibido. O squash desta spec reescreve exclusivamente os commits que a PRÓPRIA seção acabou de
produzir, na mesma sessão, no exato momento em que ela fecha — nunca uma seção anterior já
squashada, nunca um commit já compartilhado (`git push`, PR aberto, mergeado). Os dois standards
que declaram essa regra (`## Impact`) são reescritos para tornar esse escopo explícito.
## Alternatives Considered

- **Adiar todo commit até o fim da seção** — cada task ticaria sua caixa sem commitar, e um único
  `git commit` cobriria a seção inteira. Mais simples de implementar, mas troca a prova em
  `git log` de progresso intra-seção por apenas o arquivo tickado-e-não-commitado no working tree:
  um crash no meio da seção fica pior de diagnosticar do que hoje. Rejeitada — colide com o
  critério de go/no-go desta spec (não vale a pena se piorar a retomada).
- **Squash só em `/quenching:specs:conclude`, na revisão pré-merge** — zero risco novo em
  `execute.md`; o squash rodaria uma vez, na fase que já revê o branch inteiro antes do
  merge/PR. Rejeitada — deixaria o histórico ruidoso durante toda a execução, e o incômodo
  relatado já existia antes da rota de PR do orchestrate: limpar só no final não resolve o motivo
  real.

## Risks

- **Squash quebrar a retomada task-a-task** — o critério de go/no-go desta spec. ACCEPTED — a
  chain por task continua intacta durante a seção (cada task ainda commita a própria, sozinha,
  antes do squash), e uma falha do squash deixa a seção exatamente como estava (N commits
  individuais), nunca um estado parcialmente reescrito. Ver `## Design`.
- **Commit record órfão** — o `subject:`/`commit:` de uma task apontar para um commit que o
  squash já substituiu. ACCEPTED, mitigado por design — o passo de reparo (`## Design`) repontea
  cada task da seção para o subject/sha do commit squashado, na mesma passada em que o squash
  roda, antes de seguir para a próxima seção.
- **Citação perdida em prosa não declarada** — outro lugar do repositório descrever "um commit por
  task" como fato corrente fora dos dois standards e das quatro references já listados em
  `## Impact`. ACCEPTED, mitigado pela task de varredura (`## Tasks`, seção 4).
- **Nenhum exercício real em runtime antes do merge** — a decisão de validar só por revisão
  estática (`## Validation`) significa que ninguém rodou `/quenching:specs:execute` de verdade
  sobre a prosa nova antes dela chegar à revisão do branch. ACCEPTED — decisão explícita do humano
  no desenvolvimento desta spec, pesando custo (turnos de um workspace descartável) contra
  confiança; a primeira execução real acontece na primeira spec que `/quenching:specs:execute`
  construir depois desta mudar.
