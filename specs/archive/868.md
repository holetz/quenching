## Overview

Uma spec vive como issue no GitHub (ou work item no Azure Boards) e narra sua história em registros
de frontmatter — ranked, interrogated, approved, isolated, reviewed, merged. Hoje nada disso aparece
na lista de issues: só dentro do corpo, uma issue por vez. Esta spec pendura uma label por marco
atingido, calculada a partir do próprio documento a cada escrita. `## Proposal` lista o que passa a
ser verdade; `## Out of Scope` fixa que nada volta a ler essas labels, que é o que separa isto de
um segundo banco de dados; `## Design` registra por que "built" é o único marco que não vem de um
registro, e por que esta renderização não cabe nas duas categorias que o repo já tinha;
`## Open Decisions` guarda a única medição que resta, a do Azure Boards, porque a metade GitHub já
foi medida contra uma issue real. A mesma distinção que o `## Design` fixou para a label — `branch`
é isolamento, não construção — está errada na prosa de cinco arquivos, incluindo o standard que a
define; `## Impact` e a seção 7 de `## Tasks` recolhem essa correção.
## Problem

Hoje a issue do GitHub (ou o work item equivalente no Azure Boards) que representa uma spec não mostra visualmente quais registros do histórico do ciclo de vida ela já carrega — só o frontmatter narra `ranked, interrogated, approved, isolated, reviewed, merged, closed`. Precisamos de labels, em inglês, para cada um desses marcos exceto o de encerramento (`closed`), que é redundante com o estado nativo aberto/fechado da própria issue/work item — e com `built` no lugar de `isolated`, porque o marco que interessa a quem lê a issue é ter sido construída, que é o stage derivado `executing` e não o registro `branch` (`## Design` 2).
## Proposal

- A issue (GitHub) ou o work item (Azure Boards) de uma spec mostra, na própria lista, uma label
  por marco do ciclo de vida já atingido: `spec:ranked`, `spec:interrogated`, `spec:approved`,
  `spec:built`, `spec:reviewed`, `spec:merged`.
- Nenhuma label carrega o VALOR de um registro — apenas o fato de ele existir. O corpo segue sendo
  o único lugar onde `priority: {level, criticality, complexity, date}` é legível.
- Não existe label de encerramento: aberto/fechado da própria issue ou work item já é a fase.
- `spec:built` reflete o stage derivado `executing`, então uma spec construída sem isolamento
  aparece construída — o registro `branch` sozinho não conseguiria dizer isso.
- O conjunto é recalculado a partir do documento em toda escrita: uma label `spec:` apagada à mão
  volta na escrita seguinte, e uma acrescentada à mão some.
- Apagar todas as labels `spec:` do repositório não perde informação nenhuma.
- Uma escrita que não move marco nenhum não emite chamada de API extra.
- Labels fora do prefixo `spec:` nunca são tocadas.
- As seis labels existem no tracker com cor e descrição próprias, criadas quando faltam.

## Out of Scope

- Ler label de volta — nenhum comando deriva estado a partir de label; `list`, `status` e `next`
  seguem lendo o documento. Descartado porque uma projeção lida de volta é um segundo store,
  exatamente o que o docstring do `GitHubBackend` recusa.
- Label para o stage derivado (`spec:captured`, `spec:proposed`, `spec:ready`) — o enunciado é
  sobre os REGISTROS do histórico, e o stage muda a cada edição de seção, o que churnaria a issue
  a cada `section --write`. `spec:built` é a exceção deliberada, com a razão no `## Design`.
- Gerir labels alheias — a reconciliação toca apenas o prefixo `spec:`. Toda label posta por um
  humano fica intocada; remoção cega é o único jeito de esta mudança destruir dado.

## Design

1. **A label é projeção derivada, nunca store.** Regra durável: um backend externo pode espelhar
   estado derivado na UI nativa do tracker desde que a projeção seja unidirecional — calculada do
   documento a cada escrita e jamais lida de volta. Isso mantém de pé o docstring do
   `GitHubBackend` (specs.py:2595-2602): nada codifica campos de registro em nome de label, e a
   "segunda cópia driftável" que ele teme não existe se não há segunda fonte.
2. **`spec:built` ancora no stage derivado `executing`, não no registro `branch`.** Alternativas:
   ancorar em `branch` deixa a label ausente em toda spec construída in-place (execute.md:184), e
   uma label ausente lê-se como "não construído"; renomear para `spec:branched` é honesto mas tira
   "built" do histórico narrado.
3. **A reconciliação viaja DENTRO do PATCH que `_store` já faz.** MEDIDO em 2026-08-05 contra a
   issue descartável #875 deste repositório: um único `PATCH /repos/{o}/{r}/issues/{n}` carregando
   `title`, `body` e `labels` no mesmo payload retorna 200 e lê os três de volta corretos. Não há
   round trip extra, então esta renderização satisfaz a condição "free" que o próprio
   spec-backend.md concede.
4. **O diff contra a listagem cacheada decide apenas se o array vai no payload**, não se há chamada.
   ACEITO: um cache velho pula uma reconciliação; a escrita seguinte corrige, e nada lê de volta.
5. **`files` e `memory` implementam a projeção como no-op.** Não há tracker; um arquivo paralelo de
   labels seria precisamente o segundo store que a decisão 1 proíbe.
6. **O cálculo de quais marcos existem é código compartilhado; só o transporte é por backend** —
   labels no GitHub, tags de work item no Azure Boards. É a mesma divisão que faz `derive_info`
   rodar uma vez para todos os backends.
7. **O PATCH CRIA a label que não existe**, em vez de responder 422 — medido na mesma chamada:
   `spec:approved` e `spec:ranked` passaram a existir no repositório sem nenhuma chamada a
   `POST /labels`. Não há passo de criação. O que a implementação precisa fazer é fixar cor e
   descrição por marco, porque o GitHub atribui uma cor arbitrária a uma label nascida assim.
8. **Esta mudança emenda docs/standards/architecture/spec-backend.md com uma TERCEIRA categoria** ao
   lado de projeção e storage: renderização de estado derivado, admitida sob condições CUMULATIVAS —
   não duplica campo canônico algum (o marco é derivado de registros, não é um deles), é recalculada
   da fonte a cada escrita, custa zero chamadas extras, e é descartável sem perda. O título e as
   sub-issues continuam recusados: o título duplicava um campo canônico, as sub-issues custavam uma
   chamada por item por escrita.

Contratos que esta mudança não pode contradizer:

- `SpecBackend` é o documento, não os verbos (specs.py:1810). A projeção não acrescenta uma sexta
  primitiva: ela roda dentro de `write_spec`, que já existe, e o conjunto desejado é calculado por
  código compartilhado, não por um método que cada backend reimplementa.
- `record_keys` lê do schema (specs.py:3799), para que acrescentar um registro seja edição de
  schema e nunca também de código. O mapa marco→label precisa herdar essa propriedade, ou
  acrescentar um registro volta a exigir duas edições.
## Alternatives Considered

- **Revogar a decisão do docstring e deixar labels carregarem valor** (`priority:p1`,
  `refined:adversarial`). Perdeu: inventa um segundo formato que só um parser novo lê de volta — o
  motivo já registrado em specs.py:2595-2602, contra o qual nada mudou.
- **Não fazer nada e continuar pagando o custo que o docstring aceitou.** Perdeu: o custo foi
  aceito quando a lista de issues não era a interface do front. Com `backend: github` declarado,
  ela é — e uma lista que não distingue uma spec capturada ontem de uma aprovada e em construção
  cobra esse custo todo dia.
- **Um verbo próprio `specs.py labels --sync`, fora do caminho de escrita.** Perdeu: zero custo no
  caminho quente, mas uma projeção que depende de alguém lembrar de rodar é uma cópia que diverge —
  a perna de drift que a decisão 1 existe para desarmar.

## Open Decisions

- Qual é o equivalente exato de "criar a tag que falta" no Azure Boards — tags de work item podem
  nascer do uso, como as labels do GitHub comprovadamente nascem, ou precisar existir no projeto.
  COMO SE DECIDE: a mesma medição que resolveu a metade GitHub, contra um projeto Azure real. Sem
  projeto disponível, vira uma tarefa `- [ ]` e a metade azure fica atrás de selftest em vez de uso.
## Risks

- A emenda ao standard escrita antes de o código provar a categoria. MITIGAÇÃO: o grupo dos docs é o
  último do `## Tasks`, depois da prova contra as 94 specs, e a `authority:` é graduada quando cai —
  que é exatamente o que unproven-capability-warning.md existe para pegar.
- Um cache de listagem velho pula uma reconciliação. ACEITO — a escrita seguinte corrige, e como
  nada lê a label de volta, uma label velha não corrompe estado nenhum, só atrasa a exibição.
- Remoção de label fora do prefixo `spec:` destruiria trabalho humano. MITIGAÇÃO: o filtro por
  prefixo é a única lógica de remoção que existe, e o selftest prova que uma label alheia sobrevive.
- Churn no feed da issue: cada carimbo de registro passa a gerar um evento de label. ACEITO — são
  seis eventos no ciclo de vida inteiro de uma spec.
- A terceira categoria vira brecha para futuras projeções frouxas. MITIGAÇÃO: a emenda declara
  condições CUMULATIVAS e nomeia as duas que já foram recusadas — o título e as sub-issues — como
  casos que ela continua não admitindo.
- azure-boards nunca foi exercitado ponta a ponta. ACEITO — herdado do standard, não criado aqui.

## Outcome

superfície nativa (labels `spec:` num issue do GitHub, `System.Tags` num work item do Azure Boards)

issue #877 (o comparador por conjunto, não por lista ordenada, foi o que corrigiu isso). Seis
cores/descrições de label do GitHub são fixadas uma vez, sob mudança real de conjunto. Provado contra
as 94 specs reais deste repositório (cálculo offline vs. registros) e uma issue descartável ponta a
ponta. A narração errada de `branch` como "built" foi corrigida nas quatro cópias que a carregavam:
`plan-lifecycle.md`, `spec-driven.md`, `QUENCHING.md` (duas vezes) e `status.md` (corpo e
`description`) — `branch` narra `isolated`; "built" é o stage derivado `executing`. Glossário
(`Projection / storage`) estendido com a terceira categoria via `/quenching:docs:define`.
