## Problem

O hook `after_specs_execute_task` declara `/security-review` (spec 1167, PR #1172). Na spec 1180, o hook resolveu e foi invocado como `Skill` pelo worker, mas falhou porque `refs/remotes/origin/HEAD` não existia no clone: o `git diff origin/HEAD...` do próprio skill abortou com `ambiguous argument 'origin/HEAD...'` (reproduzido em 2026-10-07 na sessão condutora). Um clone feito com `git clone` costuma ter `origin/HEAD`, mas um clone criado com `git init` mais `remote add`, ou um `fetch` que nunca rodou `set-head`, não tem. Neste clone, a sessão condutora corrigiu com `git remote set-head origin -a`; em outros clones e em alvos, o problema continua.

Consequência: em todo clone sem `origin/HEAD`, a revisão de segurança declarada falha em toda task e, como é `optional`, só aparece na linha `HOOKS:` do worker. A pergunta original do humano ("o hook não rodou") continua verdadeira nesses clones.

## Proposal

- Before invoking any declared hook, step 5g of `/quenching:specs:execute` guarantees `refs/remotes/origin/HEAD` resolves: when the probe already read at the start of the run found it absent, it runs `git remote set-head origin -a`, and falls back to `git remote set-head origin <resolved base>` when that cannot reach the remote.
- The guarantee is local (one ref in the clone's git dir) and a no-op where `origin/HEAD` already exists, so `/security-review`'s `git diff origin/HEAD...` no longer aborts in clones made by `git init` plus `remote add`.
- The Codex translation of the command carries the same step.

## Out of Scope

- Changing `/security-review` itself: it is a built-in skill outside this repository.
- Making the hook non-optional or failing the run: the hook stays `optional`, its failure still surfaces on `HOOKS:`.
- Repairing `origin/HEAD` anywhere other than before a declared hook (other commands already resolve the base through `symbolic-ref` with fallbacks).

## Impact

### Product code this spec expects to touch

- `plugins/quenching/commands/specs/execute.md` — step 5g
- `plugins/quenching/tests/test_specs_execute.py` — the hook test

## Validation

- Reproduction on main: in a fresh `git init` clone with `remote add origin` and `fetch`, `git symbolic-ref refs/remotes/origin/HEAD` exits 128 and `git diff origin/HEAD...` prints `ambiguous argument 'origin/HEAD...'`; after `git remote set-head origin main` the same diff exits 0.
- `python3 -m unittest discover -s plugins/quenching/tests -p 'test_specs_execute.py'` exits 0 and asserts the step names `set-head`.
- `bash scripts/verify_repo.sh` exits 0.

## Design

- Rule: a hook that shells out to `origin/HEAD` is given a repo where it exists; the executor owns that precondition because it is the one that invokes the hook. Repairing it in the command body keeps it working in every clone and target without touching user git config.
- Alternatives weighed: documenting `set-head` in the README (leaves every unfixed clone failing silently), and a `.claude/quenching.json` hook `condition` (the executor never evaluates conditions). Rejected.
- The fallback uses the base already resolved by the run's chain (`origin/HEAD -> init.defaultBranch -> main`), so it works offline when `refs/remotes/origin/<base>` exists.
- The Codex skill is regenerated with `python3 scripts/sync_codex_plugin.py`, never hand-edited.

## Alternatives Considered

- Document the manual `git remote set-head origin -a` only: rejected, the failure stays silent on `HOOKS:`.
- Have the executor evaluate the hook `condition` and skip: rejected, executor never evaluates conditions by design.

## Open Decisions

- Why now / not-worth-doing: answered by the Problem (the declared review fails on every task in such clones); no further human input is needed.

## Risks

- `set-head -a` needs network access and may fail offline: mitigated by the explicit-base fallback; if both fail the hook failure is reported as before. ACCEPTED — optional hook.
- Writing a ref into the shared git dir from a worktree: ACCEPTED — it is the same ref `git clone` would have created.
