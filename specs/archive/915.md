## Overview

Hoje `execute` não deixa nenhum rastro legível de qual(is) spec(s) construiu num branch ou
worktree, e `conclude` sempre exige o slug como argumento explícito — inclusive para
desenvolvimentos que nunca passaram por uma spec, que hoje não têm como se beneficiar da revisão e
do discovery que `conclude` produz. Esta spec fecha essa lacuna em duas frentes que se apoiam:
`execute` passa a marcar o branch que constrói — uma linha `quenching-slugs: <slug1>,<slug2>` na
descrição do branch, reescrita (nunca duplicada) a cada task commitada, documentada em
`specs-execute/git.md` §Recording the isolation e no contrato
`/.docs/standards/workflows/plan-git-record.md` que ela estende; e `conclude`, sem receber
`--spec`, lê essa marcação através do novo `specs-conclude/auto-discover.md` para se
autodescobrir — resolvendo sozinho o caso de um slug válido, descartando um slug marcado que já não
existe mais em `plans/`, perguntando no caso de vários slugs válidos, e sempre perguntando — nunca
por um limiar de tamanho — se deve materializar uma spec mínima quando não há marcação válida
nenhuma; recusado, roda headless. A marcação nunca acontece para execução `In place`, o que evita
contaminar um branch compartilhado ou de terceiros. `## Risks` aceita conscientemente a limitação
central da abordagem: a descrição do branch é local ao `.git` de quem a escreveu e não sobrevive a
`clone`/`fetch`.
## Problem

Hoje `/quenching:specs:execute` não deixa nenhum rastro, na worktree ou na branch, de qual(is) spec(s)
foram executadas nela — e `/quenching:specs:conclude` sempre exige o slug como entrada explícita.
Isso obriga quem está fechando o ciclo a lembrar (ou redescobrir) o slug correto, e não abre nenhum
caminho para branches/worktrees que nunca passaram por uma spec: hoje elas não têm como se
beneficiar do enriquecimento e do discovery que `conclude` produz.

O objetivo é ajustar o fluxo em duas frentes que se conectam: (1) `execute` passa a marcar a
worktree/branch com o(s) slug(s) das specs que executou nela, para que `conclude` rodando na mesma
worktree/branch, sem receber o slug como argumento, consiga descobrir sozinho o que deve concluir a
partir dessa marcação; (2) quando a marcação não existir, `conclude` passa a destilar as
modificações da própria branch como substituto — permitindo a etapa de enriquecimento (e
possivelmente de discovery) mesmo para desenvolvimentos que nunca usaram specs. Uma possibilidade a
explorar no desenvolvimento desta spec é converter esses desenvolvimentos sem spec em specs simples,
só para materializar as modificações antes de fechá-las.

Este pedido pede complexidade alta: o mecanismo de marcação, a resolução de ambiguidade (múltiplas
specs marcadas, marcação desatualizada em relação ao HEAD, worktrees reaproveitadas) e o
comportamento de fallback por destilação/discovery em branches sem spec merecem ser desenhados e
criticados com cuidado antes de qualquer implementação.

## Proposal

- `execute` grava, a cada task commitada, uma linha reconhecível `quenching-slugs: <slug1>,<slug2>` na
  descrição do branch (`git branch --edit-description` / `branch.<name>.description`) — preservando
  qualquer texto humano já presente nesse slot, reescrevendo a linha (nunca duplicando) a cada
  commit, o que mantém a marcação sempre atual em relação ao HEAD.
- `execute` nunca marca quando a spec roda **In place** — a marcação só existe quando `execute`
  controla a criação ou adoção do branch, nunca sobre um branch compartilhado ou de terceiros.
- `conclude`, sem receber `--spec`, lê a marcação do branch atual: um único slug marcado resolve
  sozinho; mais de um pergunta ao humano qual concluir agora — o contrato de "uma spec por chamada"
  não muda; nenhum marcado cai no fallback abaixo.
- Sem marcação nenhuma, `conclude` oferece — nunca impõe — materializar o diff do branch como uma
  spec mínima (`cq specs new`, título e `## Problem` derivados do diff) quando o diff parece
  grande ou relevante o bastante para merecer um registro permanente; recusado, ou diff pequeno,
  `conclude` roda "headless": revisão do branch, `/.docs/` emergente e destilação, sem nunca criar
  um arquivo de spec.

## Out of Scope

- Concluir várias specs marcadas no mesmo branch numa única chamada de `conclude` — a ambiguidade
  vira uma pergunta ao humano, nunca um loop automático; o contrato de "uma spec por chamada"
  não muda.
- Marcar retroativamente branches ou worktrees que já existiam antes desta spec — só passam a ser
  marcados os que rodarem `execute` depois que esta spec estiver construída.
- Propagar a marcação entre máquinas ou clones (`git push`, `git fetch`) — a descrição do branch é
  local ao `.git` de quem a escreveu; um colega puxando o mesmo branch em outra máquina não a vê.
  Aceito como limitação da abordagem escolhida — ver `## Risks`.
- Alterar o record `branch: {base, work}` que `execute` já grava na própria spec — este é um sinal
  novo e paralelo, nunca uma substituição do que já existe.
- Mudar como `/quenching:specs:create` ou `/quenching:specs:develop` resolvem o slug de uma spec —
  a mudança é só em `execute` (quem grava a marcação) e `conclude` (quem a lê).

## Validation

- `execute` isola (worktree ou branch) e commita uma task; `git config branch.<name>.description`
  (o mesmo slot de `git branch --edit-description`) mostra uma linha `quenching-slugs: <slug>` — e
  só essa linha, qualquer texto humano acima/abaixo permanece intocado.
- Uma segunda task commitada na mesma branch/worktree não duplica a linha — o mesmo `git config
  branch.<name>.description` continua mostrando uma única ocorrência de `quenching-slugs:`.
- Rodando `/quenching:specs:execute` para uma segunda spec na mesma branch/worktree, a linha passa
  a listar os dois slugs (`quenching-slugs: <slug1>,<slug2>`).
- Uma execução `In place` (sem isolamento) não escreve nada: `git config
  branch.<name>.description` no branch original permanece exatamente como estava antes de
  `execute` rodar.
- Com um único slug marcado e válido, `/quenching:specs:conclude` chamado sem `--spec` na mesma
  branch/worktree resolve sozinho e nomeia o slug resolvido antes de seguir com a revisão.
- Com dois slugs marcados, `/quenching:specs:conclude` sem `--spec` pergunta via `AskUserQuestion`
  qual concluir agora, e segue só com o escolhido.
- Com um slug marcado que `cq specs status` não encontra mais em `plans/`, `/quenching:specs:conclude`
  sem `--spec` trata a marcação como ausente em vez de travar ou resolver o slug morto.
- Sem marcação válida nenhuma, `/quenching:specs:conclude` sem `--spec` mede o diff da branch
  contra a base e pergunta via `AskUserQuestion` se deve materializar uma spec mínima (`cq specs
  new`, título e `## Problem` derivados do diff) antes de seguir — recusado, segue "headless":
  revisão do branch, `/.docs/` emergente e destilação, sem nunca criar um arquivo de spec.

## Design

- **Mecanismo de marcação: descrição do branch.** `execute` escreve em
  `git config branch.<name>.description` (o mesmo slot de `git branch --edit-description`) em vez
  de um `git config` dedicado, de uma convenção de nome de branch, ou de um arquivo versionado —
  comparados em `## Alternatives Considered`. A descrição está amarrada ao **ref**, não ao
  diretório físico da worktree, então cobre tanto a forma **Worktree** quanto a forma **Branch**
  (mesmo checkout, branch novo) que `execute` já oferece.
- **Formato: uma linha reconhecível, preservando o resto.** `execute` lê a descrição atual, escreve
  ou atualiza só a linha `quenching-slugs: <slug1>,<slug2>` e mantém qualquer outro texto humano
  intocado acima ou abaixo dela. A linha é reescrita — nunca duplicada — a cada task commitada, o
  que resolve a marcação desatualizada em relação ao HEAD sem precisar de um passo extra de limpeza.
- **`In place` nunca marca.** Quando a spec roda sem isolamento, direto num branch que já estava em
  uso, `execute` não escreve nada — evita contaminar um branch compartilhado ou de um branch de
  terceiros com o slug de uma spec. `conclude` continua exigindo `--spec` explícito nesse caso,
  exatamente como hoje.
- **Fallback sempre perguntado, nunca decidido por um limiar.** Sem marcação nenhuma, `conclude`
  mede o diff do branch (arquivos e commits desde a base) e sempre pergunta — via
  `AskUserQuestion`, mostrando essa medição como contexto — se deve materializar uma spec mínima
  primeiro (`cq specs new`, com título e `## Problem` derivados do diff), reaproveitando depois o
  fluxo normal de `done`/archive. Nenhum limiar de tamanho decide sozinho: "grande o bastante" é um
  julgamento que muda por repositório, e a pergunta já é barata. Recusado, `conclude` roda
  "headless": revisão do branch, `/.docs/` emergente e destilação, sem nunca criar um arquivo de
  spec.
- **Marcação inválida trata-se como ausência.** Um slug marcado que `cq specs status --spec <slug>
  --json` não encontra mais em `plans/` (arquivado, removido, ou nunca existiu) é descartado da
  lista antes de qualquer resolução — `conclude` nunca trava nem assume silenciosamente um slug
  morto. Se sobrar um único slug válido, resolve sozinho; se sobrar mais de um, pergunta; se não
  sobrar nenhum, cai no mesmo caminho de "sem marcação nenhuma".
- **Ambiguidade resolvida por pergunta, nunca por loop.** Mais de um slug marcado (e válido) no
  mesmo branch lista os candidatos via `AskUserQuestion` e segue só com o escolhido — `conclude`
  continua fechando uma spec por chamada.
## Alternatives Considered

Quatro formas de marcar o branch foram comparadas antes de escolher a descrição do branch:

| Abordagem | Por que perdeu |
| --- | --- |
| `git config` dedicado por branch (`branch.<name>.quenching-slugs`) | Tecnicamente mais correto — sem risco de colidir com uma anotação humana — mas perdeu para a descrição do branch por escolha explícita na sessão de shape desta spec. |
| Convenção de nome (`plan/<slug>`) | Zero escrita nova, já funciona para branches cortados pela própria oferta de isolamento do `execute`. Mas não cobre branches cortados por outra ferramenta (esta própria worktree usa `holetz/<slug>`, não `plan/<slug>`), não guarda múltiplos slugs no mesmo branch, e renomear o branch perde a marcação sem aviso. |
| Arquivo versionado no branch (ex.: `.claude/quenching-active-spec.json`) | Sobrevive a qualquer clone ou checkout, mas vira código-acoplado: precisa ser removido antes do merge, e um esquecimento vaza estado de meta-processo para o branch base. |
| Sempre materializar uma spec para trabalho sem marcação | Mantém `plans/`/`archive/` como registro completo de tudo que foi concluído, mas contradiz o objetivo central desta spec — permitir concluir sem burocracia extra sobre trabalho que nunca teve spec — e polui o front com specs sintéticas de baixo valor para diffs pequenos. |

## Risks

- **A marcação é local ao `.git` de quem a escreveu, não sobrevive a `clone`/`fetch`.** Um colega
  puxando o mesmo branch em outra máquina não vê `quenching-slugs:` nenhum — ACCEPTED: é a
  limitação que `## Out of Scope` já aponta; o fallback de destilação existe justamente para cobrir
  esse caso.
- **Colisão com texto humano já presente na descrição do branch.** `execute` só reescreve a linha
  reconhecível `quenching-slugs:` — qualquer outra linha (uma descrição escrita à mão) permanece
  intocada acima ou abaixo dela. Mitigado por construção: nunca há uma escrita que apague o resto
  do campo.
- **Marcação obsoleta num branch reaproveitado depois que a spec que o marcou já foi arquivada.**
  Se o mesmo branch/worktree for reaproveitado para um desenvolvimento novo sem passar de novo por
  `execute` com uma spec, `quenching-slugs:` ainda aponta para o slug antigo, que não existe mais
  em `plans/`. Mitigado: `## Design` trata um slug marcado que `cq specs status` não encontra em
  `plans/` como marcação inválida, e `conclude` cai no mesmo caminho de "sem marcação nenhuma" em
  vez de travar ou assumir o slug morto silenciosamente.
