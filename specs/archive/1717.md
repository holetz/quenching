## Problem

`cq knowledge project` splits a glossary term at the last em dash in its definition. Independent verification in `../resume-map-verify.json`, item 6, at 719ca3e5: `- **Spec** — A unit of work — written in prose.` projects as `*[Spec — A unit of work]: written in prose.`; project check reports `OK — current` (exit 0).

Cause: `plugins/quenching/assets/bin/quenching/knowledge/projection.py:101` uses `rsplit(" — ", 1)`. The glossary format in `assets/knowledge/glossary.md:17-18` does not prohibit em dashes inside definitions. Consequence: the intended tooltip disappears and an incorrect abbreviation is emitted with a green check. The current repository glossary has no affected entries; the template seed is already excluded by `_entry_from`, so impact is limited to consumers using this valid prose format.

Scope: separate the label from the definition at its actual delimiter and preserve the complete definition. Files: `plugins/quenching/assets/bin/quenching/knowledge/projection.py` and `plugins/quenching/tests/test_knowledge_projection.py`. Cover literal em dashes inside bold/link labels so the repair does not merely move ambiguity. No template or format redesign. S5 precedes S8 conservatively.

Acceptance: the reproduction projects term `Spec` with its complete definition; bold/link labels containing em dashes remain correctly parsed; the new behavior check fails on the base. `python3 -m unittest discover -s plugins/quenching/tests -p test_knowledge_projection.py` and `bash scripts/verify_repo.sh` exit 0.

## Proposal

- A glossary bullet is split into label and definition at the delimiter that closes the label, so `- **Spec** — A unit of work — written in prose.` projects term `Spec` with the complete definition `A unit of work — written in prose.`.
- Bold and link labels that contain a literal em dash (`**A — B** — def`, `[A — B](p.md) — def`) still parse as one label.
- A regression test covers the reproduction and both label forms, and fails on the base.

## Out of Scope

- Changing the glossary template or the bullet format: the format already allows em dashes in definitions, so the parser is what is wrong.
- Escaping or quoting syntax for plain labels containing an em dash: plain labels end at the first ` — `.

## Impact

### Standards this spec will write into docs/standards/

- none — a parser repair that follows the existing format.

### Product code this spec expects to touch

- `plugins/quenching/assets/bin/quenching/knowledge/projection.py` — the bullet split in `parse_glossary`
- `plugins/quenching/tests/test_knowledge_projection.py` — regression cases

## Validation

- `python3 -m unittest discover -s plugins/quenching/tests -p test_knowledge_projection.py` exits 0 and its new test fails on the base.
- `bash scripts/verify_repo.sh` exits 0.

## Design

- Replace `rsplit(" — ", 1)` with one anchored regex: the label is a bold span, a link span, or plain text up to the first ` — `; the definition is everything after the following ` — `. Rule: the delimiter is the first em dash outside a bold or link label, never the last one in the line.
- Assumption: a plain label never contains an em dash; this matches the format in `assets/knowledge/glossary.md`.

## Alternatives Considered

- Keep `rsplit` and special-case definitions: rejected, it moves the ambiguity instead of removing it.
- Split on the first ` — ` only: rejected, it breaks bold/link labels holding a dash.

## Open Decisions

- none — the delimiter rule is settled by the format.

## Risks

- A plain label with an em dash now splits early. ACCEPTED — the format never defined such labels and the old behaviour was equally wrong for them.
