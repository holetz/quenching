## Problem

Na rodada 1 do autopilot de 2026-11-23 (épico 288), `cq git pr create --head <branch> --spec <id>` abriu os PRs #292 a #298 e não gravou o registro `pr` em nenhuma das specs 233, 244, 251, 285 e 286, segundo o relatório do spec-orchestrator. O protocolo do orchestrator (quenching/agents/spec-orchestrator.md, passo de publicação) conta com esse carimbo: sem ele, um re-spawn não adota o PR existente e pode tentar abrir um segundo, e o `status` perde o link do PR. Na 233 o erro foi `git-pr-spec-head-mismatch`, porque o registro `branch` write-once apontava para a branch abandonada (dor da 2210); nas outras quatro a causa não foi diagnosticada.

Minimal fix proposed: reproduzir com `cq git pr create --spec` numa spec de teste, ler por que o stamp não acontece sem erro, e fazer o verbo gravar o registro ou sair com `reason: stamp-failed`, como o protocolo espera.

## Proposal

- `cq git pr create --spec <id>` never reports success while the `pr` record exists only in this clone: when the store sync that follows the stamp fails, the verb exits 1 with `reason: store-not-synced`, keeping the PR facts (`url`, `number`) in the payload, as `stamp-failed` already does for a failed stamp.
- The two failure reasons are told apart in `quenching-git/references/pr-create.md`, with the recovery for each (`stamp-failed`: `pr record`; `store-not-synced`: `cq specs push`), so an orchestrator re-spawn adopts the PR instead of opening a second.
- A test pins both the stamp from a linked worktree and the refusal to report a clean success over an unsynced record.

## Out of Scope

- Making `sync_store` itself more robust (retries, conflict handling): ruled out, the fix is to stop hiding its failure, not to change the store.
- `pr merge` and `pr record` sync notes: `pr merge --spec` already exits 1 on `stamp-failed`, and its sync note is a separate contract; deferred.
- The `git-pr-spec-head-mismatch` of spec 233 (write-once `branch` record pointing at an abandoned branch) belongs to its own pain; this spec only keeps the refusal visible.

## Design

### Diagnosis

The reproduction on the current code (a real `git` store, a fake `gh`, a linked worktree, explicit `--head` and `--spec`) stamps the record: `_create` already runs `_stamp` and exits 1 `stamp-failed` when the stamp is refused. What it does not do is judge the sync that follows: `sync_store` failing returns `{ok: false, message}` into `payload["specs"]`, while the verb returns `OK` with `ok: true`, and `_specs_note` appends the failure as a tail of the human line. The stamp lives in the clone's local pending commit until the sync lands, so a caller that reads only the exit code and `ok` (the `spec-orchestrator`'s publication step does) saw a stamped PR that no other clone or re-spawn could read: `status` lost the PR link and a re-spawn found no `pr`. This is the one silent path found; the other four causes the 2026-11-23 report left undiagnosed are not reproducible on this code.

### Decisions

- A failed sync after a stamp is a finding, not a note: exit 1, `ok: false`, `reason: store-not-synced`, the PR facts kept. Rule: a sync point that cannot publish what the verb just wrote never reports clean success.
- Only `--spec` runs are judged: without `--spec` the verb wrote nothing to the store and the note stays a note.
- A `skipped` sync (no git store, nothing pending) is success.

### Assumptions

- The orchestrator's runs that lost the record failed the store sync (a push race with another epic PR rewriting the store branch); inferred from the code path, not observed — the section Validation depends on the injected failure, not on this inference.

### Mapa de dependências

(varredura inline: executor sem Task, 2026-11-25) Callers of `_create`'s payload: the `git_pr_create` MCP tool, `quenching/agents/spec-orchestrator.md` (reads `reason: stamp-failed` → `STATE: blocked` with the PR url), `pr-create.md` step 5. `azure_pull.py` has its own `merge_azure` sync, untouched. Adding a new `reason` breaks no consumer that already handles `stamp-failed` as blocked-with-url.

## Alternatives Considered

- Retry the sync inside `_create`: rejected, it hides a real store conflict and still needs a terminal answer when the retries run out.
- Fold `store-not-synced` into `stamp-failed`: rejected, the recoveries differ (`pr record` against `specs push`) and the orchestrator must not re-stamp a record that already exists.

## Open Decisions

- none — every decision the work needs is settled in `## Design`; the unobserved cause is covered by the injected-failure test, not by a decision.

## Risks

- A consumer that treats any exit 1 of `pr create` as "no PR opened" would open a second PR. Mitigation: the payload keeps `url` and `number`, and `pr-create.md` states the PR exists on both reasons.
- The injected-failure test passes while the real cause is another. ACCEPTED — the verb now fails loudly on the one silent path found; any other cause surfaces as its own reason.
