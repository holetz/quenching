## Problem

Nothing stops a commit from being signed with the wrong identity: a target repository published as open source (guion) received a commit authored with a corporate address, and it reached the public history because the leak gate only knows generic patterns since the private denylist was retired, and a denylist can never enumerate every address that must not appear. The owner wants a clear, per-repository declaration of which author and committer emails are allowed (exact addresses and domain or pattern forms such as `*@users.noreply.github.com`), enforced by git hooks the plugin installs (`pre-commit` on the configured identity, `pre-push` on the author and committer of every commit being published) and by the specs store guard, so that a commit with an email outside the allowlist is refused before it exists or before it leaves the machine.

## Proposal

Declare, per repository, which emails may sign a commit, and judge every identity the plugin can see against that declaration.

- **The declaration.** `shared.gitIdentity.allowedEmails` in `.agents/quenching.json`: a non-empty list of exact addresses or glob patterns (`holetz@gmail.com`, `*@users.noreply.github.com`), matched case-insensitively with `fnmatch`. Absent → no identity check anywhere, behaviour unchanged. Present but malformed (not a list, an empty list, a non-string or blank entry) → the gate fails closed with exit 2, so a typo never disables it silently.
- **One module.** `quenching/common/identity.py` reads the declaration, matches an email, and produces `leak.Finding`s labelled `email-not-allowed` that name the offending email, for the configured identity (`git var GIT_AUTHOR_IDENT` / `GIT_COMMITTER_IDENT`, which honour `--author` and the `GIT_*_EMAIL` variables) and for the author and committer of every commit a push publishes (the same commit set `leak.scan_push` judges).
- **Three enforcement points.** `cq security leak --staged|--pre-push` adds the identity findings to its own, so this repository's `scripts/githooks/` hooks enforce it with no change; a new `cq git identity --staged|--pre-push [--remote]` runs only the identity check (exit 0 clean or undeclared, 1 findings, 2 malformed declaration), which the target hooks call — it lives in the `git` package because every deploy carries it, while `quenching-security` is optional; the specs git store's `_guard_identity` refuses a store commit whose identity is outside the list (`sp-identity-not-allowed`).
- **Target hooks.** `cq deploy` ships `pre-commit` and `pre-push` under `.agents/quenching/assets/githooks/`, each calling `.agents/quenching/bin/cq git identity`. Activation stays the per-machine choice the security pillar already states: when the target declares an allowlist and `core.hooksPath` does not point at those hooks, `cq deploy` prints a warning naming the exact `git config core.hooksPath .agents/quenching/assets/githooks` command. Deploy writes no git configuration.
- **Refusal text.** Every finding names the email and the remedy: `git config user.email <an allowed address>` for the configured identity, `git commit --amend --reset-author` (or a rebase for older commits) for a commit already made.
- This repository declares its own list (`holetz@gmail.com`, `noreply@github.com`, `*@users.noreply.github.com`), which matches every author and committer in its last 500 commits.
## Out of Scope

- Rewriting the history already published in holetz/guion (or anywhere else): the owner's decision, with a force-push this plugin never makes.
- A server-side control (GitHub rulesets, push protection, a CI identity check): this spec guards the machine that commits; a CI job judging the authors of a PR is a natural follow-up, not this build.
- Activating the target hooks automatically: deploy and the security pillar write no git configuration (security-pillar.md §The leak gate — pointing `core.hooksPath` is a per-machine choice).
- Bringing the retired private denylist back, or adding new generic content patterns.
- Judging the author *name*, GPG/SSH signatures, or `Co-authored-by:` trailers (the Claude co-author hook already owns trailers).
- A `cq config check` schema: that verb lists missing seed keys only, and an allowlist has no meaningful seed value; validation happens where the declaration is read.

### Flow

```
git commit ──pre-commit──> cq security identity --staged   (target)   ┐
                          cq security leak --staged        (this repo) ├─> identity.load(root)
git push ───pre-push────> ... --pre-push --remote $1                  ┘     absent  → exit 0
cq specs <write> ─────────> GitStore._guard_identity ──────────────────┘     invalid → exit 2
                                                                              outside → finding / sp-identity-not-allowed
```

### Decisions

- The key lives under `shared` because hooks, the store guard and deploy all read it; `gitIdentity` is a block so a later identity rule has a home. No root-level envelope change: `shared` children are not schema-checked by `load_config`.
- Matching is `fnmatch.fnmatchcase(email.lower(), pattern.lower())`: email domains are case-insensitive in practice, and one rule covers exact and glob entries.
- The configured identity is read with `git var`, not `git config user.email`, because git exports `--author` and `GIT_AUTHOR_EMAIL` to the hook and `git var` reports what the commit will actually carry. An ident git cannot form yields no finding: git itself refuses that commit.
- The target hooks call `identity`, not `leak`: shipping the content gate to every target would start refusing commits over generic patterns (CPF-shaped fixtures) nobody asked for there.

### Assumptions

- Git exports the `--author` identity to `pre-commit` (builtin/commit.c `determine_author_info`) — `## Validation`'s end-to-end check proves it; if it does not, the staged check judges the configured identity only, as `leak` does today.
- A commit already on the destination's remote-tracking refs (a GitHub web merge with `noreply@github.com`) is not re-judged by `pre-push`, because the commit set is `leak._commits_to_push`'s — `## Risks` depends on it.

## Alternatives Considered

| Approach | Cost | Buys | Forecloses |
| --- | --- | --- | --- |
| **Allowlist in `.agents/quenching.json`, judged by hooks and the store guard (chosen)** | one module, one command, two shipped hooks | per-repo declaration in the tracked config; fails closed; no private file | nothing server-side |
| Bring back a private denylist of corporate domains | small | blocks the known-bad domain | can never enumerate every address; leaks the terms if committed — why it was retired |
| Only `git config user.email` per repo (`includeIf`) | zero code | fixes this machine | nothing enforces it; the next clone or machine repeats the incident |
| Server-side check (CI job / ruleset) | workflow + permissions | catches every contributor | runs after the email is already pushed to a PR branch — the leak this spec must prevent |

## Open Decisions

- none — every decision of shape is settled by the code read and the security-pillar standard (see `### Decisions` under `## Design`); history rewrite and a server-side check are out of scope, not open.

## Risks

- **A maintainer pushes a contributor's commits** (cherry-picks, a rebased PR branch) and the allowlist refuses them. Accepted: the remedy is to add the contributor pattern; the refusal names the email.
- **Malformed declaration blocks every commit and store write** (fail closed). Accepted by design; the exit-2 message names the key and the expected shape.
- **Hooks not activated in a target** leave it unprotected; mitigated by the deploy warning, not eliminated — activation stays per machine.
- **Windows**: the shipped hooks are POSIX `sh`; Git for Windows runs hooks through its bundled `sh`, and `bin/cq` is the launcher the hooks exec. Not proved here on Windows.
- **Lockstep drift**: changing the deploy payload changes this repository's own `.agents/quenching/`; task 2.1 regenerates it so the gate stays green.
