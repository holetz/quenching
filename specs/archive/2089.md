## Problem

The adopter's specs live in Azure Boards work items (holetz/forge epic 1, `## Design` §Spec store), while the quenching specs service's interface and MCP must answer at the speed of a local read. Keep a local cache of the store — work items, their Markdown descriptions, records and dependency links — in step with Azure DevOps: service hooks on every change, plus a periodic reconciliation for a missed hook. Serve every interface and MCP read from it, and write every edit, from a person in the interface or from an agent, back through the store adapter to Azure, never to the cache alone. A stale entry is detectable by revision, and a write invalidates its own entry before it answers. Azure Boards stays the one source of truth. References: `automazeio/ccpm` (specs synced into a tracker) and `microsoft/azure-devops-mcp` (epic §Reference projects).

Formerly holetz/tempering#5.

Member S11 of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent).

## Proposal

- With sync enabled for an Azure Boards store, every read the specs service answers (the `cq specs` verbs, `cq specs serve`, `cq specs mcp`) is served from a local cache and costs no `az` call when the entry is current.
- The cache holds, per work item, the canonical document, its descriptor, native fields, tags and the `rev` it was read at; it lives in the user cache directory, outside the repository, and is never authoritative.
- Every change in Azure reaches the cache by one of two paths: a service-hook event (`workitem.created|updated|deleted|restored`) applied by `cq specs sync serve` or `cq specs sync apply`, and a reconciliation (`cq specs sync reconcile`, and a read that finds the last one older than a TTL) that compares every id and `rev` and refetches only what differs.
- A stale entry is detectable by revision: an event or a reconciliation that names a `rev` above the cached one marks the entry stale, and the next read refetches it.
- Every write goes through the Azure adapter (`write_spec`, `create_spec`, `move_spec`), never to the cache alone; the entry is dropped and refetched before the call answers, and a refused stale write (the adapter's `rev` test) drops the entry too.
- Azure Boards stays the single source of truth: deleting the cache loses nothing, and the next read repopulates it.
- All of it is proved against an in-memory double of the `az` transport; nothing in the test suite reaches an Azure DevOps organisation.

## Out of Scope

- Exposing the hook receiver to the internet (TLS, reverse proxy, the forge HTTP profile): the receiver binds loopback and is fronted by whatever the adopter runs (forge S14). Ruled out because the exposure is an infrastructure decision with its own grants.
- Registering the service-hook subscription in Azure DevOps (a subscription is created in the organisation's project settings or through its REST API): writing to the real organisation is outside this spec; the README documents the payload and the secret instead.
- A cache for the GitHub and git backends: GitHub Issues sync is S31 (2091) and git has no new feature.
- A shared multi-host cache or a database: the cache is per machine and per user, like `azure_cache_path`.
- Changing the `cq specs` write semantics, the CAS contract or the `hybrid` serialisation.
- Turning sync on by default or declaring it in `.claude/quenching.json`: opt-in by environment for now (see Open Decisions).
- Proving the sync against the real `holetz/quenching` Azure organisation: a separate human step after parity.

## Design

**Shape.** A decorator, not a new backend. `SyncedBackend(inner)` implements the five `SpecBackend` primitives over a `SyncCache` and forwards everything else (`__getattr__`) and `name` to the Azure backend, so the portal, the MCP server and every command keep calling `open_backend` and see one backend. It wraps only the Azure backend, only when `QUENCHING_SPECS_SYNC` is set to a truthy value.

**Cache layout.** One JSON file per work item plus one `meta.json`, under `<user cache dir>/quenching/azure-sync/<sha256(org\nproject)[:16]>/`, the same directory rule as `azure_cache_path` and for the same reason (per machine, outside the tree). Per-item files make concurrent writers harmless without a lock (no `fcntl`, so it works on Windows): each write is `write_text` (atomic rename) and an entry is only replaced by one with a `rev` greater than or equal to the stored one. An entry is `{id, rev, stale, fetchedAt, descriptor, info}`; `meta.json` holds `reconciledAt`. Credentials are never stored; the documents are what `azure_cache_*` already keeps in memory.

**Read path.** `read_spec(id)`: a fresh entry is returned from disk (deep copy, `_azure_rev` kept); a missing or stale entry is read through `inner.read_spec` (one batch call), stored, returned. `list_specs()` is the descriptors of the fresh entries after a cold fill through `inner.list_specs()`; `list_specs(lean=True)` passes through to the adapter, because lean rows carry native state and tags that an entry does not hold. A read that finds `reconciledAt` older than `QUENCHING_SYNC_RECONCILE_S` (default 300) runs `reconcile` first.

**Revision.** `AzureBoardsBackend.revisions()` returns `{id: rev}` from the WIQL plus the lean batch (the `rev` is a top-level field of every work item, so no body is fetched). `reconcile` diffs it against the cache: higher `rev` or unknown id is refetched, an id missing from Azure is dropped. An event carries the `rev` of the change; `apply_event` compares it with the cached one and marks `stale` rather than refetching inline, so the receiver answers fast and the cost lands on the next read.

**Write path.** `write_spec`, `create_spec` and `move_spec` call the inner method with the same arguments; the inner already tests `rev` in the JSON-Patch, so a write based on a stale cached `info` is refused by the server and can never overwrite. After the call (success or `BackendRefusal`) the entry is dropped and, on success, refetched before returning, so the caller's next read already sees the new revision.

**Receiver.** `cq specs sync serve [--host 127.0.0.1] [--port N]` is a stdlib `http.server` on loopback, POST `/hooks/azure`, `Authorization: Basic` compared in constant time with the secret from `QUENCHING_SYNC_HOOK_SECRET` (never argv, never logged), a body ceiling, and a background thread that runs `reconcile` every TTL. `cq specs sync apply` reads one event from stdin for any other receiver (the forge HTTP profile). The portal is not reused for the route: its per-run token and loopback origin model is for a person's browser, and a webhook has neither.

**Event shape.** `workitem.created|updated|deleted|restored` as documented for Azure DevOps service hooks: the id is `resource.workItemId` (updated) or `resource.id`, the revision is `resource.rev` or `resource.revision.rev`. An unknown shape is a 400, never a silent skip. The shape is taken from the public documentation and proved against a double; the first real delivery is the human's check (Open Decisions).

**Binding contracts.** `docs/standards/architecture/spec-backend.md` §Granular reading admits a cache inside `cq specs` on three conditions (not authoritative, nothing outside the CLI reads it, the backend stays the source of truth); all three hold. The read-only guard (`transport_read_only`) stays at the transport, so sync adds no write path that skips it. The leak guard `guard_store_write` still runs inside the adapter's `write_spec`.

## Alternatives Considered

Read from the epic's §Reference projects (holetz/forge epic 1) before composing:

- `automazeio/ccpm` (MIT) — **adapted, not vendored.** What is taken: the idea that local specs and the tracker are two copies with the tracker authoritative for state, and the sync as an explicit verb. What is left: ccpm is shell and `gh` calls over files, push/pull on demand with no event input and GitHub-only; this spec needs events plus reconciliation over Azure and a cache served to an interface.
- `microsoft/azure-devops-mcp` (MIT, to confirm) — **rejected as the read path, adapted for the event shape.** It calls the live API on every tool call (the latency this spec removes) and is reached with Entra ID against the real organisation, which the proof here may not touch. Nothing is vendored; the work-item fields it returns are the ones the adapter already reads.
- `MrLesk/Backlog.md` (MIT) — **rejected.** One local store with no external system to keep in step; it shows the MCP plus local board shape the service already has.
- `cq specs serve` (`specs/portal.py`) — **reused for the access pattern** (every read through `open_backend`, writes through the CLI verbs so CAS and refusals hold), **rejected as the hook host** (see Design, Receiver).
- `azure_cache_path`/`azure_cache_*` in `backends/azure.py` — **reused as the pattern** (user cache dir, keyed by org and project, a corrupt file is a miss, never authoritative); not extended, because it caches resolutions, not documents.

Whole-shape alternatives that lost:

- **Polling only (reconciliation without hooks).** Simple, no receiver, but staleness is bounded by the period and a short period costs a WIQL plus a batch each time; the human asked for service hooks on every change.
- **Write-through cache that treats itself as the truth until a flush.** Fastest, and exactly what the problem forbids: an edit would reach Azure late or never. Writes go to the adapter first.
- **A database (SQLite) as the cache.** Gives queries and locking, but adds a dependency surface and a lock the Windows target (2090) must also honour; per-item files plus a monotonic `rev` rule need neither.
- **Keeping the cache on the `quenching` git branch.** It would be committed, travel between machines and look authoritative, which `azure_cache_path` already rules out.

## Open Decisions

- Enabling by `.claude/quenching.json` instead of the environment variable: decided when the configuration provider (2040) serves the specs namespace from the specs service; until then the variable is the opt-in. Settled by whoever owns the next config change, with the first adopter run as evidence.
- Default reconciliation period (300 s): kept until the first run against a real organisation measures the WIQL plus lean batch cost; then adjusted by a one-line change.
- Whether `cq specs mcp` (a long-lived process) should also run the background reconciliation: decided after S4 telemetry shows read staleness; today it reconciles on a read past the TTL.
- Delivery of the service hook into the loopback receiver (tunnel, forge reverse proxy): decided in forge S14; this spec ships the receiver and the `apply` stdin form so either works.
- The real-organisation proof (one hook delivery, one reconciliation): the human's step after parity, using the `holetz/quenching` organisation; no worker or test writes there.

## Risks

- **A missed hook leaves a stale entry.** Mitigation: the reconciliation compares every id and `rev` each TTL, and the adapter's `rev` test refuses any write based on a stale read. ACCEPTED for reads within the TTL: a read can be up to one period old until the hook or the reconciliation lands.
- **A hook payload shape differs from the documented one.** Mitigation: an unknown shape is a 400 and the reconciliation still converges; the real-delivery check is an Open Decision.
- **The receiver is a new network listener.** Mitigation: loopback bind by default, constant-time secret check, secret only from the environment, a body ceiling, no write on any path (it only marks or drops cache entries). A non-loopback `--host` is refused in this spec.
- **Two processes write the cache at once.** Mitigation: per-item atomic files and a monotonic `rev` rule; the worst case is a redundant refetch.
- **The cache holds spec documents on disk.** Mitigation: the user cache directory (per user, outside the repository), no credential stored, and `cq specs sync status` names the path; deleting it is always safe.
- **The wrapper hides a method the callers need.** Mitigation: `__getattr__` forwards the rest and a test asserts the four known extra methods resolve through it.
