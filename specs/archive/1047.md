## Problem

The `ops` front converges how a repository is *operated*. Nothing converges how it is *proven*, and
a green suite is the single most trusted signal in a repository — which is exactly why an
unexamined one is dangerous.

Measured on `databricks-risco-gold` on 2026-08-30. The suite is not neglected: **1,495 tests across
108 files and 14,122 lines, all passing in 21.5 seconds.** That is a serious investment. What it
proves is another matter:

- **Coverage measures 8,663 statements at 63%, all of them in `src/safra`** — the framework.
  `bundle/`, which holds **1,772 tracked modules and 124,085 lines** and *is the product*, is not
  measured at all. Neither is `scripts/` (12,653 lines) nor `analysis/` (32,563 lines). The number
  on the report is true and answers a question nobody asked.
- **There is no floor.** `addopts` carries `--cov` and no `--cov-fail-under`. Coverage can fall to
  zero without failing anything.
- **`addopts` carries `--maxfail=1`.** The suite stops at the first failure, so a broken run reports
  one problem per iteration — the worst possible default for the CI this repository does not have.
- **There is no CI.** No `.github/workflows`, no `azure-pipelines.yml`, no `.pre-commit-config.yaml`.
  Every gate in the repository runs when a human remembers to run it.
- **Zero custom markers.** 58 `parametrize`, 15 `usefixtures`, 3 `skipif`. There is no way to ask
  for the fast tests, or to exclude the ones that need a workspace.
- **One `conftest.py`, twelve lines**, whose whole content is an import executed for its
  registry-bootstrap side effect. 40 fixtures live scattered across 21 test files; there is no
  fixture library, so shared setup is copied.
- **21.5 seconds for 1,495 tests means almost nothing touches Spark.** The suite proves the
  framework — the registry, the naming taxonomy, the DAG, the linter. The transformations that
  produce the gold layer have essentially no data-correctness tests: no golden inputs, no
  `assertDataFrameEqual`, no data contracts.
- **`tests/workflow/` is a declared directory with zero lines in it**, and `tests/` has neither a
  `README.md` nor a `CLAUDE.md` while `scripts/` has both.
- **The registry is a process-wide singleton**, bootstrapped by that conftest import and shared
  across all 1,495 tests, with nothing randomizing collection order. Order-dependence here would be
  invisible until the day it is not.

None of that is a bug in any test. It is the shape of the suite, and no check in this plugin can
see a shape. As with `ops`, what is missing first is the contract.

## Proposal

Declare `proof` as the plugin's seventh pillar and sixth **front**: the target repository's
verification surface — its layers, its fixture library, its gates, and the CI that runs them.

This spec writes the **contract alone**. The verifier, the align and the layer-minting command are
three separate specs.

**1. The canonical tree.** A declared proof root (default `tests/`) holding: a generated `README.md`
describing what each layer proves; a `conftest.py` that bootstraps and nothing else; a `fixtures/`
library, one module per domain; and one directory per **declared layer**.

**2. Layers are declared, not imposed.** The contract requires that a repository's layers exist, are
named, are disjoint, and each declares what it may touch and what it costs. It ships a recommended
default set — `unit` (no session, no I/O), `contract` (shape, schema, registry and naming
invariants), `data` (transformation correctness over golden inputs), `integration` (a real session
or workspace; marked and skippable) — and does not require it. A repository that has organized its
suite around its own axis declares that axis instead. This is the same restraint the `ops` contract
applies to routers: bind the declaration, not the choice.

**3. The layer contract**, four rules:

| # | Rule |
| --- | --- |
| 1 | The **directory** declares the layer; the marker is **derived from the path** by a collection hook, never hand-applied |
| 2 | Every derived marker is registered in `[tool.pytest.ini_options].markers`, with `--strict-markers` on |
| 3 | Every layer declares what it may reach — nothing · the tree · a session · the workspace — and its wall-clock budget |
| 4 | A fixture needed by more than one module lives in the library — pytest cannot share a module-level fixture, so reuse without a library takes the form of a **copy**, and the same fixture name defined in two or more modules is that copy; `conftest.py` bootstraps and defines no domain fixture |

Rule 1 is the load-bearing one. A hand-applied marker is a marker somebody forgets, and the measured
target's zero markers over 1,495 tests is what forgetting looks like at scale. Deriving the marker
from the path means no test can be unmarked and no marker can disagree with where the test lives.

**4. The gate contract**, five rules:

| # | Rule |
| --- | --- |
| 1 | The gate names its **measured surface** — coverage is declared per source root, and a root the repository ships and the gate does not measure is a finding |
| 2 | Every measured root carries a **floor that only rises** — a ratchet file the gate updates upward and never down |
| 3 | `addopts` carries no `--maxfail` — the failure budget belongs to the invocation, not the configuration |
| 4 | Order independence is **proven**, not assumed: the gate runs at least one randomized-order pass |
| 5 | The gate runs **in CI**. A repository whose gates run only when a human remembers has no gate, and the CI definition is this front's artifact too |

**5. Eleven finding codes** the verifier will implement: `pf-unlayered`, `pf-unmarked`,
`pf-loose-fixture`, `pf-fat-conftest`, `pf-unmeasured-surface`, `pf-no-floor`, `pf-stop-first`,
`pf-order-unproven`, `pf-no-ci`, `pf-empty-layer`, and — only where `ops` is also configured —
`pf-untested-entrypoint`, an operations entry point that no layer reaches.
## Out of Scope

- **Any code or command.** `cq proof` and `commands/proof/**` are the next three specs.
- **Writing tests.** The front converges the *shape* of a suite. What a given test should assert is
  the repository's own business.
- **Prescribing a data-testing library.** The contract requires the `data` layer's comparisons to be
  value-and-schema exact and to name their golden input; whether that is `pyspark.testing`,
  `chispa`, or something else is the repository's declaration.
- **Prescribing a CI provider.** Rule 5 binds that a CI definition exists and runs the gate.
- **Coverage targets.** The ratchet starts where the repository is. The contract forbids a floor that
  falls; it names no number.
- **Changing `databricks-risco-gold`.** It is the measured target, not a deliverable here.

## Design

**Why the name is `proof` and not `tests`.** `command-surface.md` retired `skill` as a front name
because it also named an artifact inside the front. `tests` has that defect exactly. `proof` names
what the surface produces; nothing inside it is called "a proof". It also sits well in this plugin's
own vocabulary: quenching hardens a metal, and proof testing is what establishes that the hardening
held.

**Why layers are declared rather than imposed.** The measured target has 24 test packages organized
on three different mirror axes at once — framework (`table/`, `task/`, `job/`), product
(`catalogs_risco_gold/`, `catalogs_shared/`) and tooling (`checks/`, `naming/`, `docgen/`) — with
inconsistent naming between `catalog/` and `catalogs_*`. Imposing four directories on that would
mean relocating 108 files as the price of adopting the front, and a front nobody can afford to adopt
converges nothing. Requiring layers to be *declared and disjoint* fixes what is actually broken —
there is no way to select a subset of this suite — without demanding a migration first.

**Why the marker is derived from the path.** A marker is a promise a human makes on every test they
write, 1,495 times. The measured target made it zero times. A collection hook that reads the path and
applies the marker makes the promise structural: the directory is already a decision the author had
to make, and deriving from it means `pf-unmarked` can only fire on a marker that was never
registered, never on a test somebody forgot to label.

**Why the measured surface is a rule and coverage percentage is not.** A 63% figure over the wrong
8,663 statements is worse than no figure, because it *looks* like an answer. What a gate owes is
honesty about what it measured; the number follows from the repository's own work. That is also why
the floor ratchets rather than being set: a fixed target set above where a repository stands forces
tests written to move a number, which is the standard failure mode of coverage gates.

**Why `--maxfail` in `addopts` is a finding.** `addopts` applies to every invocation — a developer's,
CI's, a bisect's. `--maxfail=1` there converts a run that could have reported twelve failures into
twelve runs. As an invocation flag it is useful; as configuration it is a permanent handicap.

**Why order independence is proven and not assumed.** The measured target shares one process-wide
registry singleton across 1,495 tests, bootstrapped by a `conftest.py` import side effect. That is
not a defect — it is a reasonable design — but it is exactly the shape in which one test's mutation
leaks into another's assertion, and the leak stays invisible while collection order happens to be
stable. A randomized-order pass is the only thing that turns "we think it is fine" into evidence.

**Why the CI definition is this front's artifact.** Rule 5 is the one rule that is about nothing
inside `tests/`, and it belongs here anyway: a suite that runs only on request is not a gate, and the
front would otherwise converge a beautiful shape that nothing enforces. The measured target proves
the point — its gates are real, documented and good, and there is no CI file in the repository.

**Why `pf-untested-entrypoint` is conditional.** It is the one code that needs the other front's
inventory. Where `ops` is not configured it does not fire, and it says so, rather than reporting a
clean surface it never looked at.

## Alternatives Considered

- **Fold proof into the `ops` front as one "engineering hygiene" surface.** Rejected: they converge
  different trees with different verifiers and different audiences, and one align carrying both would
  present a plan whose two halves have nothing to do with each other.
- **Impose the four-layer tree.** Rejected under §Why layers are declared — the adoption cost is a
  108-file migration, and the front's actual complaint is selectability, not directory names.
- **Require hand-applied markers, like most pytest guidance does.** Rejected: it is the rule the
  measured target already fails 1,495 times over, and a rule that depends on remembering is a rule
  that measures diligence rather than structure.
- **Set a coverage floor (say 80%) in the standard.** Rejected: it makes adoption conditional on a
  test-writing project, and it produces tests written for the number. The ratchet gets the same
  direction of travel with none of that.
- **Name the front `quality`.** Rejected as too wide: it would also claim linting and formatting,
  which `ops` and the repository's own toolchain own. `proof` names the suite and the gates.
- **Leave CI out of the front.** Rejected under §Why the CI definition is this front's artifact.

## Open Decisions

- **Where the ratchet file lives, and its format.** A single JSON keyed by source root is the obvious
  shape; whether it sits at the repository root, under the proof root, or inside
  `.claude/quenching.json` is resolved at the verifier spec's task 1, against what the config loader
  reads without a second parser.
- **Whether `pf-empty-layer` is an error or a warning.** The measured target's empty
  `tests/workflow/` is either a stub with intent or forgotten scaffolding, and the front cannot tell.
  Resolved in `layer-contract.md` at task 3, with the deciding question stated rather than the answer
  assumed.
- **Whether the `data` layer is required or recommended.** A repository with no data transformations
  has no use for one, and requiring it would make the front wrong for most repositories. Resolved at
  task 2 by conditioning it on the repository declaring a data layer at all — with the observation
  that a pipeline repository which declares none is itself worth reporting.
- **How a repository declares "what a layer may reach".** A free-text field is unverifiable; an
  enumeration (`nothing` · `tree` · `session` · `workspace`) is checkable but may not fit every
  repository. Resolved at task 2 by shipping the enumeration and allowing an escape value that the
  verifier reports rather than grades.

## Risks

- **A contract with no implementation ages badly.** *Mitigation:* the README row says **declared**,
  and the standard's `authority` reflects a contract awaiting its tooling.
- **The nine measured claims are one repository's.** *Mitigation:* every rule is stated against a
  defect class, and each cites the independent source that motivates it — the pytest project's own
  marker guidance, the coverage-ratchet practice, and the randomized-order argument — so a rule
  survives only when measurement and source agree.
- **"Declared, not imposed" can hollow the contract out.** A repository could declare one layer
  called `tests` and satisfy every rule. *Mitigation:* it could, and it would then be honest about
  having one layer, which is strictly better than the current state where nothing is declared at
  all. The front reports the declaration; `pf-untested-entrypoint` and `pf-unmeasured-surface` still
  bite, because they compare the suite against the repository rather than against itself.
- **Rule 5 reaches outside the proof root and can look like scope creep.** *Mitigation:* the standard
  states the reason (a gate nobody runs is not a gate) and the align's own spec puts CI wiring in the
  judgement band, reported rather than installed.
- **Two new pillars in one plan invalidate every "five pillars" count claim at once.**
  *Mitigation:* both contract specs name `align-surface.md` and `command-surface.md` in their Impact,
  and `citation-check.sh` runs in both validation sets.
