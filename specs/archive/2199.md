## Problem

The human asked to remove completely the capability of a cross review by Codex: `cq codex review`, the `shared.codex.crossReview` opt-in, the parallel Codex review in `/quenching-specs conclude` step 2 and `/quenching-specs autopilot`, and the per-task review hook recipe. The Codex executor (`cq codex eligible`/`implement`) and the quota probe it relies on stay.

## Proposal

Delete the Codex cross review end to end and keep the executor. Code: `cq codex review` and `codex/review.py` go, the helpers the executor borrowed from it (`RUN_NAME`, `measured_tokens`, `refusal`, `NOT_MEASURED`) move into `codex/implement.py`, the review-only half of the git guard (`tree`, `strict_refs`, `run_skip` and their private helpers, the `strict` mode of `refs`) is removed, and the `codex_review` MCP row goes. Configuration: `shared.codex.crossReview` and `shared.codex.model` (the review model) stop being read, leave `DEFAULTS`, the seed and the key registry; a leftover value is ignored and named in `warnings`, and the probe loses its `crossReview: "off"` gate (the executor's own `executor.enabled` stays the opt-in, checked by `cq codex eligible` before the quota). Prose: the parallel Codex review of `/quenching-specs conclude` step 2 and its report line, the Codex review of `/quenching-specs autopilot` step 6, the per-task review hook recipe that `/quenching-specs execute` points to, the README, the plugin-configuration reference and the standards all stop describing it; the deployed surface is regenerated.

## Out of Scope

- The Codex executor (`cq codex eligible`, `cq codex implement`, execute step 5b, the `CODEX:` lines of spec-runner and spec-verifier) and the quota probe it uses — they stay, unchanged in behaviour.
- Codex as a deploy harness (`cq deploy --harness codex`, `.agents/skills`, `scripts/eval_harnesses.json`) — unrelated to reviewing.
- The Claude-side reviews (conclude step 2's own review, autopilot's `spec-reviewer`) — they stay and simply run alone.
- Rewriting history: archived specs, `CHANGELOG.md` entries and decision lineage keep what they recorded; lineage only gains this spec.
- Release, version bump and changelog entry — owned by conclude/release.
- Any target repository's `.agents/quenching.json`; a leftover `crossReview` there is ignored with a warning.

## Design

Today the review is a separate path through the pillar: `codex/__init__.py` dispatches `review` to `run_review` (`codex/review.py`), which builds its own argv, snapshots the whole tree with `guard.tree`/`guard.strict_refs`, and is called only from prose — conclude step 2 and autopilot step 6 (both via `cq codex probe` then `cq codex review`) and the optional `after_specs_execute_task` hook recipe in the codex-pillar standard. The executor shares three things with it: `RUN_NAME`, `measured_tokens` and `refusal` (imported by `implement.py` from `review.py`), and the base/refs half of the guard. So the removal moves those three into `implement.py`, deletes `review.py`, and prunes from `guard.py` only what no executor path reaches (`tree`, `strict_refs`, `run_skip`, `_skipped`, `_digest`, `_local_config`, `refs(strict=)`). `test_codex_guard.py` covers `base_state`/`base_moves`, which stay.

`crossReview` today does double duty: it is the review's opt-in and the probe's gate, which is why `eligible.reserved` and `implement` force it to `"auto"` before probing. With the review gone the gate has no purpose: the probe reads the quota whenever called, and the executor's opt-in stays `executor.enabled`, which `eligibility` checks before it asks the quota, so a repository that declares nothing still never starts Codex. `shared.codex.model` is the review's model only (the executor uses `executor.modelSmall`/`modelVerified`/`modelSmallTier`), so it goes too. A declared leftover of either key is ignored with a `warnings` line, the same fail-visible rule a bad value already follows. The key registry's group `review` ("Review (Codex)") becomes `codex` ("Codex"), and the `reservePercent` description stops saying "kept free for reviews".

### Assumptions

- "Remover completamente a capacidade de cross review" covers every Codex review path (conclude, autopilot, per-task hook) but not the executor, which writes code rather than reviewing it (Out of Scope).
- A target that had opted in with `crossReview: "auto"` is better served by a visible warning than by a hard refusal (Risks).

## Alternatives Considered

- Keep `crossReview` and the subcommand but stop calling them from conclude/autopilot: rejected — the request is a complete removal, and a dormant verb keeps the guard's heaviest half and its tests alive.
- Remove the whole `cq codex` pillar, executor included: rejected — the request names the cross review only; the executor is a distinct capability with its own opt-in.
- Refuse (exit 2) on a leftover `crossReview` key: rejected — it would break every already-seeded target on upgrade for a key that now means nothing; a warning is enough.

## Open Decisions

- none — the request names the capability, and the code shows exactly where it ends and the executor begins.

## Risks

- A target that opted in silently loses its Codex review after upgrading; mitigated by the `warnings` line on the leftover key and by the `breaking` tag carried into the release notes.
- Pruning the guard could remove something the executor reaches; mitigated by keeping every function `implement.py` imports and by running `test_codex_implement.py` and `test_codex_guard.py` in the task's `verify:`.

## Handoff

Codex: skipped — the session writes every task; the change removes a Codex capability and needs no Codex run. Build in the session's own checkout on branch `ccr-278a8d47-q48q5c`.
