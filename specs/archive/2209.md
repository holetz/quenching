## Problem

`/quenching-git cleanup` offers nothing for a worktree slot whose lock outlived its work: `cq git stale` marks it `locked` and `preserved`, so the only remedy is a manual `cq git worktree release` per slot, and `release` then refuses on any ignored file outside `shared.regenerablePaths`. In a target observed on 2026-11-20 (databricks-risco-gold, `worktreeSlots.min` 10), 10 of 16 slots were held by specs already in `archive`, with HEAD contained in `origin/master`, no tracked changes and no live process in the directory; cleaning them took a manual audit, moving `.quenching/handoff/*.md` back to the main checkout, moving `databricks/.databricks/` (Databricks CLI bundle state, a regenerable path the target's `.databricks/` entry misses once the bundle root moved into a subdirectory) and generated `build/` output aside, and then releasing slot by slot — the run should detect this state and resolve it itself.

Evidence the report already has or can cheaply derive per slot: the holder spec's stage (`archive`), HEAD ancestry against the remote base, porcelain status, processes with cwd inside the slot, and the lock's session id. Ignored content that blocked release in that run fell into three classes: handoff files under `.quenching/handoff/` (belong beside the spec in the main checkout, never discardable), tool state under a nested `.databricks/` (regenerable), and build output of a generator (regenerable, but only the target can declare it).

## Proposal

O relatório de `cq git stale` passa a avaliar cada slot **tomado** (lock do quenching) e a oferecê-lo como candidato de **reclaim** só quando toda a evidência está a favor: a spec dona do lock está em `archive`, o HEAD do slot está contido em `<remote>/<base>`, o porcelain está limpo, nenhum conteúdo ignorado fica fora do regenerável declarado (`shared.regenerablePaths`, mais os arquivos de `.quenching/handoff/` e `.quenching/codex/`, que o release recolhe) e nenhum processo tem cwd dentro do slot. Qualquer evidência ausente ou contrária mantém o slot `preserved`, com o bloqueador nomeado.

O candidato entra no `manifest` como `kind: slot`, com a ação `cq git prune --slot <path> --id <id> --expect-tip <head> --confirm-inactive`, que relê o relatório e chama o próprio `cq git worktree release`. O release, por sua vez, **move** `.quenching/handoff/` para o `.quenching/handoff/` do checkout principal (nome colidindo → sufixo, nunca sobrescreve) em vez de recusar por ele. `/quenching-git cleanup` ganha a decisão **D4 — slots arquivados**, separada de D3.

```
antes:  stale → slot tomado = preserved [locked] → release manual por slot → recusa em ignorados
depois: stale → slot tomado → evidência (archive, HEAD ⊂ origin/base, limpo, sem processo, ignorados cobertos)
              ├─ tudo a favor → manifest kind=slot candidate [archived-holder] → D4 → prune --slot → release
              └─ falta algo   → preserved [bloqueadores nomeados]
        release → move .quenching/handoff/* para o checkout principal → detach → unlock → branch -d se mergeada
```

## Out of Scope

- Mudar a semântica de `shared.regenerablePaths` (uma entrada com barra final ancora na raiz, ao contrário do gitignore): o regenerável segue o que o alvo declara (decisão do épico 2214); a divergência fica em `## Discoveries`.
- Declarar caminhos regeneráveis de um alvo (`databricks/.databricks/`, `build/`): é do alvo, no seu `.agents/quenching.json`.
- O caminho de `acquire` que libera um slot tomado com branch mergeada (`_take` / `_merged_holder`): não muda aqui; o vazamento de `.quenching/handoff/` nesse caminho fica em `## Discoveries`.
- Remover (`git worktree remove`) um slot tomado: o reclaim devolve o slot ao pool; remover continua sendo só do slot livre acima do piso.
- Liberar sem confirmação humana: o cleanup continua pedindo a seleção e a confirmação de inatividade; nenhum grant, hook, CI ou `allowed-tools` muda.
- Detecção de processos fora do Linux: sem `/proc`, a evidência é `process-lookup-unavailable` e o slot fica preservado.

### Forma

- `slots.reclaim_evidence(cwd, slot, remote, base, rules) -> {spec, phase, head, eligible, blockers, ignored, processes}`. Bloqueadores, em ordem: `foreign-lock` (lock que não é do quenching), `holder-not-a-spec` (lock sem id numérico), `holder-unknown` (a spec não resolve no backend), `holder-not-archived`, `base-unresolved` (sem `refs/remotes/<remote>/<base>`), `unmerged-head`, `inspection-failed`, `dirty` (porcelain com tracked ou untracked), `ignored-content-unrecognized`, `process-lookup-unavailable`, `process-in-slot`. `eligible` só sem bloqueador.
- Ignorados: os mesmos `ignored_entries` + `classify` do `release`; `.quenching/handoff/` e `.quenching/codex/` não bloqueiam, porque o release os recolhe ao checkout principal.
- Processos: Linux lê `/proc/<pid>/cwd` (`readlink`, realpath) e conta todo pid cujo cwd é o slot ou está dentro dele; entradas sem permissão (outros usuários) e pids que somem são ignorados; sem `/proc` → `None` → `process-lookup-unavailable`.
- `stale_report` não busca (`fetch`) nada: usa o `<remote>/<base>` já buscado, como o resto do relatório.
- Manifest: cada slot tomado vira uma entrada `kind: slot` (id `entry_id("slot", realpath)`), `candidate` com `reasons: ["archived-holder"]` e `recommended: true`, ou `preserved` com os bloqueadores; a entrada `kind: worktree` desse slot deixa de existir (o `report["worktrees"]` continua listando-o com `locked`).
- `prune --slot <path>`: exige `--confirm-inactive` e `--expect-tip`; relê o relatório e age só sobre um `kind: slot` `candidate` no mesmo tip e id; então chama `slots.release` com `--path <path>` e `--base <base>`, e devolve o payload dele.
- `release`: depois do fetch e antes do `switch --detach`, move cada arquivo de `<slot>/.quenching/handoff/` (quando é diretório real, não link) para `<primary>/.quenching/handoff/<mesmo caminho relativo>`; nome existente → `<stem>-<slot>-<n><ext>`; payload `handoff: [{from, to}]`. O filtro de `left` passa a ignorar também `.quenching/handoff`.

### Assumptions

- Processos de outros usuários não seguram cwd num slot do usuário; a leitura de `/proc` os ignora (→ `## Risks`).
- `info["phase"] == "archive"` é o sinal de spec arquivada em todo backend (git, GitHub, Azure), como `cq specs status` reporta (→ `## Design` §Forma).

| Abordagem | Custo | Ganho | O que fecha |

## Risks

- **Processo invisível**: um processo de outro usuário (ou num namespace de PID diferente, como um contêiner) com cwd no slot não aparece em `/proc`; mitigação: a seleção D4 e `--confirm-inactive` continuam humanas.
- **Fase lida errada**: um backend inacessível faria toda spec `holder-unknown` — o slot fica preservado, nunca liberado.
- **`origin/<base>` desatualizado**: sem fetch, um merge recente ainda não buscado deixa o slot `unmerged-head` (falso negativo, seguro); o cleanup já manda buscar explicitamente e refazer o relatório.
- **Colisão de handoff**: dois slots com o mesmo nome de handoff — o sufixo evita sobrescrever; nenhum arquivo é apagado.
