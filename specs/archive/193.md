## Problem

quenching/assets/bin/quenching/codex/eligible.py:81 só tira a / inicial e compara o primeiro segmento, e specs/parse/tasks.py:57 não normaliza o caminho. Reprodução: eligibility dá 1 (recusa) para files:["docs/x.md"] e 0 (elegível) para ["./docs/x.md"]. Consequência: o Codex é despachado para escrever conhecimento sob docs/, que a regra proíbe. No espelho, implement.py:147 compara ./src/a.py com o caminho que git status reporta, nunca casa, e a guarda reprova uma escrita legítima.

## Proposal

Uma única normalização de caminho do repositório, `repo_path(entry)` em `quenching/assets/bin/quenching/codex/eligible.py`, aplicada a toda entrada de `files:` antes de qualquer comparação no pilar Codex: tira a anotação `(new)`, troca `\` por `/`, aplica `posixpath.normpath` (que remove `./` e resolve `x/../`) e tira as `/` iniciais. `eligibility` passa a julgar `docs/`/`knowledge/` e a medir os tokens sobre o caminho normalizado, e `run_implement` (`implement.py:156`) compara com `git status` o mesmo caminho normalizado. Assim `./docs/x.md` e `src/../docs/x.md` são recusados como `docs/x.md`, e `./src/a.py` casa com o `src/a.py` que o git reporta.

## Out of Scope

- Normalizar `files:` no parser (`specs/parse/tasks.py`) ou reescrever specs gravadas: o texto da spec fica como o autor escreveu; só o pilar Codex compara caminhos normalizados.
- `specs/commands/parallel.py::_norm_file` (que usa `strip("./")`, também impreciso para `..`): é outro consumidor, com outra semântica (sobreposição de `[P]`); fica como descoberta.
- Caminhos que escapam da raiz (`../x`) e caminhos com aspas no `git status --porcelain`: nenhum dos dois é o defeito relatado.
- O texto de `docs/standards/architecture/codex-pillar.md`: já diz "none of them under `docs/` or `knowledge/`"; só o código divergia.

## Design

Uma função, um lugar: `repo_path` mora em `eligible.py` ao lado de `strip_annotation` (que `implement.py` já importa de lá), e substitui as três comparações hoje feitas com `lstrip("/")`:

```
entrada de files:      repo_path               uso
"./docs/x.md"      ->  "docs/x.md"         ->  recusa docs/ (eligible.py:81)
"/src/a.py (new)"  ->  "src/a.py"          ->  task_tokens (eligible.py:42)
"./src/a.py"       ->  "src/a.py"          ->  guarda vs git status (implement.py:156)
"src/../docs/x"    ->  "docs/x"            ->  recusa docs/
```

`posixpath.normpath` já é o idioma do repositório para isso (`git/audit.py:402`). Um caminho vazio ou `.` vira `.` após normpath; não é `docs` nem casa com `git status`, o que mantém o comportamento atual para entradas sem sentido.

### Assumptions

- A semântica de `files:` é um caminho relativo à raiz do repositório; `./x` e `x` nomeiam o mesmo arquivo — sustenta `## Proposal`.

## Open Decisions

- none — a forma da normalização é decidida pela evidência (`posixpath.normpath`, idioma já usado em `git/audit.py:402`), e o escopo é o pilar Codex.

## Risks

- Um `files:` hoje escrito como `./x` passa a casar com a guarda: é o comportamento pretendido, não uma regressão.
- `normpath` colapsa `a//b` e `a/./b`; qualquer comparação com `git status` só melhora, porque o git nunca reporta essas formas.
