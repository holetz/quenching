## Problem

Reading is not enough for the PO and for agents that develop specs: they need to create specs, write sections, stamp records, check tasks and add epic members through the quenching specs service's MCP. Expose those verbs from the same rules core `cq` runs on, with explicit confirmation on gated moves (approval, promote) so a model cannot stamp a human decision.

Formerly holetz/tempering#2.

Member S7 of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent).

## Proposal

Extend the `cq specs mcp` stdio server (member 2085) with a write surface over the same core, and with a human confirmation on the moves that stamp a human decision.

- Seven write tools, each a fixed CLI verb dispatched in-process through `cli.main` exactly like the read tools: `specs_create` (new), `specs_section_write` (section --write, one heading per call, body on stdin), `specs_record`, `specs_task` (check, uncheck, block, descope), `specs_epic_add`, `specs_discover`, `specs_promote`.
- Gated moves: the `approved`, `reviewed`, `merge` and `outcome` records and `specs_promote`. The server asks the human through the client with MCP `elicitation/create` and runs the verb only on an accept. No argument confirms anything; a client without the `elicitation` capability gets `mcp-confirmation-unavailable`, a decline or cancel gets `mcp-confirmation-refused`, and nothing changes.
- `approved` takes no fields: the server writes `date` and `by=human` after the accept, and only on a spec that met the ready gate (`mcp-not-ready` before the question otherwise). `low-gear` and `orchestrator-forced` are never reachable through MCP. `specs_promote` has no `force`; its CLI `--dry-run` refusals reach the human before the question does.
- The write tools carry `readOnlyHint: false`; the gated ones carry `destructiveHint: true`. Reads keep their annotations and the size contract (no tool returns a whole spec).

## Out of Scope

- Swapping `Bash(cq specs ...)` grants in agents and commands for these tools. That 1:1 swap is authorized by the human only with review in the PR before merge, and belongs to a later member, not to this spec.
- Any grant, `allowed-tools`, `tools:`, hook, script or CI widening (epic 2045).
- Configuration verbs (`config`, `verification`, `title`, `tags`, `assignee`, `start`, `target`, `release`, `migrate`) and sync: member 2087 and later.
- A generic "run cq" tool or argv passthrough.
- `--force` on promote, and the `by=low-gear` / `by=orchestrator-forced` approvals.

## Design

**Decision 1 — same dispatch, closed table.** `WRITES` is a second closed map from tool name to a fixed verb, built like `TOOLS`; every argument is validated and passed as a separate argv element. Section bodies travel on a replaced `sys.stdin` for the one in-process call, never through a shell, and every call gets an empty stdin otherwise so no verb can read the protocol stream.

**Decision 2 — confirmation is out of band.** The model cannot confirm: confirmation is a server-to-client `elicitation/create` request whose answer comes from the client's human, read synchronously from stdin (the loop is serial). Fail closed: no `elicitation` capability declared at `initialize`, a decline, a cancel, a closed stream, or `confirm` not exactly `true` all refuse. The alternatives of a confirm token echoed by the model or a `confirm: true` argument were rejected because the model can supply both.

**Decision 3 — preflight before the question.** A gated move is checked first so the human is never asked to confirm something the core will refuse: `approved` requires the ready gate (as `portal.py` does), and `promote` runs the CLI `--dry-run`.

**Decision 4 — approvals keep their truthful `by`.** The server writes `approved` with `by=human` only after the accept. Generic `fields` are refused for `approved`, so nothing can claim another attribution.

Binding contracts: exit codes and `--json` payloads stay as the CLI emits them; the tool failure shape stays `isError: true` plus the CLI `code`.

## Alternatives Considered

**Reference projects (epic holetz/forge#1), read 2026-10-24.**
- **MrLesk/Backlog.md (MIT)**: reuses the shape of one store behind an MCP server and the board; adapts it by dispatching into the existing `cq` core instead of a parallel store; rejects its unconfirmed write tools, because the specs service has human-only gates.
- **microsoft/azure-devops-mcp (MIT, to confirm)**: adapts the read-only/toolset idea (annotations plus a closed tool table) and rejects the remote endpoint and Entra auth, which belong to the Azure Boards adapter, not to a local stdio server.
- **automazeio/ccpm (MIT)**: rejects; it targets tracker sync, which is member 2088.
- **`cq specs serve` (`portal.py`)**: reuses its approval rule (ready gate checked before `approved`, `by=human`) and adapts it to the MCP transport.

**Alternatives for the confirmation.** A `confirm: true` argument or an echoed token: rejected, the model can supply either. Reject all gated moves over MCP and leave them to the CLI: safe but gives the PO no path; kept as the fallback when the client has no `elicitation`.

## Open Decisions

- none — every item was decided from the evidence. The 1:1 swap of `Bash(cq specs ...)` grants for these tools is deliberately a later member with human review before merge.

## Risks

- A client that declares `elicitation` but auto-accepts defeats the human gate; the server cannot detect it. Mitigation: the question names the move and spec, and the README says the gate is only as good as the client.
- A client that does not implement `elicitation` cannot use gated moves; the refusal names the CLI and portal as the way.
- Concurrent stdin reads while asking drop unrelated messages; acceptable because the loop is serial and clients wait for their call's answer.
