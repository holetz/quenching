## Problem

A 1687 (PR #1693) fez `knowledge/config.py:38-42` cair nos padrões quando `.claude/hooks/hooks-config.json` não é UTF-8 ou não é um objeto JSON. A revisão de correção da rodada 3 do autopilot de 2026-10-15 reproduziu, com um bundle que só tem WARNs:

- `{"okfValidate":{"warnAsError":true}}` → `cq knowledge validate docs` sai 1 (esperado);
- o mesmo conteúdo com um byte Latin-1 (`"caf\xe9"`) → sai 0, sem nada no stdout nem no stderr;
- `[{"okfValidate":{"warnAsError":true}}]` → sai 0, em silêncio.

Em 0f9b988d os dois casos falhavam alto (traceback, exit 1). Agora uma config quebrada faz o gate de warnings **passar** em silêncio, em vez de falhar. Um JSON truncado já era silencioso antes. Consequência: quem declarou `warnAsError` perde o gate sem aviso. O contrato pede recusa (exit 2) com uma mensagem que nomeie o arquivo para config ilegível, inválida ou que não seja objeto, nunca o padrão silencioso.

## Proposal

- `cq knowledge validate` recusa (exit 2, `--json` com `code`) quando `hooks-config.json` ou `hooks-config.local.json` existe e é ilegível, não é UTF-8, não é JSON válido ou não é um objeto JSON.
- A mensagem da recusa nomeia o arquivo e o motivo.
- Config ausente continua usando os padrões; config válida sem o bloco `okfValidate` continua usando os padrões.
- Os testes que fixavam "cai nos padrões" passam a fixar a recusa, um por gatilho.

## Out of Scope

- Mudar o contrato de `nav` (já recusa via `nav-config-unreadable`).
- Validar o conteúdo das chaves de `okfValidate`: fora do que o relatório reproduz.

## Design

- Regra durável: uma config declarada que não pode ser lida nunca vira o padrão em silêncio; recusa (exit 2) nomeando o arquivo.
- `_load_config` levanta `ConfigError(path, motivo)` para OSError, UnicodeDecodeError, ValueError e raiz não-objeto; arquivo ausente segue sendo ignorado. `run_cli` captura e chama `refuse({"code": "config-unreadable", "message": ...}, args.json)`, o mesmo caminho de `nav`.
- Alternativa pesada contra: warning no stderr e seguir com padrões, rejeitada porque o gate de `warnAsError` continuaria passando.

## Alternatives Considered

- Manter o fallback e só avisar no stderr: o gate declarado continuaria passando; perdeu.

## Open Decisions

- none — o código de recusa `config-unreadable` é nomeado no Design.

## Risks

- Repos com config já quebrada passam a falhar com exit 2: ACCEPTED — é o contrato pedido, e a mensagem diz o arquivo.
