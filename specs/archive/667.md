## Problem

Na 1042262, depois do merge, o envio do store (`pr_merge` → specs push, `specs_external(verb="push")`, `cq specs reconcile --write`, `cq specs promote --to archive`) falhou seis vezes seguidas contra o Azure DevOps: `error: unable to rewind rpc post data - try increasing http.postBuffer`, `RPC failed; curl 65/56/55 Recv failure`, `the remote end hung up unexpectedly`. O promote deixou `outcome: done` gravado e a spec em `plans` ("re-run promote"). Só passou com `http.postBuffer=1048576000` e `http.version=HTTP/1.1` no ambiente do comando, uma configuração que o agente teve de inventar. A melhoria tem de tirar essa intervenção manual da escrita do store.

Minimal fix proposed: o push do store, ao reconhecer a falha de `postBuffer`/RPC, tenta uma vez de novo com `-c http.postBuffer=… -c http.version=HTTP/1.1` e, se falhar de novo, devolve um código que nomeia o retry.

**Insumos**

- Runtime de push do store (`quenching/assets/bin/quenching/specs/`, onde está `sp-git-push-failed`)
- Saída citada acima; o comando que passou: `GIT_CONFIG_COUNT=2 … cq specs promote 1042262 --to archive --outcome done --json`
- Spec de origem: 1042262 (databricks-risco-gold, PR 234120), 2026-11-27., conclude passo 8

## Proposal

`GitBackend._push` reconhece a falha de transporte de repositório grande (`http.postBuffer`, `RPC failed`, `hung up unexpectedly`, `curl <n>`) e repete o push **uma vez** com `-c http.postBuffer=1048576000 -c http.version=HTTP/1.1`. Se o retry também falha, a recusa deixa de ser o genérico `sp-git-push-failed` e vira `sp-git-push-transport-retried`, cuja mensagem nomeia o retry feito e a configuração usada, para o agente não precisar inventá-la. Falhas que não são de transporte (rejeição, autenticação) seguem sem retry.

## Out of Scope

- O `promote` ficar com `outcome: done` gravado e a spec em `plans` quando o push falha: com o retry no push a causa dominante some; reordenar o promote é outra spec.
- Configuração global do git do usuário e variáveis `GIT_CONFIG_*` do ambiente.

- `quenching/tests/test_specs_git_backend.py` — regressão do retry
- a superfície implantada deste repositório (`.agents/quenching/assets/bin/quenching/specs/backends/git.py`), atualizada por `cq deploy --target . --write`

### Standards this spec will write into docs/standards/

- none — o comportamento é interno do runtime de push; nenhum standard descreve o transporte do store.

## Validation

- `python3 -m unittest quenching/tests/test_specs_git_backend.py` passa, incluindo: um push que falha com `unable to rewind rpc post data` é repetido uma vez com os dois `-c` e, se o segundo passa, o write termina ok; se o segundo também falha, a recusa é `sp-git-push-transport-retried`; uma falha sem marcador de transporte não é repetida. O teste de retry falha na base.
- `python3 quenching/assets/bin/cq deploy --target . --check` sai 0 depois do redeploy.
- `QUENCHING_TEST_SCOPE=affected bash scripts/verify_repo.sh` termina com zero erros.

## Design

`_push` ganha um laço de no máximo duas tentativas: a primeira como hoje; se `code != 0` e a saída casa `_TRANSPORT_MARKERS`, a segunda antepõe `-c http.postBuffer=… -c http.version=HTTP/1.1` ao `push` (as opções `-c` vêm depois de `-C`/`--git-dir` do `_base()`, antes do subcomando). Se a segunda falha, a saída devolvida termina com uma linha `quenching: retried with http.postBuffer, http.version=HTTP/1.1`; `sync` testa essa linha e escolhe o código `sp-git-push-transport-retried`. O retry vale também para o push sem lease (o append) porque ambos passam por `_push`.

### Assumptions

- O tamanho 1048576000 e HTTP/1.1 são os que passaram na 1042262 — `## Proposal` depende disso.

## Alternatives Considered

- Aumentar o `http.postBuffer` sempre, sem esperar a falha: muda o transporte de todo push, inclusive os que funcionam.
- Mais de um retry: a causa é determinística; um segundo igual não ajuda e adia o erro.

## Open Decisions

- none — o problema e o código resolvem o desenho.

## Risks

- Um marcador largo demais repete um push que falhou por outra causa; o custo é um push a mais, e a recusa final continua carregando a saída do git.

## Outcome

Entregue: `GitBackend._push` repete uma vez o push do store com `-c http.postBuffer=1048576000 -c http.version=HTTP/1.1` quando a saída casa um marcador de transporte (`http.postBuffer`, `RPC failed`, `hung up unexpectedly`, `curl 55/56/65`, `unable to rewind rpc post data`); se o retry também falha, a recusa é `sp-git-push-transport-retried`, cuja mensagem nomeia o retry feito. Falhas sem marcador de transporte não são repetidas. Quatro testes em `test_specs_git_backend.py` fixam o comportamento; a superfície implantada foi regenerada.

Ficou de fora: o `promote` deixar `outcome: done` gravado com a spec em `plans` quando o push falha (reordenar o promote é outra spec); config global do git do usuário.
