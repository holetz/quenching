## Problem

A target project that only needs to READ another project's provider-owned specs cannot get that
capability on its own. Enabling the `quenching` plugin registers all 54 commands, and
[install-profiles.md](/docs/standards/architecture/install-profiles.md) (spec 1111) measured that
`shared.profiles` changes no command residency, so a profile cannot narrow that surface. The
concrete case is an Obsidian vault that wants to list another project's open specs and their
unchecked tasks as its to-do list. It needs to do that without the aligners, the lifecycle writers
or the git pillar in its context, and without any path to write the tracker.

## Proposal

- A third plugin in this marketplace, `quenching-specs-reader`, carrying exactly ONE command:
  `/quenching-specs-reader:read`. A target enables that plugin alone and pays for one description.
- A read-only entry point, `bin/cq-specs-read`, which admits only the read verbs of `cq specs`
  (`list`, `status`, `show`, `section` without `--write`/`--fold`, `next`, `config`) and disables
  every backend write primitive at runtime before dispatching. Read-only is a property of the
  code, not of the prose.
- The project to read is chosen by `--root <checkout>`, then by the `QUENCHING_SPECS_ROOT`
  environment variable (settable in the target's `.claude/settings.json` `env` block), then by the
  working directory. This lets a vault that is not itself a repository point at a sibling checkout.
- The Python package and specs schema are NOT hand-copied. `scripts/sync_specs_reader_plugin.py`
  generates `assets/bin/**`, `assets/specs/**`, `VERSION` and `.claude-plugin/plugin.json` from
  `plugins/quenching/`, records a source digest, and runs with `--check` in
  `scripts/verify_repo.sh`, so drift fails the repository gate.

## Out of Scope

- Reading a GitHub repository with no local checkout (a `--repo owner/name` mode) — provider
  resolution is derived from the checkout's remote today, and adding a checkout-free resolution
  is a backend change with its own cache-key and Azure questions; the vault case has the checkout.
- Writing anything into the vault (exporting specs as notes) — the reader returns data; what the
  target does with it is the target's business, and a writer would reintroduce a write path.
- A Codex translation of the reader — Codex skills already come per-skill from
  `quenching-codex`; nothing measured a need.
- Narrowing the `quenching` plugin itself — profiles stay a conduction scope, as measured.

## Validation

- `bash scripts/verify_repo.sh` passes, including the new reader lockstep step.
- `python3 scripts/sync_specs_reader_plugin.py --check` exits 0 on a fresh tree and 1 after
  touching any file under `plugins/quenching/assets/bin/`.
- From a non-git directory, `QUENCHING_SPECS_ROOT=<this checkout> plugins/quenching-specs-reader/bin/cq-specs-read list --json --lean`
  returns `ok: true` with this repository's specs.
- `cq-specs-read new x`, `cq-specs-read section 1 Problem --write` and `cq-specs-read task ...`
  refuse with exit 2 and write nothing.
- A headless Claude Code session started with only `--plugin-dir plugins/quenching-specs-reader`
  lists `quenching-specs-reader:read` and no `quenching:*` command.

## Design

- **A separate plugin, not a profile.** Plugin enablement is the only unit Claude Code gives a
  target to turn on; install-profiles.md already records that profiles do not change residency.
- **Generated payload, hand-owned surface.** The same model as `quenching-codex`: the editable
  source stays `plugins/quenching/`. The generator owns an explicit file set and never touches the
  hand-owned `commands/`, `bin/` and `README.md`. The layout `assets/bin/` + `assets/specs/` is
  preserved because `quenching/specs/schema.py` finds `assets/specs/` relative to its own package.
- **Version derived, not bumped.** `release` bumps four artifacts and the marketplace regex
  replaces only the first `"version"`. The reader's `plugin.json` and `VERSION` are therefore
  generated from `plugins/quenching/VERSION`, and its marketplace entry carries no `version`, so a
  release shows up as a `--check` failure that `--write` repairs, never as silent drift.
- **A distinct executable name.** `cq-specs-read`, not `cq`: when both plugins are enabled, each
  `<pluginRoot>/bin` is on `PATH`, and a second `cq` would shadow the full one.
- **Read-only in two layers.** A verb allowlist refuses at the argument boundary (exit 2), and the
  shim replaces `write_spec`/`create_spec`/`move_spec` on every loaded backend class with a
  refusal, so a read verb that one day grows a side effect still cannot write the tracker.

## Alternatives Considered

- **`shared.profiles` to hide commands** — rejected: measured in spec 1111 to change nothing about
  residency.
- **A reader plugin whose `source` is `./plugins/quenching`** — rejected: same directory, same 54
  commands.
- **Symlinks from the reader into `plugins/quenching/assets/bin`** — rejected: plugin installation
  copies into a cache, and a symlink leaving the plugin root is not guaranteed to survive it.
- **Letting the reader depend on the `quenching` plugin's `cq` on PATH** — rejected: it would
  force the target to enable the full plugin, which is the problem.

## Open Decisions

- none — the checkout-free `--repo` mode is recorded under Out of Scope and would be its own spec
  once a target without a checkout exists.

## Risks

- The generated payload grows the repository by about 1.5 MB per copy — ACCEPTED: the Codex
  sibling already carries the same package, and the gate keeps it byte-identical.
- A future `cq specs` read verb could gain a write side effect — mitigated by the runtime write
  block, which refuses at the backend primitive regardless of the verb.
- A release forgets to regenerate the reader — mitigated by `--check` in `verify_repo.sh`.

## Handoff

- The reader lives at `plugins/quenching-specs-reader/`; the editable source of its payload is
  `plugins/quenching/assets/bin/` and `plugins/quenching/assets/specs/`.
- Run `python3 scripts/sync_specs_reader_plugin.py --write` after touching the source, then
  `bash scripts/verify_repo.sh`.
- Commit subjects follow `plan/<id>-<handle>: <task-id> <title>`.

## Outcome

Shipped `quenching-specs-reader`, a third marketplace plugin with one command
(`/quenching-specs-reader:read`) and one read-only entry point (`cq-specs-read`). Its payload and
version are generated from `plugins/quenching` by `scripts/sync_specs_reader_plugin.py`, and
`--check` runs in `scripts/verify_repo.sh`. Measured end to end: a headless Claude Code 2.1.284
session started from a non-repository directory with only this plugin registered
`quenching-specs-reader:read` and no `quenching:*` command. With `QUENCHING_SPECS_ROOT` set, it
listed the live front and read one spec's tasks.

Beyond the declared tasks: `citation-check.sh` now resolves `${CLAUDE_PLUGIN_ROOT}` against the
citing file's own plugin, and the review narrowed the command grant to `Bash(cq-specs-read:*)`.
Left out, by design: a checkout-free `--repo` mode and a Codex translation of the reader. For the
next reader: a `dontAsk` session needs `Bash(cq-specs-read:*)` in the target's
`permissions.allow`, as recorded in the reader README and in `specs-reader-plugin.md`.
Reviewed, distilled, ready for merge.
