## Overview

Quando um comando de spec escreve a lista de tarefas, ele às vezes inclui coisas como "subir a
versão", "atualizar o changelog" ou "atualizar a documentação". Nenhuma dessas cabe ali: no momento
em que a lista é escrita ninguém ainda sabe qual vai ser o release, e duas specs trabalhando ao
mesmo tempo escolheriam o mesmo número e colidiriam no merge. Quem faz isso é a etapa de
fechamento, `/quenching:specs:conclude`, que roda depois de tudo pronto e já sabe a resposta.

O `conclude` já diz isso no próprio corpo — mas só do lado dele. Quem *escreve* a lista nunca foi
avisado, então a tarefa nasce, ocupa uma caixa, entra no plano que o humano aprova, e só é recusada
lá na frente. Esta spec leva a regra para o lado que escreve.

Com uma ressalva importante, para a regra não virar "nenhuma tarefa de documentação": um documento
que a spec **declarou** de antemão que vai escrever continua sendo tarefa, e obrigatória — o
validador inclusive cobra. O que sai é o que só a construção **revela**. A linha é temporal:
declarado antes é tarefa, revelado depois é do fechamento.

## Problem

Os comandos que **autoram** a lista de tasks de uma spec — `/quenching:specs:create` e
`/quenching:specs:develop`, e a reference compartilhada
`assets/references/specs-develop/spec-driven.md` — não proíbem nada, e por isso continuam nascendo
na spec tasks de bump de versão, de atualização de docs e de outras obrigações que só se resolvem
no merge.

A fronteira já está declarada do lado que **consome** a lista: `commands/specs/conclude.md:77` diz
que o que um padrão prende ao *merge* — um bump de versão entre artefatos, uma obrigação de release
— se resolve no conclude e não se constrói como task, com a razão em `conclude.md:224-228` (um bump
feito ali parte da base que a branch realmente merge, em vez de colidir com uma spec irmã que
bumpou para o mesmo número dias atrás). A `description` de `commands/specs/execute.md` já roteia
"a version bump or other release obligation → /specs:conclude".

O resultado é uma regra escrita só na saída: o execute recusa a task, mas ela já foi escrita, já
ocupou uma caixa e já apareceu no plano que o humano aprovou. A autoria não conhece o contrato que
o fechamento aplica.

## Proposal

Escrever, no lado que **autora** `## Tasks`, a mesma fronteira que o `conclude` já aplica no lado
que a **consome**: uma task é trabalho cujo resultado é conhecível no momento em que ela é escrita
e que cabe em um commit na branch da spec. Três classes ficam de fora, cada uma com o comando que
de fato a possui:

| Classe que não é task | Por que não é | Quem a possui |
| --- | --- | --- |
| Obrigação de merge — bump de versão, entrada de changelog, re-stamp de manifest, tag, nota de release | O que o release É depende da última task, então nada disso é conhecível na task 1; agendada como trabalho ela ainda colide entre branches irmãs que bumpam da mesma base para o mesmo número | `/quenching:specs:conclude` passo 5 |
| O `/.docs/` que o trabalho **revelou** | Não existe no momento da autoria — é resultado do que foi construído, não insumo dele | `/quenching:specs:conclude` passo 3, que o escreve junto com a revisão da branch |
| As ações de fechamento do ciclo — revisar a branch, arquivar, destilar, mergear ou abrir o PR | São os passos do próprio `conclude`, não trabalho que a spec entrega | `/quenching:specs:conclude` |

E uma classe que **permanece** task, dita explicitamente para a regra não engolir o que já é
obrigatório: cada caminho `/.docs/standards/**.md` que a spec **declara** sob a sub-heading parseada
de `## Impact` continua tendo sua própria checkbox. Esse é o pareamento que `sp-impact-uncovered`
cobra e que `/quenching:specs:execute` escreve durante a construção — construir a spec *é* provar a
regra. A fronteira é **declarado versus revelado**, nunca "docs versus código".

A regra é prosa nos corpos que autoram, ancorada num standard do repo:

- `/.docs/standards/workflows/plan-artifacts.md` — o contrato ganha a seção que diz o que `## Tasks`
  não carrega, ao lado das que já dizem por que ele está no ready set e como `## Impact` declara os
  standards. É o standard que a spec declara em `## Impact`, então o `execute` o escreve.
- `plugins/quenching/assets/references/specs-develop/artifacts.md` §`## Tasks` — a doutrina de
  autoria que `/quenching:specs:develop` carrega no passo 5, e o sítio primário da correção. A dica
  de agrupamento `(setup → core → wiring → tests → docs)` também é apertada: aquele `docs` solto
  convida exatamente a task que esta spec proíbe.
- `plugins/quenching/assets/references/specs-create/plan-mapping.md` §The mapping — o caminho do
  arquivo de plano, onde uma linha "Etapas: bump da versão" do plano nativo é copiada para
  `## Tasks` sem que nada a barre.
- `plugins/quenching/commands/specs/develop.md` e `create.md` — um invariante em cada, porque
  invariante é o que sobrevive a uma releitura parcial do corpo.

## Design

### A fronteira é declarado versus revelado, não docs versus código

O eixo errado é "task de docs é proibida". Ele quebra imediatamente: escrever
`/.docs/standards/**.md` é task obrigatória sempre que a spec declarou o caminho sob a sub-heading
parseada de `## Impact` — `parse_impact_standards()` lê exatamente esses caminhos e `validate` emite
`sp-impact-uncovered` (warn) para qualquer um que nenhum item de `## Tasks` nomeie
([plan-artifacts.md](/.docs/standards/workflows/plan-artifacts.md) §`## Impact` carries one parsed
sub-heading). Construir a spec *é* provar a regra.

O eixo certo é **temporal**: o que a spec **declarou** antes de construir é task; o que a construção
**revelou** é do `conclude`. É a mesma linha que `conclude.md:74-76` já traça
(*"Declared rules were already written… What lands here is what the work revealed"*), agora dita do
outro lado.

### A ressalva que impede a regra de proibir uma spec legítima

Uma spec cujo **produto é o release** — mexer no lockstep de versão, no fluxo de release, no
`CHANGELOG` como artefato — tem bump e changelog como a entrega, não como obrigação de merge. A
regra não pode engolir esse caso, senão torna essa spec inescrevível.

O teste que separa os dois: **a task existiria se esta branch nunca fosse mergeada?** Escrever o
código que executa o bump existe por si; executar o bump *deste* ciclo só existe porque há um merge.
O primeiro é task; o segundo é passo 5 do `conclude`.

### O que muda em cada arquivo

| Arquivo | A mudança |

| `assets/references/specs-develop/artifacts.md` §`## Tasks` | O bullet novo com a regra e o comando dono de cada classe; e a dica de agrupamento `(setup → core → wiring → tests → docs)` apertada, porque aquele `docs` solto convida exatamente a task proibida |
| `assets/references/specs-create/plan-mapping.md` §The mapping | Uma linha na tabela de mapeamento para as partes do plano nativo que caem nas três classes: não viram `## Tasks`, e a razão é nomeada com o comando dono |

Os dois references são corrigidos porque nenhum dos dois cobre o outro: `develop` carrega
`artifacts.md` só no passo 5, e o caminho de arquivo-de-plano do `create` nunca o abre — ele lê
`plan-mapping.md`.

## Alternatives Considered

- **Um achado `sp-` mecânico no `specs.py validate`, por heurística de palavra-chave sobre o texto
  da task.** Descartado: acerta `- [ ] 6.1 Bump the VERSION file` e erra
  `- [ ] 4.1 Escrever /.docs/standards/ci-cd/versioning-release.md`, que contém "version" e é
  exatamente a task obrigatória do §`## Impact`. Um gate que produz falso positivo na task que o
  outro gate exige treina o humano a ignorar os dois. Parkeado em `## Discoveries` como spec
  própria, se alguém achar um sinal melhor que palavra-chave.
- **Mudar só o `conclude`, para ele absorver a task em vez de o autor não a escrever.** Descartado:
  a caixa já teria ocupado o plano que o humano aprovou e já teria contado no ready gate. O custo
  aparece antes do `conclude` rodar.
- **Confiar na recusa que a `description` do `/quenching:specs:execute` já faz.** Descartado: é a
  última linha, não a primeira, e só funciona para quem lê aquela `description` — o `develop` que
  escreveu a task não a lê. Ela permanece como rede, sem ser a regra.
- **Proibir toda task de docs.** Descartado no `## Design`: quebra `sp-impact-uncovered` e o
  pareamento que ele cobra.
- **Escrever a regra só na reference `artifacts.md`, sem standard.** Descartado: a reference é
  prosa do plugin: um repo target que use o quenching herda o comportamento, mas o contrato que o
  justifica não fica ancorado em `/.docs/standards/`, onde as outras regras do artefato spec vivem.

## Risks

- **A regra pousa em prosa que a sessão não carrega.** `artifacts.md` §`## Tasks` só é lido no passo
  5 do `/quenching:specs:develop`; o caminho de arquivo-de-plano do `/quenching:specs:create` lê
  `plan-mapping.md` e nunca abre `artifacts.md`. Mitigação: os dois references recebem a regra, e os
  dois comandos recebem um invariante — invariante é a parte do corpo que sobrevive a uma releitura
  parcial.
- **A regra ser lida como "nenhuma task de docs".** É o erro mais provável, e ele quebra
  `sp-impact-uncovered`. Mitigação: a classe que **permanece** task é dita no mesmo bullet, antes
  das que saem, e o teste do `## Design` (a task existiria se esta branch nunca fosse mergeada?) é
  citado junto.
- **A ressalva do release-como-produto virar porta dos fundos.** Uma spec pode alegar que seu
  produto é o release para escapar da regra. Mitigação: o teste é sobre a task, não sobre a spec —
  escrever o código que executa o bump é task; executar o bump *deste* ciclo não é, mesmo numa spec
  de release.
- **Custo de contexto.** Cada bullet novo em `artifacts.md` §`## Tasks` é relido em todo turno do
  passo 5 do develop. Mitigação: a regra é um bullet com tabela compacta, e a marcação
  `<!-- rules -->` / `<!-- rationale -->` mantém a razão fora do que `--rules-only` carrega.
- **`/.docs/standards/workflows/plan-artifacts.md` declara `resource: plugins/quenching/commands/specs/**`,
  então esta branch envelhece o doc.** É `stale-doc`, advisory por construção
  (CLAUDE.md §Operating this repo) — não é falha, e o gate se lê como zero erros.

## Outcome

**done** — a fronteira que só existia do lado que consome a lista de tasks agora existe do lado que
a autora, em quatro lugares e uma camada só: o contrato em
`/.docs/standards/workflows/plan-artifacts.md` §What `## Tasks` does NOT carry, a doutrina de
autoria nas duas references que os comandos realmente carregam
(`specs-develop/artifacts.md` §`## Tasks` para o `develop`, `specs-create/plan-mapping.md` §The
mapping para o caminho de arquivo de plano do `create`), e um invariante em cada um dos dois corpos.

O eixo é **declarado versus revelado**, nunca docs versus código: o `/.docs/standards/**.md` que a
spec declara sob a sub-heading parseada de `## Impact` continua sendo checkbox obrigatória — é o
pareamento que `sp-impact-uncovered` cobra — e o teste que separa os dois é *a task existiria se
esta branch nunca fosse mergeada?*

**O que a construção revelou, e que a spec não sabia ao ser escrita.** A regra já existia em
`/.docs/standards/ci-cd/versioning-release.md` §When the bump happens — *"A version bump is never a
task in a spec… and never at conclude either"* — mas num standard de `ci-cd` que ninguém autorando
tasks lê, e escrita só sobre bump de versão. Esta spec a generaliza (o `/.docs/` revelado e as ações
de fechamento do ciclo entram junto) e a põe onde a autoria passa.

**Merge:** estratégia `merge-commit`, rota **pull request** contra `develop` — a branch
`plan/obrigacoes-de-merge-nao-nascem-como-task`, cortada de `develop` em 6dbef27, não é mergeada
localmente; a revisão humana vive no PR, que é como a marcha mínima do
`/quenching:specs:orchestrate` paga por rodar o ciclo inteiro numa autorização só.

**Obrigações de release: nenhuma.** O lockstep de seis artefatos move-se uma vez por release, em
`develop`, imediatamente antes do merge `develop → main`, e nunca no conclude de uma spec. Nada foi
bumpado — o que é a própria tese desta spec aplicada a ela mesma.

**Ficou de fora.** Uma checagem mecânica (`sp-`) que recuse a task de obrigação de merge foi pesada e
descartada: heurística de palavra-chave produz falso positivo justamente na task que
`sp-impact-uncovered` exige (`Escrever /.docs/standards/ci-cd/versioning-release.md` contém
"version"). Não virou spec porque não há sinal melhor identificado — vale uma se alguém achar um.
