## Problem

The PO plans by dates and dependencies, and Azure Boards' native views are not the interface the team wants to customize. Render a Gantt in the quenching specs service's web interface from the schedule quenching derives (quenching S5: start, target, dependencies, critical path), over the cache kept in sync with Azure DevOps (S11), so a date or dependency changed in the Gantt is written back to Azure Boards through the store adapter. The critical path comes from quenching's schedule, never from the chart library. References: SVAR Gantt and frappe/gantt for rendering, Backlog.md and quenching's `cq specs serve` for the board around it (epic §Reference projects).

Formerly holetz/tempering#4.

Member S9 of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent).

## Proposal

- The specs portal has a Gantt page (`#/gantt`, next to Board and Ranking) that draws one bar per open spec on a date axis, with a today marker, from the schedule `cq specs schedule` already derives.
- The page marks the critical path the schedule reports (`criticalPath`, `critical`), draws one arrow per `dependsOn` edge, shows `slipDays` on a bar that finishes after its `target`, and lists the specs the schedule cannot place (no `start`, no `target`, or blocked by an undated dependency) in a separate "no dates" list instead of inventing a date.
- A dependency cycle shows as the page's alert with the cycle's ids, as the epics page does, and no bars.
- `GET /api/schedule` serves that data through the same snapshot and ETag path as the other reads, so it is a read of the store and nothing else.
- Changing a date or a dependency from the page is not part of this spec: it needs a new POST route, which the portal standard reserves for a human decision (see `## Open Decisions`).

## Out of Scope

- Write-back from the Gantt (dragging a bar, editing `start`/`target`/`dependsOn` in the page, and from there to Azure Boards). The portal standard says "No new POST route enters without a human decision", and the epic's autonomy policy authorizes no such widening. The existing verbs (`cq specs start|target|depends`) already do the write, so the future route is a thin wrapper, parked as a decision rather than built.
- The cache kept in sync with Azure DevOps (S11) and the store adapters (S4, S29): the page reads whatever backend `open_backend` returns today.
- Vendoring SVAR Gantt or frappe/gantt, or any chart library: the portal has no CDN and no build (CSP `script-src 'self'`).
- Computing a critical path in the browser: it comes from the server's schedule only.
- Azure Boards' native Delivery Plans, which stay as they are.

## Design

### Mapa de dependências (2026-10-25)

| File | Relation | What breaks if it changes |
|---|---|---|
| `plugins/quenching/assets/bin/quenching/specs/portal.py` | source of the route; imports `schedule` from `quenching.specs.parse.deps` | the reader copy and Codex/OpenCode mirrors go stale until regenerated |
| `plugins/quenching/assets/bin/quenching/specs/parse/deps.py` | `schedule()` is the only source of dates and the critical path | untouched here; the page must not recompute |
| `plugins/quenching/assets/portal/{index.html,app.js,app.css}` | the page | the same mirrors, and CSP forbids inline script and style |
| `plugins/quenching/tests/test_specs_portal.py` | route and asset contract | none beyond itself |
| `docs/standards/architecture/specs-portal.md` | the review contract of every portal change | the Routes list and Regeneration paragraph must match the code |

Decisions, as durable rules:

- **The server derives, the page draws.** `GET /api/schedule` returns `{ok, fetchedAt, cycle, nodes, criticalPath}` exactly as `schedule()` computes it over the snapshot's `infos`, with each node gaining `stage` (the portal's own derived stage) and `phase` already present. The browser reads `critical` and `criticalPath`; it never orders, dates or ranks anything.
- **Archived specs are left out** of `nodes` by default (`schedule()` already selects open specs with dependencies plus their closure, and an archived-done dependency is kept as an edge target so its finish still drives successors).
- **The read reuses `_snapshot`** under `Portal.lock`, the TTL cache and `_validated` (ETag), like `/api/epics`. It adds no store read of its own.
- **Rendering is hand-written SVG built with `createElementNS` and `textContent`**, in the page's existing helper style: the standard forbids innerHTML, inline script/style and CDN, and the page needs only bars, arrows, a today line and a month axis. Bars are keyboard-focusable links to `#/spec/<id>`, with an accessible label carrying id, title, dates and critical flag; colour is never the only marker (critical bars also carry a text chip and a heavier outline).
- **Placement:** a bar spans `earliestStart..earliestFinish`; when only one end exists the node goes to the "no dates" list. A zero-length span draws as a one-day bar.
- **Contracts that bind:** `docs/standards/architecture/specs-portal.md` (routes, security guarantees, no innerHTML, regeneration), and the epic Design rule that no new grant, hook, script or CI step enters.

## Alternatives Considered

Read from the epic's reference projects (holetz/forge epic 1, `## Design` §Reference projects, 2026-10-24) before developing.

| Reference | License | Decision | Why |
|---|---|---|---|
| `cq specs serve` (`portal.py`, this repository) | MIT | **Reuse** | the page is one more view and one more GET on the existing portal: token, Host/Origin, CAS and snapshot cache are already solved |
| SVAR Gantt | MIT core; critical path is PRO | **Reject** | React component (the portal has no build), and the critical path is the paid tier; the schedule already has it |
| frappe/gantt | MIT | **Adapt the idea, reject the code** | vanilla JS is compatible, but vendoring third-party code into a no-CDN, no-build, CSP-bound page buys little over ~200 lines of SVG for bars and arrows; its bar-and-arrow layout is taken as the visual model |
| Backlog.md | MIT | **Adapt** | the closest shape (local board over one store, with dependencies); it has no Gantt, so only the "board plus another view over the same store" structure is taken |
| ccpm | MIT | **Reject for this spec** | its value is the sync of specs into a tracker, which belongs to the adapter members (S4, S29, S31), not to a view |
| microsoft/azure-devops-mcp | MIT *(to confirm)* | **Reject for this spec** | tool shapes for the Azure adapter; the page does not talk to Azure |

Whole-shape alternatives rejected:

- **Gantt with write-back in the first delivery** (the Problem's full wish): lost because it adds POST routes the standard reserves for a human decision; the read comes first and the write is a one-route follow-up.
- **Compute the schedule in the browser** from `/api/specs`: lost because it would duplicate `schedule()` and could disagree with `cq specs schedule` on the critical path.
- **Render the Gantt inside the epics page only**: lost because the PO plans across specs, not only epic members.

## Open Decisions

- Whether the Gantt writes back (dates and dependencies, through new POST routes wrapping `cq specs start|target|depends`, the same verbs the terminal uses and so the same CAS and refusals). Decided by the human, who must record the decision against the portal standard's "no new POST route without a human decision"; until then the page is read-only. Parked as a discovery for the follow-up spec.
- Whether the page should offer archived specs behind a toggle. Decided by the PO's first use of the page; the default stays open specs only.
- Whether the data stays comparable in latency once the tracker cache (S11) replaces the git read. Decided when S11 lands; the route reads through `_snapshot`, so it follows whatever cache the snapshot gains.

## Risks

- A store whose specs carry no dates renders an almost empty chart. Mitigation: the "no dates" list names them with the reason, so the empty state explains itself.
- Dates exist in frontmatter on the git backend but a tracker backend may not return `start`/`target` in `frontmatter`. Mitigation: the route reads what `schedule()` reads; a test on the memory backend pins the field names, and the Open Decision about S11 covers the tracker case.
- A large store makes the SVG heavy. ACCEPTED — the schedule selects open specs with dependencies and their closure, which is small next to the full store.
- A pure-read page leaves the PO unable to act on a slipped date. ACCEPTED — the write-back is the human's decision above, and the spec page's existing verbs remain.
