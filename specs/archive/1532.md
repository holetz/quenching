## Problem

Achado no autopilot de 2026-10-11 (noite). O passo 5 de `plugins/quenching/commands/specs/autopilot.md` manda
mover para o épico humano uma spec que o orchestrator devolve `blocked` com `needs-human:`. Só que todo membro já
pertence ao épico da rodada, e `cq specs epic` só tem `add`: `cq specs epic add 1527 1518` recusa com
"error: spec 1518 already belongs to epic 1522" (exit não zero), e `cq specs epic --help` lista apenas `{add}`.

Consequência: a instrução do protocolo não pode ser executada. O épico humano 1527 teve de citar a 1518 por
referência no Problem, e `cq specs status --epic 1527` mostra 0/0 membros, então o humano não vê pela ferramenta o
que lhe cabe decidir.

## Proposal

- `cq specs epic add <epic> <spec> --move` moves a spec that already belongs to another epic: the item leaves the old epic's `## Tasks`, is listed in the new one, and `epic:` on the spec is restamped, all in one write batch.
- Without `--move`, a spec that belongs to another epic is still refused with `sp-epic-member-taken`, and the refusal message names `--move` as the remedy.
- `--move` refuses (exit 2, nothing written) when another item of the old epic waits `after` the moved label, so the old epic never holds a dangling dependency.
- After a move, `cq specs status --epic <new>` counts the spec as a member and `validate` raises no `sp-epic-divergent`.

## Out of Scope

- Editing `plugins/quenching/commands/specs/autopilot.md`: the epic 1534 Design keeps it untouched; its step 5 becomes executable through the tool alone.
- A separate `epic remove` verb: a bare removal leaves a spec with no epic and widens the surface; the move is the only need.
- Moving an epic itself or nesting epics: still one level only.

## Design

- **Decision:** a flag on `epic add`, not a new verb. `add` already owns both ends of the link (item plus `epic:` key, one `write_specs` batch); a move is the same write plus removing the old item. No new grant or command surface is introduced.
- **Rule:** the removal slices `lines[lineno:blockEndLineno]` of the old item out of the old epic's text, the same block bounds `insert_item` uses. Group headings of the old epic are left as they are.
- **Rule:** a move writes three documents (old epic, new epic, member) in one `write_specs` batch where the backend has one; elsewhere the new epic is written first, so a half-failed move leaves the divergence `validate` names, and re-running the same command repairs it.
- **Rule:** the old epic is read through `load_epic`; if it is unreadable or has no item for the spec, only the restamp and the new item are written (repair path).
- Binding contract: `docs/standards/workflows/epics.md` — one level only, a spec belongs to one epic.

## Alternatives Considered

- A new `cq specs epic move` verb: rejected, duplicates `add`'s two-ended write and adds a verb.
- `epic remove` then `epic add`: rejected, two non-atomic writes leave a spec with no epic between them.
- Changing autopilot to cite by reference only: rejected, the epic 1534 Design keeps autopilot untouched and the human would still see 0/0 members.

## Open Decisions

- none — the dependent-item case is decided: `--move` refuses, and the human resolves the dependency.

## Risks

- A move that drops an item other items wait on would corrupt the old epic's graph. Mitigation: `--move` refuses when any item lists the label in `after`.
- The mirror drifts from source. Mitigation: the repo gate checks lockstep, and the sync script is a task.
