## Problem

Achado reproduzido pela revisão de correção do épico 1522 (2026-10-11). O HUD se declara somente leitura, mas a cada
`turn.complete` faz rede e escreve no `.git`. `plugins/quenching-hud/hooks/register.tsx:21` roda `cq specs status`, e
no backend git esse comando faz fetch de `origin` sempre que o cache passa de 30s (`specs/backends/git.py:41`,
`_tip`/`_fetch`). Reprodução num clone de scratch com `GIT_SSH_COMMAND` falso: `cq specs status --spec 1522 --json`
levou `refs/remotes/origin/quenching` de ausente a `8791f559…`, o ssh falso registrou `git-upload-pack`, e o cache foi
gravado em `$XDG_CACHE_HOME/quenching/git/<hash>.json`. Sem `.claude/quenching.json`, o backend padrão (github)
consultou a API do GitHub.

Consequência: ssh e rede a cada turno (timeout de 120s), escrita de ref no `.git` compartilhado com as worktrees,
e chamadas ao GitHub em qualquer repo com branch `plan/<n>-`. Isso desmente `plugins/quenching-hud/README.md:22`
("nunca escreve em … disco") e `.claude-plugin/marketplace.json:58` ("writes nothing"). Corrigir significa estreitar:
uma leitura sem fetch (o cache ou o ref local), ou ao menos documentar o custo com honestidade. Nunca alargar.

## Proposal

- O README do `quenching-hud` e a descrição do plugin em `.claude-plugin/marketplace.json` deixam de afirmar que o HUD "nunca escreve em disco" / "writes nothing".
- Ambos dizem o que de fato acontece a cada `session.start` e `turn.complete`: `cq specs status` pode fazer fetch de `origin` (no máximo uma vez a cada 30s) gravando `refs/remotes/origin/quenching` no `.git` compartilhado e um cache em `$XDG_CACHE_HOME/quenching/git/`, e, no backend github, consultar a API do GitHub.
- A afirmação "somente leitura" fica restrita ao que é verdade: o plugin não escreve spec nem branch e não registra comando, botão ou hook de ferramenta.

## Out of Scope

- Uma leitura sem fetch em `cq specs status` (flag ou variável de ambiente): exigiria mudar o `cq` e o espelho `quenching-specs-reader`, e `process.run` do HUD não tem garantia de aceitar `env`. Adiado para `## Open Decisions`.
- Mudar a frequência de atualização do HUD ou o TTL de 30s do backend git.
- Qualquer alargamento de grant, hook ou superfície executável: esta spec só estreita a afirmação.

## Design

- Regra durável: o que um plugin declara sobre seus efeitos colaterais é o que o comando que ele executa faz, não o que o plugin escreve diretamente. O HUD delega a `cq specs status`, cujo backend git faz fetch (`_tip`/`_fetch`, TTL `FETCH_TTL_S = 30`) e grava ref e cache.
- Escolha: documentar com honestidade agora (estreita a afirmação, não toca o `cq`), em vez de mudar a transferência de leitura. Alternativa pesada: leitura sem fetch no `cq`, adiada.
- Os fatos vêm do achado reproduzido pela revisão do épico 1522, registrado em `## Problem`; nada novo é afirmado além disso.

## Alternatives Considered

- Leitura sem fetch no `cq` (cache ou ref local): resolveria a causa, mas toca o `cq` e o espelho `quenching-specs-reader` e não cobre o backend github; fica como decisão aberta.
- Remover o HUD das atualizações a cada turno: muda o produto, não só a afirmação.

## Open Decisions

- Vale uma leitura sem fetch para o HUD (flag em `cq specs status` ou ref local)? Decide-se numa spec própria se o custo de rede por turno incomodar; a medida é o tempo de `turn.complete` num clone com `origin` lento.
