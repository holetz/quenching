## Problem

The GitHub Copilot harness (the VS Code Agents window, backed by the Copilot CLI) reads a target's `.claude/settings.json` and `.mcp.json` as its own, but `cq deploy` writes the owned hooks only in the Claude shape — a `bash` command over `$CLAUDE_PROJECT_DIR` — so on Windows the Copilot harness cannot run them, and a failed `preToolUse` command denies the tool call, leaving the agent unable to act. Sessions opened with Copilot's "New Worktree" isolation also cut a worktree of their own — from the current HEAD, without the gitignored files a target needs and without its `worktreeSetup` — that collides with the worktree `cq git worktree add` cuts for the same task, so the agent ends up working in two isolations at once.

## Proposal

- Every hook `cq deploy` installs in `.claude/settings.json` runs under both the Claude Code and the GitHub Copilot harness, on Linux, macOS and Windows: its command is one polyglot line that bash, PowerShell and cmd parse the same way, launching a Python body.
- `deny-claude-coauthor` and `warn-git-add-all` are Python bodies (`assets/hooks/<name>.py`) with today's behaviour, opt-out and fail-open, reading either harness's input shape.
- A missing body is still a no-op, now checked inside Python instead of by `test -f`.
- The matcher of both hooks also names the PowerShell tool, so a Windows session's shell calls are guarded too.
- The manual and `docs/standards/automation/hooks.md` say what the Copilot harness reads from a deployed target (`.claude/settings.json` hooks, `.mcp.json`) and that a Copilot session opens with **Branch** isolation, leaving the worktree to `cq git worktree add`.
## Out of Scope

- A separate `.github/hooks/quenching.json` in Copilot's own format: the Copilot harness already reads `.claude/settings.json`, and a second file would run each hook twice there (decision of 2026-11-20).
- A target declaring its own hooks through the deploy: a target rewrites its own hand-written hooks in the same polyglot shape; the deploy keeps owning only its own entries.
- A target's own MCP servers and machine bootstrap (editor install, extension list): they live in the target that consumes this release.
- The probe on a Windows Copilot session: parked as an `## Open Decisions` line, run after the merge by someone with that machine.

## Design

**One command, every shell.** The command is `<python prefix> -I -c "<code>"`, where `<code>` contains no `$`, no backtick and no double quote: bash, PowerShell 5/7 and cmd all hand it to Python as one argument unchanged. The code resolves the root from `CLAUDE_PROJECT_DIR` (exported by both Claude Code and the Copilot runtime, which also exports `COPILOT_PROJECT_DIR`), falling back to the working directory, prints `{}` and exits 0 when the body is missing, and otherwise runs it with `runpy`. The path inside the code is written with forward slashes, which Windows accepts, so the marker `.agents/quenching/assets/hooks/<name>.py` stays a literal substring the merge can find.

**The Python prefix.** It is `shared.mcp.command` when the repository declares it (the prefix that already starts the MCP server, e.g. `uv run --no-project python`), else `python3`. A Windows target without a declared prefix may lack `python3`; the manual says to declare it.

**Merge compatibility.** An own entry is still found by the marker path; the regex accepts `.sh` and `.py`, so a target's existing `.sh` entry is rewritten in place on the next deploy, under the same event and name. The matcher becomes part of the replacement, so widening it moves the entry rather than duplicating it.

**Input shapes.** A body reads the command from `tool_input.command` (Claude Code, and Copilot's `PreToolUse` alias) or from `toolArgs` (an object or a JSON string, Copilot's native `preToolUse`), and keeps today's output shape (`hookSpecificOutput.permissionDecision`), which both runtimes accept.

**Cost.** Each matched shell call pays one Python start (plus the prefix's own start) instead of `bash` + `grep`; the fast path reads stdin and runs one regex before any JSON parse.

### Assumptions

- Copilot's `_vsCodeCompat` reading honours the regex `matcher` and maps its shell tools onto `Bash`/`PowerShell` — Proposal (matcher bullet); unproven on Windows, see `## Open Decisions`.
- PowerShell passes a double-quoted argument with inner single quotes to a native program unchanged — Design (one command).

## Alternatives Considered

- **`.github/hooks/quenching.json` with `bash` and `powershell` variants** — Copilot's native format, but the harness also reads `.claude/settings.json`, so each hook would run twice, and the Claude-shape command would still fail on Windows. Rejected.
- **Both files** — fixes Windows but keeps the double run and two files to keep in step. Rejected.
- **`bash`/`powershell` keys inside the Claude-shape entry** — Copilot prefers them, but Claude Code's settings schema is not known to accept extra keys on a hook. Rejected as a risk to the primary harness.

## Open Decisions

- Probe on Windows with a Copilot session after the merge: which shell runs the command, whether `CLAUDE_PROJECT_DIR` arrives, the tool names the matcher sees and the input field names; decided by running the probe script the manual lists, recorded as a `## Discoveries` line or a follow-up spec.

## Risks

- A target with neither `shared.mcp.command` nor `python3` on PATH gets a hook that cannot start; Claude Code treats a non-2 exit as non-blocking, but Copilot denies the call. Mitigation: the manual's note and `cq deploy` printing the prefix it used.
- Copilot may not map `Bash` onto its own shell tool names; then the guard silently does not fire there (fail open, never a block).
- One Python start per shell call is slower than `bash` + `grep` on the fast path; bounded by the 5-second timeout and measured in the test.
