## Problem

Os comandos git do `cq` têm timeout fixo de 60 s (`COMMAND_TIMEOUT_S` em `quenching/assets/bin/quenching/common/git.py:9` e `TIMEOUT_S` em `git/preflight.py:36`), sem nenhuma configuração; numa máquina Windows atrás de VPN, onde um `git fetch` leva 35 s ou mais, o `cq git worktree retire` recusou por esse timeout. Usuários em redes lentas precisam de um limite ajustável (por exemplo `QUENCHING_GIT_TIMEOUT_S`) e de uma mensagem de timeout que diga como ajustá-lo.

## Proposal

- Os comandos git que o `cq` dispara por `quenching.common.git` (`_git`, `_git_run`, e as leituras de `git/base.py` e `git/audit.py`) e por `cq git preflight` passam a usar um limite lido de `QUENCHING_GIT_TIMEOUT_S` (segundos, inteiro positivo); ausente ou inválido, continua 60 s.
- Um git que estoura o limite em `_git_run` volta com código 124 e uma mensagem que diz o limite em vigor e como ajustá-lo (`set QUENCHING_GIT_TIMEOUT_S=<segundos>`), e essa mensagem chega à recusa de `cq git worktree retire`/`acquire`/`add` (`git-worktree-fetch-failed`).
- `cq git preflight` diz o mesmo quando um probe estoura o tempo.
- O padrão `docs/standards/workflows/plugin-configuration.md` registra a variável onde hoje diz que os timeouts de git ficam só no código.

## Out of Scope

- Uma chave de configuração (`shared.gitTimeoutSeconds`) — o padrão de configuração diz que os timeouts de git ficam no código; a variável de ambiente é por processo e basta para a máquina lenta. Uma chave exige decidir camada (user/local) e entra no seed, o que é uma decisão de contrato à parte.
- O timeout próprio do store de specs (`specs/backends/git.py`, `GIT_TIMEOUT_S = 120`) e as chamadas a `gh`/`az` (`git/pull.py`, `specs/backends/github.py`, `azure.py`, `delegate.py`) — têm limites próprios e não foram a causa relatada.
- `knowledge/schema.py`/`knowledge/stale.py` e `common/doctor.py` — só leem o repositório local; continuam com o default de 60 s.

## Design

- **O limite é lido a cada chamada, não no import.** `git_timeout_s()` em `common/git.py` lê `os.environ["QUENCHING_GIT_TIMEOUT_S"]`; aceita um inteiro (ou float) > 0, e qualquer outro valor cai em `COMMAND_TIMEOUT_S` (60), que continua exportado porque `knowledge/schema.py`, `common/doctor.py` e os backends o importam como default. Ler a cada chamada deixa os testes ajustarem o ambiente sem recarregar módulos.
- **A mensagem de timeout é construída em um lugar só.** `timeout_message(argv, seconds)` em `common/git.py` produz `git <verbo> timed out after <n>s; set QUENCHING_GIT_TIMEOUT_S=<seconds> to raise the limit`; `_git_run` captura `subprocess.TimeoutExpired` antes do `SubprocessError` genérico e devolve `(124, "", <mensagem>)` — 124 é o código que `preflight._push_reason` já lê como `unreachable`. As recusas que citam o stderr (`git-worktree-fetch-failed`) passam a carregar a dica sem mudar o código da recusa.
- **`_git` continua lendo ausência como fato** — só passa a usar o limite configurável; sua semântica de `""` não muda.
- **O preflight usa o mesmo limite.** `TIMEOUT_S` sai; `_tool` chama `git_timeout_s()` e, no timeout, devolve `(124, "", timeout_message(...))` no lugar de `"timed out"` — a palavra `timed out` continua na mensagem, então `_UNREACHABLE` segue casando.
- **Contrato que não pode ser contrariado:** `docs/standards/workflows/plugin-configuration.md` §Settings read outside the file diz que os timeouts de git não são chaves. A variável não é chave do arquivo de configuração; o padrão é atualizado para dizer que o default fica no código e a variável o sobrescreve por processo.

## Alternatives Considered

- **Chave `shared.gitTimeoutSeconds` no arquivo de configuração** — perdeu: contraria o padrão atual (timeouts de git ficam no código), exige escolher camada e mexer no seed e no `config show --effective`; a variável resolve a máquina lenta sem contrato novo.
- **Subir o default para 120 s ou mais** — perdeu: não há limite certo para toda rede, e um git travado num CI leva o dobro para falhar; não dá ao usuário como ajustar.
- **Flag `--timeout` em cada verbo git** — perdeu: são dezenas de verbos e os chamadores (skills, MCP) teriam de repassá-la; o problema é da máquina, não da chamada.

## Open Decisions

- none — o nome da variável vem do `## Problem`, e o formato (segundos, positivo, fallback 60) segue as outras leituras de limite do `cq`; nada depende de um humano.

## Risks

- Um valor alto demais deixa um git travado segurar o `cq` por mais tempo — ACCEPTED: é a escolha explícita de quem define a variável, e o default não muda.
- Um valor inválido ignorado em silêncio esconde um erro de digitação — mitigação: o fallback é o default seguro (60), e a mensagem de timeout imprime o limite em vigor, então o usuário vê que o valor não pegou.
- Conflito com a spec 625 (MCP) — mitigação: nenhum arquivo desta spec está em `mcp/*` ou `deploy/translate.py`; o README de prova gerado é regenerado se divergir no merge.
