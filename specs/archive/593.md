## Problem

Medido em 2026-11-26 pelo condutor: `specs_promote(spec=541, outcome=done)` recusou com sp-open-tasks porque a task S2 (membro 528, abandonado como superseded) está `dropped` e conta como aberta; `force:true` no MCP é ignorado (o verbo não expõe a flag) e só `cq specs promote 541 --outcome done --force` fechou. Consequência: todo épico do autopilot com um membro abandonado (passo 2 abandona com evidência) cai para a CLI ou fica aberto para sempre — 245, 300, 306, 326, 335, 358 estão abertos. Proposta: uma task `dropped` com membro arquivado como abandoned não conta como aberta para o outcome done do composto; ou o MCP expõe force.

## Proposal

- Um item de composto cujo membro está arquivado com `outcome: abandoned` deixa de contar como aberto para o `done` do composto (`open_items`), de modo que `specs_promote(outcome=done)` e `cq specs promote --outcome done` fecham um épico com membro abandonado sem `--force`.
- Um membro arquivado sem `done` e sem `abandoned` (outcome ausente ou desconhecido) continua aberto: só a abdicação explícita é aceita.
- O MCP não ganha `force`.

## Out of Scope

- Expor `force` no schema de `specs_promote`: o `force` ausente é intencional (specs/mcp.py:487) e a decisão do épico 594 (## Design, 2026-11-26) manda corrigir a regra do store.
- `dry_run` no MCP: é a spec 597.
- Fechar os épicos 245, 300, 306, 326, 335 e 358: é operação do condutor depois do merge, não código.

## Impact

### Standards this spec will write into docs/standards/

- none — a regra é de implementação; nenhum padrão novo.

### Product code this spec expects to touch

- `quenching/assets/bin/quenching/specs/parse/epics.py` — `open_items` deixa de contar item `dropped` com membro `abandoned`
- `quenching/tests/test_specs_epics.py` — teste da regra

## Validation

- `python3 -m unittest discover -s quenching/tests -p test_specs_epics.py` passa, incluindo o teste novo: épico com membros done e um abandonado arquiva `done` em dry-run sem `--force`.
- O mesmo teste falha na base sem a correção (`sp-open-tasks`).
- `python3 -m unittest discover -s quenching/tests -p test_specs_epic_members.py` continua verde (membro aberto ainda recusa).

## Design

- Decisão: a regra mora em `open_items` (única consumidora: `promote.py`), filtrando `status == "dropped"` com `member.frontmatter.outcome == "abandoned"`. `member_state` e `derive_epic` ficam intactos, pois o portal e `next` dependem de `dropped` (um abandonado continua sem destravar dependentes). Evidência: `parse/epics.py:128`, `test_an_abandoned_member_never_unblocks_its_dependents`.
- Decisão do épico 594: preferir a regra do store a expor `force` no MCP.
- Contrato: um item dependente (`after:`) de um abandonado segue `waiting` e portanto aberto; a regra só desonera o item abandonado em si.

## Alternatives Considered

- Expor `force` no MCP: rejeitada pelo épico 594; abre um bypass geral do gate de tasks abertas.
- Mudar `member_state` para um estado novo: rejeitada; amplia o raio (portal, next, status) sem ganho.

## Open Decisions

- none — a decisão de forma foi tomada pelo épico 594.

## Risks

- Um abandono erroneamente carimbado deixaria um épico fechar como done sem o trabalho; mitigado porque o abandono é um ato explícito registrado com evidência e `outcome: done` do épico continua exigindo `## Outcome` e merge. ACCEPTED — é o contrato do autopilot.

## Outcome

Membro arquivado sem `done` nem `abandoned` continua aberto, e um dependente de abandonado segue `waiting`. Dois testes novos em test_specs_epics.py (RED na base: sp-open-tasks). Fora: `dry_run` no MCP (spec 597) e o fechamento dos épicos 245, 300, 306, 326, 335, 358, que é operação do condutor. Revisado, nada a destilar.
