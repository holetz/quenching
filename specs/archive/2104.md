## Problem

A 2048 estreitou o `codex-git-guard` (`plugins/quenching/assets/bin/quenching/codex/guard.py:83-90`) ao próprio worktree. Os workers paralelos continuam funcionando, mas um run do Codex com `--dangerously-bypass-approvals-and-sandbox` pode rodar `git -C <base> reset|checkout`, `git branch -f main <sha>` ou `git update-ref` sem ser detectado. Esse ponto cego foi achado na revisão da rodada 5, em 2026-10-25.

**Decisão do humano (2026-10-25): vigiar só retrocessos.** A guarda volta a ler, antes e depois do run, o HEAD do checkout base (o worktree principal de `git worktree list`) e a ref da branch primária (`refs/heads/<primary>`). Ela aceita o avanço fast-forward, em que o valor novo descende do antigo, como um `git pull` ou um merge do condutor. Ela barra:

- um retrocesso ou reescrita: o valor novo não descende do antigo;
- uma troca de branch do HEAD base, que muda o symbolic-ref;
- um HEAD destacado no base;
- a remoção da ref.

O HEAD e as refs dos outros worktrees continuam fora, como a 2048 decidiu.

Done when: testes provam os cinco casos (fast-forward aceito; reset para trás, `branch -f` para um não-descendente, troca de branch e remoção barrados); `docs/standards/architecture/codex-pillar.md` §The git guard e as docstrings de `guard.py`, `implement.py` e `review.py` descrevem a regra; os espelhos são regenerados e o gate passa. Nenhum grant, hook ou CI muda.

## Proposal

- A guarda lê, antes e depois de cada run do Codex (revisão e executor), o HEAD do checkout base (o worktree principal de `git worktree list`) e a ref da branch primária.
- Um avanço fast-forward do HEAD base ou da ref primária (o valor novo descende do antigo) é aceito.
- Um retrocesso ou reescrita (`reset`, `branch -f` para um não-descendente, `update-ref`), uma troca de branch do HEAD base, um HEAD base destacado e a remoção da ref primária saem como `moved` e viram exit 2 `codex-git-guard`.
- O HEAD e as refs dos outros worktrees continuam fora da guarda.
- Testes provam fast-forward aceito e os quatro casos barrados.
- `docs/standards/architecture/codex-pillar.md` §The git guard e as docstrings de `guard.py`, `implement.py` e `review.py` descrevem a regra.

## Out of Scope

- Grants, hooks e CI: nenhum muda; a decisão do humano limita a mudança ao código da guarda.
- Vigiar o HEAD e as refs de outros worktrees: a 2048 os tirou da guarda de propósito, porque um worker paralelo os move legitimamente.
- Vigiar avanços (commits novos no base): o humano decidiu vigiar só retrocessos.
- Reverter ou limpar o base após uma violação: a guarda só detecta; quem limpa é o humano.

## Design

- **Regra durável:** a guarda vigia dois valores compartilhados, e só contra retrocesso: o HEAD do checkout base e a ref primária. "Retrocesso" é o valor novo não descender do antigo (`git merge-base --is-ancestor`); igual ou descendente é aceito.
- **Checkout base:** a primeira entrada de `git worktree list --porcelain`.
- **Ref primária:** o alvo de `origin/HEAD`; senão a branch do HEAD base; senão `main` ou `master` que exista. É fixada antes do run e reusada depois.
- **Falha fechada:** qualquer falha do git é `GuardError`; antes do run recusa (exit 2), depois do run vira divergência. Um HEAD destacado é estado, não falha, mas é barrado como violação quando era uma branch antes.
- **Contratos:** `docs/standards/architecture/codex-pillar.md` §The git guard; a 2048 manteve fora o HEAD e as refs de outros worktrees.
- **Alternativa por decisão:** comparar igualdade estrita do HEAD base barraria o `git pull` e o merge do condutor, que são legítimos; por isso o teste de ancestralidade.

## Alternatives Considered

- Igualdade estrita do HEAD base e da ref primária: rejeitada, barra fast-forward legítimo.
- Voltar a vigiar todos os worktrees e refs: rejeitada, a 2048 a estreitou porque workers paralelos movem essas refs.
- Confiar só no prompt que proíbe git: rejeitada, o bypass não tem sandbox; a prova tem de ser por código.

## Risks

- Uma ref primária mal resolvida deixaria o ponto cego: mitigada pela ordem origin/HEAD, branch do base, main/master, e por falha fechada nos erros do git.
- ACCEPTED — um avanço fast-forward malicioso do base passa; o humano decidiu vigiar só retrocessos.
- A guarda adiciona alguns processos git por run: custo desprezível diante de um run do Codex.
