## Problem

The Azure Boards backend stores a whole spec in one work item and maps `start`/`target` to `Microsoft.VSTS.Scheduling.StartDate`/`TargetDate` (`plugins/quenching/assets/bin/quenching/specs/backends/azure.py`), but a spec's dependencies (`after:`, and the cross-spec dependencies of 2039) never become work item links, so Boards' own timeline cannot match the Gantt the quenching specs service draws from the same schedule (`holetz/quenching#2088`). Write each dependency as a `System.LinkTypes.Dependency` predecessor link on write, remove the links a dependency no longer names, and read them back round-trip, so both views read one set of dependencies.

Member S29 of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent).

## Proposal

- A spec's `dependsOn` ids (the `after:` of the schedule, 2039) are written to its Azure Boards work item as `System.LinkTypes.Dependency-Reverse` links (the predecessor side), one per dependency that is a work item id of the same organisation.
- A write that changes `dependsOn` removes the predecessor links the spec no longer names, in the same patch that adds the new ones; a write that leaves `dependsOn` unchanged sends no link op and makes no extra request.
- A new spec born with `dependsOn` carries its links in the creation patch.
- The links read back: `AzureBoardsBackend.predecessor_links(spec_id)` returns the predecessor ids Boards holds, equal to the spec's `dependsOn` after a write.
- `docs/standards/architecture/spec-backend.md` states the mapping beside the `ArtifactLink` bullet.

## Out of Scope

- The epic `## Tasks` item-level `after: S1,S3` labels: they name items of an epic, not work item ids, so they have no link target until the epic's members are resolved to ids; the schedule already derives member edges into `dependsOn`. Parked as a discovery.
- Successor links (`Dependency-Forward`) written on the other item: Boards shows them as the inverse of the predecessor link, so one side is the whole fact.
- Reading links on a listing (`$expand=relations` on every load): `workitemsbatch` does not combine `fields` with `$expand`, and the document already carries `dependsOn`; links are read only when a write needs their indexes, and by `predecessor_links`.
- The Gantt (2088), sync by service hooks (2089), the `migrate` verb (2084) and every other adapter.
- Any change to the git, github or memory backends, grants, hooks or CI.
- Drift repair on an unchanged write: a human who removed a link in Boards sees it restored by the next write that changes `dependsOn`, not by any write.

## Design

**Link type.** The predecessor of item B is A: B carries `{"rel": "System.LinkTypes.Dependency-Reverse", "url": <A's _apis/wit/workItems/ url>}`. `dependsOn` is exactly "the specs this one waits for", so it is the predecessor side on this spec's own item.

**Wanted set.** `deps_of(frontmatter)` (the shared normaliser), keeping only all-digit ids (a work item id of this store), dropping the spec's own id. Computed from the text this write puts in place (`fresh`), not from the old `info`.

**Diff is by id, never by position.** `azure_predecessor_ops(relations, wanted, url_of)` indexes the item's existing `Dependency-Reverse` relations by the id at the tail of their `url`, emits `remove /relations/<index>` for the ones not wanted (highest index first, so earlier indexes stay valid) and `add /relations/-` for the wanted ones not linked. Other relations (parent, `ArtifactLink`) are never touched.

**When the links are read.** A write compares `dependsOn` of the pre-write `info` with the fresh one, the same internal diff `_link_new_artifacts` uses. Equal: nothing. Different: one `az boards work-item show --expand relations` for the indexes, and the link ops ride in the document's own patch, so the compare-and-swap `rev` test guards both and the patch stays all-or-nothing. A creation has no relations to read and adds its links to the creation patch.

**Read back.** `predecessor_links(spec_id)` is one `work-item show --expand relations` and returns the sorted predecessor ids.

**Binding contracts.** `docs/standards/architecture/spec-backend.md` (five primitives, one refusal boundary); the backend never raises past `BackendRefusal`; `_az_patch` stays the only door for a write. The backend is exercised through doubles only; the quenching organisation is never written by a test or a worker.

## Alternatives Considered

Reference projects read from epic holetz/forge#1 §Reference projects (2026-10-24):

- **microsoft/azure-devops-mcp (MIT, to confirm): adapted.** Its work item tools are the shape the Azure adapter should mirror, and it links work items by relation type (predecessor/successor). Adapted: the same relation vocabulary, written through this backend's existing JSON-patch door (`az rest`), not through its MCP. Not vendored; the licence is unconfirmed.
- **automazeio/ccpm (MIT): adapted, in part.** It maps PRD → epic → tracker issues with dependency mapping; the idea of writing dependencies into the tracker is the same. Rejected: its GitHub-only sync and its dependency model (issue bodies), which do not give Boards a native link.
- **MrLesk/Backlog.md (MIT): rejected for this member.** Dependencies live in its own store with no external sync, so there is nothing to reuse for a tracker link.
- **`cq specs serve` portal (MIT): not reused.** The management view reads the schedule, not Boards links; it belongs to 2088.
- **SVAR Gantt, frappe/gantt: not applicable.** Rendering is 2088's.

Whole-shape alternatives of this spec:

- **Write both predecessor and successor links.** Rejected: Boards shows the inverse of one link on the other item, and writing both doubles the patch ops and the drift surface.
- **Read relations on every listing.** Rejected: the batch endpoint does not combine `fields` with `$expand`, so it would cost a request per item or lose the field projection, to answer a question the document already answers.
- **Delete and re-add every link on each write.** Rejected: it bumps revisions on unchanged writes; the diff by id removes only what changed.
- **Map the epic item `after:` labels too.** Deferred, see `## Out of Scope`.

## Open Decisions

- Whether a dependency that is not a numeric id of this organisation (another store's id) should be reported instead of skipped silently — decided when 2084 (`migrate --to azure`) states how cross-store ids are renumbered; this spec skips them and says so in the standard.
- Whether the epic item labels get links — decided by the follow-up in `## Discoveries`, after the epic reader exposes the label-to-id map to a backend.

## Risks

- **A live Boards process rejects the relation type or the url form.** Mitigation: the url is the same `_apis/wit/workItems/<id>` form the parent link already proves; the type name is Microsoft's documented `System.LinkTypes.Dependency-Reverse`. ACCEPTED — the real organisation is not touched by this spec's tests, so first live use is the proof; a refusal names the op through `azure_patch_culprit`.
- **A dependency on a work item that does not exist (or another project) makes the whole patch refuse, including the document edit.** Mitigation: the patch is atomic and says which op failed, and `cq specs validate` already flags `sp-dep-missing` before.
- **A link removed by hand in Boards is not restored by a write that leaves `dependsOn` unchanged.** ACCEPTED — reaffirming on every write would read relations on every write.
- **Index-based removes go stale if the item changes between read and patch.** Mitigation: the `rev` compare-and-swap test op in the same patch refuses it.

## Outcome

Shipped: the azure-boards backend now mirrors a spec's numeric `dependsOn` ids as `System.LinkTypes.Dependency-Reverse` (predecessor) relations on its work item. The links are diffed by id (removes first, highest index first, adds appended), ride the document's own patch so the revision test guards both, and are read only when `dependsOn` changed. `create_spec` links every wanted predecessor and `predecessor_links` reads them back. Pure cases and an in-memory round trip against a double of the `az` calls cover it; no real organisation is contacted. The standard `docs/standards/architecture/spec-backend.md` carries the mapping, and the four mirrors and generated manifests were regenerated.

Left out: slug or non-numeric dependencies, other relation types (never touched), and any mapping for `github`.
