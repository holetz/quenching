## Problem

Hoje a spec declara `start` e `target`, mas nenhuma data de fim própria; o Gantt do board desenha as barras só com o `earliestStart`/`earliestFinish` que o `cq specs schedule` deriva. O pedido é adicionar uma data de fim à spec e fazer o Gantt do board usá-la como informação para desenhar o gráfico.

## Proposal

- A spec declares an end date, the frontmatter key `end` (`YYYY-MM-DD`), beside `start` and `target`, read and written by `cq specs end <id> [value]` with the same real-calendar validation (`sp-bad-end`).
- `cq specs schedule` uses `end` as the spec's own finish: a node with `end` finishes on `end` (never earlier than its derived `earliestStart`), an archived `done` dependency finishes on `end` before `target`, and every node carries `end` in the payload.
- The Gantt of the board draws each bar up to that finish and shows the declared end in the bar label and in the table view, so the chart reflects the end the spec declares instead of only the derived one.
- The standards and references that describe `start`/`target` describe `end` too.

## Out of Scope

- Native counterparts of `end` in the deprecated GitHub/Azure backends (`FIELD_KEYS`, `Microsoft.VSTS.Scheduling.FinishDate`): the git store is the live backend, and a tracker round-trip is a separate decision. On those backends `end` simply stays in the document's frontmatter.
- Stamping `end` automatically at conclude: the field is declared by a person or an agent; deriving it from merge time is a different change.
- Any change to how `earliestStart` is derived.

## Impact

### Standards this spec will write into docs/standards/

- `docs/standards/workflows/spec-dependencies.md` — the derivation uses `end` as the declared finish

### Standards at `authority: background` this spec may resolve

- none — no background standard governs the schedule fields.

### Product code this spec expects to touch

- `quenching/assets/bin/quenching/specs/parse/deps.py` — `schedule()` reads `end`
- `quenching/assets/bin/quenching/specs/commands/cli.py`, `fields.py`, `deps.py` — the `end` verb and the human line
- `quenching/assets/bin/quenching/specs/schema.py` — `end` among the optional frontmatter keys
- `quenching/assets/portal/app.js` — the Gantt label and table
- `quenching/references/specs-develop/specs-surface.md`, `spec-driven.md` — the verb and the STATE keys
- the regenerated deployed surface under `.agents/`

## Validation

- `python3 -m unittest discover -s quenching/tests -p test_specs_deps.py` and `-p test_specs_deps_commands.py` pass, including the new `end` cases.
- `cq specs end <id> 2026-12-01` prints and stores the date; `cq specs end <id> 2026-02-30` exits 2 with `sp-bad-end` and writes nothing.
- `cq specs schedule --all --json` shows `end` on every node and `earliestFinish == end` for a node that declares one.
- `bash scripts/verify_repo.sh` is green apart from the base red named by spec 2208.

## Design

- **Name: `end`.** Coherent with `start`/`target` (one short lowercase noun; `specs/parse/deps.py:161` reads both through `_date`). `target` stays the plan; `end` is the finish the spec declares, so slip is `end` against `target`.
- **Rule: a declared fact beats a derived one, a derived one beats nothing.** In `schedule()`: `finish = max(end, earliest)` when `end` and `earliest` are both known, `end` alone when `earliest` is unknown, the old derivation otherwise. `blocked` still yields unknown, since an open undated dependency makes `earliestStart` unknown and no date is invented. An invalid `end` reads as absent, like an invalid `start`.
- **Archived `done`**: `finish = end or target`, and `finishes[spec]` the same, so dependents start after the real end.
- **Storage**: a plain frontmatter key written through `cmd_field` (the `start`/`target` branch), listed in `schema.frontmatter.optional`. It is not added to `FIELD_KEYS`: that tuple is the keys with a native tracker counterpart, and none is wired for `end`.
- **Gantt**: `app.js` already places `earliestStart`→`earliestFinish`, so the bar follows `end` through the payload; the label and the table add the declared end so the reader sees what drove the bar.

## Alternatives Considered

- Computing the Gantt bar in the page from `end`: rejected, the page "computes no date" (`design-system/components/GanttChart/README.md`); the derivation stays in `cq specs schedule`.
- A `duration` field instead of `end`: rejected, the request asks for a date and `start`/`target` are dates.

## Open Decisions

- The native tracker mapping of `end` (`FinishDate`) is decided if a tracker backend is revived; today it is out of scope.

## Risks

- A recorded `end` earlier than the derived start is clamped to the start (`max`), so a stale `end` never draws a negative bar; ACCEPTED — the schedule is a projection, not a validator.
- A frontmatter key unknown to a stricter reader: mitigated by listing `end` in the schema's optional keys, covered by the test that sets it.
