## Problem

O fluxo atual exige agrupar os commits por seção da spec, criando uma regra de organização que não é necessária para concluir o trabalho. Essa exigência e qualquer menção a essa lógica devem ser removidas do fluxo.

## Proposal

- The execution contract will retain one verified, independently anchored commit per task and will no longer reset, recommit, or rewrite task anchors at a section boundary.
- A section boundary will remain only an execution and handoff point; it will not change the commit history or combine task commits.
- The source command, execution reference, git references, standards, generated Codex mirror, tests, and published knowledge projections will describe the same per-task history.
- The optional squash merge offered by the git merge flow will remain a distinct merge-time choice; this spec changes the execution loop's section behavior, not merge strategy semantics.
- Historical provider-owned specs and their recorded task anchors will remain unchanged.

## Out of Scope

- Changing the task ordering model, task sections, verification policies, delegation rules, parallel markers, Handoff refresh events, or section-boundary stop offers. These remain useful coordination boundaries even when commits are not grouped.
- Removing or changing the optional squash strategy at merge time. That is a separate operation owned by the git merge flow and must keep its own branch-retention caveat.
- Rewriting completed task records from older specs that already point several tasks at one section commit. Those records describe history that existed and must not be backfilled.
- Changing the commit subject grammar beyond restoring the task identifier as the default anchor for future task commits.
- Applying this change to a target or external worktree during definition. Execution will implement only the files named by the tasks on the work branch.

## Impact

- docs/standards/workflows/task-execution.md — the execution contract must describe per-task commits without a section squash.
- docs/standards/workflows/plan-git-record.md — task anchors and default commit subjects must no longer depend on section-level rewriting.

### Product code this spec expects to touch

- plugins/quenching/assets/references/specs-execute/execution.md — make the per-task commit chain authoritative and remove the section-squash reference section and proof narrative.
- plugins/quenching/assets/references/git/commit.md — restore the task subject as the default future anchor.

## Design

The execution loop keeps the existing verified chain: run the task gate when the declared verification policy requires it, tick the task with its future commit anchor, stage only the declared files and spec record, commit the task, and assert the subject or sha that was recorded. The section-close branch is deleted. No section base sha is captured or derived, no ancestry guard is run for a section reset, and no task records are re-stamped after a section closes.

A section boundary remains a clean point at which execution may offer to pause and refresh the relevant Handoff state. It is not a history operation. Task sections continue to organize dependency order, delegation context, and parallel eligibility; those concerns do not imply commit grouping.

The source command and references are authoritative. The Codex surface is regenerated from them and checked for parity. The merge flow retains its optional squash merge, because that combines a finished branch into its base at a different lifecycle moment and is recorded by the merge contract; it must not be confused with an execution-time section reset.

Existing task anchors are read forever. New tasks use the normal per-task subject or sha supported by the current backend. No archived provider document is rewritten to make an old section anchor look like a task anchor.

## Alternatives Considered

- Keep section squashing and only revise its prose. Rejected because the requested outcome is behavioral: the executor would continue rewriting history and grouping task anchors.
- Remove all task sections and Handoff boundaries as well. Rejected because sections still provide dependency order, delegation context, parallel eligibility, and resumable stopping points without requiring a history rewrite.
- Replace section squashing with one commit for the whole spec. Rejected because it loses task-level retry, review, and anchor granularity while solving no stated problem.
- Move the grouping to the merge command. Rejected as a default; merge-time squash is already an explicit strategy with different ownership and lifecycle semantics, and it must remain optional.
- Migrate old task records to new task subjects. Rejected because archived records are historical facts and rewriting them would falsify the commit they originally described.

- If branch review discovers historical records that cannot resolve after the behavior change, decide whether that is a separate migration spec. Resolve it at conclude from the measured branch evidence; do not expand this spec or rewrite archived records during execution.

## Risks

- Per-task commits may make a branch longer than the former section-level history. Accept this as the requested trade; preserve the existing verify, self-review, task anchor, and no-amend rules so every commit remains independently reviewable and resumable.
- A generated Codex surface or a secondary reference may retain the old section-squash rule. Mitigate with source-driven translation, translation check, citation check, and the active-surface absence sweep.
- Merge-time squash wording may be removed accidentally while deleting execution-time squash wording. Mitigate by keeping the merge references in scope and asserting that the optional merge strategy and its branch-retention caveat remain.
- Existing records may be mistaken for stale implementation. Mitigate by treating provider-owned historical specs as immutable and by testing both legacy subject anchors and current sha anchors where the backend supports them.
- A no-match grep could hide a wording variant. Mitigate with the focused regression test and the full component, unit, citation, and functional gates; the test must inspect behaviorally significant operations, not only one phrase.
