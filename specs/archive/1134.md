## Problem

The repository still presents Quenching as a broadly adoptable Claude Code plugin and makes documentation and installation claims that conflict with the current implementation, including the retired knowledge hook and host-specific Codex instructions. It also lacks one small, disposable experiment that lets a learner reproduce the intended workflow and inspect its limits without treating the project as production-ready. The current project direction is to make the repository an honest, reproducible workflow study with a bounded first experiment.

## Proposal

- Reframe the public landing pages and onboarding material as an experimental study of AI-assisted repository workflows. State clearly that the material is educational and reproducible, not production validation or a security guarantee.
- Remove the retired `cq knowledge hook` claim and other stale host, namespace, command-count, path, and installation claims from the authoritative source material. Regenerate the Codex projection from source; do not hand-edit generated files.
- Clarify that a command's declared read-only behavior describes its intended command surface and grants, not containment against arbitrary shell or Python execution.
- Add a compact first workflow-study tutorial backed by a disposable fixture. It must show exact setup, status/check/write/check steps, expected changes, verification output, and reset instructions, with host-specific Codex guidance grounded in the official skills-loading model.
- Add a deterministic runner and focused regression checks so the study can be reproduced and the key factual claims cannot silently drift again.

## Out of Scope

- Changing CLI behavior, permissions, or the retired hook contract; the hook must remain retired.
- Cleaning the existing component frontmatter warnings, changing the inconclusive functional-checks exit contract, running the broad command-evaluation backlog, or hardening the project for production use.
- Reworking the full backlog or building a multi-front experiment suite; this spec delivers one representative disposable experiment.
- Adding a release entry or version bump. An existing incorrect changelog link may be corrected as documentation maintenance, but no release is cut by this spec.
- Deploying a documentation site, adding external integrations, or claiming that an assistant session has been measured when only deterministic CLI behavior was exercised.

## Design

### Source and projection ownership

The Claude-facing plugin material remains the editable source. `scripts/sync_codex_plugin.py` regenerates `plugins/quenching-codex/`; generated README and knowledge files are committed snapshots and are never edited independently. The source/projection check and validator are run immediately after the source task.

The public wording uses one consistent study framing across the root README, plugin README, onboarding pages, and vision page. Retired-contract mentions are removed at their actual mention sites rather than through a blind replacement. The Codex installation guidance names the repository-local `.agents/skills` loading model and links to the official skills documentation; it does not invent a `codex --plugin-dir` interface.

### Reproducible experiment flow

```text
clean temporary target
        |
        v
status (no write) --> project --check (seeded stale projection, expected non-zero)
                              |
                              v
                       project --write (one generated diff)
                              |
                              v
                 project --check + knowledge validate (green)
                              |
                              v
                    print reset path and remove target
```

The fixture is copied into a temporary directory outside the repository. The runner seeds only the minimum stale state, captures the expected exit codes and generated-file change, and cleans up on success or failure. Its README separates deterministic CLI evidence from the stronger, unmeasured claim that an arbitrary assistant cannot write through an available shell.

### Evidence boundary

The runner proves the checked-in deterministic workflow and its cleanup contract. It does not prove that a model will follow the workflow, that all host integrations behave identically, or that read-only declarations provide security isolation. Those limits are stated beside the experiment and in the tutorial.

## Alternatives Considered

- Rewrite the full backlog and harden every surface for production adoption — rejected because it would turn a bounded workflow study into a different project and would exceed the evidence available.
- Update prose only and omit a fixture — rejected because readers would have no executable path to reproduce the central claim.
- Edit the generated Codex projection directly — rejected because it would create source/projection drift and be overwritten by the next sync.
- Change the CLI to add a replacement hook or stronger sandboxing — rejected because it changes implementation scope and is not required to make the existing study honest.

## Open Decisions

- none — the first experiment is intentionally deterministic and disposable; any real assistant-session comparison remains future work and must not be implied by this pass.

## Risks

- Generated Codex files can drift if source edits bypass the sync script. Mitigation: run the sync check and generated validator in the source task and the final gate.
- Public wording can overcorrect into an unhelpful disclaimer. Mitigation: pair every limitation with exact reproducible commands and expected evidence.
- Temporary-fixture cleanup can mask a failed assertion or leave residue. Mitigation: use a trap, print the target path on failure, and test both success and expected non-zero checkpoints.
- A stale path or retired-contract mention may survive outside the obvious landing pages. Mitigation: focused regression checks plus repository-wide prose review during conclusion.
- The changelog link correction could be mistaken for a release action. Mitigation: keep it as a one-line maintenance fix and add no version or release metadata.
