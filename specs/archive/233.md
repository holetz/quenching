## Problem

O `cq components bridge` (bridge.py, subcomando plan) compara bytes crus do disco com os bytes gerados e, num checkout Windows com `core.autocrlf=true`, reporta como "edited" arquivos que ninguem editou: o disco tem CRLF e o gerado tem LF. E o mesmo falso positivo que a spec 226 corrigiu no `cq deploy` (`eol_canonical` em `quenching/assets/bin/quenching/deploy/tree.py` e comparacao pelo canonico em `deploy/cli.py`), mas o bridge nao foi coberto.

O que a melhoria precisa tornar impossivel: um arquivo limpo (conteudo LF igual ao gerado) aparecer como edited ou ser reescrito so por diferenca de fim de linha.

**Insumos**

- quenching/assets/bin/quenching/components/bridge.py (plan: comparacao de bytes crus)
- quenching/assets/bin/quenching/deploy/tree.py e deploy/cli.py (a correcao da spec 226, a reaproveitar)
- spec 226, conclude de 2026-11-22; fix no repositorio fonte do quenching, chega aos alvos por `cq deploy`

## Proposal

- `cq components bridge` (plan, check and write) compares and hashes line-ending-canonical text: a copy whose bytes differ from the generated ones only by CRLF versus LF is clean, never `update` or `edited`.
- A clean file is never rewritten for an end-of-line difference alone, and the manifest hashes stay the LF hashes a POSIX checkout writes.
- The correction reuses deploy's `eol_canonical` (spec 226) instead of a second copy of the rule.
- A test proves a CRLF copy of an LF-generated tree reports no change, and a real content edit under CRLF still reports `edited`.

## Out of Scope

- `deploy/tree.py` and `deploy/cli.py` stay untouched: epic 288 assigns `tree.py` to specs 287, 252 and 277, and the rule already exists there.
- Normalizing the end-of-line the bridge WRITES (always LF, as generated): `.gitattributes` and `core.autocrlf` stay the repository's.
- Binary data: `eol_canonical` already returns it untouched.

## Design

- **Reuse, lazily.** `deploy/tree.py` imports `bridge` at module level, so `bridge` imports `eol_canonical` from `quenching.deploy.tree` inside the function that needs it, never at module top (a top-level import is circular). Moving the helper to `common/` would edit `tree.py`, which epic 288 reserves.
- **Both sides canonical.** The expected tree (source `.agents/skills` read under autocrlf is CRLF on disk) and the disk copy are both passed through `eol_canonical` before `==` and before `sha256`, so the manifest records the LF hashes, the same ones deploy records (`deploy/cli.py` hashes the canonical bytes).
- **Hash the canonical disk bytes for `edited`.** `sha256(canonical(disk)) != recorded` decides `edited`, so a CRLF copy of a recorded file is never `edited`.
- **Write the expected (canonical) bytes**, so a rewritten file is LF; only a genuine content or mode difference triggers a write.
- Decision (declared autonomy, no Windows-only skip): the tests run on every platform by writing CRLF bytes explicitly with `write_bytes`, so no `skipIf` is needed.

## Alternatives Considered

- Move `eol_canonical` to `quenching/common/`: cleaner layering, but needs an edit to `deploy/tree.py`, owned by other specs of epic 288. Deferred as a follow-up.
- Copy the five-line helper into `bridge.py`: two copies of one rule drift apart; rejected.

## Open Decisions

- none ? the design settles every question; layering cleanup is parked as a discovery.

## Risks

- Circular import if `bridge` imports `deploy.tree` at module top ? mitigated by the in-function import, and the existing bridge and deploy tests exercise both entry points.
- A binary file with CRLF must keep being compared raw ? `eol_canonical` returns it untouched (NUL or non-UTF-8); ACCEPTED: a valid-UTF-8 binary with no NUL is treated as text, as deploy already does.
