## Problem

`cq deploy --check` declares one bit of itself: `0 clean, 1 drift, 2 refusal`. It is also the deployed-surface lockstep the gate runs. `plan()` answers "is this file drift?" with `path.stat().st_mode & 0o777 != _mode_`, where `_mode_` is the two-valued mode the built tree declares — `0o644`, or `0o755` when the source carries any executable bit (`deploy/tree.py::_mode`).

Those are different questions. The declared side is "executable or not"; the disk side is the whole permission word, including the group and other write bits that no git checkout carries. Under `umask 0002` — the default on this machine and on every worktree cut from it — git creates files as `0o664`, so a fresh worktree of a deployed target reports one `mode` change per generated file: 602 entries on `databricks-risco-gold` on 2026-10-30, with every byte identical and `git status` clean.

`--write` closes it by chmod-ing the whole tree to `0o644`, which is why the drift comes back on the next checkout: the check is measuring a bit the checkout was never asked to preserve.

## Proposal

Compare the executable bit, not the permission word:

```python
elif bool(path.stat().st_mode & 0o111) != bool(_mode_ & 0o111):
    changes.append(_change("mode", rel))
```

`deploy/tree.py::_mode` already reduces the source to that same question (any executable bit → `0o755`), and `components/commands/bridge.py` already compares `& 0o111`. A `cq` that lost its executable bit still reports `mode` drift — the fact a target can observe — and group/other write bits stop being drift.

## Out of Scope

- The write path. `--write` keeps chmod-ing each generated file to its declared mode: that is how an install leaves a known surface, and it is idempotent.
- `components bridge --check` and its manifest: they already compare `& 0o111`.
- What deploy generates, how the manifest records hashes, and any target's own files.

- `plugins/quenching/tests/test_deploy.py` — one test that a group-writable surface is clean, one that a non-executable `cq` is still drift.
- The regenerated distribution copies and the redeployed surface of this repository.

## Design

The change is one branch of `plan()`. `_mode_` comes from the built tree and is always `0o644` or `0o755` (`tree.py::_add` defaults to `0o644`; every other call passes `_mode(path)`), so `_mode_ & 0o111` is `0` or `0o111`. The disk side becomes "does any executable bit survive", and the comparison is "is this file executable where the source says it is" — the only part of the mode git tracks and the only part a caller can observe.

`bool` rather than `& 0o111` equality because a checkout under a stricter umask can produce `0o700` for a script: it is executable, and the declared `0o755` is satisfied as far as the surface is concerned.

## Alternatives Considered

- **Keep `0o777` and normalize the disk side before comparing** — the disk side is the one carrying umask bits; normalizing it to `0o644`/`0o755` is the same comparison written twice.
- **Ignore mode entirely** — rejects a real defect: a `cq` without its executable bit breaks every bare `cq` call the deployed surface makes.
- **chmod during `--check`** — a check that writes is not a check, and `--check` runs in CI over a tree nobody agreed to modify.

## Open Decisions

- none — the two-level convention already exists in the code (`_mode`, `bridge.py`), so the shape is settled by precedent.

## Risks

- **A surface installed with a stricter mode (`0o600`) is now clean.** Accepted: deploy owns content and the executable bit; confidentiality of the checkout is the filesystem's and the ACL's business, not the manifest's.
- **A source file that gains the executable bit still drifts.** That is the case the check exists for, and it is preserved.
