## Problem

O plugin só entrega payload de GitHub Pages, enquanto alvos Azure DevOps não têm caminho de publicação. Também não há preview local integrado para aprovar o site antes do handoff.

## Proposal

- Adicionar payload Azure Pipelines para publicação ou artefato de documentação e decisão explícita de destino no fluxo.
- Adicionar preview local sob confirmação ou servidor estático efêmero com URL no relatório.

## Out of Scope

- Provisionar ou configurar um serviço de hospedagem no Azure (Static Web Apps, Storage Static Website ou equivalente). O plugin deve entregar um artefato publicável e tornar o destino uma decisão explícita; credenciais, domínio e infraestrutura pertencem ao repositório alvo.
- Reorientar `docs_dir`, publicar outras homes do bundle, corrigir defaults do Zensical ou definir `site_url`. Esses contratos pertencem às specs S1/S2 do dossiê e são pré-requisito desta entrega.
- Manter um processo de preview residente, exposto fora de loopback ou versionar o diretório `site/`. O preview serve somente à revisão local e efêmera.

## Impact

- assets de CI Zensical
- comandos `build` e `produce` da família documentation

## Validation

- Fixture Azure DevOps valida sintaxe do pipeline e artefatos esperados.
- Preview é iniciado e encerrado de forma controlada, com URL relatada.

## Design

### Mapa de dependências

| Área | Papel na mudança | Se mudar sem esta spec |
| --- | --- | --- |
| `plugins/quenching/assets/zensical/ci-github-pages.yml` | único modelo atual de entrega CI | alvos Azure continuam sem payload compatível |
| `plugins/quenching/assets/zensical/README.md` | contrato instalado e instruções de validação | o novo payload ou preview ficam sem rota para o usuário |
| `plugins/quenching/commands/knowledge/documentation/build.md` | inventário, confirmações, aplicação, QA e relatório da camada do site | o fluxo continuará proibindo preview e ignorando Azure Pipelines |
| `plugins/quenching/commands/knowledge/documentation/produce.md` | orquestra o ciclo e seu handoff | o destino seguirá sendo descoberto tarde ou não será declarado |
| `plugins/quenching/commands/knowledge/align.md` | instala os payloads iniciais | novos alvos não recebem a opção Azure desde o primeiro alinhamento |
| `plugins/quenching-codex/skills/knowledge-documentation-{build,produce}/SKILL.md` | tradução distribuída dos corpos de comando | a superfície Codex diverge da fonte Claude |
| `plugins/quenching/tests/` | regressão de assets e tradução | templates ou contratos podem regredir sem evidência |

### Entrega portátil para Azure DevOps

O payload novo `assets/zensical/azure-pipelines-docs.yml` constrói o site com o toolchain declarado pelo alvo e publica `site/` como Pipeline Artifact nomeado `documentation-site`. Ele não presume serviço Azure, segredo, domínio, branch nem permissão fora da execução de pipeline. Assim, qualquer repositório Azure DevOps ganha uma URL de artefato navegável e um insumo estável para uma etapa posterior de deploy.

`build` inventaria a presença de `.azure-pipelines`/`azure-pipelines*.yml` e do payload instalado, além do workflow GitHub existente. Quando o remote aponta para Azure DevOps e não há rota de entrega, reporta um finding específico; a instalação do payload permanece uma confirmação própria, pois cria automação no alvo. `produce` pergunta no início qual é o destino pretendido e o registra no relatório: artefato de pipeline, deploy de infraestrutura já existente, ou nenhum. A ausência de destino é uma lacuna explícita, nunca um site declarado como publicado.

### Preview local controlado

`build` oferece preview apenas depois de o build estrito ter êxito e sob confirmação explícita. A implementação preferida é `zensical serve` ligado a `127.0.0.1` em porta disponível, com URL e PID informados; o comando encerra o processo quando a revisão acaba ou o usuário pede a interrupção. O relatório diferencia preview iniciado, encerrado, recusado e indisponível. Nenhuma execução de `produce` inicia servidor implicitamente: ela somente encaminha a escolha para `build` e registra o resultado.

A regra durável é: artefato de pipeline é a entrega padrão portátil; um deploy remoto só é configurado quando o destino, a infraestrutura e as credenciais forem declarados pelo alvo; preview nunca é um daemon nem uma evidência de publicação.

## Alternatives Considered

| Abordagem | Benefício | Custo ou limite | Decisão |
| --- | --- | --- | --- |
| **Artefato Azure Pipelines + decisão explícita de destino** | funciona em qualquer projeto Azure sem presumir infraestrutura e dá acesso ao site ao time | não cria URL pública por si só | escolhida — entrega uma rota concreta sem inventar credenciais |
| Deploy automático para Azure Static Web Apps | pode produzir URL publicada | exige segredo, recurso e convenções de cada alvo | rejeitada — configuração específica não pode ser deduzida pelo plugin |
| Deploy para Storage Static Website | baixo custo em alguns alvos | também exige conta, permissões e política de rede | rejeitada — mesma dependência de infraestrutura do alvo |
| Manter somente GitHub Pages | já existe como payload | é incompatível com o remote Azure medido no dossiê | rejeitada — preserva exatamente a lacuna encontrada |
| Servidor estático próprio no plugin | controle total sobre ciclo e porta | duplica o servidor do Zensical e amplia manutenção | rejeitada — `zensical serve` já satisfaz o preview local quando controlado |
| Preview automático em todo build | reduz uma confirmação | abre processo persistente sem intenção do usuário | rejeitada — o processo efêmero precisa de consentimento explícito |

## Open Decisions

- **Destino remoto padrão além do artefato.** A recomendação é não escolher um: o template sempre publica `documentation-site`; Static Web Apps ou Storage entram somente como etapa adicional do alvo. *Como se decide*: o operador do repositório informa infraestrutura, URL desejada e credenciais disponíveis ao aceitar o plano de `build`/`produce`.
- **Convenção de caminho e nome do YAML Azure no alvo.** A recomendação é oferecer `azure-pipelines-docs.yml` no payload e instruir o alvo a referenciá-lo pela convenção local, sem sobrescrever seu pipeline raiz. *Como se decide*: o inventário do `build` detecta a convenção existente; na ausência, a confirmação de instalação escolhe o caminho final.
- **Dependência S2 (`site_url`).** O artefato e o preview podem ser entregues sem URL canônica, mas uma publicação remota completa precisa da chave. *Como se decide*: concluir S2 antes de configurar deploy remoto; até lá o relatório marca a publicação externa como pendente.
- **Política de porta do preview.** A recomendação é loopback e porta dinâmica para evitar conflito e exposição de rede. *Como se decide*: a implementação prova que a URL só escuta em `127.0.0.1`; uma exceção de rede requer pedido explícito do usuário do alvo.

## Risks

- **O artefato é confundido com deploy público.** Mitigação: o relatório usa "artefato publicado" e "site externamente publicado" como estados distintos, e exige `site_url`/destino para o segundo.
- **O YAML instala dependências de forma incompatível com o alvo.** Mitigação: usar o `requirements.txt` já declarado pelo site e validar o payload em fixture; falhas de toolchain permanecem visíveis no job.
- **Preview fica órfão ou acessível na rede.** Mitigação: loopback obrigatório, PID relatado e encerramento controlado; o fluxo nunca inicia preview sem confirmação.
- **Os corpos Claude e as skills Codex divergem.** Mitigação: tarefas alteram ambas as superfícies e executam os testes/linters de tradução pertinentes.
- **S2 ainda não fornece `site_url`.** ACCEPTED — esta spec preserva a entrega por artefato e registra que deploy externo depende do pré-requisito, em vez de escrever URL fictícia.
