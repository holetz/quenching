## Problem

No Windows, com `core.autocrlf=true` (working copy CRLF, índice LF), `cq deploy --target . --check` e `--write` acusam como `edited` arquivos que o deploy escreveu e que ninguém tocou. Num checkout limpo de `main` (278c3255b, 7.11.1), `python quenching/assets/bin/cq deploy --target . --check` sai 1 com `edited .opencode/agents/quenching-spec-scout.md` e `edited .opencode/agents/quenching-spec-verifier.md` (`git ls-files --eol` mostra `i/lf w/crlf`). O manifesto `.agents/.quenching-deploy.json` guarda o sha256 dos bytes LF do blob, e o check compara com os bytes CRLF do disco.

Consequência medida no conclude autônomo da spec 2249 (2026-11-22), passo 7: o merge de `origin/main` conflitou só em `.agents/.quenching-deploy.json`. O procedimento de `quenching/skills/quenching-specs/references/conclude.md` §7 (tomar o lado da base com `git show :3:<path> > <path>` e depois `cq deploy --target . --write`) não roda no Windows por dois motivos: (1) no PowerShell, `>` grava UTF-16LE, e o deploy leu o manifesto como ausente (`installedVersion: null`, `refused: the target holds files no deploy manifest owns`); (2) com o manifesto correto, `--write` recusa com `refused: the target edited files the last deploy wrote`. O runner teve de improvisar: refazer o hash de cada entrada a partir dos blobs do índice (`git show :<path>`), à mão.

A melhoria precisa tornar impossível que um checkout limpo com autocrlf seja lido como editado (comparar normalizando EOL, ou hashear o blob do índice quando o arquivo está limpo no git), e o passo 7 do conclude precisa de uma forma da extração do lado da base que não dependa do redirecionamento do shell.

## Out of Scope

## Design

O defeito é de leitura: no Windows o checkout tem CRLF tanto na fonte (`quenching/`) quanto no alvo, enquanto o manifesto commitado guarda o sha256 dos bytes LF. Medido num worktree limpo da base: `cq deploy --check` lista 215 mudanças, em três famílias:

- `edited` nos arquivos traduzidos (lidos com `read_text`, que já entrega LF) e nos copiados: o disco CRLF difere dos dados e o hash do disco difere do registrado;
- `manifest` e `update .claude/skills/.generated-files.json`: os arquivos copiados com `read_bytes` entram na árvore com CRLF, e seus hashes não batem com os commitados;
- `mode .agents/quenching/bin/cq.cmd`: o Windows reporta bit executável por extensão.

Normalizar na entrada (`_add`) dá uma árvore igual ao conteúdo do índice em qualquer plataforma; comparar o disco pelo canônico absorve o CRLF do work tree. Os bytes escritos passam a ser LF; o git com autocrlf não vê diferença de conteúdo, e um arquivo já presente e igual módulo EOL não é reescrito.

### Assumptions

- Nenhum arquivo implantado precisa de CRLF no alvo (verificado: nenhum `i/crlf` em `quenching/`); um `.cmd` com LF já é como o índice o guarda. Depende disto: `## Proposal` item 1.
- `git checkout-index --stage=3 -f -- <path>` escreve o lado da base de uma entrada em conflito; é plumbing que não move HEAD nem reflog, e não é o `git checkout` proibido aos agentes. Depende disto: `## Proposal` item 3; a task 2.1 prova num repositório temporário.

## Alternatives Considered

| Abordagem | Custo | Ganho | Fecha |
| --- | --- | --- | --- |
| Canonizar EOL na árvore e comparar o disco pelo canônico (escolhida) | ~20 linhas em dois arquivos | checkout limpo nunca é `edited`, manifesto idêntico entre plataformas | CRLF intencional num arquivo implantado (não existe hoje) |
| Hashear o blob do índice (`git ls-files -s`) quando o arquivo está limpo no git | um subprocesso git por deploy | exato para o conteúdo commitado | alvos fora de git e arquivos sujos continuam errados; mais código |
| Exigir `.gitattributes` com `eol=lf` no alvo | uma linha por alvo | nenhum código | empurra o defeito para cada usuário Windows e não corrige a fonte |
| No conclude, ensinar o redirecionamento por shell (`Out-File -Encoding utf8`) | prosa por shell no corpo | nenhum código | aumenta o corpo e ainda corrompe não-ASCII no PowerShell 5 |

## Open Decisions

## Risks

- Um arquivo binário sem NUL e UTF-8 válido seria tratado como texto; mitigação: só CRLF vira LF, e o caso não existe na carga atual.
- Um alvo implantado antes por um deploy no Windows tem hashes CRLF no manifesto; mitigação: `_edited` aceita o hash cru ou o canônico, então a atualização não acusa edição.
- `checkout-index` lembra o `git checkout` proibido; mitigação: o §7 nomeia o comando exato, e a prova da task 2.1 mostra que HEAD e reflog não mudam.

## Handoff

Construída: 2/2 tasks. O deploy lê a fonte pelo `_read` (CRLF vira LF em texto) e compara o disco pelo canônico (`_same`, `_edited`); o bit executável não conta no Windows. O lançador `cq.cmd` continua gerado com CRLF de propósito. No Windows, `cq deploy --target . --check` sai 0 neste ramo. O conclude §7 usa `git checkout-index --stage=3 -f -- <path>`. Falta: conclude (gate do CI como prova; o gate local no Windows tem a linha de base de plataforma).
