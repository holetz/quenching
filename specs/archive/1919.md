## Problem

The opensource front has no explicit language contract for the community artifacts it writes or reports. A target using Portuguese conversation or artifact declarations can therefore receive inconsistent guidance when preparing its community surface for publication. The owner requested English for that surface on 2026-10-17.
## Proposal

- Declare `language: en` for every opensource template and expose that contract in status, doctor and apply independently of target language declarations.
- Require English prose in community artifacts and owner-supplied placeholder prose; apply warns about the latter without rejecting values or claiming to detect their language.
- Report README and SECURITY as hand-offs to their existing knowledge and security owners.
- Keep repository documentation and the general communication contract unchanged.
## Out of Scope

- Automatic prose-language detection or claims that metadata proves existing content is English: the communication standard explicitly rejects reliable machine identification.
- Translation, overwriting existing community artifacts, or changes to upstream template bytes and hashes.
- `docs/`, `knowledge:align`, general artifact language configuration and any transfer of README/SECURITY ownership.

## Impact

### Product code this spec expects to touch

- Opensource aggregate/apply, template source metadata, align command and its bands/catalog references.
- Opensource front tests and generated module/Codex mirrors of those source files.
## Validation

- `python3 -m unittest discover -s plugins/quenching/tests -p test_opensource_front.py` proves all templates declare English; a Portuguese-configured target receives a declared, unmeasured contract without a fabricated language finding; owner routing stays unchanged; apply warns for supplied values in dry-run and write while preserving substitution bytes and refusal behavior.
- `bash scripts/verify_repo.sh` exits zero, including generated mirrors.
- Preserve all upstream bytes/hashes and every general communication standard.
## Design

Epic 1961's owner decisions supersede the stale capture proposal: English is a declarative template/community contract, never a heuristic detector. Each `sources.json` template carries `language: en`. Status/doctor expose `artifactLanguage` with `language: en`, `basis: template-declaration`, `contentVerified: false`, and owner hand-offs for README/SECURITY. Artifact rows carry their template language without asserting actual content language.

Apply returns the selected template's `language` and `contentVerified: false`; supplied placeholders yield an informational `os-var-language-unverified` warning requiring English prose while accepting names, identifiers, URLs and owner values unchanged. The warning is declarative for every supplied placeholder because classifying prose would itself imply an unreliable detector. Align asks for English prose and reports residual target-language uncertainty as owner judgement, never as a new automatic finding. Existing-file refusal and template integrity remain unchanged.

## Alternatives Considered

- Stopword detection: rejected by epic decision because it cannot reliably establish language and would contradict the communication contract.
- Force English across `docs/`: rejected because this front owns community artifacts, not repository-wide documentation policy.
- Reject non-English-looking `--var`: rejected because names and identifiers are not reliably classifiable prose; warnings preserve owner choice.
