## Problem

O front de specs é provider-owned — uma spec É um GitHub issue ou um Azure Boards work item — mas a
identidade que a CLI e os treze comandos usam é um **slug** que o próprio plugin inventa
(`slugify(nome)`), grava dentro do documento (`slug:` no frontmatter) e repete no marcador do corpo
(`<!-- quenching-spec: <slug>.md -->`). O store já tem uma identidade — `#974`, `961489` — e ela é
ignorada. Como o slug só existe DENTRO do documento, descobrir qual issue é qual spec obriga baixar
o corpo de todas.

Medido contra este repositório em 2026-08-22, 154 spec issues, backend `github`: `cq specs status
--spec X` custa **3,81 s** porque baixa o tracker inteiro para achar uma spec; `cq specs list
--json` custa **4,82 s** e **5,25 MB**, dos quais 4,2 MB são corpos de spec contra 10 KB de títulos
— uma razão de **420:1** de bytes transportados sobre bytes úteis. O Azure já pagou esse preço com
um cache em disco `slug → work_item_id` que existe unicamente porque a identidade não é nativa; o
`github` não tem nem isso e relê o tracker inteiro a cada processo.

## Proposal

- **O ID nativo do backend é a identidade.** `read_spec(spec_id)` vai direto ao item: uma chamada,
  **0,39 s / 7,7 KB** contra os 3,81 s de hoje.
- **A resolução deixa de ser tolerante e passa a ser exata.** Os quatro degraus de `resolve_one` —
  slug exato, título exato, um match aproximado acima de 0,75, refusal — colapsam em um: o ID existe
  ou não existe. `sp-ambiguous-slug` deixa de ser alcançável **por construção**, porque dois specs
  não podem compartilhar um ID nativo.
- **A listagem ganha um modo enxuto que não transporta corpo nenhum.** Medido:
  `gh issue list --search '"quenching-spec" in:body' --json number,title,state,labels` devolve
  **as mesmas 154 specs, conjunto verificado idêntico, em 1,59 s e 70 KB**. O GitHub filtra o
  marcador server-side. No `azure-boards` o equivalente já existe — a WIQL filtra por
  `System.Tags CONTAINS '<discoveryTag>'` — e basta o batch parar de pedir `System.Description`.
- **O título absorve o papel do `summary:`, que sai do contrato.** Hoje **15 de 154 specs (9%)**
  têm `summary:` escrito, e **146 (95%)** já têm um título real. O título é nativo, já vem de graça
  em toda listagem, e a coluna `Summary` da tabela ranked já cai nele em 91% das linhas.
- **Nada é migrado.** As 154 specs existentes mantêm seu marcador com payload e seu `slug:` legado;
  o leitor tolera as duas formas e ignora o payload.
- **Em git a identidade aparece como número mais um handle cosmético** — `plan/974-citacao-pendurada`,
  `plan/974: 3.2 <task>`, `quenching-specs: 974,981`. Só o número é resolvido.

## Out of Scope

- **Promover `stage` e `complexity` a labels de valor** (`spec:stage:ready`, `spec:complexity:high`)
  para a listagem enxuta responder a tabela ranked inteira — oferecido ao humano e recusado nesta
  rodada. Codificar um struct num label é o que `spec-backend.md` §Rendering derived state proíbe, e
  a consequência aceita está registrada na linha abaixo.
- **`cq specs next --front --table` continua pagando a listagem completa.** `stage`, `tasks`,
  `priority` e `date` derivam do documento e não têm superfície nativa que os carregue. `--lean` não
  alimenta a tabela ranked, e isso vai declarado no payload em vez de ser descoberto.
- **Uma varredura das 154 specs existentes** para remover `slug:` e reescrever o marcador — recusada
  em favor de um leitor tolerante. Nenhuma spec é tocada.
- **Trocar a FORMA do argumento de cada verbo** — a assimetria atual (`new` posicional `name`;
  `section`/`record`/`promote`/`discover` posicional `spec`; `status`/`show`/`task`/`parallel` com
  `--spec` obrigatório) é preservada. Trocar a forma no mesmo passo que troca o significado dobraria
  a superfície de quebra sem comprar nada.
- **`cq specs find` continua O(N)** para branch e commit: os records vivem no documento, e nenhum ID
  nativo os torna alcançáveis sem lê-lo. Só o payload devolvido muda.

## Design

**A medição decidiu a forma, não o argumento.** Três alternativas foram medidas contra o
repositório real antes de qualquer decisão: a listagem de hoje (3,17 s / 5,25 MB), a leitura de uma
spec por ID (0,39 s / 7,7 KB) e a listagem enxuta por busca server-side (1,59 s / 70 KB, conjunto
idêntico verificado). É a terceira que dispensa toda migração.

**As primitivas continuam cinco**, o que preserva `spec-backend.md` §The interface is the document.
Duas mudam de assinatura e ambas ENCOLHEM: `read_spec(slug)` → `read_spec(spec_id)`, mesma forma com
implementação direta; e `create_spec(phase, filename, text)` → `create_spec(phase, text)`, porque o
`filename` existia apenas para alimentar o payload do marcador e sem payload não tem quem o consuma.

**O documento não carrega o próprio ID, e nada entra no lugar do `slug:`.** É a mesma regra que já
mantém `created_at` fora dele: um fato de que o store é dono não ganha espelho no documento. O
frontmatter obrigatório passa de `slug, title, date` para `title, date`.

**O recibo de resolução é retirado junto com a tolerância.** `resolvedBy`/`resolvedFrom` e
`read_one`'s announcement existiam para anunciar uma resolução aproximada; sem degraus aproximados
não há o que anunciar. `read_one` sobrevive como a porta única, e o teste estrutural
`EveryVerbAnnouncesThroughTheEmitter` muda de alvo em vez de ser retirado.

**A listagem enxuta é uma capacidade nova, nunca uma substituição.** `list_specs(phase, lean=False)`.
A listagem completa continua sendo o que `next --front`, `triage`, `validate` e `find` usam. O que
`--lean` entrega de graça, além de id/título/estado, são os records visíveis pelos labels `spec:*`
que já vêm na mesma resposta.

**O marcador volta a ter uma função só.** Ele existe para distinguir uma spec de uma issue qualquer
— um repositório pertence aos seus humanos, e um backend que tratasse toda issue aberta como spec
listaria os bug reports e depois escreveria por cima. Carregar a identidade era o segundo emprego
que o encarecia.

**Duas lacunas conhecidas fecham de carona**, porque a fase 4 já abre os mesmos arquivos: não existe
`cq git slugs --remove`, embora `execute-queue` e `fanout.md` exijam tirar da linha um spec
bloqueado; e `references/git/isolation.md` ainda carrega uma segunda implementação do mesmo
read-merge-write num bloco `python3 -c` inline, que `git/slugs.py` afirma ter absorvido.

## Alternatives Considered

- **Manter o slug e adicionar um índice `slug → id` em disco no `github`**, espelhando o que o
  `azure-boards` já faz. Resolveria a leitura de uma spec sem tocar em contrato nenhum, e foi
  rejeitada porque trata o sintoma: o cache existe PORQUE a identidade não é nativa, e mantê-lo é
  pagar para sempre por uma indireção que a mudança elimina. Não resolve a listagem, e deixa duas
  identidades convivendo.
- **Slug como alias de leitura** — o ID vira a identidade, tudo escreve por ID, mas um slug digitado
  continua resolvendo por um degrau extra. Rejeitada na decisão do humano: mantém a resolução O(N)
  viva indefinidamente e o custo nunca some de verdade.
- **Corte limpo COM varredura** das 154 specs, removendo `slug:` e reescrevendo o marcador.
  Rejeitada: a medição da busca server-side mostrou que o discovery funciona sobre o marcador antigo
  sem nenhuma reescrita, então a varredura compraria apenas limpeza estética ao preço de 154 PATCHes.
- **Um prefixo de tracker no identificador** (`gh-974`), útil se um repo apontasse para dois
  trackers. Rejeitada: mais verboso em toda linha de comando, para uma configuração que não existe.
- **Promover estado a labels de valor** para a listagem enxuta responder a tabela ranked inteira —
  ver `## Out of Scope`.

## Open Decisions

- **A latência do índice de busca do GitHub.** O índice é eventualmente consistente: uma issue recém-criada pode não aparecer em `--search` por alguns segundos. `create` não depende disso — o ID vem do POST — mas um `list --lean` logo em seguida pode não vê-la. **Como se decide:** medir a latência real contra este repositório durante a construção; se for material, `--lean` é declarado como a visão que pode atrasar e a listagem completa fica como a autoritativa.
- **Medição realizada em 2026-08-22:** a issue descartável `#991` apareceu no `gh issue list --search "quenching-spec" in:body` usado por `list --lean` no segundo poll, após `5.999s`; ela foi fechada após a medição. Essa latência é material: `--lean` é uma visão eventualmente consistente e a listagem completa permanece autoritativa.
- **Se `--lean` deve ser o default de `cq specs list`.** **Como se decide:** com a latência acima medida e com a coluna de records via labels já implementada — a resposta depende de quanto `--lean` consegue mostrar na prática, que só é observável depois da fase 2.
## Risks

- **Um alvo já instalado quebra no upgrade.** O argumento de todo verbo muda de significado e
  `cq specs summary` deixa de existir. Mitigação: a spec é `breaking` por declaração, e a retirada
  do verbo é anunciada na release — não há shim, porque um shim que aceita slug reintroduz
  exatamente a resolução O(N) que a mudança existe para eliminar.
- **O discovery por busca depende de um comportamento do GitHub que não é contratual.**
  `in:body` funciona hoje, medido, com conjunto idêntico — mas é search, não API de dados.
  Mitigação: a listagem completa permanece como caminho autoritativo e `--lean` é sempre uma
  otimização declarada, nunca a única forma de enxergar o front.
- **A varredura de prosa é ampla e mecânica** — 13 corpos de comando e sete famílias de reference,
  com `execute.md` (29 ocorrências), `develop.md` (28) e `execute-queue.md` (25) na frente.
  ACEITO — o risco é omissão, não corrupção, e `cq components lint` mais `cq knowledge validate`
  são o que mede a omissão.
- **Perder informação ao retirar `summary:`.** As 15 specs que têm um summary escrito passariam a
  mostrar só o título. Mitigação: o summary dessas 15 é lido e dobrado no título antes do campo
  sair, o que cabe folgado no teto nativo de 256 caracteres contra os 64 de título médio de hoje.
- **Esta spec nasce com um slug, e é a última que precisa de um.** ACEITO — a captura roda sob o
  contrato vigente, e a própria construção a converte.

## Outcome

Entregue. A identidade de uma spec é o ID nativo do backend — `989`, `961489` — e o slug saiu do
contrato inteiro: do frontmatter, do marcador do corpo, da resolução, dos treze comandos e da prosa.

**O que a spec prometeu e a medição confirmou**, contra este repositório e o tracker vivo:

- `cq specs status --spec <id>` custa **0,9 s**, contra os 3,81 s de uma varredura do tracker
  inteiro para achar um documento pelo slug enterrado em cada corpo.
- `cq specs list --lean --json` devolve **157 specs em ~2,0 s / 52 KB**, contra 4,82 s / 5,25 MB da
  listagem completa. O GitHub filtra o marcador server-side; no `azure-boards` a WIQL equivalente já
  existia.
- `cq specs list --json` continua reportando **as mesmas 157 specs**, e `validate --by-code` sobre
  elas devolve os **mesmos 9 erros** que o `main` devolve — nenhuma spec legada foi tocada, e o
  leitor tolerante é o que prova a decisão de não varrer. O `main`, aliás, só enxerga 139 delas: as
  specs já capturadas com o marcador sem payload são invisíveis para ele.
- `sp-ambiguous-slug` deixou de ser alcançável **por construção**: dois specs não compartilham um ID
  nativo, e os quatro degraus tolerantes de `resolve_one` colapsaram em "existe ou não existe".

**O que a revisão de branch encontrou e este run consertou.** A spec chegou ao conclude com as 29
tasks marcadas e a migração pela metade: a suíte tinha caído de 331 verdes para 60 falhas e cinco
dos oito verbos do CLI crashavam contra o backend real. `create_spec` ficou na assinatura antiga nos
dois backends externos enquanto o chamador já usava a nova, então `cq specs new` era `TypeError` em
produção; sete módulos de comando ainda liam `info["slug"]`; e `hybrid_title_split` ainda exigia
`slug` como primeira chave do frontmatter, o que desligou em silêncio a projeção do título nativo em
toda spec nova. Duas regressões de desempenho vieram junto: a leitura direta por ID transformou
`list --json` em 157 GETs individuais (78 s), corrigida fazendo a leitura reusar a listagem que o
processo já pagou. Tudo isso está em `plan/989: fechar a migração do slug para o ID nativo`.

**O que ficou de fora**, deliberadamente e por decisão registrada em `## Out of Scope`: promover
`stage`/`complexity` a labels de valor, migrar as 154 specs existentes, trocar a forma dos
argumentos de cada verbo, e `cq specs find` continuar O(N). A esses soma-se um item do
`## Validation` que **não foi executado**: o ciclo completo numa spec descartável, recusado por criar
uma issue de verdade no tracker. Os demais itens do `## Validation` correram verdes.

**Estado no fecho:** revisada, destilada, pronta para merge. 327 testes OK, `components doctor` e
`components lint` com zero erros, `cq knowledge validate` com zero erros.
**A ponte para `/.knowledge/`**, escrita nesta conclusão:

- `distilled:` [A direct read reuses the listing the process already paid for](/.knowledge/standards/architecture/spec-backend.md) — a leitura por ID nativo é a barata a frio e uma chamada desperdiçada a quente, com as duas medições que se contradizem (0,39 s numa spec; 4,82 s → 78 s em 157) e a distinção entre reusar uma listagem do próprio processo e confiar num cache entre processos.
- `distilled:` [A conditional projection's guard fails loudly, or it does not fail at all](/.knowledge/standards/code/conditional-projection-guards.md) — o guard que caiu no fallback "armazena inteiro" quando `slug:` saiu do frontmatter, e as três consequências: nomear a forma que o contrato escreve hoje, tolerar toda forma que o leitor tolera, e afirmar contra o artefato que o produto produz.
- `glossary:` **Provider ID** e **Cosmetic handle** entram; **Resolution receipt** sai com o par `resolvedBy`/`resolvedFrom` que esta spec retirou.

Nenhuma obrigação de release foi liquidada, por regra: `ci-cd/versioning-release.md` §When the bump
happens reserva o lockstep para o `cq specs release`, na branch primária, e proíbe expressamente que
