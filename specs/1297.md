## Problem

Neste repositório o store das specs é o branch git `quenching` (`cq specs config` imprime `backend: git`; os locators são `quenching:specs/<id>.md`; `origin/quenching` recebe os commits `specs: write <id>`), e `GitBackend.name` é `"git"` (`plugins/quenching/assets/bin/quenching/specs/backends/git.py:82`). Mesmo assim, `cq specs list --json` devolve `"backend": "github"` (medido em 2026-10-08), e `AGENTS.md:20` diz "The spec backend is GitHub". As issues do GitHub são a cópia de antes da migração.

Consequência: um agente que confia no payload ou no harness corrige a spec na issue do GitHub, que o `cq` não lê. Em 2026-10-08 a sessão condutora editou a issue #973 para tirar `title:` duplicado e o `validate` não mudou, até ela achar o store no branch e restaurar a issue.

## Proposal

- `cq specs list --json` (and every payload built by `front_fields`) reports the backend actually opened: `git` here, matching `cq specs config` and `GitBackend.name`.
- `AGENTS.md` says the spec store is the git branch `quenching`, with a pointer and no restated rules.

## Out of Scope

- Renaming the `backend` key or adding a `provider` key to the payloads: additive churn for installed targets with no consumer asking for it.
- Touching the GitHub issue copies that predate the migration.

## Impact

### Standards this spec will write into docs/standards/

- none — a payload value is corrected; no durable standard changes.

### Product code this spec expects to touch

- `plugins/quenching/assets/bin/quenching/specs/commands/output.py` — `front_fields` preferred `provider` over `backend`
- `plugins/quenching/tests/test_output.py` — regression test
- `AGENTS.md` — line 20

## Validation

- `cq specs list --json` reports `"backend": "git"` in this repo.
- The new unit test fails before the change and passes after.
- `bash scripts/verify_repo.sh` exits 0.

## Design

- Defect measured: `front_fields` returns `cfg.get("provider") or cfg.get("backend")`. `config._read_backend` sets `backend` to `git` when the store is the branch, while `provider` stays the host (`github`, from the remote), so the provider always won. The payload is not right by design: its docstring says the name "says which remote owns the canonical document".
- Rule: a workspace payload names the backend opened, `cfg["backend"]`; for external stores `backend` already equals the provider, so nothing else changes. Fall back to `provider` only if `backend` is absent.
- The Codex and specs-reader mirrors are generated from the Claude source by `scripts/sync_codex_plugin.py` and `scripts/sync_specs_reader_plugin.py`; never hand-edit them.

### Mapa de dependências

- `front_fields` is used by list, next, validate, doctor, epic and read commands; all inherit the fix. Mirrors in quenching-codex and quenching-specs-reader are regenerated.

## Alternatives Considered

- Document `provider` semantics and fix only AGENTS.md: rejected, the measured defect misled an agent into editing a store the tool does not read.

## Open Decisions

- none — the field's meaning is settled by `GitBackend.name` and `cq specs config`.

## Risks

- A consumer that read `backend == "github"` from payloads for the git store would now see `git`. ACCEPTED — the old value was the defect; goldens and the gate show any such consumer.
