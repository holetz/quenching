## Overview

- none — only `## Problem` is filled; nothing else exists yet to connect.

## Problem

When `/specs:execute` builds a spec, it reads the spec file from the checkout it happens to be
standing in — the current branch. But a spec that has been isolated into a worktree lives there
too, and that copy is the one the work is actually happening against: it carries the ticked boxes,
the discoveries and any section the executor has been updating on the branch.

Reading the main checkout's copy instead means executing against a stale view — boxes that are
already ticked in the worktree still look open, and a write lands in the wrong file.

`/specs:execute` should prefer the spec inside the worktree for that slug when one exists, and
fall back to the current branch only when it does not.
