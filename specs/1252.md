## Problem

`/quenching:git:branch` cria a worktree padrão como irmã do repositório (`git worktree add ../<repo>-<name>`, `plugins/quenching/commands/git/branch.md:60`), e o orquestrador usa o mesmo padrão (`/home/unicred/Projetos/claude-quenching-<id>`, `/home/unicred/Projetos/cq-wt/`). Fora do diretório do projeto, o harness do Claude Code devolve o cwd ao checkout principal depois de cada comando ("Shell cwd was reset to …"), então todo comando de um worker que não leva caminho explícito roda no checkout base. Nas orquestrações de 2026-10-07/08 isso apareceu duas vezes: o `/security-review` revisou o checkout base, com diff vazio, em 5 de 8 construções do épico 1192 (a 1210 contornou mirando a worktree), e no épico 1231 `cq components translate --write` sem `--root .` relatou 0 mudanças com a tradução Codex desatualizada, até os workers passarem `plugins/quenching/assets/bin/cq --root .`.

Consequência: num worker, qualquer ferramenta que dependa do cwd (o `cq` sem `--root`, skills que rodam `git diff`, testes) mede ou escreve o checkout errado em silêncio — resultado verde sobre a árvore que não mudou.

## Proposal

- `/quenching:git:branch` and `/quenching:specs:execute` state that after a worktree is taken, the harness may return the shell cwd to the base checkout after every command, so each later command in that worktree carries the worktree explicitly (`cd <worktree> && ...`, `git -C <worktree>`, `cq --root <worktree>`).
- The rule names the failure mode: a cwd-dependent tool measures the base checkout in silence and reports green.

## Out of Scope

- Changing the harness or the default worktree location (sibling `../<repo>-<name>`): the harness behavior is outside this repository, and moving the worktree inside the project would change `/quenching:git:branch`'s documented contract.
- Making `cq` detect a stale cwd on its own: deferred, it cannot know the intended checkout.

## Impact

### Product code this spec expects to touch

- `plugins/quenching/commands/git/branch.md` - step 4, the worktree form
- `plugins/quenching/commands/specs/execute.md` - the isolation return and the loop
- `plugins/quenching/assets/codex/` - regenerated Codex translation, if the gate reports drift

## Validation

- `grep -c "git -C" plugins/quenching/commands/git/branch.md plugins/quenching/commands/specs/execute.md` prints a non-zero count for each file (zero before the change for branch.md).
- `bash scripts/verify_repo.sh` exits 0.

## Design

A durable rule: any command that moves work into a worktree outside the project directory must tell the agent that the cwd is not durable there. The rule sits where the worktree is created (branch.md step 4) and where execution continues from it (execute.md), because those two are what a worker reads. The hook-target paragraph in execute.md already applies the rule to hooks; this generalizes it to every command.

### Mapa de dependências

- `plugins/quenching/commands/git/branch.md` - creates the worktree; cited by execute.md step on isolation.
- `plugins/quenching/commands/specs/execute.md` - continues from the worktree; its hook paragraph already carries the narrower rule.
- Codex translation under the plugin assets - derived from both bodies; must be regenerated (2026-10-08).

## Alternatives Considered

- Put the worktree inside the project directory so the harness never resets the cwd: rejected, it changes the documented `git worktree add ../<repo>-<name>` and risks nested-repo noise.
- Only fix the `/security-review` hook target: rejected, already done and the `cq` case from epic 1231 is the same root cause.

## Open Decisions

- none - the shape follows from the Problem and needs no human choice.

## Risks

- A longer body costs reading tokens on every load: mitigated by one short paragraph per file.
- The rule is prose, so a worker may still omit the path: ACCEPTED - the prose is the only lever this repository has.
