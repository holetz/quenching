## Problem

Os grants `Bash(git status:*)` e `Bash(git stash list:*)` do orchestrator (`agents/orchestrator.md:4`, `:72-73`) admitem filtro da config e `--output` (repro `review9/audit`).

Estreitamento: severidade baixa na fila.

Caminhos curtos: `agents/` e `commands/` sob `plugins/quenching/`; `git/`, `components/` e `specs/` sob `plugins/quenching/assets/bin/quenching/`.

## Proposal

Direção: a auditoria por onda por verbo `cq git` de argv fixo.

- Os dois grants saem do `tools:` do orchestrator e a auditoria por onda (`orchestrator.md:72-73`) passa a um verbo `cq git` de argv fixo.

## Out of Scope

- `Bash(git worktree list:*)` and `Bash(git for-each-ref:*)` stay in the orchestrator's `tools:`: neither takes a config-driven filter driver nor an `--output` flag in the position the grant admits, and the finding names only the two grants. Nearest lookalike: converting every read grant of the agent to `cq git`.
- The verifier's `cq git audit` is untouched; it already reads the worktree facts with a fixed argv.

## Impact

### Product code this spec expects to touch

- `plugins/quenching/assets/bin/quenching/git/state.py` — `cq git state` also reports the `stash` entries.
- `plugins/quenching/assets/bin/quenching/git/__init__.py` — the verb's help text.
- `plugins/quenching/agents/orchestrator.md` — the two grants leave `tools:`; step 6 reads `cq git state`.
- `plugins/quenching/tests/test_git.py` — the stash report and the grant guard.
- `plugins/quenching-codex/**` — regenerated translation.

## Validation

- `python3 -m unittest discover -s plugins/quenching/tests -p test_git.py` exits 0, including `test_reports_stash_entries` and `test_no_raw_status_or_stash_grant`.
- `grep -c "Bash(git status\|Bash(git stash list" plugins/quenching/agents/orchestrator.md` prints 0.
- `bash scripts/verify_repo.sh` exits 0.

## Design

- Reuse the existing fixed-argv verb `cq git state` (already runs with `audit.SAFE` and blanked `filter.<x>` drivers, takes only `--json`) and add a `stash` field, rather than minting a new verb: the orchestrator needs exactly status plus stash on the base checkout, and `state` already reports status. Alternative weighed: a dedicated `cq git wave-audit` verb; rejected as a second surface for one extra field.
- Durable rule: an agent that audits a checkout holds a `cq git` verb, never a raw `git <read>:*` grant, since a prefix grant admits `-c`/`--output` after the verb.
- `cq git state` takes no `--root`; the orchestrator runs it as `cd <base checkout> && cq git state --json`.

## Alternatives Considered

- Keep the grants and narrow them with a pattern: rejected, a command-text pattern cannot exclude `--output` or config-driven drivers (same finding as the verifier's earlier grants).
- A new `cq git wave-audit` verb: rejected, see Design.

## Open Decisions

- none — the Proposal fixes the direction and the evidence settles the verb.

## Risks

- A consumer of `cq git state --json` that rejects unknown keys breaks: ACCEPTED — the field is additive and the in-repo readers index by key.
- The orchestrator forgets `cd <base>` and audits the wrong checkout: mitigated by naming it in step 6.
