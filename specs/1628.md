## Problem

O épico 1627 quer separar o ciclo de specs das frentes de alinhamento, com a condição de que o conjunto
completo ligado não perca nada em relação a hoje. Três mecanismos do host tornam isso incerto e nenhum foi
medido para o caso de vários plugins quenching ligados juntos:

- **Namespace.** O nome do plugin é o prefixo do comando; um plugin `quenching-specs` troca
  `/quenching:specs:*` por outro nome em 10 corpos, nos `Not for:` cruzados de 58 comandos, nos 6 agentes
  (`quenching:orchestrator`…), no manual e na tradução Codex.
- **`${CLAUDE_PLUGIN_ROOT}`.** Só resolve no plugin que carrega o arquivo (`plugin-layout.md` §A mold cites
  nothing it does not also install). `align/tool-resolution.md` é citada por 9 corpos de `specs`, 7 de
  `components` e 4 de `knowledge`.
- **`bin/` no `PATH`.** O host acrescenta o `bin/` de cada plugin ligado; dois `cq` se sombreiam, motivo de o
  leitor se chamar `cq-specs-read`.

A linha de base a preservar: 35 comandos invocáveis pelo modelo somam 7.261 caracteres de descrição residente
(specs 1.481, git 1.408, knowledge 2.693, components 1.250); os 23 restantes já são
`disable-model-invocation`. Arestas de import fora de `common`: `git → specs` (7), `proof → ops` (2),
`components → session` (1).

O entregável é uma resposta, não código: em sessões frescas (`claude -p --plugin-dir`, uma por arranjo), medir
custo residente, roteamento por descrição, resolução de `cq` e de citações com 1, 2 e todos os módulos
ligados, para as formas candidatas (núcleo gerado por módulo; plugin base + dependentes; namespace mantido ×
renomeado). Sai com um ADR em `docs/decisions/` dizendo **go ou no-go**, quantos módulos, quem é dono do `cq`
e o destino do namespace. No-go abandona a onda 3 com a evidência.
