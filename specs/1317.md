## Proposal

Direção: verbo `cq git` de argv fixo que remove a worktree e apaga só branch mergeada (`-d`, nunca `-D`), roteado pelo orchestrator.

## Out of Scope

- Merging the PR with `--delete-branch`: `cq git pr merge` keeps its fixed argv (`--merge --match-head-commit`), because `gh` deleting the branch is a side effect the steward does not own.
- Deleting the remote branch: `cq git prune --remote-branch` already does it and stays the human's pick in `/quenching:git:cleanup`.
- `-D` or `worktree remove --force`: a dirty or unmerged worktree stands and the verb exits 1.
- Reworking `/quenching:git:cleanup` for the human: its steward step stays `blocked` when the prompt names no merged spec.

### Decisions

- **One verb, fixed argv: `cq git worktree retire --path <worktree> --branch <branch> --base <base> [--remote origin] --json`.** It is the Proposal's human decision: a `cq git` verb that removes the worktree and deletes only a merged branch, routed by the orchestrator. It lives under `worktree`, not `prune`, because `prune` acts only on what `cq git stale` reports and a live worktree is not an orphan.
- **Merged means reachable from the remote base.** The verb fetches `<remote>/<base>` (the local base when the remote is absent) and requires the branch tip to be an ancestor of it before touching anything. A PR merged through `gh` moves the remote base, not the local one.
- **Order: validate, `worktree remove`, `branch -d`.** The worktree goes first because git refuses to delete a branch checked out in a worktree. No `--force`, no `-D`: `branch -d` uses its own merge check, so if the local base is behind the branch stands and the verb exits 1 with git's message, the next `cq git prune --branch` finishing it once the base is updated.
- **Refusals (exit 2) before any write:** a name starting with `-` or not a valid branch; the path not registered; the path the primary worktree or the cwd's own checkout; the registered branch of that path differing from `--branch`; `--branch` equal to the base; the branch not an ancestor of the base.
- **The steward runs it from the base checkout** (never from inside the worktree being removed); its prompt names the step `cleanup`, the worktree path, the branch and the base. Without those it stays `blocked: needs-human`.
- **Routing.** The orchestrator hands the cleanup to `git-steward` only after the same steward's `merge` step succeeded for that spec's PR, since a spec whose PR stays open for the human keeps its worktree.

## Alternatives Considered

- Extend `cq git prune` with `--worktree` for live worktrees: rejected, it would void its "only what `stale` reports" contract.
- Merge with `gh pr merge --delete-branch`: rejected, it needs a raw `gh pr merge` grant the steward lacks, and it only works from the worktree, which deletes it under the caller.
- Give the steward `Bash(git branch -d:*)`: rejected, a pattern on command text is the exact hole the `cq git` verbs close.

## Open Decisions

- none — the Proposal fixes the direction and the Design settles the argv.

## Risks

- The local base behind the remote leaves the branch after the worktree is gone: ACCEPTED — exit 1 with git's message, the branch stands, nothing is lost, and `cq git prune --branch` finishes it after the base moves.
- A worktree with uncommitted work: `worktree remove` without `--force` refuses and the verb exits 1 with the worktree standing.
- A squash or rebase merge makes the tip not an ancestor: the verb refuses (exit 2) and deletes nothing; the steward returns `blocked`.
