## Problem

`cq git pr merge`: `--wait 540` (`agents/git-steward.md:43`) passa do timeout padrão de 2 min do Bash e o verbo só imprime no fim (repro: exit 124, 0 bytes); `skipping` conta como verde (`git/pull.py:24`); merge sem `--match-head-commit` nem `mergeStateStatus` (`:84`).

Consequência: "o CI certifica o gate" é mais fraco que a prosa.

Fonte: revisão de correção opus do épico 1289 (2026-10-08), item S4 da fila `.quenching/autopilot/2026-10-08/round1-queue.md`. Caminhos curtos: `agents/` e `commands/` sob `plugins/quenching/`; `git/`, `components/` e `specs/` sob `plugins/quenching/assets/bin/quenching/`.

## Proposal

A fila não traz direção para este item; a proposta abaixo sai dos três defeitos e é para confirmar no develop.

- A espera do `--wait` cabe no timeout do Bash que o steward usa (o steward passa um `timeout` explícito ou o verbo espera em fatias menores) e o verbo imprime progresso antes do fim, de modo que um timeout não devolve 0 bytes.
- Um check `skipping` não conta como verde quando é um check exigido do gate.
- O merge fixa o head lido (`--match-head-commit <sha>`) e lê `mergeStateStatus` antes de mergear.

## Out of Scope

- Squash, rebase, auto-merge or `--admin` merging: `cq git pr merge` stays `--merge` only (`pull.py` docstring); not a defect here.
- The Azure PR route: it lives in the `/quenching:git:pr:create` body and has no `cq` verb.
- Changing `WAIT_MAX_S` or the poll interval: the cap stays 540 for a caller with a longer timeout; the steward is what moves.

## Design

- **Wait fits the Bash timeout.** The steward calls `--wait 90` and repeats while `reason: pending` (the 30-minute ceiling is unchanged); the verb also prints one line to stderr before each sleep, so an overrun by any caller leaves output instead of 0 bytes. The verb keeps accepting up to 540.
- **`skipping` is green unless required.** When every bucket is pass or skipping and at least one is skipping, the verb asks `gh pr checks --required --json name`; a skipping check in that set yields state `skipped`, reason `skipped-required`, exit 1, and its name in `notGreen`. When `gh` cannot give the required list, every skipping check counts as required (fail closed). Assumption: `--required` lists the branch-protection checks; a repo with none keeps today's behaviour.
- **The merge pins the head.** The verb reads `headRefOid` before polling, and again with `mergeStateStatus` just before merging. It merges only when the head is unchanged and the state is `CLEAN` or `HAS_HOOKS`, passing `--match-head-commit <sha>`; otherwise reason `merge-state`, exit 1, with the observed values in `message`. `gh` itself rejects the merge if the head moves after the second read.

## Alternatives Considered

- **Raise the Bash `timeout` in the steward instead of shortening `--wait`**: rejected, the steward's grant does not fix a timeout argument and output would still arrive only at the end.
- **Treat every `skipping` as not green**: rejected, a conditional job skipped by a path filter would block every docs-only PR.

## Open Decisions

- Whether `UNSTABLE` (a non-required check failing) should be mergeable: left refused (only `CLEAN`/`HAS_HOOKS` merge); decided by the first autonomous run that meets it and reports `merge-state`.

## Risks

- A repo without branch protection reports `BLOCKED`/`UNKNOWN` states that refuse a legitimate merge: ACCEPTED — the refusal is explicit (`merge-state` with the message) and the human merges.
- `gh pr checks --required` exits 8 while pending and 1 with no required checks: handled by reading the JSON, not the exit code.
