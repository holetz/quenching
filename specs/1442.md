## Problem

O `--spec` do `cq git worktree add` deixou de recusar um branch com o id de OUTRA spec: `cq git worktree add --spec 1 --branch plan/2-beta …` sai `ok: true` e grava `work=plan/2-beta`, e a spec 2 também passa a ser dona do branch; o cq de 49ed50e2 recusava com `git-worktree-spec-head-mismatch` (`/tmp/claude-1000/-home-unicred-Projetos-claude-quenching/a284eb01-1fc3-4a7f-ae95-abf7651b3d1b/scratchpad/review16/wt1`). Onde: `plugins/quenching/assets/bin/quenching/git/pull.py:205-206`, `plugins/quenching/assets/bin/quenching/git/worktree.py:155`. Direção: recusar quando o nome casa `(?:.+/)?(\d+)-` com um id diferente; `feat/PROJ-77-x` segue aceito.

Origem: item D4 (baixa, regressão da 1432) da fila da rodada 8 do autopilot de 2026-10-08 (`.quenching/autopilot/2026-10-08/round8-queue.md`), da revisão de correção opus da rodada 7 (épico 1431).

## Proposal

- `cq git worktree add --spec <a> --branch <name>` refuses with `git-worktree-spec-head-mismatch` when `<name>` carries the id of a different spec (`(?:.+/)?(\d+)-` capturing an id other than `<a>`), even before the spec has a `branch.work` record.
- A branch whose name carries no leading numeric id (`feat/PROJ-77-fixture`) or carries the spec's own id stays accepted.
- A test beside the existing `worktree add --spec` tests fails without the fix and passes with it.

## Out of Scope

- Changing `cq git pr` behavior: it keeps `by_name=True`, which already requires the spec's id in the name.
- Resolving the other spec's ownership; only the cross-id refusal is restored.

## Impact

## Design

- In `_spec_vs_head`, when no `branch.work` record exists and `by_name` is off, `owned` is false if `re.match(r"(?:.+/)?(\d+)-", head)` matches an id different from `sid`; otherwise true. Rule: a branch name carrying another spec's id is never owned by this spec; a name with no numeric id is not a claim and passes.
- Alternative weighed: a check in `worktree.py` only. Rejected: the ownership rule lives in `_spec_vs_head`, and one place keeps `pr` and `worktree` coherent.

## Alternatives Considered

- Restoring the pre-1432 rule (name must start with the id): rejected, it refuses `feat/PROJ-77-x`, which 1432 deliberately admits.

## Open Decisions

- none — the direction is stated in the Problem and the evidence answers the shape.

## Risks

- A convention branch such as `release/2024-q3` would match `(\d+)-` with id 2024 and be refused for a spec that is not 2024. ACCEPTED — the direction in the Problem asks for exactly this pattern, and a numeric-led segment is indistinguishable from a spec id.
