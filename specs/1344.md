## Proposal

O reflog traz o sha antigo e o novo e o check 7 julga movimento, não mensagem. Depois do R3.

## Out of Scope

- Changing the audit payload shape (`reflog.branch` / `reflog.head` stay lists of strings) — the verifier already reads them; only the content of the entries changes.
- Running the audit on a wider set of refs than the branch and `HEAD` — not what the Problem names.

## Design

- Durable rule: check 7 judges **movement**, not message. Each entry carries the ref's new sha (`%H`); the next older entry's sha is the old one. An entry whose sha equals the older one moved nothing and is dropped whatever its message; any entry that moved the ref is kept.
- A moved entry with an empty message (`git update-ref <ref> <sha>` without `-m`) is kept under the placeholder `(no reflog message) <old12>..<new12>`, so the verifier sees the rewind. The oldest entry has no older sha and is always kept (the ref's creation).
- Vectors, one test each: (1) `update-ref refs/heads/<branch> <older>` without `-m` shows in `reflog.branch`; (2) `update-ref HEAD <older>` without `-m` shows in `reflog.head`; (3) `update-ref` to the same sha, with and without a message, stays out; (4) a moved entry with a message (`reset --hard HEAD~1`) stays, and the existing no-op reset test still holds.
- Alternatives weighed: keep the `reset:` special case and only stop dropping empty subjects — rejected, it leaves a moved-nothing entry with another message (e.g. `checkout`) as noise and keeps judging by text.

## Alternatives Considered

- Reading `git reflog` old/new shas with `--format=%H %gs` plus ancestry (fast-forward vs rewrite) per entry — rejected: the Problem asks for movement, and a fast-forward is already visible as a commit; the extra git call per entry adds failure modes under the fail-closed `errors` contract.
