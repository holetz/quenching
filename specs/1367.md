## Problem

`cq git pr record` (`plugins/quenching/assets/bin/quenching/git/pull.py:166-208`, conferência só por nome em `:183`) confia no `--head` declarado: `--spec 2 --head plan/2-qualquer --number 1351 --url …/pull/1351` → `ok: true`, e o `pr_states` do épico (`plugins/quenching/assets/bin/quenching/specs/commands/epic.py:29-45`) passa a ler um membro não mergeado como `done`. Junto: `cq git pr create --body -` publica um "-" literal (PR #1363, 2026-10-08).

Origem: item T3 da fila da rodada 3 do autopilot de 2026-10-08 (`.quenching/autopilot/2026-10-08/round3-queue.md`), da revisão de correção opus da rodada 2 (épico 1337).

## Proposal

Direção: conferir o head real da PR (gh/az) contra a branch da spec antes de gravar; `--body -` lê stdin.

## Out of Scope

- O `pr_states` do épico (`plugins/quenching/assets/bin/quenching/specs/commands/epic.py:29-45`) conferir sozinho o head da PR contra a branch do membro — é a defesa do lado do leitor; esta spec fecha a porta de escrita (`cq git pr record`), que é por onde o dado errado entra. Fica como linha de `## Discoveries`.
- Mudar o grant do `git-steward`, um hook, CI ou `allowed-tools` — o verbo já roda `gh`/`az` dentro do `cq`, nada precisa ser alargado.
- Tornar `--head` opcional em `pr record` (derivá-lo da PR) — muda o contrato do verbo citado em `plugins/quenching/commands/git/pr/create.md` §5; aqui ele continua obrigatório e passa a ser conferido.
- Documentar `--body -` no corpo de `/quenching:git:pr:create` — o corpo passa `--body "<body>"` e segue correto; nenhum espelho Codex é regerado.

### O head real em `pr record`

Depois de `_spec_vs_head` (que só confere o nome) e antes de `_stamp`, `_record` pergunta ao provedor qual é o head da PR, pela mesma rota de `_create` (`azure-boards` se `_provider()` diz isso, senão GitHub):

- GitHub: `gh pr view <--url> --json headRefName,number` — compara `headRefName == --head` e `number == --number`.
- Azure: `az repos pr show --id <--number> --detect=true --output=json` — compara `sourceRefName` sem o prefixo `refs/heads/` com `--head`.

Divergência → `refuse` (exit 2) com `code: git-pr-record-head-mismatch`, a mensagem nomeando o head real. Provedor que não responde ou JSON ilegível → exit 1 com `reason: head-unreadable` e a mensagem do `gh`/`az`, sem carimbar (o docstring do módulo já reserva o 1 para "`gh`/`az` refused"). Nada é gravado em nenhum dos dois.

### `--body -` em `pr create`

Em `_create`, antes de abrir a PR: `args.body == "-"` → `args.body = sys.stdin.read()`. Vale para as duas rotas (o GitHub manda por `--body-file=-`, o Azure por `--description=`). Corpo vazio depois da leitura segue a regra de hoje (GitHub envia vazio; Azure omite `--description`).

## Alternatives Considered

| Abordagem | Custo | Compra | Fecha |
| --- | --- | --- | --- |
| Conferir o head real na escrita (`pr record`) — **escolhida** | uma chamada `gh`/`az` por record | o record nunca nasce errado; o épico continua lendo só `state` | nada |
| Conferir no leitor (`pr_states` lê `headRefName` também) | uma chamada a mais por membro em toda leitura de épico; o épico precisa saber a branch do membro | defende contra records já errados | fica como discovery, não exclui a escolhida |
| Derivar `--head` da PR e tirar a flag | quebra o contrato citado em `create.md` §5 | um argumento a menos | a conferência de posse, que precisa de um head declarado para comparar com `branch.work` |

## Open Decisions

- none — a rota do provedor, o código de saída de cada falha e a leitura do stdin saem do próprio módulo (`_create`, docstring de `pull.py`); nada ficou sem evidência.

## Risks

- Uma PR aberta num fork tem `headRefName` sem o dono; a comparação por nome segue a mesma que `pr create` usa no `--head`, então o risco é o de hoje. Suposição: o fluxo deste plugin abre PR do mesmo repositório.
- `az repos pr show --detect=true` depende do `origin` apontar para o Azure; fora disso o provedor não é `azure-boards` e a rota cai no GitHub — igual a `_create`.
- Ler stdin quando nada foi redirecionado prende o processo; só acontece com `--body -` explícito, que é o pedido de ler.

## Handoff

- none — o comportamento é coberto pelos testes de `PullRequestVerbs`; não há validação de campo depois do merge.
