## Problem

Specs already store `start` and `target`, but dependencies exist only as `after:` between items of one epic, so there is no cycle-checked dependency graph across a backlog and nothing to draw a timeline from. Add dependencies between arbitrary specs, a cycle check in `validate`, and a derived schedule (dates, critical path, slippage) exposed as data for the PO's Gantt view.

Member S5 of holetz/forge epic 1 (Deliver the self-hosted AI-assisted development platform around Omnigent).

## Proposal

- A spec may declare the specs it depends on: a first-level `dependsOn: [2036, 2037]` frontmatter key (ids of this store), written only by `cq specs depends <id> [--add 12,34] [--remove 12] [--json]`, which is idempotent, refuses an unknown id, a self-reference and an edge that would close a cycle (`sp-dep-cycle`, nothing written), and prints the key when given no flag.
- `cq specs validate` checks the whole graph: `sp-dep-missing` (error: the id names no spec), `sp-dep-self` (error), `sp-dep-cycle` (error, naming the cycle path), and `sp-dep-dropped` (warn: depends on a spec archived with an outcome other than `done`).
- `cq specs schedule [--spec <id>] [--json]` derives, from the graph plus each spec's existing `start`/`target`, an ordered schedule as data: per spec its planned `start`/`target`, the derived `earliestStart`/`earliestFinish`, `slipDays` (derived finish minus `target`, only when positive), `critical` (on the longest chain), plus the `criticalPath` as an id list and the `cycle` when one exists. Exit 1 on a cycle, 0 otherwise. Nothing is written: the schedule is derived on every read and the PO's Gantt view consumes the JSON.
- The contract is written to `docs/standards/workflows/spec-dependencies.md`, indexed, and the verbs are listed in the specs-surface reference.

## Out of Scope

- Ranking: `cq specs next --front` and `next --epic` keep their current ordering and `after:` semantics; folding `dependsOn` into the four-factor rank is a follow-up.
- Epic membership: `after:` between items of one epic is unchanged and `dependsOn` never replaces it; the nearest lookalike is `epic add --after`, which stays the epic-local edge.
- Cross-repository dependencies (`owner/repo#id`): this store's ids only, because the foreign-store read of spec 2036 belongs to epic members.
- The portal's Gantt rendering and any tracker-native projection of `dependsOn`: this spec exposes data only.
- Capacity, calendars and working-day arithmetic: durations are calendar days between `start` and `target`.

## Design

**Storage.** `dependsOn` is a first-level frontmatter key beside `epic`, not one of `FIELD_KEYS`: no tracker has a native counterpart, so it is carried in the document and never projected (`schema.json` note, the `epic` argument). It is written as a flow list of ids (`dependsOn: [2036, 2037]`), which `parse_frontmatter` already reads back as strings; a scalar `dependsOn: 2036` is read as one id. The read tolerates a leading `#`.

**Purity.** `parse/deps.py` holds the whole derivation over a `{id: info}` map and never does I/O, like `parse/epics.py`: `deps_of(fm)`, `find_cycle(edges)`, `dep_findings(infos)` and `schedule(infos, ids)`. The commands only read through the backend (`list_specs` then `read_specs`) and print.

**The derivation.** Nodes are the open specs that declare or receive an edge plus their transitive dependencies (archived ones included, as fixed-point inputs). For each node in topological order: `duration` = days between its `start` and `target` when both are set, else unknown; `earliestStart` = the latest `earliestFinish` among its dependencies, never earlier than its own `start`; `earliestFinish` = `earliestStart` plus `duration`, or the node's own `target` when only that is set, else unknown. An unknown stays `null` and propagates as unknown, never as zero. A dependency archived `done` finishes at its `target` when it has one, else it constrains nothing. `slipDays` = `earliestFinish - target` when positive. The critical path follows, from the node with the latest known `earliestFinish`, the dependency that fixed each `earliestStart`. Dates are ISO strings and arithmetic is `datetime.date`.

**Cycle safety.** `find_cycle` is the same depth-first search shape `parse/epics.py` already uses; `depends --add` simulates the edge before writing, and `validate` reports a cycle that was hand-written. `schedule` on a cyclic graph reports the cycle and derives nothing.

## Alternatives Considered

| Shape | Costs | Buys | Forecloses |
| --- | --- | --- | --- |
| **A. `dependsOn` frontmatter key + pure derivation (chosen)** | one more optional key; no native tracker mapping | works on every backend, cycle-checked in one place, reuses `start`/`target` | tracker-side dependency links |
| B. Generalise epic `after:` to arbitrary specs | the edge would live in an epic document that must exist | reuse of the epic derivation | dependencies between specs of no common epic, which is the problem |
| C. A separate `deps.md` index document in the store | a second source of truth that drifts from the specs | one file to read | the edge travelling with the spec it constrains |
| D. Store the derived schedule in frontmatter | stale on the next edit | cheap reads | honesty: derived data must not be stored |

## Open Decisions

- Whether `next --front` should rank a spec with an unfinished dependency below ready ones: not decided here; decided by the follow-up that touches ranking, from how the PO uses the schedule once it exists.
- Whether working-day arithmetic is wanted: decided when a PO schedule shows a calendar-day error worth correcting; this spec assumes calendar days.
- Why now and what would make this not worth doing: the Problem states the missing graph and the Gantt consumer (epic S5 of holetz/forge epic 1); no further appetite evidence was available to this unattended pass, so it proceeds on the epic's own ordering.

## Risks

- A derived schedule read as a commitment: undated specs stay `null` and the standard says the output is a projection of `start`/`target`, never an estimate.
- A cycle hand-written into two documents makes `schedule` unusable: it reports the cycle and exits 1, and `validate` names it as an error.
- Generated mirrors drifting: task 3.2 regenerates them and runs the gate before the spec is concluded.
- Irreversibility: low — a new optional key and two read-mostly verbs; removing them leaves harmless frontmatter.
