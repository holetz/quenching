## Problem

O orchestrator lança um `spec-runner` só para o `stamp-pr` (`orchestrator.md:55`, `spec-runner.md:27`; piso medido ~31k tokens por spec), embora o `cq git pr create` já leia o número e a url do PR que abriu.

Toca `agents/orchestrator.md`, `agents/spec-runner.md` (S13), `agents/git-steward.md` (S4, S7), `git/pull.py` (S4) e `commands/git/pr/create.md` (S10); por isso é a última.

Fonte: avaliação do post sobre subagentes (2026-10-08), item S14 da fila `.quenching/autopilot/2026-10-08/round1-queue.md`. Caminhos curtos: `agents/` e `commands/` sob `plugins/quenching/`.

## Proposal

**Decidido pelo humano em 2026-10-08.** O `cq git pr create` grava o registro `pr` da spec com o número e a url que ele mesmo leu, e o orchestrator para de lançar um `spec-runner` só para o `stamp-pr` (`orchestrator.md:55`, `spec-runner.md:27`; piso medido ~31k tokens por spec). Nenhum grant novo de escrita de spec ao steward.

## Out of Scope

- A spec-write grant for the `git-steward` (`cq specs record`, `cq specs section`): the Proposal rules it out; the verb does the write, the steward's `tools:` line stays as it is.
- The Azure route: `az repos pr create` has no `cq git` verb, so `/quenching:git:pr:create` step 5 keeps stamping it with `cq specs record`.
- The `merge` record and the `merge` step of the steward: untouched.

## Design

- **Decision (the human's, 2026-10-08):** the verb that opened the PR writes the record, because it is the only party that read the number and url from `gh` itself. Rule: a record that is a git fact is written by the git verb that produced the fact.
- `--spec <id>` is optional on `cq git pr create`; without it nothing is stamped, as today. With it, after `gh` succeeds, the verb merges `number`, `url`, `date` (today) into the `pr` record through the specs `cmd_record` function (the same path `cq specs record` takes, so the schema validation is the same) and adds `"pr": {...}` to its JSON payload. The record is write-many.
- A failed stamp after the PR exists: the payload keeps `ok: true`-equivalent facts (`url`, `number`) plus `stamp: {ok: false, message}` and the exit is 1, so the caller reports the PR and the failure and never re-runs `gh pr create`.
- The steward's grant `Bash(cq git:*)` already covers the flag; no `tools:` change.

## Alternatives Considered

- Give the steward `cq specs record`: rejected by the human (Proposal) — a new write grant on spec state.
- Keep the spec-runner `stamp-pr` spawn: the cost this spec removes (~31k tokens per spec).

## Open Decisions

- none — the Proposal fixes the design; the exit code on a failed stamp is decided in Design above.

## Risks

- A stamp refused by the schema leaves a PR open with no record: mitigated by the `stamp` object and exit 1, which the steward returns as `blocked` with the message.
- Two prose copies (Claude and Codex) drift: mitigated by regenerating the translation in task 3.1.
