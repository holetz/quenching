## Problem

Na 465 (2026-11-25, worktree `quenching-slot-12`, execute autônomo) o `cq specs claim acquire 465` falhou duas vezes com exit 2: `error: git could not move refs/quenching/claims/465: error: failed to push some refs to 'https://github.com/holetz/quenching.git'`. O push manual do mesmo lease, com o argv que o `claims.py` monta, mostrou a causa: o commit do lease nasce com a identidade fixa `quenching <quenching@localhost>` (`quenching/assets/bin/quenching/specs/claims.py:29`, `IDENTITY`), e o pre-push do próprio repositório (leak gate, `scripts/githooks/pre-push`) a recusa: `commit 42e081d9d3ae (author):1: [email-not-allowed] quenching@localhost` — `leak gate (pre-push): 2 finding(s)`, exit 1. O push --dry-run e o push comum da branch passam, então o mecanismo de lease inteiro fica inoperante neste repositório e todo build roda sem reserva (o fluxo trata exit 2 como "sem reserva" e segue). A melhoria tem de fazer o lease empurrar num repositório que declara `shared.gitIdentity.allowedEmails`, sem abrir mão de o commit do lease não carregar a identidade do dono.

Correção mínima proposta: o leak gate (ou o `IDENTITY` do lease) trata o namespace `refs/quenching/claims/*` como isento da checagem de e-mail — a identidade sintética é o ponto do mecanismo, não um commit de trabalho.

**Insumos**

- `quenching/assets/bin/quenching/specs/claims.py:29` — `IDENTITY = {"GIT_AUTHOR_NAME": "quenching", "GIT_AUTHOR_EMAIL": "quenching@localhost", ...}`
- `cq specs claim acquire 465` — exit 2, `sp-claim-git`, mensagem citada acima; repetido duas vezes, 2026-11-25
- `git push --quiet --porcelain --force-with-lease=refs/quenching/claims/465: -- origin 42e081d9d3ae:refs/quenching/claims/465` — exit 1, `commit 42e081d9d3ae (author):1: [email-not-allowed] quenching@localhost`, `leak gate (pre-push): 2 finding(s)`
- `git push --dry-run origin HEAD:refs/heads/plan/465-...` — exit 0, `leak gate (pre-push): clean` (o push da branch passa; só o lease é recusado)
- spec 465, `/quenching-specs execute` step 2, 2026-11-25
