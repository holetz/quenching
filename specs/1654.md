## Problem

Quenching must always store canonical specs and epics on the `quenching` Git branch, but version 6.4.0 derives the backend from the repository remote when its host-specific configuration is absent: in Bricksmith, `cq specs config --json` reported `backend: github` and `present: false`, so autonomous execution created full specs in GitHub issues instead of the branch; the Codex translation also reads `.agents/quenching.json` while the Claude source reads `.claude/quenching.json`, causing the installed Codex CLI to ignore the Quenching project's existing `backend: git` declaration and report the deprecated tracker store.

Make the branch store mandatory for every host and entry point, with issues or work items serving only as optional projections, and realign existing projects when necessary by detecting and safely converting legacy tracker and checked-in planning documents, preserving identities, epic dependencies, tasks, lifecycle records, outcomes, evidence links and paused handoffs, verifying the converted store before removing obsolete copies and repairing references, and never silently falling back to a tracker backend when configuration or branch resolution fails.

## Discoveries

- Live migration evidence from Bricksmith: GitBackend._store_once currently adds push --no-verify, conflicting with the target harness that requires its leak gate; realignment must honor normal target hooks and fail closed, and normalize machine-specific paths without losing source history or lifecycle records before publishing the canonical branch. A process-local adapter that removes only --no-verify let the real pre-push gate reject the unsafe candidate; no branch was published on failure.
- 2026-10-17: reproduzido de novo em holetz/my-career (6.4.0). Sem .claude/quenching.json, config e list dão backend github e present:false, e o cq specs doctor fica em silêncio (findings vazio) porque doctor.py:92 testa o backend declarado, não o efetivo. O conserto estreito está na #1849.
