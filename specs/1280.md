## Problem

Duas lacunas do passo de branch num run autônomo com os agentes de `main` (re-revisão de 2026-10-08):

- **Nenhuma rota autônoma cria a worktree.** `agents/orchestrator.md:37` manda o passo `branch` ao steward, mas `commands/git/branch.md:58` pergunta via AskUserQuestion sem ramo `autonomous`, e `agents/git-steward.md:18-20` só repassa `autonomous` ao passo `pr`; pelo caminho do runner, `commands/specs/execute.md:105-108` cai na mesma pergunta, `agents/spec-runner.md:32-33` devolve `needs-human`, e `orchestrator.md:60-61` nunca relança isso.
- **A onda seguinte parte de uma base velha.** O orquestrador só libera o dependente depois do merge (`orchestrator.md:21-22`), mas o merge é `gh pr merge <url> --merge` (`git-steward.md:28`), que não atualiza ref local; nenhum agente roda fetch; `branch.md:60` corta a worktree a partir do HEAD do checkout base (o `main` local); e o check de base atrasada do `conclude` (`commands/specs/conclude.md:242`) compara com esse mesmo `<base>` local.

Consequência: o run para em toda spec sem worktree; e, quando anda, o dependente é construído, verificado e vira PR sem o código da dependência que esperou.

## Proposal

- Sob a palavra `autonomous`, `/quenching:git:branch` toma a forma Worktree sem **AskUserQuestion**, carimba o `branch:` como hoje e devolve o caminho da worktree.
- Sob `autonomous`, a worktree é cortada de `origin/<base>` logo após `git fetch origin <base>` (sem `origin`, do `<base>` local, dito no relatório), com `--no-track`; um `worktreeSetup` declarado não roda sem humano e sai no relatório como pulado.
- `/quenching:specs:execute` repassa `autonomous` ao `Skill("quenching:git:branch", …)` que já chama no passo 2, e o caminho do runner deixa de cair em `needs-human` por isolamento.
- O `git-steward` repassa `autonomous` ao passo `branch` (não só ao `pr`) e devolve a worktree numa linha `WORKTREE:` do seu formato fixo.
- O orquestrador manda o passo `branch` ao steward antes de lançar cada `spec-runner`, carregando `autonomous` quando o run carregou, e nomeia no prompt do runner a worktree devolvida; a onda seguinte, cortada depois do merge, parte do remoto e carrega o código da dependência.
- O check de base atrasada do `/quenching:specs:conclude` (passo 6) faz `git fetch origin <base>` e conta contra `origin/<base>` quando `origin` existe, de modo que um merge feito só no remoto não passa por zero.

## Out of Scope

- `agents/verifier.md` — a spec 1278 (grants do verificador, `cq git audit`) está aterrissando em paralelo; mexer nele colide sem ganho para estas duas lacunas.
- Atualizar o `main` local do checkout base (fetch + fast-forward) depois do merge — escreveria no checkout do humano, que o orquestrador audita como limpo e não é dono; o corte a partir de `origin/<base>` dispensa isso.
- Mudar o comportamento interativo de `/quenching:git:branch` (sem `autonomous`): o humano continua escolhendo a forma e o corte continua do `HEAD` local, que pode carregar commits locais ainda não publicados.
- Rodar `worktreeSetup` sem humano — o consentimento dele é a oferta de isolamento (`docs/standards/workflows/worktree-setup.md` §The consent is the isolation offer); fica em `## Open Decisions`.
- Atualizar a branch atrasada no `conclude` (merge ou `/quenching:git:sync`) — continua decisão do humano, `needs-human` sob `autonomous`.
- Republicar o plugin instalado (6.4.0): os agentes instalados não executam esta correção até o próximo release, que é do `/release`.

## Design

- **O `autonomous` é a pré-resposta do condutor, como em `/quenching:git:pr:create`.** A forma que ele escolhe é a recomendada pelo próprio `branch.md` (Worktree), a mais estreita que deixa o passo rodar; nada mais é concedido. Sem a palavra, o comando pergunta como hoje.
- **O corte sob `autonomous` parte do remoto.** `git fetch origin <base>` e `git worktree add <path> -b <branch> --no-track origin/<base>`; `--no-track` porque um upstream `origin/<base>` faria um push sem destino explícito mirar a base. Sem `origin` (padrão de `/quenching:git:sync` passo 2: `NO-REMOTE`), corta do `<base>` local e diz isso; erro de fetch para e é reportado, nunca vira "sem remoto".
- **O registro não muda.** `branch: {base, work}` continua carimbando o nome da base, não `origin/<base>`.
- **`worktreeSetup` não roda sem humano.** Suposição nomeada: o consentimento dele é a exibição verbatim na oferta, que sob `autonomous` não existe; o relatório diz `setup: skipped (autonomous)`. Este repositório não declara `worktreeSetup` (`cq specs config --json` → `null`).
- **Quem cria a worktree num run orquestrado é o steward**, porque o roteamento já manda `branch` a ele (`orchestrator.md:37`); a rota pelo `execute` (runner sem worktree) ganha o mesmo repasse como rede, não como caminho primário.
- **O `conclude` compara com a base remota sempre que há `origin`**, com ou sem `autonomous`: o PR é aberto contra o remoto, e é contra ele que "a branch carrega a base" tem sentido. O fetch só move refs de rastreamento remoto.
- Contratos que não podem ser contrariados: nenhuma escrita no checkout base (auditoria por onda, `orchestrator.md:62-64`); proibições de stash/checkout/reset dos agentes; `verifier.md` intocado.

## Alternatives Considered

- **Fast-forward do `main` local após o merge** (o steward rodaria `git fetch` + `git merge --ff-only` no checkout base) — perdeu: escreve no checkout do humano, que pode ter commits locais ou estar noutra branch, e a auditoria por onda o trata como intocável.
- **O orquestrador cria a worktree ele mesmo** — perdeu: ele não tem `git worktree add` nem `cq specs record` nas grants e por desenho nunca escreve; o roteamento já dá o passo `branch` ao steward.
- **Cortar sempre de `origin/<base>`, também no modo interativo** — perdeu: muda o comportamento do humano, que pode querer cortar de commits locais ainda não publicados; fica restrito a `autonomous`.
- **O runner adota a branch sem worktree (`In place`)** — perdeu: dois runners paralelos no mesmo checkout base colidem, e a auditoria exige o base limpo.

## Open Decisions

- Se um `worktreeSetup` declarado deve rodar sob `autonomous` — decidido pelo humano na revisão deste PR; até lá não roda e é reportado como pulado.
- Se o `/quenching:git:branch` interativo também deve oferecer o corte a partir de `origin/<base>` — decidido quando um humano relatar base velha num fluxo sem orquestrador; nenhuma evidência hoje.

## Risks

- O `autonomous` vazar para o caminho interativo e criar worktree sem consentimento — mitigação: o ramo é condicionado à palavra literal no input, como em `pr:create`, e o steward só a repassa quando o prompt a carrega.
- Uma worktree criada sem `worktreeSetup` falhar no gate por falta de dependências — ACCEPTED — o run devolve `failed` com o gate citado, melhor que rodar um comando arbitrário sem humano; este repo não declara setup.
- Fetch falhar (rede, credencial) e o corte cair no local velho em silêncio — mitigação: erro de fetch para o passo e é reportado; só a ausência de `origin` cai no local, e é dita.
- `--no-track` omitido e o push mirar a base — mitigação: a flag está no comando do corpo e na `## Validation`.
- Os agentes instalados (6.4.0) continuarem com a lacuna até o release — ACCEPTED — release é do `/release`, fora desta spec.
