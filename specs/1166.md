## Problem

Na sessão anterior o backend GitHub devolveu vários HTTP 500; toda escrita só passou com nova
tentativa manual. Em `plugins/quenching/assets/bin/quenching/specs/backends/github.py`:

- `_gh_run` repete só leituras: `max_attempts = GH_MAX_ATTEMPTS if reads else 1` (linhas 156-159).
  `_gh_transient` já reconhece 429/500/502/503/504 (linha 94), mas `_gh_is_read` (100-118) classifica
  todo `-X PATCH/PUT/DELETE` como escrita. Quase toda escrita do fluxo é um PATCH idempotente do
  corpo inteiro (`_store`, 863), de estado (`_set_state`, 945), de comentário de continuação (1032),
  ou um `gh issue edit --type` (960). Só o POST de criar issue (907) e de criar comentário (1035)
  não são idempotentes.
- Num 500, o chamador recebe `sp-gh-api-error`, exit 2, `attempts: 1` (245-249). O spec-runner é
  instruído a "ler, nunca repetir às cegas" o exit 2 (`agents/spec-runner.md`, §How you work).
- `cq specs new` faz o POST (907) e depois `_set_type` (921), `_sync_parts` (929), `_set_state` (933).
  Uma falha nesses passos recusa **sem o número da issue já criada**. O retry cego duplica: já
  aconteceu, com 36 issues para 12 specs em 2026-09-02 (memória do projeto). `commands/specs/create.md`
  não traz a regra de buscar pelo título antes de retentar.
- Uma spec com várias partes recebe primeiro o PATCH do head (que declara N partes) e depois os
  comentários (1028-1036). Um 500 no meio deixa o head declarando partes que não existem, e a leitura
  recusa com `sp-gh-parts-missing` e a mensagem falsa "a continuation comment was deleted" (998-1005).
  Com a contagem de partes inalterada, o head novo fica com uma parte velha **sem recusa**.
- `promote --outcome` grava o outcome (`write_spec`) e depois o `move_spec` (PATCH de estado), sem
  avisar que a primeira etapa foi aplicada se a segunda falhar (`specs/commands/promote.py:~125`).

Consequência: cada 500 transitório vira trabalho manual de retry; um retry ingênuo duplica issues;
uma falha no meio de uma escrita multi-parte pode corromper o corpo de uma spec grande.

## Proposal

- A write that is idempotent by construction (PATCH, PUT, DELETE and `gh issue edit`) is retried with the same bounded backoff reads already get, so a transient 429/500/502/503/504 no longer surfaces as `sp-gh-api-error` with `attempts: 1`.
- A POST (create issue, create comment) is still sent exactly once.
- `create_spec` failing after the POST landed refuses with the created issue number and URL in the refusal, and says not to run `new` again.
- `sp-gh-parts-missing` no longer claims only that a comment was deleted; it also names an interrupted multi-part write as a cause.
- `promote --outcome` whose `move_spec` fails says the outcome was already written.
- `commands/specs/create.md` tells the executor to search by title before retrying a failed `cq specs new`.

## Out of Scope

- Reordering the multi-part write (head first, comments after). A different order trades one inconsistency for another; retrying the PATCHes shrinks the window, and the refusal now names the cause. Deferred.
- Retrying POST. A timeout can fire after GitHub accepted it, so a blind second POST duplicates; ruled out.
- The Azure Boards backend and the `files` backend.
- Changing `agents/spec-runner.md`: its "exit 2 is read, never repeated blindly" rule stays correct once transient writes retry inside the transport.

## Design

- Rule: only calls that are safe to repeat are repeated. `_gh_is_read` stays the read guard (it also drives the read-only transport refusal); a new `_gh_is_idempotent` returns true for reads, `-X PATCH|PUT|DELETE` on `gh api`, and `gh issue edit`. `_gh_run` uses it for `max_attempts`. The read-only refusal keeps using `_gh_is_read`.
- Rule: DELETE counts as idempotent here; a repeated DELETE that already succeeded answers 404, which is non-transient and is reported as before.
- Rule: a multi-step create must never lose the identifier of what it already made. `create_spec` wraps the steps after the POST, and on a `BackendRefusal` adds `issue`, `url` and a remedy to the refusal dict before re-raising.
- Rule: a refusal for the second step of a two-step command names the first step as applied (`promote`).
- The backoff stays `GH_RETRY_BACKOFF` and the cap `GH_MAX_ATTEMPTS`; no new knobs.

## Alternatives Considered

- Retry every write including POST, deduplicating by title afterwards: rejected, it moves the duplicate problem into cleanup and needs a listing per retry.
- Leave the transport alone and only document manual retry: rejected, it is today's behaviour and the cost the spec names.

## Open Decisions

- Whether to reorder the multi-part write (comments before head). Decided by measuring, after this ships, whether `sp-gh-parts-missing` still occurs.
- Why now / what waiting costs: the Problem states repeated manual retries and a past 36-for-12 duplication; the pass assumes that is sufficient.

## Risks

- A PATCH retried after a timeout that GitHub actually applied: harmless, the body is whole-document and idempotent; ACCEPTED.
- A conditional write (`updated_at` guard) retried could conflict with its own first success. Mitigation: read `_store` while implementing; if the PATCH carries a precondition, a stale-write refusal stays a refusal, and a test pins it.
- Longer wall time on a persistent outage: at most two sleeps of 0.25s and 0.5s per write; ACCEPTED.
