## Problem

O passo `branch` do steward não carimba `branch:`: desde a 1365 o steward não tem `cq specs record` (`plugins/quenching/commands/git/branch.md:19`), e o registro depende de o worker carimbar na adoção do execute (`plugins/quenching/commands/specs/execute.md:82-89`). A 1410 terminou sem `branch:` (transcript `agent-a1553217d1a562538.jsonl`: "I skipped the `branch:` record stamp"), e o conclude não carimbou `reviewed`. Direção: `cq git worktree add --spec <id>` carimba `branch:` como o `cq git pr create --spec` carimba `pr` (decisão B do humano).

Origem: fila da rodada 6 do autopilot de 2026-10-08 (`.quenching/autopilot/2026-10-08/round6-queue.md`), item P2, da auditoria do condutor sobre a 1410 (épico 1403).

## Proposal

`cq git worktree add` ganha `--spec <id>` (opcional). Com ele, depois de cortar o worktree, o verbo carimba `branch: {base, work}` da spec pelo mesmo `cmd_record` que `cq git pr create --spec` usa para o `pr`, e o passo 4 de `/quenching:git:branch` deixa de carimbar `branch:` por conta própria. O carimbo deixa de depender de o worker lembrar de carimbar na adoção do execute (decisão B do humano, épico 1418).

## Out of Scope

- `cq git specs <branch> --add` (a marcação `quenching-specs:`) segue como está, em passo próprio.
- O carimbo na adoção de branch já existente (`execute.md:82-89`) segue, como rede de segurança para branches que este verbo não cortou.
- Nenhum alargamento de grant, hook ou `allowed-tools`: `Bash(cq git:*)` já cobre `cq git worktree add --spec`.

## Impact

- `plugins/quenching/assets/bin/quenching/git/worktree.py`: `_add` valida a spec e carimba `branch` depois do corte.
- `plugins/quenching/assets/bin/quenching/git/__init__.py`: o argumento `--spec`.
- `plugins/quenching/tests/test_git.py`: testes ao lado dos de `WorktreeAdd`.
- `plugins/quenching/commands/git/branch.md`: o passo 4 passa `--spec` e não carimba mais.
- Espelhos gerados: `plugins/quenching-codex/scripts/bin/quenching/git/worktree.py`, `.../git/__init__.py`, `plugins/quenching-codex/.generated-files.json`.

### Standards this spec will write into docs/standards/

## Validation

`python3 -m unittest discover -s plugins/quenching/tests -p 'test_git.py'` passa, com os novos testes de `worktree add --spec`; `bash scripts/verify_repo.sh` sai 0.

## Design

`_add` aceita `args.spec`. Antes de qualquer escrita, se `--spec` veio, a spec precisa resolver (`git-worktree-spec-unknown`, exit 2, nada cortado), reaproveitando `read_one`/`open_backend` como `pull._spec_vs_head`. Depois do `worktree add` e do link, `_stamp_branch(spec, base, work)` chama `cmd_record` com `base=<base>` e `work=<branch>`, no padrão de `pull._stamp`, e o payload ganha `branchRecord: {ok, value|message}`. Uma falha do carimbo não desfaz o worktree: sai exit 1 com `ok: false` e a mensagem, como o `linkRefusal`. O `base` é o `--base` recebido, fato observado do corte.

## Alternatives Considered

- Manter o carimbo no passo 4 do `branch.md` (status quo): é o que a 1410 mostrou falhar, porque o steward não tem `cq specs record`.
- Alargar o grant do steward para `cq specs record`: alarga permissão, vetado pela política da rodada.

## Open Decisions

- none — a decisão B do humano fixa a direção; o desenho segue o padrão do `pr create --spec`.

## Risks

- A `branch` é write-once por contrato? Se `cmd_record` recusar um segundo carimbo, o verbo reporta a recusa sem desfazer o worktree; o teste cobre o caso.
- Chamar `cmd_record` do worktree.py cria import novo de `quenching.specs`; mitigado por seguir o mesmo import de `pull.py`.
