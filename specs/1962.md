## Problem

Caso real, 2026-10-18. Uma auditoria de perfil público do dono achou, no próprio `quenching` (público), o nome da organização do Azure DevOps do empregador num fixture de teste. A varredura seguinte achou variantes do mesmo nome, o nome do projeto, o nome de um time e o de uma vertical do empregador. Estavam em comentários de código (nas quatro cópias geradas do plugin), em dois docs do bundle e em fixtures de `tests/test_specs_azure.py`. Os valores não estão aqui de propósito: esta spec é pública. A remediação local está guardada no stash `anonimizacao-identificadores-empregador`.

`cq opensource readiness` não pegaria nada disso. A classe `internal-identifiers` só procura sufixos de host internos e faixas IPv4 privadas, mais os endereços de autor e committer. Ficam quatro lacunas:

1. **Tenant em URL de SaaS.** Um nome de organização ou tenant dentro de uma URL pública de SaaS (`dev.azure.com/<org>`, `<org>.visualstudio.com`, `<tenant>.sharepoint.com`, `adb-<id>.azuredatabricks.net`, org privada no GitHub) é identificador interno, mas o host é público, então o filtro de sufixo não o vê.
2. **Termos que só o dono conhece.** Nome do empregador, de cliente, de time, de vertical e codinome de projeto interno nenhum padrão genérico encontra. O dono precisa poder declará-los sem que a lista entre no repositório.
3. **Proveniência.** Um repo pode derivar de um projeto do empregador, desenvolvido em sala limpa (só conhecimento, sem cópia de código). É um fato legal que só o dono atesta, como `history-consent`, e o readiness não tem classe para ele.
4. **Repo já público e coerência da vitrine.** O readiness é pensado para antes da publicação, mas o dono tem vários repos já públicos e quer alinhar todos eles. Nenhuma frente confere se o que o repo diz de si bate com o forge. Exemplo real: um README diz "Private repository" num repo público. Outro: repo público sem descrição nem topics.
## Proposal

Rascunho da visão de quem usa a frente para manter vitrine de carreira; o `develop` decide.

- **Tenants de SaaS em `internal-identifiers`**: uma lista pinada em `assets/` de padrões de URL com tenant (Azure DevOps, visualstudio.com, SharePoint, Databricks, Snowflake, Atlassian e afins). Ela casa o segmento do tenant em HEAD e no histórico e reporta só o local (`opaque:` quando for o caso), nunca o valor.
- **Denylist do dono**: `--denylist <path>` aponta um arquivo **fora** do target com os termos sensíveis, um por linha. O path dentro do target é recusado, como `pr-scratch-inside-target`. A busca é por palavra, sem diferenciar maiúsculas, em HEAD e no histórico. O achado `pr-owner-term` é blocker e traz só o local, nunca o termo. Sem `--denylist`, a classe fica `not-measured` em vez de limpa.
- **Classe `provenance`** no evidence file: `{"provenance": {"state": "original|clean-room|derived", "reviewedBy": "..."}}`. `derived` vira blocker até haver licença ou autorização; `clean-room` e `original` passam com revisor; a ausência é `not-measured`.
- **Advisories de vitrine** (provider, `info`): descrição ausente, topics ausentes e afirmação de visibilidade no README que contradiz o forge (`pr-visibility-claim`).
- **Modo portfólio**: readiness, só leitura, sobre todos os repos públicos de um dono (`gh repo list <owner> --visibility public`), com uma tabela por repo e o agregado. É o caminho de "alinhar todos os meus projetos".
- **Primeiro alvo**: aplicar a remediação do stash neste repo pelo fluxo do align, com regeneração dos espelhos (`ct-manifest-drift` apareceu no gate com as cópias editadas à mão).
